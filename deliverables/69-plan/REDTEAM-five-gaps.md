## A. 「提示词真的能产出该风格」

### A1 到底是 1/30 还是 0/30？——都不是，是"验证已失效"

Lead 的依据是"那次验证用的提示词含 `#4A5C3A`，而当时的 `buildPrompt('S19')` 没有这个色"。**我独立核实：现在有。**

```
buildPrompt('S19') 现在含 #4A5C3A : true
当前调色板行：#4A5C3A（green）、#E4DECD（paper）、#D8CFB6、#E9E3D2、#2A241C、#3A3227、#7C7460
S19 style.css :root 实际声明 14 色，提示词点名 7 色 + 1 个反向禁令 #6366F1
```

`git log -S"4A5C3A" -- prototypes/_selection/prompts.js` → 由 `cea8436`「修提示词的正确性：7 个 Agent 审出的 P0，30 案圆角/字体/主色/线宽全修」引入。**所以 Lead 的"0/30"依据在 HEAD 上已经不成立。**

**但是**，把当前 `buildPrompt('S19')` 与当初真正验证过的那份（`deliverables/99-scratch/prompt-s19.md`）逐条对照，**19 个可探针的约束里只有 14 个两边都在，5 个分歧**：

| 约束 | 当前 buildPrompt | 验证过的那份 |
|---|---|---|
| 标题字体 `Spectral` | **缺** | 有 |
| 本案风格名（"S19 铜版标本柜"） | **缺**（只说"这个风格"） | 有 |
| 5 个抽屉按 `3+2` 两行 | **缺** | 有 |
| 检索号 `B-01-001` 三段式贯通 | **缺** | 有 |
| 「只有 3 个豆怎么收」收敛规则 | **缺** | 有 |

**这才是真问题**：验证过的那份是**手写的、带本案专有结构的**（1165 字里点名 `Spectral`、`B-01-001`、`3+2` 分栏）；当前 `buildPrompt` 是**通用模板 + 本案 DNA**，它能保证"像这个风格"的**质感**（色/字/圆角/阴影/线宽），但**不再保证"是这个版式"**（抽屉数、编号贯通、收敛规则）。

**判决：A1 的"1/30"和"0/30"都在争一个失效的证书。** 准确说法是：**验证过的是另一份提示词，当前这份没验证过；且当前这份在"版式可复现性"上比验证过的那份弱 5 条。**

### A2 这个问题能回答吗？——不能，除非先定义"通过"

一份提示词喂给 GPT-4o / Claude / v0 / 本地模型，产出必然不同。**"验证通过"至少有三个互不相同的定义**，而三个定义给出三个不同答案：

1. **约束合规**（色值/字体/圆角/阴影/线宽对不对）→ 可机械判定，**这正是 A5 能 30/30 覆盖的那层**。
2. **风格可辨识**（拿远半米像不像那个风格）→ 需要人判或判官模型，**主观且不可复算**。
3. **版式可复现**（抽屉数、编号贯通、分栏比例）→ 可机械判定，但**当前提示词有 5 条缺失**（见 A1）。

**30 案的提示词有 42.3% 的字完全相同**（31 句 boilerplate，767 字），只有 **57.7% 是本案独有**。这意味着"风格"活在一个很薄的切片里，而 LLM 的采样方差**足以淹没这个切片**。

**判决：A2 的前提不成立。** 不是"没验证"，是**"验证"这个词在这里没有可操作的定义**。正确提法是："在模型 M、温度 T、采样 k 次下，约束合规率是多少"——这才可复算，也才可推广。

### A3 3/30 能推广吗？——统计上几乎不能

精确二项（Clopper-Pearson，单侧 95%）。`x=n` 全过时下界有闭式解 **`p_lo = 0.05^(1/n)`**：

| 观测 | 点估计 | 95% 置信下界 |
|---|---|---|
| **3/3 全过** | 100% | **36.8%** |
| 5/5 全过 | 100% | 54.9% |
| 10/10 全过 | 100% | 74.1% |
| 20/20 全过 | 100% | 86.1% |
| **29/29 全过** | 100% | **90.2%** |
| 30/30 全过 | 100% | 90.5% |
| 59/59 全过 | 100% | **95.0%** |

- 要证明**通过率 ≥90%**（95% 置信），需要 **29 次连续全过**。
- 要证明 **≥95%**，需要 **59 次**。
- 要证明 **≥99%**，需要 **299 次**。

**3/3 全过只把"通过率 ≤36.8%"这个假设排除了。** 换句话说：3 个全过**连"比抛硬币好"都证明不了**——若真实通过率是 50%，3/3 全过的概率是 12.5%，**完全不显著**。

若用均匀先验做贝叶斯外推：3/3 后验是 Beta(4,1)，**下一案通过的概率 0.80，30 案里期望通过 24.6 个，30 案全过的概率只有 0.24%**。

**判决：A3 前提成立（样本量确实不够），但比用户以为的更严重——不是"3 个不够"，是"3 个什么也证明不了"。** 而且**验 29 个的成本**（每案要真跑一次 LLM + 一次机械判定）远高于 A5 的 30/30 自洽性检查。

### A4 子 Agent 手写 ≈ 真 LLM 吗？——不，且偏差方向已知

- **子 Agent**：读提示词 → 理解约束 → 手写 HTML。它对"不得用 `#6366F1`"这类**显式禁令**会**忠实执行**（因为它真的读了）。
- **真 LLM**：下一 token 采样。它**倾向走训练分布的高频路径**——圆角卡片、居中大标题、三条 feature、紫蓝渐变，**正是提示词里那 8 条"防退化"要挡的东西**。

两条路径的失败模式**不同**：子 Agent 更容易犯"结构对但不好看"，真 LLM 更容易犯"好看但滑向 AI 味"。**用子 Agent 验出来的通过率是上偏的。**

`deliverables/62-verify/impl/` 里确实有 `S07.html` / `S23.html` / `S30.html` 三份实现（19.4KB / 19.7KB / 15.9KB），配 13 张占位图——**但那是子 Agent 手写的，不是真 LLM 产出**。这三份的存在**不能**当作"3/30 端到端验证"的证据。

**判决：A4 前提不成立。** 子 Agent 验证是**低成本冒烟测试**（能抓"提示词自相矛盾"），**不是**端到端验证的替代品。

### A5 更便宜的替代？——有，实测 30/30 可覆盖

我跑了**提示词自洽性检查**：把 `buildPrompt(id)` 里**声称的值**与 `style.css` / DOM 里**实际的值**逐条比对，30 案全覆盖，**成本 <1 秒/案**：

| 检查项 | 通过 | 失败 |
|---|---|---|
| 调色板：提示词点名的每个 hex 都在 CSS 里真实存在 | **30/30** | 0 |

**它能替代端到端的哪一部分？** 端到端链路是三层：`提示词写对 → AI 照做 → 人判像不像`。自洽性检查**只验第一层**，但它是**最便宜且唯一能 30/30 全覆盖的一层**。它挡不住"AI 不听话"，但能挡住**"提示词自己就写错了、AI 忠实执行、人再判像不像，三层全白跑"**——而 A1 已经证明这种错**真实发生过**（S19 的 5 条缺失）。

**判决：A5 成立。** 自洽性检查**不能替代**端到端，但它是**端到端的前置门禁**：先 30/30 自洽，再抽样端到端。跳过第一步直接做端到端，是在用最贵的方式发现最便宜的问题。

### A6 修提示词的代价——这是全局耦合，不是逐案修补

- `prompt-copy.js`：**1,047 行 / 99.6KB**，`buildPrompt` 的文本模板 + 30 案分支逻辑都在这里。
- `build-prompts.mjs`：**399 行 / 17.5KB**，30 案的 `plain`（37 处）、`scenes`（34 处）、`mechanism`（9 处）、`reuse`（5 处）、`risk`（4 处）都在这里。

**判决：A6 成立，且比"没人算过"更严重——这个成本结构意味着"逐案修"这个提法本身就不成立。**

### D5 清掉 mono 的代价——成立，仓库自己承认了

## E. 「移动端 19.4 屏太长」

### E1 19.4 是真的吗？——不是，是 13.7

```
390 × 844 实测：docH = 11,564px → 11564 / 844 = 13.70 屏
1440 × 900 实测：docH =  8,835px →  8835 / 900 =  9.82 屏
 768 × 1024 实测：docH = 15,272px → 15272 / 1024 = 14.91 屏
```

**19.4 只在可见高 ≈596px 时成立**：

| 视口高 | 屏数 |
|---|---|
| 844 | **13.70** |
| 800 | 14.46 |
| 720 | 16.06 |
| 667 | 17.34 |
| 640 | 18.07 |
| **596** | **19.40** ← 只有这一档 |
| 568 | 20.36 |

`docH` 恒定 11,564。**19.4 = 11,564 / 596。** 596px 是"把浏览器地址栏+工具栏算进分母"或"375×667 设备再减工具栏"的口径。**390×844 是逻辑视口，不该再减 chrome。**

**判决：E1 数字错，且错在分母。** 同一份 docH，换分母得两个数，这不是"测量误差"，是**口径没对齐**。

### E2 「太长」是缺陷吗？——不是

- 13.7 屏 ÷ 30 张卡 = **每屏 2.2 张卡**。
- 行高实测 **340–431px**（含缩略图 152px 宽 + 定义段）。
- 对比：手机淘宝搜索结果页、豆瓣电影列表页，**每屏 2–3 条**是标准密度。

**判决：E2 不成立。** 30 条内容的列表页 13.7 屏是**正常密度**，不是缺陷。

### E3 E 与上一轮成果互斥吗？——**互斥，且已实测出临界点**

首屏完整卡 **1 张，余量 52.25px**（`firstBottom = 791.8 < vh = 844`）。

把列表元数据从 13px 调到 16px（**正是 a11y / body-size 规则要求的**）：

| 变体 | 屏数 | 首屏完整卡 | 余量 |
|---|---|---|---|
| 基线（13px 元数据） | 13.70 | **1** | +52.25px |
| 元数据 16px | **16.13** | **0** | **−8.47px** |
| 元数据 18px | 18.19 | 0 | −45.41px |
| 元数据 20px | 20.19 | 0 | −139.05px |

**反过来压缩**（往下调）：

| 变体 | 屏数 | 完整卡 | 余量 |
|---|---|---|---|
| 元数据 12px | 12.12 | 1 | +132.39 |
| 元数据 11px | 11.34 | 1 | +146.16 |
| 隐藏缩略图 | **10.66** | 1 | +137.75 |

**结论：往下压能到 10.7 屏，但代价是缩小字号或去掉缩略图——两者都是 a11y 倒退。**

**而 README 第 389 行早就写明了这个 trade-off**：

> 「已知仍未清零的一条：`body-size` 判「正文 13px」。这是**选的**，不是漏的——本页正文主体是方案卡的元数据（30 案 × 十几个 13px 字段名与读数），把整页正文抬到 16px 会让列表页首屏从 1 张完整卡掉到 0 张（这正是 `67-exec` 那一轮花几十像素救回来的东西）。」

**我复现了这个数：16px → 完整卡 0 张，余量 −8.47px。README 的取舍是真的。**

**判决：E3 成立且比提问者以为的更尖锐——不是"互斥"，是"52px 的余量只够在 13px 和 16px 之间二选一"。**

### E4 虚拟滚动的代价

本页的立身之本是**纯静态、无构建、无依赖**（README：「整个仓库**纯静态**：没有后端，没有构建，没有依赖安装」）。虚拟滚动要：

1. 引一个 JS 框架/库（**破"零依赖"**），或自写 200+ 行（**破"纯静态"**）。
2. **30 张卡不再全在 DOM 里** → `Ctrl+F` 失效、`#S07` 深链要额外处理、详情面板的 `querySelector('.row[data-id=…]')` 全部失效（`app.js:1215` 正在这么做）。
3. `file://` 双击可开（README 明写是功能前提）**大概率失效**。

**判决：E4 成立。虚拟滚动的代价不是"引个库"，是拆掉仓库的三个硬承诺。**

### E5 真正的痛点是什么？——判断对，但提问者自己说对了

实测：**每屏 2.2 行**，行内已经有：

```
S01 · 红黑斜排报 · Red Wedge Broadsheet · F型 · NEWS-FRONT · 门槛低
混乱活力/街头 · 没裁齐的报纸感，红斜块压住版面 · 苏联构成主义印刷
· P-03 · 条目可增减（设计时 6 条） · 1440/768/390 · FAIL 0 / WARN 4
```

**身份信息是足够的。** 所以"滚到第 8 屏忘了前面"**不是信息不足**，是**缺"我在第几张 / 还剩多少"的进度感**。

- **"滚 19.4 屏太累"** → 解法是**压缩**（缩字号/去缩略图）→ **与 E3 的 a11y 方向冲突**。
- **"滚到第 8 屏忘了前面"** → 解法是**加锚点/序号/进度**→ **与 E3 完全不冲突**，且**不加任何依赖**。

**当前页面有没有进度？** 有 `列出 30 / 30 个方案`（`#count`），但那是**筛选结果数，不是滚动位置**。**没有"第 8/30"、没有粘性序号、没有分组标题。**

**判决：E5 的前提（"19.4 屏"）错，但痛点判断对。** 真正该做的是**加进度锚**（零成本、零依赖、不破首屏），**不是压缩**（高成本、破 a11y、破 E3）。

## 我认为真正该做的三件事

### 1. 把 A5 的"提示词自洽性"做成 30/30 的门禁，**先于**任何端到端验证

**为什么是它**：它是唯一能 **30/30 全覆盖、<1 秒/案、零模型依赖**的检查，而且**A1 已经证明它挡得住真实发生过的错**（S19 的 5 条约束缺失就是这样漏过去的）。

**具体做什么**：
- 把本轮 `a5-selfconsistency.mjs` 的思路固化成 `prototypes/_build/verify-prompts.mjs`：对 30 案逐条比对「提示词声称值」vs「CSS/DOM 实际值」，覆盖调色板 / 圆角 / 阴影 / 字体链 / 线宽 / 条目数。
- 本轮已跑出基线：**调色板 30/30、圆角 30/30、阴影 29/30**（S19 那 1 处外阴影要么修 CSS，要么在提示词里说清楚）。
- **再补一条**：把 A1 发现的 5 条缺失（风格名 / 标题字体 / 抽屉分栏 / 编号贯通 / 收敛规则）作为**"版式可复现性"字段**加进 `buildPrompt`，否则提示词只能保证"像这个风格"，不能保证"是这个版式"。

**成本**：1 个脚本 + 1 次全库提示词回归。**远低于**验 29 次端到端（A3 证明验 3 次都不够）。

### 2. 把 `degrades`/`minItems` 接进详情面板，**用已有数据**解决 C2+C4

**为什么是它**：C2 实测 **0/30 面板有出口**，这是本轮**唯一一条"完全成立且零争议"的缺陷**。而修它**不需要新数据**——`capacity.degrades` / `minItems` / `hardIds` 都已在 `prompts.js` 里，只是没接到面板。

**具体做什么**：
- 在每个 `hard` 或 `degrades==='yes'` 案的详情面板顶部加一行**可执行**的提示：
  > ⚠ 这个版式按 **N 条**内容手工排定。你只有 M 条时会空 N−M 格。
  > → 内容不够？看 [同家族的 X 案] 或 [M02 大众模板]
- **不要**做成"你用不了，去用模板"（C4 证明那是劝退）；做成**"这个版式需要什么条件 + 不满足时的替代"**。
- 顺带把 `empty-screens`（D3 唯一一条真缺陷）在 S13 上修掉或登记进 §9.15——**现在它是唯一既没修也没豁免的一条**。

**成本**：一个面板区块 + 14 案的数据映射。**不碰任何原型、不碰提示词模板。**

### 3. 移动端加"进度锚"，**不要压缩**

**为什么是它**：E1 证明 19.4 是分母错（实际 13.7），E2 证明 13.7 屏不是缺陷，**E3 实测证明任何压缩都会打破"首屏 1 张完整卡"**（52px 余量，16px 就翻负）。**所以 E 这条唯一正确的解法是 E5 自己指出的那个：加进度，不加密度。**

**具体做什么**：
- 行首加**序号**（`08 / 30`），或
- 顶部 `#count` 旁边加**滚动进度**（`第 8 / 30`），或
- 按 `family`（F/R）或 `structure` 加**分组标题**（30 案已有 `fr` 和 `structure` 字段）。
- **零依赖、零构建、不碰字号、不影响首屏余量。**

**明确不该做的**：虚拟滚动（E4：拆三个硬承诺）、缩字号（E3：a11y 倒退）、去缩略图（E3：可辨识性倒退，实测能到 10.66 屏但代价是每行失去唯一视觉锚）。
