|---|---|---|---|---|---|

## 我比审计报告多发现的一点

审计报告的口径是「CSS 原始文本声明值 + `non-scaling-stroke` 的 SVG 线宽」。

**但 HTML 内联的 `stroke-width=` 属性同样会渲染**，而 `build-prompts.mjs` 只从 CSS 抽。

这解释了 S25 和 S27 的偏差来源：
- **S25**：CSS 里只有 `stroke-width: 3`，所以提示词写 `3px`。但 `index.html` 里有 `<... stroke-width="1">`、`"1.2"`、`"2"` 三个内联值，**它们才是页面上真正大量出现的线宽**。
- **S27**：CSS 里 `1.6`、`3`，提示词却写 `1.2`、`2.4`、`3`。而 HTML 有 `.8`、`1.6`。**`1.2` 和 `2.4` 在 CSS/HTML 里都不存在。**

## 「不要自创第三级」这句话本身是荒谬的

30 条提示词全部以这句结尾：
```
线宽只用这几级：<列表>，不要自创第三级。
```

- **S25 只给 1 级**（`3px`），哪来的「第三级」？
- **S19 给 4 级**（`0.4、0.8、1、3px`），「不要第三级」与列了 4 级直接冲突。
- **S09 给 3 级**，这句才勉强说得通。

**这句话是从某个 3 级线宽的案子模板里抄出来的，然后套到了所有 30 案。** 提示词有 42.3% 的字是 30 案完全相同的 boilerplate（红队实测），这句就在其中。

## 为什么这一项特别重要

线宽是**风格签名的一部分**：
- S19 的「0.4/0.8 双级细线」是它「铜版蚀刻」风格的核心
- S25 的粗线、S10 的「红版错位露纸 1.5px」都是各自的识别标记

AI 拿到的线宽表如果和原型不符：
- 拿 S25 举例：AI 会以为「全站只用 3px」，做出来的东西**丢掉 1px 和 1.2px 的层次**，那就不是 S25 那个风格了。
- 拿 S27 举例：AI 会到处用 `1.2px` 和 `2.4px`——**这两个值在原型里根本不存在**。

## 处置建议

### 立即可做（不改产品，只改记录）
在 README 的「做不到与已知边界」加一条：线宽表的抽取只覆盖 CSS 声明，**不覆盖 HTML 内联 `stroke-width`**，因此 5 案的线宽表不完整。附本表。

### 真正的修法（需要改 `build-prompts.mjs`，成本 M）
线宽抽取要同时扫三个来源：
1. CSS 声明的 `border-width` / `outline-width` / `stroke-width`
2. **HTML 内联的 `stroke-width=` 属性**（当前完全没扫）
3. SVG `<path stroke-width>` 与 `vector-effect` 状态（区分「用户单位」与「屏幕像素」）

**并且要把「不要自创第三级」这句话改成按实际级数生成**：1 级就说「只用 1 级」，4 级就列 4 级，别写「第三级」。

### 无法修的部分
S15 的情况（声称 `0.5/0.8/1/1.7/3`，CSS 边框只有 `2/3`，其余全在缩放的 SVG stroke 上）说明：
**提示词说「线宽只用这几级」时，AI 会以为是 CSS border，而原型用的是 SVG 线条。** 这个语义错位不是补数据能解决的 —— 需要在提示词里明说「这些线宽用在 SVG 描边上」。

## 与 A 项的关系

这一项是 **23 条硬 FAIL 里最集中的一类（5 案）**，而且是**确定性可验、不需要端到端生成**的那类。

它再次支持红队的判断：**先把「提示词声称值 vs 原型实际值」做成 30/30 门禁，再谈端到端。** 因为线宽这类错误会让端到端验证的结论无法归因 —— AI 照着错的线宽表做，做出了「不像」的页面，你无法区分是「提示词不够好」还是「数据本身是错的」。
