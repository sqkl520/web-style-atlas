## 三、为什么这是本轮最严重的缺陷

### 3.1 用户会直接受害

用户的路径是：
1. 在选型台看到某个案（比如 S19），觉得不错
2. 点「复制 AI 提示词」
3. 把提示词喂给 AI
4. AI 生成页面 → **5 色**
5. 用户回头看仓库里 S19 的截图/原型 → **看到 12 色**
6. **用户会以为自己操作错了，或者 AI 没听懂**

而真相是：**提示词和参考图不一致，且提示词是对的（更严格），参考图违反了提示词。**

### 3.2 它让「提示词自洽性检查」在结构上无效

红队和可验证性审计都建议「把提示词声称值 vs 原型实际值做成 30/30 门禁」。

**但这类检查的真值来自同一份 CSS**——`build-prompts.mjs` 从 `style.css` 抽色，检查器也从 `style.css` 读色。**两边同源，抽漏了的部分两边一起漏，永远对得上。**

这正是为什么：
- 可验证性审计跑出「`palette-used` 21 PASS / 9 WARN」「`palette-closed` 21 PASS / 9 FAIL」
- 而我在浏览器里全量采样，得到 **20/30 违规**

**差别在于：审计读的是 CSS 声明，我读的是浏览器实际画出来的。** 一个色可能在 CSS 里声明了但没被任何规则引用（死变量），也可能通过 `color-mix()`、`opacity`、伪元素、SVG 属性等各种方式出现。

### 3.3 它是一个「决策」，不是 30 次修补

面对这个不一致，只有两条路：
- **(a) 改提示词**：把 55 个集合外颜色补进去 → 30 条提示词会变长（每个多 2–6 个色值），且要重新生成
- **(b) 改参考图**：让原型只用提示词声明的色 → 那是**改 20 个设计作品**

**这是产品级决策，必须由你定，不能由 Agent 决定。**

## 四、我建议的方向：先查清 55 个颜色的性质，再决定

不是所有「集合外颜色」都一样。要分成三类：

| 类型 | 例子 | 处置 |
|---|---|---|
| **A. 正文/骨架色被漏掉** | S19 `#5E5443`（247 次，明显是正文色） | **必须补进提示词**——漏了它，AI 做出来的正文颜色就是错的 |
| **B. 同色系深浅变体** | S25 `#4A423A` / `#6B625A`（同色系，可能是 hover/边框微差） | 可以合并进提示词为「同色系深浅可微调」 |
| **C. 照片/图片里的颜色** | S21 的 `#C5BEAD`（是照片里的墙） | **不该算**——但我的脚本已经排除了 img 和背景图，所以这类应该已经滤掉了 |

**规划 Agent 建议的第一件事（2 小时）就是做这个分类**：抽 2 案逐色核对，证明「247 次的 `#5E5443` 是正文色，不是测量噪声」。

我认同这个优先级。理由：
- 它是唯一**用户直接受害**的缺陷
- 它决定后续是改提示词还是改参考图（**一个决策**，不是 30 次修补）
- 它把 A 项从「学术练习」变成「有明确修复目标的工程任务」

## 七、一个诚实的边界

1. **我的采样排除规则可能过严或过松。** 我排除了 `pre/code/kbd/samp` 内的代码片段与纯黑纯白。如果某个设计真的用纯黑当主色，会被我误排除。
2. **`#0000EE`（S02/S09 各 7 次）是浏览器默认链接色** —— 这说明那两个案有未设置 `color` 的 `<a>` 标签，是**真实的样式缺陷**，不是设计色。这类需要单独归类。
3. **我读的是「声明值 + 浏览器计算值」，不是像素。** 若要最严格，应该做像素直方图（可验证性审计的 `probe-pixels-masked.mjs` 就是这么做的，它得到「声称色占 CSS 绘制像素均值 88.5%」，比我这个口径宽松）。
4. **规划 Agent 的数字（17/30、33 色）与我的（20/30、55 色）不一致，这本身说明「什么算违规」需要先定义清楚。** 这可能比数字本身更重要——如果连测量口径都要争，那用户读到「只用这几个色」时的理解必然也是模糊的。
