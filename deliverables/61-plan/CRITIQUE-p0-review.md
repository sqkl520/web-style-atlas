## 1. 逐项：可能引入的新缺陷 / 更小的替代 / 验收缺口

### P0-1 圆角行反查

**先说实测：反查没有把「真没写圆角」错判成「全直角」以外的错。** 4 个 `未声明` 案
（S04/S07/S08/S21）实测 `border-radius` 声明 **0 处**、SVG `rx=` **0 个**，确实是全直角。
这一层判对了。**问题出在「写死那句话」上。**

**新缺陷（具体）：

`0 / 50%` 那 5 案的 50% 宿主，实测是这五处：

| 案 | 50% 的宿主 selector | 是「圆形徽标/圆点」吗 |
|---|---|---|
| S05 | `.lamp`（注释原文：*状态灯：8px 圆形实体灯*） | ✓ 是 |
| S14 | `.field::before`（注释原文：*参考椭圆：450×700 椭圆*）、`.centroid` | ✗ **是椭圆，不是徽标** |
| S16 | `.slab-no::before` | ✗ 不是徽标 |
| S17 | `.spinner` | ✗ 不是徽标 |
| S25 | `.holes li::after`（打孔） | ~ 算圆点 |

⇒ 统一写「仅圆形徽标/圆点为 50%」在 **3/5 案上是事实错误**。AI 读到「徽标」会去画圆形徽章，
而 S14 那处是挂在伪元素上的参考椭圆、S17 是 spinner。**这是用一个错事实替换一个不可执行记号**，
比「0 / 50%」更糟——「0 / 50%」至少不撒谎。

**更坏的一处（S25）**：现盘输出是

```
3. 圆角：圆形（50%），只用在圆点与圆形徽标上，其余元素不加圆角。
```

这句话**以「圆形（50%）」开头**。模型读约束是首因权重，这半句就是它唯一会记住的东西，
而后半句「其余元素不加圆角」是它最容易丢的（IFScale：高密度下失败形态是整条丢弃）。
S25 全站唯一的圆角是 1.6px 打孔圆点 —— 这句会让 AI 做出圆角卡片。**这一句应改成以「0」开头。**

**更小的替代**：不要写固定句，按 selector 现算：
`3. 圆角：全站 0；唯一例外是 `.holes li::after` 这类 1.6px 圆点用 50%，卡片/按钮/图片一律不得有圆角。`
一句话，主句是 0，例外带 selector，可 grep。

**验收不够**：现在只断言「30/30 可执行、`。。` 命中 0」。
**要补的「没改坏」断言**：
- 圆角行**必须以 `全站`/`0` 开头**（不许以 `圆形`/`50%` 开头）→ 抓 S25。
- 圆角行里出现「徽标」的案，必须恰好是 `.lamp` 那类状态灯案（白名单），否则失败 → 抓 S14/S16/S17。
- 每案圆角行里 `。` 的**出现次数 == 1**（不是「没有 `。。`」，因为 `。 。` 也能绕过）。
- 交叉断言：`border-radius` 声明数为 0 的案（实测 4 个）与输出「0 处声明」的案必须同集合。

### P0-2 标题字体改按变量名取 —— **口径错，必须改**

**实测统计（30 案 `:root` 里「值是字体串」的变量名）**：

```

──────────────────────────────────────────────────────────────
不同变量名总数：24
:root 里一个字体变量都没有的案：15/30
  S02 S03 S05 S11 S12 S14 S15 S16 S17 S19 S20 S22 S27 S28 S30
```

**两种写法我都跑了**（真相 = 我用 CDP `getComputedStyle(h1).fontFamily` 取的 30 案实测首族）：

| 策略 | 能取到值 | 正确 | 错 | 无信号 |
|---|---|---|---|---|
| 现方案（按数组顺序猜，`HEAD` 版） | 30/30 | **20/30** | **10** | 0 |
| 计划写法（`--display` / `--text`） | 8/30 | 8 | 0 | **22** |
| 保守写法（只认 display/head/title 语义） | 9/30 | 9 | 0 | **21** |

⇒ **变量名法不会引入新错（0 个新错），但它只覆盖 8/30。**「按变量名取」作为**唯一**策略是
一个只能修 8 案、却要被验收宣称 30/30 方案 —— 这就是「做了反而更坏」：
**原来 10 处错是可见的（错的名字写在提示词里），改完变成 22 处「不知道」被写成「已修好」。**

**顺带纠正一个基线数字**：红队报「7/30 错」，我按 CDP `getComputedStyle` 实测是 **10/30**。
红队漏报 **3 案**：

```
S01  提示词 Archivo            实测 Noto Sans SC
S03  提示词 IBM Plex Sans      实测 IBM Plex Mono      ← h1 本身是等宽体
S09  提示词 Syne               实测 LXGW Marker Gothic
```

所以这个缺陷比计划与红队写的**都更严重 3 案**。这也说明「按数组顺序猜」的失败面
不止「display 猜错」，还包括「标题本来就是 mono/CJK 但被归类成西文展示体」这一类
（S03 的 h1 就是 `IBM Plex Mono`）—— 这恰好是「按变量名取」也救不了的，因为 S03 没有字体变量。

**实际该写的口径**（现盘执行者已经这么做了，这是唯一正确方向）：
**按 `h1` 规则的 `font-family` 解析，先展开 `var()`，再按 CSS 层叠取最后一条命中规则。**
不能只按变量名——因为 15 案没有变量名；也不能按数组顺序——因为那是声明顺序，不是角色。

**实测验证（现盘-03:56 的 `dna-clean.json`）**：`fonts.display` 与我的 CDP 真相 **30/30 一致**。
所以这件事能做对，但**计划里写的那个方法做不到**。

**验收必须换判据**：不能断言「按变量名取到了」，要断言
`buildPrompt(id)` 的标题 == 该案 `http://…/index.html` 的 `getComputedStyle(document.querySelector('h1')).fontFamily` 首族，**30/30**。
静态解析不可信 —— 我第一版静态解析在 S13 上就判错了（静态得 Noto Serif SC，CDP 实测 EB Garamond）。

**要补的「没改坏」断言**：
- `dna.fonts.display` 不得为空，**尤其不得等于兜底串** `有刻印感的衬线`（见 §2 末的实测事故）。
- `dna.fonts.body` 不得等于 `mono`（S19 现在 body=Noto Serif SC、mono=IBM Plex Mono，正常；
  但要防「三个字段全填同一个值」这种静默退化 → 实测现盘 S01/S09 的 display == body，属真实情况，需白名单）。
- 断言 30 案的 `fonts` 三个字段**类型是对象且三键齐全**，否则 `prompt-copy.js` 会走兼容分支。

### P0-3 剥 CSS 注释残留

**实测污染面只有 1 个值，不是一类问题**：

```
prompts.js:595  "IBM Plex Mono\" /* taste-skill-ignore: 字段4 辅助数字，只用于页码/辑号/归档号 */"
```

全文件含 `/*` 或 `taste-skill-ignore` 的只有 **2 行**：L1（`prompts.js` 的文件头 banner，那是合法注释，
不是值）+ L595。**所以这一项的真实工作量是「一个字段」，风险不在「剥不剥」，在「在哪儿剥」。**

**新缺陷**：如果按红队原话在 `clean-dna.mjs` 加 `/\/\*[\s\S]*?\*\//g` 去扫 **整个 `style.css`**，
会把 `/* 蚀刻墨绿 */`、`/* 主色，对纸底 5.42:1 */` 这类**角色注释**一起删掉 —— 而
规划报告 B01（`:433-435`）明确写着「**注释就是现成的角色信息，不需要新造数据**」。
**P0-3 和 P0-4 是同一份注释的两个消费者，先剥了 P0-4 就没原料了。**
现盘 `clean-dna.mjs` 里确实还有一处 `css.replace(/\/\*[\s\S]*?\*\//g,"")`（S14 兜底数频次那条），
那是**为了数 hex 而临时剥**，不写回文件，这个是安全的 —— 差别就在「剥临时副本」还是「剥源」。

**更小的替代**：只在**产出一个值**的那一步剥（`cleanName()` / 字体名 / 色名），
不动 CSS 源；并且加一条「名字里含 `/*` 就丢整条并记录」而不是静默清洗 —— 因为这条脏串的根因是
`--f-mono` 的值后面跟了注释，说明抽取正则没停在 `;` 上，清洗只是把症状藏起来。

**验收不够**：现在只断言 `prompt` 里 `/\*|taste-skill-ignore/` 命中 0。
**要补的「没改坏」断言**：
- `style.css` 文件里 `/*` 的出现次数**改动前后相等**（证明剥的是副本不是源）—— 30 案逐案比。
- `dna-clean.json` 的 `palette` 里「带变量名」的比例 == 改动前（证明色名还在，没被连注释一起吞）。
- 断言脏串案的 **mono 字段仍非空**（S07 的 mono 必须还是 `IBM Plex Mono`，不是被整条丢掉）。

### P0-4 调色板 5→7 —— **建议降级（详见 §2a）**

**新缺陷（可量化）**：我把现盘 30 案 palette 两两算了 CIEDE2000 近似 ΔE（ΔE<10 ≈ 肉眼难分）：

```
≥6 色的案：17/30，其中 17 案都含「难区分」色对
色对总数 315，ΔE<10 的 46 对（15%）
```

逐案「列了 N 色、视觉上只有 M 种」：

| 案 | 列出 | 实际可区分 | 多余的是 |
|---|---|---|---|
| S06 | 7 | **4** | `#ECDEC6`/`#E6D8BC`/`#E0D0B0`/`#E4D5B8` 四个纸色，最小 ΔE **1.2** |
| S19 | 7 | **4** | `#E4DECD`/`#D8CFB6`/`#E9E3D2` 三个纸色，ΔE 1.8–8.4 |
| S24 | 7 | **4** | `#E6EDF2`/`#F3F8FB`/`#DCE7EF`/`#C9D8E4` 四个纸色，ΔE 3.1–9.0 |
| S30 | 6 | **4** | `#EDEDED`/`#E6E6E6`/`#FFFFFF`，ΔE 2.5–8.7 |
| S05 | 7 | **5** | `#0E100D`/`#111111`/`#050605` 三个黑，ΔE **1.8** |
| S14 | 6 | 4 | 兜底频次色，且无变量名 |

⇒ **第 6/7 槽加进去的不是「强调色」，主要是纸色/墨色的近似档。** 这是最坏的一种「信息更全」：
它不增加可执行信息，只增加「哪一个是主色」的判断负担。

**计划写的判据不存在**：

```
30 案 :root 里含 primary/accent/brand 字样的变量名：0 个
全 30 案 :root 里 "--primary" 出现次数：0
data.js 的 primary 字段：30/30（这才是唯一来源）
```

而且 `data.js` 的 `primary` **不总是强调色** —— 实测 S02 `primary=#EFE6D0`（那是 ivory 纸色）、
S05 `#BFB9A6`（panel 灰）、S09 `#151310`（ink 墨）。所以「优先保留 `--primary`/主强调色」
这条如果照着做，会把**背景色当成强调色排到第一位**。这是另一个新缺陷。

**更小的替代（我建议的就这一版）**：保持 5 槽，但**按角色取**（底/墨/强调/线/+1 个次强调），
再对 `data.js.primary` 做一次「若不在 5 槽内则替换掉最不常用的那一槽」。
实测这个最小版本够用：

```
primary 在 :root 声明顺序 ≤5 位的案：28/30
需要第 6 位：S19（#4A5C3A）
需要第 7 位：S24（#5D43AD）
第 8 位以后：0 案
```

⇒ **上限是 6，不是 7**；只有 2 案需要第 6 槽。再加一条 ΔE≥10 去重，30 案里
「4 色」的 10 案根本不需要补。

**验收不够**：现在只断言 `S19 含 #4A5C3A、S24 含 #5D43AD`（现盘已 30/30 通过）。
**要补的「没改坏」断言**：
- 每案 palette 长度 **≤6**（不是 7），且**任意两色 ΔE≥10**，否则失败 —— 抓 S06/S19/S24/S30。
- 断言 palette **第一个**色不是 `data.js.bg`（防止把背景色当强调色排最前）—— 抓 S02/S05/S09。
- 断言 **30 案里 `--primary` 出现次数仍为 0**（防止有人真去 CSS 里新造这个变量）。
- 断言提示词里「配色只用这几个值」这一行**字符长度不超过某个上限**（如 78 字），
  超了就是又塞回去了 —— 现在 S05 那行已 96 字。

### P0-5 默认气质按案派生

**实测：现盘仍是 30/30 都含「安静、有手艺感」**（我用 CDP 调 `window.buildStylePrompt(id)` 逐案跑的）。
所以这一项**还没落地**，下面的意见是「落地前必须先解决」的。

**新缺陷（最严重的一条，可直接复现）**：现盘 S09 的提示词里**同时**有两句：

```
请把整页做成这个风格：亮黄手写价目板，小店摆摊那种热闹。
气质上更像一个安静、有手艺感的地方，不要做成通用的商业落地页。
```

同一屏、隔一行、**自相矛盾**。而计划的验收是「S09/S12/S16/S30 不得出现『安静』」——
这是**字符串级断言**，删掉「安静」两个字就能过，但真正打架的是后半句
「**不要做成通用的商业落地页**」—— 它对 S12「很吵」、S16「速度感」、S30「潮流有劲」同样是反向拉扯。
**只删「安静」= 用一个更弱的矛盾换一个更强的矛盾（因为删完之后那句只剩「不要做成通用落地页」）。**

**更小的替代**：`plain` 字段本身已经带气质（实测 S09「小店摆摊那种热闹」、S12「很吵」、
S16「速度感」、S30「潮流有劲」）。所以**不要派生，直接删**：
当 `plain` 命中气质词表（热闹/吵/劲/贵/暗/冷…）时，**整行「气质上更像…」不输出**。
零新数据、零新逻辑、不可能派错。要保留那句「不要做成通用的商业落地页」就单独输出，不绑气质。

**如果要派生，唯一有依据的源是 `tone`**（`data.js` 里实测 7 桶：
混乱活力×5 / 奢华暗黑×3 / 冷静克制×4 / 机能冷峻×5 / 温暖手作×4 / 学术档案×5 / 荒诞幽默×4）。
比「按 plain 派生」稳，因为 plain 是自由文本、没有封闭词表。

**要补的「没改坏」断言**：
- 机器可判的**冲突断言**：若 `plain` 含「热闹|吵|劲|速度|贵|暗」，则气质行不得含「安静|手艺」。
- 断言 30 案里「气质上更像」这一行**不出现同一个短语超过 7 次**（= 不能又是 30/30 同一句）。
- 断言**改动前后「气质」行总字符数不减到 0**（防止为了过断言把整行删掉，
  连「不要做成通用落地页」这条有效约束一起丢）—— 这条是本项最需要的。

### P0-6 `reset` 补 `state.sceneIds = new Set()`

**实测：现盘已修好，且我确认主路径没问题**

```
initial         30 / 30
点「茶饮」芯片   2 / 30
点「清空筛选」   30 / 30   ← 已修
reset 后 aria-pressed=true 的场景芯片：0 颗
```

**但一行的版本不够 —— 实测出一处会让验收「假通过」的细节**：

场景芯片有两批。实测结构：

```
#flt-scene 里的直连芯片：16 颗（在 .chips 里）
.scene-more 里的近似芯片：28 颗（在 .chips **外面**，父节点是 .rail-block）
reset 里原来的选择器 $$('.chips button') 能选到的场景芯片：16 / 44
```

⇒ 只加 `state.sceneIds = new Set()` 能修**列表**（30/30），但 `$$('.chips button')` **选不到那 28 颗
近似芯片**，它们会保持 `aria-pressed=true`。计划的验收「芯片后 reset → 回到 30/30」

## 2a. 重点攻击：P0-4 到底该判哪个方向

**你问的两个方向是矛盾的：(i) 信息更全 vs (ii) 约束更多→更容易被忽略。我的判定是：这两个方向
在这件事上都不适用，真正的风险是第三个 —— 「同一个约束里的字面量变多，模型分不清主次」。**

依据全部来自 `deliverables/61-research/prompt-efficacy.md`，逐段指认：

1. **「约束条数」这个自变量，加 2 个色值不改变它。** 报告 §2.2（`:176-195`）说的是
   「**同时要求模型满足 N 条独立约束**」时的衰减（IFScale：N 从 10 到 500，先降的是 250 之后）。
   而调色板是约束 **#1「配色只用这几个值：…」这一条内部**的字面量，条数仍约 20 条。
   ⇒ 按 §2.4 的表（`:228-233`），「约束条数（简单约束）约 20 条」的判定是「**低风险**，在阈值内」。
   **所以「5→7 会越阈值」这个担心没有实证支持。**

2. **但「字面量变多」在颜色这一维上确实有反面证据，且比我预期的强。** 报告 §1.1（`:46-49`）：
   Design2Code 的 Color 分项是所有维度里最差的（GPT-4o **84.1** vs Text **98.2**），
   而且**「把信息写清楚」不等于「模型就会照做」**—— text-augmented prompting 把 block/text 分
   显著抬高，**颜色分几乎不动甚至下降（84.1→83.1）**。作者称之为「与信息量无关的执行缺口」。
   ⇒ 这条直接否掉了「多给两个色 = 信息更全」的假设：**颜色这一维上，加字面量的边际收益接近 0。**
   报告 §3.2（`:254-279`）给的正确形态也不是「多列几个 hex」，而是
   「**先固化一个 `:root{--bg:…;--fg:…;--accent:…}` 块，再要求全站只用 `var(--*)`**」。
   **这是 P0-4 真正该做的事，而它比「5→7」更小（槽位反而更少），效果还更强。**

3. **判据层面：唯一有正面实证的是「hex > 语义词」（Sci Rep，r=0.84 vs 0.79，§1.1 `:53-66`）。**
   这条支持「用 hex」，但**不支持「越多 hex 越好」**——它比的是**记号形式**，不是**数量**。
   报告 §0 前置结论第 3 条（`:23`）也明确写着「不要把这写成『已有研究证明』」。

4. **我的补测（报告里没有的）**：加进去的第 6/7 色 15% 是 ΔE<10 的近重复色，
   S06/S19/S24 报 7 色实际只有 4 种可区分色。**这正好落在 Design2Code 那个缺口的正中间**：
   模型本来就在颜色上最弱，再给它三个肉眼难分的纸色，它只会在这些近似值之间抖。
   ⇒ 结论：**「信息更全」不成立（加的是噪声），「约束更多导致被忽略」也不成立（条数没变）。
   成立的是「同一约束内的信噪比下降」。判 (ii) 的变体，不是 (i)。**

5. **一句话裁决**：P0-4 该做，但**该按「角色取 5 槽 + 只给 2 案补第 6 槽」做，不该「放宽到 6–7」**。
   前者能达成计划的真实目标（S19/S24 的主色不丢，实测只需第 6 位），后者花 15% 的噪声去买同一个结果。

## 4. P0 整体遗漏了什么

### 4.1 「先修错的，再补缺的」这个顺序，对，但它有个前提被漏掉了

红队的排序在**信息层**是对的（拿到错的比搜不到严重）。但它默认了一个前提：
**「修错的」是低风险、可回退的。这在本仓库不成立。**

实测：

```
git ls-files 检查：
  UNTRACKED  deliverables/99-scratch/build-prompts.mjs     ← P0-2/P0-3/P0-4 都改它
  UNTRACKED  deliverables/99-scratch/clean-dna.mjs
  UNTRACKED  deliverables/99-scratch/dna-clean.json
  UNTRACKED  deliverables/99-scratch/dna-raw.json
  TRACKED    prototypes/_selection/prompts.js              ← 它是上面这些的产物
.gitignore:62  deliverables/*-scratch/
prompts.js 首行： 「自动生成，勿手改。生成器：deliverables/99-scratch/build-prompts.mjs」
```

⇒ **P0-1~P0-4 正在改的是「一个 .gitignore 掉的生成器 + 它产出的受跟踪文件」。**
后果有两层：
1. **克隆者拿到 `prompts.js` 却拿不到生成器**（而且首行写的那条路径在克隆里根本不存在）。
2. **下一次任何人改 `prompts.js`、或重跑生成器，都无法验证是否与现在一致** —— 没有基线。

这正是规划报告 A03 的判断（`:678-680`：「A03 必须第一，因为 A01/A02 都要改 `prompts.js`，
而它现在是由不受跟踪的脚本生成的。**先改文件后补生成器 = 制造一次必然的静默分叉**」）。
**Lead 的 P0 七项里没有 A03。** 所以：

> **「修错的」应该等「补缺的」里的 A03（生成器入库）先做 —— 只需要 15 分钟（S 级），
> 而 P0 已经改完了。**

这是 P0 最大的遗漏，且它**不是**「做完再补」能救的：现在 `prompts.js` 已经和 HEAD 差了
470 行（`git diff --stat` 实测 `prompts.js | 470 +++---`），而生成器不在版本里 ——
**这个 diff 是不可复算的。**

### 4.2 另一种「修错的反而应该等补缺的先做」

有，而且 P0-5 就是：
**P0-5 想修「气质默认值错」，但真正让气质错的是「这个提示词根本不解 business/内容量」**
（`buildPrompt` 的 `o.biz` 默认「一家小店」，全库 0 个调用方传 opts —— 红队 `:171`）。
先派生气质 = 给一个「用户没填业务」的提示词配一个更贴切的气质 ——
**用户拿到的第一句仍然是「我经营一家小店」，气质贴切了反而更误导**（因为它现在读起来更可信）。
⇒ **P0-5 应该等 opts 默认值策略（红队 P0-2）先做，或与它一起做。**

### 4.3 P0 全改完，用户实际感知到什么

**7 项里 5 项用户看不见。** 逐项过：

| 项 | 用户在哪一刻感知 | 感知强度 |
|---|---|---|
| P0-1 圆角 | 复制提示词 → 粘给 AI → AI 生成出正确的方角 | 间接，需 1 小时 AI 往返才看得出 |
| P0-2 字体 | 同上（且多数用户不认识 EB Garamond 与 Literata 的差别） | 间接、弱 |
| P0-3 注释残渣 | 复制提示词时**看到一段乱码** —— 这一项其实是**唯一当场可见**的提示词修复 | 直接、强（但只 1 案） |
| P0-4 调色板 | 同上，且用户看不出「少了一个主色」 | 间接、极弱 |
| P0-5 气质 | 同上 | 间接 |
| **P0-6 reset** | **点「清空筛选」，列表从 2 行变 30 行** | **直接、强** |
| **P0-7 空状态** | **搜一个行业词，第一次被告知「这套图集不按行业建索引」** | **直接、强（这才是 P0 里最有价值的一条）** |

⇒ **P0 的价值集中在两项（P0-6 / P0-7 的空状态），而 P0-6 修的是 4.5 小时前自己引入的回归。**
如果用户今天打开选型台，他会感觉到的变化是：**「清空筛选终于能用了」+「搜不到的时侯页面说的实话了」+「页头多了一块模板出口（并且手机上前两屏更长了）」。**
其余 4 项（P0-1~P0-5）对他而言是**不可见**的 —— 它们的价值在「下一个拿提示词去施工的人」。
