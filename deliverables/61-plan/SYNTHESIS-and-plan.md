## 1. 冲突一：补「找得到」还是补「拿到的是对的」

这是七份报告最根本的分歧，且**红队赢了**。

| 立场 | 主张 | 代表 |
|---|---|---|
| 补覆盖 | 用户搜不到 → 先补行业词、把模板接进索引 | 我最初的判断 |
| **补正确性** | 用户能搜到，但搜到之后拿到的东西是错的 → 先修输出 | 红队 + 规划 Agent |

**证据链**（完全独立的两路，结论一致）：

- 红队：`buildPrompt` 30 条里 0 条圆角约束可执行、7 条标题字体错、1 条吐 CSS 注释。
- 规划 Agent（不认识红队）：**同一批缺陷**，编号 A02「修 buildPrompt 四个确定性缺陷」，并把它列为「全表性价比最高」。

两路独立得出同一结论，且都给出行号级定位。**我采纳**。

**为什么这比「搜不到」严重**：搜不到是诚实的空，用户会换个词；**拿到错的施工图，用户会以为是 AI 不行**，而错误来自仓库。

## 2. 冲突二：「44 个行业词 29 个零命中」这个数字

**这个说法不成立。**两路独立复核，结论一致：

1. `sceneIndex`(44) 与 `unsupported`(29) 是两个**交集为 0** 的集合，不能相除。
2. 真实分层（我实测）：
   - 16 个直连词（有对口方案）
   - 28 个只有近似
   - 29 个完全不在索引
   - **合计 73 个词**
3. 规划 Agent 另查出两处我漏掉的：
   - 16 个直连词里 **4 个点了芯片有结果、打字搜不到**（咖啡店/潮牌/修鞋理发/小吃店）——同屏两套检索互相矛盾。
   - 我给的 33 词表里有 5 个不属于 unsupported（餐厅/律师/诊所/花店/民宿），且漏了「独立开发者」。

**gallery-ia 报告给了更狠的一版**：按 `app.js` 真实 haystack 逐词跑，73 个用户词里 **45 个零命中（62%）**，其中 **17 个零命中的芯片其实是有方案的**。

**我的复算**（部分印证）：
```
direct-reachable schemes: 10 -> S01 S04 S06 S08 S09 S12 S16 S22 S25 S28
never reachable by ANY scene word: 3 -> S10 S15 S21
```

⇒ **场景索引只能直达 10/30 个方案**。这比"29 个词没命中"更能说明问题：不是词表短，是**索引结构和方案集合没对齐**。

## 3. 冲突三：模板该不该接进场景索引

**不该。**我原本认为这是「最该先修的」，红队与规划 Agent 都反对，理由分工不同但都成立：

- **规划 Agent（技术阻断）**：`app.js:122` 是白名单过滤。实测 `sceneIds={M02}` → **0/30 行**、`{M02,S06,S19}` → **2/30**。模板 id 不在 `window.SCHEMES` 里，塞进芯片会被**静默吃掉**。
- **红队（信息架构）**：模板是另一条产品线（README 自己写「这层目标是不犯错，拿起来就能用」vs「30 案目标是被记住」）。混进「你是做什么的」会让用户同时看到风险等级完全不同的东西，而界面不告诉他该选谁。

**两路一致的替代方案**：把 `#tpl-exit`（模板出口）提到首屏 + 空状态补一句「当前数据不支持按行业搜」。

**但我发现了双方的共同盲点**：`#tpl-exit` 现在在 rail 第 11 组，实测首屏曝光 0。而 `deliverables/60` 早在 40 小时前就写下「修（1）：把它上移到首屏」——**已诊断、未执行**（见 §7）。

## 4. 冲突四：⚠️ 标记该不该导流到模板

**先修口径，再谈导流。**红队查出这个标记本身就是错的口径：


⇒ 现在的 ⚠️ **既漏报又误报**。在它可信之前，给它加链接等于把不准确的判断传播得更远。

## 5. 冲突五：怎么验证「提示词真能产出该风格」

**我最想做的事，被红队证明方法有破绽。**而且红队的论证我认为成立：

1. **实现者=验收者**，同一模型同一上下文，等于自己判卷。S19 的实测记录自己写着「第一版缺陷是实测才发现的，推理发现不了」——那第一版也是「我」写的。
2. **CDP 只能验「存在/相等」类断言**，验不了「像不像那个气质」。一个页面可以同时满足全部机械断言并且仍然像通用落地页。
3. **成本错配**：30 条各验一次至少 30–60 人时；而 30 条里的确定性缺陷（圆角/字体/脏串）一个 node 脚本 30 秒就能列全。**先花 30 秒修 30 条，再花 30 小时验 3 条。**

**修正后的方法**（采纳红队）：只验 3 条（S07 / S30 / S23，分别代表「会被压扁的密集目录」「hard 边界」「写死坐标」），且**必须换一个不知道答案的实现者**——另开 session，只给提示词，不给原型路径。

## 9. 需要用户拍板的两件事

1. **入场顺序**：先 P0 修错（约 1–2 小时，纯静态零风险），还是先补行业覆盖？
   → 我建议先 P0，理由见 §1。但如果用户觉得「搜不到」更痛，P1-1 可提前。
2. **仓库定位**：红队指出这是最根本的分裂——
   - 若定位是「挑风格的图集」：那 P2-3（补行业）确实是缺口，但 `deliverables/53` 用外部市场数据裁定这个需求（b 项 55%）是编的。
   - 若定位是「agent 可用的风格条件语料 + 反 AI 味施工法典」：那最该补的是**语料正确性**，即 P0。
   → 这个定位决定后面所有排序。**我没有替用户决定。**
