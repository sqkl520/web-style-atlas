## ② `hard` 判据的可操作定义

### 2.1 先否掉现在的定义

现在「机制绑死在行业数据上」不可判定，因为**「行业」不是可测量的谓词**。S10 的 `scenes` 写「B 端采购」，但它的机制只要求「有两列可比的数」——`B 端采购` 与 `工程规格` 只是这个抽象约束的两个实例。把实例当成约束，就是这 9 个标注的原始错误来源。

### 2.2 判据（三条件合取）

> **一个案子是 `hard`，当且仅当同时满足 H1、H2、H3。**

**H1（不变式，可测量）**：该案的可运行原型对其输入内容满足一条**可写成算式或结构谓词的不变式 I**，且实测残差在明示容差内。
- 形式二选一：
  - **数值恒等式**：如 S15 `w×h/6400 = 声明 m²`，容差 ≤1%；S03 `h = round(0.9333×曝光秒)`，容差 ≤1px。
  - **结构双射 / 关系性质**：如 S29 `{图上编号} ≡ {表行号} ≡ {回链号}`（有序集合相等、零重复）；S21 `angle = 15×pairs` 且 `excl` 长度 `= pairs` 且关系对称且零悬挂。
- **反例（不构成 H1）**：只是「有 N 个槽位」。槽位数是**基数**，属 D3，不属 hard。

**H2（承重，可变异证伪）**：存在一个**只改内容/数据形态、不改条目数**的变异 M，使该案 1-附 所指的**签名元素**出现可测缺陷。
- 签名元素 = `1-附(机制)` 那句话的主语。S03 是「年代轴」，S29 是「编号双射」，S15 是「按面积的热区」，S18 是「连续流水 + 折页」，S21 是「切口角度 ↔ 互斥对数」。
- 可测缺陷的**准入门槛（四选一，须量化）**：
  1. 签名元素**渲染为空或退化**（元素数 → 0，或文本节点为空）；
  2. 签名元素**几何失真**：声明值与实测值偏差 >5%，或单位间碰撞数 >0；
  3. 签名元素的**读数与它所声称描述的量脱钩**（例如最近邻列表不是真的最近）；
  4. 签名元素的**语义前提被违反**（例如折页"每 20 行一道"落在无序列表上）。
- **反例（不构成 H2）**：页面只是变短。变短是 D3（`degrades`）的事。

**H3（泛化违背，可抽样）**：在选型台的真实输入分布下，普通需求**大概率**违背 I。
- 操作化：取 `prompt-copy.js` 的入口文案「我经营 {biz}，{what}」为样本框架，抽 20 个非工业、非专业领域的 `biz`（餐饮、健身、花店、律所、民宿、宠物、教培、咖啡、服装、摄影、装修、婚庆、书店、瑜伽、牙科、园艺、烘焙、酒吧、中介、画廊），判断其内容能否满足 I。
- **判据**：≥14/20（70%）不能满足 ⇒ H3 成立。这个阈值是**约定**，不是真理，但它把「大概率」变成了可复算的数，且改动阈值只影响边缘案。

### 2.3 四维拆解（定义 D 的回答）

不要用单一 `hard`，拆成 4 个独立字段。**`hard` 变成派生量，不再是手写量**：

| 字段 | 取值 | 怎么测 | 用途 |
|---|---|---|---|
| `readPath` | `runtime` / `authoring` / `none` | 静态污点：签名元素几何是否由 `dataset` / `getAttribute('data-*')` / 内容 `textContent` 派生；`none` = 内容与签名元素之间无数据通路 | 区分「代码真读」与「作者手工对齐」。**两者都可 hard，但警告话术不同** |
| `inputShape` | `none` / `numeric` / `rankable` / `ordered` / `containment` / `graph` / `keyed` | §3.2 的形状探测器 | 警告句里说「它需要什么」而不是「它属于哪个行业」 |
| `cardinality` | 整数 `minItems` + `degrades ∈ {yes,no}` | 已有 `minitems-parsed.json`（`deliverables/60-minitems-degrade-audit.md`） | **与 hard 正交**，见 §5.2 |
| `substitutionTolerance` | 0–3 分（0 = 换成任意内容都不破；3 = 换就破） | §3.3 替换实验 | 作为 hard 的量化底，避免「是/否」二值丢失信息 |

**派生规则**（写进生成器，替代 `hard: true`）：

```
hard = (H1 成立) ∧ (H2 成立) ∧ (H3 成立)
     ⟺  inputShape ≠ none  ∧  substitutionTolerance = 3  ∧  H3 抽样通过
```

`readPath = none` 的案子**自动 hard=false** —— 机制不读内容，就没有「换内容会退化」这回事，它只有「换个题材仍然长得一样」的问题（那是差异化问题，不是可用性问题）。

- 「看起来像工业页」（视觉印象）。

- `scenes` 字段里的行业词（那是**结果**，是有人先认定它绑行业才写上去的，循环论证）。

## ③ 可证伪的实测方法

四个仪器，全部零依赖、可在本仓库直接跑。**每个仪器都必须先声明自己的失效条件**，否则就会像上一轮那样得出「纯条数」这种一句话结论。

### 3.1 仪器 I1：不变式提取与校验（`inv.mjs`，无浏览器）

**做什么**：把 H1 的不变式写成一段可执行的断言，跑一遍，输出 JSON（含残差与容差）。

**已跑通的三条**（本轮即是）：

```
S15  ∀ rect: |w×h/6400 − declared_m²| / declared_m²  ≤ 0.01
     → 实测 max = 0.00%（14/14）
S21  ∀ bar: angle == 15 × pairs  ∧  |excl| == pairs
     ∧ ∀ e ∈ excl: e ∈ [1,14]  ∧  bar ∈ excl(e)
     → 实测 14/14 命中，42 条互斥，0 悬挂，0 单向
S29  {data-part} ≡ {#part-NN} ≡ {data-back}   （有序集合相等 + 零重复）
     → 实测 23 ≡ 23 ≡ 23，三个数组 JSON 全等
```

**脚本骨架**（可作为 `deliverables/63-test/inv.mjs` 的起点）：

```js
// 每个案子一个 check，返回 {id, invariant, residual, tolerance, pass}
const CHECKS = {
  S15: (html) => {
    const rects = [...html.matchAll(/data-code="([A-Z]-\d)"[\s\S]*?<rect class="edge" x="-?\d+" y="-?\d+" width="(\d+)" height="(\d+)"/g)]
      .map(m => ({ code: m[1], px: +m[2] * +m[3] }));
    const rows = [...html.matchAll(/<tr id="z-([A-Z]-\d)">([\s\S]*?)<\/tr>/g)]
      .map(m => ({ code: m[1], m2: +/<code>([\d.]+)m²<\/code>/.exec(m[2])[1] }));
    // ↑ 陷阱：必须限定在 tr 内取 m²，否则会把图版说明里的 m² 也算进来
    const err = rows.map(r => {
      const g = rects.find(x => x.code === r.code);
      return g ? Math.abs(g.px / 6400 - r.m2) / r.m2 : 1;
    });
    return { id: 'S15', invariant: 'rect_px/6400 == declared_m2',
             residual: Math.max(...err), tolerance: 0.01, pass: Math.max(...err) <= 0.01 };
  },
  // S21 / S29 同构，略
};
```

**边界（会误判的情况）**：
- **单位换算假设必须显式写出**。S15 的 6400 px²/m² 是我从 14 行反推出来的（80 px/m）；如果作者其实用的是别的换算，这条不变式就是伪的。**所以 I1 必须输出换算系数，让人能反驳**，而不是只输出 pass。
- **只对「同一份文件内闭合」的关系有效**。S29 的双射跨 HTML 的两个区块，闭合，可测；但「图上位置」一列链到 `#ch3` 而非具体零件，这部分**不可静态验证**，必须靠 CDP 点击。
- **抓取正则极易多吃**。我第一次跑 S15 时用 `<code>([\d.]+)m²</code>` 全文件抓，得到 22 个值、合计 361.68 m²、覆盖率 252.3% —— 因为把两处图版说明里的面积也抓进来了。**限制在 `<tr>` 内**才得到正确的 68.80 m² / 48.0%。这类错误会让结论反向。

### 3.2 仪器 I2：数据形态探测器（`shape.mjs`，无浏览器）

**做什么**：给每个案子打 `inputShape`，并输出「签名元素由什么派生」的静态污点链。

**规则表**（可机械执行）：

| 命中条件 | `inputShape` | 依据 |
|---|---|---|
| 存在 `id="part-NN"` ↔ `data-part="NN"` ↔ `data-back="NN"` 三向匹配 | `keyed` | S29 |
| 存在 `data-excl="a,b,c"` 且引用闭合、对称 | `graph` | S21 |
| 存在 SVG 图元坐标 + 与之配对的「面积/长度/深度」列，且成比例 | `containment` | S15 |
| 存在时刻列且单调，或 `--at` / `--i` 索引到固定长度列表 | `ordered` | S18 |
| 存在 `data-price` / `data-lead` 且被 `sort()` 消费 | `rankable` | S10 |
| 存在 `GLYPH` / 字符白名单，且长度由输入字符串决定 | `numeric` | S05 |
| 几何由 `Math.sin/cos/hypot` + 参数函数派生，参数来自 UI 而非内容 | `none`（自足参数件） | S20 |
| 内容节点与签名元素之间无 `dataset`/`getAttribute` 读路径 | `none` | S03 |

**边界**：
- **`none` 不等于「简单」**。S20 是 `none` 但它有 7538 字符内联脚本、19 个字面量数组，是全库最复杂的实现之一。**`inputShape=none` 说的是「不读内容」，不是「没机制」。**
- 静态污点会**漏掉间接派生**：如果某个案把内容读进数组、排序后取第 i 个去写 `--x`，正则看不出来。此时必须落到 I3。
- 反过来会**误报**：`--i:0` 这类纯序号变量不是内容依赖（S14 的 `--i` 只用于动画延迟 `calc(var(--i) * -0.67s)`），但形似。**必须看该变量是否流向几何**，而不是看它存不存在。

### 3.3 仪器 I3：替换实验（`subst.mjs`，CDP）——**这是最硬的方法**

**做什么**：在运行中的页面上，用 CDP 注入**同条数、异形态**的内容，测签名元素指标。

**五步协议**（每一步都必须留 before/after 数字）：

1. **定位签名元素**（读 `_specs/SNN.md:15` 的主语）。
2. **定义签名指标**（一个数）：S03 轴高度 / S14 碰撞对数 / S15 矩形面积残差 / S18 折页位置 / S21 切口角度 / S29 互指是否成功。
3. **构造两条替换语料**：
   - `C_same`：同条数、**同形态**（对照，指标应不变 —— 若变了，说明测的不是内容依赖）。
   - `C_diff`：同条数、**异形态**（例如给 S29 的零件表换成菜谱步骤：步骤名 + 无编号 + 有顺序但无唯一码）。**关键：条数完全相同**，否则测的是 `degrades` 不是 `hard`。
4. **测 Δ**：`Δ = |metric(C_diff) − metric(C_orig)| / metric(C_orig)`。
5. **判定**：Δ > 阈值（几何类 5%，计数类 ≥1）且缺陷落在 §2.2 的四类之一 ⇒ H2 成立。

**本轮已跑通的三个替换实验（数字可直接复现）**：

| 案 | 变异 | 签名指标 | before → after | 结论 |
|---|---|---|---|---|
| S03 | 首条 `30 s` → `300 s`（曝光放大 10×） | 该带 `<img>` 高度 | 28px → **28px** | 高度不跟曝光 → H2 ✗ |
| S03 | 追加第 9 条带 | `.axis` 高度 / 年份刻度数 | 640px / 5 → **640px / 5** | 轴不跟条数 → H2 ✗ |
| S14 | 11 枚 `--w` 全改 240px | 两两碰撞对数 | 0 → **0** | 间隔不靠宽度差 → H2 ✗ |
| S15 | `9.36m²` → `90.00m²` | 该热区 rect 的 w/h | 288×208 → **288×208** | 作者期绑定，运行期不读 → `readPath=authoring` |
| S29 | 第 07 行改 99 号 | 图/表能否互指 | 可互指 → **不可互指**（`svgHas99=false`） | 双射手工维护，换内容即断 → H2 ✓ |
| S18 | 删至 5 行 | 折页数 / 挂牌 `--at` 落点 | 3 道 / 5,10,18,34 → **3 道 / 不变** | 折页与挂牌是静态索引 → H2 ✓（需 ≥34 行的有序表） |

**边界（这一段比方法本身重要）**：

- **必须测对宿主节点，否则会造出假缺陷。** 我自己在 S18 上犯过一次：删掉第 21–60 行后测 `document.querySelector('.ln').parentElement` 的高度，得到 `480 → 480`，写成「高度不变，机制不跟内容」。**这是错的** —— 那个 `<pre>` 是第 1 段（只含 1–20 行），第 21 行以后在另外两个 `<pre>` 里，删的都不是它的孩子，高度当然不变。S18 是「3 个 pre × 20 行 × 24px = 480px」的分段结构，不是单一 60 行块。**任何「没变化」的结论都必须先怀疑自己测错了节点。**
- **注入式变异会绕过原作者期约束**。S15 的矩形坐标写死在 HTML，改表里的数字不会动矩形 —— 但这**不证明**「S15 不 hard」，只证明 `readPath=authoring`。判 hard 用的是 H1+H2+H3，H2 的缺陷形式应取「重新用异形态内容排版会不会破」，不是「改一个数字会不会联动」。**这两件事必须分开报。**
- **同条数约束不能松**。一旦替换时改了条数，`degrades` 就会混进来。本轮所有替换实验都保持条数不变，正是为了把两个轴隔开。
- **不会误判的情况**：Δ 为 0 且 `readPath=none` —— 这是强证据的「不 hard」。
- **最容易误判的情况**：Δ 为 0 但 `readPath=authoring`（S15）—— 不能据此判不 hard，要看重新排版的可行性（H3），那是判断，不是测量。

## ④ 测试优先级

排序依据不是「哪个看起来有问题」，而是 **P（结论是错的）× 代价（错的方向有多贵）**，再除以成本。

**方向不对称性**（贯穿整张表）：
- 该 hard 却标了 hard → 劝退一个本来能用的人（可恢复，用户会自己点开看）；
- 不该 hard 却标了 hard → 同上；
- **该 hard 却没标 → 用户拿去做，做出来是坏的，且没有任何提示**（不可恢复，直接伤信任）。
- 所以 **false negative 比 false positive 贵一个数量级**，未标注的 21 案的风险高于已标注的 9 案。

## ⑤ 这个任务的坑与风险权衡

### 5.1 会不会与上一轮审计不一致？会。谁对？

**会不一致，而且本轮已经不一致了 3 处**（S05、S20 的归因，S14 的漏报）。

裁决规则必须**在看结果之前**定好，否则两边会各说各话：

1. **可复算者胜**。谁的结论附了能重跑的命令与数字，谁对。本轮所有结论都附了 §3.5 的命令。
2. **同一现象不同解释时，取能同时解释更多现象的那个**。「S05 是纯条数」解释不了「中文读数渲染为空」；「S05 是条数 + 数字值域」能同时解释两者，所以后者胜。
3. **两边都对时，看定义域**。上一轮说 S14「不 hard」，本轮也说「不 hard」，但上一轮的理由（纯条数）经不起「统一宽度零碰撞」这个实验，所以**结论保留、理由替换**。
4. **上一轮没做的实验，本轮做了就以后者为准**，但要标明「这是新增证据，不是推翻旧证据」。

**最重要的分歧点**：上一轮和我都用过「读代码判断」。区别是它只读，我加了**变异探针**。差别是决定性的：S15 光读代码会得出「矩形是手绘的、坐标写死 ⇒ 位置约束」，跑一次变异才知道**改声明面积不动矩形**，于是必须区分 `runtime` / `authoring`。这个区分直接改变了 hard 的判定口径。

### 5.2 `hard` 与 `degrades` 是正交的吗？——**是，但实测只近似正交，必须显式隔离**

**结论：概念上正交，数据上高度纠缠，方法论上必须强制隔离。**

实测（从 `prompts.js` 直接算）：

```
hard      9 : S03 S05 S10 S14 S15 S18 S20 S21 S29
degrades 13 : S02 S04 S05 S08 S12 S14 S15 S18 S19 S20 S22 S23 S29
重叠      6 : S05 S14 S15 S18 S20 S29
仅 hard   3 : S03 S10 S21
仅 degrades 7 : S02 S04 S08 S12 S19 S22 S23
两者都不  14 : S01 S06 S07 S09 S11 S13 S16 S17 S24 S25 S26 S27 S28 S30
```

- **2×2 四格都有实例**，所以正交性成立（这也是 `prompt-copy.js:470` 那条注释的判断依据）。
- 但**重叠 6/9 = 67%**，远高于随机。原因是：位置写死的案子，其机制往往也依赖特定结构（手绘 14 个热区 ⇒ 必须真有 14 个不等面积舱室）。**纠缠来自「同一个设计决策同时产生了两个后果」，不是概念混淆。**

**隔离规则（写进测试脚本，不靠人自觉）**：

| 规则 | 做法 |
|---|---|
| R1 **同条数** | 所有替换实验（I3）的 `C_diff` 语料**条数必须与原文完全相同**。改条数就落到 `degrades`，实验作废。 |
| R2 **不引用** | 判 hard 的脚本**不许读** `minitems-parsed.json` 的 `degrades` / `minItems`。判 degrades 的脚本也不许读 `hard`。两个脚本各自独立跑，最后才合并。 |
| R3 **两个指标** | 报告里 hard 用「签名元素缺陷类型」（§2.2 四类），degrades 用「单元位空缺数 / 空洞面积」。**指标不共用。** |
| R4 **话术分开** | UI 上已经分开了（`prompt-copy.js:475-477` 两句话），保持。**不要在撤 hard 时顺手改 degrades，反之亦然。** |

**为什么必须这么严**：S05 正是典型的混淆产物 —— 它的 8 块面板面积比是 `degrades` 证据（位置数出来的），点阵读数是 `inputShape` 证据。上一轮把两者一起打包成「纯条数约束」，于是既否掉了 hard、也没有单独留下 H-4 这个真 bug。**混淆的代价是把两个问题一起丢掉。**

### 5.3 如果 hard 从 9 变 4（本轮结论），撤掉的 5 个警告会不会让用户误用？

**这是本任务最需要权衡的一点。分四层回答。**

**第一层：警告本身是冗余的吗？—— 部分冗余，但冗余的那部分是错的。**

`buildPrompt()`（`prompt-copy.js:156`）**每一条提示词都带机制句**：
```js
mech = "这个风格的签名动作：" + d.mechanism;
```
而 `d.mechanism` 就是 `_specs` 第 15 行那句话，例如 S21 的「10 栏中 1–4 与 7–10 栏给两张表，5–6 栏留给 14 枚 24×96px 横条首尾相扣，条间留 1px 纸色缝，右端按 30/45/60° 斜切——先后由切口角度读出」。

**这句话已经把「需要什么结构」说清楚了**，而且它**一定会**进提示词。按钮旁那句警告只是它的一个更粗的摘要。所以撤掉警告**不会丢失信息** —— 失去的是一个**说错行业的摘要**（S21 的 `scenes` 写「工序依赖/调度排班」，但它实际需要的是「互斥关系」；一个 CI/CD 流水线用户完全能用，却被劝退了）。

**第二层：撤掉之后，真实的误用风险有多大？**

按本轮结论，5 个被撤的案子里：
- **S03**：撤了也不会误用 —— 它的机制是「纵向年代轴 + 高度即曝光」，任何有「一组带数值的条目」的内容都能用。真正的问题是**它自己空 309px**（H-1），那是质量问题，不是 `hard` 问题。
- **S10**：只需要两列可排序的数。几乎任何 B 端页都有。**撤掉是纯收益。**
- **S20**：不读内容。撤掉警告不会让人做出坏页面 —— 图永远是同一张图。**撤掉是对的。**
- **S05**：面板布局任何 8 条目都能撑；只有「点阵读数」需要数字。**部分误用风险**，应该用一句更窄的提示替代（见第三层）。
- **S14**：统一宽度零碰撞，说明不需要「内容质量差」。**撤掉安全**。

⇒ **5 个里 3 个（S03/S10/S20）零风险，S14 低风险，S05 有窄风险。**

**第三层：撤警告不等于撤信息 —— 用三分支替代二值。**

现在的 UI 是二值（`prompt-copy.js:473-480`）：警告 / 「粘给 ChatGPT / Claude / v0 都行」。**「都行」这个词本身是过度承诺**，无论 hard 怎么标都不该说。建议改成按 `inputShape` 分支：

| `inputShape` | 按钮旁的话 | 覆盖 |
|---|---|---|
| `keyed` / `graph` / `containment` / `ordered` | ⚠ 这个版式的机制要求内容具备「{具体形态}」；如果你的内容没有，机制会退化成装饰。 | S15 / S21 / S18 / S29 |
| `numeric` / `rankable` | 这个版式对内容有一条具体要求：{具体}。其余部分通用。 | S05 / S10 |
| `none` | 机制自成一件，与你的内容无关；换什么内容它都长这样。（差异化风险，不是可用性风险） | S03 / S20 / S14 |

**这个改法的好处**：`hard` 从「劝退开关」变成「形态提示」，用户读到的是**可执行的约束**（"我需要提供互斥关系"）而不是**不可反驳的判断**（"你不适合"）。而且它自动消解了 §5.1 的争议 —— 结论分歧只影响分支归属，不影响「能不能用」。

**第四层：怎么验证撤对了？—— 用可证伪的验收口径，不用感觉。**

撤一个警告前，必须过这一关（写进验收单，不靠评审）：

> **反向替换验收**：构造 `C_diff`（同条数、异形态），把它当作真实内容按该案机制排版。若产出的签名元素**仍然成立**（§2.2 四类缺陷全不出现），则撤警告正确；若出现任一类缺陷，则**不撤**，改为按 `inputShape` 降级话术。

本轮 5 个撤标案的这个验收状态：

| 案 | 反向替换验收 | 状态 |
|---|---|---|
| S03 | 换成任意「条目 + 一个数值」，高度仍按 0.9333 折叠（因为它是作者期规则，人工套用即可） | ✅ 可撤 |
| S10 | 换成任意「行 + 两个可排序数字」，6:7:9:8:5 与 1.5px 错位完全成立 | ✅ 可撤 |
| S20 | 不读内容，任意内容都成立（代价是图与内容无关 —— 差异化问题） | ✅ 可撤 |
| S14 | 统一宽度零碰撞 ⇒ 不要求内容质量差 | ✅ 可撤 |
| S05 | 面板成立；但**点阵读数遇中文为空** ⇒ 有窄缺陷 | ⚠️ 撤 hard，但保留 `numeric` 分支提示 |

### 5.4 其他坑（按危险程度）

1. **改 hard 的地方有三处，改错一处不会报错**。真源是 `build-prompts.mjs` 的 `HUMAN`；`prompts.js` 是生成物；`hardIds` 字段是**哑弹**（零消费）。只改 `prompts.js` 会被下次生成覆盖；只改 `hardIds` 完全无效。**必须改 `HUMAN` 再重跑生成器。**
2. **`HUMAN` 块已经证明会腐烂**（H-5：6/9 的 `minItems` 与实测不符，9/9 的 `minPics` 不符）。所以**不要用类似方式手写新的 `inputShape`** —— 它必须是 §3.2 探针算出来的，写进 JSON，再由生成器读。
3. **S03 的 `degrades` 一改，会连带改变提示词正文。** `prompt-copy.js:233-237` 按 `degrades` 二分：`yes` 时输出「单元位置是手工排定的…不要留空槽」，`no` 时输出「自动流排版」。改 S03 的 `degrades` 会让 S03 的提示词第 2 条整句换掉 —— 这是**正确的连锁反应**，但必须有人确认新句子对 S03 成立（成立：8 条带位置固定）。
4. **CDP 探针有环境依赖**：需要本机 Chrome（已确认存在）+ Node 22+（本机 26.12.1）。**探针跑在 `file://` 下**，没有跨域问题；但如果将来原型改成走 `http://`，`file://` 假设会失效。
5. **探针会残留浏览器进程**。本轮有一次探针输出了正确结果但 `pwsh` 进程不退出（被转入后台）。**协议里必须 `await b.close()` 并给外层超时**，否则 CI 里会挂住。
6. **不要用「视觉印象」复核**。9 个 hard 案里，S03 / S14 / S20 视觉上都极其「工业/专业」，但它们的机制恰恰最不依赖内容。**这个案子的教训就是：视觉上的专业性 ≠ 机制上的内容依赖。**

## ⑥ 我判断里可能错的地方

按「错了后果最重」排序。

1. **H3 的 70% 阈值是我拍的，不是推出来的。**
   它的作用是把「大概率违背」变成可复算的数，但 14/20 这个门槛没有依据。**改阈值会直接改变边缘案的归属** —— S05（数字读数很常见）和 S10（可排序数字很常见）最可能翻。如果有人用 50% 阈值重跑，S05/S10 可能变成 hard。**建议：把这个阈值写进配置文件并标注「约定，非实证」，让分歧可见而不是隐藏。**

2. **S20 判「不 hard」我最有把握，但也最可能有争议。**
   我的理由是 `readPath = none`（机制不读内容）。但另一种读法成立：**「不读内容」本身是一种更强的问题** —— 用户拿 S20 做餐饮页，会得到一张与餐饮毫无关系的声场图，那比「退化」更糟。如果评审认为「机制与内容无关」**也应该警告**，S20 就该保留警告，只是话术从「换内容会退化」改成「它不消费你的内容」。**这是价值判断，不是测量结果，我不该替它拍板。**

3. **S21 的「对称 + 度 2–4」可能过拟合了这份实现的随手取值。**
   我测出 42 条互斥全对称、`angle = 15 × pairs` 恒成立。但这可能只是**作者把同一张表写了两遍**（先定 pairs 再顺手算 angle），不是「机制要求」。
   反证方向：如果我把 `data-angle` 改成不满足 15×pairs 的值，页面**不会报错**，只会显示错误的切口（实测：改 `data-pairs` 不改 `data-angle`，切口类名不变、角度不变 —— 即角度是静态 class）。**所以「angle = 15×pairs」是作者的写作习惯，不是运行期强制。** 这意味着 H1 对 S21 的支撑比我在 §1.1 里写的弱：真正撑住 S21 的是「互斥图必须存在且封闭」，而不是「角度必须等于 15 倍」。**如果只保留后半句，S21 的 hard 依据仍成立（无互斥关系就没有切口档位可言），但我在表格里并列的两条证据不等重，这一点我写得不够严谨。**

4. **S03 的 0.9333 系数，我只验证了 8 个点。**
   `h = round(0.9333 × 曝光秒)` 在 8 个样本上残差 ≤0.05 px/s，但 8 个点拟合一个系数，**不能排除作者是逐条手填的**（实际上 `style="--h:28px"` 就是手填）。若如此，H1 对 S03 的成立性更弱 —— 不过这不影响结论（H2 已经失败），只影响我给它记的 `readPath` 应从 `authoring` 改成 **`manual`（逐条手填，无统一规则）**。这个区分我漏了。

5. **§3.4 的机械筛表只能证伪「hard 与写死位置相关」，不能证明「hard 与任何静态指标都不相关」。**
   我用的 6 个指标是随手选的。换一组指标（比如「内容节点的 CSS 选择器特异性」「是否存在 `content-visibility`」）可能显示不同的聚集。**这张表的正确用法是「找出候选」，不是「排除候选」。**

6. **我没有验证「换内容后页面是否仍然好看」。**
   全部实验测的都是**机制的结构完整性**（高度、碰撞、互指、折页位置）。一个案子可以「机制完整但视觉退化」—— 例如 S15 换成菜谱后，14 个热区仍然按面积比例画，但「热区 = 舱室」的语义消失了，页面会变成一张无意义的几何图。**我的判据抓不到这一类退化。** 如果评审认为「语义退化」也该算 hard，那 S15 / S29 的 hard 依据要加一条 H2 的新形式（语义前提被违反），而这会**扩大** hard 集合，可能把 S18 / S21 之外的案子也拉进来。

7. **两个我自己抓到的测量错误，说明这类任务的主要风险在方法而不在判断。**
   - S18：测错了宿主节点（测第 1 个 `<pre>` 的 480px，实际删的是第 2/3 个 `<pre>` 的行），差点写成「高度不跟内容」的假缺陷。
   - S15：正则没限定 `<tr>` 内，把图版说明的 `m²` 也算进来，得到 361.68 m² / 覆盖率 252.3%，比正确值（68.80 m² / 48.0%）大三倍多，**足以把结论推向相反方向**。
   **这两次都发生在「用脚本抓数」而不是「判断」的环节。** 建议：任何进入报告的数字，必须有一个**手算或用第二种方法算出的对照值**；两次不一致时，先怀疑脚本。
