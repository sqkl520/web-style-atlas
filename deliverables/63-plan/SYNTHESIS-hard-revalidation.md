## 2. 被推翻的三条关键证据（独立验证 Agent 用 CDP 实测）

### 2.1 S18「前三个精确命中」是伪精度

审计说：`--at:5/10/18` 精确命中第 5/10/18 行的牌。
**实测**：CSS 规则是
```
style.css:122  .hangrail .hang{ top: calc(var(--at,0) * var(--line) + var(--line) + 2px) }
style.css:17   --line: 24px
```
`top = at×24 + 24 + 2`，而第 n 行顶部是 `(n−1)×24`。解 `at×24+26 = (n−1)×24` 得 **n = at + 2**。
⇒ 四张牌**全部偏 +2 行**（5→第7行、10→第12、18→第20、34→第36），一张都没命中。
审计把 `--at` 的源数据值当成了渲染后的行号。

**这是真 bug**（不是 hard 判据）：`+ var(--line)` 应该去掉，改回 `top: calc(var(--at) * var(--line) + 2px)`。
另外 `--at:34` 应对应第 28 行（857 牌所在行），现在也是错的。

### 2.2 S14 的 H1 链不成立

审计说：`build/polar-layout.py:47` 的 `estimate_h(len(body))` 用正文字符数算高度 → 坐标依赖数据。
**实测**：`lines = max(3, estimate_h(...))`，而 **9/11 条撞下限**——字数根本不参与。
把 11 条高度全拍平，**只有 1/11 个坐标动 24px**；逐条扰动有 6/11 条纹丝不动。
CDP 实测正文涨到 1.7× 仍零重叠。
⇒ 真实依赖是 `--w` 与 r 档（纯数量），**与行业无关**。撤。

### 2.3 S15 的引用伪造（但结论对）

审计说：「按 `S15.md:26` 1 单位 = 1.25cm」。
**实测**：该行讲的是 12 栏 / 8px 基线，**一个字没提换算**。6400 是从数据反推的。
但残差 14/14、0.0000% 我复算**成立**，且验证 Agent 补了更强的一条：14 个 rect 的 x/y/w/h **全是 8 的倍数**。
⇒ 结论对，引用错。保留。

## 7. 方法论教训

三份审计的分歧不在读得细不细，在**证据强度表述**。
出错的全部集中在「需要跑一次页面才能确认的地方」：S18 的渲染位置、S08 的坐标范围、S14 的坐标敏感性。

**下轮规则**：渲染位置断言必须附 CDP 测量值；只读代码可以下「有没有读取语句」的结论，不能下「渲染在第几行」的结论。

## 8. 替换实验的结论与它推翻的东西

替换实验 Agent 交付了**最后一份、也是方法最严的报告**：9 案 × 3 视口 × 4 个变体，216 张截图。

**结果：9 个 `hard:true` 里 8 个 NOT-HARD、1 个 PARTIAL，无一案接近 15% 阈值。**
最大文档高变化只有 **1.09%**（S21 的 768 档），S29 三视口逐像素全同。

**这个结果是反直觉的，且它自己抓出了第一轮的假象**：
第一轮替换后 S03/S05/S10 有 20–26px 位移，它差点写成"轻微退化"。
加了一组对照（**只换中文、数字与拉丁保留**）后发现：**9 案全部 0px**。
原来那些位移全是它自己替换拉丁署名（如 `Haraldmmueller · CC BY-SA 4.0`）导致来源行重排的假象。

**它给出的机制解释推翻了我对 hard 的整个理解框架**：
这些原型把数据**预先炸进标记**——S14 有 110 个 CSS 变量、S21 有 175 个 `data-*`、S29 有 51 个数值 `data-*`、S20 有 33 条 SVG path。
**文案是最自由的一层，机制根本不读它。**

> 所以准确的说法是：**版式没崩，是故事崩了**。
> S03 的"带高 = 曝光秒数"在水果版里已成空话——几何 0px 变化，语义归零。

### 这个结论与我的裁决冲突吗？

**不冲突，但改变了 hard 该表达什么。**

| 我的裁决 | 替换实验 | 如何并存 |
|---|---|---|
| S15/S18/S21/S29 保留 | 8/9 判 NOT-HARD | 实验测的是**版式会不会崩**（=degrades）；hard 问的是**机制读不读数据值**（=看不到但存在） |
| S03/S05/S10/S14/S20 撤销 | 同样 NOT-HARD | 一致 |

实验只能证伪"换文案版式会崩"，证伪不了"机制依赖数据的形态"。
**S29 就是最好的例子**：三视口逐像素全同，但它的 23 个编号 `data-part` / `tr#part-NN` / `data-back` 三列严格双射——
换内容不崩，是因为**作者已经把数据炸进标记了**；而对用户来说，"你得先有 23 个带唯一编号且能交叉引用的条目"这个要求仍然成立。

⇒ **hard 的正确表述不是"换内容会退化"，而是"你得先具备某种数据结构"。**
这正是概念批判 Agent 建议的方向（`portability.requires{what, ifMissing}`），也与我保留 4 案的理由一致。

### 实验自己标注的四个局限（我照录，不掩饰）

1. **强制每条文案等长**，等于替案子挡掉了最易崩的一种替换。真实换行业时长度会变，长度敏感性要另测。**NOT-HARD ≠ 可以随便换内容。**
2. **只测版式不测语义**。
3. S21 的字体问题**靠几何指标发现不了**（宽度同为 1em）——它的文津宋体是按本页 455 个实际用字手工裁切的子集（71 个 unicode-range 分片），73 个水果字形无一在内，回退系统衬线体。凡自建裁切中文字体的案都会踩。
4. 不等 `fonts.ready` 量，S21 的 docH 在 4676–4728 跳。
