# 选型台详情面板 · 信息架构与可发现性审查

审查对象：`prototypes/_selection/`（30 个案选型台），详情面板 `#detail`。
方法：Chromium 156（真实浏览器，CDP 驱动），逐字段量 **起始 top / 高度 / 字数 / 首屏可见比例**，并在 8 种结构方案 + 2 个候选推荐上重复同一套探针。
所有数字均为实测，未估算。复现脚本见 §9。

### 关于「滚动 3.3 屏」这个既有数字

任务书写的 `scrollHeight ≈ 2991px / clientHeight 900 = 3.3 屏` 现在已经不成立了。本次实测为 **3969px / 4.41 屏**（S15）、3684px（S08）。差额来自上游两次数据变动：`layout` 字段补进 30/30（+490.5px）与「可落地要点」的接入。**「越堆越深」这个趋势是真的，而且比任务书记录的更严重** —— 详见 §1.1 与 §1.2。

> **⚠️ 审查期间页面还在长（必读）**：另一位 agent 正在往详情面板顶部加一个「提示词填充」表单。实测同一台机器、同一份 `index.html`，**在本次审查的 60 分钟里**：`.prompt-cta` 从 **92.8px 涨到 348.7px**，首个字段的 top 从 **1156 → 1411.9px**，面板从 **4.41 屏 → 4.69 屏**（桌面）、**6.00 → 6.33 屏**（移动）；前导占首屏可用高度的比例从 **131.5% → 163.1%**（桌面）、**150.7% → 189.0%**（移动）。也就是说：**这个问题正在自动恶化，而且恶化速度比任何一次修复都快。** 本报告的所有结构方案都跑在冻结快照上（下段），所以**结论的排序不受这次漂移影响** —— 反而更成立：推荐方案的第一条动作（把前导压成一条）现在能省下的高度是 1323px，不是 1067px。

## 0. 结论摘要（给赶时间的人）

1. **真正的问题不在字段堆叠，而在字段之前的前导。** 快照里字段正文从 **1156px** 才开始（现在线上已是 **1411.9px**），而首屏可用高度只有 **811.6px**（900 − 88.4px sticky 头）。也就是说：**即使把 11 个字段全部折叠成 0 高度，首屏也一个字段都露不出来。** 面板里 69.4% 的高度是字段，但用户打开时先撞上的是前 30.6% —— 而那 30.6% 里的每一块（预览器、闸门、四处文案）单独看都合理，合起来是 1.3–1.6 屏。
2. 因此「加折叠」单独做没有用。实测：甲（分组折叠）首屏完整字段 **0**，丙（摘要+核心展开）**0**，戊 **0**。把所有字段折起来只把面板从 4.41 屏压到 3.51 屏，首屏内容一个字没变。
3. **「可落地要点」不是被埋起来的，它是被上一次修复埋起来的。** 它落在 **2364.8–2777.5px**（第 2.6–3.1 屏），而用户打开面板时看到的是预览器 + 闸门 + 四条文案。

   > 数字订正：任务书里记的是「落在 1874–2313px」。那是 `data.js` 还没有「布局与网格」时的落点。本次审查期间上游补了 `layout` 字段（30/30 有值，490.5px），把「可落地要点」又往下推了 **490.5px**，现在更靠下。上一轮把它接进面板这件事本身没错，错在**接进来的位置之前已经堆了 1156px 的别的东西**。
4. 现状面板里**没有任何可折叠/跳转机制**：`details` 0、`summary` 0、`[aria-expanded]` 0、`[role=tab]` 0、`a[href^="#"]` 0、`nav` 0、正文里的 `h3–h5` 0。唯一的 sticky 元素是 `.detail-head`。（完整清单见 §1.5）
5. 推荐方案（壬）实测：桌面 **1.85 屏**（3969 → 1663px，−58.1%），移动 **2.45 屏**（5065 → 2064px，−59.2%）；首屏从 **0 个字段**变成 **1 个完整字段 + 3 行判断事实 + 全部 5 个折叠组的标题**（标题里逐字写着里面有哪些字段）。
6. 代价必须说清楚：折叠让 8 个字段退出**无障碍树**（但不退出 Ctrl+F 文本索引），这是这套方案唯一的真实损失，见 §7.3。

### 3.2 逐方案取舍

**甲 · 字段分组 + 折叠（5 组，观感/版式两组默认展开）**
- 用户看到：前导不变（1156px），滚过前导后是 4 个字段全文，然后 3 条折叠行。
- 需滚：3.51 屏（省 0.9 屏）。**首屏字段 0。**
- 成本：低。只加 `<details>` + 分组容器，不动字段内容。
- 风险：折叠组 summary 若不列出内部字段名，收起=藏起来。实测我第一版 summary 有 CSS 网格 bug（文本 span 落进 18px 的 marker 列，逐字换行，一条 summary 高 **565px**），折叠反而使面板变高 —— 折叠件的排版本身就会翻车。

**乙 · 顶部 11 个字段锚点跳转条**
- 用户看到：字段上方多一条 sticky 的 11 个按钮，内容一字不少。
- 需滚：**4.53 屏，比现状更差**（跳转条自己吃掉 111px）。首屏字段 0。
- 成本：低-中。要处理锚点落点被 sticky 头 + 跳转条双重遮挡。
- 风险：**它解决的是"找不到"，不解决"太深"**。而且它把 11 个字段名一次性摊在顶部，在 390px 下必然折成 3–4 行（实测 390px 全展开版把面板顶到 6.21 屏）。用户还得先知道该点哪个 —— 而字段名的信息量（"美学家族与参考"）对第一次来的人几乎为零。

**丙 · 摘要卡 + 核心 3 段展开 + 其余折叠**
- 用户看到：摘要卡（定义/配色/适合/不适合），然后 3 段全文，5 条折叠行。
- 需滚：2.67 屏。**首屏字段仍 0** —— 摘要卡本身 150–250px，正好把已经 131.5% 的前导推得更远。
- 成本：中。摘要要从 `def`/`palette`/`scenes` 里现抽。
- 风险：摘要与「一句话视觉定义」内容重复，白花 150px+；且 5 个折叠组里有 3 个是"实现"，读起来像技术文档。

**丁 · 双 tab（看设计 / 看实现）**
- 用户看到：一个二选一的 tab。选"看设计"是 9 个字段，选"看实现"是 2 个。
- 需滚：3.47 屏。**首屏字段 0**（前导还是那 1156px）。
- 成本：中。要新增 tab 语义（`role=tab`/`aria-selected`）+ 状态记忆。
- 风险：**"实现"这一层被藏进第二个 tab 里，恰好是「可落地要点」最容易被判"不存在"的形态** —— 与这一轮要解决的问题正面冲突。而且它把 9 个字段原样留在"设计"页，等于没减负。

**戊 · 结论卡 + 核心 3 段 + 按任务分组的 3 个折叠组**
- 用户看到：结论卡 4 行 + 3 段全文 + 3 条按任务命名的折叠行（"它为什么长这样"/"会动什么"/"要动手做"）。
- 需滚：2.77 屏。首屏字段 0。
- 成本：中。
- 风险：同丙，卡重复占位；且分组名是"任务"而非"内容"，用户想找"字体"时得先猜它被归到哪一组 —— 除非 summary 里逐字列出。

**己 · 只折预览器（对照组）**
- 用户看到：预览器变成一条 62px 的 summary，字段全平铺。
- 需滚：4.01 屏（只省 0.4 屏）。首屏 1 个**部分**字段。
- 价值：这个对照回答了一个关键问题 —— **单折预览器值得做，但它只值 0.4 屏**；439px 的预览器省下来后，第一个字段从 1156 挪到 792，才刚够"露出标题"。

**庚 · 己 + 甲**
- 3.08 屏。首屏 1 个部分字段。省 1.33 屏。仍不进完整字段。

**辛 · 前导收缩（预览器 + 文案配件）+ 摘要 + 3 段 + 3 组**
- 2.02 屏 —— 第一次真正压进 2 屏附近。首屏 1 个部分字段，但**首个字段 top=871**，只露出 30px 标题，等于没读到。
- 教训：光把前导从 1156 压到 535 还不够，因为摘要卡又吃掉 150px+。

**壬 · 推荐（见 §5）**
- **1.85 屏（桌面）/ 2.45 屏（移动）**，首屏 1 个完整字段 + 3 行事实 + 5 个折叠组标题，首个字段 top=**425.2**。

## 4. 移动端特判（390×844）

移动端不是"桌面缩小"，是**另一个数量级**：

| 指标 | 桌面 900 | 移动 844 | 变化 |
|---|---|---|---|
| 面板宽 | 560 | **390**（全屏层） | 内容列宽 −30% |
| 首屏可用高度 | 811.6 | 734.5 | −9.5% |
| scrollHeight（现状） | 3969 | **5065** | **+27.6%** |
| 屏数 | 4.41 | **6.00** | +36% |
| 前导高度 | 1156 | **1216.1** | +5% |
| 前导/首屏可用 | 131.5% | **150.7%** | 更糟 |
| 单字段最高（布局与网格） | 490.5 | **723.6** | +47.6% |
| 可落地要点高度 | 412.7 | 568.2 | +37.7% |

**同样字段堆叠在 390px 下的具体后果：**

1. **「布局与网格」一个字段就占 723.6px = 移动首屏可用高度的 98.5%。** 一个字段几乎整整一屏。桌面版它是 490.5px（60% 屏）。
2. 字段区总高 **3790.8px**，是移动首屏可用的 5.16 倍。用满屏步进要滚 **6 次**才到最后一个字段。
3. 前导里 `.parts` 从 299.7 涨到 **377.4**（错误状态那条折成 119.8px），`.prompt-cta` 从 92.8 涨到 **112.2**（风险提示折 3 行）。

### 5.2 三个必答问题

**① 用户第一次打开面板，第一眼看到什么？**

桌面 900px 内（实测 S15 / S08 / S29 三案一致）：
- 复制 AI 提示词按钮（120–213）
- 原型预览一条（217–279，写着当前档位与"点开看三档截图"）
- 打开原型 + FAIL/WARN + 闸门数字（297–401）
- **一句话视觉定义全文**（417–571）
- **配色 / 适合 / 别用在这 三行**（571–837）
- 关键视觉元素标题 + 前两行（837–900，截断）

首屏可读字数 **689 字（S15）/ 786（S08）/ 755（S29）**，现状是 **0**。

移动 844px 内：复制按钮、预览器一条、闸门、**一句话视觉定义全文**（508.6–688.2）、配色行、"适合"行开头。首屏可读 **557 字**，现状 0。

**② 想深入的人怎么找到深字段？**

三层递进，任何一层都不需要"猜"：
1. **折叠组的 summary 逐字列出组内字段名**（`美学家族与参考 · 字体策略`），不是"更多"、不是"实现细节"。用户想找字体，扫一眼 5 条 summary 就能定位到第 1 组。
2. **summary 报出组内规模**（"3 段 / 约 658 字"）。用户能判断"点开要读多久"。
3. **Ctrl+F 仍然有效**：折叠内容留在浏览器的文本索引里（实测 4 个只出现在单一字段里的词，折叠后 `resultCount` 仍为 1）。这一点让"折叠"不等于"删掉"。

外加两条不新增控件的兜底：`J/K` 换方案（已有）、`Esc` 收起（已有）、`#S07` 深链（已有）都不受影响。

**③ 我放弃了什么？**

1. **放弃了"11 个字段一眼全见"。** 现状虽然 0 个进首屏，但滚到底确实能看到 11 个标题。壬只有 3 项默认可见 + 5 条折叠标题 —— 8 个字段名要靠 summary 读，不再有独立的 13px `dt` 行。
2. **放弃了无障碍树里的 8 个字段**（实测见 §7.3）。折叠内容退出 AX 树，屏幕阅读器用户要展开才能读到。这是这套方案**唯一的真实损失**，不能用"Ctrl+F 还能搜到"糊过去。
3. **放弃了「布局与网格」作为独立可见字段。** 它 490.5px（移动 723.6px）是单个最高的字段，只能进「要动手做」组。
4. **放弃了「可落地要点」的平铺可见性。** 它从"没人知道存在"变成"标题里点名 + 折叠组第一行"。改善是真实的（从 0 曝光变成 1 次标题曝光 + 1 次字段名曝光），但它仍然不是默认展开 —— 因为它 412.7px，展开就吃掉半屏，而这轮的目标是"让值得读的字段进首屏"，不是"让最长的字段进首屏"。
5. **放弃了 `.parts` 的默认可见。** 四条文案从 836px 挪到面板末尾并折叠；它们已并进复制内容，需要单看的人点一下。

### 5.3 实施要点（给改代码的人）

- 折叠用原生 `<details>/<summary>`，不要自造 `div + aria-expanded`（键盘、Ctrl+F、`::marker` 全部免费）。
- **summary 必须是两/三行结构**：组名（16px 600）+ 副标题（13px 灰）+ 字段名列表（13px）。字段名列表是这套方案的核心，不能省。
- ⚠️ **`summary` 用 CSS grid 时，文本 span 必须显式 `grid-column: 2`**。我第一版没写，`::before` 的 `+` 占第 1 列 18px，三个 span 被自动塞进第 1 列逐字换行，**一条 summary 高 565px**，折叠反而让面板从 3969 涨到 4135。这是实测踩到的坑，写进验收项（§8-C4）。
- 折叠状态**不要持久化到 localStorage**：同一个 `<details>` 在换方案（`J/K`）时要回到默认态，否则用户上次展开的"实现"组会跟着他进下一个案。
- 预览器折叠后仍要能切三档 —— 把 `.viewer` 整体放进 `<details>` 内即可，`viewer-tabs` 的 click 处理器由 `renderDetail` 重新绑定，不受影响。
- 闸门明细用 `<details>` 包 `.gate-rules`，summary 写"FAIL n / WARN n"。**summary 必须有 ≥ 4px 的垂直 padding**：我第一版没加，实测高度 23px，低于 24px 的触控下限（验收项 C7 抓出来的）。
- **若「提示词填充」表单（另一 agent 正在加）留在面板顶部，把它一起折进「复制 AI 提示词」那条**，别再让它单独占 256px。实测它已经把 `.prompt-cta` 从 92.8px 顶到 348.7px，首个字段被推到 1411.9px —— 比本报告开始审查时又深了 256px。

## 7. 风险与代价（实测，不是推测）

### 7.1 Ctrl+F 仍然能找到折叠内容 —— 已验证

用只出现在**单一字段**里的词做文本索引探测（`DOM.performSearch`，与浏览器查找条同一套 TextFinder）：

| 词 | 所在字段 | 现状 resultCount | 折叠后 resultCount |
|---|---|---|---|
| `shape-rendering` | 可落地要点 | 1 | **1** |
| `阻尼` | 动效与交互 | 1 | **1** |
| `毛口` | 关键视觉元素 | 1 | **1** |
| `图例悬挂` | 布局与网格 | 1 | **1** |

结论：**折叠不破坏查找。** 但注意：浏览器不会替你展开 `<details>`，用户搜到后仍需自己点开（Chrome 152+ 有 `hidden=until-found` 可自动展开，本仓未使用；若要更稳可以加，但会增加实现面）。

### 7.2 折叠组永远不会被"顺手"读到

现状虽然深，但滚动是连续的 —— 用户滚到底会**顺路**扫过全部 11 个字段。折叠后，8 个字段必须**主动点击**才会出现。这是可发现性的真实交换：**从"深但连续"变成"浅但需要主动"**。缓解手段只有 summary 里逐字列出字段名（§5.2-②）。

### 7.3 无障碍：8 个字段退出 AX 树 —— 已验证

`Accessibility.getFullAXTree` 全树文本检索：

| 词 | 现状在 AX 树 | 折叠后在 AX 树 |
|---|---|---|
| `shape-rendering`（可落地要点） | ✔ | **✘** |
| `阻尼`（动效与交互） | ✔ | **✘** |
| `图例悬挂`（布局与网格） | ✔ | **✘** |
| `毛口`（关键视觉元素，仍展开） | ✔ | ✔ |

AX 节点数 2461 → 2412（−49）。**这是推荐方案唯一的实质损失。** 若这条不可接受，替代做法是：默认展开「要动手做」组，代价是面板 1663 → ~2080px（约 2.3 屏），首屏字段仍是 1 个 —— 也就是说**展开它不牺牲首屏，只牺牲总深度**。这是一个可以在实施时单独决策的旋钮，我把数据留在这里而不替产品决定。

### 7.4 其他

- **滚动穿透（现状已有，非本方案引入）**：面板打开时 `body` 的 `overflow` 是 `visible`，把面板滚到底后继续滚轮，背景清单会跟着滚（实测 `pageY 0 → 600`），关掉面板后列表停在 600px。这会让用户"关掉面板后不知道自己在列表哪一行"。**建议顺手修**（`body.detail-open { overflow: hidden }` 或 `overscroll-behavior: contain`），但它不在本轮范围内，故只记录。
- **触控目标**：壬的「闸门明细」summary 实测高 **23px**，低于 24px 的常见下限。要么加 padding，要么去掉这条折叠（闸门明细本来就少有人看）。其余所有可点元素 ≥ 33px。
- **390px 横向溢出**：全部 8 个方案 + 推荐方案均为 **0**。前提是不要做横向滚动的 tab/锚点条。

## 9.5 验收项被自己的脚本验过一遍（自审记录）

我把 §8 写成了可执行脚本 `lab/verify-acceptance.mjs`，让它跑推荐方案和现状两份。第一轮它判了我 4 个失败，其中 3 个是**我自己方案的问题**，1 个是**我报告的事实错误**，都已改：

| # | 脚本报的问题 | 性质 | 处置 |
|---|---|---|---|
| C1 | 折叠组 7 组，超出我写的"3–6 组" | 我的期望值写错（7 = 2 个字段组之外的预览器/配件/闸门辅助折叠） | 期望改为 3–7，并在准则里说明含辅助折叠 |
| C7 | 「闸门明细」summary 高 23px < 24px | **方案缺陷** | 给 summary 加 `padding: 4px 0`，现在 ≥ 31px；因这 8px，全表数字上移约 8px，报告已同步 |
| C8 | 面板滚到底后背景页仍跟着滚 | **现状即有缺陷**，非本方案引入（对现状跑同样失败） | 保留为验收项并显式标注"现状即有"，列入 §7.4 建议顺手修 |
| E4 | 30 案全部渲染 **11** 个字段，不是 10 个 | **我报告的事实错误** | 面板字段 = 10 个作者正文字段 + `palette` 渲染的「当前有效配色」= 11；§2 已改正并写明口径 |

最终：**推荐方案 31 项通过 / 1 项失败（C8，现状即有）**；对现状跑同一脚本则 A2–A7、B1–B4、D3–D8 全线失败 —— 这正是这套验收标准要区分的东西。

> 这一节存在的理由：如果验收标准只被"设计者本人读过"，它等于没写。能被自己的脚本判失败，才说明它有判据。
