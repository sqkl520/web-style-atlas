## 3. 我选的方案，以及我为什么改掉了最初的设计

### 3.1 我放弃了 A2（把向导按钮一起折起来）

A2 比 A 多省 100px，是"省得最多"的页头版本。**我不接受**：向导是这页除了清单之外唯一的第二条主路
（筛不出来 → 五个问题 → 3 个推荐 + 3 个明确排除），把它折进"这个图集是什么"下面，
等于用首屏数字换掉一个入口。manifest 里 66-audit 已经把"入口沉到 2.6 屏以下"判过一次缺陷，我不能在同一页上重犯。

**折中做法**：向导留在折叠块外面，并且**位置从 claim 之后挪到 claim 之前**。
为什么必须挪：`<details>` 只能包住**相邻**的兄弟节点，而原来 DOM 顺序是 claim → 向导 → exit，
三选二就得挪一个。挪向导的收益是 DOM 变成「标题 → 主按钮 → 解释」，
而且 1440 档上按钮比改前**高了一位**——这一位移动在桌面档是零代价的（§4.2 实测 Δ0.0）。

### 3.2 筛选栏：整条折，不做"只折后六组"

你说"保留「你是做什么的」这一组，其余折起来"。我实测了这个版本：那组常驻就占 **212.4px**
（20 颗芯片 + 提示行 + 「还有 28 个」按钮），加上一条 summary，首卡只能压到 **620 左右**——
**首屏还是 0 张完整卡**（844 − 620 = 224px 可用，而卡最矮也要 372.7）。

而且这里有个更根本的原因（§1.3 已提）：390 档的 rail 高度由 `40vh` 决定，不由内容决定。
所以"留一组"不是"省了一部分"，是"一点都没省"——`40vh` 那条限高照样生效。

所以整条折起，summary 上写清里面有什么：**「筛选 · 11 组 47 颗芯片（第一组是「你是做什么的」）」**——
组数、芯片数、第一组是什么，三个信息都在这行字上。
并且把 980 档那套 `max-height:46vh + overflow-y:auto` **取消了**（换成折起 + 展开时自然高度）：
那套限高制造的内滚嵌套本身就是个缺陷，不该在折叠版里留着。

### 3.3 行卡：我否掉了"压 max-height"，改用"缩宽度"；宽度定 160 而不是 176

**先否掉压高度。** 最初 D 方案用的是 `.shot img{max-height:104px}`。它省得够，但**裁切变重了**：
390 档这一列是满宽 358，16:9 的图本来高 201.4，压到 104 等于把它裁成 **3.4:1 的横条**——只剩桌面首屏最上面那一条。

改成 `.shot:first-child{max-width:Npx}`：图缩成 **N×(N×0.5625) 的完整 16:9**，
`object-fit:cover` + `object-position:top center` 的裁切口径**一点没变**，只是整体变小。
同样省 100px，前者还看得出首屏长什么样，后者只剩一条横幅。

**再否掉"176 就够"。** 176 是照着首卡 S01 定的（余量 21.1px，看起来够）。
但 §4.1b 的逐案矩阵推翻了这个结论：把排序切到「闸门」时首卡变成 **S13 = 454px，差 22.4px，首屏又变回 0 张卡**。
30 案里超过"首卡位置能容纳的上限"（当时是 431.6px）的有两个：S13 454、S20 434.5。
S13 高的原因是**真实内容**，不是排版：WARN 5 条（S01 是 4 条）→ 行脚注 5 行而不是 4 行（+19.5px）；
家族 213 字（S01 147）→ 元数据行 89.5 而不是 65.4（+24.1px）。**这部分钱不该由 CSS 硬削。**

所以改法从"削 S13"改成两步：**先把留白收干，再让图宽补足**。

| 步骤 | 首卡(S01) top | 最高卡(S13) 高 | 最坏余量 | 说明 |
|---|---|---|---|---|
| 起点：chrome 已折 + 图 176 | 412.4 | 454.0 | **−22.4** | 默认排序看着够（S01 410.5 / 余 21.1），gate 排序就露馅 |
| + `.main` 上内距 16→10 | 406.4 | 454.0 | −16.4 | 折叠态下这 16px 夹在筛选条与搜索框之间 |
| + `.mast` 内距 8/6→6/4 | 402.4 | 454.0 | −12.4 | |
| + `.row` 内距 8→6 / 缝 10→8 | 402.4 | 446.0 | −4.4 | |
| + `.row-foot` 行高 1.5→1.45 | 402.4 | 442.8 | −1.2 | |
| + `.row-meta` gap 3→2 | 402.4 | 440.8 | +0.8 | 刚好过线，太薄 |
| + `.row-foot` gap 3→2 | 402.4 | 439.8 | +1.8 | 仍太薄 |
| **+ 图宽 176→160** | **402.4** | **430.8** | **+10.8** | ← 取这个 |

图宽梯度（其余不变，看最坏余量）：176 → **+1.8**（等于没达标）、168 → +6.3、**160 → +10.8**、
152 → +15.3（多 4.5px，不值再缩 8px 的图）。

**160 是目前这一版能给的"所有留白都收干 + 所有案都进得去"的交叉点**：30/30 案完整进首屏，最坏余量 10.8px。
代价是缩略图从改前 358×201.4 变成 160×90（面积 20%）。这是本轮最直接的一笔内容降级（见 §7.5）。

图注（`figcaption`，写着「1440」）改成绝对定位叠在缩略图右下角，省 20.8px。
它是视口标签不是内容，叠在图上反而更容易和那张图对上。

**家族行 clamp 保持 2 行，没降 1 行**：降 1 行能再省 19.5px，但「家族名 + 一句参考对象」
是这一行里信息密度最高的部分（S01 是 147 字、S13 是 213 字，2 行刚好装家族名 + 前半句）。
现在 30/30 已达标，没有理由再从这儿抠。

**行脚注 `line-height` 1.62 → 1.45、gap 3→2**：三行 WARN 标签在 390 宽度下本来就换行，
1.62 是纯松行距。字一个没删、序号一个没少，只收行距（S01 85 → 82.4；S13 的 5 行长脚注省得更多）。

### 3.4 工具条：修了一个我自己造成的 1440 回归

第一版把 `.sort` 与 `#reset` 包进 `<details class="bar-fold">` 后，1440 档 `.bar` **59.9 → 93**、首卡 **387.9 → 421.1（+33.2）**。

原因不是 padding，是 **flex 项换了人**：`.bar` 是 `display:flex`，改前直接子项是 `.search / .count / .sort / #reset`；
包一层后直接子项变成 `details` 这个块级盒，工具条从 1 行变 2 行。

试了 5 种写法，只有一种成立：

| 写法 | `.bar` 高度 | 首卡 |
|---|---|---|
| 只给 `.bar-fold{display:contents}` | 93 | 421.1 |
| 改 gap（12→18） | 93 | 421.1 |
| `.bar-fold{display:flex}` | 93 | 421.1 |
| 改 `.search` 的 flex-basis | 93 | 421.1 |
| **`.bar-fold{display:contents}` + `.bar-fold::details-content{display:contents}`** | **59.9** | **387.9 ✓** |

为什么前四种都不行：`<details>` 的内容其实还裹在一层 UA 生成的 `::details-content` 伪元素里，
**那层盒子仍然占着 flex 项的位置**。两层都 `display:contents`，`.sort` / `#reset` 才真正回到 `.bar` 的 flex 子项序列。
这不是"宽度不够"的问题，是盒层级的问题——所以调 gap 和 flex-basis 都没用。

### 3.5 最终结构

| 块 | 折叠什么 | summary 文字 | 留在外面的 |
|---|---|---|---|
| `#mast-fold` | `p.mast-claim` + `p#tpl-exit` | 这个图集是什么 · 想要现成模板去哪 | kicker / h1 / **向导按钮** / facts |
| `#rail-fold` | 整条 rail 的 11 组（`div.rail-fold-body` 包 11 个 `.rail-block` + lead + sep） | 筛选 · 11 组 47 颗芯片（第一组是「你是做什么的」） | — |
| `#bar-fold` | `.sort` + `#reset` | 排序 | 搜索框 / **计数（aria-live）** |

三块在 HTML 里都写 `open`（= 无脚本时就是今天的样子），由 `index.html` 里一段 20 行内联脚本在
`window.innerWidth <= 980` 时收起。**为什么默认写 open 由脚本往"收"的方向改、而不是写死收起由脚本往"开"的方向改**：
无脚本时写死收起会让正文在**所有**视口都看不见——那是真丢内容；写 open 最坏只是"没省下首屏"。

脚本放在 `data.js` 之前（不是 `</body>` 前），让它在首次绘制前执行完，否则 390 档会先按展开态画一帧（453px）再跳成 262px，用户看到明显重排。

**为什么不用 `::details-content{content-visibility:visible}` 做宽档展开**：那条我实测过也能 Δ0.0，
但只在 Chromium 131+ 成立，Firefox/Safari 桌面档会把两段散文吞掉——**真丢内容**，放弃。
