## 1. 任务 1：约束逐条抽取与分类

### 1.1 方法与口径

探针 `dump-prompts.mjs`（CDP，端口 8511）加载真实的 `prototypes/_selection/index.html`，
调 `window.buildStylePrompt(id)` 导出 30 条提示词全文 → `dump30-default.txt` / `dump30.json`。

> **踩到的坑**：任务书说「`buildPrompt(id)` 需要 `document`」。实际上 `buildPrompt` 是 IIFE 内的
> 私有函数，**没有挂到 window**；对外接口是 `window.buildStylePrompt`（prompt-copy.js:993）。
> 第一次跑直接 `TypeError: window.buildPrompt is not a function`。

`extract-constraints.mjs` 把每条提示词拆成**原子约束**（不是按行）。
理由：「1. 配色只用这几个值：#A、#B、#C、#D。不新增更多彩色。」是**一行 5 条断言**，
按行统计会把 5 条算成 1 条，M 类被系统性低估——而这张表是后续所有工作的分母。

**分类定义**（写死在 `extract-constraints.mjs` 顶部，任何人跑同一段代码得同一结果）：

- **M｜机械可验**：存在确定性提取器 + 二值判据。
- **S｜半机械**：需要先定义「哪些元素算数」或做模糊匹配。
- **J｜只能人判**：审美/气质/叙事，无判据。

### 1.5 一个结构性发现

**24 种行出现在 ≥25/30 案里，占全库字数 37.5%。**

也就是说：**30 条提示词的 62.5% 是逐案内容，37.5% 是同一份通用模板**。
其中「防退化 ①–⑧」「验收三问」「输出要求」三段对 30 案**逐字相同**，
共 **16 条约束/案**（6 条 M、8 条 S、1 条 J，外加首屏轮播那条已在结构段计数）
——**这 16 条只需验一次，不需要验 30 次**。这是 §4 成本模型的基础。

### 1.6 机制句里的 252 个数字：M 的最大假象

30 条机制句共抽出 **252 个数字**（去重 121 个）：101 个 `px`、23 个 `栏`、18 个 `%`、16 个 `°`、89 个无单位。

它们看起来最"机械"，实际上**几乎全部不可验**：

> 「一块实色多边形以 **11°** 切入 **4 栏**版心，**24px** 实体隔条撑开栏沟，红块越界压住 **3 行**正文」

`11°` 属于哪个元素？`24px` 是隔条的宽还是高？提示词没写。
**没有元素选择器的数字，无法机械比对**——这正是"看起来可验"与"实际可验"的鸿沟。
所以机制句整句归 **S**，那 252 个数字只作为「弱证据」存在。

## 2. 任务 2：提示词声称值 vs 原型实际 CSS 值（30/30）

### 2.1 先讲我踩到的四个量测坑（每个都单独做过对照实验）

这个任务的结论**完全取决于怎么量**。我第一版量法给出了 42 个 FAIL，其中大部分是我自己量错。
四个坑，每个都有对照实验证据：

**坑 1 — `getComputedStyle` 会把亚像素线宽取整。**
`probe-width-precision.mjs` 用 data URL 造了 0.4 / 0.8 / 1.25 / 1.5 / 2.4 / 5.5 / 14.5px 七条边：

| 声明值 | `getComputedStyle` 报 | Typed OM (`computedStyleMap`) 报 | CSSOM 声明值 |
|---|---|---|---|
| 0.4px | **1px** | 1 px | 0.4px |
| 0.8px | **1px** | 1 px | 0.8px |
| 1.25px | **1px** | 1 px | 1.25px |
| 5.5px | **5px** | 5 px | 5.5px |
| 14.5px | **14px** | — | 14.5px |

⇒ **只有 CSSOM 声明值保真**。用 computed 去验「线宽只用 0.4/0.8px」必定全错。

**坑 2 — SVG `stroke-width` 是用户单位，不是屏幕像素。**
`probe-units-derived.mjs` A 段：同一条 `stroke-width:2`，在 24 单位 viewBox 缩到 100px 时
渲染宽度是 **10px**，缩到 200px 时是 **20px**。

S19 的 `0.4px`/`0.8px` 恰恰画在 `<path class="e4/e8">` 上（`stroke-width:0.4` + `vector-effect:non-scaling-stroke`）。
我第二版拿 `computed strokeWidth`（报 `0.4px`）当 px 用是对的——**只因为这一案碰巧有 `non-scaling-stroke`**。
S15 就没有：拿用户单位比 px 会得出"超纲 0.5/0.8/1.2px"的假结论（那些是缩放过的手绘抖线）。

**坑 3 — 含 `var()` 的 CSS 简写在 CSSOM 里读出来是空串。**
`debug-shorthand.mjs` 在 S15 上实测：`border-bottom: 3px solid var(--pencil)` 的
`getPropertyValue('border-bottom-width')` 返回 `""`。
S15 有 **15 条**这样的声明，整批丢失，我第二版只剩 `2px` 一个值 → 误判"超纲"。
终局改用**原始样式表文本 + `:root` computed 值展开 `var()`**。

**坑 4 — 普通 HTML 元素的 `fill` 有 computed 值（黑色），但它不画任何东西。**
第一版把 `html`/`body` 的 `fill: rgb(0,0,0)` 统计成"99.99% 面积的黑色上屏"，
于是 **30/30 案**都多出一条假的 `#000000`。必须限定 `el instanceof SVGElement`。

**外加一个通用坑**：`CSSStyleRule` 在现代 Chrome 里**也有 `.cssRules`**（空的 `CSSRuleList`，truthy）。
写成 `if (rule.cssRules) { walk(...); continue; }` 会把**每一条样式规则**当容器跳过——
我的 `authorHex` / `declWidths` 一度全是空数组。必须判 `.length`。

### 2.2 终极判据：像素直方图（排除图片区域）

computed style 推出的"上屏色"每一版都有假阳性。**像素不会撒谎。**
`probe-pixels-masked.mjs` 的做法：

1. CDP 全页 PNG 截图 → 塞回页面 → `canvas.getImageData`
2. **先把所有 `<img>`/`<video>`/带 `url()` 背景的元素的包围盒铺成掩膜**，直方图只统计掩膜外像素
3. 每个主要色（≥0.3% 面积）算到最近声称色的 **ΔE（CIE76 on Lab）**

第 2 步是必须的：S21 有 20 张照片共 10.6MB，不遮罩会得出"作者新增了 `#C5BEAD`（占 6.87% 面积）"——
那其实是照片里的墙。

**结果（29 案有效，S02 全页被图片铺满、掩膜 100%，无法测）：**

| 指标 | 值 |
|---|---|
| 声称色占 CSS 绘制像素比例 | **均值 88.5%**，最高 S04 98.4%，最低 S06 38.1% |
| ≥90% 的案 | 20/29 |
| 80–90% 的案 | 6/29 |
| <80% 的案 | 3/29（S06 38.1%、S09 53.7%、S14 71.5%） |
| 真正「新彩色」（ΔE>6 且 饱和度≥0.15 且 色相偏离>25°） | **仅 2 案各 1 个**：S24 `#1B1136`(14.3% 面积)、S25 `#181C0D`(1.7%) |

### 2.4 不一致逐条列出

#### A. 线宽分级 — 5 案（HARD）

这一项是**唯一一处提示词明确承诺了精确值、而原型确实没对上**的地方。

**口径（四路都读，缺一路就会误判）**：
① CSS 边框/outline 声明值（`var()` 已展开，小数保真）
② `vector-effect:non-scaling-stroke` 的 SVG 线宽（等于屏幕 px）
③ CSS 里的 `stroke-width` 声明（无单位 = 用户单位，但**它是作者的意图值**）
④ 只统计"确实有元素在用"的宽度

> 我在这项上犯了两次错，都靠对照实验抓回来：
> 第一次漏了 `outline: 3px solid var(--spot-b)`（S25 的 `3px` 其实是 focus 环，不是 border）
> ——差点得出"声称的 3px 在原型里不存在"的假结论；
> 第二次漏了无单位 `stroke-width`（S15 的 `0.5/0.8/1/1.7` 全在这条路上）
> ——差点得出"声称值全在缩放的绘图几何上、不可复现"的假结论。

|---|---|---|---|
| S09 | 2 / 3 / 3.5px | 2 / 3 / **3.6**px | 超纲 3.6px |
| S10 | 1.25 / 2px | 1.25 / **1.5** / 2px | 超纲 1.5px |
| S15 | 0.5 / 0.8 / 1 / 1.7 / 3px | 0.5 / 0.8 / 1 / **1.2** / **1.4** / 1.7 / **2** / 3px | 超纲 1.2/1.4/2px |
| S25 | 3px | 3px（focus outline）+ **1.2**px（SVG 装订线） | 超纲 1.2px |
| S27 | 1.2 / 2.4 / 3px | **1.8**px（`--mis`）/ 1.6 / 3px | 超纲 1.8px；**1.2px 与 2.4px 从未落地** |

- **S09**：原型 CSS 注释自己写着「线宽 3.6px（区间 3.2–4.4）」，提示词写 `3.5px`。**注释与提示词差 0.1px。**
- **S10**：`--misreg: 1.5px` + `border-left: 1.5px solid var(--paper)`（红版错位露纸）。这条线是**版式机制**，但没进提示词的线宽表。
- **S15**：声称的 `0.5 / 0.8 / 1 / 1.7` 全部落地（在 SVG `stroke-width` 上），但另外还有 `1.2 / 1.4 / 2` 三个没在表里的值；且**提示词说「线宽只用这几级」时，AI 会以为是 border-width，实际原型主要靠 SVG 线条**——这条指令的可执行性本身有问题。
- **S25**：声称的唯一值 `3px` 只出现在 `:focus-visible` 的 outline 上；承载视觉的装订线是 SVG 的 `1.2px`。**"线宽只用 3px"这句话在正常浏览状态下几乎不可见。**
- **S27**：**最严重的一案**——声称 3 个值里 `1.2px` 和 `2.4px` 在整份 CSS 里一次都没出现（注释里写了"窄屏收 1.2px"，但没有任何媒体查询真的声明它）。

#### B. 配色「不新增更多彩色」— 9 案，但多数是我的口径问题（SOFT）

用像素直方图（排除图片）复核后，真正构成"新增彩色"的**只有 2 处**：

| 案 | 颜色 | 占 CSS 绘制面积 | ΔE | 说明 |
|---|---|---|---|---|
| S24 | `#1B1136` | 14.28% | 25.7 | 声称色板是 7 色，这是第 8 个，且占地 14% |
| S25 | `#181C0D` | 1.72% | 8.1 | 橄榄黑，与 `#1E1A16` 同族但色相偏 46° |

其余 7 案（S02/S06/S14/S16/S19/S23/S27）的"越界色"经 ΔE 复核**全部是声称色的深浅变体**
（ΔE 多在 2–13，色相偏差 <25°），是 opacity/alpha 叠色产生的，不是作者引入的新色。
⇒ **这条约束在字面上被 2 案破坏；但"不新增更多彩色"作为一句话本身不可机械判**，
因为它没说「同色系深浅算不算」。

#### C. 等宽字体 — **0 案假声称**（我前面判错过，这里是纠正）

`probe-mono-fonts.mjs` 的正确口径分两步：
1. 该族在 **computed `font-family`** 里被声明了几次（30 案：23–358 次，全部 >0）；
2. 找到**至少一个**声明了该族的元素，用 `CSS.getPlatformFontsForNode` 查谁在画字。

结果：**29 案 PASS（含 1 案 `PASS*`）、1 案 N/A（S25 无 mono 声称），0 案 FAIL。**

**我在前几版判过 3 案 FAIL，全部是选择器错误：**

| 案 | 我误判的原因 | 事实 |
|---|---|---|
| S03 | 只挑了首个含 mono 族的元素 → 挑到 `h1.d1`（用 NSimSun），报"画字是 NSimSun" | `IBM Plex Mono` 全页声明 **64 次**，画字命中 |
| S08 | 挑到 `code`，平台报 `IBM Plex Mono`，而声称是 `Overprint Numerals` → 判"假声称" | **`Overprint Numerals` 是 `@font-face` 的本地别名**：`src: url("assets/fonts/plex-numerals.woff2")` —— 就是一个改名后的 IBM Plex 数字子集。**不是假声称，是作者刻意做的本地化别名** |
| S18 | 挑到 `code`（走 `--mono` = Martian Mono），报"VT323 没用上" | `VT323` 走 `--term`，用在 `.nameplate code` 上，**声明 90 次** |

⇒ **这一项数据层完全干净。** 同时它暴露了验证方法的一个真问题：
**「哪个元素代表这个字体约束」这件事本身需要判据**，不能随手 `querySelector('code')`。
S08 的案例更值得记住：**`@font-face` 别名会让"声明名 ≠ 内部族名"，
任何按族名做字符串比对的验证器都会在这里误报。**

#### D. 字族名与字体文件内部名的差异（不是缺陷，但验证必须处理）

多数案的 `getPlatformFontsForNode` 返回内部名带字重/变体后缀，例如：
声称 `Martian Mono`，实际画字报 `Martian Mono SemiExpanded` 或
`Martian Mono SemiExpanded Condensed`；声称 `JetBrains Mono`，报 `JetBrains Mono Medium`。

对 AI 来说这不是问题（`font-family: "Martian Mono"` 能命中）。
但对**机械比对**来说，这是一个必须写进判据的归一化步骤：**族名比对要做前缀/包含匹配，
或者干脆用 `@font-face` 的 `src` URL 来定身份**（S08 就是这么解决的）。
不做归一化，30 案里有 10 案会被误判成"字族不对"。

#### E. 阴影 — S11（HARD）

提示词声称「只用 inset（凹槽，无外投影）」，实测 **`drop-shadow` 用了 12 处**、`inset` 只 1 处。
`filter: drop-shadow()` 不是 `box-shadow`，但它确实是一个投影。
⇒ **S11 的阴影声称与实现方向相反**（声称凹槽，实际用硬边投影）。

#### F. 圆角 — 0 案 FAIL，但 4 案 N/A + 2 案口径模糊

- S05（5 处）、S13（2 处）、S14（1 处）、S21（3 处）：有非零圆角，但**全为 `50%` 且全在 `input` 上**。
  这落在「仅圆形徽标为 50%」的授权范围内 → 我判 PASS，但**字面上「全站一律 0」对这 5/2/1/3 个元素不成立**。
- 任务书自己也提到了这个坑，我的实测证实了它：**判据必须写成「除圆形控件外为 0」**，否则会误伤。

#### G. 轮播 — S20（SOFT）

`[class*=carousel]` 命中 4 个元素，但 `autoplay` 属性 0、`setInterval` 0。
⇒ 是静态的轮播式版面，不是自动播放。**「首屏不要轮播图」这条对静态轮播区是否成立，提示词没说清。**

#### H. 反向发现：声称了但从未上屏的色（9 案）

S02/S05/S06/S08/S09/S10/S14/S17/S19 有 1–2 个声称色在页面上一次都没画出来。
这不构成谎报（多说一个色不是错），但**说明「配色只用这几个值」这句是从 `:root` 变量抄的，
不是从实际渲染反推的**——它列的是"作者声明过的色"，不是"页面真的用到的色"。

### 2.5 这一项的判决

> **提示词的数据层整体可信，但"精确值"层有一类系统性缺陷。**

拆开说：

1. **字体链、等宽数字、禁用族、渐变、毛玻璃、emoji、图片位、阴影（除 S11）、圆角（除 4 案口径）—— 干净。**
   字体相关四项 **119/119 全过**，没有假话。说明 `clean-dna.mjs` 从 computed 层
   反推标题/正文字体的那条管线是对的。

2. **线宽是唯一的系统性谎区（5/30）。**
   根因很清楚：`lineWidths` 这个字段是从 **CSS 文本**抽取的（混合了 border、outline、
   SVG 用户单位、SVG 绝对单位），而提示词把它写成「线宽只用这几级：Xpx」——
   **把一个来源混杂、还包含从未使用值的集合，包装成了一句精确指令**。
   S27 尤其严重：声称的 3 个值里 2 个在整份 CSS 里一次都没出现。

3. **「不新增更多彩色」这句话本身不可机械判。**
   它没有定义「新增」的粒度（同色系深浅算不算？opacity 叠色算不算？照片算不算？）。
   我用四档口径得出四个不同的答案（18 / 10 / 2 / 2 FAIL）。
   **一句判据不明确的话，无论原型多干净，都无法被验证。**

4. **最值得注意的一条：提示词里那些"最像可验证"的数字（机制句 252 个），全部不可验证。**
   因为它们没有元素锚点。而真正可验证的（字体链、色值）恰恰是提示词里最不显眼的部分。

### 2.6 一个必须记住的方法论教训：验证器自己的假阳性

本轮我判错过的每一条，都不是因为"看错了页面"，而是因为**量法选错了**：

| 我判过的错 | 真实情况 | 根因 |
|---|---|---|
| 30/30 案都有 `#000000` 越界 | 普通 HTML 元素的默认 `fill`，不画任何东西 | 没限定 `instanceof SVGElement` |
| CSS 里"一个 hex 都没写" | 遍历 bug：`CSSStyleRule.cssRules` 是 truthy 的空列表 | 判 truthy 而非 `.length` |
| 19 案线宽"超纲" | 把 SVG 用户单位当 px 比 | 没做 viewBox 缩放换算 |
| S15"线宽超纲 0.5/0.8/1.2" | 这些在 `stroke-width` 声明里，是真的 | 只读 border，没读 stroke |
| S25"声称的 3px 不存在" | 在 `:focus-visible` 的 `outline` 简写上 | 简写只匹配纯 px 值 |
| S03/S08/S18"字体假声称" | S08 是 `@font-face` 别名；S18 在 `.nameplate` 上 | 只挑一个元素查平台字体 |
| S21"新增了 #C5BEAD 占 6.87%" | 照片里的墙 | 没遮罩图片区域 |
| 全库 1327→1237 条约束 | 分段条件写错漏 90 条 | 逻辑错 |

**8 类错误，没有一类是"数据源有问题"，全部是验证器的问题。**
这直接支撑了 §3 协议的核心要求：**判据必须先登记，且判据里要写死"怎么量"，
不只是"量什么"。**

### 3.1 先审上次那次验证（S19）——它有 6 个漏洞

> → 因此提示词新增了「抽屉是有厚度的块」这一条。**这是实测才发现的，推理发现不了。**」

这本身是好事（说明实测算出了东西），但它同时意味着：**提示词被改过了，而实现是在旧提示词下做的。**

而"风格像不像"恰恰是用户最关心的问题。

**漏洞 5：单案、单次、无重复。** 没有第二个实现者、没有第二次生成。
无法区分「提示词有效」和「这次运气好」。

**漏洞 6：实现者知道自己在被验证哪 8 项。** 判据（那 8 行表格）和实现产物放在同一个
`99-scratch/` 目录里，实现时判据已经写在提示词文档里了（第 21 行的「每个抽屉正面高度 ≥130px」就是判据）。

### 3.2 协议

#### 3.2.1 信息隔离

**核心原则：实现者的文件系统里不能存在 `prototypes/`。**

物理做法（不是靠"请勿查看"的口头约定）：

```
D:\Web\style\_e2e\<run-id>\
├── prompt.txt              ← 只有 buildStylePrompt(id) 的输出，逐字节
├── assets/                 ← 只含 images/占位-N.jpg（纯色 1 张，无原型素材）
├── START.md                ← 任务书：只许读同目录下的文件
└── out/                    ← 实现者只能往这里写
```

具体约束：

1. **`<run-id>` 与案号解耦**：目录名用 `run-a3f2`，不出现 `S19`。实现者不知道自己在做哪一案，
   就无法去"猜"原型长什么样（30 案都在同一个 `prototypes/` 下，知道案号就能找到）。
2. **干净目录里没有 `style.css`、没有 `index.html`、没有 `_fonts/`**。字体走 Google Fonts CDN 或
   预置一份**去掉族名注释**的字体包（`_fonts/css/*.css` 的文件名里带族名，`spectral__400-600.css`
   直接暴露了标题字体——这是个真实的泄漏点）。
3. **提示词逐字节落盘**：`run.mjs` 里 `writeFileSync(prompt.txt, await page.eval(id => window.buildStylePrompt(id)))`，
   并在文件头写 `sha256`。后续验收时重算 sha256，确认"验的就是这一条"。
4. **实现者是新起的子 Agent，`cwd` 设为 `<run-id>/`**，不带仓库上下文（用 `subagent`，不用 `subagent_fork`——
   fork 会带上"我知道 S19 原型长什么样"的对话历史）。

#### 3.2.2 作弊检测

物理隔离之后仍然要检测，因为隔离可能失效。**四道独立检测，任一中招即判该案作废：**

| # | 检测项 | 判据 | 实现 |
|---|---|---|---|
| 1 | **字体声明来源** | 生成页面里出现 `_fonts/css/` 路径、或 `prototypes/` 字符串 → 作废 | `grep` 产物 |
| 2 | **原型专属字符串** | 生成页面出现原型里独有的品牌词/编号格式（如 S19 的 `K-07-112`、`CAT-404`）→ 作废 | 从 `prototypes/Sxx/index.html` 抽 20 个独有 token 建黑名单 |
| 3 | **CSS 指纹相似度** | 生成页与原型 `style.css` 的**声明序列**做 3-gram Jaccard；>0.35 需人核 | 见下 |
| 4 | **进程级审计** | 实现期间对 `prototypes/` 做 `mtime` 快照 + Windows 上查 Chrome/编辑器最近打开文件 | 开工前 `Get-ChildItem -Recurse | Select FullName,LastWriteTime` 存快照 |

**第 3 项要小心**：Jaccard 高不一定是抄——同一份提示词本来就会导致相似的 CSS
（都写 `border-radius: 0`）。所以正确用法是**只看"提示词没说的部分"**：
把提示词里出现过的值（色值、字体名、线宽、圆角）从两边的声明里剔除，再比剩下的。
剔除后仍 >0.35 才是可疑。

**第 4 项是本协议唯一"不可伪造"的证据**：mtime 快照 + 文件访问审计。
但要注意：并发 Agent 可能改 `prototypes/`，所以快照要记录**每个文件的 mtime 而不只是目录**，
且只对**读**敏感（写是别人的事）。

#### 3.2.3 判据预先登记

**必须在生成之前写死，并且锁进 git。**

`prereg-<run-id>.json` 内容（在实现者开工**之前** commit）：

会给出 18 / 10 / 2 三个不同的 FAIL 数。

#### 3.2.4 第三方复核

**"像不像"必须由不知道原型存在的人判。**

- **J 类（气质）**：3 名评审，**盲评**。给他们看的是「提示词里那句 plain 描述」+「生成页面截图」，
  **不给原型截图**（给了原型就变成"像不像原型"而不是"像不像那句话"）。2/3 票通过。
- **M 类**：不需要人，但要**双人独立跑同一份 `prereg` 脚本**，比对输出 JSON 逐字节相同。
  不同 = 脚本有非确定性（时间/随机/字体加载时序），该案作废。
- **S 类**：1 名不参与实现的评审，按 `prereg` 里写死的口径判。

**为什么 J 类不能给原型截图**：原型是"标准答案"，但用户拿到的是「照提示词生成的页面」。
如果评审看着原型打分，就会奖励"抄得像"，而不是"提示词说得清"。

#### 3.2.5 可复现

换一个人重跑得到同样结论，需要三件事：

1. **提示词逐字节可复现**：`buildStylePrompt` 是纯函数（无随机、无时间）。
   **本轮做了实测**：审计开始时 dump 一次、并发改动之后又 dump 一次，
   两份 30 条提示词拼接后的 SHA256 **完全相同**（54,564 字符），
   逐案比对 **0 处变化**。唯一的差异是 JSON 外层的 `dumpedAt` 时间戳。
   ⇒ 提示词本身可复现；但**导出器必须把时间戳排除在比对之外**，否则哈希永远不等。
2. **量测脚本确定性**：已发现的三个不确定性来源要固定 ——
   - 字体加载：必须 `await document.fonts.ready`
   - 视口：必须 `p.setViewport()`（`launch({width,height})` **不切换视口**，这是任务书提醒的坑，我实测确认）
   - 滚动位置：全页截图前 `scrollTo(0,0)`；且**必须遮罩图片区域**再算像素直方图（§2.2）
3. **环境固化**：Chrome 版本、`dsf`、`--force-color-profile=srgb`（`cdp.mjs` 已带）、
   以及**每个被测量文件的 mtime**（见 §0：只记 git HEAD 会漏掉未提交的并发改动）。
   全部写进 `prereg` 的 `env` 字段。

### 3.3 协议的一句话总结

> **隔离靠物理（干净目录 + 案号脱敏），防作弊靠 mtime 与字符串黑名单，
> 防自欺靠"判据先于实现 commit"，防审美偏见靠"评审看不到原型"。**

### 3.4 这套协议的成本代价（诚实说）

物理隔离要求**每个案单独起一个子 Agent、单独一份干净目录**。这意味着：

- 30 案 = 30 次 Agent 启动 + 30 次人工核对 mtime
- 判据要先写 30 份（虽然模板段落可复用，见 §1.5）

**这是 §4 的成本模型里最贵的一项。**

## 4. 任务 4：成本-覆盖率曲线

### 4.1 单案成本拆解（实测，不是估算）

| **判据预登记** | 15 分钟（首案）/ 5 分钟（后续） | ✅ | 模板可复用 |

**所以「半天级」的来源不是量测，而是：实现 + 判据登记 + 隔离审计 + 盲评。**

### 4.2 5 个子 Agent 并行能做到几案

**并行度分析**（每个子 Agent 独立跑一案）：

- 机械量测：**无冲突**（各起各的 Chrome、各用各的端口）。5 并行 = 30 案 **1 分钟**。
- 实现：**无冲突**（各自干净目录）。5 并行 = 5 案/轮。
- 盲评：**不能并行**（同一个评审团顺序看，避免互相污染）。
- 隔离审计：**不能并行**（要串行做 mtime 快照对比，避免并发写混淆）。

⇒ **瓶颈是「人的环节」，不是「机器的环节」。**

1. **A 档已经免费做完了，而且抓到了真问题。** §2 的 20 条 FAIL 里，
   5 条线宽不一致 + S24/S25 的 2 个真新增色 + S11 的阴影方向反了

2. **10 案足够覆盖结构性差异。** §1.5 证明 37.5% 的字数是 30 案共用模板；

   - `hasVoid=yes`（7 案）抽 3 案
   - 声称色 4/5/6/7 各抽 2–3 案

3. **30/30 的边际收益低于成本。** D 档 34 人时 vs C 档 12 人时，多出的 22 人时主要花在
   已经证明"干净"的 20 案上（字体链 30/30 全过、渐变/毛玻璃/emoji 30/30 全过）。
   花 22 人时去确认"已知为真"的事，不如把这笔钱花在修 §2 的 5 条线宽缺陷上。

4. **但 C 档有一个硬前提**：5 条线宽不一致的案（S09/S10/S15/S25/S27）**必须全抽**，
   否则端到端验证会在已知有问题的提示词上跑，结论无意义。

### 4.5 每案的成本瓶颈在哪（逐个说清）

| 环节 | 是否瓶颈 | 证据 |
|---|---|---|
| **生成**（AI 实现） | ⚠️ 中 | 1.8K 字提示词 → 单文件 HTML，实测上次 S19 产物 15KB/365 行 |

## 6. 我核实后认为任务书说错了的地方

### 6.1 「`buildPrompt(id)` 需要 `document`」——函数根本不在 window 上

任务书说「`buildPrompt(id)` 需要 `document`，参考 `dump30-frozen.txt` 的做法」。
实际 `buildPrompt` 是 `prompt-copy.js` IIFE 内的私有函数（line 151），
全文件只在 **line 993** 有一处导出：`window.buildStylePrompt = buildPrompt;`。
`typeof window.buildPrompt === 'function'` 实测为 **false**。
正确调用是 `window.buildStylePrompt(id)`。

### 6.2 「S19 是「半天级」」——量测只占 9.5 秒

任务书说「端到端验证 1 案的成本（参考上次 S19 是「半天级」）」。
实测 `probe-timing.mjs`：**单案全自动量测 9.5 秒**（含截图与像素直方图），其中 DOM 量测仅 44ms。
S19 那次"半天"的时间分配是：写提示词文档（75 行）、实现页面（365 行）、手工量 8 项。
**"半天级"描述的是那次的工作量，不是端到端验证的固有成本。** 工具化之后量测环节基本归零，
瓶颈转移到「实现」和「人判」——这两项任务书没提。

### 6.3 「`border-width: 0.4/0.8px` 是机械可验的 M 类」——需要三个额外条件

任务书把 `border-width: 0.4/0.8px` 列为 M 类典范。实测它有三个坑（§2.1）：
1. `getComputedStyle` 与 Typed OM **都会取整成 1px**，只有 CSSOM 声明值保真；
2. 含 `var()` 的简写在 CSSOM 里读出来是**空串**（S15 的 15 条声明整批丢失）；
3. 线宽的落点有四种形态：`border-width` / `outline-width` / SVG `stroke-width`（用户单位）/
   SVG + `non-scaling-stroke`（等于 px）。**S19 的 0.4/0.8px 是第四种，S25 的 3px 是第二种（focus 环），
   S15 的 0.5/0.8/1/1.7 是第三种。**

⇒ 「0.4px 可机械验」这句话成立，但**前提是四路都读**。我第一版只读 computed、第二版只读 CSS 边框，
两次都得出过错误结论（S25 误判"3px 不存在"、S15 误判"声称值不可复现"），
都是靠后续对照实验抓回来的。

### 6.4 「读 computed style 才准」——有一半对

任务书说「读 computed style 才准，不要解析 CSS 文本——文本可能有不生效的死声明」。
**对配色成立，对线宽反过来。**

- 配色：computed 确实准（死变量不会出现在 computed 里）。
- 线宽：**computed 会把 0.4px 报成 1px**，必须回到 CSS 文本。
- 而且两个方向都有反例：`prototypes/S25/style.css` 的视觉线宽活在 SVG `stroke-width:1.2` 上，
  只看 CSS 边框会漏；S15 的 15 条 `border-*: 3px solid var(--pencil)` 在 CSSOM 里读出来是**空串**，
  只看 CSSOM 也会漏。

⇒ **正确做法是"四路都读、互相校验"**：computed 定"有没有生效"，CSS 文本定"声明了多少"，
CSSOM 定"哪些是 var() 简写"，`getPlatformFontsForNode` 定"谁在画字"。**没有任何单一读法够用。**

### 6.5 「提示词里的色值可能带语义括号，如 `#EFE7D7（paper）`」——这不是最大的坑

任务书提醒剥括号。这确实存在（S01/S02/S19 等），但**它不是主要误差源**。
真正的主要误差源是：
- 灰度照片（S21 的 `#C5BEAD` 占 6.87% 面积，是照片里的墙）
- 普通 HTML 元素的默认 `fill: black`（让 30/30 案都多一条假 `#000000`）
- 未访问链接的 UA 默认 `#0000EE`（S02/S09 各 1 处）
- 同色系深浅变体（ΔE 2–13，被误判成"新彩色"）

剥括号是一行正则；**排除照片/UA 默认/深浅变体**需要像素直方图 + ΔE + 色相判定。
我用三档口径跑同一个问题，得到 **18 / 10 / 2** 三个不同的 FAIL 数——这才是这条约束的真难点。

### 6.6 「有的案 `border-radius` 是「仅圆形徽标为 50%」」——实测这些 50% 全在 `<input>` 上

任务书的判断方向对了。我的实测补充了具体事实：S05(5)/S13(2)/S14(1)/S21(3) 的 50% 圆角
**全部落在 `input` 元素上，0 个在"徽标"上**。
所以「仅圆形徽标为 50%」这个授权描述**与实现不符**——实现是"圆形表单控件"。
提示词的措辞应该改，否则 AI 会以为可以给徽标加 50% 圆角。

### 6.7 「30 案各约 1800 字」——基本准确

实测默认调用下 1639–1998 字，均值 **1818**。这一条任务书没说错。

### 6.8 「5 个子 Agent 并行」——并行不是瓶颈

任务书问「如果本轮用 5 个子 Agent 并行，能做到几案」。
实测结论：**并行度不缺，缺的是人的环节**。机械量测 30 案全量只需 4.75 分钟（单线程），
5 并行更是 1 分钟。真正卡住的是：实现（20 分钟/案，且因隔离要求必须新起 Agent）、
判据预登记、盲评（不可并行）、隔离审计（不可并行，要串行拍 mtime 快照）。

⇒ **5 个 Agent 并行能把"实现"从 30×20 分钟压到 6×20 分钟，
但压不掉盲评和审计。C 档（10 案）的 12 人时里，约 8 人时是人的工作。**

### 6.9 任务书没提但很重要：`prompt-s19.md` 用的提示词是被修掉的版本

任务书只说「那次用的提示词与线上 `buildPrompt('S19')` 不是同一条」。
我量化后发现更严重：`prompt-s19.md` 写 `Spectral`，而 `prompt-copy.js` line 161-171 的长注释
明确记录 **"S19 提示词写 Spectral、实际 h1 是 Noto Serif SC" 是已被修复的 bug**。
⇒ 那次验证用的**正好是被后来修掉的那一版**，它的"实测达标"结论不仅不能迁移，而且是反向证据。

### 6.10 `S08` 的「Overprint Numerals」不是假声称，是 `@font-face` 别名

这条值得单独写，因为它是一个**看起来像谎、实际是正确做法**的样本：

```css
/* 数值面：自托管的等宽拉丁子集，本地别名 Overprint Numerals */
@font-face {
  font-family: "Overprint Numerals";
  src: url("assets/fonts/plex-numerals.woff2") format("woff2");
}
```

提示词说「编号/价格等数字用等宽 Overprint Numerals」——**完全准确**，
因为那是作者为一个 IBM Plex 数字子集起的本地别名。
但任何"查平台字体名再和声称名做字符串比对"的验证器都会在这里报假阳性（我第一次就报了）。

⇒ **协议要求**：字体验证必须以 `@font-face` 的 `src` 为身份锚点，不能只比族名。

### 6.11 我这一轮自己判错过的 8 处（审计者自己的可信度）

见 §2.6 的表。概括：**没有一处是"数据源在说谎"，全部是验证器选错了量法。**
这也是本轮最重要的产出之一——它说明 §3 的协议里「判据要写死怎么量」比「判据要写死量什么」更关键。

另外修了一处**分母错误**：约束抽取器的两个分段 bug 让 1327 条变成 1237 条（漏 90 条）。
分母错了，后面所有百分比都错。修正记录在 §1.2。

## 8. 一页结论

1. **30 条提示词共 1327 条原子约束，M 646 / S 540 / J 141（M 占 48.7%）。**
   其中 37.5% 的字数是 30 案共用模板，「防退化+验收三问+输出要求」共 16 条/案只需验一次。

2. **提示词数据层总体可信：449 次判定中 415 PASS / 20 FAIL / 9 WARN / 5 N/A。**
   字体链（30/30）、等宽数字（29/29）、渐变/毛玻璃/emoji（各 30/30）、图片位（30/30）**零假话**。

3. **唯一系统性谎区是线宽（5/30）。**
   S09 声称 3.5 实际 3.6、S10 少报 1.5、S15 多出 1.2/1.4/2 三个未登记值、
   S25 声称的唯一值 3px 只在 focus 环上（视觉装订线是 1.2px）、
   **S27 声称的 1.2px 与 2.4px 在整份 CSS 里一次都没出现**。
   根因：`lineWidths` 从 CSS 文本抽取（混合了边框、outline、SVG 用户单位），
   却被包装成「线宽只用这几级：Xpx」这样一句精确指令。

4. **「不新增更多彩色」这句本身不可机械判。**
   像素直方图（排除照片）显示声称色平均覆盖 **88.5%** 的 CSS 绘制像素，
   真正的新彩色只有 **2 处**（S24 `#1B1136` 占 14.3%、S25 `#181C0D` 占 1.7%）。
   同一句话在三种口径下得出 **18 / 10 / 2** 三个 FAIL 数。

5. **端到端验证的真实成本：量测 9.5 秒/案，人的环节 50 分钟/案。**
   「半天级」是工作量描述，不是固有成本。

6. **推荐 C 档：10/30 分层端到端 + 已完成的 30/30 数据层。约 12 人时。**
   硬前提：5 条线宽不一致的案必须全抽。

7. **没有 LLM API key**，实现环节无法脚本化。
   `tools/taste-skill/` 的 `inspect.mjs`/`lint.mjs` **与本案约束冲突**
   （它把 S19 要求的三款字体判为 WARN、把 S19 的检索号判为"装饰性编号"），
   只能当参考不能当判据。仓库里**没有截图对比工具**，我自建了像素直方图。

8. **最大的方法论风险不是"AI 会不会照做"，而是"验的人会不会挑对自己有利的判据"。**
   §3 的协议里，物理隔离（干净目录+案号脱敏）、判据先于实现 commit、
   盲评不给原型截图——这三条是防自欺的核心，也是成本的主要来源。
