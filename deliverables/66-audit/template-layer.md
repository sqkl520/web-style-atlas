## 0 先给结论

Lead 的两条核心侦察，**一条方向对但事实已过期，一条只对了一半**。

| Lead 的断言 | 核实结果 |
| --- | --- |
| 发现 1：`sceneIndex` 里 `M0` 命中 0 次，模板层完全不在索引里 | **事实正确**（`Select-String` 实测 0 次），但**推论已过期**：模板层已经接进来了，走的是独立通道（`#tpl-strip` / `#empty-tpl`），不经过 `sceneIndex`。搜「餐厅」看到的**不是**「没有符合条件的方案」，是 M02 卡片。 |
| 「用户搜餐厅 → 0 个直连、只有 2 个近似，界面在给他看方案」 | **错**。实测搜「餐厅」= 0 行方案 + M02 卡 + 三个模板的全量行业清单，**模板是主角**。 |
| 「搜餐厅看到的是『没有符合条件的方案』还是『有 M02 模板』」 | **两者都有，且是同屏两句**：上句 `#empty` 说"没有"，下句 `#empty-tpl` 说"但模板层有 M02"。这是**设计过的分岔**（见 §2.3），不是漏洞。 |
| 发现 2：`unsupported` 29 词里有大量模板能覆盖 | **部分正确，但覆盖面被高估了**。29 词中模板逐字命中的是 **0 个**（README 原文一次都没写这 29 个词）。我按结构判「能套」的是 **11 个**（甜品/美甲已有相邻候选，另 9 个没有）。剩下 18 个模板确实给不了。 |

**真正的问题不在「模板没接进来」，在「接进来了但说不准」**：73 个词里有 **14 个**界面输出的结论与模板实际能力不符（§1.3），全部集中在「模板能给，界面说给不了」这一个方向。

**另外发现一个与模板无关、但更严重的 P0**：17 个词的 `near` 只有近似方案，空状态写着"点左侧芯片能筛出来"，**按字面点下去仍然 0 行**（§2.4）。这是搜索框与芯片两条路互斥导致的死路，比模板层的问题更伤。

## 1 三层覆盖矩阵（73 词 × 3 层）

### 1.1 词表与判据

**73 词的并集怎么来的**（`tpl-audit/static-map.mjs`）：

```
sceneIndex 44 | unsupported 29 | overlap [] | union 73
index with direct: 16 | near-only: 28
```

`unsupported` 与 `sceneIndex` **零重叠**，并集就是 73。这点 Lead 预判的「可能有重叠」不成立——生成器 `build-prompts.mjs` 里 `SCENE_INDEX` 与 `UNSUPPORTED` 是两个互斥的字面量数组。

**三层判据**（写死在这里，后面整张表按它判）：

| 判据 | 定义 | 依据 |
| --- | --- | --- |
| **直连** | 该词（或唯一别名）**逐字**出现在源头的适用清单里 | 30 案层：`data.js` 的 `scenesYes`；模板层：`templates/M0x/README.md` 的适用句 |
| **近似** | 源头没写这个词，但同一套结构能承载，且**不缺关键段落** | 我的判断，逐条给理由（下表 B 列括号内） |
| **可套用** | 模板的段落集合 ⊇ 该品类的最低必需段落集 | **这是本次审计最关键的一条判据，见下** |
| **不适用** | 缺 ≥2 个该品类必需段落，或需要交易/后端能力（购物车、支付、预约库存、检索） | 逐条列缺什么 |
| **未收录** | 30 案层：词不在 `sceneIndex` 也不在 `unsupported` 之外的任何映射里 | — |

**「可套用」到底怎么判**——Lead 问「M02 说餐厅咖啡馆都能套，那甜品店算不算」。我的答案是：**要用段落对得上，不是用「都是本地实体店」这种范畴对得上。**

M02 的 7 段（README 第 31 行原文）：`顶部（店名＋导航＋订位按钮）→ 主视觉大图＋信息带 → 招牌与菜单价目 → 营业时间与地址 → 店内环境图 → 顾客评价 → 订位与联系 → 页脚`。

- **甜品店**：有招牌产品、有价目、有营业时间、有地址、有评价、要接预订 → **7 段全中** → 可套用，且是高质量套用。
- **美甲店**：缺「甲型价目 + 预约时段表」这两个它自己的核心段 → **7 段里中 6 段，缺的正好是它最要紧的** → 只能算「相邻候选，当起点改」，不能算「可套用」。这正是 `prompt-copy.js` 现在给 M02 配的 adjacent 待遇，**我认同这个判定**。
- **酒吧**：酒单价目=菜单、有营业时间（且是深夜）、有环境图、有评价、有订位 → **7 段全中** → 可套用。现在界面说「给不了你」，**错了**。

所以判据一句话：**「同一类页面骨架」而不是「同一类生意」**。按这个尺子，`prompt-copy.js` 现在对甜品/美甲的保守是对的，但对酒吧/宠物/茶饮的「给不了」是错的——它们的段落匹配度和甜品一样高。

### 1.4 反向核对：`sceneIndex` 自己站得住吗

我把 44 个索引词逐词拿去 `data.js` 的 `scenesYes` 里对照（`tpl-audit/index-grounding.mjs`）：

```
A. 索引漏收（案子里写了，索引没收）: 19
B. 索引无据（索引收了，案子没写这个词）: 55
```

- **A 的 19 条**是真的漏：`档案`在 S13/S15/S17/S19 的 `scenesYes` 里都写着，索引只收了 S07/S11/S23。
- **B 的 55 条**大多不是错——索引是"人判定的行业→案子"映射（`build-prompts.mjs` 里人工维护的 `SCENE_INDEX`），本来就不要求逐字对齐 `scenesYes`。但**这解释了为什么「搜词」和「点芯片」会给出不同答案**（见 §2.4）。

**结论**：`sceneIndex` 与 `unsupported` 都是**人工裁定**，不是从 `data.js` 推出来的。这个设计本身没问题（索引比全文匹配准），但它导致了一个副作用：`sceneIndex` 里有、搜索框里搜不到。这个副作用现在正在制造 P0。

### 2.4 真正的问题：空状态给的恢复路径是死路（P0，与模板无关）

**为什么**：芯片把 id 写进 `state.sceneIds`，但**不碰 `state.q`**（`prompt-copy.js:769-781`，注释明说"直接驱动现有的 #q 搜索框"——实际并没有）。而 `app.js:132` 的 `match()` 是 `state.q` 与 `sceneIds` **取交集**。用户先搜了词、再点芯片，搜索框里的词还在，交集恒为空。

### 3.6 附带发现：29 个 unsupported 的说明**从来没有显示过**

`README.md:78` 写着：「29 个如实标为"没有"，收在「还有 28 个只有近似的 →」里，**不藏起来**」。

实测这句话不成立。`prompt-copy.js:897-905`：

```js
note.style.cssText = "margin-top:8px;font-size:12px;opacity:.72;display:none";
moreHost.appendChild(note);
```

这条 note 被 append 进 `moreHost`，但 `moreHost` 自己也是默认 `display:none`，且唯一写它 display 的地方是展开按钮：

```js
moreHost.style.display = expanded ? "" : "none";   // 只能 "" 或 "none"
```

**子元素的 `display:none` 是内联写死的，没有任何一行代码把它改成非 none。** 所以即使点开「还有 28 个只有近似的 →」，这块也永远不可见。

实测（`probe-73.mjs` 的 `unsupportedAfterExpand`，73 次查询、每次都在展开后查）：

```json
{"inlineStyle":"margin-top: 8px; font-size: 12px; opacity: 0.72; display: none;",
 "display":"none","rects":0,"parentDisplay":"block"}
```

`rects:0` = 布局盒为零 = 用户看不见。截图 `shots/11-rail-expanded-unsupported-invisible.png` 是展开态全景，画面里没有这块。

**后果**：`unsupported` 的 29 个词在**任何一个界面入口都不可见**——不在芯片里（芯片只来自 `sceneIndex` 的 44 词），不在 rail 说明里（这块被 `display:none` 压死），只能靠用户自己往搜索框里盲打才碰得到。这与 `README` 承诺的"不藏起来"直接相反。

这条与模板层是同一类病：**代码写了、数据在、渲染路径不通**。它也是 §2.4 那个 P0 的同类——"界面承诺了一件事，实际做不到"。

1. `wizard.js:243` 括号里那句「**向导不覆盖那一层**」——不是遗漏，是声明。
2. `wizard.js:8` 的模块注释定死了打分口径："五个问题的答案都映射到方案上**已经实测出来的值**：内容量=report.json 正文字数、图片量=真实图片张数、彩度=调色板最高饱和度、门槛、记忆点"。**模板没有 `report.json`，没有实测值，所以进不了这个打分器**——不是不想，是数据模型不兼容。

## 5 三种接法的取舍

前提：`sceneIndex` 与 `#ledger` 的 `S\d{2}` 白名单是硬约束，模板**不能**进 `ledger`、不能进 `#count`（实测 `benchSetSceneIds(["M02"])` → 0/30，`["M02","S06","S19"]` → 2/30，与 `app.js:366-369` 注释一致）。所以下面四个方案都不挑战这条。

### 甲：模板进 `sceneIndex`，搜「餐厅」时方案行 + 模板行一起出

**用户实际看到**：`列出 2 / 30 个方案` 下面直接混着模板卡，或者 `列出 2 / 30` 旁边写 `+1 模板`。

**代价（实测）**：
- **会让 30 案存在感变弱**。这不是猜测：现在的模板带（独立容器、已经是最轻的接法）在「设计工作室」上占掉首屏 **54%**，把三行方案全推到 940px 之下（§2.6）。如果模板再混进 `#ledger`，方案行还会被进一步稀释。
- **会让用户以为模板和方案同层级**。`#count` 说"30 个方案"，模板进来后这个 30 就不再是"全部"；改 `#count` 就得改 `app.js` 的契约（"页面上每个数字都来自磁盘"），不改就是数字说谎。
- **技术上是负收益**：`app.js` 的白名单会静默吞掉 M02，要么改白名单（动到闸门口径），要么在 `#ledger` 里留一个不响应筛选的行（更糟）。

**结论：放弃。** 它解决的是"模板看不见"，但实测模板**已经看得见**（49/73 词有输出），而它引入的"层级混淆"是真实代价。

### 乙：模板独立成一条「你可能想直接用模板」的提示，不混在方案列表里 —— **这就是现状**

**用户实际看到**：`#tpl-strip`（有方案时）/ `#empty-tpl`（0 行时），独立容器、独立渲染函数、不进 `#count`、不进 `#ledger`、卡片上明写「模板 · 不计入方案数」。

**代价**：
- **已经付过的代价**：首屏挤压（设计工作室 54%）、移动端 1.56 屏、24 个「有方案但词没命中模板」的词不挂模板带（这是对的，不该挂）。
- **它没解决的问题**：模板层的**判断**还是错的（14 个 `✗`）。乙解决的是"能不能看见"，没解决"说得对不对"。

**结论：保留乙作为骨架，在它上面修判断。** 这是我推荐的基础。

### 丙：`unsupported` 的词不显示"没有"，改成"没有精细方案，但有模板能套"

**用户实际看到**：搜「酒吧」从「这一类，这套图集和模板层都给不了你」变成「30 个案里没有，但 M02 的 7 段里有 6 段对得上（缺 XX），可以当起点改」。

**代价**：
- **必须逐词写理由，不能批量改**。`prompt-copy.js:881` 的注释已经定了规矩："每条的 why 都必须包含 README 写的是什么、没写什么。只写'也能用'就是编能力。" 这条规矩是对的，丙必须遵守。
- **写错就是编能力**。29 个词里我能给出可靠段落匹配论证的只有 11 个（§1.2）；剩下 18 个（电商/政务/金融/医疗/地产/旅游/汽车/母婴/美妆/物流…）**必须继续显示"给不了"**——它们缺的是交易、检索、合规这些模板结构上根本没有的东西。
- **工作量**：11 条 `TPL_ADJACENT` 条目，每条 80–150 字理由。

**结论：采纳，但只对这 11 个词采纳，不搞"29 个都改"。** 这是本次审计里性价比最高的一改。

### 丁（我加的）：修「点芯片」的死路，顺带让芯片成为模板层的主入口

**用户实际看到**：搜「咖啡店」→ 点「咖啡店」芯片 → `列出 4 / 30 个方案`（而不是现在的 0）+ M02 卡。搜「书店」→ 点芯片 → 3 行。

**为什么它比甲/乙/丙都重要**：17 个词现在走进死路（§2.4），而这 17 个里有 **6 个已经在模板块给出卡片**（咖啡店 M02、餐厅 M02、花店 M02、民宿 M02、修鞋理发 M02、律师 M01）——也就是说，用户明明已经看到了"有 M02"，却被上面那句"点芯片能筛出来"引进 0 行。修好它，模板层的可发现性跟着一起修好，**不需要新加任何模板 UI**。（另有小吃店：结构上 M02 可套，但 `TPL_ADJACENT` 没写，P1 补上后也会出卡。）

**代价**：改 `prompt-copy.js` 的芯片 click handler（点芯片时清 `#q`，或者改成"点芯片 = 清搜索框 + 设 sceneIds"），约 3 行。风险是"用户手动打的词被静默清掉"——所以要么清空时在搜索框旁留一句"已按行业筛选，搜索词已清空"，要么芯片改成 toggle 时不清词但在空状态里加一句"请先清空搜索框"。**这是唯一一个改动量小、收益覆盖模板层 + 主清单两处的方案。**

### 5.4 我放弃的东西（明说）

1. **放弃甲**：会把 30 案压下去，实测 54% 首屏是硬证据。
2. **放弃"29 个 unsupported 全部改写"**：会变成编能力。18 个词模板确实给不了，继续诚实说"没有"是对的。
3. **放弃"向导加模板推荐"**：模板没有 `report.json` 口径的实测值，塞进欧氏距离就是造假。但我建议把向导那句 13px 脚注**提到第 1 屏**（问第一个问题之前），改成平级出口——不动打分逻辑，只动位置。
4. **放弃"把模板带从方案上方移到下方"**：`index.html:172-176` 的注释记录了移到下方的实测代价（模板带 top=1520，整条在 900px 视口外，"模板层在芯片这条主路径上等于不存在"）。位置不能再动，只能压高度。

## 6 我核实后认为 Lead 说错了的地方

### 6.1 「模板层完全不在场景索引里」—— 事实对，结论过期

`M0` 在 `prompts.js` 里确实 0 次（`Select-String` 实测，和 Lead 一致）。但模板层**不是靠 `sceneIndex` 接进来的**，是靠 `prompt-copy.js` 里独立的 `TEMPLATES` + `TPL_ALIAS` + `TPL_ADJACENT` + `#tpl-strip`/`#empty-tpl` 通道。这个接法是 commit `87a0235`（2026-10-26「11 个 Agent 审出的第二批缺陷：模板进反查…」）做的。

**所以「模板不在 sceneIndex 里」现在是设计，不是缺陷。** Lead 拿它当缺陷来推，会推出错误结论。

### 6.2 「用户搜餐厅 → 30 个案里 0 个直连、只有 2 个近似。而 M02 模板第一行就写着…用户在找模板，界面在给他看方案」

**实测不成立。** 搜「餐厅」：0 行方案 + M02 完整卡片（含色板、适用行业原文、打开链接）+ 三个模板全量清单，M02 卡片 top=635，首屏内（`shots/01`）。**界面没有"给他看方案"——没有方案可给，它给的就是模板。**

### 6.3 「搜『餐厅』时，用户看到的是『没有符合条件的方案』还是『有 M02 模板』？」

**两个都有，同屏，上句"没有"、下句"但模板层有"，相隔 158px（`#empty` top394-bottom552，#empty-tpl top552 起）。** 这是 `index.html:183-190` 写死的分工，注释里明说"顺序不能反"：先承认 30 案层的缺口，再给模板层的答案。

如果只看 `#empty` 就判"界面在说谎"，会漏掉紧跟其后的真答案。**这也是我建议不要动 `#empty` 结构的原因。**

### 6.4 「`unsupported` 29 个词里有大量模板能覆盖」「甜品/酒吧/美甲 → M02 同类；个人主页/简历 → M03；金融/政务/医疗 → M01」

逐条核：

| Lead 的说法 | 核实 |
| --- | --- |
| 甜品 → M02 | **已经做了**，`TPL_ADJACENT` 有条目 + 免责句（`shots/04`）。不是缺口。 |
| 美甲 → M02 | **已经做了**，同上。 |
| 酒吧 → M02 | **确实是缺口**，我判可套用，界面说给不了。✓ Lead 对。 |
| 个人主页 → M03 | **确实是缺口**，我判可套用（M03 骨架就是个人主页）。✓ Lead 对。 |
| 简历 → M03 | **我不同意**。M03 是 homepage（名字/作品/关于我/联系），简历要教育、经历时间线、技能矩阵、可打印版。**这是两种页面，不是一种。** Lead 把"个人主页"和"简历"并列，但它们对 M03 的匹配度差很远。 |
| 金融/政务/医疗 → M01 | **我不同意，而且这是最危险的一条**。M01 是"专业服务型公司"的展示页（三服务 + 客户 logo + 成果数据 + FAQ + CTA）。金融缺产品条款/风险提示/监管备案；政务缺办事指南/表格下载/无障碍 AA；医疗缺科室/医生/挂号/执业资质/免责。**把这三个指给 M01，等于让用户拿一个营销页去承载合规页面**——README 里 M01 自己都没这么承诺。Lead 的推理是"都是专业机构"，但判据应该是"段落对不对得上"，不是"客户类型像不像"。 |

### 6.5 数字口径的一处错

Lead 说「`unsupported` 29 个词里有大量模板能覆盖」。实测：**29 个词里，模板 README 逐字命中的是 0 个**（`verify-templates.mjs` 对这 29 词逐个 `includes` 全 false，唯一沾边的是 M02 `index.html` 里"儿童座椅"这三个字，是餐厅设施不是行业）。按结构判「能套」的 11 个（含已做的甜品/美甲），**"大量"高估了，实际是 9 个待补 + 2 个已做**。

### 6.6 一个 Lead 和我都要承认的：`unsupported` 名单本身有一处错

`农业` 在 `unsupported` 里，但 `data.js` 的 S19 `scenesYes` **明写着**「生物、医药、农业与标本馆类数据库的检索界面与官网」。实测搜「农业」→ **1 行（S19）**。

所以 `unsupported` 说"农业没有"，而搜索能给 1 行。**这是 `unsupported` 数组与 `data.js` 的直接矛盾**，与模板层无关，是既有数据缺陷。同类但较轻的：`电商/政务/金融/医疗/母婴/儿童/时尚` 这 7 个词只出现在各案的"不适合"从句里（`data.js` 交叉验证：`全在否定句: true`），标为 unsupported 是**正确**的——这点 `unsupported` 没错。

## 7 我的推荐

### 7.1 推荐方案：乙（保留现状骨架）+ 丁（修死路）+ 丙的 11 条限量版

**按优先级：**

**P0（与模板无关，但最伤）**——修「点芯片仍 0 行」。17 个词，其中 6 个已经带着模板卡（用户看到了 M02 却被引向 0 行）。
改 `prompt-copy.js` 芯片 click handler：点芯片时清 `#q`（并在搜索框 aria-live 里说一句"已按行业筛选"）。改完这 17 个词的"点芯片能筛出来"才成立。

**P1**——`TPL_ADJACENT` 补 7 条强匹配（茶饮/宠物/酒吧/会计/个人主页/独立开发者/小吃店）+ `TPL_ADJACENT` 补 4 条边界（家教/培训/儿童/社团），每条按现有规矩写"README 写了什么、没写什么、缺哪段"。**不碰 18 个真给不了的词。**

**P2**——把向导那句 13px 脚注从 `#wz-method` 末行（第 4.94 屏）提到第 1 屏问题之前，作为与"走向导"平级的第二个出口。不动打分逻辑。

**P3**——把 `scene-unsupported` 那块放出来（§3.6）。现在它被内联 `display:none` 压死，29 个词在任何入口都不可见，与 `README.md:78` 承诺的"不藏起来"相反。改法：把 `display:none` 从 `note.style.cssText` 里去掉，或改成跟着 `moreHost` 的展开态走。**这一条是 4 行内的修复，收益是让 29 个词第一次真正可见。**

**P4**——修 `农业` 与 `unsupported` 的矛盾（要么从 `unsupported` 移除，要么从 S19 的 `scenesYes` 移除，二选一，需要作者裁定）。

**P5**——`TEMPLATES[].desc` 里"信息密度克制"这句无 README 依据，改成有依据的说法，或在该卡上标明"作者判断"而非"README 原文"。

### 7.2 为什么不是甲

甲会让 30 案的存在感变弱，这不是价值判断，是实测：现在的模板带（最轻的接法）在「设计工作室」上已经占掉 54% 首屏、把 3 行方案全部推到首屏外。混进 `#ledger` 只会更糟。而且甲解决的问题（模板看不见）**在实测里不存在**——49/73 词已经有模板输出。

### 7.3 我放弃了什么

1. **放弃让 29 个 unsupported 词全部"有话说"**——18 个词模板结构上真给不了，继续诚实说"没有"比编一句"可以当起点改"更有价值。
2. **放弃让向导推荐模板**——模板没有 `report.json` 口径的实测值，进欧氏距离排序就是造假。向导不覆盖模板层是对的，错的是它把这句话藏在第 5 屏。
3. **放弃"把模板做成第四个筛选维度"**——那会让 `#count` 的"30"失去意义，而"30"是整个选型台的锚。
4. **放弃修 `sceneIndex` 与 `data.js` 的 55 条"索引无据"**——索引是人工裁定，比全文匹配准，这 55 条里绝大多数是对的（如「档案」收 S07/S11/S23 而不收 S13/S15/S17/S19 是判断）。真正要修的是它导致的副作用（P0），不是它本身。

## 9 一页话总结

模板层**已经在里面了**（49/73 词有输出），Lead 的"完全不在索引里"是事实但结论过期。真正的问题是**它说得不准**：14 个词界面说"给不了"，其中 7 个（茶饮/宠物/酒吧/会计/个人主页/独立开发者/小吃店）模板的段落匹配度和已经放行的甜品一样高，只是表里没写；另 7 个是边界情况，该说"可当起点"而不是"给不了"。

比模板层更该先修的是**17 个词的芯片死路**：空状态写着"点芯片能筛出来"，照做还是 0 行，因为芯片不清搜索框、而筛选是取交集。这 17 个里有 6 个的模板块已经给出了卡片。

还有第三件、也是最便宜的一件：**29 个 unsupported 词的说明块从来没显示过**（内联 `display:none` 写死，展开也压着），而 `README.md:78` 写着"不藏起来"。4 行内可修。

**推荐**：保留现有的独立通道骨架（乙），补 11 条相邻候选（丙的限量版），先修芯片死路（丁），把向导那句 13px 脚注提到第 1 屏。**放弃**甲（会把 30 案压下去，实测 54% 首屏）、放弃"29 个词全部有话说"（18 个真给不了，编不出来）。
