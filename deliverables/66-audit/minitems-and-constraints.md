### 1.3 S18 的偏差是报告自己写对了、数据文件写错了

`60-minitems-degrade-audit.md:42` 写的是：

> `index.html:97/121/145` 三段 `pre.lines`，**每段 20×`span.ln`**（文案"每 20 行压一条折痕"）

"每段 20 条"是对的（实测段1=20、段2=20、段3=20，共 60）。但报告表格的 `minItems` 列填的是 **20**，
而不是 60。`minitems-parsed.json` 照抄了 20，提示词就写"20 个条目"。

```

段1: 全部 span.ln=20  其中 ln--out=7  普通=13
段2: 全部 span.ln=20  其中 ln--out=3  普通=17
段3: 全部 span.ln=20  其中 ln--out=3  普通=17
总 span.ln = 60
```

这是**报告表格列填错**（把「每段条数」当成「总条数」），不是口径分歧。
按报告自己的口径（同父级兄弟组取最大的一组）应该是 20 —— **报告的口径与表格值在这案上是矛盾的**：
`minItems` 定义为"取最大的一组"，3 段各 20 条、父级不同，最大组就是 20；但 S18 的设计规模显然指 60 行。
**报告在 S18 上同时用了两套口径**：口径 1 说"取最大一组"（→20），正文说"三段各 20 行"（→60）。
提示词取 20，对"版式规模"这个语义来说偏小 3 倍。

## 2. 结构约束段的内部一致性

### 2.1 HEAD 版（审计对象）：第 1 条与第 2 条方向相反，13 案

**但互斥没有消失，它搬家了**：从「第 2 条 vs 第 3 条」搬到了「第 1 条 vs 第 2 条」。
第 1 条以第一人称断言"我实际有 N 个"，第 2 条紧接着要求"用你真实的条目数去排"——
**同一件事给了 AI 两个互不相容的信息源**：一个是提示词刚刚替他声明的事实的，一个是让他自己去问的。
13 案（恰好是 `degrades=yes` 全集）同时含这两句。

顺带一个机械缺陷：第 2 条里 `请先用你真实的 条目数去排` 有一个多余空格，
因为模板是 `"真实的 " + unit + "数"`，`unit="条目"` 拼出 `真实的 条目数`。13/30 案都带这个空格。

### 2.2 用户拿到这种提示词，AI 会怎么选

这是判断题，我给出推理链而不是结论式断言：

1. **第 1 条是陈述句、第一人称、带具体数字**（"我实际有 46 个条目"）。LLM 会把用户第一人称陈述
   当作**给定事实**，权重高于祈使句。这符合 instruction hierarchy 的常见行为：
   事实前提被当作"上下文"，约束被当作"要求"，两者冲突时模型倾向保住上下文（因为改上下文等于篡改用户信息）。
2. **第 2 条是条件句**（"如果确实不足 N 个"）。模型会先判断"是否不足"——而第 1 条已经断言
   "有 N 个"，于是条件不成立，第 2 条的补救分支**永不触发**。
3. 结果：13 案的提示词里，第 2 条实际上被第 1 条**短路**了。AI 照 N 排，不问用户。
   对 `degrades=yes` 的案这恰好是"对的答案、错的理由"（N 本来就是要排满的槽位数）；
   但**代价是 AI 会编造 N 条内容**——因为第 1 条说的是"我有 N 个"，AI 只能假设内容存在，
   而用户没给内容，于是 AI 自己编。这正是第 2 条想禁止的"为了凑数编造内容"。
4. **对 `degrades=no` 的 17 案，后果更糟**：第 2 条说"条目增减只会让页面变短、按你真实的数量排即可"，
   而第 1 条说"我实际有 46 个"（S07）。这两句在这里**没有任何一方能救**：
   第 2 条给的是自由，第 1 条给的是数字。模型最可能的输出是折中——排 46 条编造内容，
   或者排十几条然后自称"46 条中的一部分"。两种都不可验收。

**这就是为什么本轮的修法（LIVE 版）方向是对的**：把 N 从"我"这一侧挪到"版式"这一侧
（"这个版式设计时排了 46 个条目——这是版式的规模，不是你的内容量"），
第 1 条从**事实断言**降级为**背景说明**，第 2 条才成为唯一的内容量指令。

### 3.2 对照"我只有 3–10 个产品"

一个真实小生意（咖啡店、理发店、设计工作室）手上通常有 3–10 条内容。按这个区间看：

- **`degrades=yes` 的 13 案里，9 案的 N 超过 10**（S02 16、S14 11、S15 14、S18 20、S19 20、S29 23，

  它说的是"我有 N 个"。

  都在 12 以上**。这些案删到 3 条只是变短（报告 §对照"我只有 3 个产品" L86-88 明确列为"可放心用"），
  但提示词第 1 条会告诉 AI"我有 46 个"，**把一个可放心用的案变成一个会逼 AI 编 46 条内容的案**。

### 3.3 如果用户真按「我有 46 个条目」去理解

后果按可信度排序：

1. **AI 真的会排 46 个。** 这不是猜测：第 1 条是第一人称事实断言 + 具体数字 + "就排 N 个"的祈使句，
   三重要素叠加。模型没有动机去质疑用户自己报的数。
2. **内容从哪来？编。** 用户只有 5 个产品，AI 要在 46 个槽位里填东西，只能造 41 个假产品名。
   而第 2 条（HEAD 版）明明写着"不要为了凑数编造内容"——**提示词自己制造了它自己禁止的行为**。
3. **验收三问抓不住。** 第 2 问是"首屏、卡片、页脚上的编号是不是同一串"——AI 编的 46 条编号
   完全可以做到连续一致。这条验收标准检验的是**内部一致性**，不是**与用户真实内容的一致性**。
4. **用户拿到的东西不可用且难诊断。** 46 条假内容铺满页面，用户要逐条删到 5 条；
   删完发现版式塌了（若 `degrades=yes`），因为槽位是按 46 个数的。
   **两种失败叠在一起**：先被逼编造，再被逼留洞。
5. **对 S07 这种"设计规模=46"的案，46 甚至不是用户能理解的量级。** 它是"一份 1950 年代报纸目录
   有 46 条分类广告"的审美参照。用户点复制时想的是"我要一个目录样式的页面"，
   拿到的是"我实际有 46 个条目"。**这句话在语义上是假的**——用户没有 46 个条目，
   也不可能有，因为他经营的不是 1950 年代的报纸。

## 4. 约束条数是否超过 LLM 可靠执行上限

### 4.1 我的判据（先写判据再数）

一条「**独立约束**」必须同时满足三条：

1. **可单独违反**：存在一份 HTML，满足其余全部要求，只违反这一条。
   → 排除同义重复。例如「配色只用这几个值」与「不新增更多彩色」违反后者必违反前者，算 1 条。
2. **可从产物判定**：看最终 HTML/CSS 就能判真假，不需要问作者意图、不需要外部资料。
   → 排除「验收三问」（自检流程）、「请先告诉我」（对话要求）。
3. **不是另一条的逻辑推论**：若 A 成立则 B 必然成立，B 不计。
   → 例如已限定「线宽只用 1px、2px」，「不要自创第三级」是同一句的复述。

计数粒度：

- 一个**封闭取值集合**算 1 条（配色 7 个 HEX 算 1 条，不是 7 条）。
- 一条句子里的**每个可独立违反的数值规格**各算 1 条：S26 机制句
  「5:3:4 分宽 / 高 100%/64%/80% / 沉 16px / 压叠 1.5px 与 1.2px / 12 栏 / 11°」= 8 条，
  因为可以只把"栏线 11°"改成 10° 而其余全对。
- 「防退化 ①–⑧」每条算 1 条（8 条禁令互不蕴含：可以只犯 emoji 不犯渐变）。
- 「本案专属禁令」（risk 段）按**可独立违反的规避动作**计数（编号项按项数）。
- **不计**：开头两行（用户自填，不是对 AI 的约束）、验收三问、'请先告诉我'、
  '不要解释只给代码'（归入"输出格式"组，单独列，但仍计入总数——因为它可独立违反）。

### 4.3 但我认为「20 条」这个门槛本身不成立——独立复核

上一轮红队引用「FollowBench 之类，约 20 条约束是 LLM 连续全满足的上限」。
我查了原始来源，**这个数字与论文数据差一个数量级**：

| 来源 | 实测结论 |
|---|---|
| [FollowBench](https://arxiv.org/abs/2310.20410)（ACL 2024） | 测试 13 个模型，**约束层数只做到 5 层**（L1–L5）。GPT-4 在**第 5 层**（5 条约束）的 HSR 仍有 **61.9%**；CSL（连续满足层数）GPT-4 = **3.3**、GPT-3.5 = **2.9**，开源模型大都在 1.4–2.4。 |
| [IFEval](https://arxiv.org/abs/2311.07911)（Google） | 25 类可验证指令、约 500 条 prompt，每条含**一条或数条**可验证指令；**没有给出「N 条以上就崩」的阈值**。 |
| [ComplexBench](https://arxiv.org/abs/2407.03978)（NeurIPS 2024 D&B） | 4 类约束、19 个维度、4 种组合方式；结论是"复杂多约束组合下现有模型显著不足"，**同样没有 20 这个数**。 |

三点必须说清楚：

1. **FollowBench 的最大难度只到 5 条约束**，不是 20。它测的是"L1→L5 性能如何下降"，不是"超过 20 条会怎样"。
   拿它支撑"20 条是上限"是**把论文里根本不存在的实验条件当成结论引用**。
2. **它的关键指标 CSL 是"连续满足的层数"，GPT-4 只有 3.3** —— 也就是说，
   如果非要给一个"可靠执行上限"，论文给的是 **约 3 条**，不是 20 条。
   20 条这个数字**比论文数据宽松 6 倍**。
3. 论文的约束是**短句、单点、可规则校验**（"写超过 400 字"、"AI 至少出现 3 次"）。
   本案提示词的"约束"是复合的长句，一条里常含 5–8 个数值规格（S26 的机制句一条就是 8 条）。
   **两边的"一条"根本不同量级。**

我的结论：**「20 条」这个门槛既不准确（来源不支持）也不重要（30/30 案都远超它，无论用 20 还是用 3）**。
真正的发现是：**用任何一个可信的数字来衡量，这套提示词都严重超标**——
按 FollowBench 的 CSL≈3 衡量超标 13 倍，按红队声称的 20 衡量超标 2 倍。

### 4.4 哪些约束可以合并/删除而不损失信息

按"删掉后 AI 产物的可验收性是否下降"排序，我给出**四组**可压缩项（合计可减 8–12 条，减到 27–31 条）：

**A. 「防退化 ①–⑧」8 条 → 3 条（省 5 条）**
这 8 条里，②⑥ 是同义（都是"不要圆角卡片 + 柔和投影 + 玻璃拟态"这一族），
③④ 是同义（都是"不要通用落地页结构"），⑤⑦⑧ 各自独立。
且 ①（紫蓝渐变）与视觉硬约束第 1 条"配色只用这几个值"**逻辑重复**——
只要 AI 真按白名单取色，①永远不可能违反。**① 是冗余的**。

**B. 字体行 5 条 → 3 条（省 2 条）**
「标题链」「正文链」「等宽数字」是 3 条独立要求。
「不要用 Playfair Display、Inter、Roboto」是**第 4 条**，
但它与第 1 条的"按这个顺序取第一个可用的"部分重复（链里没这三个，取链就不会用到）。
真正需要它的是"链全缺字时不要退回这三款"这个边界，可以并进"回退禁令"那一条。

**C. 机制句 8 条 → 4 条（省 4 条，仅对 S26/S18/S22/S24 这类高值案）**
机制句是全文最长的单句（S26 一条含 8 个数值规格）。但其中**位置/尺寸类数值**
（"沉 16px"、"高 100%/64%/80%"）与**线宽类**（"压叠 1.5px 与 1.2px"）混在一起，
而线宽类已经在第 5 条有白名单。**把机制句里与第 5 条重复的线宽值删掉**，不损失信息。

**D. risk 段 4–5 条 → 2–3 条（省 1–2 条）**
risk 段的价值最高（它是唯一"写给会犯错的人"的具体禁令），但它**有 8 案被 220 字截断**
（见 §5.3），截断处正好切在编号项中间。截断后的残句（"（4）与…"）是**纯噪声**——
既不能执行也不能忽略。要么给足字数，要么按项边界截断。

### 5.1 跨案引用：「与 7 号方案」「20 号（针笔走线）」——9 案，AI 无从解析

"10 号"、"8 号"、"26 号"是**这套图集内部的方案编号**。用户把提示词贴给 ChatGPT 时，

  它应该留在 `_specs/`，不该进用户提示词。

```
Select-String -Path deliverables/66-audit/prompts/*.txt -Pattern "\*\*" | Group-Object Filename → 每案 1 处
S19.txt:18: 3. 版式里至少要 6 个**不同的**图片位置（不是6 个 img 标签就够——...）
```

提示词是纯文本，粘给 AI 后 `**不同的**` 会以字面量出现。多数模型能正确理解为强调，

`不是 6 个 img 标签就够` 里 `不是` 与 `6` 之间**缺空格**（模板是 `"（不是" + N + " 个 img"`），

## 6. 我核实后认为 Lead 说错了的地方

### 6.1 「30 案的 minItems 中位 10」——中位是 9.5，Lead 说对了近似值，但有一处更重要的偏差

`minItems` 升序：`6 6 6 6 6 7 7 7 8 8 8 8 9 9 9 10 10 11 12 12 12 13 14 14 16 20 20 23 27 46`，
第 15/16 位是 9 和 10，**中位数 9.5**。Lead 说"中位 10"是对的近似。
**但最大 46（S07）这个说法掩盖了一个更重要的事实**：S07 的 46 是**真实的不同条目**
（正页 18 条 + 纸背 28 条，共 46 个 `<li>`，每条有独立的标题、页码、日期、分类号），
不是"作者数出来的设计规模"这么简单——它确实是这个版式的真实内容量。
**46 荒谬的原因不是"数字是编的"，而是"这个版式的真实内容量被当成了用户的内容量"。**
这个区别重要：修法不是"把 46 改小"，而是"把 46 的归属说清楚"（LIVE 版正是这么修的）。

### 6.2 「degrades=yes 的 13 案」——数量对，但名单与数据文件不一致

Lead 说"degrades=yes 的 13 案"，数量正确。但**数据显示两个版本的 13 案名单不同**：

```

报告表格 degrades=yes (13): S02 S04 S05 S08 S12 S14 S15 S19 S20 S22 S23 S29 S30

只在 JSON 里 yes： S18
只在报告里 yes： S30
```

`60-minitems-degrade-audit.md` 的表格（L42 写 S18=`no`，L54 写 S30=`yes`）与
`87a0235` 那次 commit 改过的数据文件（S18→`yes`、S30→`no`）**互相矛盾**。
commit message 明确写了这次改判（"### 8. 数据修正：S18 / S30 的 degrades 判反了"），
**但没有同步更新 60 号报告**。所以现在仓库里有两份权威数据，差 2 案。

我核实了 CSS，**commit 的判断是对的**：
- S18 `style.css:132` `.hangrail .hang{position:absolute;left:0;top:calc(var(--at,0) * var(--line) + 2px)}`
  —— 4 张牌按 `--at` 行号绝对定位，日志从 60 行砍到 6 行时两张悬空 → `yes` 正确。
- S30 `style.css:188-189` `.cut__col{display:flex;flex-direction:column}` +
  `.cut__col--a{grid-column:1/7;grid-row:1}` —— **列**是写死的，**列内条目**是 flex 自动堆，
  删 4 张只是变短 → `no` 正确。

**所以错的是 60 号报告，不是数据文件。** 但报告是被 `build-prompts.mjs:88` 注释引用为"来源"的那份，
它的权威性高于派生物。这个不一致会让任何后续审计得出相反结论。

### 6.3 「30 案的提示词仍含互斥指令」——按 Lead 描述的那个互斥，答案是 0 案；但有个更隐蔽的互斥，13 案

Lead 描述的互斥是「第 2 条说按实际数量收敛、不要凑」vs「第 3 条说先凑到 N 个」。
**这个互斥已经不存在了**：HEAD 版里第 3 条根本不存在（被合并进第 2 条），
`凑到/先凑/补足` 在 30 份里命中 0 次。

**但存在另一个互斥，Lead 没提到**：第 1 条（"我实际有 N 个"）vs 第 2 条（"用你真实的条目数"）。
这个互斥在 **13 案**里同时存在，恰好是 `degrades=yes` 全集。
上一轮 Agent 修的是"第 2 vs 第 3"，修对了，但**没有发现第 1 条才是真正的地雷**——
因为它长得像背景陈述，不像约束。

### 6.4 「约 20 条约束是 LLM 连续全满足的上限（FollowBench）」——来源不支持这个数字

见 §4.3。FollowBench 的最大难度是 **5 条约束**，GPT-4 的 CSL 是 **3.3**。
"20 条"这个数字在论文里**不存在**。如果要用一个数字，应该是 **约 3 条**（CSL）。
用 20 条反而**低估了问题的严重性**：按 3 条衡量，30/30 案超标 10 倍以上。

### 6.5 「提示词里有 C-1.6 / R-28 / V-11 / 0X 号文件」——命中 0 次

```

→ 只命中配色变量名（#B8860B（gold）这类），无内部编号、无文件名、无 CSS 变量名
```

提示词在这一项上**是干净的**。真正的问题不是我预期的内部编号，而是 §5.1 的跨案引用（"10 号"）。

## 7. 我抓到的、Lead 没提到的问题

按严重度排序。

### 7.1 【最严重】提示词第 2 条禁止的东西，是 3 个案子的签名机制

见 §2.3。"不留空位、不留占位符、编号连续不跳号"对 S19/S02/S06 是**反设计**：

- **S19**：`index.html:215` 明写「空抽屉不删除、不合并：第 4 与第 16 两个空位留在柜面上」，
  2 个 `dw--void` 是"检索号即档案"机制的证据；
- **S02**：第 5 级 `is-vacant` 是"16 件器物实测台账（缺号 1 处）"的证据，删掉 caption 就成假话；
- **S06**：3 张 `card--blank` + 1 张 `card--fault` 是"这一页打不开"的叙事。

**一个严格照提示词做的实现，会把这 3 案最核心的东西删掉。** 这不是措辞问题，是提示词与设计意图
正面冲突。而且这个冲突**两个版本都有**（HEAD 第 1 条 / LIVE 第 2 条都写"不留占位符"）。

### 7.2 S18 的 minItems 差 3 倍（20 vs 60），且报告自身口径矛盾

见 §1.3。报告正文说"三段各 20 行"（=60），表格填 20，数据文件抄 20。
`degrades=yes` 的案里 N 是"槽位数"，S18 的 60 行日志是**同一段连续纸**上的行，
按"同父级兄弟组"口径确实该分 3 组取最大（=20），但按"设计规模"语义该是 60。
**报告在 S18 上同时用了两套口径。**

### 7.3 S23 的 minPics=10 但原型只有 6 张不同的图

见 §1.5。提示词第 3 条明确要求"**不同的**图片位置，同一张图重复用不算"，
而 S23 原型自己把 4 张图各用了 2 次。**提示词在要求 AI 做到原型没做到的事。**

### 7.4 「不要自创第三级」与实有级数不符：13/30 案

```
node deliverables/66-audit/_chk-third.mjs
S25    1 级  3px，不要自创第三级。                                     ← 只有 1 级
S13    7 级  1px、2px、3px、5.5px、7px、9px、14.5px，不要自创第三级。    ← 已有 7 级
S24    6 级  0.4px、0.6px、0.8px、1px、2px、2.5px，不要自创第三级。
S29    6 级  0.4px、0.6px、1px、2px、3px、6px，不要自创第三级。
S15    5 级  0.5px、0.8px、1px、1.7px、3px，不要自创第三级。
S16/S18/S19/S20/S30  4 级
S08/S09/S11/S12/S14/S27  3 级
```

「不要自创第三级」这句话只在恰好 2 级时成立（14 案）。其余 13 案里：
- 7 案有 3 级 → 句子自相矛盾（"这三级里不要有第三级"）；
- 5 案有 4 级 + 1 案 5 级 + 2 案 6 级 + 1 案 7 级 → **AI 无法理解"第三级"指哪一级**；
- **S25 只有 1 级**（`3px`）→ "不要自创第三级"完全无意义。

正确写法应该是"只用上面这几个值，不要新增第五个/第二个值"，随级数变化。
这是**模板把 2 级案的措辞推广到了 30 案**。

### 7.5 S07 的机制句要求 0.5px 栏线，但线宽白名单是 1px、2px

```
node deliverables/66-audit/_chk-linewidth.mjs
S07 白名单[1,2]  机制句: 栏线0.5px✗   <<< 冲突
S18 白名单[0.8,1,2,4]  机制句: 边条12px✗   <<< 冲突
S09 白名单[2,3,3.5]  机制句: 描边3.5px✓  内线2px✓
```

S07 机制句（第 6 行）：「正面 5 栏对背面 7 栏、**栏线 0.5px**」；
第 5 条（第 13 行）：「线宽只用这几级：**1px、2px**」。
**AI 无论怎么做都违规**：画 0.5px 栏线违反第 5 条，画 1px 栏线违反机制句。

S18 是另一种：「两侧 **8px 边条**」—— 但 8px 是边条**宽度**不是线宽，属误报；
真正的冲突在 S18 的「**12px 孔距**」（间距不是宽度）。
所以**精确判定只有 S07 一案是真冲突**（S18 是我的关键词窗口误报，已在 v2 收紧后保留但标注）。

这个 bug 的成因：机制句来自 `_specs`/`mechanisms.mjs`，线宽白名单来自 `clean-dna` 扫 CSS，
**两条数据流从没有人放在一起比对过**。

### 7.6 `o.count` / `o.unit` 是死参数，但注释说它们有语义

`prompt-copy.js:302-303`：`var count = o.count || s.minItems; var unit = o.unit || "条目";`

全库 grep：`o.count` / `o.unit` **只在定义处命中**，`deliverables/` 下 200+ 个探针脚本调的都是
`buildStylePrompt(id)` 或 `buildStylePrompt(id, {biz, action})`。

```
Select-String -Path prototypes/_selection/*.js,prototypes/_selection/*.html -Pattern "count\s*:|unit\s*:|tone\s*:"
app.js:22:  tone: new Set(),      ← 是搜索状态集合，不是 opts
wizard.js:77:  tone: r.tone,       ← 是 UI 状态，不是 opts
prompt-copy.js:740:  return { biz: ..., action: ... };   ← 只返回两个字段
```

LIVE 版给这两个参数写了 10 行注释解释"它们现在的意思是换一个版式规模"，
**但没有任何调用方**。这正是仓库反复记录的病（"界面上有的控件，背后没有消费者"）
换了个位置：**有注释的参数，没有调用方**。

### 7.7 提示词长度：均 1793 字（HEAD）/ 1816 字（LIVE），落在 Lead 说的区间内

```
HEAD 版字符数: min=1632 max=1920 均=1793 总=53780
LIVE 版字符数: min=1652 max=1946 均=1816
```

Lead 说"约 1,630–1,920 字"，**准确**。LIVE 版修完后变长 14 字（`均 1793 → 1816`），
因为第 1 条从"我有 N 个"改成了"这个版式设计时排了 N 个条目——这是版式的规模，不是你的内容量"。
**这个变长是值得的**（用一个从句换掉一个假前提），但值得记录：修 bug 让提示词更长了，
而 §4 的结论是提示词已经太长。

### 7.8 S02 在 1024–1439px 上只显示 14 级，`minItems=16` 只在 ≥1440px 成立

`prototypes/S02-gilded-symmetry-salon/style.css:409` 与 `:416`：

```css
@media (min-width: 1024px) and (max-width: 1439px) {
  .ladder-right .step:nth-child(n + 8) { display: none; }   /* :409 */
}
@media (min-width: 768px) and (max-width: 1023px) {
  .ladder-right .step:nth-child(n + 8) { display: none; }   /* :416 */
}
```

右梯 9 级在 768–1439px 上被砍到 7 级，**总可见单元 16 → 14**。
而 `minItems=16`、`degrades=yes`、提示词说"位置是按 16 个数出来的，少一个就空一格"。

```
全库扫描（nth-child(n+N){display:none}）：
S02: 3 处  nth-child(n + 8) { display: none    ← 砍的是重复单元本身
S28: 2 处  nth-child(n+4) { display: none      ← 砍的是表格列（注释明写"数据仍在 DOM 里"），不是单元
```

所以 **S02 是唯一一案**：它的 `minItems` 与 `degrades` 判定只在 1440px 以上成立。
在 1366×768（最常见的笔记本分辨率）上打开原型，实际只看到 14 级、**不留洞**——
因为作者用媒体查询把多的两级直接隐藏了。
提示词却告诉 AI"少一个就空一格，把空出来的位置删掉、整块重排"。
**AI 照做，会得到一个「在 1440px 上也不该留洞」的版式**，与原型的行为不符。

这是 `minItems` 判据的一个盲点：60 号报告的口径只数 DOM，**没数媒体查询关掉了几个**。
