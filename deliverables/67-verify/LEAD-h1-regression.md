> 执行 C（`EXEC-rules-compliance.md`）报「三档实测 1440/768/390」，规划 Agent 报「五档」。
> 我跑了 **8 档**，发现他们都没测到的一档退化。

**执行 C 说「1180 档余量 63px 最薄」——不完整。1024 和 980 档已经是负余量（−22 / −38）。**

## 关键是：1024 档是「从 1 变 0」

我做了 A/B（在页面上注入 `!important` 把 h1 改回旧的 `clamp(30px,4vw,56px)`）：

| 档位 | 现在（h1 5.2vw） | 旧（h1 4vw） | 变化 |
|---|---|---|---|
| **1024×900** | 首卡 590 / **完整卡 0** | 首卡 564 / **完整卡 1** | **退化：1 → 0** |
| 980×900 | 首卡 466 / 完整卡 0 | 首卡 441 / 完整卡 0 | 不变（本来就 0） |
| 1180×900 | 首卡 560 / 完整卡 1 | 首卡 530 / 完整卡 1 | 不变 |

**1024×900 是 iPad 横屏、13" 笔记本的常见尺寸。** 接上 `--s-h1` 后 h1 从 53px 涨到 61px、
折成两行，把首卡推后 26px，正好越过「完整卡」的临界点（余量从 +? 变成 −22）。

## 为什么会漏

- **执行 C** 只测了规划 Agent 给的 5 档（1440/1180/980/768/390），而且它的 980 档记录是「完整卡 0→0」——它测到的 980 本来就是 0，看不出退化
- **规划 Agent** 测的是 1440/1180/980/768/390，它的表里 980 也是「0→0」、`完整卡` 列写「0→0」
- **两边都没测 1024**，而 1024 恰好是唯一「原来是 1、现在变 0」的档

## 我的判断

**这是一个需要决策的取舍，不是必须回滚的 bug。**

- `--s-h1` 的收益：1440 档 h1 从 56→74px（3.9→5.1vw），修掉了 `focal-point` FAIL（阈值 4.5vw）；四档（1440/1280/1180/768）`focal-point` 转 PASS
- `--s-h1` 的代价：1024 档首屏完整卡 1 → 0；980 档本来就是 0，未受影响

**1024×900 的首屏完整卡**与**选型台自己的闸门合规**，两者都要付代价时选哪个？

我的倾向：**接受 1024 档的退化，保留 `--s-h1`**。理由：
1. `focal-point` 是仓库自己的闸门规则，而「首屏完整卡」这个指标移动端审计已证明「无出处、无区分力」（3800 也是同类问题）
2. 1024 档退化的表现是「首卡露出大部分但不完整」——用户仍能看到编号、标题、一句话定义、闸门结论
3. 若要两者兼得，可以把 1024-1180 档的 h1 单独调回 4.5vw（过线但不高），那是第 3 种选择

**这一条要写进文档，不能让下一个读 commit 的人以为「所有档位都变好了」。**
