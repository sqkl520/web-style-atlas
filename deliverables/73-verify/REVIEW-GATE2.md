## 2. PC1 · check-texture 的选择器解析（最重）

### 2.1 交付方声明 vs 事实

声明：重写三版；v3 对每个 `{` 记录块、配对 `}` 取声明；body 规则数 **85**；S02 已修；ab-texture 改 7 个变异。

事实：**全部属实。** 我不用它的任何数字，自己重建。

### 2.2 我做了什么：三种独立方法数 body/html 规则

方法必须与 v3 不同。v3 的做法是「对每个 `{`，**往回**找上一个 `}`/`;`/`{` 定界符当选择器」。

- **方法 A（我的主方法）**：字符级 tokenizer。处理字符串字面量、括号嵌套、注释；
  选择器归属由 **token 流**决定（`open` 前紧邻的 `sel` token），decls 用**字符位置切片**取。
  这是「向前归属」而不是「向后回溯」，与 v3 的启发式正交。
  → `INDEP files=31 allRules=6987 bodyRules=85`

- **方法 B（沙箱内跑 v3 本身）**：把 31 个 `style.css` 复制到沙箱，
  跑 v3 副本 → `body/html 规则数 85`。

- **方法 C（纯正则 token 边界）**：`/(?<![\w.#:\-])body(?![\w.#:-])/` 找裸 tag token，
  再检查其右侧跳过空白后是否为 `{` 或 `,`（多选择器组）。
  → `方法C(选择器 token): 85`

**三法一致 = 85。** 终验当时说的"闸门只看到 34/85"确实修好了。
逐案分布也对得上直觉（S16/S24 各 5 条，S17 只有 1 条，S01 3 条）。

### 3.3 关键问题：这个 `lowContrast: 0` 是"检查过的 0"还是"跳过的 0"？

**我改用可证伪的实验。** 直接读 `probe.mjs:254-262`：

```js
const bgBehind = (el) => {
  for (let p = el; p && p !== document.documentElement; p = p.parentElement) {
    const cs = getComputedStyle(p);
    if (cs.backgroundImage !== 'none' || …) return null;   // ← 短路点
    const v = rgba(cs.backgroundColor); if (v.a >= 0.9) return v;
    if (cs.position === 'absolute' || cs.position === 'fixed') return null;

  return bodyBg;
};
…
const bg = bgBehind(t.el); if (!bg) continue;   // ← :282 静默跳过

**实验 1（机制级，最小对照）**：造两个只有 body 背景不同的页面。

| 变体 | body 背景 | `lowContrast` | `body.contrast` |
|---|---|---|---|
| A | `background-color:#0b0b0f`（纯色） | **2 条**（ratio 1.1，need 4.5） | null |
| B | 同色 + `background-image:url("grain.png")` | **`[]`** | null |

但 A 抓到 2 条低对比度、B 一条都没有。**bgBehind 短路会让 lowContrast 恒为 0 这件事，
我用真实 Chrome 复现了。** 这就是终验说的「虚拟 0」。

**实验 2（在已修的 S02 上）**：把一段 18px、`color:#1f1f25`（对 `#0b0b0f` ≈1.2:1）的正文
插进 S02 的 `<body>` 顶部，重跑 inspect：

```

所以 `report.json` 里三个视口的 `lowContrast: []` 是**检查过的 0**，不是跳过的 0。

**实验 3（反证 HEAD 版本）**：`git show HEAD` 的 S02 报告里 `body.contrast` 也是 15.8、
`lowContrast` 也是 `[]` —— 但 HEAD 的 `body` 规则**确实有** `background-image: url(...)`。

光看 `lowContrast: 0` 无法区分真假，必须靠实验。也说明交付方"手工测算"那条论据**不足以**支撑结论 ——
真正支撑结论的是我实验 2 的结果。

### 4.4 为什么会漏：判据的形态问题

```js
const isMeta = sentences.some((s) =>
  /本闸门|这条断言|检查器|check-contract|check-twolines|C[1-6]\b|该规则|这个工具/.test(s) &&
  /抓到|报出|检测到|发现|上线当天|会红|报\s*WARN|拦下|据此/.test(s));
```

这是「主语出现 ∧ 动作出现 → 一律放过」。它没有区分**动作的宾语**：
- 「本闸门**抓到**两处矛盾」= 工具发现了问题 → 真元描述
- 「检查器没有**报出**这些欠款」= 工具**没**发现问题 → 这是在**声称欠款仍然存在**

两者主语和动作都齐，但语义相反。另外「该规则从未被任何断言**检测到**已清」
里的"检测到"是**被否定**的（从未），判据也没看否定词。

这是**判据设计本身的缺陷**，不是"再多堆几个词"能解决的。
它比修复前好（修复前是纯 OR、±410 字符窗口，恒真式；现在是 AND + 同句，至少挡住了
"每条只嵌一个元词"这一类），但**还不是一个能信的结构判据**。

## 5. PC5 · ab-stale 的基准 + 文档归因

### 5.1 交付方声明 vs 事实

声明：基准改为从 `report.json` 读 `at`；M3/M4 仍用 `report.mtime`；**现在 4/4**；
`LEAD-P1b` 归因已改正。

事实：**实测 3/4**（多次运行、多种起点下都复现）。且 **M2 失败的真因既不是基准、也不是阈值**。
这是本次复核最重要的发现。

### 5.2 我跑出来的

```
[基准] report.at    = 2026-10-22T11:32:12.307Z
[基准] report.mtime = 2026-10-30T20:07:32.960Z
[基准] 两者差 12035 分钟 ← 第一版误用了 mtime

✓  M1 把 css mtime 调到比 at 新 10 分钟 → 必须红       （exit=1）
✗  M2（反向）把 css 调到只比 at 新 2 分钟 → 必须绿      （exit=1）   ← 声明说绿
✓  M3 把 jpg mtime 调到比 report.mtime 新 10 分钟 → 必须红 （exit=1）
✓  M4（反向）把 jpg 调到只新 1 秒 → 必须绿（5 秒容差）     （exit=0）
═══ check-stale 变异测试: 3/4 ═══
```

而且这个 3/4 **不稳定**：换一个起点重跑，M3 也会挂（变成 2/4），M2 有时又绿。
理由是脚本本身有第二个基准缺陷（§5.5）。**所以「4/4」这个声明在任何起点下都不成立。**

### 5.3 M2 为什么红：不是基准，是提示词链

交付方与终验都把 M2 归因成"测试脚本用错了基准（`report.mtime` vs `at`）"。
我按同样的设置隔离触发源，抓到的是**第三条链**：

```
── M2 css = at + 2min   期望=0 实得=1 ✗
     提示词链·dna-raw(_prompts/dna-raw.json)  S12-lime-knockout-wall/style.css 落后 5 分钟
     →  node prototypes/_prompts/extract-dna.mjs
```

也就是说：把 S12 的 `css` 设成 `at + 2min`（2026-10-30T20:21:19），
这个时刻**同时也比 `_prompts/dna-raw.json` 的 mtime（20:16:37）新 4.7 分钟**，
于是 `check-stale.mjs` 第 ③ 节（提示词链，阈值 `>3`，比的是**输入 mtime vs 产物 mtime**）
独立触发。**跟第 ① 节的 3 分钟阈值、跟 `at`/`mtime` 基准都无关。**

这是一个**测试隔离缺陷**：M2 想测的命题是「第 ① 节阈值 3 分钟 → css 只新 2 分钟时应绿」，
但它选的变异（动 S12 的 css mtime）**会同时改变提示词链的输入 mtime**，
所以这个变异无法只命中第 ① 节。**测试没有隔离被测对象。**

### 5.4 我证明了第 ① 节的阈值本身是对的

把 `dna-raw.json` 的 mtime 抬到 `at+30min`（让它永远比 css 新），隔离掉提示词链，再测边界：

| 设置 | 期望 | 实得 | 第①节是否报 S12 |
|---|---|---|---|
| css = at + 2min | 绿 | 第①节不报（其它链报） | ✗ 不报 |
| css = at + 3min（恰好 3.0） | 绿（条件是 `>3`） | 第①节不报 | ✗ 不报 |
| css = **at + 3min 1s** | 红 | 第①节报「S12 style.css 落后 3 分钟」 | ✅ 报 |
| css = at + 10min | 红 | 第①节报「落后 10 分钟」 | ✅ 报 |

**第 ① 节的 3 分钟阈值与 `>3` 的边界都完全正确。** 交付方把阈值从 1 改到 3 这件事本身没做错。
错的是 **ab-stale 声称 4/4**，以及**归因**（说"真因是测试脚本用错基准"——
真因是**测试没有隔离提示词链**；基准那处改动仍然是对的、必要的，但它**不是** M2 红的原因）。

> 这说明终验当时用 `DEBUG_STALE_CHAIN=1` 看到"四环 gapMin 全为负"是对的：
> 那是在**它那一次**的运行状态下看的。但状态会随渲染/编辑变化 ——
> 我先跑时 dna-raw（20:16:37）比 css 的原始 mtime（10-22）新得多，链是"未触发"；
> 一旦 M2 把 css 的 mtime 推到 20:21，链就触发了。**"链没触发"不是一个稳定事实，
> 而是那次快照的性质。** 这也解释了为什么交付方改完基准后仍然只能在某些起点下看到绿。

### 5.5 我另外发现：ab-stale 自身还有第二个基准缺陷

`ab-stale.mjs:34` 在**脚本启动时**就把 `repMtime` 定死：

```js
const repMtime = statSync(REP).mtimeMs;      // L34
…
const restore = () => { writeFileSync(REP, repOrig, 'utf8'); … };  // L46 ← 每次都会刷新 mtime
```

而 `T()` 在**每个变异前都调 `restore()`**，`writeFileSync` 会把 `report.json` 的 mtime
刷成"现在"。于是 M3 设的 `jpg = repMtime(启动时) + 10min`，实际比较的却是
`report.mtime(现在)`：

```
ab-stale 设的 jpg        = 2026-10-30T20:34:34.972Z
restore() 之后 report.mtime = 2026-10-30T20:25:40.182Z
实际差值（jpg − report）  = 534.8 秒
```

如果启动时 `report.mtime` 离"现在"超过 10 分钟，M3 就必然挂；不到 10 分钟，M3 才过。
**这就是 3/4 与 2/4 之间摇摆的来源。** 同一个脚本、同一台机器，结果取决于
`report.json` 被上次写入了多久之前。

正确的写法应该是**在变异之后**再读 `statSync(REP).mtimeMs` 当基准（或像 M2 那样，
把基准也一起 `utimesSync` 固定住，别让 `restore()` 改动它）。

### 5.6 基准选择本身：哪一节该用哪个？

终验要我逐一确认 `check-stale.mjs` 各节该用 `at` 还是文件 mtime。我读了全文：

| 节 | 行 | 比的是什么 | 该用 `at` 还是 mtime？ | ab-stale 现在用的 | 对吗 |
|---|---|---|---|---|---|
| ① 30 案源文件 | `:69` `(newest - at)/60000` | 源文件 mtime **vs report 里的 `at`** | **`at`** —— `at` 是渲染开始时刻，源文件在渲染前被改才会让报告过期 | M1/M2 用 `at` | ✅ **对** |
| ① jpg 截图 | `:104` `newestJpg > repM + 5000` | jpg mtime **vs report.json 的文件 mtime** | **文件 mtime** —— 这里问的是"两张产物谁更新"，`at` 是元数据、不代表文件写完的时刻 | M3/M4 用 `report.mtime` | ✅ **对（但基准取值时机错，见 5.5）** |
| ② 产品入口 | `:133` `(newest - at)/60000` | 产品源文件 mtime vs `at` | **`at`** | 未单独测 | — |
| ③ 提示词链 | `:222` `(newest - prodM)/60000` | 输入 mtime vs **产物 mtime** | **文件 mtime** —— 生成链没有 `at` 这种元数据，只能比文件 | ab-stale 未覆盖 | ⚠️ **未被测到** |

**结论：ab-stale 的基准选择（M1/M2 用 `at`、M3/M4 用 mtime）在"选哪个量"这件事上是正确的。**
错的是两处实现细节（M3 基准取值时机、以及没有隔离第 ③ 节）。
另外 **第 ③ 节完全没有变异测试覆盖** —— 而它恰恰是 M2 实际触发的那一节。

### 5.7 文档归因是否改正

`LEAD-P1b-stale-guard.md:133-147` 读起来是对的：

> **M2 的说明（终验 Agent 纠正了我的归因）**：我原本写「M2 报 exit 1 是因为同时触发了
> 提示词链的守卫」。**这是错的。** …真因在 `ab-stale.mjs` 的**测试脚本**：它拿
> `report.mtime`（10-30）当基准…差 11967 分钟。所以无论调多新，都会红。…
> **所以 3 分钟阈值本身是有效的**，是测试脚本用错了基准。

**归因文字改了，但改成了另一个（仍然不完整的）错误归因。** 它说"真因是测试脚本用错基准"，
我实测的真因是"测试没隔离提示词链"。两者都不算"提示词链在正常运行中被触发"，
但也不是同一件事。文档还留着 **"记为待修：`ab-stale.mjs` 的基准应改为…"** 这种**未来时**，
而交付方口头声明是"已改" —— 文档没有同步到"已改 + 仍然 3/4"的现状。

`LEAD-P1b:130` 的 M3 那一行仍标 `✓`，与实测不符。

### 5.8 判定

**❌ PC5 未清掉。**
- 基准**选择**（哪个量）改对了，这一点值得肯定。
- 但**「4/4」不成立**（实测 3/4，且不稳定到 2/4）。
- **归因仍然不对**（真因是提示词链 + 测试未隔离，不是 `mtime` vs `at`）。
- M3 有**第二个**同类的基准缺陷（`restore()` 刷新 mtime）。
- 第 ③ 节零覆盖。
