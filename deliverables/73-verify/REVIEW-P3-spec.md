## 1. 结论

**不通过。**

不是因为工作没价值，而是因为**报告的三条头条数字里，有两条是错的，而唯一那条「确凿发现」是假阳性**。

| 报告头条 | 我的复算 | 判定 |
|---|---|---|
| 可核性 260 / 审美 154 | 260 / 154，逐类可复现 | ✅ 成立 |
| 面积和 **30/30 通过** | 加法确实全等于 100，但**核的是规格自身自洽，不是原型符合规格** | ⚠️ 数对、话不对 |
| 断点 **21/23**，S08 真偏差 | 真实是 **28/30**（字面）；**S08 是假阳性**，行为上 30/30 | ❌ 数字错 + 结论错 |
| 基线 29/29 | 可复现，判据偏弱但方向对 | ✅ 成立（弱） |
| 栏数 11 条确认 | 「11」不成立：判据对随机错误检出率仅 **35%**，且 S16 零直接命中被判 FULL | ❌ 不成立 |

一句话：**报告最想让你记住的那件事（S08 的 768），是它自己探针的一个 bug。**

如果按报告的结论去改 `style.css`，会把一个**当前正确**的实现改坏。这是本次验收最需要拦住的事。

另外两点必须点明：

- 报告的「21/23」这个分母不是从数据里来的——`LEAD-p3-breakpoints2.mjs:69` 里硬写了一个 `- 7`，而 30 个案**全部**都有断点断言，正确分母是 30。
- 报告说 S13 的「100」是 `100ms`——**这在物理上不可能**，那个正则要求数字后跟 `px`。真实来源是字段 8 的 `` `border-radius` ≥ 100px ``。误判结论对，**归因是编的**。

### 2.2 第 2 条：攻击「面积和 30/30」

#### 手工抽 3 份，人眼核字段 3

**S02**（`prototypes/_specs/S02.md:19`，字段 3 原文摘录）：

> `#0B0B0F` 炭黑卡纸＝背景，**58%**；`#B8860B` 暗金＝主色与纹样，**18%**；
> `#EFE6D0` 象牙纸白＝正文与烫金漏白，**20%**；`#3A2E1A` 暗棕＝阴影与压痕，**4%**。
> **面积和 100。**

我的加法：58 + 18 = 76 → 76 + 20 = 96 → 96 + 4 = **100**。✓

**S13**（`prototypes/_specs/S13.md`，字段 3）：

> 背景色 `#F4E3BE`（…饱和 22.1%、明度 85.1%，情绪：无墨）**56%**；正文色 `#241F17`（…）
> **27%**；主色 `#7B612C`（…）**9%**；压印暗侧 `#D6CDB9`（…）**8%**，**面积和 100**。

我的加法：56 + 27 = 83 → 83 + 9 = 92 → 92 + 8 = **100**。✓
（注意：`饱和 22.1%`、`明度 85.1%` 确实混在同一段里，探针必须先剥掉它们，否则 100 + 22.1 + 85.1 立刻爆表。）

**S26**（`prototypes/_specs/S26.md`，字段 3）：

> 背景 `#D3D1CA` 占 **44%**；主色 `#485270` 占 **30%**（…饱和 21.7%…）；
> 强调 `#121212` 占 **14%**（L 7%）；辅助 `#C8341F` 占 **12%**。**面积和 100**。

我的加法：44 + 30 = 74 → 74 + 14 = 88 → 88 + 12 = **100**。✓

**三份都是真的 100。** 探针没有在这三案上撒谎。

#### 探针是不是靠「丢掉解析失败的色」凑出来的？

我把 `areas()` 的每一个丢弃动作都打印出来对过原文。三案的丢弃项：

| 案 | 丢弃内容 | 类型 | 该丢吗 |
|---|---|---|---|
| S02 | `#B8860B` 38%（第二次出现） | 重复 hex | 该丢（那是明度不是面积） |
| S02 | `#111111`（无 %） | 无面积 | 该丢 |
| S02 | `#8B5CF6`/`#22D3EE`/`#C9A227` | 否定语境 | 该丢（「反的是」） |
| S13 | `#6366F1` 6% | 否定语境 | 该丢（6% 是「亮度差不超过 6%」） |
| S13 | `#A8843C`、`#111111` | 否定语境 | 该丢 |
| S26 | `#3B82F6`（无 %） | 无面积 | 该丢 |
| S26 | `#121212`/`#485270` 重复、`#FFFFFF` 无 % | 重复/无面积 | 该丢 |

**没有任何一条真面积声明被丢掉。** 如果丢了一条真的，和就不可能是精确的 100。
所以「靠丢色凑 100」这个作弊假设，**在这三案上不成立**。

#### 但 30/30 这个数字的证据力，远低于它看起来的样子

三点，按杀伤力排序：

**（a）它核的是「规格自己会不会加法」，不是「原型符不符合规格」。**
30 份规格里有 **29 份**字面写着「面积和 100」（只有 S11 没写这句，但它 44+38+13+5 也确实是 100）。
也就是说探针做的是：读一句「面积和 100」，再自己加一遍，得到 100，宣布通过。
这在数学上没错，但**它检验的对象是规格作者的算术，不是 CSS**。放在「P3 规格一致性」的标题下，
读者会以为是「原型的配色面积符合规格」，那是另一件事。

**（b）真正碰 CSS 的只有那 10 案。**
报告 §1 的笑脸「10 一致 / 0 不一致」我复核过，是真的：这 10 案的 CSS 头注释里 hex 与规格 **完全交叠（3～4 个全中）**，百分比也对得上，
不存在「零交叠却判一致」的漏洞。但**覆盖只有 10/30**，剩下 20 案 CSS 里根本没有面积注释，
所以「原型面积符合规格」这件事，**有 20 案从来没被检验过**。

**（c）判据的容差放走了 0.4 的错。**
`LEAD-p3-areas.mjs:91` 用 `Math.abs(sum-100) < 0.51`。我把 S02 的 4% 改成 4.4%，
合计 100.4，**判据照样打 ✓**。对手写规格这不是大问题，但要知道它不是「精确等于 100」。

#### 探针有没有真本事？有

我做了变异测试（`deliverables/73-verify/_p3out/area-mutation.mjs`）：

| 变异 | 探针应报 | 实报 |
|---|---|---|
| 58% → 60% | 102 | **102** ✓ |
| 58% → 55% | 97 | **97** ✓ |
| 删掉 4% 那个色 | 96 | **96** ✓ |
| 加第 5 色 7% | 107 | **107** ✓ |
| 4% → 4.4% | 100.4 | 100.4，判 ✓（漏检） |

所以它**不是只会点头的探针**，四类真错全部抓到。这一点报告没吹，值得补一句。

#### 三轮修 bug 是不是过拟合？

我做了消融（`_p3out/area-ablation.mjs`），三个修复各自都在承重：

```
全部修复开启      30/30
去掉去重          27/30   S05=144.0  S10=111.0  S23=108.0
去掉否定语境      27/30   S13=106.0  S16=126.0  S19=124.0
去掉 HSL 剥离     29/30   S26=121.7
三个全关          21/30
```

三个修复**都对应真实的解析歧义**，不是拿答案倒推参数。报告 §1 那张「v1→v2→v3」表格是诚实的。

**但去重规则是脆弱巧合。** `LEAD-p3-areas.mjs:72` 的 `if (seen.has(H)) continue` 意味着「同一 hex 只认第一次」。
它能work，纯粹因为**这 30 份规格的面积声明恰好都写在最前面**，后面再提这个 hex 都是在说明度/对比度。
我用脚本扫了全 30 案，只有 2 例「同一 hex 出现两个不同数值」（S05 的 `#4FA83D` 18%/44%、S10 的 `#F2EFE8` 58%/11%），
两例都是「先面积、后明度」，取首值正确。**这是运气，不是规则。**
如果哪天规格把面积写在句末，这条规则会静默给出错答案，而且**不会报错**。

**本节裁定：** 算术 30/30 **成立**；「30/30 通过」这个**表述**高估了证据力，必须改写为
「规格面积和自洽 30/30；其中仅 10 案可与 CSS 注释对照，10/10 一致；另 20 案未检验原型」。

### 2.3 第 3 条：攻击 S08 断点结论 —— **报告错了**

这是本次验收最重要的发现。**S08 不是偏差，报告的核心结论是假阳性。**

#### 规格原文（`prototypes/_specs/S08.md:25`，字段 5 末段）

> ≥1440px 六块板全显并保留右侧 220px 的工艺参数栏；1024–1439px 折为四块板、层间距压到 16px、
> 参数栏并入底部；**<768px 等距轴转为垂直堆叠**；层叠机制完整保留……

**先记一笔：S08 的字段 5 只有三个区间，没有 768–1023 这一档。**
报告 §2 第 89 行写「规格是一个互斥的区间划分：`<768` / `768–1023` / `1024–1439` / `≥1440`」——
**这四个区间里，第二个是报告自己加的，规格里不存在。** 后面「641–767 落在规格没有定义的区域」整段推论，
建立在这个虚构区间上。

#### CSS 实际（`prototypes/S08-amber-overprint-lightbox/style.css`）

```
260: @media (min-width: 1024px) and (max-width: 1439px) { … 隐藏 layer4/5，--step-y:16px }
267: @media (max-width: 640px)  { … .states 改列表、表格隐藏第 4/5 列 }
277: @media (max-width: 1023px) { … }
```

`768` 出现 0 次 —— **这一句报告说的是真的**。但「768 没出现」≠「<768 的行为没实现」。
关键在 277 行那个块里（`style.css:277-291`）：

```css
@media (max-width: 1023px) {
  .two-col { grid-template-columns: minmax(0, 1fr); }
  .iso-stage { height: auto; perspective: none; }
  .iso-plane { position: static; }
  .plate {
    position: static; width: auto; height: 54px; margin: 0 0 var(--thick);
    transform: none; animation: none;
  }
  …
}
```

`position` 回到文档流 + `transform: none` + `perspective: none` —— **这就是「等距轴转为垂直堆叠」**，
而且是逐条对应：绝对定位取消 → 回到文档流 → 纵向排列。
`--thick` 未被覆盖，`min(10px, 6px + var(--l) * 1px)` 仍在（`style.css:177`），
所以规格要求的「侧壁面厚度仍按层号从 6px 递增到 10px」也保住了。

#### 我不信推理，我去渲染了

用系统 Chrome 无头加载 `style.css`，量 `.plate` 的计算样式（脚本见 `_p3out` 同目录的实测记录）：

| 视口宽 | position | transform | 高度 | 是否垂直堆叠 |
|---|---|---|---|---|
| 500 | relative | none | 54px | **是** |
| 624 | relative | none | 54px | **是** |
| 684 | relative | none | 54px | **是** |
| **744（=641–767 区间）** | relative | none | 54px | **是** |
| 868 | relative | none | 54px | **是** |
| 1008 | relative | none | 54px | **是** |
| 1024 | absolute | none | 300px | 否（等距横向） |

**641–767px 区间实际是垂直堆叠的，不是报告说的「仍是等距横向布局」。**

报告 §2 第 84 行那句「它会沿用 1023px 的规则，即仍是等距横向布局，而不是叠加」——
**把 1023px 规则的内容整个说反了。** 那条规则正是叠加的实现。

#### 那 S08 到底有没有偏差？

按行为看，**没有**：

- `<768px 垂直堆叠` → CSS 在 ≤1023 就叠了，**是超集，覆盖 641–767，满足要求**
- `1024–1439 四块板` → `style.css:263` 隐藏 layer4/5，✓
- `≥1440 六块板` → 无隐藏规则，✓

「CSS 叠得比规格要求更早」不是不符合规格。规格说的是「<768 必须叠」，CSS 说「<1024 就叠」，
**逻辑蕴含成立**。

唯一能算「不一致」的，是「768–1023 在规格里没定义、CSS 却叠了」——但**规格没规定的地方，实现填上不是偏差**，
这是定义域外，不是冲突。

**本节裁定：S08 假阳性。报告唯一那条「确凿发现」，是探针把「阈值字面量缺失」当成「行为缺失」。**
`LEAD-p3-breakpoints2.mjs:64` 的判据是 `!cbp.some(c => Math.abs(c - b) <= 1)`，只比对**数字**，
完全不看**该数字背后的规则是否已经把行为实现了**。这是方法论错误，不是手误。

### 2.4 第 4 条：攻击「21/23」与断点正则

#### 真实是 22/23 还是 21/23？—— 都不是，是 28/30

`LEAD-p3-breakpoints2.mjs:69`：

```js
console.log(`\n═══ 汇总: ${dirs.length - bad.length - 7}/${dirs.length - 7} 全覆盖，${bad.length} 案有缺 ═══`);
```

那个 `- 7` 是**硬编码**。它显然是从 `LEAD-p3-cols2.mjs` 的「规格无栏数 7」抄过来的，
但它出现在**断点**探针里，而断点探针的适用范围完全不同。

我实测：**30 个案全部都有断点断言，一个都不少。**

```
有断点断言的案数 = 30
全覆盖 = 28   有缺 = 2
报告写的分母 = dirs.length - 7 = 23   ← 与实测案数 30 不符
```

所以真实数字是 **28/30**，不是 21/23。报告把探针打印的 `21/23` 原样搬进了交付物，
没有检查这个数是不是从数据里长出来的。**这是「复算命令能跑通」和「复算结果可信」之间的差别。**

顺带：`LEAD-p3-bp-base-lw.mjs` 同一个仓库里做同一件事，输出的是 **26/30**（它用另一套更窄的正则，
漏了 `≥`）。同一份数据，两个探针给 26/30 和 21/23，报告只引用了后者，也没解释差异。这本身是个红旗。

#### 那个正则会不会误抓非断点？

正则：`/[<≤>≥]\s*=?\s*(\d{3,4})\s*px/g`（`LEAD-p3-breakpoints2.mjs:24`）

**会。而且有系统性风险。** 我把全 30 份规格里所有命中都打出来人工分类（137 处原始命中）：

真正的误抓 **只有 S13 一例**，但它的性质很严重：

```
S13  字段 8：全站不得出现圆角胶囊按钮（`border-radius` ≥ 100px 或等价写法）
```

**这不是断点，是圆角上限。**

它是怎么进来的？`LEAD-p3-breakpoints2.mjs:22`：

```js
const seg = md.slice(i, i + 1800);   // i = indexOf('布局与网格')
```

从字段 5 开头**固定切 1800 字符**，而不是切到字段 6 为止。我量了 S13：字段 5 只有 **375** 字符，
`≥ 100px` 在字段 5 起点之后 **1756** 字符处 —— 正好落在 1800 的窗口里。

**这是一个对全部 30 案都成立的越界风险**，只是 S13 运气不好被撞上。
我实测其它案没被撞（字段 5 最长也没超 1800，所以尾部没截断；但窗口向**后**溢出到字段 6/7/8 是普遍现象）。

**报告的归因是错的，而且错得可以证明：**

报告 §2 第 64 行写「S13 的 `≥100`（实为 `100ms` 时长）」。
`100ms` 在 S13 里确实存在 1 处（字段 7「按钮按下改为 0.8px 瞬时位移配 100ms 亮度变化」）。
**但那个正则要求 `100` 后面紧跟 `px`，`100ms` 永远匹配不上。**
物理上不可能。真实来源就是上面那个 `border-radius ≥ 100px`。

结论「S13 是探针误判」对，**理由是编的**。这种「结论对、归因错」比结论错更危险——
它会让人以为修了 `100ms` 相关的东西就好了，而真正的 bug（窗口越界）原封不动。

#### 报告和它自己的探针互相矛盾

`LEAD-p3-breakpoints2.mjs:78-79` 对 S13 打印的是：

```
判定: **真实偏差**
```

（因为 `hasEquivalent` 只查 ±1px，100 找不到等价物。）

报告 §2 说 S13 是「探针误判，非偏差」。
**报告在正文里推翻了探针的输出，却没有回去修探针。**
所以今天任何人按 §7 跑复算命令，屏幕上会打出与报告相反的话。

**本节裁定：分母错（21/23 应为 28/30）；正则确有系统性误抓风险（窗口越界，
不只 S13 危险）；报告的 S13 归因不成立；报告与探针输出自相矛盾且未修。**

### 2.5 第 5 条：攻击「栏数不可核」的诚实性

报告承认探针不可靠 —— **这个态度是对的，是全文最值钱的一段。**
但它给的那个数「**11 条机器确认成立**」不成立。我抽了 3 个 FULL 手工核：

#### 抽检 1：S04 `spec=[4,6,8,12]` → FULL

`prototypes/_specs/S04.md` 字段 5：「底下埋 12 列隐网格（栏宽 88px、栏沟 0），每块纸按固定种子**跨 2 至 6 栏**…
≥1440px … 贴墙区占 **8 栏**；900–1439px … 最大跨栏降到 **4 栏**；<900px … 纸块跨满 **12 栏**」

CSS（`style.css:78`）：`grid-template-columns: repeat(12, minmax(0, 1fr))`。

**这条成立。** 12 列网格真实存在，且规格的 4/6/8/12 是「跨栏数」不是「轨道数」。

#### 抽检 2：S16 `spec=[9,12]` → FULL（★ 零直接命中）

`prototypes/_specs/S16.md` 字段 5 原文关键句：

> 块宽在 **12 栏投影上取 4 / 6 / 7 / 9 栏四个值**

CSS 全部轨道（`style.css`）只有 `[1,2,3]`，**没有 12 栏投影，也没有 4/6/7/9**。

探针为什么判 FULL？因为它只抽到 `[9,12]` —— 写成「4 / 6 / 7 / 9 栏」时，
**只有最后一个数字前面紧邻「栏」字，前三个被 `(\d+)\s*栏` 整体漏掉**。
然后 `explain()` 用 `9 % 3 === 0`、`12 % 3 === 0` 判「都能解释」。

**这条是假阳性。** 探针漏抽了 3 个数值，再用一条过宽的除法规则把剩下 2 个洗白。

#### 抽检 3：S10 `spec=[3,5]` → FULL

`prototypes/_specs/S10.md` 字段 5：「**五栏**，栏宽比 6:7:9:8:5（第 **3** 栏最宽放主表、第 **5** 栏最窄放注释）」

抽到的 `[3,5]` 根本不是栏数，是「**第 3 栏**」「**第 5 栏**」的序数！
真正的「五栏」因为写成中文数字「五」，`(\d+)\s*栏` 抓不到。

CSS 是真五栏：`grid-template-columns: 6fr 7fr 9fr 8fr 5fr`（`style.css:151` 等 3 处）。

**判定 FULL 的结果碰巧是对的，但推理过程完全是噪音** —— 它匹配的是序数，却拿五栏的实现去印证。

#### `explain()` 这个判据本身有多弱

`LEAD-p3-cols2.mjs:48-52`：

```js
function explain(spec, tracks) {
  if (tracks.has(spec)) return 'direct';
  for (const t of tracks) if (t > 1 && spec % t === 0) return `÷${t}`;
  return null;
}
```

我测了它面对随机错误时的检出能力：拿 1..16 每个整数去问「能不能被这套轨道解释」：

```
平均: 10.3/16 个任意整数都能被"解释"
→ 该判据对随机错误的检出率仅 35%
```

**换句话说，随便编一个数，有 65% 的概率被判「能解释」。**
S01/S05/S06/S09/S10/S14/S15/S16/S20/S21/S22/S23/S24/S25/S26/S30 都是 12/16，
S07/S10 甚至 13/16。这样的判据给出的「11 条确认」，**不能作为「确认」写进交付物**。

#### 「118 条栏数断言」这个基数也偏高

`LEAD-spec-mechability.mjs:24` 用的是**全文**正则，不是字段 5：

```
"栏数"断言: 全文计 118 条, 字段5内只有 83 条 → 35 条来自非布局字段
```

而且这 83 条里，我分类后**有 27 条是「跨 N 栏 / 第 N 栏」这类跨度或位置**，不是轨道总数：

```
像"跨 N 栏 / 占 N 栏 / 第 N 栏"（跨度或位置）= 27
其余（更像轨道总数或分区数）                    = 56
```

所以「118 条栏数断言」实际可核的轨道数断言，量级是 **56 条上下**，不是 118。

**本节裁定：报告的诚实态度 ✓，但「11 条确认成立」这个数 ❌。抽 3 个 FULL，
1 个真成立（S04）、1 个假阳性（S16）、1 个推理无效但结果碰巧对（S10）。**
报告应该写的是「FULL 判定不可信，11 条里我人工只认下部分」，而不是给一个 11。

### 2.8 第 8 条：S08 那个偏差要不要修

**前提就不成立——不该修，因为没有偏差。**

但这个问题值得正面回答，因为它暴露了报告的风险：

#### 如果按报告去改（`640px` → `767px`），会发生什么

1. **改错了对象。** 报告以为 `<768 转垂直堆叠` 没实现，实际 `style.css:277` 的 `≤1023` 已经实现了。
   改 `640→767` 不会「补上」任何东西，只会把 **267 行那个块**（状态区改列表、表格隐藏第 4/5 列）
   的适用范围从 ≤640 扩到 ≤767。
2. **风险是真实的。** 768 是 `report.json` 里**已经截图取证过**的视口（1440/768/390 三档）。
   把 640 改成 767 后，768 恰好不受影响（767 < 768），**但 641–767 这一段会多出一堆样式，
   而这一段没有任何截图基线**。等于在一个没取证过的区间做无谓改动。
3. **会污染已通过的闸门。** S08 现有 **2 条 FAIL**：
   ```
   palette-terracotta @1440  button #c46a1f
   font-count       @1440    4 typefaces
   ```
   这两条和断点无关，但改动 `style.css` 会让 `report.json` 失效、需要重跑闸门，
   而这轮工作**没有义务**去动一个已经取证过的案。为了一个不存在的偏差去扰动 2 条已知 FAIL 的案，纯亏。

#### 正确做法

**不修 CSS。在报告里把这条降级为「探针局限」，不是「实现偏差」。**

如果一定要留痕，记录方式应该是：

> S08 字段 5 只声明 `<768` / `1024–1439` / `≥1440` 三档，`768–1023` 未定义。
> CSS 将垂直堆叠实现为 `@media (max-width: 1023px)`（`style.css:277-291`），
> 覆盖并超出规格要求（641–767 亦为堆叠，实测确认）。**判为符合。**
> 规格的 `<768` 与实现的 `≤1023` 之间是「实现更严格」，不是偏差。
> 若将来要把 768–1023 单独定义成横向布局，那才是需要动 CSS 的需求变更，不属于本轮。

**这才是「768 在 CSS 里出现 0 次」这句话应有的结论：字面量没有，但行为有，且更宽。**
