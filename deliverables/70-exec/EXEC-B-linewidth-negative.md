## 1. 任务 1：复核 Lead 的线宽数字

### 1.1 结论先说

| 判据 | Lead 报的 | 我实测的 | 是否一致 |
|---|---|---|---|
| 实际用到「声称之外」的线宽 | 15/30 | **19/30**（基线口径） | ❌ 差 4 案 |
| 声称了但页面完全没用到 | 12/30 | 11/30（基线口径） | ⚠️ 差 1 案 |

**差值不是"谁错了"，而是两版探针各有一个方向相反的缺陷。** 下面逐条给证据。

### 1.2 我的探针与 Lead 的判据差异（已隔离验证）

我用 `probes-b/B-criteria-4bags.mjs` 把四套判据放进**同一个页面会话**里同时跑
（保证输入完全一致），结论：

| 差异点 | Lead 探针 | 我的探针 | 影响 |
|---|---|---|---|
| 零尺寸跳过 | `width===0 \|\| height===0`（OR） | `width===0 && height===0`（AND） | **我多出 3 案的值** |
| `opacity:0` | 不排除 | 我第一版排除 | **我少算 1 案** |
| SVG 模板几何 | 不区分 | 我第一版全排除 | **我少算 4 案** |
| `<use>` 实例化 | 不处理 | 需要专门处理 | 双向 |

#### 缺陷一：Lead 的 OR 判据丢掉了真实的细线（我得 19 而非 15）

Lead 的探针写的是：

```js
if (cs.display==='none' || cs.visibility==='hidden' || rect.width===0 || rect.height===0) return;
```

一条水平 `<line x1=0 y1=1 x2=108 y2=1>` 的 `getBoundingClientRect().height` **就是 0**，
但它是页面上真实画出来的 1px/2px 分隔线。OR 判据把它整根丢掉。

证据（`probes-b/criteria-4bags.json`，只在我这边多出的值）：

| 案 | 值 | 宿主 | 说明 |
|---|---|---|---|
| S03 | 1.5 | `<line>` 17 个 | 80×0，JS 画的刻度主格线 |
| S25 | 2 | `<line>` 8 个 | 108×0，装订导引线（`.leader`） |
| S29 | 0.4 | `<path>` 1 个 | 1059×0，斜线诊断图 |

这 3 个值都是真实的、有宽度的水平/斜向线条，**只是高度为 0**。

#### 缺陷二：我第一版把 `<symbol>` 里的几何全排除了（我曾少算 4 案）

S19 的 `0.4`/`0.8` 蚀刻线写在 `<defs><symbol id="ec">` 里，被 **26 个 `<use href="#ef">`** 引用。
我第一版看到"在 symbol 里"就整条排除，于是 S19 被误报成"0.4 和 0.8 是假声称"。
修正方式：**以 `<use>` 元素为宿主**，顺着 `href` 找到被引用元素，把它的 computed
`stroke-width` 记到这条 use 上。这样"被引用的 symbol"会计数、"纯备用图标库"不计数。

#### 缺陷三：`opacity:0` 不等于"没画"（我少算 1 案）

S26 的 `.foot__grid` 有 `border-top: 8px solid`，但它是**滚动揭示元素**，
首屏 computed `opacity` 就是 0。按 opacity 排除会把 8px 整条抹掉。
它滚到视口就会显示，是真实的设计分级。修正：只看 `display`/`visibility`。

### 1.4 ⚠️ 一个 Lead 没提、但改变了整个判断的测量事实

**Chrome 在 dpr=1 下会把 `border-width` 量化成 `max(1, floor(w))`，但不量化 `stroke-width`。**

探针 `probes-b/B-border-quantization.mjs`，用 30 个代表性的 px 值逐个实测：

| 作者写的 | `border-top-width` 实测 | `stroke-width` 实测 |
|---|---|---|
| 0.2 / 0.35 / 0.4 / 0.5 / 0.6 / 0.8 | **全部 1px** | 原值不变 |
| 1.1 / 1.2 / 1.25 / 1.4 / 1.5 / 1.6 / 1.7 | **全部 1px** | 原值不变 |
| 2.4 / 2.5 | **2px** | 原值不变 |
| 3.2 / 3.5 / 3.6 | **3px** | 原值不变 |
| 5.5 | **5px** | 原值不变 |
| 14.5 | **14px** | 原值不变 |

**30 档里 20 档被 border 量化，stroke 0 档。**

注意**不是 `round()`**：`round(1.5)=2` 但实测 `1px`；`round(3.5)=4` 但实测 `3px`。
唯一吻合的模型是 `max(1, floor(w))`。

**这条对验收标准的影响**：任务书写「声称值必须能在页面上真实找到（±0.05px）」。
对 stroke 成立；对 border **物理上不可能成立** —— 一条 `border: 1.25px` 在这台机器上
永远只能量到 `1px`。所以我在验收里并列两个口径（§4.1），并明确指出哪些"不达标"
是量化造成的、不是抽取错误。

Lead 报告写：「这些是亚像素线在设备像素比缩放后的实测值，不是设计分级」。
**实测证明它们是作者在源码里手写的设计值**：

|---|---|---|---|

| 3.6px | S09 | `style.css:402` `.ico path{stroke-width:3.6}` | **手写** |
| 1.25px | S08/S10/S11/S14/S18/S21 | HTML 属性或 CSS 裸数字 | **手写**（6 案一致） |

全库源码里**字面写着**的线宽值共 **29 种**（比渲染出的 22 种还多），
所以"渲染产物"这个假设解释不了它们。**它们是设计决策，只是不像常规的整数分级。**

## 2. 任务 1：`lineWidths` 该抽什么

### 2.1 它扫了哪些来源

`clean-dna.mjs` 的 `lineWidthVerdict()`（进场时在 452 行，A 重写后在 584 行）：

| 来源 | 进场时 | A 重写后 | 我补充后 |
|---|---|---|---|
| CSS `border` / `border-width` / `border-top` 等 | ✅ | ✅ | ✅ |
| CSS `outline` / `outline-width` | ✅ | ✅ | ✅ |
| CSS `stroke-width`（含 SVG 裸数字） | ✅ | ✅ | ✅ |
| `var()` 展开 | ✅ | ✅ | ✅ |
| `calc(Npx * M)` | ✅ | ✅ | ✅ |
| `@media` 按 1440 视口过滤 | ❌ | ✅ | ✅ |
| HTML `stroke-width="N"` 属性 | ❌ | ✅ | ✅ |
| `<pattern>/<mask>` 等纹理容器内的 stroke | ❌ | ❌ | ✅（我加） |
| 脚本运行时 `setAttribute("stroke-width", N)` | ❌ | ❌ | ✅（我加） |
| 交互态（`:hover`/`:focus-visible`） | 混入 | 混入 | 排除→**A 改为保留** |

### 2.2 为什么会出现 3.6px

**不是** `getComputedStyle` 的亚像素取整。S09 的 `style.css:402` 字面写着
`stroke-width: 3.6`，S24 的 `index.html:347` 字面写着 `stroke-width="3.2"`。
它们是作者的原始设计值，被 `getComputedStyle` **忠实**读出。

真正的"脏值"只有一类：**border 的量化**（§1.4）。作者写 1.25px 的 border，
`getComputedStyle` 返回 1px —— 这是 Chrome 的渲染行为，不是抽取缺陷。

### 2.3 上限几级？为什么 S13 收进 7 级

**进场时没有上限**。但有"按 0.5px 粒度去重"的逻辑（`Math.abs(c-w) < 0.5` 就合并），
**除了 `< 1px` 的细描边不受此限**（保留全部）。所以：

- S13 的 1、2、3、5.5、7、9、14.5 —— 两两间距都 ≥ 0.5，一个都没被合并 → 7 级
- S15 的 0.5、0.8、1、1.2、1.36、1.4、1.7、2、3 —— 9 级，合并后 5 级
- S19 的 0.4、0.8 —— 都在 1px 以下，**不合并**（注释写明：这是蚀刻分层的签名）

A 重写后**取消了 0.5px 合并**（注释理由：合并等于替作者改设计），
改由 `@media` 过滤 + HTML 属性补全来控制级数。实测新分布：

| 级数 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| 案数 | 0 | 5 | 8 | 9 | 2 | 2 | 3 | 1 |

### 2.4 S25 与 S13 的根因（Lead 点名的两个"最严重"）

**S25**：旧声称「线宽只用 3px」，页面实测 `1×5 1.2×2 2×8`，一次 3px 都没用。
根因：**那个 3px 是 `:focus-visible{outline:3px solid var(--spot-b)}`（style.css:58）**，
只在键盘聚焦时出现。页面真实的线是 HTML 的 `stroke-width="1.2"`（装订线）
与 `.leader` 的 2px（引线）。

**S13**：旧声称 7 级（1、2、3、5.5、7、9、14.5），实际只有 5 种（1、1.5、3、5、9）。
根因两条：
- `2px` 来自 `:focus-visible{outline:2px}` —— 交互态
- `7px` 来自 `@media (max-width: 1023px){ .clause__head{border-top-width:7px} }` —— 1440 下不生效
- `14.5px` 来自 `.clause:hover .clause__head` —— 交互态
- 漏掉的 `1.5px` 来自 HTML 属性（`stroke-width="1.5"`，6 处 icon）—— 旧代码不读 HTML
- 漏掉的 `5px` 是 `5.5px` 的 border 量化

**Lead 对这两案的定性完全正确。** 我给的是根因级解释。

### 2.5 最佳修法：我的判断与理由

任务书问：「只收干净值 + 按频次取前 N 级」还是「忠实记录全部实测值」？

**我的判断：两个都不对。真正该修的是"层级口径"，不是"值域清洗"。**

理由（每条都有实测支撑）：

1. **"只收干净值"会破坏 7/30 案的风格签名。**
   S19 的 0.4/0.8 是蚀刻分层的全部依据（26 个 use 引用）；S09 的 3.5/3.6 是外描边与
   图标的差分；S24 的 0.4/0.6/0.8 是三级蚀刻。按"0.5 的倍数"筛，这三个签名全部消失。
   这正是旧代码（0.5px 合并）干过的事，注释里记着代价。

2. **"按频次取前 N 级"会把签名级当噪声删掉。**
   S19 的 0.4px 只出现 26 次，而 1px 出现 120 次。按频次截断，0.4 会被 1px 挤掉 ——
   但它才是这个案"是什么"的关键。频次反映的是使用面积，不是设计重要性。

3. **"忠实记录全部实测值"会把渲染假象写进施工图。**
   这正是当前缺陷：`:focus-visible` 的 outline、窄屏 `@media` 的值、
   纹理 pattern 里的 0.2px，全都混进了"线宽只用这几级"。

**所以正确的修法是三层：**

| 层 | 修法 | 实现 |
|---|---|---|
| ① 语境 | 只收「桌面 1440 成立 + 非交互态 + 非纹理」的声明 | A 做了 @media 与 HTML；我做了纹理、JS 运行时；交互态见 §2.6 |
| ② 来源 | 补全 HTML 属性与 JS 运行时生成的值 | A 做了 HTML；我做了 JS |
| ③ 值域 | **不做清洗**。作者写 3.6 就写 3.6 | A 已取消 0.5px 合并 |

对"1.1px 对 AI 毫无意义"这个论点，我的回应是：**它的无意义来自它是 stroke 值而
不是分级值，不来自小数**。S19 的 0.4/0.8 同样是小数，但它们有意义 —— 因为它们是
**两级、且承担分层功能**。判断标准应该是"这个值是否承担设计功能"，不是"它是不是整数"。

真实的无意义值只有一类：**border 量化后的伪值**。应付它的办法不是清洗数据，
而是**在验收标准里承认量化**（§4.1）。

## 3. 任务 2：负向指令全量清点

### 3.1 方法

`probes-b/B-negative-inventory.mjs`。不数"有多少个'不要'"，而是回答两个可操作问题：
① 有多少负向句式？② 其中有多少**点名了具体值**（hex / 字体名 / 数值 / 具名组件）？

只有第 ② 类才有"命名即加权"风险。分段按提示词的固定骨架切

### 3.3 改写方案（原则来自证据，不是偏好）

依据 arXiv 2601.08070 "Semantic Gravity Wells"（n=40,000，含 activation patching 因果干预）：
**87.5% 的违规发生在「明确点名被禁词」时**。机制是"命名即加权" —— 负面指令里的名词
照样进入注意力分配，只有极性标记被更弱的权重表达。

三条原则：

1. **「不要 X」→「用 Y」**（正面唯一解）
2. **让被禁项的名字彻底不出现**（连提都不提）
3. **信息量不减**：原来靠"禁止"排除的设计空间，改由"指定"收窄到同一处

### 3.4 实现（全部在 `prompt-copy.js` 模板层，不逐案硬改 30 条）

| 位置 | 改法 |
|---|---|
| 防退化 8 条 | 全部重写为正面处方。①「色彩面积按 palette 明度顺序分配，渐变只用相邻两级」；②「层级只用『直角边界 + 本案阴影』这一套词汇」；③「首屏按本案阅读起点对齐，全屏只留一个主行动」；④「并列条目用不等栏宽与不同内部结构」；⑤「图形一律用本案线宽级线条画」；⑥「所有底色不透明，浮起用位移与边界差」；⑦「可读性只由底色与字色的明度差承担」；⑧「动效只用机制句里那一个动作」 |
| 字体黑名单 | 「不要用 Playfair Display、Inter、Roboto」→「不要用 **上面两条链之外的** 字体」（**宾语从族名换成类别**） |
| 视觉硬约束抬头 | 「不得改色、不得换字体」→「配色与字体照此固定」 |
| 阴影行 | 「不许用柔和外投影制造'浮起卡片'」→ 删除（`d.shadow` 已是正面指定） |
| 线宽行 | 「不要自创新值」→「全站线条都从这几级里取」 |
| 首屏轮播 | 「首屏不要轮播图」→「首屏只用本案方式摆出的静态内容，一屏内所有内容同时可见」 |
| 图片位 | 「不许用 1px 图或纯色块顶替」→「每个位都要占出真实可见的面积与合适比例」 |
| 验收第 3 问 | 「有没有圆角、影子跑到纸外、发光字、表情图标、两个主按钮？」→「上面 8 条正面要求与第 3–5 条硬约束，是不是每一条都看得见？」 |
| 输出要求 | 「不许用 1px 图…」→「带真实面积与比例」；「不要解释…只给代码」→「回复里只放这一份代码」 |
| `d.risk` 导语 | 砍掉「最易滑向「复古博物插画墙」：一旦…」整段（点名退化风格），只保留"规避动作"起的部分 |
