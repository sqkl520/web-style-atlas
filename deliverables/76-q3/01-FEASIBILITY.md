# Q3 第一项可行性判定：SPEC 七行结构化段

> 2026-11-11　试点结论：**CSS 语义抽取不可靠，按计划应退回「机制句 + 出处」的轻量版**

计划原文（`00-MASTER-PLAN.md` Q3 第一条）：

> **SPEC 七行结构化段**替代单句机制句（比例／密度／字阶／节奏／图像／交互／构造），每行可回溯到 CSS。
> ⚠️ 这是全计划最大的一块未估准工作……Q3 的做法是 **3 案试点**：若 CSS 抽取可靠则铺开，
> 不可靠则退回到「机制句 + 出处」的轻量版。

我做了试点，结论是**不可靠**。下面是证据。

---

## 一、规模确认（35 案实测，剥注释后）

| 声明类型 | 全库条数 | 单案中位 |
|---|---|---|
| `font-size` | **1,300** | 37 |
| `line-height` | **669** | 19 |
| `gap` | **570** | 17 |
| `grid-template-columns` | **394** | 10 |
| `letter-spacing` | 207 | 5 |
| `@media` | 184 | 5 |

计划里 Q1 时记的是 30 案的 179 / 373 / 618 / 437 —— 现在 35 案是 184 / 394 / 669 / 570。
**规模本身不是障碍**（我写的解析器 60 行就扫完全部 35 案、平均 332 条声明/案），
障碍在语义。

## 二、解析器能做到什么（这部分是成功的）

写了一个逐字符状态机，能正确产出**每条声明 + 行号 + 所处 media 条件**：

```
L131 [base]                          .sheet → minmax(210px, 3fr) 16px 9fr
L304 [(min-width: 1440px)]           .sheet → 3fr 16px 9fr
L309 [(min-width: 1024px) and (max-width: 1439px)] .sheet → 1fr
L325 [(max-width: 1023px)]           .sheet → 1fr
```

行号、media 上下文、选择器都准确。**「每行可回溯到 CSS」这一半是成立的。**

## 三、失败的是「合成句子」这一半

### 3.1 同一个答案有多个候选，选错就全错

S23 的 `.masthead` 是 `5fr 7fr`，而它的主内容区 `.wall` 是
`repeat(36, minmax(0, 1fr)) 96px`。**「主导轨」到底是哪一个？**

- 按「轨道数最多」选 → 选到 `.wall`（36 轨），合出毫无意义的句子；
- 按「轨道数最少」选 → 选到 `.states`（1fr 1fr），那是两张状态卡的网格；
- 规格字段 5 真正讲的是别的东西（S23 的字段 5 甚至没有可抽取的"栏"这一层）。

我试过三种选取启发式（最多轨道 / 最多文字量 / 最大面积），**没有一个在 35 案上都对**。

### 3.2 轨道数 ≠ 栏数

| 案 | CSS 轨道 | 规格原文说的 | 差在哪 |
|---|---|---|---|
| S25 | `.contents: 3fr 7fr` | 「左半 3 栏、右半 7 栏」 | 3fr/7fr 是**两半的宽度比**，不是栏数。真实栏数是 `column-count` |
| S17 | `minmax(210px, 3fr) 16px 9fr` | 「主联占 4–12 栏，存根联占 1–3 栏」 | 3 条轨道对应 12 栏栅格里的两个区域 |
| S23 | `5fr 7fr` | 无对应描述 | 报头两段的宽度比 |

**这是最致命的一条**：把 `3fr 7fr` 合成「比例 3:7」并告诉 AI「照这个排」，AI 会排成
30%/70% 的两块 —— 而那个案子的真实结构是「左半 3 栏 + 右半 7 栏」，共 10 栏。
**数对了，意思错了。**

### 3.3 混合写法无法压成一行

S17 的 `minmax(210px, 3fr) 16px 9fr` 里，第一轨同时有「最小 210px」和「比例 3」两层约束。
只写「3:9」会丢掉最小宽（窄屏下左侧不会小于 210px 这个事实），
只写「210px 起、比例 3:9」又长到不适合放进一行。

全库这类混合写法只有 1 案（S17），但它说明**没有一种统一句式能覆盖所有情况**。

### 3.4 单位不统一

35 案里的主导轨写法分布：

| 写法 | 案数 | 例子 |
|---|---|---|
| 纯 fr 比例 | 32 | `5fr 4fr 4fr 3fr` |
| 混合最小宽 | 1 | `minmax(210px, 3fr) 16px 9fr` |
| 百分比 | 1 | `12% 54% 34%` |
| 自适应（无固定比例） | 1 | `repeat(auto-fit, minmax(240px, 1fr))` |

前四种还能处理，但**还有一批轨道是 `var(--bar)` / `var(--spine)` / `var(--fold-track)`**
—— S01 的 `5fr var(--bar) 4fr var(--bar) 4fr var(--bar) 3fr`，
真实的 4 栏要靠 `--bar: 24px` 才能算出来。要解析这个需要**求值 CSS 变量**，
那是另一个量级的工程（变量可以继承、可以在 media 里覆写、可以互相引用）。

### 3.5 我在试点中自己犯的三个错（都被后续核对抓出）

1. **`split(/\s+/)` 切碎 `minmax(0, 1fr)`** —— 括号内有空格，一切四段。
   导致 16 案被判「抽不到比例」，而它们其实都有。
2. **把 `repeat(auto-fit, …)` 当固定比例** —— 那是响应式自适应，没有固定比例可言。
3. **把 `minmax(210px, 3fr) 16px 9fr` 的 `minmax` 过滤掉** —— 它是真值，不是噪声。

三个错都在同一类地方：**用字符串启发式判断 CSS 语义**。修正一个，下一个就冒出来。
这正是计划里那句「不可靠」的具体形态。

## 四、结论与建议

### 不铺开 SPEC 七行。退回轻量版。

**轻量版 = 机制句 + 出处**，它的成本是：

- 机制句已经存在（`dna.mechanism`，35/35 有值，`check-prompts` 的
  `mech-value-not-in-source` 在守它）；
- 出处只是给它加一个 `{file, line}` 字段 —— 而**行号抽取这一半是成功的**（见第二节）。

也就是说：**我已经把「出处」这一半做出来了，缺的只是把它接进 dna。**
这正是计划给 Q3 留的退路，而退路的成本远低于正面攻。

### 具体做法

1. 保留解析器（`parse()`），用它产出 `provenance`：

```js
dna.provenance = [
  { claim: '11° 斜切楔形', file: 'style.css', line: 151 },
  { claim: '4 栏 5:4:4:3', file: 'style.css', line: 195 },
];
```

2. `claim` 怎么来：**从机制句里切分句，每个分句配一条最匹配的声明**。
   匹配判据用「分句里的数值 + 单位」去 CSS 里找同值的声明 —— 这是
   `check-prompts.mjs` 的 `mechSourceNumbers()` 已经在做的事，**复用它**。

   这条路径的好处：**不合成新句子**，只给已有的句子找出处。
   所有语义判断都由人写的机制句承担，机器只做「找同值声明」这种机械工作。

3. Q3 验收（计划原文）：「任取一份提示词，用户能点开看到每个数字的 CSS 出处。」
   轻量版**完整满足这条**——而且比七行版更诚实：
   七行版会让用户以为那些句子是从 CSS「推」出来的，
   轻量版明说「句子是人写的，出处是机器找的」。

### 如果将来还想做七行

前提是这三件事先解决，否则会重蹈覆辙：

1. **求值 CSS 变量**（至少 `:root` 里那些静态的）；
2. **区分「栅格栏数」与「Grid 轨道数」** —— 这两个概念在本仓库里被混用，
   而它们不是一回事（12 栏栅格可以有 3 条轨道）；
3. **为「主导轨是哪一个」建立显式标记**，而不是靠启发式猜 ——
   例如在 CSS 里给主布局容器加 `/* @primary */` 注释。
   手写标记虽然"不优雅"，但它把歧义消掉了；启发式永远会有一个案子猜错。
