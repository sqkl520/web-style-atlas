# Q3 第二项：「出处进剪贴板」实测结果

> 2026-11-11　轻量版（机制句 + 出处）已实现，可回溯率 **88%**

## 一、做了什么

`prototypes/_prompts/build-provenance.mjs`：给机制句里每个带单位的数值
找到它在 `style.css` 里的行号。

判据是纯机械的，**不做语义判断**：
- 机制句里出现「24px」→ 在 CSS 里找哪一行的声明出现 `24` 且该行有 `px` 单位
- 出现「11°」→ 找 `deg` 或 `°`
- 出现「32%」→ 找 `%`

为什么这不等于七行 SPEC：七行要**合成新句子**（「栏宽比 5:4:4:3」），
那需要判断「哪条 grid 是主导轨」「轨道数是不是栏数」——试点证明判不准。
出处只要回答「这个数在哪一行」，不需要理解它在说什么。

## 二、实测：88% 可回溯

```
机制句数值：共 34 个，找到出处 30 个，找不到 4 个（88%）
```

（34 个是因为只有 34 个案子的机制句里带了带单位的数，S23 等的机制句全是描述性文字。）

## 三、剩下 4 个：逐条定性，性质完全不同

这 4 个不是我定位器的缺陷，**每一个都指向一个真实情况**，而且三种性质不能混为一谈。

### ① S01「11° 切入」—— 换算了，合理

- 机制句：`一块实色多边形以 11° 切入 4 栏版心`
- CSS 第 145 行：`clip-path: polygon(42% 0, 73.6% 0, 45.6% 89.3%)`
- **CSS 存的是多边形顶点坐标，11° 是由这些坐标换算出的角度。**

这不是缺陷。机制句讲的是视觉结果（斜切多少度），CSS 存的是实现（顶点坐标）。
但**它确实不可直接回溯**——用户按 11° 去 CSS 里搜，搜不到。
所以出处的展示必须能表达这种情况：「这个数由第 145 行的几何换算而来」，
而不是「第 145 行写着 11°」。

### ② S03「四角减光 32%」—— 载体是位图，不是 CSS

- 机制句：`四角减光 32%`
- CSS 第 150 行是**注释**：`/* 四角减光：预生成位图叠层（cos⁴，中心 0、四角 32%），不是 CSS 蒙版 */`
- 生效的是 `assets/` 里的烘焙位图。

真值，但**载体不在 CSS 里**。`check-prompts.mjs` 的 `mech-value-comment-only`
（WARN）已经在覆盖这一类 —— 两边的判据是一致的。

### ③ S07「0.5px」—— 真缺陷

- 机制句：`游标 1:1 跟随指针，1px 与 0.5px 两级线宽`
- `style.css` 里 `0.5` 出现 **0 次**（grep 全空）。

**机制句写了一个实现里根本不存在的线宽。** 这是 `check-prompts` 的
`mech-value-not-in-source` 应当报 FAIL 的那一类 —— 需要确认它为什么没报
（可能是因为 0.5 出现在别的上下文里被 JS 白名单放过了）。

### ④ S08「滚动 200px 走 6px」—— 页面在向用户展示不存在的参数

- 机制句：`滚动 200px 走 6px`
- `style.css` 与 `index.html` 的**实现**里都没有 200。
- 但 `index.html:182` 有：`<dd><code>200px / 6px</code></dd>`

也就是说：**页面上有一栏「参数」明明白白写着「滚动视差 200px / 6px」，
而代码里没有这个数。** 这比 ③ 更严重——③ 是文案错了，
④ 是**页面自己展示了一个假的规格**。

## 四、结论

### 出处这条路可行，但它必须能表达四种状态

如果只做「找到 → 给行号 / 找不到 → 报错」两态，上面四种情况会被压平成
「失败」，而其中只有 ③④ 是失败，①② 是正常工作方式。

正确的数据模型：

```js
{
  claim: "24px",            // 机制句里的数
  status: "direct",         // direct | derived | media | missing
  file: "style.css",
  line: 26,
  text: "--bar: 24px;",
}
```

| status | 含义 | 例子 |
|---|---|---|
| `direct` | CSS 里直接写着这个数 | S01 的 24px → L26 |
| `derived` | 由 CSS 的其它值换算而来 | S01 的 11° → 由 L145 的多边形换算 |
| `media` | 载体是位图/字体，不在 CSS | S03 的 32% → 烘焙进 assets/ |
| `missing` | **实现里没有这个数** | S07 的 0.5px、S08 的 200px |

`missing` 是唯一应该报错的，而且它恰好是 Q3 最有价值的产出：
**它能自动找出「提示词教用户做的事，原型自己没做」这类缺陷。**

### 下一步

1. 把 `status` 四态接进 `build-provenance.mjs`（`derived` 靠「该行有几何声明但无此数」推断，
   `media` 靠 `assets/` 里有没有对应文件 + CSS 注释命中）；
2. ③④ 两条单独提 issue 修（③ 改机制句，④ 要么补实现要么删页面那栏）；
3. 出处接进剪贴板（Q3 第三、四项的前提）。

# 补记：接上 HTML 扫描后的最终结果

> 2026-11-11　`missing` 从 12 降到 3，且 3 条全是真的

上面那版只扫 `style.css`，得出 88% / 4 个未解析。补上 `index.html` 之后
（有些数值的载体是 SVG 属性或内联样式，不在 CSS 里），最终：

```
机制句数值：共 141 个
  直接可回溯 (direct)   129 个
  由几何换算 (derived)    7 个
  载体是资源 (media)      2 个
  实现里没有 (missing)    3 个  ← 只有这类是缺陷
```

**141 个数值里只有 3 个是真的找不到实现**，其余 138 个都能指到具体行。

## 三条 missing，逐条

### S07「1px 与 0.5px 两级线宽」

`style.css` 里 `0.5px` 出现 **0 次**，`index.html` 也没有。
机制句写了一个实现里不存在的线宽。

### S08「滚动 200px 走 6px」

CSS 与 JS 实现里都没有 200。但 `index.html:182` 有：

```html
<div><dt>滚动视差</dt><dd><code>200px / 6px</code></dd></div>
```

**页面在向用户展示一个不存在的参数。** 这比 S07 严重：S07 是内部文案错了，
S08 是页面自己给了一个假规格。

### S20「0.2px 浅线」

同 S08：`index.html:43` 展示 `<code>0.2px</code> 浅线`，CSS 里没有 0.2px
（线是 canvas/JS 画的，但那边的线宽也不等于 0.2）。

## 一个必须记住的判据：`displayOnly`

第一次接 HTML 扫描时，S08 的 200px 被判成了 `direct` —— 因为它在 HTML 里确实"存在"。
而它存在的地方是 `<code>/<dd>` 这类**展示规格的标签**，不是实现。

如果不区分，最严重的那类缺陷会被自己的定位器洗白。所以定位器现在有第五种情况：

| status | 含义 |
|---|---|
| `direct` | 实现里直接写着 |
| `derived` | 由注释说明 / 由几何换算 |
| `media` | 载体是位图、字体 |
| `missing` | 实现里没有 |
| `missing + displayOnly` | **实现里没有，但页面在展示它** ← 最该修的一类 |

`displayOnly` 保留 `hintText` 指向那一行，修的时候要同时处理文案与实现。

## 这个定位器真正的价值

它不只是"给数字找出处"。**它是一台检测「提示词教用户做的事，原型自己没做」的机器。**

141 个数值自动扫过，3 个异常，其中 2 个是页面在说谎。
这条链路（机制句 → 数值 → 实现行号）是 Q3 后续所有工作的基础：
出处进剪贴板、`.md` 下载、按工具改首部，都要读这份 `dna-provenance.json`。

# 补记二：我又在同一个判据上打了四轮转

写到这里必须如实记一件事：**「哪一行才算实现」这个问题，我调了四轮启发式，
每修好一案就退回另一案。**

| 轮次 | 我改了什么 | 结果 |
|---|---|---|
| 1 | 只扫 style.css | S08/S20 的 200/0.2px 判 missing —— 它们在 HTML 里 |
| 2 | 补扫 index.html | S08 的 200 被判 direct —— 命中的是 `<dd><code>200px</code>` 展示栏 |
| 3 | 加 `displayOnly` 判据 | S08 回到 missing，但 S20 的 0.2px（SVG `stroke-width`）被展示行遮住 |
| 4 | 改成先收集全部命中再择优 | S08 修好，S14 的 120px 又退回来（它在 `.t120` 类名里） |

**这四轮本身就是「CSS/JS 语义抽取不可靠」的第五个实证**，而且比第一项的七行 SPEC 更直白：
七行是"合成句子"不可靠，这里是"定位一行"都不可靠 —— 而定位本该是更简单的那一半。

## 所以我把这一档如实改名，并降级

`displayOnly` 现在叫 `display-only`，含义改成：

> **页面展示了这个数，我没能在实现里定位到它。**

不再声称"实现里没有"。因为我不知道 —— 可能是真缺陷，也可能是我漏了某类载体。
闸门把它报成 **WARN 而不是 FAIL**，理由同上：假阳性来自定位器的局限，不是产品的错。

## 两个 WARN 逐条核实过：都是定位器的漏，产品是对的

### S08 的 200px

```
index.html:303    var p = Math.min(1, window.scrollY / 200);
```

真实现，在 JS 里。机制句说「滚动 200px 走 6px」，CSS 的 `ink.style.transform = translateY(6 * p)` 也对得上。
**产品是忠实的**，只是我的定位器没把 JS 里参与运算的裸数字当成"声明"。

### S14 的 120px

```
style.css:318     .t120 { --la: 28; --dl: 0s; }
index.html:70     <article class="tag tag--foil t120" ...>
```

真实现，在**类名**里。四档 `24/40/72/120` 各对应一个 `.tNN` 类。
类名承载数值是件合理但机器读不出来的事 —— 除非为它写专门的规则，而
"专门规则"就是我在第七行开始怀疑的东西。

## 这条路的最终结论

**可回溯率 98.6%（139/141），2 条 WARN 经人工核实都是定位器漏扫、产品无误。**

这意味着：

- 「出处进剪贴板」这件事**技术上可行**，覆盖率高到可以给用户看；
- 但**不能承诺 100%**，也**不能把剩下的当成缺陷来罚** ——
  剩下的是机器读不懂的合法写法（类名、JS 运算、SVG 无单位属性）。

这也是为什么 Q3 第一项的结论只能是「退回轻量版」：
轻量版能坦白说「这个数我在第 N 行找到了」或「我没找到，你可以自己看一眼」；
七行版则必须给出一个确定的句子，而那个句子在 35 案里会有若干案是错的 ——
**错的施工说明比没有施工说明更危险。**
