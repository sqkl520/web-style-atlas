## 任务 3：`layout` 在 S12/S15/S19 为空

### 根因：解析器的正则开了口子，**md 里不缺**

三份 md 的字段 5 都写得完整。实测从 md 里按 `**5. 布局与网格**` 到 `**6. 关键视觉元素**` 之间取原文，与修好后的 data.js 值**逐字相等**：

```
S12 原文 549 字｜data.js 549 字｜完整相等: true
S15 原文 640 字｜data.js 640 字｜完整相等: true
S19 原文 420 字｜data.js 420 字｜完整相等: true
```

**病根**在 A 惯例正则 `^(\d{1,2})(-附)?[.．]?\s*NAME：` —— `[.．]?` 是**可选**的。于是：

```
S12.md 第 26 行：[**5. 布局与网格**] 之后紧跟的正文第一句
    "8 栏，基线 6px（对齐街机像素栅格），栏间距 0。不对称方式：七个洞口按 3 / 2 / 1 / 1 …"
```

被 A 正则读成「**字段 8**，名字 = `栏，基线 6px（对齐街机像素栅格），栏间距 0。不对称方式`」。它落在 `**5. 布局与网格**` 结束位置之后 **1 字节**处（实测：B 匹配 end=1432，A 匹配 i=1433），于是字段 5 的段落被切成长度 0，正文反倒挂到了 `fields["栏，基线…"]` 这个谁都不读的键上。

**为什么恰好是这 3 案**：正文第一句必须**以数字开头**才咬得住 `^\d{1,2}`。全库扫描：

```
A 命中总数 135 ｜其中"数字后无 . 无 -附"的 3
S12 | "8 栏，基线 6px（对齐街机像素栅格），栏间距 0。不对称方式："
S15 | "12 栏，基线 8px，栏间距 20px。不对称方式："
S19 | "12 栏，基线 8px，抽屉面板高 24px（3 个基线单位）。不对称方式："
```

（复算脚本 `deliverables/65-exec/_sep-scan.mjs`）

一位数与两位数混着（8 / 12 / 12），所以「把 `\d{1,2}` 改成 `\d`」这种修法治不了——**只能收掉「分隔符可选」这个口子**。

### 修法

```diff
-  for (const m of text.matchAll(new RegExp('^(\\d{1,2})(-附)?[.．]?\\s*' + NAME + '：', 'gm'))) {
+  for (const m of text.matchAll(new RegExp('^(\\d{1,2})(-附|[.．])\\s*' + NAME + '：', 'gm'))) {
```

分隔符（`-附` 或 `.`/`．`）改成**必需**。

**为什么不是「名字必须在 FIELDS 白名单里」**：`-附` 那一路的 key 剥掉括号后是空串，白名单会把 10 案的机制句起点全挡掉，那 10 案的字段 1 又会把机制句吞回去——**这正是 L143–145 记录的老 bug**（当时把 `[.．]` 写成必需，导致「1-附」没被认成起点）。所以修法的红线是：只能收「一个分隔符都不带」的口子，不能反过来要求「必须有点」。这条已写进代码注释。

**`primary`：保留，但它是派生值，不是数据。**
依据：它与 `palette[1]` 30/30 恒等（结构决定），且 29/30 等于从规格读出的原值、1/30（S01）是兜底推断。只要生成器的 `pal` 构造顺序不变（`bg` 先、`primary` 后），`primary` 就永远 = `palette[1]`。**删掉的代价**：`prompt-copy.js` 之类的下游若按名取主色会失锚（实测目前没有，但 `primary` 是唯一一个"语义化命名"的色角色，`palette[1]` 是位置命名）。**留下的代价**：多一个可漂移的副本。**净结论：保留**——它是当前唯一能表达"这个色是主色"的具名字段，而位置索引一旦有人重排 palette 就会静默错位。但**必须在注释里写明"恒等于 palette[1]"**，否则下一个人会以为它是独立解析结果。

**`buttonText`：保留，但它是 1 bit 的派生值。**
