## 1 攻击点 1：P1a 是不是在修一个不存在的问题？

### 指控

契约 §7.2 的「FAIL ⊆ 允许表」**不是**描述性文字，它是真正的约束力条款 ——
所以「把它变成可执行断言」这个方向不错。但 **P1a 断言的方向选错了**：
它守的是「有没有多出来的 FAIL」，而仓库今天真正腐化的地方是
**「文档声称有的 FAIL 其实不存在」**，这个方向 P1a 结构性地看不见（§1.4 实测）。

### 证据

**§7.2 确实是规范性条款，不是描述。** `_CONTRACT.md:121` 的小节标题就写着
「## 7 完成判据（**缺一不算完**）」，第 124 行：

```
124: 2. `render-scheme.mjs` 跑通，**`FAIL = 0`，或 FAIL 集合 ⊆ §9.15 允许表 ∪ 逐案批准记录，
       且每条在交付说明里有一条引到文件行号的豁免理由**（裁决句，治 32 号矛盾点 4：
       本节 §7 与 §9.15"保留 + 报告原始 FAIL"从前互斥——从现在起按这句仲裁：
       **表内规则的 FAIL 不计入"缺一不算完"**，但**必须在交付说明中逐条列明**，
       无说明即回到违反）。WARN 允许，但要在交付说明里逐条解释为什么 WARN 可接受。
```

「裁决句」「缺一不算完」「无说明即回到违反」—— 这三个措辞把它钉成活条款。
**判定：P1a 的前提「这是一个真约束」成立。加锁的对象不是废话。**

### 证据 2.4：覆盖面假象 —— 野目录被算成「干净案」

选择器 `/^S\d{2}-/` 此刻匹配 **31 个目录**，其中一个是未跟踪的
`prototypes/S99-probe-attack/`（内容是 `{"url":"x"}`，没有 `style.css`）：

```
共 31 个：S01 … S30 S99
其中**不是 S01–S30** 的：S99-probe-attack

S99-probe-attack/.inspect/report.json = "{\"url\":\"x\"}"
has findings? false   has at? false
→ check-contract 判据 (j.findings || []).filter(FAIL) = [] → **算作 0 FAIL 的干净案**
→ check-stale 判据 !Number.isFinite(at) → continue → **静默跳过**
style.css 存在? false → check-prompts 直接 ENOENT 崩
```

而 `check-contract.mjs` 的输出标题硬编码「**30 案**实测 FAIL」。
实测 `check-prompts.mjs` 现在就是 exit 1：

```

code: 'ENOENT'
```

**这个目录不是我建的**（我的探针只读）。它此刻在盘上，且已经让一个检查器崩了。
**判定：P1a 的「覆盖 30 案」是假象 —— 这条成立。** 它遍历的是「任何名字像 Sxx 的目录」，
但对无 `findings` 的报告视为通过、对自己印的案数不做断言。

### 2.5 正确做法

1. **锚点改成标定过的行**：用 `/^\*\*9\.15 /m` 或 `/^## .*9\.15/m` 定位标题，
   找不到就 `exit 2`（而不是 `indexOf` 找到就切片）。
   Lead 探针里那句 `indexOf('9.16')` 同样危险：`9.16` 也可能先出现在别处。
2. **只解析 §9.15 标题之后的第一张 Markdown 表**，用 `|---|` 分隔行确认表头，
   不要「往后捞所有以反引号开头的表格行」。
3. **反向断言必须补上**：`文档声称的 FAIL` 应与 `实测 FAIL` 相等。
   这是今天真有两例缺陷的方向（README-EN:425 多报 6 条、契约 §6 多报 17 处 shadow）。
   具体做法：把 README/README-EN 的 FAIL 清单解析出来，与 `data.js` 的
   `gate.fail` 逐案比 —— `check-docs.mjs` 已有 `nums/gate` 断言了「FAIL=0 的案数 = 29」，
   **但只查总数、不查「哪几案哪几条」**，所以 4 案 8 条 vs 1 案 2 条能同时满足「29/30」。
4. **对案数做断言**：`matched.length === 30`，且每个匹配目录必须存在
   `style.css` / `index.html` / `.inspect/report.json` 三件套，缺一即 FAIL。
   否则野目录会稀释分母。
5. 若真要覆盖 §7.2 的「∪ 逐案批准记录」，先把 `deliverables/tool-runs/` 从
   `.gitignore` 里挪出来（契约 §7.2:127 自己要求的），否则这条分支永远是空集。

## 3 攻击点 3：P1b 会不会大面积假阳性？

1. **P1b 的前提是错的**：`check-stale.mjs` **已经**在查这 30 份 report.json。

3. 触发数不是接近 30，而是 **0–1**。**不会全红**，但也不是「发现了 30 个问题」——
   它今天**什么也没发现**。

`prototypes/_build/check-stale.mjs:40-61`：

### 3.2：「日期分布」是错的度量

计划书的论据是 `report.json` 的**绝对日期**（10-17 ×4 … 最早 13 天前）。
但陈旧度的定义是**相对**的：源文件有没有比产物新。实测：


但量错了对象（问题问的是「源文件改过没有」）。**

两个时点、三个口径的完整矩阵（`rt-stale-matrix.mjs`）：

```
口径A（源 mtime vs report.json mtime，>0 分钟即触发）: 0/30 触发
口径A'（>1 分钟容差）                                : 0/30 触发
口径B（源 mtime vs report.at，check-stale 现行判据）  : 0/30 触发
口径A 下 gap<=0（css 比 report 旧，永远不报警）       : 30/30
```

逐案样例（`gap` 为负 = 报告晚于源，即新鲜）：

```
S03  style.css 2026-10-20T12:15  report.at 2026-10-23T23:25   gapB -269.7
S05  index.html 2026-10-17T03:55 report.at 2026-10-17T06:08   gapB -132.9
S06  style.css 2026-10-17T02:04  report.at 2026-10-17T02:27   gapB  -23.8
S14  style.css 2026-10-24T08:27  report.at 2026-10-24T08:29   gapB   -2.9
S30  index.html 2026-10-19T01:18 report.at 2026-10-25T00:45   gapB   -0.3
```

**判定：P1b 会「大面积假阳性」—— 不成立（0 案触发，不是 30 案）。**
但计划书用来论证「这是个问题」的数字（13 天、日期分布）**是错的度量**，
**这条成立**。真相是：这 30 份 report 全部新鲜，P1b 今天无事可做。

### 3.4：判据会不会用错 —— mtime vs at（这条计划书选对了方向但悄悄选错了字段）

计划书原话：「某案 `style.css`/`index.html` 比它的 `report.json` **新**」——
这句话没说清比的是 `report.json` 的 mtime 还是 `at`。两者不等价，实测有反例：

```
═══ 口径 C：计划书提议的判据（源 mtime vs report.json **mtime**）═══
  report.json 的 mtime 与 at 偏离 >1 小时的案: 1/30
    S14  mtime − at = 6163 分（文件被重写过，但 at 没更新）
```

S14 的 `report.json` 在 `at` 之后 4.3 天被重写过（内容或 BOM 变动），
但 `at` 没跟着更新。**用 mtime 当判据，会把 S14 的「报告时间」往后推 4.3 天，
从而掩盖 4.3 天内的源文件更新。** 契约 §9.6 已经指定了唯一依据：

```
161: **9.6 `report.json` 的 `at` 字段是"这份报告还算不算数"的唯一依据。**
162: 配合 `index.html`/`style.css` 的 mtime 与 sha256，才能说清"我验证的是哪个修订"。
```

**判定：这条是计划书的措辞漏洞，不是致命错误**（现有的 `check-stale` 用的就是 `at`，
是对的）。但如果 P1b 真按字面「比 report.json 新」实现成 mtime 比较，
就会与 §9.6 冲突并把 S14 类案静默洗白。**正确做法：只比 `at`，并在输出里回显 `at`。**

### 3.5 正确做法

**P1b 应当取消**，理由是它要建的东西已经存在且已在守 `at`。
如果一定要做，唯一有价值的增量是三件小事，都不是新守卫：

1. 给 `check-stale.mjs` 补一条 `报告 at 缺失 / 非法` 的 **FAIL**（现在 `continue` 静默跳过，
   见 §3.1 代码：`catch { continue; }` 与 `if (!Number.isFinite(at)) continue;`）。
   S99 那种 `{"url":"x"}` 就是靠这条静默通道溜过去的。
2. 给 `check-stale.mjs` 补一条 `源文件缺失` 断言（`if (existsSync(p))` 不成立时静默跳过，
   一个只剩 `index.html` 的残案会被判「新鲜」）。
3. **不要**引入绝对年龄阈值。若真想要「报告太老」的告警，那是**发布纪律**，
   不是正确性缺陷，应放在周报而不是闸门里，否则 6 个「13 天没动但内容正确」的案会长期挂红。

## 4 攻击点 4：P1b 的语义 —— 截图也旧，比「数字旧」重得多还是轻得多？

### 指控

**「截图也旧」比「数字旧」重得多，但这个论据不支持 P1b 的新增守卫 ——
它支持的是「现有 check-stale 比想象中更重要」。** 因为 `report.json` 与截图是
**同一次事务的产物**，任何覆盖 `report.json` 的守卫**自动**覆盖截图，
所以这个更重的后果并不能推出「需要一条新规则」。

### 证据 4.1：爆炸半径实测

```
30 案 .inspect 里共有 272 张截图
其中 mtime 早于（更新的）源文件的: 0 张（0.0%）
含 ≥1 张陈旧截图的案: 0/30
```

同时报告陈旧的案数也是 0（并行 Agent 重渲染后）。
**两者严格同进同退** —— 因为 `render-scheme.mjs` 一次写完 `.inspect/` 全部产物：

```
S08 .inspect 目录（重渲染后的写入时刻，秒级）:
desktop-fold.jpg     2:26:43
desktop-page-01.jpg  2:26:51
desktop-page-02.jpg  2:26:52
desktop-page-03.jpg  2:26:52
tablet-fold.jpg      2:26:56
tablet-page-01.jpg   2:27:03
tablet-page-02.jpg   2:27:03
mobile-fold.jpg      2:27:07
mobile-page-01.jpg   2:27:16
mobile-page-02.jpg   2:27:16
report.json          2:27:17
```

`report.json` **最后**写（2:27:17），截图在前面同一分钟内。
这是有意的顺序（报告是这次渲染的「收据」）。

### 4.2 严重性对比：为什么「截图旧」确实更重

每案 `.inspect` 有 **2–10 张**截图（实测 272/30 ≈ 9.1 张/案），而 `report.json`
只有一个。所以**单个陈旧事件的受影响产物数**是 ~10 件，不是 1 件。

更关键的是**性质不同**：

| | 数字旧（FAIL/WARN） | 截图旧 |
| --- | --- | --- |
| 谁能发现 | 重跑 `render-scheme` 一比就知道 | **没人能发现** |
| 后果 | 选型台印一个过时的 FAIL 计数 | 评审看的是**不存在的页面** |
| 可自证 | `at` 字段会暴露 | 截图上没有任何时间戳 |

契约 §9.6 要求交付说明写明 `report.json` 的 `at` + 两个源的 mtime + sha256，
**但 `.inspect/*.jpg` 没有任何自证字段**。一张 7 天前的 `desktop-fold.jpg`
和一张 7 分钟前的，在文件管理器和 HTML 里长得一模一样。

而且这个仓库已经**因截图错过一次真缺陷**（§9.20）：

```
354: 1. `.inspect` 三档只截前 2–3 屏 ⇒ 长页底部的状态（S02 错误码在 390 档第 11/11 屏）
        **在交付截图里永远看不到**（33 号 AH-07/T1-7）。
```

也就是说：**截图早就不是「页面真相」，它是有取景缺陷的证据框**（§9.20 标题就叫
「取景缺陷不是页面缺陷」）。再叠一层「截图可能还是旧修订的」，
等于让一个本来就不完全的证据框再失去时效性。

### 4.3 判定

**指控成立**：「截图也旧」确实比「数字旧」**重得多**。
但**这个更重的后果不构成新增守卫的理由**，因为它和数字陈旧是**同一个布尔量**
（`源 mtime > report.at`）的两个下游表现。重写一遍判据只会制造第二处需要同步维护的代码 ——
这正是 `_entries.mjs` 那个文件存在的理由（它自己的注释写着：三处复制同一个选择器，
导致 `_selection` 被同时漏掉）。

### 4.4 正确做法

1. **不要新增判据**，把「截图陈旧」写进 `check-stale.mjs` 现有的提示文本里
   （它现在只写「选型台与 data.js 展示的是旧修订的闸门结果与截图」——
   已经写了「截图」，够了）。
2. 真正值得加的是**给截图加自证**：`render-scheme.mjs` 在 `.inspect/` 里落一个
   `provenance.json`（`report.at` + 三档截图的 sha256 + 源文件 sha256）。
   这解决的是 §9.6 对 `report.json` 已经解决、对截图**从未解决**的问题 ——
   即「我看到的这张图是哪个修订」。这是一个**新能力**，不是给旧结论上锁。
3. 若要人可读，把 `at` 烧进截图角落（水印），但这会改视觉，需另评估。

### 证据 5.2：真正的风险 —— 只治了一半，且留了垫片

**风险 A：`palette` 有完全相同的病，但没改。** 实测两个数据源的字段形状差异：

```
同名不同形状的字段（跨两个数据源）:
   palette       data.js=array      dna=string
```

`data.js.palette` 是**数组**（`bg, primary, …` 最多 4 色），
`prompts.js.dna.palette` 是**字符串**（`#RRGGBB（角色名）、…`）。
**这与 `fonts` 是同一类缺陷，严重程度还更高** ——
`check-twolines.mjs` 的 R1/R6/R7 三条硬断言全都在 `palette` 上，

改了「只用来显示的 `fonts`」，留下「被三条硬断言读的 `palette`」同病不改，
这个优先级是反的。**判定：P2 的病根选错了对象 —— 这条成立。**

**风险 B：`r.fontsSpec || r.fonts` 是兼容垫片，会让下一轮审计读不出真相。**
`data.js` 已经没有 `fonts` 键（实测 0 个），所以 `|| r.fonts` 分支**永远取不到值**。

§9.23 第 2 例：「搜不到」被当成「不存在」。下次有人 grep `r.fonts` 会命中
`app.js:239` 与 `1357`，得出「还有两处在读旧字段」的错误结论。

**风险 C：改名会让 `check-docs.mjs` 的 sandbox 装载路径产生盲区。**
`check-docs.mjs:390` 用 `vm.runInContext(data.js)` 装载 `window.SCHEMES`。
改名后 `gate` 等字段名没变，所以它不红 —— 但这也意味着
**没有任何检查器会验证「`fontsSpec` 有值」**。实测 `check-docs` 现在是绿的：


它查 `audit` 有没有值、`layout` 有没有值（`status/layout-fix`），

「缺 字体策略：无」，但那只是 console 输出，不参与退出码。
所以 P2 改完之后，**「改漏一处」和「改对」在检查器眼里是同一种绿**。

### 5.3 判定

- 「改动面超过 5 处」→ **不成立**（源文件 4 处）。
- 「收益抵不上风险」→ **部分成立**，但理由不是处数，而是：
  ① 选错了病根对象（`palette` 更严重且未改）；
  ② 引入死垫片 `|| r.fonts`；
  ③ 改名后没有任何检查器验证新字段有值，改漏与改对同绿。

### 5.4 正确做法

1. **先给 `fontsSpec` 加一条断言**（`check-docs.mjs` 的 `panel/fields` 里加一项
   `fontsSpec 30/30 有值且长度 ≥200`），**再做改名**。顺序反了就会有一个
   「改了但没人验证」的窗口期 —— 这个仓库对这个模式有明确教训
   （`collect-schemes.mjs:355` 的注释：「数组里列了名字，赋值表里少一行」，
   同一个病发生过两次）。
2. **删掉 `|| r.fonts` 死分支**，或者保留一个 `data.js` 里的 `fonts` 别名并注释
   「已废弃，仅为外部脚本兼容，2026-11-30 删」。二选一，不要留一个永远为 false 的兜底。
3. **把 `palette` 的形状差异也处理掉**：要么 `data.js.palette` 改名 `paletteList`，
   要么在 `check-twolines.mjs` 里加一条断言「两侧 palette 形状必须显式声明」。
   现在的状态是：`check-twolines` 用 `asHexList()` 把两边都归一成 hex 列表再比，
   **形状差异被抹平了**，所以这个病永远不会被任何检查器发现。
4. 改名时把 `data.js` 的 30 个键、`collect-schemes.mjs:364` 的赋值、`app.js` 两处读取
   **放在同一次提交**，并用 `node prototypes/_build/collect-schemes.mjs && node check-docs`
   做前后指纹对比（§9.22 第 3 条：对会产出报告的命令做前后指纹）。

### 6.2 校准：探针必须先抓住已知真缺陷，否则不可信

我用契约 §9.11 已认账的 S01 偏离做校准：

```
═══ 校准：探针能否抓出契约 §9.11 已认账的 S01 真偏离 ═══

```

**这一条很重要**：我在校准前写了两版探针都**读不到 S01 的 16px**
（第一版 `evalLen` 先判字面量后替换 `var()`，第二版把 `--fs-body: 16px`

却仍然打印出漂亮的「命中率」。这是 §9.23 的教科书案例，
也是 P3 的最大风险：**探针自己的 bug 会伪装成「这案没问题」。**

```
function cssVars(css) {   // 修好之后
  /* 存**带单位**的字符串，不要存 parseFloat —— 上一版存了 16（丢单位），
     evalLen 替换 var() 之后拿到 "16"，再判 /^-?[\d.]+px$/ 就判不出，
     于是 S01 的 --fs-body: 16px 被读成「读不到」。§9.23 第三次同型。 */
```

### 6.3 纯审美的部分（以及为什么它比想象中小）

真正**不可机械判定**的只剩这些，且都可以降级成「结构化人判」：

| 内容 | 为什么不可机械判定 | 可降级为 |
| --- | --- | --- |
| 「是不是好设计」 | 无真值 | **不做**。这是评审的活，不是 Agent 的 |
| 「像不像那个美学家族」 | 需要视觉判读 | 给参考图 + 判据清单，2 人独立打分，分歧即挂起 |
| 「机制是否真的成立」 | 需要理解交互 | 转成可测的：`prefers-reduced-motion` 下机制是否还在（契约 §6 已要求） |
| 「不对称是否读得出」 | 主观 | 转成数字：栏宽比最大/最小 ≥ 某阈值（S01 规格写「差 2 个单位」） |
| 「去 AI 味」 | 已有 40 条 R 规则 | 已有规则引擎覆盖，不需 P3 |

**结论：P3 应该先把 299 条机械断言跑完，人只看机器筛出来的差异清单。**

逐个核实（这一步是关键，不能只信探针）：

**S01** —— 真偏离，但**已被契约 §9.11 认账**，且没有在 CSS 里留注：

```
Select-String '规格原写|见裁定|偏离规格' → 无命中
```
→ 已在 `_CONTRACT.md:177` 记录。**不是新发现。**

**S03** —— **有裁定依据，是合规的**：

**这是 P3 最重要的反面教材**：如果 P3 的 Agent 只做机械比对、不读 CSS 注释，
它会把 S03 报成缺陷，而这是一条**已在设计里留了裁定引用的合规偏离**。
全 30 案里只有 S03 一案留了这种裁定注（实测 `1/30`）——
说明「裁定是否落在实现旁边」本身是不一致的，P3 必须顺手核这个。

**S07** —— **真偏离，且没有任何检查器报过**：

```

S07 --lead: 28px   /* 4 × 7px */

探针: 正文 16px（规格 15），行高 28px（规格 15×1.85 = 27.75px）
S07 CSS 里「1.85」出现 0 次
```
→ 正文 16px 而非 15px（同 S01/S03 的偏移模式），行高 28px 落在 7px 基线上
（`4×7`）而不是 1.85 倍。
**折中解释是合理的**（28px 同时满足 7px 基线整数倍），但**规格写的是 1.85**，
而仓库对这类折中的规矩是「留裁定引用」（S03 做了，S07 没做）。
**这是一条真实的、未被记录的规格偏离 —— P3 应当产出这样的东西。**
值得注意的是：`_CURRENT-VALUES.md:41` 提到 S07 的色值「一字未动」，
但**字号/行高不在 `_CURRENT-VALUES` 的管辖范围内**，所以这条偏离永久无声。

**S10** —— 行高 24px vs 规格 15×1.7 = 25.5px：

```

S10 body: font-size: var(--body); line-height: var(--leading)
实测解析: --leading 求值 24px；24 / 15 = 1.6（规格 1.7）
```
→ 24px 是 8px 基线的整数倍（`3×8`），与 S07 是**同一个设计决策**：
优先守住基线网格，牺牲规格写死的行高倍数。**这条需要人判**，
但它是一个**可定位、可讨论的具体偏离**，不是「像不像好设计」。

### 6.4.1 关键补充：S01/S03/S07 的 15px→16px 不是三次手滑，是闸门逼出来的

我一开始把「正文 16px 而规格 15px」当成三个独立缺陷。实测后必须修正这个判断：

```
id   规格正文  实现正文  是否改大  规格行高  实现行高  有裁定注
S01   15       16        是        1.75     28        —
S02   16       16        否        1.85     —         —
S03   15       16        是        1.8      —         有
S06   15       15        否        1.9      —         —
S07   15       16        是        1.85     28        —
S08   16       16        否        1.8      —         —
S09   16       16        否        1.8      —         —
S10   15       15        否        1.7      24        —

规格写 15px 的案: 5 → S01 S03 S06 S07 S10
实现改成别的字号: 3 案 → S01(15→16) S03(15→16) S07(15→16)
其中有裁定注的: 1 案 → S03
```

**起因在闸门规则里，`rules.mjs:106-107`：**

```
106: if (m.type.body && m.type.body.size < 15) add('FAIL', 'body-size', … 'Body copy 16–20px. …');
107: else if (m.type.body && m.type.body.size < 16 && !mobile) add('WARN', 'body-size', …);
```

规则把 **15px 判成 WARN**、把 16–20px 定为目标。而 `_specs/*.md` 字段 5 冻结的是
「正文 15px」。**规格要求的 15px 在闸门眼里是「通常不对」的。**
于是 5 个规格写 15px 的案里，3 个改成了 16px —— 这是**在两个权威之间选边**，
不是执行失误。

**这对 P3 是本报告最重要的一条操作性结论：**

1. P3 若把「15→16」当缺陷报，它会报出 **3 个「为了讨好闸门而做的改动」**，
   而这 3 个改动**恰恰是正确响应**（闸门规则是硬约束，规格是软冻结）。
2. 但同一批改动里 **2 个（S01、S07）没有留裁定注**，S03 留了。
   所以真正的缺陷不是「改了 15px」，而是「**改了却没记录理由**」——
   这才是可证伪的、值得报的东西。
3. `_CONTRACT.md:177`（§9.11）已经用 S01 举过这个例子，但**没有把它归纳成规则**，
   所以 S07 又犯了一次。P3 应当把这条固化成断言：
   **「规格冻结值被改动 → CSS 里必须有 `spec-adjudicated: <依据>` 注释，否则 FAIL」**。

**这条断言的价值**：它能同时抓住 S01（无注）、S07（无注），并正确放过 S03（有注），
**0 假阳性**。这是本次红队能找到的、最值得进 P3 的单条判据。

### 6.5 任务书点名的那个例子（「12 栏 → repeat(12,…)」）其实很容易假阳性

任务书建议「规格说 12 栏，原型 CSS 里是不是真的 `repeat(12, ...)`」。
实测这条判据本身**不可靠**：

```
id   规格声明栏数     CSS 的 repeat 栏数        命中
S10  3/5              —                        ✘ 无交集
S16  12/9             3                        ✘ 无交集
S17  12/3             —                        ✘ 无交集
S26  12/5/3/4         —                        ✘ 无交集
S29  10/5             —                        ✘ 无交集
S03  3/9/12           2                        ✘ 无交集
S23  14/2             36/6/3                   ✘ 无交集
```

**这 7 条「无交集」全是探针假阳性。** 逐条核实：

```
S10: grid-template-columns: 6fr 7fr 9fr 8fr 5fr;   ← 5 栏，完全正确，只是没用 repeat()
S17: grid-template-columns: minmax(210px, 3fr) 16px 9fr;   ← 3 栏 + 16px 铅条，正确
S26: grid-template-columns: 7fr 5fr / 5fr 3fr 4fr  ← 正确，显式 fr 而非 repeat
S16: grid-template-columns: 1.08fr 0.92fr         ← 2 栏
```

**判据的正确答案是「`repeat(N,…)` **或** 恰好 N 个列轨道（展开 `minmax` 内的 fr）」，
而不是「字符串里有没有 `repeat(N,`」。** 按后者实现，23 案里会误报 7 案 = 30% 假阳性。

**这是 P3 的核心方法论结论**：纯字符串匹配在 CSS 上不可用。
必须解析成「列轨道列表」，再比结构与比例。这需要写一个小的 CSS 值解析器
（我为了解析 `calc(var(--u) * 3)` 已经踩了两次坑，见 §6.2）。

### 6.6 判定与正确做法

**判定：「P3 没有客观判据」不成立（299 条机械断言）。但「P3 可以直接派 Agent 去比对」
也不成立 —— 朴素比对会产生 30% 级假阳性（§6.5）和 20/30 案级假阳性（§6.7）。**

**正确做法（具体建议）**：

**第一步：写一条机械闸门 `check-spec.mjs`**，不派 Agent。它做 6 类断言：
1. 字段 3 正向色 → `style.css` 里存在（**必须先剥掉「为什么不像 AI 默认配色：反的是 …」
   之后的否定从句**，否则 20/30 案全红，见 §6.7）；
2. 字段 5 栏数/栏宽比 → 解析 `grid-template-columns` 的**列轨道列表**，比数量与 fr 比例；
3. 字段 5 栏沟 → 解析 `--gutter`/`gap`/`calc`；
4. 字段 5 正文 px / 行高 → 解析 `body` 的 `font-size`/`line-height`，展开 `var()`；
5. 字段 5 断点 px → `@media` 里存在；
6. 字段 4 字体族 → `font-family` 里存在。
   **每条允许 `/* spec-adjudicated: R-xx */` 形式的豁免注**（照抄 S03 的做法），
   有豁免注的降级为 INFO 并回显注的理由。**没有豁免注的就是 FAIL。**

**第二步：只有机械闸门报完之后，才派人**。人只看两类：
- 闸门报「规格与实现不一致且无豁免注」的案（今天至少 S07、S10、S25 一案待判）；
- 闸门**核不到**的字段（字段 1/2/6/7/8/9/10/11/12 —— 这些是文字，不进闸门）。

**第三步：把「人判」也做成可证伪**。对每个核不到的字段，要求 Agent 输出
**「规格原句 + 实现位置（文件:行号）+ 一致/不一致 + 依据」** 四元组。
「不一致」必须有行号，否则不算。这样即使结论是主观的，**证据是可核的**。

**绝对不要做的**：让 Agent 自由「看看像不像」。理由见 §6.7。

### 6.7 P3 的最大风险不是主观，是「假阳性的规模」

我的**第一版**（朴素）探针的输出：

```
A 字段3 四个 hex 全部出现在 CSS:            0/30 = 0%
字段3 至少漏 1 个 hex:                    20 案 → S01[#6366F1 #FFFFFF] S02[#8B5CF6 #22D3EE #C9A227]
  S03[#6366F1 #22D3EE] S04[#EC4899 #8B5CF6] S05[#22D3EE #10B981] S06[#6366F1 #F5EFE6 #C4A484] …
```

**「20/30 案漏色」是彻底的假阳性。** 原因有两个，都是我自己的量具错：

1. **`#6366F1` 是规格里被「反」掉的颜色**。字段 3 后半句写着
   「为什么不像 AI 默认配色：反的是 `#6366F1` 靛蓝与纯白 `#FFFFFF`」——
   **这些 hex 是禁止项，不是要求项。** 把它们算成「规格要求的色」，
   于是 20 个案子被报成「漏了 #6366F1」。
2. **S11–S30 的规格格式不同**：字段名单独成行，值在下一行。
   按「含『配色系统』的那一行」取值，只拿到标签本身（`**3. 配色系统**`，11 字符），
   于是正则匹配不到任何 hex，那 20 个案子全部退化成空列表。

修掉这两处之后：

```
A 字段3 正向色全部在 CSS 里:      29/30 = 97%
仍有漏色:                        1 案 → S25[#181C0D #232410]
```

而 S25 那一案也是假阳性 —— `#181C0D` 在规格里明写是「**派生色值**，
它是两版油墨与承印纸相乘的实测结果而不是一个配色决策，**不占配色名额**」
（`_specs/S25.md` 字段 3 原文）。**它本来就不该出现在 CSS 里。**

**这就是 P3 的真实风险画像**：一个没校准的 Agent 会报「20/30 案配色不符」，
看起来收获巨大，实际是 **100% 假阳性**。若照那个报告去改设计，
会去给 20 个案子硬塞 `#6366F1` —— **把整套语料改坏。**

## 7 攻击点 7：这四项的排序对不对？

### 指控

**排序反了，而且反得很确定。** 但结论不是「应该先做 P3」——

### 证据 7.3：正确的排序与其理由

**第 0 位（立刻）：修 P2 留下的半成品。**
`data.js` 已改名 `fontsSpec`，但：
- `app.js:239,1357` 留了 `|| r.fonts` 死垫片（`data.js` 里 `fonts` 键已 0 个）；

- 没有任何检查器验证 `fontsSpec` 有值（`check-docs` 全绿）。

理由：**半成品比没做更危险。** §9.23 记的正是「验证器写错会诱导你回滚正确的工作」，
而这里是「改名改一半会让下一轮 grep 得出相反结论」。

**第 1 位：P3 的机械闸门（`check-spec.mjs`）。**
理由：
- 唯一有真实产出的项（≥3 个现存偏离）；
- 299 条断言全是数字，不需要审美；
- 它有**最强的独立性**：`_specs/*.md` 是人写的，`style.css` 是实现，
  两者的比对不受任何生成链污染。而 P1a 的允许表与 FAIL 虽然独立，
  但允许表本身是人补登记的（§9.15 第 201 行就是 2026-10-24 手补的）——
  **它的独立性已经被人工介入削弱过。**
- 它是**唯一能覆盖 `_CURRENT-VALUES.md` 覆盖不到的东西**的检查器。
  实测 `_CURRENT-VALUES.md` 只管色值/字体/错误码，**字号与行高不在管辖内**（§6.4 S07）。

**第 2 位：P1a 换方向。**
保留现有 `check-contract.mjs`，但改三处：
1. 修锚点（`/^\*\*9\.15 /m`，找不到 exit 2）；
2. 加反向断言：**文档声称的 FAIL 集合 == 实测 FAIL 集合**（今天的 README-EN:425
   「4 案 8 条」vs 实测「1 案 2 条」、契约 §6「17 处 shadow」vs 实测 0 处，两例都抓得到）；
3. 对案数做断言（`matched.length === 30` + 三件套存在性）。
理由：这三点都是**今天有真实缺陷**的方向，而原版三条 C1/C2/C3 没有。

**第 3 位（取消）：P1b。**
理由：规则已存在且已在守 `at`；0/30 触发；论据用了错度量。
唯一增量是「`at` 缺失/非法 → FAIL」（现在 `continue` 静默跳过），
这条应当并进 `check-stale.mjs`，不必新开一项。

### 7.4 「给已有结论上锁」vs 「发现新问题」——这个二分要修正

计划书隐含的二分是「P1a/P1b 上锁、P3 发现」。实测不完全是：

- P1a **现在**是上锁（差集为空）。但它换方向后（反向断言）**能发现新问题**。
  所以它不是「本质上是上锁」，是「**这一版实现选错了断言方向**」。
- P1b 是纯粹的上锁，且锁已经在了。**应当取消。**
- P3 是发现，但**必须先有机械闸门**，否则它的「发现」是 100% 假阳性（§6.7）。

所以排序的真正理由是**「缺陷检出率 / 实现成本」**，不是「上锁 vs 发现」：

```
P3 机械闸门   : ≥3 个现存缺陷 / 299 条断言       ← 最高
P1a 换方向    : 2 个现存缺陷（README-EN、契约 §6）/ 改 3 处代码  ← 次高
P2 收尾       : 0 个新缺陷，但清掉 3 个风险      ← 必要，不是收益
P1b           : 0 个现存缺陷 / 已存在            ← 取消
```
