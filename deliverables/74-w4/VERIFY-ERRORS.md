## 2. 逐条证据

### S17 — 「金额列 96px」 → **CONFIRMED（数字不存在）**

```
$ grep -c "96px" S17-revenue-stamp-stub/style.css      → 0
$ grep -c "96px" S17-revenue-stamp-stub/index.html     → 0
$ grep -n  "96"   S17-revenue-stamp-stub/style.css     → 无任何命中
```

唯一的金额列规则，分三档：

```css
/* style.css:181 — 默认档（含 >=1440px 桌面） */
td.num { text-align: end; }                 /* 只有右对齐，没有任何宽度 */

/* style.css:308-321 — 仅 1024–1439px */
@media (min-width: 1024px) and (max-width: 1439px) {
  ...
  td.num { width: 88px; }                   /* style.css:320 */
}
```

所以「96px」不但不存在，`88px` 也只出现在**中间那一档**：桌面默认档没有任何固定宽度，
完全靠 `text-align: end` + `font-variant-numeric: tabular-nums`（`style.css:43`）对齐。

还有第二层漂移：spec 自己写的是「>=1440px … 金额列固定 96px；1024–1439px … 压到 80px」
（`_specs/S17.md:29`），实现是「桌面无宽度；中档 88px」——**两个断点都没照 spec 做**，
88 既不是 96 也不是 80。

**改写建议**：「两联按 3fr、16px、9fr 分栏，中缝是半径 1.2px、孔距 6px 的孔列，行高 24px、
金额列靠等宽数字右对齐（1024–1439px 档压到 88px），印面偏中缝 2mm——撕口位置与小数点对齐即读出归属。」

（原句「孔径 1.2px」也不准：SVG 里是 `r='1.2'`（`style.css:151`），孔径＝直径 2.4px，
1.2 是半径。「行高 24px」实为 `th,td{height:var(--row)}`＝行盒高 24px，`line-height` 是 21px
（`style.css:165`）——两处都是轻度过失，见 §4。）

### S10 — 「固定右下错 1px」 → **CONFIRMED（且句子自相矛盾）**

```
$ grep -oE "[0-9.]+px" S10-grid-versus-sheet/style.css | sort | uniq -c
  ... 7 x 1.5px, 4 x 1.25px, 3 x 3px, 2 x 5.5px ...   （全表无 1px）
$ grep -n "1px" S10-grid-versus-sheet/style.css   → 无输出
$ grep -n "1px" S10-grid-versus-sheet/index.html  → 无输出
```

`1px` 在 CSS 与 HTML 里**一次都没有**（连 `11px`/`21px` 这类含 `1px` 子串的都没有）。
真值：

```css
/* style.css:32-33 */
  --misreg: 1.5px;
  --misreg-start: 3px;

/* style.css:211, 216 — 红版整体位移 */
.plate-rules { transform: translate(var(--misreg), var(--misreg)); }        /* 1.5px, 1.5px */
.sheet:not(.settled) .plate-rules { transform: translate(var(--misreg-start), var(--misreg-start)); }  /* 3px */
```

方向「右下」是对的（`translate(+1.5, +1.5)`；红套准角标
`bottom: calc(10px - var(--misreg)); right: calc(10px - var(--misreg))`，`style.css:130`）。

**致命点不是 1≠1.5，而是同一句里自相矛盾**：前半说「错 1px」，后半说「再收到 1.5px」——
同一个量给了两个终值，LLM 只能二选一。最可能的混淆源是 `1.25px`：`--column-rule` 与
`--reg-w` 都是 1.25px（`style.css:25-26`），那是**套准线的线宽**，不是**套印错位量**。

**改写建议**：「五栏按 6:7:9:8:5 分宽，红版相对黑版固定右下错 1.5px、进视口时先错 3px 再收到 1.5px，
标题基线上移 6px——对比强度由栏宽比与错位像素共同给出。」

### S09 — 「留 5% 至 10% 缺口」 → **PARTLY TRUE（数在区间内，但说法形状是错的）**

先按 path 几何重算（不采信注释）：

```
outer d="M3.2 22 L4.1 4.4 L58 3.5 L113.7 4.7 L114.5 22.6 L113.3 39.3 L58 40.5 L3.2 39.4"
实际描画长 272.03（单位），首尾未闭合段 17.40 → 17.40/289.43 = 6.01%
inner d="M28 10.8 L106.3 11.3 L107.3 22.1 L106.4 32.6 L29 33.5 L10.1 32.7 L9.9 10.9"
实际描画长 217.81，首尾未闭合段 18.10 → 18.10/235.91 = 7.67%
```

CSS 注释（`style.css:310`）说「外线 6.0% 落在左边、内线 7.7% 落在顶边，不在同一边」——
**注释与几何完全吻合**（6.01 / 7.67），不是谎话。外线首点 `(3.2,22)` 收于 `(3.2,39.4)`＝左边竖直边；
内线首点 `(28,10.8)` 收于 `(9.9,10.9)`＝顶边水平边，确实「不在同一边」。

那么 5%–10% 错在哪：它没给出任何假数，但**把两个固定常量写成了一个可变区间**，
而且丢掉了这条机制唯一有设计价值的部分：两个缺口**分处不同的边**，所以重描时缺口不会一起跳。
这是「vague 而非 wrong」——但作为 AI 建造提示，写 5%–10% 会让 LLM 去造一个「缺口位置随机的区间」，
而真值是「6.0% 与 7.7% 两个定值，且不同边」。

**改写建议**：「价目行以 1.5° 整体倾斜，行高 56px、左端起点错开 4 至 12px，描边外线 3.5px 与内线 2px，
两线各留缺口 6.0% 与 7.7% 且分在不同边——可读性交给等宽数字，手绘只做外圈。」

同句其余数字全部核实为真：`--tilt:1.5deg`（`:32`）、`min-height:56px`（`:283`）、
`stroke-width:3.5` / `2`（`:307-308`）、HTML 的 `--start` 取值为 4/5/6/7/8/9/10/11/12（区间 4–12 成立）。

### S03 — 「右侧 9 栏」 → **FALSE（实现）／TRUE（设计意图），即任务书问的 (c)**

穷举全案 CSS 的每一处栅格：

```
$ grep -n "grid-template-columns" S03-.../style.css
:124  .chrono { grid-template-columns: var(--axis-w) minmax(0, 1fr); }          <- 2 轨
:222  .chrono { ... var(--axis-w) minmax(0, 1fr) minmax(0, 540px); }            <- >=1440 时 3 轨
:233  .chrono { ... 200px minmax(0,1fr); }   :240  168px ...
:188  .plates { grid-template-columns: repeat(2, minmax(0, 1fr)); }             <- 2 列
$ grep -rn "repeat(12" S03-.../          → 无
$ grep -rn "9 栏|九栏|span 9" S03-.../    → 仅 style.css:120 的注释
```

**全案不存在任何 12 栏栅格，也不存在任何 9 栏。** 唯一的「12 栏/9 栏」出现在
`style.css:120` 的一行注释里，而那行注释只是把 spec 抄了一遍：

```
/* ── 观测记录：12 栏，左 3 栏年代轴，右 9 栏影像带 ──────── */
```

spec 原文两处一致：`deliverables/04-schemes-01-10.md:105` 与 `prototypes/_specs/S03.md:25`
都写「纵向年代轴占左侧 3 栏（宽度 264px）… 右侧 9 栏放影像带与读数卡，列数 12」。

**关键判断（回答任务书的 a/b/c）**：是 **(c) both**，但要点在归因——
「9 栏」是对**设计意图的真陈述**（spec 确实这么规定），同时是对**实现假陈述**（从未落地）。
它不是笔误、不是算错，而是**机制句逐字复制 spec 字段 1-附 的结果**：所有 mechanism 都是
spec 1-附 的原样搬运（S03 见 `_specs/S03.md:15` 与 `04-schemes-01-10.md:95`，逐字相同）。
实现把 12 栏简化成「264px 固定轴 + 1fr 流体带」，2 轨，没有 12 栏分母，因此「3:9」这个比例
在页面上不存在，读者看到的是一根固定轴加一条通栏影像带。

对「给 LLM 的建造提示」而言这就是**假**：照着写会产出 12 栏栅格 + 9 栏内容区，
而那是一个结构上完全不同的页面。

**改写建议**：「一条 264px 宽的纵向刻度轴随滚动固定，右侧影像带以 1fr 吸收余量、带高按 30 秒曝光折成 28px 一档，
四角遮罩压掉 32%，1.2px 自绘十字游标随指针移动——层级由高度与固定位置承担，不由名字承担。」

（顺带：原句「游标随焦距比移动」也是空指——全案 CSS/HTML/JS 无任何 `焦距`/`focal` 字段，
`游标` 只是 `pointermove` 跟指针的 1.2px 十字，`index.html:302-308`。这是对机制的第二处虚构，
但任务书没点它，见 §4。）

### S07 — 「正面 5 栏对背面 7 栏」 → **CONFIRMED（5/7 是页宽比，不是栏数）**

```css
/* style.css:70-74 */
/* 跨页版心：5fr 1px 7fr，1px 是字段 11 要求的跨页实线 */
.pages { display:grid; grid-template-columns:5fr 1px 7fr }

/* style.css:80-82 —— 真正的文字栏数 */
.toc { column-rule:.5px solid var(--slate); column-gap:var(--gutter) }
.page-recto .toc { column-count:2 }     /* 正面 2 栏 */
.page-verso .toc { column-count:3 }     /* 背面 3 栏 */
```

`5fr : 7fr` 是**两张纸的宽度比**（正页 : 背页），不是「5 栏 : 7 栏」。
文字实际是 **2 列（recto） 对 3 列（verso）**。

**有没有哪个断点能救「5 栏 / 7 栏」？没有**，逐档穷举（`style.css:153-181`）：

| 断点 | `.pages` | recto 列数 | verso 列数 |
|---|---|---|---|
| >=1280px | `5fr 1px 7fr` | 2 | 3 |
| <=1279px | `1fr` | 3 | 3（recto 被提到 3） |
| <=899px | `1fr` | 1 | 1 |

三档里没有任何一档出现 5 或 7 列。**唯一 7 是 `.plate-grid{repeat(7,1fr)}`（`:123`）**——
那是档案图版的 7 列网格，与跨页版心无关，不能拿来当「背面 7 栏」。

与 S03 同源：spec `_specs/S07.md:23` 写「跨页版心左 5 栏右 7 栏（栏宽 62px、栏沟 18px）」，
从未实现；实现退回到「页宽 5:7 + 目录 2/3 列」。注意 `--module:62px`（spec 的栏宽）
在 CSS 里**只被 `.lede` 的 max-width 用过一次**（`:49`），没有参与任何栅格。

同句其余全部为真：`8% 至 14%`（`app.js:48,50` 的 `--ghost-o` 与 `hot` 上限 `.14`）、
整体偏移 `1px`（`app.js:24` `translate(W,1) scale(-1,1)`，viewBox 按像素设，1 单位＝1px）、
`栏线 0.5px`（`column-rule:.5px`，`:80`）、`页码竖排 28px 行高`
（`.folio{writing-mode:vertical-rl; line-height:var(--lead)}`，`:107`，`--lead:28px`）。

**改写建议**：「同一段文字在纸背以 8% 至 14% 不透明度做镜像并整体偏移 1px，
正面 2 栏对背面 3 栏、页宽比 5:7、栏线 0.5px，页码竖排 28px 行高——正反两面同时进入同一张版心。」

## 3. 独立抽检（4 案，不在名单内）—— 发现 3 处新错误

### S01（新错误，硬）：「红块越界压住 3 行正文」 → **FALSE，而且这是本仓已修过的 bug**

原句：「一块实色多边形以 11° 切入 4 栏版心，24px 实体隔条撑开栏沟，**红块越界压住 3 行正文**——…」

CSS 自己记着修复过程与结论（`style.css:133-141`，verbatim）：

> ⚠️ Lead 看图后修的遮字缺陷（2026-10-24）：… 红块**真的吃掉了第二栏“争议集中在两处”和第三栏标题的笔画**，
> 截图上那两行是断的。… 修法：**只把正文列抬到楔形之上——红楔从此切进栏间留白与栏首空白，压不到字**。

实现也确实是这么落的：

```css
/* style.css:149-154 */
.columns { position: relative; z-index: 3; }
.col     { position: relative; z-index: 3; }
.wedge   { background: var(--red); z-index: 1; }   /* 楔形在正文之下 */
```

正文列 `z-index:3`、楔形 `z-index:1` ⇒ **楔形现在压不到任何一行字**。
「压住 3 行正文」描述的是修复前的那版页面，作为建造提示会让 LLM 主动去造一个
「色块盖住正文」的可读性缺陷——而这正是本仓花了力气修掉的东西。

附带：楔形高 300px、报头高 148px ⇒ 垂下正文区 **152px ≈ 5.43 行**（28px 行高），不是 3 行；
且 `clip-path` 用百分比，角度随视口变：实测 **10.95°（W=1440）、9.76°（1280）、7.83°（1024）**，
只有 >=1440 档才真是 11°。

**改写建议**：「一块实色多边形以 11° 切入 4 栏版心，24px 实体隔条撑开栏沟，
红块从报头垂下 152px、切进栏间留白与栏首空白而不压字（正文列层叠高于楔形）——
阅读顺序由角度与留白占用决定，与它叫什么名字无关。」

### S24（新错误，硬）：「并留 2px 缺口」 → **未实现**

原句：「…支线由 2.5px 递减到 1、0.6、0.4px **并留 2px 缺口**——深度由层数与线宽读出。」

四条线宽都真（`.vm 2.5 / .vb 1 / .vc .6 / .vd .4`，`style.css:155-158`），但「2px 缺口」查无实现：

```
$ grep -n "dasharray" S24-.../style.css
:154 .vein path{ ... stroke-dasharray:100 100; stroke-dashoffset:0 }
$ grep -oE 'class="v[mbcd]" d="[^"]*"' | awk -F'M' ...   → 18 条路径，每条只有 1 个 M（连续，无断段）
```

`pathLength="100"` + `stroke-dasharray:100 100` 在长度恰为 100 的路径上＝**一整段实线、零缺口**，
这个 dasharray 只是给生长动画（`dashoffset:100 → 0`）用的。没有任何以 px 为单位的
`stroke-dasharray`，也没有在节点处切成两段路径。全案唯一带明确尺寸的缺口是
`<rect class="leaf__gap" width="4" height="4">`（4px 纸白，微交互用，`style.css:201`）——不是 2px。

「2px 缺口」只活在文案里（`index.html:99`、`:205`、`:325` 三处 prose）。这是**文案声称、代码未做**的典型。

同句第二处：「**每层各伸 2 栏**」与实现冲突——`.lv{grid-template-columns:5fr 3fr}`（`:133`）
是对整幅 8 轨做 5:3 切分（＝5 轨与 3 轨），不是「中轴两侧各 2 栏」。spec 自身也自相矛盾
（`_specs/S24.md:21` 既说「各伸出 2 栏」又说「宽度比 5:3」）；实现只兑现了 5:3。

**改写建议**：「8 栏加中轴，每层按 5fr:3fr 左右对切、最多 4 层，窄侧下沉 24px，
支线由 2.5px 递减到 1、0.6、0.4px、节点处靠孢子形留白断开——深度由层数与线宽读出。」

### S12（轻）、S19（干净）

- **S12**：7 处 opening 每行块数 3/2/1/1，与「按 3/2/1/1 递减」**吻合**（实测 grid-row：
  row1 有 op-01/02/03，row2 有 04/05，row3 有 06，row4 有 07）；`12/28/44px` 三级＝`--g1/--g2/--g3`（`:23-25`）；
  `0.5px 翻边`＝`.knock{padding:0.5px}`（`:225`）；45°/135° 两条 `--stripe` 都在。
  **轻度过失**：「切角 30px」只对 5/7 成立——`op-03` 覆盖为 `--cut:36px`、`op-07` 为 `--cut:16px`（`:265`、`:269`）。
- **S19**：20 抽屉 / 5 行 / 宽档 2·3·4 栏（`--s` 值恰为 5×2、10×3、5×4）/ 面板高 24px（`:196`）/
  下移 24px（`:244`）/ 开口 144 vs 卡面 168（`:207`、`:216`）/ 线宽仅 0.4 与 0.8（`:297-298`）——
  **全部核实为真，无新错误**。（`--s:5`、`--s:7` 属于 `.xc` 图版组件，不是抽屉，未混入计数。）

## 5. 真错误数：**7 条硬错 + 4 条轻错**，不是 5 条

- **原五条**：S17、S10 成立；S09 是「含糊而非虚假」（PARTLY TRUE）；S03、S07 成立且最重。
- **抽检新增 3 条硬错**：S01「压住 3 行正文」、S24「留 2px 缺口」、S24「每层各伸 2 栏」。
- **4 条轻错**：S12「切角 30px」、S17「孔径 1.2px」「行高 24px」、S03「游标随焦距比移动」（凭空字段）。

## 6. 根因（比修五条句子更重要）

`dna.mechanism` 不是从实现里重新测出来的，而是**逐字复制 spec 的字段 1-附**：

```
$ for f in _specs/S03.md deliverables/04-schemes-01-10.md _prompts/dna-raw.json ...; do grep -l "右侧 9 栏的高度" $f; done
prototypes/_selection/prompts.js  prototypes/_prompts/dna-clean.json  prototypes/_prompts/dna-raw.json
prototypes/_specs/S03.md  deliverables/04-schemes-01-10.md
```

五条错句各自同时存在于 **5 个文件**（`prompts.js`、`dna-clean.json`、`dna-raw.json`、
`_specs/Sxx.md`、`deliverables/04-schemes-01-10.md`）——所以是「规格先写、实现后改、句子不跟」的
系统性漂移，不是五处独立笔误。这也解释了为什么 CSS 注释里会出现与代码互相打脸的
「12 栏/9 栏」「5 栏/7 栏」：注释抄的是 spec，代码走的是另一条路。

修法建议：这五句（以及抽检出的三句）应以**实现**为唯一事实源重写，
并由一条闸门比对 mechanism 里的每个带单位数字与 CSS/HTML 实测值，避免下一次 spec 再漂。
