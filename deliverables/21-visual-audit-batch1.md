### 0.2 `file://` 下 CSS `mask-image: url(...)` 整块失效 —— 会凭空造出"整块内容消失"

- 现象：S04 的 9 张纸块、S07 的书口毛边在 `file://` 下**整块不可见**；同一批页面在 HTTP 下完全正常。
- 归因：MDN 明确写出 `mask-image` 的 `<image>` 源只接受 http/https，`file://`（相对或绝对）会被 CORS 拒绝并**按全透明黑处理**——元素被整体蒙掉。
  <https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/mask-image>
- A/B 实证（同一页同一次会话）：`mask-image` 存在时，S04 首块纸块所在区域 **100% 为单色 `#f0e2c8`（图像内仅 1 种颜色）**；置为 `none` 后同一区域出现 **5813 种颜色**、海报正常绘制。
- **决定性对照**（同页同尺寸，只换协议）：
  `http://127.0.0.1:8791/prototypes/S04-mango-collage-wall/index.html` → 该区域 5818 种颜色（正常）
  `file:///D:/Web/style/prototypes/S04-mango-collage-wall/index.html` → 2 种颜色（全空）

**结论：`file://` 采集的图不能用来判定"图版缺失 / 整块空白"。** 本报告正文的图版相关结论全部基于 HTTP 采集。
（附带发现：`--virtual-time-budget` 下 CSS 动画可能停在起点——用 `--dump-dom` 探针读 S04 `.slip` 得到 `opacity:0`、`transform:none`，而 CDP 实时查询同一元素是 `opacity:1`、动画 `finished`。凡"整块消失"类现象我都不采信 CLI 单点。）

**【S01-F1｜明显｜红楔压住正文（1440 与 768 两档）】**
- 现象：报头的红色楔形块（`.wedge`）盖住了第 2、3 栏的正文。

- 修法：把 `.wedge` 挪到正文层之下（或给 `.columns` 建层叠上下文并置于 `.wedge` 之上）；或按 CSS 注释里写的原意，在 <1023 档把 `clip-path` 收窄到只扫过 `.slug-slot` 的 74px 留白。

**【S01-F2｜明显｜红底折角栏内同一行文字混色，暗字落在红上 2.89:1】**

- 修法：补一条 `.col-head-red .col-meta { color: var(--paper); }`。

**【S01-F3｜轻微｜390 档报头信息行行尾悬挂分隔符】**

## 3. 我最不确定的 3 条

1. **S02 的 `.leak` 到底算不算缺陷？**（最不确定）
   不确定在哪：落点由 `日期 % 7` 决定，我把 7 个落点全跑了一遍（`q-s02leak.js`），1440 档 **5/7** 落点压到正文、390 档 **7/7** 压到正文——所以"今天恰好压到"不是巧合。但我无法排除作者**就是要**让补丁随机落到任何地方（包括文字上），把它当作"档案被涂改"的叙事。
   需要什么证据才能定：让作者确认 `.leak` 是否允许压文字；或者一个"落点必须避开文字盒"的规格约束。
   在此之前的处置：按"人看着不对"的标准报为**明显**（被盖的字是 1:1 同色，完全读不出）。

2. **S03 的"判读列被阶梯挤到 28px"是意图还是副作用？**
   不确定在哪：`style.css:267` 的注释明确写了"逐条右缩 12px 的阶梯错位，缩到第 6 条停止"，说明阶梯是有意设计；但没有任何地方说"判读列每行 1–2 字"。我判断这是阶梯实现方式（改 padding-right）的副作用，而不是意图本身。
   需要什么证据才能定：设计者确认阶梯的**视觉目标**——如果目标只是"整条读数卡逐级右移"，那改到行级 padding/translate 即可，我的报法成立；如果目标就是"文字列越来越窄"，那这条要降级或撤回。

3. **`file://` 与 HTTP 的差异会不会影响最终验收？**
