## 结论

**规格里写的面积占比（「背景 62%、主色 14%」）与页面真实像素占比相差一个数量级。把这种数字补进提示词，等于教 AI 复制一个原型自己都不遵守的规格。**

| 案 | 规格声称 | 真实像素实测 | 差距 |
|---|---|---|---|
| **S21** | 主色 `#3E3A34` **42%**、背景 `#E4DCC9` **34%** | 背景 **85.3%**、主色 **11.4%** | 主色虚报 3.7 倍 |
| **S16** | 主色 `#C52C0F` **41.6%**、背景 `#F7EBCF` **16.2%** | 背景 **92.2%**、主色 **1.4%** | 主色虚报 **30 倍** |
| **S07** | 背景 `#E7E7E0` **56%** | **90.2%** | 背景少报 1.6 倍 |
| **S08** | 背景 `#120C08` **58%** | **88.4%** | 少报 1.5 倍 |
| **S10** | 背景 `#F2EFE8` **58%** | **89.0%** | 少报 1.5 倍 |
| **S25** | 背景 `#E8E4DE` **48%**、主色 `#914A27` 26% | 背景 **73.6%**、主色 **10.6%** | 主色少报 2.5 倍 |

## 我踩到的第 7 个坑：用「元素数」当面积代理

第一版（`LEAD-color-ratio.mjs`）我用「有多少个元素用了这个色」当占比代理，结果荒谬：

```
S22  #2e2a24: 声称 14% → "实际" 86.5%  （差 72.5pp）
```

原因很直白：**文字色会被很多元素继承**（每个 `<p>`、`<span>` 都算一个），但文字占的像素面积很小；**背景色只有 1 个元素**，却占满整屏。

这个代理在方向上是反的。

**修正**：用 CDP `Page.captureScreenshot` 截屏，逐像素解 PNG，统计颜色直方图。这才是"配比"的正确度量。

---

## 修正后的方法：像素直方图 + LAB 距离归并

### 第一步：截屏统计

`LEAD-pixel-ratio.mjs` 在 1440×900 截屏，自己写了个 PNG 解码器（`zlib.inflateSync` + 5 种 filter 还原），逐像素统计。

**结果暴露了一个新问题——颜色种类数差异巨大：**

| 案 | 独立像素色数 |
|---|---|
| S25 | **840** |
| S12 | 890 |
| S10 | 2,219 |
| S07 | 2,713 |
| … | … |
| S24 | 47,755 |
| S30 | **87,947** |

**相差 105 倍。** 原因是抗锯齿、渐变、纹理、照片。直接数 hex 毫无意义。

### 第二步：按 CIE76 距离归并到调色板色

`LEAD-pixel-mapped.mjs` 把每个像素色归到最近的调色板色（Lab 空间欧氏距离，阈值 25，超过则算"集合外"）。

## 关键发现：规格的占比是「设计意图」，不是「实测」

这个差距不是 bug，而是**两种不同性质的数据混在了一起**：

- 规格字段 3 的「62% / 14% / 21% / 3%」是**设计意图**：作者在规划时希望这个色占多少视觉重量。
- 实际渲染出来的占比取决于内容量、留白、版面结构。

**S16 最能说明问题**：声称主色 `#C52C0F` 占 41.6%，实测只有 1.4%。看 S16 的 CSS 就明白了——朱红只用在少数强调元素上（一条斜排的标题、几个标记），而 `#F7EBCF` 宣言纸色铺满整个页面（92.2%）。

规格里写「朱红 41.6%」是一个**愿望**，实现出来是 1.4%。如果把这个数字写进提示词，AI 会试图把页面刷成 41.6% 的朱红——那会是一个完全不同的设计。

### 更严重的是：规格声明的面积和本身就不等于 100

| 案 | Σ |
|---|---|
| S11 | 68.6% |
| S12 | 67% |
| S13 | 80.8% |
| S14 | 75% |
| S15 | 56.5% |
| S16 | **123.8%** |
| S17 | 82.8% |
| S18 | 50.6% |
| S19 | 89.5% |
| S20 | 78.1% |
| S26 | **121.7%** |

11/30 案的声明面积和不等于 100（S16 和 S26 甚至超过 100）。

**这些数字里有相当一部分不是百分比，是我把「色相 44.3°」「饱和 10.1%」「明度 84.9%」这些 HSL 分量误当成了面积占比。** 这是我又一个解析错误——但反过来说明：**规格里的这些百分号本身就在混用多种含义**，任何自动抽取都会出错。

## 对「补配比」决策的影响

用户已裁决方向包含「补配比」。基于实测：

| 原设想 | 实测后 |
|---|---|
| 把规格的面积占比补进提示词 | 规格占比与真实像素差 1.5–30 倍，且有 11/30 案 Σ≠100% |
| 用真实像素占比替代 | 可行，但需要先决定"首屏还是全页""含不含照片"——口径未定 |
| 提示词给「主色 60/30/10」这类经典比例 | 检索 Agent 查到**零证据**支撑 AI 遵循，且该术语是 over-fitted，可能触发套路解 |

**我的判断**：配比这件事，**先别做**。理由不是"没价值"，而是：
1. 现有数据源（规格）的占比不可信（虚报 30 倍）
2. 真实像素占比的口径还没定（首屏 / 全页 / 含不含图）
3. 检索 Agent 查到「60-30-10」在 AI 生成场景零证据
4. 在已经过载的约束集（20 条，CSE 研究显示 >10 条就进崩塌区）上再加数条

**如果一定要做**，正确做法是：把「主色应该占视觉主导」这种定性关系写进去，而不是给具体百分比。
