### 我一度误判为回归的两处，复核后都是正确的

#### S04：我看到 diff 里 `72px → 40px`，以为是回归

复核 `prototypes/S04-mango-collage-wall/style.css`：

```
46: .board h1{
47:   font-size:72px; ...        ← 桌面值
...
206: @media (max-width:899px){
219:   .board h1{font-size:40px}  ← 窄屏覆盖
```

**执行 Agent 最终交付的是 72px**（见全量清单）。我看到的 40px 是它中途状态——它在自我纠正。

#### S12：`54px → 88px`，是不是取了窄档值？

复核 `prototypes/S12-lime-knockout-wall/style.css`：

```
110: h1 {
111:   font-size: clamp(54px, 6.6vw, 104px);   ← 基础（<1440 档）
...
388: /* ── 断点一：≥1440px 保持 8 栏与满屏墙面（默认样式即此档） ────── */
389: @media (min-width: 1440px) {
391:   h1 { font-size: clamp(88px, 6.6vw, 112px); }
392: }
```

**注释明写「≥1440px … 默认样式即此档」。** 我们的测量视口是 1440，所以取 88px 是对的。

### 唯一的隐患：S12 是 30 案里唯一取 `min-width` 媒体查询的

我的检查脚本扫出：

```
⚠ S12  h1Size=clamp(88px, 6.6vw, 112px)  该值只出现在 @media 内:
     L391 [@media (min-width: 1440px) {] h1 { font-size: clamp(88px, 6.6vw, 112px); }
```

其余 29 案的 h1Size 都来自基础规则。S12 取 1440 档是特例但正确——**需要在 `h1SizeWhy` 里说明这是 `min-width` 覆盖，否则下一个人会以为抽错了**。

### 新增的 `h1SizeWhy` 字段是好的设计

每条都写明「哪个选择器的哪条规则、什么口径」，例如：

```
S01  "h1 后代规则 `.masthead h1` 声明 var(--fs-h1) → 展开为 clamp(48px, 6.67vw, 96px)（桌面 1440px 口径）"
```

这解决了一个真问题：**h1Size 这种值最容易被误抽，有了溯源字段就能审。**

## 三、闸门已建成并跑通

`prototypes/_build/check-prompts.mjs`（新增，~330 行）。

### 设计原则（全部来自本轮实测教训）

| 原则 | 依据 |
|---|---|
| **独立来源对账** | 提示词的内容必须与 `style.css` 的真实声明对上，不能与 `dna-clean.json` 对上——后者就是提示词的来源，自己对自己没意义 |
| **纯文本、零浏览器** | 秒级跑完。上一轮 3 案端到端花了 3 个 Agent，统计上证不了什么（要证 ≥90% 需 29 次）；文本自洽性可以 30/30 全量 |
| **只报可判定的** | 不判「像不像」，只判「说的和做的一致不一致」 |

### 立刻抓到的三条真问题

1. **4 案线宽声称值在 CSS 里查不到**——包括 `1.36px`、`3.6px` 这种明显是亚像素缩放残渣的值。

3. **25 案措辞自相矛盾**——列了 3–9 级却说「不要自创第三级」。

### 闸门的价值已经体现

它在我还没提交任何改动时，就把「30/30 提示词都点名 `#6366F1`」这个我此前判断为「只有 1–2 句」的事实纠正了。
