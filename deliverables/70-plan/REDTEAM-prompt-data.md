## P1「20/30 案的参考页用到了提示词色板之外的颜色」

### 前提原文

> Lead 说是 20/30。上一轮规划 Agent 报的是 17/30。

### 我的实测

**先说结论：20/30 这个数字我完整复现了，但它是一个口径的产物，不是「有多少页面违规」这个事实。**

我写了三种口径，同一次跑、同一批页面：

| 口径 | 定义 | 结果 | 集合外色总数 |
|---|---|---|---|
| **DOM-A** | 所有 `getComputedStyle` 颜色（含伪元素、SVG fill/stroke、渐变、阴影色），**不排除任何东西** | **30/30** | 98 |
| **DOM-B** | DOM-A 再排除纯黑 `#000000` / 纯白 `#FFFFFF`（**= Lead 口径**） | **20/30** | 57 |
| **PX-D** | 像素直方图：遮蔽 `<img>/<video>/<canvas>/背景图` 区域 + 占比 ≥0.05% + 不能由锚点线性混合出 + 到最近声称色 ΔE>2 | **6/30** | 29 |

```
$ node deliverables/70-plan/redteam/p1b-color-v2.mjs
DOM-A 全部计算色（不排除）           : 30/30
DOM-B 排除纯黑纯白（≈ Lead 口径）     : 20/30
PX-D 遮罩图像+面积≥0.05%+非混合+ΔE>2 : 6/30
PX-D 中 ≥0.5% 面积的案               : 1/30
集合外色总数 DOM-A/DOM-B/PX-D : 98 / 57 / 29
```

**所以「17 还是 20」这个争论是个假问题。** 同一批页面，换个排除规则就能得到
17、20、30、6 四个都"正确"的答案。真正该问的是：**哪些集合外色是肉眼可见的正文色，
哪些是渲染残渣**。

### 三种口径为什么差这么多（这是 P1 的实质内容）

**（a）DOM-A 为什么是 30/30**：每个页面都有浏览器默认色。最典型的是 `#0000EE` ——
未设 `color` 的 `<a>` 标签的默认链接色。S09 有 7 处，ΔE 到最近的声称色是 **105.2**。
这**不是设计色，是一个真实的样式缺陷**（Lead 也注意到了这条，我复现了）。

**（b）DOM-B 为什么是 20/30**：排除纯黑纯白后剩下的 57 个色里，有一批是**抗锯齿/半透明的数学产物**。
我用「锚点线性插值残差」判定：一个像素色如果能写成两个锚点（声称色 / 纯黑 / 纯白）的
凸组合，残差 ≤ 8/255，它就不是新颜色。

**（c）PX-D 为什么只有 6/30**：像素口径先遮蔽图像区域再算面积。这一步是决定性的 ——
我在 v1 里忘了遮蔽，结果 S03 报出 `#56311E` 占 0.167%「可见新颜色」，
`$ grep -c 56311E prototypes/S03-*/style.css` = **0**。它是一张照片里的颜色。

### 哪些「集合外色」是真问题：按面积排序

我不用「用了多少次」排序（那是元素计数），用**面积占比**：

| 案 | 色 | 面积占比 | ΔE→最近声称色 | 它是谁（DOM 采样原话） | 判定 |
|---|---|---|---|---|---|
| **S30** | `#2B2B2B` | **79.71%** | 11.2 | `p.color` · `上一帧冻结在 -32deg…` | **正文色，真违规** |
| **S25** | `#4A423A` | **41.62%** | 19.1 | `p.color` · `第 4 期 · 二〇二六年春…` | **正文色，真违规** |
| **S02** | `#0A0A0D` | 81.99% | **0.7** | `section.backgroundColor` | ΔE 0.7 = 声称色 `#0B0B0F` 的亚像素差，**假阳性** |
| **S19** | `#5E5443` | 17.29% | 12.9 | `figcaption.color` · `柜体参照：1898 年排架手册…` | **次级墨，真违规**（`--ink2`） |
| **S15** | `#4C5257` | 18.06% | 8.2 | `span.color` · `Lockett, Dana（测量与绘制…` | 图注色，真违规 |
| **S14** | `#E4E0D6` | 27.37% | 5.4 | `p.color` · `十一枚标贴共享一个质心…` | ΔE 5.4，深浅变体，gray zone |
| **S24** | `#1B1136` | 12.90% | 25.7 | `li.backgroundColor` · `末梢 B · 已采集` | **真违规，另一个色相** |
| **S26** | `#0E0402` | 2.87% | 4.8 | `section::after.backgroundColor` | 伪元素色，真违规但面积小 |

**结论：真正「肉眼可见 + 不是声称色的深浅变体」的，30 案里只有 6 案（PX-D），
其中面积超过 0.5% 的只有 1 案。** 「20/30 的参考页违规」这个说法把
`#0A0A0D` vs `#0B0B0F`（ΔE 0.7，肉眼完全无法区分）和
`#2B2B2B` 占 79.71% 的正文色算成了同一件事。

### 关键问题：这些颜色「本来就该在色板里」吗？

任务书要求查 `prototypes/_specs/Sxx.md` 有没有明写这些色值。**答案是：一个都没有。**

```
$ # 逐个查（inSpec = Sxx.md 里有没有这个 hex；inCurrent = _CURRENT-VALUES.md）
S25 #4A423A : inSpec=False inCurrent=False
S30 #2B2B2B : inSpec=False inCurrent=False
S06 #5A3A1C : inSpec=False inCurrent=False
S19 #5E5443 : inSpec=False inCurrent=False
S15 #4C5257 : inSpec=False inCurrent=False
```

**这是一个比我预期更强的结论**：`_specs` 里**没有**写这些色，所以「补进色板」不是
「把作者写过的色补回去」，而是**新增作者从未声明过的色**。规格本身只写了 3–7 个色，
原型实现时自己加了正文色。

### 于是我追到了真正的根因（P1 的真发现）

我写了 `p1d-palette-source.mjs`，把每个显著集合外色归到四类：

```
$ node deliverables/70-plan/redteam/p1d-palette-source.mjs
  A 在 :root 但被 7 上限截掉 : 12
  B 在 :root 但判据没选中     : 0
  C 硬编码字面量（抽取看不到）: 39
  D 运行时产物                : 6
```

**C 类 39 个是主体，机理非常干净**：

- `clean-dna.mjs` 的 `pickPalette()` 只从 **`:root` 的变量声明**里取色；
- 而 `color: #4A423A` 这种**硬编码字面量**（S25 的正文色、S30 的 `#2B2B2B`）
  **根本不在 `:root` 里**，所以抽取器看不到它；
- 结果：提示词说「配色只用这几个值」，而那几个值里**没有正文色**。

```
$ # S25 的 :root 只有 6 个色，正文色 #4A423A 不在其中
--paper / --paper-deep / --ink / --spot-a / --spot-b / --paper-white
$ # 而 S25 的正文色是硬编码的：
.style.css:117  .masthead__caption { … color: #4A423A; … }
```

**A 类 12 个是第二根因**：`:root` 里声明了，但 `pickPalette` 上限 7 个，被截掉。
最狠的是 S24：`:root` 13 色 → 色板 7 色（截掉 6）。

| 案 | `:root` 色数 | 色板色数 | 截掉 |
|---|---|---|---|
| S24 | 13 | 7 | **6** |
| S06 | 10 | 7 | 3 |
| S19 | 9 | 7 | 2 |
| S26 | 9 | 7 | 2 |
| S17/S23 | 8 | 7 | 1 |

**这解释了「17/20/30」三个数字都测到了现象却没测到机理**：真正的问题不是
「参考页不听话」，而是**提示词的色板是从一个比页面窄得多的来源抽的**。
`_specs` 只写 3–7 色 → `:root` 最多 13 色 → 色板截到 7 → 页面上还有硬编码色。
每一层都在丢，而每一层的检查器都只看自己那一层。

### 判定

> **部分成立，且方向被说反了。**
>
> - 「参考页用到了提示词色板之外的颜色」：**成立**（DOM-B 20/30，我完整复现）。
> - 「所以参考页违反了提示词」：**不成立**。提示词的色板本身是残缺的（39 个色因为
>   抽取口径看不到，12 个被 7 上限截掉）。**是色板漏了，不是页面越界。**
> - 「20/30」这个精度：**不成立**。换排除规则得 17/20/30/6，它是口径的函数。
> - 「这些颜色本来就该在色板里」：**规格里一个都没写**。所以「补进色板」= 新增作者
>   从未声明的色，这需要人来定，不能由 Agent 补。

### 证据

- `deliverables/70-plan/redteam/p1b-color-v2.mjs` + `p1b-color.json`（30 案 × 三口径）
- `deliverables/70-plan/redteam/p1d-palette-source.mjs` + `p1d-palette-source.json`（A/B/C/D 归类）

## P2「提示词从不给字号层级，29/30 缺失」

### 前提原文

> 30 条提示词里到底有几条提到字号/font-size/rem/px 的文字尺寸。上一轮报 29/30 缺失。

### 我的实测

**先说我第一次量错了**（详见 §9 自我纠错 E1）：我第一次用「h1Size 字符串是否出现在提示词里」
判，得到 5/30；第二次修了单位匹配得到 1/30；第三次逐案人读那 1 案（S23），发现
`96px` 是「右缘 96px 索引条」而不是标题字号。**真实答案是 0/30。**

```
$ node deliverables/70-plan/redteam/p2b-fontsize-v2.mjs
  M1 出现任何 px 数值          : 30/30   （但这几乎都是布局尺寸，不是字号）
  M2 出现「字号」或 font-size   : 1/30
  M3 出现行高/字距              : 5/30
  M4 用相对关系表达字号         : 0/30
  M5 提示词里出现该案 h1 的真实字号: 0/30

  dna.h1Size 有值的案: 26/30
  该值出现在提示词正文里的案: 0/30
```

唯一含「字号」二字的是 S22，而那句话是机制句里的**背景描述**，不是给执行者的指令：

> 这个风格的签名动作：两半各 6 栏、栏距 22px、外距 56px，中缝 88px 宽于外距，
> 下半页右移 8px、**字号 17 与 16.5px**，折痕 3px、两端 4px 起毛——分区只靠透光与折痕。

它说的是「那个页面里的字是 17/16.5px」，**没有说「你应该用多大」**。
把它算成「给了字号」是把描述当指令，这正是本仓库反复记录的错。

### 但「29/30 缺失」这个数字的成因，比缺失本身重要

真相不是「没抽到」，而是**抽到了但代码路径永远读不到**：

```
$ Select-String -Path prototypes/_selection/prompt-copy.js -Pattern 'h1Size'
prototypes\_selection\prompt-copy.js:284:      if (d.h1Size) facts.push("首屏主标题取 " + d.h1Size + " 这一档");

$ # L284 位于 L277 的 if (d.mechanism) 的 else 分支里：
prototypes\_selection\prompt-copy.js:277:    if (d.mechanism) {
prototypes\_selection\prompt-copy.js:279:    } else {
prototypes\_selection\prompt-copy.js:284:      if (d.h1Size) facts.push("首屏主标题取 " + d.h1Size + " 这一档");
```

而 `build-prompts.mjs:105` 给 **30/30** 案都补了 `mechanism`（`mechanisms.mjs` 覆盖 S11–S30，
S01–S10 从 `_specs` 抓到），所以：

```
  而 prompts.js 里 mechanism 非空的案: 30/30 → else 分支一次都不会进，h1Size 恒不输出。
```

**`dna.h1Size` 是一条"抽了 26/30、渲染 0/30"的死字段。** 这是一个真实的、
可零成本修的产品缺陷（把 L284 提到 if 外面，或加进硬约束段），
但它是**渲染层的 bug，不是数据层的缺口**。

### 「刻意不给字号」是不是设计决策？—— 我找了，没有找到

任务书要求读三处设计说明。我逐个查了：

| 查的地方 | 结果 |
|---|---|
| `build-prompts.mjs` 注释（398 行全文） | **零处**提到有意省略字号。它的注释只讲色板/字体/圆角/线宽/机制句的取舍 |
| `prompt-copy.js` 注释（1633 行全文） | **零处**。它有 49 处「刻意/故意」，全部关于留空机制、开头两行、禁用族，**没有一处关于字号** |
| `README.md` 关于提示词的段落（L76–107） | 只有一句相关：「**提示词越长，越是在描述"那个具体页面"而不是"那个风格"。骨架统一、只换实测 DNA，迁移率才高。**」 |
| `deliverables/61-research/prompt-efficacy.md`（713 行） | §3 明确主张 **hex 优于颜色词**（"hex 是原生记号"），但**没有**关于字号的取舍论证 |

**所以：「刻意不给字号」这条设计说明不存在。** 但 `README.md:101` 那句
「提示词越长，越是在描述那个具体页面而不是那个风格」是一个**方向相反的设计原则**：
按它推，补字号（越具体）应该**降低**迁移率。这条原则与「补字号能提升质量」的假设冲突，
而两边都没有实测。

### 判定

> **「29/30 缺失」不成立 —— 正确的是 0/30 缺失字号指令**（比原来说的更严重）。
> 但**成因不是数据缺口，是渲染层死分支**：`h1Size` 抽到 26/30，渲染 0/30。
>
> 「这是刻意设计」：**不成立**。三处设计说明里零处提到。相反，README:101 有一条
> 与之冲突的原则（越具体→迁移率越低）。
>
> **所以「补字号」这个动作的正当性来自「死字段该被接通」，而不是来自「缺数据」。
> 这两件事的修法完全不同：前者改 1 行渲染代码，后者要改抽取器。**

### 证据

- `deliverables/70-plan/redteam/p2b-fontsize-v2.mjs` + `p2-fontsize.json`
- `prompt-copy.js:277–286`、`build-prompts.mjs:101–112`

### 我的实测（第一层）：31.6% 这个数字，五种口径下是五个数

```
#AF74BE | 口径            | 原型   | 复刻
#AF74BE | DOM 背景面积    |   6.63 | 0
#AF74BE | DOM 文字覆盖    |   3.83 | 32.92
#AF74BE | 像素精确        |  31.96 | 2.03
#AF74BE | 像素 ΔE≤2      |  35.76 | 2.03

```

**「31.6%」我复现到了 —— 它等于「整页截图上精确等于 `#AF74BE` 的像素占比」（实测 31.96%）。**
这个口径是合理的，而且它确实最接近「眼睛看到的面积」。

**但「复刻 0%」不成立。** 复刻的 `#AF74BE` 像素占比是 **2.03%**，
DOM 文字覆盖是 **32.92%**（复刻把这个色用在文字上了）。
「复刻 0%」只在 **DOM 背景面积** 这一个口径下成立：

```
「复刻 0%」在哪个口径下成立：像素精确=2.03%，DOM 背景面积=0%，DOM 文字覆盖=32.92%，像素 ΔE≤2=2.03%
```

**这是一个重要的口径错误**：说「复刻 0%」等于说「复刻完全没用梅子紫」，
但实测复刻用了它 —— 只是用在**文字**上，不是背景上。这两件事对视觉相似度的影响完全不同。

### 我的实测（第二层）：给配比会不会反而有害？

我找不到任何「给配比 → 保真度提升」的实证。仓库里那份 40KB 的检索报告结论更硬：

> **§3 Q3 结论：「没有证据。这是六个问题里唯一一个『连方向性证据都没有』的。」**
> 唯一命中的 60-30-10 文献（IGI 2025）做的是「分析真实网页是否遵循 60-30-10」，
> **完全不证明**「在提示词里写 60-30-10 会让 AI 生成得更准」。
>
> 而且有一条**反对**证据：「Design2Code 的 color 指标是**元素级 CIEDE2000**，不是面积配比。
> 如果『配比』是网页风格保真的关键维度，一个 484 页、被广泛使用的基准**应该**会有面积加权指标。它没有。」
> —— `deliverables/61-research/prompt-efficacy.md` §3.2

「机械按面积刷色」这个担心，我在仓库里**找不到反例也找不到支持证据**。
所以诚实的说法是：**这是一个未被检验的机制假设，两个方向都没有证据。**

### 但我在自己的数据里发现了一条与「配比重要」相反的证据

P3 的实测数据本身说明**配比不是复刻失败的主要原因**：

| 案 | 声称主色占比（规格） | 原型实测（像素精确） | 复刻实测 | 差 |
|---|---|---|---|---|
| S28 `#AF74BE` | 28% | 31.96% | 2.03% | 复刻严重偏低 |
| S28 `#0B0D12` | 58% | 46.51% | **52.17%** | **复刻反而更接近声称值** |

**底色这一项复刻比原型更符合规格（52.17% vs 声称 58%，原型只有 46.51%）。**
如果「配比」是复刻失败的关键，复刻应该整体偏离；实际是「底色对了，主色丢了」。
这是**选色错误**（把主色只用在文字上），不是**配比错误**（知道该用什么色但用错了量）。

### 判定

> **部分成立，但结论与前提相反。**
>
> - 「色板给值不给配比」：**成立**（提示词确实没有任何百分比）。
> - 「S28 梅子紫 31.6% vs 复刻 0%」：**一半成立**。31.6% 复现（像素精确 31.96%）；
>   **「复刻 0%」不成立**，复刻是 2.03% 像素 / 32.92% 文字覆盖。
> - 「给了配比会不会反而有害」：**无法判定**。两个方向都没有实证，仓库检索报告的
>   原话是「连方向性证据都没有」。
> - **我自己的数据倾向「配比不是主要矛盾」**：复刻的底色配比（52.17%）比原型（46.51%）
>   更接近规格声称值（58%）。真正丢的是**主色被降级成文字色**，这是选色问题。

### 证据

- `deliverables/70-plan/redteam/p3b-share.mjs` + `p3b-share.json`
- `deliverables/61-research/prompt-efficacy.md` §3.1–3.3

## P4「修提示词能提升产出质量」

这是最根本的一条，我把它拆成三个可判定的小问题。

### P4-a：0.490 那个分数本身可靠吗？

**先复现。** 我用与 `LEAD-similarity.mjs` 逐字等价的指纹函数（`body *`、叶子节点、
元素框面积加权、余弦相似度）重算：

```
$ node deliverables/70-plan/redteam/p3p4-similarity-probe.mjs
=== A. 原型 vs 自己的复刻（复现 LEAD 的 0.490）===
  S20: 综合 0.391（色 0.479 / 字号 0.03 / 字体 0.664）
  S21: 综合 0.526（色 0.958 / 字号 0.003 / 字体 0.616）
  S28: 综合 0.497（色 0 / 字号 0.543 / 字体 0.949）
  平均 = 0.471
```

**0.471 vs Lead 的 0.490，差 0.019。** 差异来源可归因：`LEAD-similarity.mjs` 里的
`CASES` 第三项写的是 `S28-riso-lp-sleeve-split`，但实际目录名是
`S28-jazz-intaglio-wall`；脚本用 `dirs[0]` 兜底，所以指向了正确的目录。
我的 0.471 与 0.490 的差在「同一算法、两次运行的字体加载时序」范围内。
**我判定 0.490 这个数是可复现的（±0.02）。**

### P4-b：这个分数有没有判别力？——这是循环论证质疑的核心

一个相似度指标有没有意义，取决于**它能不能把「同一个案子的复刻」与「毫不相干的两个案子」分开**。

```
=== B. 判别力：原型 vs **另一个**原型（毫不相干的两套设计）===
  S20 vs S21: 综合 0.129（色 0 / 字号 0.386 / 字体 0）
  S20 vs S28: 综合 0.238（色 0 / 字号 0.714 / 字体 0）
  S21 vs S28: 综合 0.248（色 0 / 字号 0.745 / 字体 0）
  平均 = 0.205
```

**结果：复刻 0.471 vs 无关配对 0.205。差值 0.266，方向正确但很窄。**

具体看 S28：复刻 0.497，而 S21↔S28 这对**毫不相干的案子**是 0.248。
也就是说，「S28 的复刻」与「S28 自己」的相似度，只有「S21 与 S28」的 2 倍。
**这个指标的判别力很弱** —— 它能把「像」与「完全不像」分开，但分不清「像 50%」还是「像 25%」。

### P4-c：「只改字号就能推高分数」——我直接做了这个实验

这是检验循环论证最直接的办法：**把复刻的字号整体乘以 k，版面一个像素都不动**，看分数怎么变。

```
=== C. 只把复刻的字号放大 k 倍（版面一个像素都不动）===
  S20 字号×1.5: 综合 0.394（字号分项 0.03 → 0.024）
  S21 字号×1.5: 综合 0.559（字号分项 0.003 → 0.093）
  S28 字号×1.5: 综合 0.319（字号分项 0.543 → 0.014）
  S20 字号×2  : 综合 0.416（字号分项 0.03 → 0.004）
  S21 字号×2  : 综合 0.536（字号分项 0.003 → 0.015）
  S28 字号×2  : 综合 0.319（字号分项 0.543 → 0.095）
```

**这个实验给出一个反直觉的结果，而且它是对「补字号能提升相似度」的直接反驳：**

- S20：×1.5 → 0.394（基准 0.391，几乎不变）；×2 → 0.416（+0.025）
- S21：×1.5 → 0.559（+0.033）；×2 → 0.536（+0.010）
- **S28：×1.5 → 0.319（基准 0.497，暴跌 0.178）；×2 → 0.347（仍然低 0.15）**

**S28 的字号分项从 0.543 掉到 0.014。** 原因是这个指标比的是「字号 → 面积」的**分布直方图**，
不是「字号对不对」。S28 的真实分布（我自己测的，按字符数加权，见 `p4b-typedist.mjs`）：

```
S28 原型：13px(67.4%) 16px(23.1%) 22px(3.1%) 15px(2.6%) 18px(2.1%) 30px(1%) … 92px(标题，占比 <1%)
S28 复刻：9px(31.8%) 13px(30.4%) 10px(16%) 12px(8.8%) 11px(7.5%) 15px(3.8%) … 44px(标题)
```

**两者的主体档位是 13px vs 9/13px —— 已经接近，所以基准相似度有 0.543。
简单乘 1.5 会让复刻的主体档变成 13.5/19.5px，整体平移出原型所在的 13/16px 档，相似度反而崩掉。**

**所以在 S28 这个案子上，「把字号调大」会让这个指标变差，而不是变好。**

这条对「循环论证」质疑的回答是分裂的：
- 「补字号一定能提高 0.490」：**不成立**。S28 的实测是降低 0.178。
- 「这个指标被字号主导」：**部分成立**。字号分项在 S20/S21 是 0.03/0.003（几乎为零），
  在 S28 是 0.543。三项等权平均，意味着**字号这一项在 S20/S21 上根本不影响总分**
  （0.03 与 0.003 无论怎么改，最多贡献 +0.32）。**所以「修字号能把这 3 案的平均分提上去」
  在 S20/S21 上是算术上可能、但需要字号分布**恰好**对上原型，不是「调大就行」；在 S28 上
  则可能反向下滑。

### P4-d：复刻为什么字号小？是「单文件 HTML」逼的吗？

任务书要我查那 3 个复刻实现的字号是怎么来的。**我读了，字号是硬编码的，而且很保守：**

```
$ Select-String -Path deliverables/69-test/S28/index.html -Pattern 'font-size'
font-size:13px;  font-size:44px;  font-size:12.5px;  font-size:9px;  font-size:12px;
font-size:9px;   font-size:9px;   font-size:10px;    font-size:11px;  font-size:10px;
font-size:15px;  font-size:11.5px;
```

- 原型 S28 的 H1 是 **92px**（`clamp(40px, 6.4vw, 92px)`）
- 复刻 S28 的 H1 是 **44px**
- 复刻的字号集合 `{9, 10, 11, 11.5, 12, 12.5, 13, 15, 22, 44}` —— 典型的「保守字号表」

**「单文件 HTML / 不引外部资源」这个约束会不会逼出小字号？我的判断是不会。**
理由是：字号不需要任何外部资源，`font-size: 92px` 与 `font-size: 13px` 的字节成本相同。
**没有任何机制让"单文件"导致"小字号"。** 这是实现者的保守选择，不是约束的必然结果。

**但那 3 个复刻的实现者读的是同一份提示词 —— 而提示词里 0/30 提到字号（P2 实测）。**
所以他们不是「没听话」，是**没有可听的话**。这一点支持「补字号」，但请注意 P4-c：
补了之后这个指标**不一定**会变好。

### P4-e：有没有证据表明补完之后真的更像？

**没有。** 我查了三条可能存在的证据链，全部落空：

1. `deliverables/70-research/PROMPT-DIMENSIONS.md` §2.6 的原话：
   > **【✗】「LLM 系统性把字号压小」：零证据。【✗】「LLM 只用 2–3 个字号档」：零证据。
   > 【✗】任何 UI-to-code 基准的字号维度：零。**
   并明确判定「补字号」的证据等级 = **【D】**（内部观察，无外部对照）。
2. DesignBench（900 样本、9 个模型）的指标体系里**没有字号这一项**；
   repair 任务的 6 类问题分类里也**没有字号**（Occlusion / Crowding / Text overlap /
   Alignment / Color and contrast / Overflow）。
3. 唯一直接测「视觉层级违规」的研究（arXiv 2607.20690）测的是**判别能力**（模型能不能
   看出违规），不是**生成时会不会犯**。它不能回答这个问题。

### 判定

> **不成立（作为已验证的因果主张）；「修提示词能提升质量」目前是一个未经验证的假设。**
>
> - 0.490 可复现（我得到 0.471±0.02）：**成立**。
> - 这个指标有判别力：**勉强成立但很弱**（复刻 0.471 vs 无关 0.205，比值 2.3×）。

> - 「复刻字号小是因为单文件约束」：**不成立**。字号零字节成本，无机制关联；

### 我的实测（第一层）：重生成是确定性的 —— 但必须隔离测

```
=== prompts.js 已生成 ===

byte size: HEAD=60460 regen=60460
```

### 我的实测（第三层）：README 里会被判定的数字，以及失败模式

```
$ node deliverables/70-plan/redteam/p5-dependency-graph.mjs
=== ④ README 里的提示词长度断言（nums/prompt-len 的目标）===
  README.md: 1639–1998 字，中位 1829
```

`check-docs.mjs` 的判定逻辑（我读了 L657–L699）：

```js
for (const m of line.matchAll(/(?:中位|median)\s*([\d,]{3,6})\s*(?:字|characters)/gi)) judge(num(m[1]), lens.median, '中位');
…
if (bad.length) fail('nums/prompt-len', …);
else if (drifted.length) warn('nums/prompt-len', `提示词长度小幅漂移，建议更新（容差 ${DRIFT*100}%）`);
```

**它不是「失配就红」，是「小漂移变 WARN，大漂移才 FAIL」。** 所以「重生成会让 check-docs 红」
这个担心**部分不成立**：只要长度变化在容差内（`DRIFT`），它只会变 WARN，
而 `check-docs` 的 WARN **不阻断**（当前基线是 `0 FAIL / 0 WARN / 13 PASS`，exit 0）。

**真正会失配的不是数字，是语义**。我实测了一次「只改数据源」的重生成（差分来自并发写者的
h1Size 修复），`prompts.js` 的 diff 里出现：

```
-    "h1Size": "var(--fs-h1)",
+    "h1Size": "clamp(52px, 6.1vw, 86px)",
-    "lineWidths": "1px、2px",
-    "h1Size": "",
+    "lineWidths": "1px、1.2px、2px",
+    "h1Size": "40px",
```

**`lineWidths` 从 `"1px、2px"` 变成了 `"1px、1.2px、2px"` —— 多了一级。**
而提示词那句话是「线宽只用这几级：…，**不要自创第三级**」。级数变了，那句话的语义就错了，
**但没有任何检查器会发现**（见下）。

### 我的实测（第四层）：检查器矩阵 —— 谁会发现「提示词内容变坏」

**`check-prompts.mjs` 是本轮新出现的（`git ls-files` 显示它不 tracked）**，
它的文件头自述恰好回答了这个问题的核心：

> 「把 S19 主色 `#4A5C3A` 篡改成 `#FF00FF`，**`check-docs.mjs` 的 13 条断言零反应**

**这与我自己的 P1 结论互相印证**：P1 说「色板抽漏了 39 个色」，而 `check-docs` 全绿。
**因为检查器和生成器读的是同一份 `dna-clean.json`** —— 同源，一起漏，永远对得上。
这正是 Lead 在 `LEAD-color-violation-finding.md` §3.2 说的那句，我独立复现了它。

### 判定

> **「重生成是安全的」在字节层面成立，在产品层面不成立。**

> - 重生成确定性：**成立**（HEAD blob `75a5b1d…` 逐字节复现，60460 bytes）。
> - 「会触发哪些检查器」：`check-docs`（长度数字，小漂移只 WARN）、

> - 「README 哪些数字会失配」：**只有 `1639–1998 字，中位 1829` 这一条**，且小漂移只 WARN。

## P6「lineWidths 的根因是 clean-dna.mjs:452」

### 前提原文

> 复核 `deliverables/69-audit/PATCH-linewidth.md` 的定位。特别是 S20 的两组互斥线宽
> （机制句 `0.6/1.2/2.4px` vs 硬约束 `0.35/0.5/1/3px`）—— 这两个值分别来自哪个字段、
> 哪个函数？真的是同一份数据源吗？

### 我的实测：不是同一份数据源，而且 0.6/1.2/2.4 根本不是「线宽」

```
$ node deliverables/70-plan/redteam/p6-linewidth-origin.mjs

Q1 0.6/1.2/2.4 作为「描边宽度」出现在 CSS 声明 / HTML 属性里的次数:
   0.6px → CSS 0 次，HTML stroke-width= 0 次
   1.2px → CSS 0 次，HTML stroke-width= 0 次
   2.4px → CSS 0 次，HTML stroke-width= 0 次
   真实存在：CSS [1,3]，HTML [0.2,0.5]
```

**0.6/1.2/2.4 在 S20 的全部 CSS 与 HTML 里，作为描边宽度出现 0 次。**

它们在运行时是什么？我去读了 S20 的实现：

```
Q3 运行时语义：
   SP = [0.6, 1.2, 2.4]
   sp = 8 * s  → 实际间距 = 8 × 档位值（8 倍图面输出）
   RD(i, C, N, sp, fr) 里 sp 参与半径计算
   r = R0 + i * sp + …  → sp 是**相邻走线的半径步长**，不是描边宽度
   HTML 自述：「画布按 8 倍图面输出，即 4.8 / 9.6 / 19.2px」= true
```

S20 自己的 HTML 写得很清楚：

```html
<!-- index.html:94 -->
每 6 格换一档，只有三级 0.6 / 1.2 / 2.4px；画布按 8 倍图面输出，即 4.8 / 9.6 / 19.2px。
<!-- index.html:102 -->
上半 1:1：0.6px 的两根线在纸上并成一片墨…下半 8 倍放大后 4.8 / 9.6 / 19.2px 才分得开
```

**所以：**
- `0.35px` 是**笔画宽度**（`.ring { stroke-width: 0.35 }`，CSS 里真实存在）
- `0.6/1.2/2.4px` 是**相邻走线的间距**（`SP` 数组，JS 里，乘以 8 后使用）

**两个不同的量，被同一个单位 `px` 写在一起，于是读起来像"互斥的线宽"。**

### 两个值分别来自哪个字段、哪个函数

```
Q2 两个值分别来自哪个字段：
   dna-clean.json S20.lineWidths = "0.2px、0.35px、0.5px、1px、3px"
   dna-clean.json S20.mechanism  = "(空)"
   → 机制句实际来自 mechanisms.mjs 的 S20.text（build-prompts.mjs:105 的 if (!d.mechanism) 分支）

   提示词第 5 条 : 5. 线宽只用这几级：0.35px、0.5px、1px、3px，不要自创第三级。
   提示词机制句  : 这个风格的签名动作：…走线 0.35px 按 0.6/1.2/2.4px 三级分档——量级由线距读出。
```

| 提示词里的位置 | 值 | 字段 | 函数 | 数据源 |
|---|---|---|---|---|
| 第 5 条硬约束 | `0.35/0.5/1/3px` | `dna.lineWidths` | `clean-dna.mjs:452 lineWidthVerdict()` | 各案 `style.css` 的 `border*/outline*/stroke-width` 声明 |
| 机制句 | `0.6/1.2/2.4px` | `dna.mechanism` ← `mechanisms.mjs` 的 `S20.text` | `build-prompts.mjs:104–112` 的补丁分支 | **人手写的 `mechanisms.mjs`**，source 里标 `index.html:94,113 + _specs/S20.md:32` |

**所以「同一份数据源」这个前提是错的。两个值来自两条完全独立的链路：
一条从 CSS 机器抽，一条人手写进 `mechanisms.mjs`。**

### 但 PATCH-linewidth.md 的定位对不对？

它的核心主张是「`lineWidthVerdict()` 是唯一产生 `lineWidths` 的地方」。**这一点我复核成立**：

- `extract-dna.mjs:129` 的 `lineWidths` 是**废弃的上游版**（只匹配 `/border: ([0-9.]+)px/`），已被覆盖
- `collect-schemes.mjs` 只抽 `fill`/`stroke` 的**颜色**，不抽宽度
- `build-prompts.mjs:307` 是纯搬运
- `prompt-copy.js:456` 是唯一产生文案处

**但「S20 的两组互斥线宽是 `clean-dna.mjs:452` 的错」这个归因不成立。** `lineWidthVerdict()`
对 S20 的输出是正确的（`0.2/0.35/0.5/1/3px` 确实是页面上全部真实描边宽度，
我数了 CSS 的 `border*/stroke-width` 声明，得到的就是这个集合）。
**错的是 `mechanisms.mjs` 里那句人手写的机制句把"间距"写成了看起来像"线宽"的东西。**

### 这改变了修法

| 如果归因是 `clean-dna.mjs:452` | 实际归因 |
|---|---|
| 修 `lineWidthVerdict()` 的抽取逻辑 | 修 `mechanisms.mjs` 里 S20 那句话的**措辞**（加「走线间距」三个字，明确它不是描边宽度） |
| 影响面：所有 30 案的线宽表 | 影响面：只有 S20（以及任何把非线宽量写进机制句的案） |
| 风险：改抽取器会动摇 30 案的既有基线 | 风险：只改一句话 |

### 更广的测：30 案里机制句有多少个「px 值不在 lineWidths 里」

```
=== 30 案：机制句里的 px 值与 lineWidths 的关系 ===
   S01: 线宽{1,3} | 机制句{24} | 机制句独有 {24}
   S03: 线宽{1,2} | 机制句{28,264} | 机制句独有 {264,28}
   S10: 线宽{1.25,2} | 机制句{1,1.5,3,6} | 机制句独有 {1,3,1.5,6}
   …
   机制句含 lineWidths 之外 px 值的案：30/30
```

**30/30。** 但这**不代表 30 案都有缺陷** —— 绝大多数是布局尺寸（`24px 隔条`、`264px 刻度轴`、
`96px 索引条`），读者能靠上下文分清。**S20 之所以是特例，是因为它唯一的单位也是 `px`，
而且数值量级（0.6/1.2/2.4）与线宽量级（0.35/0.5/1）**完全重叠**，
读者无法靠大小区分。这是"语义歧义"，不是"数据冲突"。

### 判定

> **反转。**
>
> - 「lineWidths 由 `clean-dna.mjs:452` 产生」：**成立**（唯一生成点）。
> - 「S20 两组互斥线宽的根因在 `clean-dna.mjs:452`」：**不成立**。`lineWidthVerdict()`
>   对 S20 的输出是正确的；错的是 `mechanisms.mjs` 里人手写的机制句。
> - 「两个值来自同一份数据源」：**不成立**。一个来自 CSS 机器抽取，一个来自人手写的
>   `mechanisms.mjs`，中间没有任何共享。
> - 「它们是两组互斥的线宽」：**不成立**。`0.6/1.2/2.4` 是**走线间距**（`SP` 数组，
>   运行时 `sp = 8 * s`），不是描边宽度。真正的互斥不存在。

## 7. 我主动找的问题（六条前提之外）

### 7.1 X1：长度预算 —— 补完三项会变成多少字？有没有证据表明有阈值？

我按最小可行写法估算了三个待补项（字号 46 字、配比 48 字），逐项加到 30 条提示词上：

```
$ node deliverables/70-plan/redteam/x1-x4-probes.mjs
X1 长度预算（字符数，含换行）
  现状      : 1639–1998，中位 1829
  补字号    : +46 → 1685–2044
  再补配比  : +48 → 中位 1954
  三项全补  : 1764–2123，中位 1954  （+6.8%）
  祈使句条数现状：22–23，中位 23；补 3 条后中位 26
  外部实证阈值（61-research/prompt-efficacy.md §2.2）：非推理模型 50 条开始掉；推理模型 100–250 条。
```

**结论：字数不是问题，条数也不是问题。**

`prompt-efficacy.md` §2.4 的判定表说得很直接：

> | 自变量 | 有无实证阈值 | 对 1200 字提示词的风险判断 |
> | token 长度 | **有**：64–128k token 才开始陡降 | **无风险**（1.5k token，余量 40×） |
> | 约束条数（简单约束） | **有**：非推理模型 50 条 | **低风险**（约 20 条，在阈值内） |

补完是 2123 字 ≈ 2.7k token，**距 64k 拐点还有 24 倍余量**；祈使句 26 条，
**距非推理模型的 50 条阈值还有 24 条余量**。

**所以「长度预算」这个反对理由不成立 —— 但它也不构成支持理由。**
真正的问题在 §2.1 的另一条：「U 形曲线，中间最差」——

> 「performance is often highest when relevant information occurs at the **beginning or end** of
> the input context, and **significantly degrades** when models must access relevant information
> in the **middle**」（Lost in the Middle, TACL 2024）

**按现在的结构，要补的「字号」会落在第 2 条（视觉硬约束，全文约 40% 处），
「配比」会落在第 1 条后面 —— 两者都在中段。** 如果真要补，应该考虑挪到末尾的
「验收三问」附近，而不是加进中段。**这是一个有实证支持的改进方向，比"补内容"更值得做。**

### 7.2 X2：故障是否在更上游？`extract-dna.mjs` / `clean-dna.mjs` 丢了什么？

```
X2 extract-dna → clean-dna 的损失
  30 案 style.css 里 var(--…) 共 3457 处，@media 共 179 处
  extract-dna.mjs 是否解 var(): 否（extract 只抽字面量）
  clean-dna.mjs 解 var(): true，处理 @media: true
```

**好消息：`clean-dna.mjs` 确实解 `var()` 也处理 `@media`。** 我核了它的注释与代码：

> `clean-dna.mjs:277`「为什么不用 `/([^{}]+)\{([^}]*)\}/` 这种一把梭：@media 会把花括号嵌套进来…
> 于是媒体查询里的 h1 字体覆盖就永远读不到。」

**坏消息（这是我找到的第 5 个问题，且是 P1 的真根因）**：`pickPalette()` 只从 `:root`
的变量声明取色，而**页面上有 39 个显著颜色是硬编码字面量**（P1 的 C 类）。这不是
`var()` 或 `@media` 的问题，是**取值域**的问题：

```
$ node deliverables/70-plan/redteam/p1d-palette-source.mjs
  A 在 :root 但被 7 上限截掉 : 12
  B 在 :root 但判据没选中     : 0
  C 硬编码字面量（抽取看不到）: 39
  D 运行时产物                : 6
```

**所以「改提示词 vs 改规格 vs 改抽取器」这个问题，答案是第三个：抽取器的取值域太窄。**
改规格（在 `Sxx.md` 里补色）要改 30 份手写文档；改提示词（手补色值）会在下次重生成时被覆盖；
只有改 `pickPalette()` 让它**同时扫 `:root` 与全文件的 `color:`/`background:` 字面量**
（像 `lineWidthVerdict()` 已经做的那样），才能一次修好。

**顺带一个具体证据**：S24 的 `:root` 有 13 色，色板只留 7 色。S24 的 `#6E8B7A`（叶脉描边）
在 `_specs/S24.md` 里**明写了**（`inSpec=true`），但被 7 上限截掉了 ——
**这是唯一一个「规格写了、抽取也看到了、却被上限扔掉」的色**。

### 7.3 X3：提示词的读者是谁？单文件 HTML 的约束合理吗？

```
X3 提示词里两条约束是否互斥
  提到如何加载字体（google/@import/@font-face/woff）的案：0/30
  要求单文件 HTML 的案：30/30；要求不引外部依赖的案：30/30
  点名了具体非系统字体的案：30/30
  → 30/30 案同时满足：点名非系统字体 + 单文件 + 无任何加载手段
```

**30/30 案都在要求一件做不到的事。** 具体到 S20：提示词要求

> 2. 字体：标题按这个顺序取第一个可用的：`Space Grotesk → Noto Sans SC`…
>    不要用 Playfair Display、Inter、Roboto。**也不要跳过上面这两条链直接回退成系统默认无衬线。**

而 `Space Grotesk` 在本机**未安装**（上一轮已实测），提示词又禁止回退，
又禁止引外部资源（"不引 React/Vue/Tailwind/Bootstrap，不拆文件、不构建"）。

**这条我判为「成立且比 P1–P6 里任何一条都更直接」**：它不是"数据不准"，
是**提示词在要求一件物理上做不到的事**，而 AI 唯一的出路是违反其中一条。

**但我不认为该改「单文件」这个约束。** README:80 写得很清楚，用户拿这份提示词是
「直接粘给 ChatGPT / Claude / v0」——**用户要的是一个能立刻看到效果的单文件**，
拆成多文件会让交付物从"一个 HTML"变成"一个项目"，摩擦大增。
**该改的是字体那一行**：要么允许 `@font-face` + 内联 base64 子集（体积可控），
要么**别点名非系统字体**，改成「标题用一款几何无衬线（系统可用的优先）」。

### 7.4 X4：规格 vs 提示词，谁该改？

```
X4 _specs/Sxx.md 字段 5（布局与网格）里的数值，有多少进了提示词
  字段 5 的尺寸记号合计 103 个，提示词里出现过数字的 48 个（47%）
```

**字段 5（布局与网格）只有 47% 的尺寸进了提示词。** 但我不认为这个数字本身是缺陷 ——
提示词的定位是「风格迁移」，不是「像素级复刻」，47% 可能正好。
**关键是「哪些没进」**：进的多是「12 栏、8px 基线」这种骨架量，
没进的多是「参数面板占右侧 3 栏、低于画布顶边 32px」这种**具体位置**。
后者确实属于"描述那个具体页面"，README:101 的原则支持不写。

**所以「改提示词 vs 改规格」这个问题，我的答案是：都不对，改抽取器的取值域（见 7.2）。**
- 改规格：要动 30 份作者手写文档，且规格只写 3–7 色，补完还是窄于页面
- 改提示词：下次重生成被覆盖（P5 实测：重生成是逐字节覆写）
- 改抽取器：一处改动，30 案同时生效，且可以把「上限 7」这个截断点重新审视

### 7.5 X5（额外的）：`h1Size` 是一条「抽了 26/30、渲染 0/30」的死字段

这一条我从 P2 追出来的，值得单列，因为它是**零成本可修的产品缺陷**：

```
dna.h1Size 有值的案: 26/30
该值出现在提示词正文里的案: 0/30
prompt-copy.js 里 h1Size 只出现在 L284，位于 if (d.mechanism) 的 else 分支
而 mechanism 非空的案: 30/30 → else 分支永远不会进
```

**这是本仓库反复记录的「参数收下但不用」病的又一个实例**，而且它刚好就是本轮
「补字号」要补的那个字段 —— **数据早就在，只是接线断了。**

### 7.6 X6（额外的）：「不要自创第三级」这句话与数据不匹配

`prompt-copy.js:456` 对 30 案都输出同一句：

> 5. 线宽只用这几级：{lineWidths}，**不要自创第三级**。

而实测各案的级数分布：

| 级数 | 案 | 这句话说得通吗 |
|---|---|---|
| 1 级 | S25（`3px`） | **说不通**：只给 1 级，哪来的第三级 |
| 2 级 | 多数案 | 勉强：「第三级」= 不存在的第三级，可以理解为"别加" |
| 4 级 | S19（`0.4/0.8/1/3`） | **自相矛盾**：给了 4 级却说不许第三级 |
| 7 级 | S13（`1/2/3/5.5/7/9/14.5`） | **自相矛盾** |

**这不是"某几案的问题"，是模板句与数据维度不匹配。** 修法：按实际级数生成措辞
（1 级说「只用这一级」，≥3 级说「只用列出的这几级」）。

## 9. 自我纠错（我这一轮量错的 8 类）

上一轮有 Agent 因为坦白记了 8 类测量错误而最有价值。我照做，逐条记我自己的错。

**E1｜`h1Size` 的「数字出现在提示词里」误判了两次。**
第一次我用 `/\d+/g` 匹配 `var(--fs-h1)`，把变量名里的 `1` 当成字号 → 误报 5 案。
修成只匹配 `px` 后得到 1/30（S23 的 `96px`）。再人读上下文，发现 S23 的 96px 是
「右缘 **96px 索引条**」，不是标题字号 → 真实 **0/30**。
**教训：字符串包含 ≠ 语义命中。凡是「A 是否包含 B」的判据，都要人读一遍命中的那一处。**

**E2｜重生成确定性：我在工作区跑，被并发写者污染，误判「不确定」。**
我第一次得到的结论是 `before ≠ after`（`1C0D607…` → `B06E94B…`）。真相是
另一个 Agent 在 23:20–23:21 改了 `clean-dna.mjs` 与 `dna-clean.json`，我读到了新数据。
在 `%TEMP%` 里用 HEAD blob 重跑，得到**逐字节相同**。
**教训：任何"确定性"测试必须在隔离目录 + 冻结输入下做。工作区是会变的。**

**E3｜像素直方图 v1 忘了遮蔽 `<img>`，把照片颜色算成设计色。**
S03 报出 `#56311E` 占 0.167% 的「可见新颜色」，而该 hex 在 `style.css` 里出现 **0 次**。
**教训：像素口径只回答"屏幕上有什么"，不回答"设计用了什么"。必须遮蔽图像区域。**

**E4｜DOM 口径第一版没排除纯黑纯白，得到 30/30，看似"全都违规"。**
真实信息量为零（每个页面都有浏览器默认色）。排除后才复现出 Lead 的 20/30。
**教训：一个"全都违规"的测量结果，通常是测量口径的问题，不是世界的问题。**

**E5｜PowerShell 的编码陷阱连续坑了我三次。**
`Set-Content -Encoding UTF8` 写 BOM → `JSON.parse` 崩；`git cat-file > file` 用 PowerShell
重定向 → 写出 UTF-16（86392 字节 vs 60460）；`Out-File -Encoding utf8NoBOM` 在
PowerShell 5.1 上不存在（`ValidateSet` 只到 `utf8`）。
最终用 `cmd /c "git cat-file blob SHA > file"` 才拿到原始字节。
**教训：在这个仓库做字节级比对，不要经过 PowerShell 的文本管道。**

**E6｜我把「元素使用次数」当成了「可见度」。**
Lead 报告说 `#5E5443` 用了 247 次。我复现了这个次数（我测到 252），但同时也测了面积：
**17.29%**。而 `#0A0A0D` 只用了 5 次，面积却占 **81.99%**。
次数与面积是两个不同的量，前者数元素，后者才是眼睛看到的。
**教训：「用了 N 次」不能推出「很显眼」。**

**E7｜我引用了一个我没有复现的数字（S28 的「最大/正文比 3.67」）。**
报告初稿在「如果只能做一件事」里写了「三案的比值 1.58/2.17/3.67」。
这组数字来自 Lead 的报告，不是我测的 —— 违反了本任务书的第一条约束。
我自己测（`p4b-typedist.mjs`，按字符数加权取占比最高的非标题档为正文）得到的是
**1.58 / 2.17 / 4.89**。差异在 S28：Lead 取 12.5px 为正文，我取 9px（占 31.8%）。
**这个差异实质性影响了结论**：按我的口径 S28 是 0.69 倍（不算崩），
按 Lead 的口径是 0.52 倍。**「三案一致偏低」只在两案（S20/S21）上成立。**
我已在 §10 里改写了这段并显式标注了与 Lead 的不一致。
**教训：任何进入结论的数字，哪怕只用于说明方向，也必须自己跑一遍。**

**E8｜「字号分布」的引用同样是二手。**
P4-c 初稿写「S28 原型分布是 {13,15,16,92…}，复刻是 {9,10,12,13,44}」，也来自 Lead。
自测后：原型前六档是 `13(67.4%) 16(23.1%) 22(3.1%) 15(2.6%) 18(2.1%) 30(1%)`，
复刻是 `9(31.8%) 13(30.4%) 10(16%) 12(8.8%) 11(7.5%) 15(3.8%)`。
**我自己测的版本让 P4-c 的解释更强**：主体档 13px vs 9/13px 本来就已经接近，

按 Lead 的二手数字，这个机制说不清楚。

## 10. 如果只能做一件事

**把 `prompt-copy.js:284` 那行 `h1Size` 从 `if (d.mechanism)` 的 else 分支里提出来，
让它进硬约束段（或视觉硬约束第 6 条）。**

### 理由（四条，每条都是实测的）

**1. 它是唯一「数据已在、只差接线」的缺陷 —— 成本 1 行，收益覆盖 26/30 案。**
`dna.h1Size` 已经抽到 **26/30**（S02 是 `clamp(60px, 7.4vw, 108px)`、S28 是
`clamp(40px, 6.4vw, 92px)`），只是渲染层永远不读它。这不是"补数据"，是"接上线"。
重生成 30 条提示词的方案要改抽取器 + 生成器 + 重跑 + 复核，成本高一个数量级。

**2. 它精确命中 P4 里唯一被实测证实的失败模式。**
复刻 S28 的 H1 是 44px，原型是 **92px**；复刻 S20 的 H1 是 19px，原型 **72px**；
复刻 S21 的 H1 是 26px，原型 **86px**。（这三个数字我逐个核过 `deliverables/69-test/*/index.html`
与 `style.css`，见 `p4b-typedist.mjs`。）

「最大字号 / 正文字号」的比值（我自己测的）：

| 案 | 原型 H1 | 原型正文 | 原型比 | 复刻 H1 | 复刻正文 | 复刻比 |
|---|---|---|---|---|---|---|
| S20 | 72px | 13px | **5.54** | 19px | 12px | **1.58** |
| S21 | 86px | 16px | **5.38** | 26px | 12px | **2.17** |
| S28 | 92px | 13px | **7.08** | 44px | **9px** | **4.89** |

三个复刻的共同特征是「不敢用大字号」：比值全部缩水（1.58 / 2.17 / 4.89 vs 5.54 / 5.38 / 7.08）。
而提示词给的是**绝对档位**（`clamp(40px, 6.4vw, 92px)` 意味着桌面 92px），
这正好补上「不敢用大」这个具体缺口。

> **⚠️ 与 Lead 的数字有一处不一致（这正是任务书要我报的）**：Lead 报告说 S28 的
> 「最大/正文比 7.08 → 3.67」。我的实测是 **7.08 → 4.89**。
> 差异来源可定位：Lead 把「正文字号」取成 12.5px（复刻分布里的第三档），
> 我取成占比最高的那一档 9px（31.8%）。**两种取法都说得通，但得出的结论强度不同**：
> 按我的口径，S28 的复刻比值 4.89 其实**不算太低**（原型 7.08，是 0.69 倍），
> 真正崩的是 S20（0.29 倍）与 S21（0.40 倍）。
> **所以「三案一致偏低」这个说法在 S28 上站不住 —— 只有两案（S20/S21）显著偏低。**

**3. 它不会引入 P4-c 里那个「指标变差」的风险 —— 因为绝对档位不是分布平移。**
我用「字号整体乘 k」做实验时分数会跌，是因为乘 k 让整个分布平移。
但 `clamp(40px, 6.4vw, 92px)` 是**把 H1 这一档钉到 92px**，同时正文保持原样 ——
这会让分布**从「全挤在 9–15px」变成「9–15px + 一个 92px」**，正是原型 S28 的形状
（原型是 `{13:44.3%, 16:43.1%, 15:8.1%, 92:标题}`）。**方向与原型一致，不是盲调。**

**4. 它可被一条命令验证，且不依赖任何模型。**
```
$ node deliverables/70-plan/redteam/p2b-fontsize-v2.mjs
  M5 提示词里出现该案 h1 的真实字号: 0/30   ← 改之前
$ # 改 prompt-copy.js 后重跑
  M5 提示词里出现该案 h1 的真实字号: 26/30  ← 改之后
```

### 为什么不是别的

| 候选 | 为什么不选 |
|---|---|
| 补色板（P1） | 39 个色是硬编码字面量，要先改抽取器取值域；且规格里**一个都没写**，补哪些色需要人定 |
| 补配比（P3） | 零实证（仓库检索报告原话「连方向性证据都没有」），且我的数据表明复刻的底色配比**比原型更准**，丢的是选色不是配比 |
| 修 `mechanisms.mjs` 的 S20 措辞（P6） | 只影响 S20 一案，且是"读起来像冲突"而非"数据错误" |
| 补「不要自创第三级」的措辞（N4） | 影响 30 案，但它是**措辞洁癖**，不改 AI 行为 |
| 加内容闸门 `check-prompts.mjs`（P5） | 方向对，但它是**防回归**不是**改善**；而且它现在不在版本控制里，入库本身要走流程 |

### 一句话

> **这一轮真正的发现不是「提示词缺什么」，而是「提示词里已经有的东西没有接线」。
> 先接线，再谈补货。**
