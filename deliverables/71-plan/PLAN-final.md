## 零、为什么长任务缩成了三个小任务

原计划要做「两条数据链合并成单一来源」。**我自己的四个探针把它推翻了三次。**

| # | 我的判断 | 推翻它的数据 | 探针 |
|---|---|---|---|
| 1 | 两链各算一遍，应合并 | `data.js` 是 `prompts.js` 的**子集**，29/30 案成立 | `LEAD-check-subset.mjs` |
| 2 | `data.js` 截断丢了重要色（S03 丢 35%）| `data.js` **精确等于**规格字段 3 的 4 色；那个 35% 的色**不在规格里**，是 CSS 派生 | `LEAD-check-order.mjs` |
| 3 | 那是 `prompts.js` 加色，破坏了规格封闭性 | 它补的 53 个色里 **52 个不在规格**，但逐个查 CSS 注释后，**几乎全是必需派生**（文字色 / 状态色 / 暗部 / 结构线 / AA 对比度）| `LEAD-check-extra-origin.mjs`、`LEAD-classify-52.mjs` |

### 最终事实

```
data.js    = 规格字段 3 的 4 个主色（面积和 100），忠实转录，24/30 案精确一致
             （另 6 案的"差异"是我误抓的负向示例 #6366F1 / #3B82F6）
prompts.js = data.js 的 4 色 + 从 :root 补的 0–4 个派生色 = 4–7 色
             补的 53 个里 52 个不在规格，但它们是实现必需的（次级墨、悬停态、暗部、AA 字色）
```

**两条链都对。它们描述的是不同层次：设计意图 vs 施工细节。**

## 一、这一轮真正该做的三件事

### 任务 1 · 修 S24 的 `#6E8B7A` 漏抽（真 bug，1 案）

**事实**：规格字段 3 明写 `#6E8B7A` 苔绿（辅助色，6%），页面用了 80 个元素（`svg-stroke`），
但 `prompts.js` 的 `pickPalette()` 没收录它。

这是**唯一一个「规格有、data.js 有、prompts.js 没有」的色**。

**修法**：`clean-dna.mjs` 的 `pickPalette()` 在从 `:root` 挑时，要保证把
**规格字段 3 声明的色**优先纳入（或至少不遗漏）。

**验收**：`LEAD-check-subset.mjs` 从 29/30 → **30/30**。

---

### 任务 2 · 建「两链关系」闸门 `check-twolines.mjs`（记录差异，不是消除差异）

这不是「让两链一致」，而是**把已验证的关系钉住**，防止未来悄悄坏掉：

| 断言 | 当前值 | 意义 |
|---|---|---|
| `data.js` palette ⊆ `prompts.js` palette | 29/30 | 若变 28，说明有新的漏抽 |
| `data.js` palette 与规格字段 3 一致（排除负向示例） | 24/30 + 6 案可解释 | 若变少，说明截断逻辑坏了 |
| `palette[0] === bg` | 30/30 | `app.js:953` 的注释依赖这个 |
| `palette[1] === primary` | 30/30 | `app.js:945` 的注释依赖这个 |
| 底色/主色都在 palette 里 | 30/30 | 摘要不能丢主信息 |
| `prompts.js` 补的色**都有 CSS 角色注释** | 51/53 | 无注释的色可能是真扩张 |

**设计原则**：闸门不要求两链相等（它们不该相等），只要求**关系成立**。
FAIL 级别只给「关系被破坏」，WARN 给「有新色但没注释」。

## 二、明确不做的事（附理由）

| 事项 | 为什么不做 |
|---|---|
| 合并两条链成单一来源 | 子集关系证明它们不是"各算一遍"；语义不同且都合理 |
| 让两链 palette 相等 | 会丢掉 52 个必需派生色，AI 就得自己编次级墨/悬停态 |
| 修 `data.js` 的截断逻辑 | 它已精确等于规格字段 3，无需修 |
| UI 加「完整色板见提示词」 | 28/30 案的 4 色是合格摘要；实测底色主色都在，用户没被误导 |
| 继续端到端验证 | 统计上做不到（要证 ≥90% 需 29 次）|

三个 Agent 正在跑，都基于旧假设：

| Agent | 处置 |
|---|---|
| 测量 Agent（四层矩阵）| **不打断**。它可能独立发现「子集关系」，那是交叉验证 |
| 红队 Agent（攻击合并方案）| **不打断**。方案已撤回，但它的攻击方向正确，可能独立得出同一结论 |
| 批判 Agent（质疑产品价值）| **不打断**。它的 Q2「让两链一致是不是假目标」正好命中我的结论 |

**如果它们独立得出同样结论，那是最好的验证。如果它们得出不同结论，我要认真对待。**

## 六、我认为这一轮最大的收获

**不是修了一个 bug，是三次推翻自己。**

原计划是一个「长任务」——合并两条数据链。它听起来很正确（消除重复、单一来源）。
但四个探针把它拆掉了：

- 第一次：子集关系 → 不是"各算一遍"
- 第二次：`data.js` 忠实等于规格 → 不是"截断丢信息"
- 第三次：53 个补色几乎全是必需派生 → 不是"扩张"

**如果我按原计划做，会做出一堆没必要的重构，而且很可能把 52 个必需色删掉。**

这个仓库的历史里，反复出现"修一个东西引入反向缺陷"（70 轮我自己就犯过：
第 6 条字号用 clamp 下限，方向与目标相反）。**这次的教训是：在动手之前，
先用探针验证「这件事真的存在吗」，而不是「我能不能修好它」。**
