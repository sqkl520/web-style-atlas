## Q1「用户真的被误导了吗」——这是整个任务的价值前提

### 1.1 先复述原任务的前提

`RECON-next-round.md` 候选 A 的说法：

> 用户在选型台上**按色块判断风格**，点「复制提示词」后拿到的却是 4–7 色的约束。
> S17 用户只看到 3 个色块，提示词却要求 7 个色——他以为的风格和实际要做的不是同一个。

这个论证的隐含前提是：**色块是用户判断风格的主要依据，且色块的"色数"本身携带语义。**
我要攻击的正是这个前提。

### 1.2 反面论证之一：代码注释说明了为什么是 4

`app.js:508` 的 `(r.palette || []).slice(0, 4)`。但注意：**这个 `slice(0,4)` 从来没有截断过任何东西。**

实测（`critique/q1-slice-is-dead.mjs`）：

```
data.js palette 长度分布: {"3":5,"4":25}
data.js palette >4 色的案: 0/30
```

`collect-schemes.mjs:486` 是 `if (pal.length >= 4) break`——**上游已经封顶 4**。
所以 `slice(0, 4)` 是一段**永远不会生效的防御性代码**。

这一条很重要，因为它改变了问题的性质：

> 原任务把它描述成「UI 层主动砍到 4 个」。
> 实际情况是「数据层就是 4 个，UI 层写了个 slice 只是恰好无害」。

**如果真的存在"用户被误导"，那个决定发生在 `collect-schemes.mjs`，不在 `app.js`。**
而 Lead 后来正是查到了这里，并判定它「精确等于规格字段 3 的 4 个主色」——见 Q2。

### 1.3 反面论证之二：`app.js:940-980` 的注释在讲另一件事

任务让我读 `app.js:940-980`。我读到的不是「为什么只画 4 个」，而是 `paletteLine()` 的注释：

- `app.js:945`：`primary` 恒等于 `palette[1]`（30/30），这是构造不变量，`collect-schemes.mjs:411-415` 先 push bg 再 push primary
- `app.js:953`：底色标签用 `palette[0]` 而不是 `r.bg`，两者 30/30 相等

这段注释的关切是**「标签打在哪一个色上」**，不是「一共画几个色」。
它连一次都没提过 4 这个数字与"色数"的关系。

**我核实了它声称的两条不变量，都成立**（`critique/q1-invariants.mjs`）：

```
palette[0] === bg        30/30
palette[1] === primary   30/30
```

**但请注意这两条是恒真的，不是被验证过的**。`collect-schemes.mjs:484-485`：

```js
const pal = [];
if (rec.bg) pal.push(rec.bg);              // pal[0] = bg，必然
if (rec.primary && !pal.includes(rec.primary)) pal.push(rec.primary);  // pal[1] = primary，必然
```

**先 push bg、再 push primary，然后才拿 `pal[1]` 去比 `primary`**——这个断言在构造上不可能失败。
这一点我在 Q6 会展开，因为它决定了新闸门 R2/R3 的价值。

### 1.4 反面论证之三：用户的实际行为路径

README 第 55 行的产品承诺：

> 一屏摊开 30 个案子。每行给出结构类型／认知门槛／调性、一句话定义（人话版，不是规格里的术语）、**配色色块**、错误码、内容量容限、闸门结果，以及**桌面 1440 真实渲染截图**。

README 第 66 行的取舍记录更关键：

> 卡片上为什么只留一张图：原来卡上是三档并排……三档对照移进详情面板的可点击视口切换器，**卡上留一张能看清的桌面图**。卡片高度 434px → 277px，首屏可见方案卡 0 → 1 张。

**这是用户真实行为路径的决定性证据。** 这个仓库花了整轮去抢那 157px 的行高，
牺牲的是「768/390 两档截图」，换来的是「首屏能看到一张完整卡」。
说明 Lead 对「什么在首屏、占多少像素」是有极强取舍意识的。

那么色块在首屏占多少？`style.css:474-475`：

```css
.swatches { display: flex; gap: 3px; align-items: center; }
.swatches i { width: 20px; height: 20px; ... }
```

**4 个 20×20px 的方块，加 3px 间隙 = 全宽 89px。** 而卡片是 `grid-template-columns: 62px minmax(0,1fr) 316px`，
即内容列为 1fr、右栏 316px。**色块占内容列宽度的比例，在一张 1440px 的卡上是 89/约 1000 ≈ 9%。**

对比同在一行里的其他元素：
- `.row-def`（一句话人话定义，用户判断风格的第一入口）
- `.row-family`（美学家族 + 参考对象，`clamp` 到 2 行，用整行宽）
- `.row-foot`（闸门 FAIL/WARN、错误码、屏数、真图数）
- 316px 宽的桌面截图（`aspect-ratio: 16/9`，约 178px 高）

**一张 316×178 的真实渲染截图，面积是 4 个色块（4×400px²=1600px²）的 35 倍。**
而 README 自己说这张图的取景理由是「能看清」。

**所以用户的路径几乎必然是「看截图 + 读一句话定义 → 判断风格」，色块是辅助索引。**
色块为**搜索与向导**服务的证据更硬：`wizard.js:34` 用它算彩度、`wizard.js:64` 用它排序、`app.js:195/215/238` 用它做筛选轴。
**它的功能是"可计算的分类特征"，不是"视觉预览"。**

### 1.5 反向检验：如果色块真的误导，应该能在数据上看见

一个好批判不能只说"我觉得不重要"。我做了正向的证伪尝试：

**检验 A：被省略的色是不是「不同的色相」？**（`critique/q1-hue-coverage.mjs`）

如果 4 色摘要丢的是**另一个色相**，那用户就会把"紫金"看成"紫"，这是真误导。

```
被省略的色中：同色相/近距离（=明暗渐变或同族）= 50   真正异色相 = 2
4 色块覆盖了全色板所有「不同色相族」的案: 30/30
```

那 2 个「异色相」都是 `#FFFFFF`（S25、S27），即纯白——**它不是设计色，是按钮字色/留白**，不进色板是合理的。
用户看到 3 个色块，和看到 4 个色块（其中一个是纯白），对"这是什么风格"的判断**没有差别**。

**这是 Q1 最强的证据：30/30 案的 4 色块覆盖了全色板的全部色相族。摘要不说谎，它只是不列全部明暗档。**

**检验 B：色块是否覆盖了页面实际渲染的主导色？**（`critique/q1-dominant.mjs`）

用 `deliverables/70-audit/measure/palette-reconcile-30.json`（测量 Agent 的真浏览器像素实测）：

```
渲染面积前 3 名全都在 4 色块里的案: 17/30
渲染面积前 3 名不全在色块里的案: 13/30
```

13/30——**这个数字看起来对我很不利，我必须如实报告。**

但继续看，这 13 案里：

- 5 案的最远色差 ≤30 RGB 单位（S06:29, S12:18, S14:10, S22:28, S25:18）——**肉眼基本同色**，是取整/混色差异
- 真正 >30 的只有 5 案：S08(49)、S15(60)、S17(40)、S24(36)、S30(31)

而这 5 案的「差异」是什么性质？
- **S17**：色块 `#E1D6BD`，实测主导色就是 `#E1D6BD`（71.7%）；差 40 的是 `#C9BFA6`（20.3%），
  而规格原文写的是「次级纸色 `#C9BFA6`……**此色不作背景**，情绪：留档」。
  也就是说**省略它是规格作者自己的选择**，不是截断错误。
- **S30**：主导色 `#E6E6E6`（17.6%）与色块 `#EDEDED`（59.2%）差 12 单位——是同一冷白的明暗档。
- **S24**：差 36 的是 `#1B1136`（13.6%），是 `:root` 里的 `--exp32` 曝光色阶档位；
  色块里已有 `#5D43AD`（同色相家族的亮端）和 `#0A1116`（暗端）。**中间档省略不改变"这是蓝晒紫"的判断。**

**结论：真正可能误导的案，不是 22/30，也不是 13/30，而是接近 0。**
剩下的差异集中在「同色相的明暗档」和「规格自己声明的次级色」。

### 1.6 我在这条上撤回一个说法

我一开始想论证「色块只是 9% 宽度，所以完全不重要」。
但跑完检验 B 后我发现这个说法**过头了**：
S03 的 `#0C1417` 占屏 48.8% 却不在色块里，S02 的 `#111111` 占屏 10.0% 也不在。
这在"视觉预览"这个用途上**确实是一处真实的失真**。

**准确的说法应该是：**
> 色块的**色相信息**是忠实的（30/30 覆盖全色相族）；
> 色块的**明暗分布**是不忠实的（大面积暗部被省略）。
> 而"明暗分布"恰恰是用户在截图里一眼就能看到、在 4 个小方块里本来就看不出来的东西。

**所以：色块作为"风格预览"是不完整的，但作为"色相索引/筛选特征"是准确的。**
用户在首屏本来就有 316px 的截图承担预览职责。

### 2.3 根因：主色抽取走了一条**会抓到错行**的正则

`collect-schemes.mjs:296-298`：

```js
const primM = /主色[^#\n]{0,24}(#[0-9A-Fa-f]{6})/.exec(p3raw)
  || /(#[0-9A-Fa-f]{6})[^#\n]{0,24}主色/.exec(p3raw)
  || /主色[\s\S]{0,40}?(#[0-9A-Fa-f]{6})/.exec(p3raw);
```

第一条是「主色」**之后** 24 字内的 hex。它先尝试，先命中就先赢。我复现了这 5 案：

```
S05 A(主色在前)= #BFB9A6    B(主色在后)= #4FA83D
S07 A(主色在前)= #1C1A16    B(主色在后)= #33505C
S09 A(主色在前)= #151310    B(主色在后)= #1F4E79
S10 A(主色在前)= #6E7076    B(主色在后)= #D32029
```

**正确的答案全都在 B 分支里，而 A 分支抢先命中了。**

为什么 A 会抢先？因为这些案的规格写作顺序是「**底 → 主色 → 正文 → 副色**」，
而 A 的正则从句子开头扫，遇到第一个「主色」二字时——那个「主色」可能属于**前一个色值的角色说明**，
于是它往后 24 字抓到了**下一个色值**。

S05 的具体过程：
`#0E100D 铁皮底＝背景，58%（…明度 5.7%，极轻绿相保留但明度抬一档）；#4FA83D 漆面绿＝主色与读数…`
——「主色」前面 24 字内有 `#BFB9A6`？不是。实际是 A 从更早的「主色」出现处开始。

**这 5 案里，B 分支 5/5 给出正确答案，A 分支 5/5 给出错误答案。**

### 2.4 ⚠️ 我在这里犯了一个错，必须记下来

看到上面那张表，我的第一反应是「**A/B 优先级反了，把 B 提到 A 前面就行**」。
我在报告的初稿里就是这么写的，并把「改 3 行正则」作为 §9 的任务 1。

**然后我把这个修法放进探针里打靶，它挂了。**

```
=== 三种主色抽取方案，对着「权威主色」打靶 ===

① 现状（A 优先）        25/30
② 我第一版的建议（B 优先）  16/30      ← 比现状更差
③ 分句法（推荐）          30/30
```

**「B 优先」会让正确率从 25 掉到 16。** 它错在哪：

```

S12  拿到 #6366F1  应为 #B5D626
S13  拿到 #6366F1  应为 #7B612C
S15  拿到 #6366F1  应为 #3A3F45

```

**B 会抓到「反的是 `#6366F1` 靛蓝主色」这类否定语境里的色，以及 §2 作废的旧值。**
`#6366F1` 是规格里反复出现的「AI 默认色反例」，它后面经常紧跟「主色」二字，

**我为什么会错**：我只看了 S02/S05/S07/S09/S10 这五案（也就是已知的错案），
看到 B 在**这五案**上全对，就下了「B 优先」的结论。**样本只包含错案，不含对照。**
这是标准的「只选正例验证」错误。

**正确的修法是分句法**：按 `；。` 切分句，取「含『主色』角色词、且不含否定词」的那个分句里的 hex。

这个错误的教训比结论本身更值得记：
**「A 错了」不等于「B 对」。** 我把一个二元选择当成了穷举，而实际答案是第三条路。

### 2.5 这里有一个更尖锐的观察：`primary` 字段**没有消费者**

我扫了 `app.js` / `wizard.js` / `prompt-copy.js`：

**「没有界面在用」的判断，让这个错值安全地活到了现在。**

### 2.6 如果我对了，意味着什么

## Q3「共享模块」是过度工程吗

### 3.1 我的判断：是。而且 Lead 已经用数据把它否掉了，这个结论我独立复核成立

原计划 WP2 要抽 `prototypes/_build/lib/palette-truth.mjs`，两个生成器都 import。

**反驳它的最硬证据是子集关系。** 我独立跑了（`critique/q3-subset.mjs`，逻辑等价于 `LEAD-check-subset.mjs`，
但我用 `new Set` 去重且从 HEAD 的 `prompts.js` 求值）：

```
data.js 的 palette 是 prompts.js 的严格子集: 30/30（ad69f20 之后）
data.js 集合 === prompts.js 集合: 8/30
严格子集（少列但都列对）: 21/30
data.js 有、prompts 没有的色: 0 个
```

**子集意味着「一条是另一条的前缀/截断」，不是「两条独立算同一件事」。**
共享模块的经典理由（消除"同一个逻辑写两遍"）在子集关系下**不成立**——
因为两个生成器的逻辑**本来就不同**：一个按规格声明序取 4，一个按主色优先 + 派生补到 7。
把它们塞进一个模块，结果只能是模块长出一个 `mode: 'ui' | 'prompt'` 参数，**复杂度不减、耦合增加**。

### 3.2 更便宜的等价方案（任务点名要评估的）

| 方案 | 成本 | 能否达到目的 |
|---|---|---|
| 抽 `palette-truth.mjs` + 改两个 import | **高**（新文件 + 改 2 处生成器 + 重跑全链 + 快照对比） | 只能保证"数据源唯一"，不保证"语义正确" |
| `collect-schemes.mjs` 直接读 `dna-clean.json` | **中**（引入反向依赖：让 UI 数据依赖提示词链的中间产物） | **更糟**：把两条链变成串联，一处坏两处坏 |
| `check-twolines.mjs` 只对账报警、不改数据 | **低**（Lead 已落地，234 行） | 能防"关系被破坏"，但见 Q6：它防的是恒真式 |
| **只修 `collect-schemes.mjs:296` 的正则优先级** | **极低**（约 3 行） | **能修掉 5/30 案的真实错标** |

**「改数据」vs「只加闸门」的对比：**

- 只加闸门（现状）成本最低，但**闸门必须查对东西**。现在它查 R2/R3/R4，其中三条是恒真的（Q6），
  唯一非恒真的 R1 在 `ad69f20` 之后也是 30/30——**这套闸门目前一个 FAIL 都产生不了，它的价值是"防未来"，不是"抓现在"。**
- 改数据（修正则）成本 3 行，**立刻修掉 5/30 案的 UI 假话**。

**所以正确答案既不是"共享模块"，也不是"只加闸门"，而是"先修那 3 行，再谈闸门"。**
Lead 的 `PLAN-final.md` 任务 1 只修了 S24 的 `#6E8B7A` 漏抽（1 案），
**没有修这 5 案的主色错标——而后者对用户的影响比前者大得多**（S24 少一个绿色 vs S05 主色说错）。

### 3.3 为什么 Lead 会漏掉它

我给一个不客气的解释：**因为探针问的是"两链关系"，而错标是"单链内的语义错误"。**

四个 LEAD 探针的名字分别是：
`LEAD-check-subset`（子集）、`LEAD-check-order`（顺序）、`LEAD-check-extra-origin`（补色来源）、`LEAD-check-truncation`（截断）。
**四个全部围绕"两链之间"，没有一个问"这一条链自己说的对不对"。**

**这是框架决定视野的典型：当你决定"这是一个两链问题"，你就再也看不见单链问题了。**
这正好呼应任务 Q5 要问的「根本原因是没共享代码，还是没人知道有两条链」——
我的答案是第三种：**不是不知道有两条链，是"两链"这个框架把问题定义窄了。**

## Q6「测试能不能证明改对了」

### 6.1 任务问的核心：会不会「两个都错，一起错到同一个错误答案上」

**我的判断：这个风险在本轮已经部分兑现了。** 三条证据：

#### 证据 1：R2/R3 是构造恒真式，不可能失败

`check-twolines.mjs` 的 R3：

```js
if (dPal[1] && pri && dPal[1] !== pri) { add('FAIL', ...); }
```

而 `collect-schemes.mjs:484-485` 的构造是：

```js
const pal = [];
if (rec.bg) pal.push(rec.bg);                    // pal[0] = bg
if (rec.primary && !pal.includes(rec.primary)) pal.push(rec.primary);   // pal[1] = primary
```

**`pal[1]` 在赋值时就等于 `primary`。R3 拿它去比 `primary`，恒等。**
R2 同理（`pal[0] === rec.bg`）。R4（"底色与主色都在 palette 里"）也是构造保证的。

**这三条断言加起来占闸门 4 条硬断言里的 3 条，全部是恒真的。**
它们唯一的用途是"防有人手改 `data.js`"——但 `data.js` 是生成物，手改会被下次生成覆盖。

#### 证据 2：我在 §2 实测的 5 案主色错标，闸门一条都报不出来

```
check-twolines.mjs 实测输出：
  R1 data.js ⊆ prompts.js      30/30
  R2 palette[0] === bg         30/30
  R3 palette[1] === primary    30/30
  R4 底色与主色都在 palette    30/30
  R5 补色有 CSS 角色注释       33/52
  合计 FAIL 0 / WARN 1
  EXIT=0
```

**同一时刻，UI 上 5 个案子的「主色」标签是错的。闸门报绿灯。**

这就是任务问的「两个都错」的具体形态：
`data.js` 的 `primary` 错 → `palette[1]` 错 → R3 比的是「`palette[1]` vs `primary`」，**两个错值相等，断言通过**。

#### 证据 3：唯一非恒真的 R5，判据本身不可靠

R5 想查"prompts.js 补的色有没有 CSS 角色注释"。实测：

```

WARN: 19 个没有注释的色，例：S17[#C9BFA6 #3F1A38 #B9A98C #DFD6BF] S24[#DCE7EF #C9D8E4]
```

我用像素实测核对这 19 个"可疑色"：

```
S17 #C9BFA6   占屏 20.25%     ← 规格明写「次级纸色 8%」，是最主要的存根联区域
S06 #E6D8BC   占屏 11.00%
S24 #DCE7EF   占屏 10.29%
S24 #C9D8E4   占屏  4.39%
S06 #E0D0B0   占屏  2.81%
```

**这些色占了屏幕面积的一到两成，全部是真实使用的派生色。**
R5 把它们标成"可能是设计扩张"，**这个 WARN 是噪音，而且会训练读者忽略 WARN**。

更糟的是 R5 的判据是"`:root` 声明行末尾有没有 `/* … */` 注释"——
一个纯**排版偶然性**（作者把注释写在上一行 vs 同一行），与"这个色该不该进提示词"没有因果关系。

### 6.2 独立来源对账 vs 单一来源一致：哪个更可靠

**我的判断：独立来源对账更可靠，而本轮的操作在削弱它。** 论证：

- **单一来源一致**的可靠上限 = 那个来源的正确性。**它对"源本身错"完全免疫。**
  本轮 `pickPalette` 开始读 `_specs`，等于把提示词链的正确性**部分押在 `_specs` 上**。
- **独立来源对账**的价值恰恰在于两个来源的错误**不相关**，所以分歧能暴露问题。
  `check-prompts.mjs` 就是这种设计（提示词 vs `style.css` 真实声明），**它有实质价值**。
- 而 `check-twolines.mjs` 对的是**同一条上游**：
  `data.js` ← `_specs` ←（现在也）→ `prompts.js`。
  **`pickPalette` 读了 `_specs` 之后，R1（子集）这条断言就变成了"自己对自己"**——
  两链共享 `_specs` 这个上游，子集关系更容易成立，**而成立不代表对**。

**这正是任务 Q6 担心的「用同一个源算两次」：它在 `ad69f20` 里刚刚发生了一次。**

### 6.3 改完 `collect-schemes.mjs`，怎么证明 `data.js` 还是对的？

任务点名要答这个。我的答案分三层，按可靠性排序：

**第一层（最强）：对权威表逐案比对，且比对口径必须包含"角色"。**
不是比集合（Lead 比的是集合，漏了角色），而是比：
`palette[1]` 是否等于 `_CURRENT-VALUES.md` 的「主色（当前）」列。
**这一条现在会报 5 个 FAIL**（我在 §2.2 已实测）。

**第二层（中）：对规格原文做"角色标签"复核。**
按分句切 `_specs/Sxx.md` 字段 3，取带「主色」角色词的分句里的 hex，
与 `data.js` 的 `primary` 比。**B 分支正则 5/5 正确，可作为独立判据。**

**第三层（弱，但本轮唯一有的）：`check-stale` + 重渲染 + 闸门 29/1/30 不变。**
这一层只能证明"没有引入回归"，不能证明"改对了"。

**关键点：第一层和第二层是彼此独立的**（一个用 CV 表，一个用规格原文），
而现在的 `check-twolines` **一条都没用**。它用的是 `data.js` 自己。

### 6.4 一个具体的 A/B 测试建议（可机械执行）

要证明闸门有效，必须证明它能红。任务要求 A6「闸门自查：故意制造分歧必须报」。
**我对现闸门做了这个测试的推演：**

- 把 `data.js` 里某案的 `primary` 改成错的（模拟 §2 的 5 案）→ **R1/R2/R3/R4 全绿**（因为 `palette[1]` 没变，只有 `primary` 字段变了 → R3 **会**红，但前提是只改 `primary` 不改 `palette`）
- 把 `palette[1]` 和 `primary` **一起**改成同一个错值 → **全绿**。**这就是 §2 的真实情况：两者一致地错。**

**所以这条闸门无法发现"一致的错"。** 它可以发现"不一致的错"——但那恰好是它构造上排除的情形。

## §7 我认为这个长任务最大的方向性错误

> **最大的方向性错误是：把「两条链之间的一致性」当作要守护的不变量，
> 而真正的缺陷是「用数组下标表达语义角色」；选错了不变量，于是整轮的投入都花在了一个恒真的断言上。**

### 7.0 一个事后补上的强证据：`0f10d8e` 犯了同一个病

我写到 §7 时，还只是从 `data.js` 一侧看到这个问题。**收尾前 Lead 提交的 `0f10d8e`，
在提示词一侧犯了完全同构的错误**，这让我可以把这个判断从「一个观察」升级为「一个模式」：

| | §2 我的发现 | `0f10d8e` Lead 的发现 |
|---|---|---|
| 位置 | `data.js` 的 `palette[1]` → UI 印成「主色」 | `prompts.js` 的 `dna.palette[0]` → 提示词说「最大面积用第一个值」 |
| 表达方式 | 下标 1 **假定**是主色 | 下标 0 **假定**是最大面积色 |
| 实际正确率 | 25/30 | 12/30（Lead 实测） |
| 用户后果 | 主色标签说错 | AI 把强调色铺满整页（差 3–5 倍面积） |
| 修复方式 | **按角色查分句**（我建议的分句法） | **改成定性角色约束**（他已落地） |

**两边都把「index」当成了「role」。** 而且两边的修复方向也一致：
**不要点名下标，要按角色描述。**

**所以真正该守护的不变量是这一条：**

> **任何「角色 → 颜色」的映射，都必须来自对角色词的解析，不能来自数组位置。**

这条不变量是可以失败的、可以机械检查的，而且它一次能覆盖两条链。
相比之下，`palette[0]===bg` / `palette[1]===primary` 这两条既恒真、又只在 `data.js` 内部成立
（Lead 在 `0f10d8e` 里正是踩了「把 `data.js` 的顺序套到 `prompts.js`」的坑）。

### 7.1 为什么这是方向错误，而不是执行错误

三个层次：

**层次一：不变量选错了。**
`palette[0]===bg` 和 `palette[1]===primary` 是 `collect-schemes.mjs` **先 push 后比较**的产物，
它们**不可能失败**。守护一个不可能失败的关系，收益是 0。
而 `palette[1]` 是否**等于权威主色**，是一个会失败、且现在确实在失败的关系——**却没人查。**

**层次二：框架决定了视野（这是 §3.3 的深化）。**
「两链」这个框架一旦确立，探针就只会问"两条链之间怎么样"。
四个 LEAD 探针全部是两链视角，**没有一个问"这条链自己说的对不对"**。
于是 5 案的主色错标在整个 71 轮侦察里**一次都没被看见**——
它不在"两链"这个坐标系的任何一个象限里。

**层次三：这个错误会被固化进文档。**
`ad69f20` 已经把「实测确认两者语义不同且都合理」写进 README:176。
**「都合理」这三个字，在 `primary` 维度上是假的。**
下一轮的读者会读到这句话，然后不再检查主色。**这是一次知识库污染。**

### 7.2 为什么 Lead 的自我推翻仍然值得肯定

我必须说清楚：**Lead 撤回「合并两链」这个决定是正确的，且证据充分。**
子集 30/30、`data.js` 精确等于规格 4 色、53 个补色 51 个不在规格但必需——
这三条我都独立复核过，成立。

**但撤回得不够深。** 撤回的是"合并"，保留的是"两链关系"这个框架。
而框架本身的错误（视角过窄）没有被撤回。

**这是「正确地回答了一个错问题」的典型。**

### 7.3 如果这个判断成立，意味着什么

1. **`check-twolines.mjs` 需要重写 R2/R3/R4**：换成"`palette[1]` vs CV 权威主色"，
   立刻从 0 FAIL 变成 5 FAIL，闸门第一次有了实质产出。
2. **`ad69f20` 的 README 描述需要修正**：「都合理」应改为「`palette` 集合对，`primary` 语义 5/30 待修」。
3. **修 `collect-schemes.mjs:293-298` 的主色抽取（分句法）**，这是 UI 侧唯一能改掉用户可见事实的动作。
   **提示词侧 Lead 已在 `0f10d8e` 改对了；UI 侧还没改。**
4. **`pickPalette` 新引入的 `_specs` 依赖应当复审**：它削弱了两链独立性（§6.2）。
5. **把「index 不能当 role」写成一条仓库级规则**，因为它已经在两条链上各犯了一次。

> ### 关于 `0f10d8e`：它反过来印证了本报告的核心论点
>
> 我写完 §2（主色错标）之后，Lead 提交了 `0f10d8e`「修一条会让 AI 做坏站的提示词：**面积锚点用了错误的色**」。
> 它的发现是：`prompt-copy.js` 让 AI「最大面积用 palette 第一个值」，而
> `dna.palette[0]` 真正是「最大面积色」的只有 **12/30**。
>
> **这是同一个病，在另一条链上**：
>
> | | 我的发现（§2） | Lead 的发现（`0f10d8e`） |
> |---|---|---|
> | 位置 | `data.js` 的 `palette[1]` → UI「主色」标签 | `prompts.js` 的 `dna.palette[0]` → 提示词「最大面积」 |
> | 病因 | **用下标位置表达语义角色** | **用下标位置表达语义角色** |
> | 错案数 | 5/30 | 18/30（按他的口径） |
> | 用户后果 | 看到的主色是错的 | AI 把强调色铺满整页 |
>
> **两条链、两个下标、同一个错误模式：index 被当成了 role。**
>
> 而且 `0f10d8e` 的 commit message 自己记录了同一个陷阱：
> 「第一版我以为 `palette[0]` 是底色（因为 `data.js` 的 `palette[0]===bg` 是 30/30），
> 就改成『底色（第一个值）铺满』。但那是 **`data.js` 的 palette**——`prompts.js` 的 `dna.palette` 是**另一套顺序**。」
>
> **他踩的正是我在 §2.5 描述的那个坑**：`palette[0]===bg` 这条「30/30 成立」的不变量，
> 只在 `data.js` 里成立，且是构造出来的；一旦跨链套用就错。
>
> **这让我更确信 §7 的判断**：本轮真正的不变量应该是「**角色不能靠下标表达**」，
> 而不是「两条链的 palette 要相等/要成子集」。Lead 在提示词侧已经改对了（改成定性角色约束），
> 但**在 UI 侧（`palette[1]` 印成「主色」）还没改** —— 那正是 §2 的 5 案。
