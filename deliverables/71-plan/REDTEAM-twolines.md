## P2「合并成单一来源不会丢信息」→ **判定：不成立（两个方向都会丢），而且现在已经在丢**

### 前提原文
> - 只从规格文本抽，会不会丢掉 `:root` 里有但规格没写的色？（参考 S19 的 `#D8CFB6`）
> - 只从 `:root` 抽，会不会丢掉规格里写了但 CSS 没用到的色？
> - 两条链的过滤逻辑不同……合并时**用谁的过滤逻辑**？

### 实测 A：只从 `:root` 抽 → 会丢掉"规格写了但 CSS 没用"的色（但这是**应该**丢的）

S19 的 `#D8CFB6` / `#E9E3D2` / `#3A3227` 三个色：

| 色 | 在 S19 style.css | 在 S19 规格 |
|---|---|---|
| `#D8CFB6` | ✅ | ❌ |
| `#E9E3D2` | ✅ | ❌ |
| `#3A3227` | ✅ | ❌ |

所以"只从规格抽"确实会丢掉这三个色——**但它们本来就该丢**：规格字段 3 的四个色面积和是 100，
这三个是 CSS 里的派生阶（纸色深浅、木色明暗），不属于"设计意图"层。这是 P1 结论的正面用例。

### 实测 B：只从规格抽 → 会丢掉**合法**色。这不是假设，是现状（新问题①）

**S17 的 `#C9BFA6`：**

| 证据 | 内容 |
|---|---|
| 规格字段 3（`style.css:6` 逐字抄录） | `纸 #E1D6BD 52%／主墨 #5A2A50 30%／印花红 #7A2E2E 10%／压纸色 #C9BFA6 8%` |
| `style.css:10` | `--stub: #C9BFA6;`，`var(--stub)` 被引用 **6 次** |
| `_CURRENT-VALUES.md:56` | **`#C9BFA6` 明确标注为「次级纸色（存根联专用压纸色，此色不作背景）」** |
| 链 A 的剔除日志 | `S17 剔除 #C9BFA6(§2 作废旧值)` |

**`_CURRENT-VALUES.md` §2 的真实语义是"旧值 → 新值"的替换表。**
而 S17 这一行里的 `#C9BFA6` 是**限制性说明**（"此色不作背景"），**不是替换关系**。
`collect-schemes.mjs:478` 的 `(stale[id]||[]).includes(h)` 把"出现在 §2 那一行"当成了"已作废"。

后果：
- `data.js` 的 S17 = `["#E1D6BD","#5A2A50","#7A2E2E"]`（3 色），**少了规格声明占比 8% 的那个色**
- `prompts.js` 的 S17 保留了它（`clean-dna` 根本不读 `_CURRENT-VALUES`）
- 而 `ad69f20` 的新闸门 **R1 不会报红**——因为这是"少报"，不是"多报"

> 重跑：`node deliverables/71-plan/redteam/rt-x8-stale-false.mjs`

### 实测 C：两套过滤逻辑的判据表（合并时"用谁的"没有好答案）

| | 链 A `collect-schemes.mjs` | 链 B `clean-dna.mjs` |
|---|---|---|
| 输入 | `_CURRENT-VALUES.md` + `_specs/Sxx.md` + 样式面 | `dna-raw.json`（=`style.css` 的 `:root`） |
| 取色范围 | 规格全文所有 hex | 仅 `:root` 里有 hex 值的声明 |
| 过滤 1 | `stale`：§2 作废旧值 | 无 |
| 过滤 2 | `keepHex()`：否定语境（`NEG` 正则）+ 角色标签三条通路（`ROLE` / `ROLE_NAME_AFTER` / `ROLE_NAME_BEFORE_OK`）+ `USAGE_WORDS` | 无 |
| 过滤 3 | `inStyle()`：样式面必须出现 ≥1 次 | **隐含**（`rowColors` 来自 `:root`，天然在 CSS 里） |
| 上限 | **4**（`:486` `pal.length >= 4`） | **7**（`:1003` `MAX = 7`） |
| 排序 | `bg` → `primary` → 规格顺序 | 主色判据（注释/变量名/文件头）→ `:root` 声明顺序 |
| 是否读规格文本 | **是**（权威） | **否**（`ad69f20` 之后才开始读，仅为"补位"） |

**实测剔除量（链 A，`--check` 日志）**：
```
调色板剔除 87 个候选 hex：否定语境或无角色标签 66｜样式面 0 次 12｜§2 作废旧值 9
```
87 个候选里只活下来 115−87 = 28…（注：30 案 palette 合计 115 项，其中 3 项来自 bg/primary 直接 push）。
**这道过滤是有损的，而且已经证明有 1 个假阳性（S17）。**

### 判定：**不成立**

- "合并成单一来源"必须选一套过滤逻辑，而：
  - 选链 A 的 → 继承 `stale` 的假阳性（S17 已实测），且上限被锁在 4
  - 选链 B 的 → 丢掉链 A 全部的否定语境过滤，`#6366F1`（30 案里 28 案都出现在"反的是"里）会大规模回灌
- 更关键：**丢信息的两个方向都存在，而且性质不同**。链 A 丢"CSS 派生阶"（应该丢），
  链 B 丢"规格声明但 `:root` 排位靠后的色"（不该丢，S24 就是）。
  单一来源无法同时正确——因为**正确答案依赖于"这个色在哪个层次上被问"**。

## P4「用户真的被误导了」→ **判定：不成立（证据不足）。WP4 应该砍掉或降级**

### 前提原文
> 我发现的现象是：选型台画 3–4 个色块，提示词要求 4–7 色。请攻击这个推论。

### 实测：色块是**无标签**的，也不声称"全部"

| 位置 | 实测 |
|---|---|
| `app.js:508` | `(r.palette||[]).slice(0,4).map(h => '<i style="background:'+h+'" title="'+h+'"></i>')` |
| `style.css:474-475` | `.swatches { display:flex; gap:3px }` / `.swatches i { width:20px; height:20px }` |
| 色块旁的文案 | **只有 `<i>` 元素，title 是 hex 值，没有任何"这是全部配色""4 色"字样** |
| `app.js:508` 附近的注释 | 讲的是 `.row-family` 折两行、行高实测、390 档 +21~48px——**没有一个字为"4 个色"辩护** |

**所以：既没有"用户被误导"的证据，也没有"4 个是刻意设计"的注释证据。**两者都缺。

### 实测：多画不一定更好（支持"4 个够用"的一部分）

对每案 prompts 的色板算两两 RGB 欧氏距离（阈值 24）：

| 指标 | 实测 |
|---|---|
| 提示词色板内存在近重复对的案 | **17/30** |
| 近重复对总数 / 色对总数 | 31 / 405 |
| 比台面多画的案 | 22/30，合计多 52 个色块 |
| 这些多出来的色里至少含 1 个近重复的案 | **17/22** |
| 额外色**全部可区分**的案 | 5/22 |

实例（S24）：`#E6EDF2 ~ #F3F8FB` ΔRGB=19、`#E6EDF2 ~ #DCE7EF` ΔRGB=12
——在 20px 色块并排、间隔 3px 的条件下，这两对基本看不出差别。
（同一量级：`2dadd81` 曾因 `#0B0B0F` vs `#0A0A0D` 差 2.4 而认定"看视觉差异发现不了"。）

> 重跑：`rt-p4-swatches.mjs`

### 但这条证据**不足以**证明"用户没被误导"

它只证明"多画不总是更好"。在一个 22/30 多画、其中 17 案含视觉重复的分布下，
"画 4 个"是一个合理的展示策略；但它**仍然**可能让用户以为"这个设计只有 4 个色"。
判定这件事需要用户侧证据。

### 仓库里有没有用户侧证据？——**实测：0 条**

我搜了全部 commit（83 个）、README、以及 `deliverables/*-plan|audit|exec/` 下的观察类报告：
没有任何一条记录"用户把色块数当成了色板总数"、没有任何用户访谈/可用性测试记录。
与配色相关的三条 commit 全是**修复数据污染**，不是修复"用户误解"：

## P5「共享模块是正确形态」→ **判定：前提已被现实废除（Lead 已放弃），但当时给的理由是错的**

### 前提原文
> 抽 `_build/lib/palette-truth.mjs`，让两个生成器都 import 它。

### 实测：两个生成器的运行环境**其实是一样的**

计划 §P5 猜"一个是否依赖浏览器/CDP"。实测：

| 生成器 | `child_process`/`spawn`/`puppeteer`/`cdp`/`http` | 输入 |
|---|---|---|
| `collect-schemes.mjs` | **0 处** | `_specs/*.md`、`style.css`、`index.html`、`assets/*.svg`、`.inspect/report.json`、`_CURRENT-VALUES.md` |
| `clean-dna.mjs` | **0 处**（`:171` 只是注释里提到 CDP） | `dna-raw.json`、各案 `style.css`、`index.html` |

**两个都是纯 `node` 直接跑、纯 `readFileSync`。** 计划里"一个依赖 CDP 所以签名别扭"的担心不成立。
真正的差异不在运行环境，而在：
- 输入集不同（链 A 读规格，链 B 不读）
- 上限不同（4 vs 7）
- 过滤逻辑不同（见 P2 实测 C）

### 方案对比（至少 2 种，按"单一来源彻底度 / 耦合 / 风险"排）

| 方案 | 单一来源彻底度 | 耦合 | 实测风险 | 判断 |
|---|---|---|---|---|
| **A. 抽 `_build/lib/palette-truth.mjs`**（原计划） | 高 | 中（两个生成器都 import） | 合并过滤逻辑必然丢信息（P2 已证）；且 `clean-dna.mjs` 是无 `--check` 的写盘脚本，抽公共模块后**改一处要同时重跑两条链**，`dna-clean.json` 会被迫重写 | **否决** |
| **B. 让 `data.js` 直接 import `prompts.js` 的 palette** | 最高 | **最强**（生成顺序倒置：`data.js` 要先有 `prompts.js`） | `prompts.js` 由 `clean-dna` + `build-prompts` 两级生成，`data.js` 由 `collect-schemes` 生成；倒置会让 `collect-schemes` 依赖一条它现在完全不依赖的链，`check-stale` 的链条要重画 | **更差**：把"两条独立链"变成"一条串行链"，任一环陈旧都会同时污染两侧 |
| **C. 不合并，建关系闸门**（`ad69f20` 实际采纳） | 低（不追求单一来源） | 最低 | 子集判据单向（漏报查不出，见 P2/new①）；alphabet 顺序语义仍无守卫（new③） | **当前最优**，但不是终点 |

### 判定：**前提不成立 / 已被废除**

"共享模块是正确形态"这个判断在**运行环境**层面没有障碍（我实测两边都无浏览器依赖），
但在**语义**层面不成立：两个生成器要的不是"同一份数据"，而是"同一份数据的不同投影"。
共享模块会把投影选择权从各自手里收走，而 P2 已证明没有一个投影是普遍正确的。

**补充（对 Lead 真正有用的一条）**：`clean-dna.mjs` 没有 `--check`，它 `:1295` **无条件写盘**。
任何"改 `clean-dna.mjs` 然后验证"的流程都必须先接受"工作区会被改写"。
这一条在计划 §4 的风险表里**没有**。

而 P2 证明没有一个过滤逻辑能同时服务两层（链 A 丢派生阶是对的，链 A 丢 S17 是错的）。

**为什么不是 WP4（UI 诚实性）：**
它建立在"用户被误导"这个**零证据**的推论上（P4），而且要动一个历史上反复改坏的首屏。

**如果还能做第二件**：给「`palette[0]` 的位置语义」补一条外部断言
（`prompts.js` 第 0 位 = 主色 ∧ 提示词面积句引用它），把新② 这类漂移永久钉住。
这正是新④ 说的"守卫不对称"该补的那一半。

### 我对这个长任务的总体判断（明确表态）

**「让用户看到的等于用户拿到的」这个长任务，按原方案不应该做。**

- 它的地基（P1：两条链描述同一件事）**已经被 Lead 自己的结论推翻**——两条链正确且互补。
- 它的动机（P4：用户被误导）在仓库里**零证据**，且有一个反向事实：4 色块是数据层上限，不是 UI 截断。
- 它的手段（P5：共享模块）会**主动制造** P2 证明的丢信息问题。

**但同一框架下有两件事必须做，且都还没做：**
1. **new② 修 `prompt-copy.js:730` 的面积锚点**（20/30 案正在给出会让站做坏的指令）
2. **new① 修 `stale` 假阳性 + 把子集判据做成双向**（否则链 A 越漏，闸门越绿）

这两件都不需要合并数据源，都不动已跟踪生成物的形状，都能用一条命令验收。


1. **把「顺序」纳入闸门。** P1 只让它查集合，而顺序是两个消费方真正的依赖
   （`app.js` 靠位置标"底色/主色"，`prompt-copy.js` 靠位置定面积）。现在 29/30 案顺序不同且**无人守**。
2. **双向验证子集。** 只查 `data ⊆ prompts` 会让链 A 越漏越绿（S17 就是活证据）。
   至少加一条"规格字段 3 声明的每个色都必须出现在 `data.js` 的 palette 里"。
3. **别再把「0 案不一致」当「两边一致」。** `dna.bg`/`dna.primary` 根本不存在，
   计划表格里的两个 ✓ 是空对空。对账表的第一列应该是"该字段在两边都存在吗"。
