### §3.1 `primary` 的冲突证据（最值得看的一条）

`collect-schemes.mjs:296` 三条正则的优先级是：

```js
const primM = /主色[^#\n]{0,24}(#[0-9A-Fa-f]{6})/.exec(p3raw)     // ① 主色 → hex
  || /(#[0-9A-Fa-f]{6})[^#\n]{0,24}主色/.exec(p3raw)              // ② hex → 主色
  || /主色[\s\S]{0,40}?(#[0-9A-Fa-f]{6})/.exec(p3raw);            // ③ 宽松
```

②在 **5 案**上给出不同答案（`⚠ r1/r2 冲突` 列），而 ① 被无条件优先。
S02 的原文是：

> `` `#B8860B` 暗金＝主色与纹样，18% ``

主色 hex 在「主色」**之前**，① 于是往后抓到了下一个色 `#EFE6D0`（正文色）。
**这是 regex1 的判据写反了，不是数据错。** 5 案名单：S02 S05 S07 S09 S10。

> **✅ 已被上游修复。** 提交 `9a3d18e` 把这三条正则换成「按 `；。换行` 切分句 →
> 只留含『主色』且不含否定词的分句 → 取该分句里离『主色』最近的 hex」，
> 并在注释里引用了同样的 5 案名单与「单纯调换 A/B 顺序会打到 16/30」的实测。

## §4 Q2 `palette` 语义判定（最重要）

### 结论：**(b) 两个都对、语义不同** —— 但 L1 的截断规则本身有一个确定缺陷

不是 (a)。理由不是"看起来都合理"，而是四组独立数据：

#### 证据 1：L1 ⊂ L3 在 30/30 成立

每一案里，`data.js` 的 palette **每一个色都出现在** `prompts.js` 的 palette 里，无一例外。
若两者是"一个错一个对"，正确的那个不会**恒为**另一个的超集。

#### 证据 2：被丢掉的 52 个色，多数是同一色族的近邻，不是独立的色

| 判据 | 数量 |
| --- | --- |
| 被丢色总数 | 52 |
| 与最近保留色 **ΔE < 10**（肉眼几乎不可分） | **33** |
| ΔE ≥ 10 **且**在 `:root` 里有角色名（真正独立的第 5+ 种色） | **19** |

实例（`04-dropped-attribution.json`）：

| 案 | 被丢色 | 面积% | 最近保留色 | ΔE | `:root` 角色名 | 判定 |
| --- | --- | --- | --- | --- | --- | --- |
| S06 | #E4D5B8 | 62.13 | #ECDEC6 | 4.23 | `--pale` | 近邻噪声 |
| S03 | #0C1417 | 44.738 | #101A1C | 3.13 | `--panel-2` | 近邻噪声 |
| S24 | #DCE7EF | 29.052 | #E6EDF2 | 3.10 | `--paper-3` | 近邻噪声 |
| S02 | #111111 | 29.976 | #0B0B0F | 2.72 | `--ink` | 近邻噪声 |
| S27 | #FFFFFF | 15.852 | #E8D7B5 | 23.22 | `--white` | **独立** |
| S23 | #B7A78C | 0.495 | #DCDCC8 | 19.76 | `--mortar-lit` | **独立** |

**关键**：逐 hex 统计会**把同一色族切成几块**。S06 的页面底色被纹理/渐变渲染成
`#E4D5B8` 这一族值，逐 hex 最近邻归类把它判给了那个 hex，于是 `data.js` 的
`#ECDEC6` 只剩 0.169%。这不是"data.js 少了 62% 的颜色"，是**测量口径把一族色拆开了**。

#### 证据 3：按「色族」重算（ΔE<10 聚类），data.js 在色族层面基本没漏

| 指标 | 值 |
| --- | --- |
| 面积落在「含任一 L1 色」的色族 | **约 92%** |
| 面积落在「完全不含 L1 色」的色族 | **约 1%**（多次连测 0.93–1.15） |
| 存在「完全不含 L1 色」色族的案 | 15/30 |
| 其中面积 > 1% | S02 S05 S08 S17 **S27 16.157%** |
| 其中面积 > 5% | **仅 S27** |
| L1 的 4 个色各自独立成族（没浪费槽位） | **30/30** |

**所以 L1 的 4 个色是「4 个不同色族的代表」，并没有重复占位。**
唯一一个**稳定复现**的严重漏色是 **S27**：`#FFFFFF` 占首屏 15.85%，被 `data.js` 截掉了
（它在 `prompts.js` 里排第 6 位，正是 `MAX=7` 才保住的）。

> **测量波动（如实记录，这条很重要）**：像素面积**不是**完全确定性的。
> 我把 `03-pixels.mjs` 连跑 3 次逐案比对，每次的"不稳定案"名单**都不一样**：
> 第一次 S18/S22、第二次 S26/S22、第三次 S23……
> 实测不稳定的案**始终只有 2/30**，但**是哪两案每次都不固定**。
> 成因是首屏有 `@keyframes` / `IntersectionObserver` 显现动画（S18 有 3 组 keyframes、
> S23 有 4 个 IntersectionObserver），截图落在动画的不同相位。
>
> **这直接推翻了我自己的一个中间结论**：我曾在一次运行里读到「S23 独立被丢色占 7.667%」
> 并据此把它列为第二个「必须显示第 5 色」的案。重跑三次后 S23 稳定在 **0.93%**，
> 那个 7.667% 是**动画相位的伪影**。
> 因此本报告只保留**跨多次运行稳定复现**的结论：
> - 「独立色部分仅约 1%」——稳定（0.93 / 0.91 / 1.15）；
> - 「被丢色合计约 10%」——稳定（9.48 / 9.72 / 9.75）；
> - 「S27 的 #FFFFFF 占 15.85%」——稳定（三次均为 16.53% 的 dropped，其中 15.852% 是该色）；
> - 逐案百分比一律视作 **±1pp**，S18/S23/S26 这几个有动画的案更大。

#### 证据 4：`app.js:508` 的 `slice(0,4)` —— 「取前 4 个」这个策略本身是对的

用实测面积作裁判，三种策略对比：

| 策略 | 平均面积覆盖 | 平均保真（4 个里有几个真在前 4） | 完全命中前 4 |
| --- | --- | --- | --- |
| `data.js` 的 3–4 色（现状） | 83.38% | 3.10/4 | 10/30 |
| `prompts.js` 的 `slice(0,4)` | **84.19%** | **3.27/4** | **14/30** |
| 按实测面积取前 4（理论上界） | 91.96% | 4/4 | 30/30 |
**「取 L3 前 4」比「用 L1 的 3–4 色」更好，且没有任何一案更差**（更差：无；更好：S14 S17 S22 S28 S30）。

> **结论：「取前 4 个」不是错误的策略。** 它比现状更接近真实，且从不变差。
> 真正的问题在别处 —— 见下面的"位置语义"。

#### 证据 5（决定性）：两套 palette 的**位置语义**不同

这才是 (b) 最硬的证据。同一个位置 `[0]`，两层放的是不同角色：

| 位置语义 | L1 data.js | L3 prompts.js |
| --- | --- | --- |
| `palette[0] === 底色` | **30/30** | **7/30** |
| `palette[0] === 主色` | 0/30 | **21/30** |
| `palette[0]` 既非底色也非主色 | 0 | 2/30（S04 #2F7D4F、S14 #C9C4B8） |
| `palette[1] === 主色` | **30/30** | — |

`app.js:956-966` 的 `paletteLine()` **硬编码**了这个角色假设：

```js
out = '底色 ' + p[0] + '　主色 ' + p[1] + (p.length > 2 ? '　' + p.slice(2).join('　') : '');
```

> **若按「让两者相等」去修（把 UI 改读 L3 的 7 色）：**
> `palette[0]` 会被标成「底色」而它其实不是底色的案 = **23/30**；
> `palette[1]` 会被标成「主色」而它其实不是主色的案 = **23/30**。
> **这个修法会直接制造 23 处错误标签。** 这就是 (a) 修法为什么不可行的实证。

### §4.1 正确的修法（不是让它们相等）

1. **保留两个字段，但改名消除歧义**
   L1 的 `palette` → `paletteUi`（底色优先，4 色，给色块用）；
   L3 的 `dna.palette` → `palettePrompt`（主色优先，≤7 色，给提示词用）。
2. **UI 必须诚实说明"你看到的是 4 个，完整配色有 N 个"**
   现状 `slice(0,4)` 静默丢弃了 1–3 个色。建议在色块行尾加 `+3` 角标或 `共 7 色` 文案。
3. **`paletteLine()` 不能再无条件给 `p[1]` 标「主色」**
   改成读真实的 `r.primary`，而不是靠位置猜。实测 3 案的 `primary` 本身是低彩度色
   （S15 #3A3F45、S21 #3E3A34、S22 #565B49），这些案标「主色」时要额外说明。
4. **把 L1 的截断上限从 4 提到与 L3 一致（7），或至少在 `data.js` 里保留完整数组 + 一个 `paletteVisibleCount`**
   这样 UI 能自己决定画几个，而不是数据层替它决定。

**UI 应该展示哪几种色（具体建议）**：
- 4 个色块不变（版面约束），但**顺序改为「底色 / 主色 / 其余按实测面积降序」**；
- 补一个 `共 N 色` 计数与展开；
- 若某案的"独立被丢色面积 > 5%"（**实测只有 S27 16.157%**），**必须**显示第 5 个色。

## §5 Q3 `fonts` 形状建议

### 结论：**保持两个字段，但改名 + 补结构化投影**

#### 检查 1：UI 怎么用 `data.js` 的 fonts？——**只有两处，都是纯文本**

`document.fonts`、`fonts.check(`、`FontFace`、`measureText` **命中数均为 0**。

> **所以"UI 需要结构化"这个前提不成立。** UI 只是展示文字。

#### 检查 3：提示词侧确实需要结构化

`prompt-copy.js:176-179` 需要 `display/body/mono` 三个槽来拼提示词，
且该对象 30/30 由 `clean-dna` 产生、30/30 原样进 `prompts.js`。
`build-prompts.mjs:300` 记录了旧版"按数组顺序猜标题"曾**错 7/30**。

#### 检查 4：两侧的**值**语义不同

| | L1 data.js | L2/L3 prompts.js |
| --- | --- | --- |
| 内容 | 规格字段 4 **原文**（含"为什么不用某字体"的论证） | 从 `:root`/h1 解析的**可执行族名栈** |
| 与原文关系 | **30/30 逐字相等** | 解析产物，26/30 与 CSS 标题一致 |
| 用途 | 给人读、给搜索 | 给 AI 执行 |

若强行统一成对象 → 丢掉规格原文里的取舍论证（最多 513 字/案）；
若统一成字符串 → `prompt-copy` 又得回去用正则猜（已知会错 7/30）。

### 建议

| 项 | 做法 |
| --- | --- |
| **保留两个字段** | `data.js` 的 `fonts` → **改名 `fontsSpec`**（规格原文，供展示/搜索）<br>`prompts.js` 的 `dna.fonts` 保持 `{display, body, mono, displayStack, bodyStack}` |
| **不要合并** | 合并会丢掉"设计意图 vs 落地事实"的区分，而这两者在 4/30 案上确实不同（S11 S19 S23 S24） |
| **补投影（可选）** | 若将来 UI 要做字体可用性提示，加一个 `fontsResolved`（从 L2 投影 3 个族名），而不是把原文塞进对象 |

> **这次分叉的真正代价是命名，不是形状**：两处都叫 `fonts`，读代码的人会以为它们是同一个东西。
> 改名是成本最低、收益最高的修法。

- 逐 hex 统计面积会把**同一色族切成几块**（S06 的 62% 假象）→ 改用色族聚类（`10-clusters.mjs`）；
- 对照实验 A1 原本断言"两次截图逐字节相同"（过强）→ 改为"差异 <1% 且面积统计跨度 <0.5pp"（实测 0）。
