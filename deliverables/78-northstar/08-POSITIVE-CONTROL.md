## 一、S97 本身的结论（不受影响）

**一份完全泛化的描述（「干净、现代、留白充足」、无机制句、无任何数值）
让模型做出了 466 行、20853 字节的完整品牌首页。**

```
466 行 / 20853 字节
10 个自选色值：#1A1917 #33503B #3E5C46 #54504A #6A655C
                #C9C1B2 #DFD9CE #EAE4DA #F6F3EE #F7F4EE
22 处 grid / flex 布局
字号比 3.41（无目标值，自定）
零机制引用（没有 tick / 刻度 / ruler / 尺寸）
```

**这条独立回答了一个问题**：模型在没有具体约束时，会自己挑一组协调的值，
做出一个「通用好看页面」。

这也间接回答了红队最初的疑问：
**「模型对任何风格描述都给一个通用好看页面」——在描述足够泛化时，这个假说成立。**

但 S31 不是那种情况：S31 的十个可测值精确命中（配色 5/5、刻度参数 `60/34/3` 与 `12/12/2`），
而 S97 的通用页面是自己编的 10 个色、自定的 3.41 倍字号。

## 二、~~S97 vs S98 的对比~~（已作废）

| | S98 | S97 |
|---|---|---|
| 有没有具体机制 | **有**（横向尺规、主次刻度、贯穿基线） | 无（只说「干净、现代、留白充足」） |
| 有没有数值 | 无 | 无 |
| 有没有可验收的判据 | **有但不完整** ——「主刻度间隔宽、刻线长而粗」，**宽多少？长多少？** | 无 ——「看着舒服」就行 |
| 结果 | **零产物** | 466 行 |

**S98 的任务是「具体到需要精确值，但没给值」——这是最难的状态。**
模型知道要做尺规、知道要有主次两级、知道间距要成倍数，
但每一个「多少」都没有答案，于是它反复权衡，永远不收敛。

S97 的任务是「什么都不具体」——模型随便挑一组它觉得好看的值就完成了。

### 2.3 所以准确的结论是

```
不是：靠数值，不靠文字。
而是：靠可收敛的具体约束。数值是最有效的收敛锚点，
      但缺了锚点时，任务越具体反而越难收敛。
```

**「半个具体」比「完全不具体」更糟。** 这是这个实验最有用的一条。

## 四、这条对产品意味着什么

### 4.1 好消息

- 提示词给足数值时，模型能精确复刻（S31 + S99，11 次验证）
- 提示词什么都不给时，模型也能做出可用的通用页面（S97）
- **最坏的情况是「给了一半」** —— 有机制描述但缺数值（S98），会完全卡住

### 4.2 一个真实的产品风险

如果某一案的 `dna` 里机制句写得很具体（「主刻度间隔宽、刻线长而粗」这种），
但数值缺失（比如 `h1Size` 或 `lineWidths` 抽取失败），
**用户会拿到一份 AI 用不动的提示词**，而且从文本上看不出来。

这正是 `plain` 为空、`minPics` falsy-0 那类缺陷的另一种形态：
**数据缺失不会报错，但会让提示词失效。**

### 4.3 建议加一条闸门

检查「机制句里有多少个可测诉求，`dna` 里有多少个对应的值」。
如果机制句说「每 60px」而 `dna` 里没有这个数，就是同一类缺陷。

这条闸门现在没有。本轮已发现的两个同类缺陷（`plain` 空、`minPics` falsy-0）
都是**事后**才发现的。

## 五、四轮实验的完整对照

| 实验 | 数值 | 机制 | 产物 | 说明 |
|---|---|---|---|---|
| S31 | ✅ | ✅ | 399 行，六值精确 | 数值 + 机制 = 可精确复刻 |
| S99 | ✅ | ✅（虚构） | 459 行，9 值精确 | 数值通道与风格无关 |
| S98 | ❌ | ✅ | **零** | 半个具体 = 卡住 |
| S97 | ❌ | ❌ | 466 行，自定值 | 完全泛化 = 通用页面 |

**两个有数值的都产出了且精确命中；两个无数值的，泛化的做了、具体的卡住了。**

这个模式比「靠数值不靠文字」更准确，也更有产品价值 ——
它指出了一种具体的失败形态：**提示词看起来完整，但缺关键数值时会静默失效。**

## 六、顺着这个发现查出的一件事：33/35 案的可测值只出现在机制句这一句话里

S98 暴露的失败形态是「机制句具体、但值缺失」。我据此查了现有 35 案：
**机制句里的可测值，有没有第二处承载？**

### 6.1 第一版检查是恒真的（记下来，因为差点拿它当结论）

我最初写的是「机制句里的数字，能不能在 `JSON.stringify(dna)` 里找到」。

结果 35/35 全中。但这个检查**必然全中** —— 因为机制句本身就在 `dna` 里，
拿数字去 `dna` 里找，等于去它自己里面找。

实测证据：S31 的 `34px` 与 `60px` 只出现在 `dna.mechanism` 和 `dna.risk` 里，
而那是同一段文字的两个副本，不是一个独立的数值字段。

### 6.2 修正后的检查

排除 `mechanism` / `risk` / `reuse` / `degrades` 这几个**描述性**字段，
只在实际承载数值的结构化字段里找（`lineWidths` / `h1Size` / `bodySize` / `palette` / `fonts` 等）。

结果：

```
机制句含可测值的案：           35/35
有值只在机制句里出现的案：      33/35
全部值都有独立字段承载的案：     2/35   （S04、S35）
```

举例：

```
S03  6 个值，只有 1 个在数据字段里，其余 264px / 40px / 32% / 264:524:540 / 1:0 只在机制句
S30  7 个值，0 个在数据字段里：32° / 96px / 9px / 28px / 1.5px / 55% / 70%
S31  5 个值，2 个有：其余 60px / 34px / 12px 只在机制句
```

S04 与 S35 之所以「全中」，是因为它们的机制句数字（`3px`、`1px`）恰好与
`lineWidths` 重合 —— 巧合，不是设计差异。

### 6.3 这意味着什么

**这不是缺陷，是设计选择。** 机制句本来就是承载这些数的地方 ——
它是这个产品最核心的一段文字。

但它有一个真实的脆弱点：

> 每一个案子的核心可测值，**都只靠机制句那一句话承载**。
> 那句话被改写、被截断、或者在生成时丢了数字，就再没有第二处能补上。

而 S98 证明了这种缺失**不会报错** —— 提示词读起来完全正常，模型却因此卡死。

### 6.4 建议（未实施）

加一条闸门：**机制句里出现的可测值，必须至少有一处在结构化字段里复述**。

判据可以复用上面这个脚本。它对现状会报 33 案不达标 ——
所以不能直接当 FAIL，应该当 **WARN + 逐案登记**，先看清哪些是合理的
（比如 `264:524:540` 这种组合比例，本来就没有独立字段可放）。

或者更简单：加一条「机制句不得为空、且必须含至少一个带单位数字」的断言。
这条现在没有，而机制句丢了数字**是会被静默接受的**。
