## 二、图片判据：74% 的案从未被检查

`prompt-copy.js` 里图片这一段有**三条**互斥分支（`:1136-1181`）：

| 分支 | 触发条件 | 句式 |
|---|---|---|
| strict | `have == 0` 或 `have >= minPics` | 「至少要 N 个**不同的**图片位置」 |
| alt | `0 < have < minPics` | 「这个版式有 N 个图片位，但你只有 M 条内容」 |
| zero | `minPics == 0` | 「本案是零图片设计」 |

`score.mjs:213` 只认第一条：

```js
const picM = prompt.match(/至少要\s*(\d+)\s*个\*{0,2}不同的\*{0,2}图片位置/);
```

而 `acp-run.mjs:96` 把测试输入写死成 `have: 5`。按这个输入分派，35 案的实际分布是：

```
strict「至少要 N 个」      9 案
alt「有N个位但你只有M条」  25 案   ← 评分器不认
zero「零图片设计」          1 案   ← 评分器不认
```

**未判覆盖 26/35 = 74%**。四个已测案里，S01、S19 走 alt，S34 走 zero，只有 S13 落在 strict。

后果直接可见：

| 案 | 提示词要求 | 实际 HTML | 评分器输出 |
|---|---|---|---|
| S01 | 6 个图片位、5 条内容 | 4 img / 4 唯一 src | **整行不存在** |
| S19 | 6 个图片位、5 条内容 | 5 img / 5 唯一 src | **整行不存在** |
| S34 | 零图片设计 | 0 img | **整行不存在**（做对了也没人知道） |
| S13 | 至少 4 个不同图片位 | 4 img / 4 唯一 src | `图片 提示词要 4 个位置；HTML 里 4 个 img` |

S01 和 S19 少放的那一两张图，是提示词**自己允许的**（"空出来的图片位改成留白或文字块"）。
所以这不是模型的问题，是判据没有对应的判分逻辑 —— 而且连"这里应该判"这件事都没有输出。

## 三、条目判据：量错了对象（第 4 类缺陷）

提示词原文（以 S19 为例，`_prompt.txt:21-22`）：

```
1. 这个版式设计时排了 20 个条目——这是版式的规模，不是你的内容量。
2. 你手上有 5 条内容，就排 5 条：不凑整、不留占位符。
```

**提示词明确要求 AI 排 5 条，不要排 20 条。** 而 `score.mjs:203` 拿 HTML 里的
`<article>` 数量去比 20，容差 ±2：

```js
const want = Number(itemM[1]);
st.items = { want, counts, closest, hit: Math.abs(best[1] - want) <= 2 };
```

实测 S19：AI 排了 5 条（完全遵照提示词），评分器报"最接近 article=5（启发式，仅供参考）"。

这个判据的两个问题：
1. **比错了对象** —— 应该比 `have`（5），不是 `minItems`（20）。
2. **量错了层** —— 提示词说的是"版式规模"，是 CSS 网格的设计尺度，不是 DOM 元素数。
   即使比 `have`，数 `<article>` 也只是在猜 AI 用哪个标签表示"一条内容"。

`70-blindtest-round1.md` §7 自己写了这一条：「结构条目数要能区分"设计规模"与"实际放置数"」，
但同一份报告的 §0 结论是「二十项检查全部通过」。

## 四、附带确认：`hard=true` 是真的

四个 `hard` 案都确实依赖 JS（`prototypes/SXX/index.html` 里的 `<script>`）：

| 案 | script 标签 | 机制依赖什么 |
|---|---|---|
| S15 | 2 | 滚动翻状态、悬停热区、三层透叠的年份切换 |
| S18 | 2 | 行尾方波 |
| S21 | 1 | IntersectionObserver 触发释放路径 |
| S29 | 2 | — |

S15 的机制甚至包含 `layerOf` 年份映射 + `matchMedia('(prefers-reduced-motion)')` 降级 ——
这类东西**没法只靠静态 HTML 复现**。所以 `hard` 标签是对的，跳过它们也是可理解的；
但代价是：产品最可能悄悄坏掉的那四个案，恰恰一次都没被端到端验证过。

## 六、更贵的一条：`hard` 案的提示词把交互整个丢了

> ### ⚠️ 本节结论已被红队实测推翻，保留原文供对照
>
> 本节说「四个 hard 案原型依赖 JS，提示词没描述，所以做出来一定缺机制」。
> **错了两处**（见 §十六）：
>
> 1. **"机制依赖 JS"不成立。** 四案去掉 JS 后首屏差异是
>    0.00% / 16.43% / 0.12% / 0.70%，其中 S18 那 16.43% 是入场动画，
>    **关掉 JS 内容反而更全**（JS 开着时有 5 个 `[data-grow]` 在等滚动，
>    `opacity:0`）。四案的机制全部由静态 HTML+CSS 承担。
> 2. **范围错了。** 不是 4 案的问题，是 35 案：`motion` 字段
>    35/35 有值、35/35 没进提示词。
>
> 本节保留下半部分仍然成立的内容（事件处理器确实一条都没进提示词），
> 但"所以机制会消失"这个推论作废。

四个 `hard=true` 的案，原型全都有真实 JS 交互（逐个核过 `index.html` 的 `<script>`）：

| 案 | 原型里的 JS 行为 |
|---|---|
| S15 | scroll 翻状态、mouseenter 热区、click 切层、focus、`matchMedia` 降级、3× `setTimeout` |
| S18 | `IntersectionObserver` ×2、scroll、requestAnimationFrame、click |
| S21 | `IntersectionObserver`、click/mouseenter/mouseleave/change/keydown/blur、`matchMedia` |
| S29 | `IntersectionObserver`、scroll/resize/load/focusin/keydown、click |

而它们的提示词（离线生成，`buildStylePrompt` 与界面上"复制"按钮同源）
**一次都没提这些动作**。唯一与"动"相关的是通用防退化第 ⑧ 条：

```
⑧ 动效只用本案机制句里写到的那一个动作，其余位置保持静止。
```

而四个案的「机制句」全部只描述静态形态：

| 案 | 机制句（`_prompt.txt:10`） | 有没有写动作 |
|---|---|---|
| S15 | 「同一图叠三层，错位 0/3/7px，第三层 56% 不透明——版本差异靠错位与透明度读出」 | 无 |
| S18 | 「行尾 8×14px 块 530ms 方波——读序由走向给出」 | 方波（纯 CSS 可做，实测原型也是 `@keyframes`） |
| S21 | 「右端按 30/45/60° 斜切——先后由切口角度读出」 | 无 |
| S29 | 「归属由编号位与出血方向给出」 | 无 |

所以第 ⑧ 条对 S15/S21/S29 是**空指针**：它指向前文一个不含动作的句子。
AI 照做只能做出静态版 —— 而静态版看起来完全对，机制却不在。

这和 `app.js:949` 已有的自我描述吻合：

> ③ 机制依赖 JS（hard，4 案）—— 唯一一个"选了会坏、而且看不出来"的字段。

**「看不出来」不只是对店主说的，也是对闸门说的。** 没有任何一条闸门检查
「提示词是否传递了原型的交互机制」。

## 八、修完尺子立刻抓到一条真缺陷：S34 的提示词与自己的机制互斥

改完判据重跑，S34 从「7/7 ✓」变成「应排 5 条，实得 7 条 ✗」。

我没有直接采信这个 ✗ —— 判据刚改过，可能就是判据又错了。逐层核了三处：

**① 提示词确实说了 5 条**（`_prompt.txt:20-22`）：

```
1. 这个版式设计时排了 7 个条目——这是版式的规模，不是你的内容量。
2. 你手上有 5 条内容，就排 5 条：不凑整、不留占位符。
3. 这个版式是自动流排版，删条目只会让页面变短、不会留空位，你按自己的数量排就好。
```

**② AI 排了 7 条，而且排的是七档**（`index.html` 的 `.entry:nth-child(1..7)`）：

```
.entry:nth-child(1) { margin-left: 0;    }
.entry:nth-child(2) { margin-left: 3%;   }
.entry:nth-child(3) { margin-left: 5.5%; }
.entry:nth-child(4) { margin-left: 2%;   }
.entry:nth-child(5) { margin-left: 7%;   }
.entry:nth-child(6) { margin-left: 4%;   }
.entry:nth-child(7) { margin-left: 1%;   }
```

**③ 原型本身就是七档，而且这七档就是这个案的全部机制**
（`prototypes/S34-.../style.css:102-108`）：

```
.d1 { margin-left: 0; }   .d2 { margin-left: 3%; }   .d3 { margin-left: 5.5%; }
.d4 { margin-left: 2%; }  .d5 { margin-left: 7%; }   .d6 { margin-left: 4%; }
.d7 { margin-left: 1%; }
```

而提示词自己抄的硬前提原文（`_prompt.txt:25`）就是：

> 「最难被复用到别的品牌之处：**七档缩进与文字重量的绑定** —— 没有一个
> "每块重量不同"的叙事，七档缩进就成了随机的错位。」

**所以：提示词在同一段里既要求"七档缩进"，又要求"只有 5 条就排 5 条"。**
5 条做不出七档。模型选了保住机制（排 7 条），提示词的另一句话被违反了。

这不是模型的错，也不是新判据的错 —— 是**提示词里的两条约束互斥**，
而旧判据（拿 `minItems` 当目标）恰好把这处矛盾掩盖成了「7/7 ✓」。

### 为什么会这样

`minItems` 在两个案上有两种互相冲突的语义：

| 案 | `minItems` | 真实含义 | 少一条会怎样 |
|---|---|---|---|
| S19 | 20 | 内容规模（可少排） | 没影响，第 3 条明说"按你的数量排" |
| S34 | 7 | **结构必需**（少一条机制就散） | 七档缩进少一档，机制消失 |

`minItems` 这一个字段承载了两种语义，提示词只能按其中一种写。
S19 的写法对，S34 的写法错。这个字段需要拆成两个
（比如 `minItems` 保留原义 + 新增 `structuralItems` 表示"少一条就坏"）。

**这条不需要跑盲测就能发现** —— 只要问一句「35 案的 minItems 里，
哪些是结构必需、哪些只是规模」，再检查提示词有没有区分。
现在的答案是一个都没区分。

## 九、`hard` 的四案：警告说了错的原因，对的原因只在一种情况下才说

`hard` 在这个仓库里有明确的、写了两处的定义：

| 位置 | 原文 |
|---|---|
| `app.js:876`（行卡 tooltip） | 「这个案的核心机制靠 **JavaScript** 跑。v0 一类工具会把 script 剥掉或改写，机制会消失，而且不易察觉」 |
| `app.js:949`（注释） | 「③ **机制依赖 JS**（hard，4 案）—— 唯一一个"选了会坏、而且看不出来"的字段」 |
| `prompt-copy.js:196-201`（v0 分支） | 「这一案的签名机制需要 **JavaScript**…**v0 会把 `<script>` 剥掉或改写**」 |

三处一致：**`hard` = 机制依赖 JS**。

但提示词上方那条始终可见的警告（`prompt-copy.js:1976-2011`）写的是另一回事：

```js
var riskyTopic = !!s.hard;
...
if (riskyTopic) why.push("机制绑在特定题材上，换普通内容会退化");
```

**"题材"不是 `hard` 的定义。** `hard` 说的是运行方式（要不要 JS），
"绑在特定题材上"描述的是 `dna.reuse` / `scenesNo` 那类可迁移性问题 —— 两个不同的字段。

### 后果对 S21 最明显

`hard` 与 `degrades` 是两个独立集合：

```
hard (4):          S15 S18 S21 S29
degrades=yes (13): S02 S04 S05 S08 S12 S14 S15 S18 S19 S20 S22 S23 S29
只 hard 不 degrades: S21
```

S21 是唯一一个「hard 但 degrades=no」的案。它 `riskyCount` 为假，
所以 `why` 数组里只有那一句题材话。于是：

- 店主选 **ChatGPT / Claude**（默认路径，`head()` 返回空数组，不加任何说明）→
  **提示词全文与整块界面上，没有任何一处告诉他"这个案要 JS"**。
- 只有选 **v0** 时才会看到正确的那句（`prompt-copy.js:196`）。

而 S21 的原型机制正是 `IntersectionObserver` 触发的释放路径。
提示词不要求它，AI 不会写；写出来的页面静态看完全正确，机制不在。

### 这不是措辞问题

同一条警告里，`riskyCount` 那半句是准确的（「单元位置是手工排定的，内容少于 N 条会留洞」，
读的就是 `capacity.degrades`）。`riskyTopic` 这半句读的是 `s.hard`，
却说了 `hard` 不负责的意思 —— 这是**字段与文案的错配**，属于本仓库记录的
第 4 类缺陷（量错了东西）在文案层的同构：警告量的对象不是它声称的对象。

### 与第八节的关系

第八节说的是「S34 的 `minItems` 有两种语义」，这一节说的是
「`hard` 的警告文案用了另一种语义」。两处都指向同一个根因：

> **这个仓库的字段没有单一含义，而下游的每一处文案各自猜了一个含义。**

`minItems` 猜了两次（规模 / 必需），`hard` 猜了两次（JS 依赖 / 题材绑定）。

## 十、最贵的一条：同一个案，两条线在机制层分开，两边五类判据都通过

这是整份审计里唯一一条**已发生的、可复现的"风格对、机制不在"**。

同一个 S13（盲压公函），两套 harness、同一份规格来源：

| 记号 | 新线 `_blindtest/S13/index.html` | 旧线 `_probe/_staged/S13-sandbox.html` |
|---|---|---|
| `135deg`（光源角） | **0** | 1 |
| `0.4mm`（压深） | **0** | 7 |
| `color-mix`（亮度差实现） | **0** | 3 |
| `inset`（凹槽阴影） | 4 | 5 |
| 文件体积 | 10,803 B | 31,256 B |
| CSS 规则数 | 130 | 314 |

判别值复算（`_discriminator-lib.mjs`，与 `_discriminator-check.mjs` 同一套函数）：

```
S13 判别值 n=8：
  #7B612C  #F4E3BE  #241F17  #D6CDB9  0.4mm  3%  5.5px  14.5px

新线命中: 5/8      旧线命中: 8/8
新线缺的三个: 0.4mm  3%  14.5px
```

**新线缺的三个全是机制量，不是配色。** 三个色值全中，说明新线做对了"公函的样子"；
三个机制量全缺，说明它没做"凸版压印"这件事。

而这三个量在提示词正文里（`_blindtest/S13/_prompt.txt`）：

> 「三是立体感必须能用「**亮度差 3% + 压深 0.4mm**」两个数解释，凡解释不了的凹凸全部删掉。」
> 「每份公函最后一行的最后一个字，**压深从 0.4mm 刻意降到 0.25mm**…」

### 为什么没有任何判据发现

`score.mjs` 的五类里，①②③ 查的是色值/字体/几何（圆角线宽字号），
④ 查条目与图位，⑤ 查禁用项。**没有一类查"机制"。**

判别值法（71/71）能看出这个差（5/8 vs 8/8），但它的判据是
「**只在这一份提示词里出现的 token** 有没有出现在产物里」——
比值 71/71 = 100% 是**在旧线 13 案上**算的，新线 4 案根本没进过这个统计。
换句话说：71/71 这个数字从来不覆盖新线，也不覆盖机制层。

### 这条修正了我先前的一个判断

我在 §一 写「④ 结构那一类是五类里最弱的一类」。**那是错的**：
最弱的是**整个五类里缺少机制这一类**。④ 只是碰巧在这四个案上有盲区，
而机制层是 35 案一个都没量过。

### 也修正了规划 Agent 的一处数字

规划 Agent 报的是「新线 1/8、旧线 6/6」。我用同一套 `_discriminator-lib.mjs`
复算是 **5/8 vs 8/8**。方向一致（新线缺机制量），量级不同。
差异可能来自它数的是"机制子项"而不是"判别值 token"——
两个口径不同，但两种口径都指向同一件事：**新线丢了机制，判据没发现**。
记在这里，免得下一个人以为 1/8 这个数是实测的。

## 十一、机制层能不能被量？能——35/35 案都有可测数值

判断"建机制量尺"这条路是否可行，可以先算一件事：
**机制句（`dna.mechanism`）里有多少个能直接在 CSS 里查的数值？**

实测（正则抓 `px / % / deg / mm / fr / #hex`）：

```
35 案机制句里的可测数值 token 总数: 137
有数值的案数: 35/35
```

分布（前 10）：

| 案 | token 数 | 构成 |
|---|---|---|
| S18 | 8 | 6 px + 2 % |
| S17 | 7 | 4 px + 1 mm + 2 fr |
| S22 | 7 | 7 px |
| S29 | 7 | 7 px |
| S30 | 7 | 5 px + 2 % |
| S08 | 6 | 6 px |
| S20 | 6 | 6 px |
| S26 | 6 | 3 px + 3 % |
| S31 | 6 | 6 px |
| S07 | 5 | 3 px + 2 % |

最少的案（S01/S04/S06/S16/S32）也有 1 个。**没有一案是纯形容词。**

这条结论的意义：**机制判据不需要人眼审美，它可以和 ① 配色一样硬**
（hex 精确匹配）。S13 那次 5/8 vs 8/8 的差，就是把它当判别值 token 算出来的，
不是主观打分。

### 但有三个必须处理的陷阱（在动手前就该定下来）

**① 数值可能只出现在"展示"位置。** 旧线 S13 产物里 `0.4mm` 出现 7 次，
但其中可能有一处是 `<dd>0.4mm</dd>` 这样的规格展示项 —— 那不算实现，
只算把数字抄进页面。仓库里已有先例：`check-provenance` 的
`displayOnly` / `mech-value-not-in-source` 判据就是为这个设的。
机制判据必须复用那套思路：**要求数值出现在会改变渲染的 CSS 声明里**。

**② `mm` / `deg` / `fr` 不能直接字符串比对。** 19/35 案的机制句含非 px 单位。
`0.4mm` 在浏览器里会被换算成 px（约 1.51px @96dpi），AI 可能写成 `1.5px`。
直接字符串比会把正确实现判成缺失 —— 这一条必须先定义"什么算等价"，
否则会产生大量假阳性，然后被判据作者"调松"，最后又变成恒真。

**③ 机制句里有的量是推导值，不是声明值。** S13 的 `14%` 在
`check-prompts` 里已被标为 `mech-value-comment-only`（「只在该案注释里找到，
不是声明 —— 不是错，但也没被守护」）。这类量不能当硬判据。

所以「机制保真度」应该和 ① 配色那样分档：
**能精确查的**（px 声明、hex）当 FAIL；**需要换算的**（mm/deg/fr）报数不判；
**推导值**只报不判。三档都要在输出里分开，不能合成一个分数。

## 十三、修这条判据时连犯两个错，两个都记下来

`score.mjs` 的 ⑤ 渐变判据（§十二）修的时候，我一次没修对。两个错都值得留着，
因为它们正是这个仓库反复描述的那两类。

### 错一（假阴性）：判据守着一句已经不存在的措辞

原判据：

```js
if (/允许渐变时只用相邻两级/.test(prompt) || /不用渐变/.test(prompt)) { … }
```

而 `prompt-copy.js` 已把措辞改成「只用同一色系里明度接近的两档」。
实测：现行 35 份提示词 **0 份**含旧措辞 → 分支一次都没执行，输出却写"无违反"。

这是第 5 类缺陷（闸门与被测物共享盲区）。修法：两版措辞都认，
且**认不出来时返回 `null` 而不是 `0`**，调用方必须把 `null` 显示成"未判"。

### 错二（假阳性）：补完立刻反着错了一次

第一版补丁把「CSS 里出现 `linear-gradient` 就报违规」当判据。跑出来：

```
S19 铜版标本柜    ⑤ 禁项   渐变受限×2
```

去看那两处：

```css
linear-gradient(var(--paper-deep),var(--paper-deep)) left top/100% .4px no-repeat
```

**两端是同一个变量。** 这是画 0.4px 细线的手法，不是颜色渐变 ——
CSS 里没有"1px 高的纯色矩形"这种原语，只能用同色两端 gradient 画。
而 S19 的提示词恰恰要求「只用同一色系里明度接近的两档」，
它用的 `#E4DECD` / `#D8CFB6` 正是同色系相邻两档，**完全合规**。

旧判据漏判（措辞变了），新判据误判（只看函数名）—— 两次都在量错的信号。
这正是本仓库记录过的那条：判据先信了一个间接信号，把直接信号扔了
（先例：S19 正文 16px 明明写在 `body{}` 里，判据却去取 ≥14px 声明的众数 22px）。

### 现在的判法

按**语义**判，不按函数名判：

```js
/* 同色两端的 gradient = 画线，不是渐变 */
function isDecorativeLine(gradBody) {
  const c = colorArgs(gradBody);   // 只取像颜色的片段：hex / var(--x) / rgb()
  return c.length >= 2 && c.every(x => x === c[0]);
}
```

只做**同色**判定，不做"明度接近"的色差判定 —— 后者要写色彩空间换算，
会引入它自己的 bug（本仓库已因此放弃追 `var()` 展开，见 `score.mjs:23-25`）。

**两头都保守**：
- 同色两端 → 剔除，并在输出里报「已剔除 N 处同色 gradient：那是画线，不是渐变」；
- 不同变量两端 → 不知道是否同色，按"可能是真渐变"报出来（宁可报，不可漏）。

修完实测四案：

```
S01 无违反〔渐变按旧措辞判〕
S13 无违反〔渐变按旧措辞判〕
S19 无违反〔已剔除 2 处同色 gradient：那是画线，不是渐变〕
S34 无违反〔渐变按旧措辞判〕
```

自测从 26 条加到 **30 条**，新增四条专门覆盖这次踩的坑
（同色算画线 / 同色计入 decorative / 真渐变仍报 / 不同变量按真渐变处理）。

### 一句话

**这条判据在修之前和修之后都报"无违反"，中间还有一次报"违规×2"。
三个结果里只有最后一个是查出来的，前两个分别是"没查"和"查错了"。**
如果只看输出那行字，三种状态完全无法区分 —— 这就是为什么三态标记
（✓ / ✗ / –）必须带原因，而不只是带符号。

## 十五、⑤ 那条死判据的精确覆盖率：0/35

对现行 35 份提示词逐个生成并统计渐变措辞（`buildStylePrompt`，`have:5`）：

```

新措辞「只用同一色系里明度接近的两档」 35 / 35
禁渐变「不用渐变」                0 / 35

```

**旧判据的正则对全部 35 案永远为假。** 它在报告里存在了几个月，
输出一直是「⑤ 禁项 无违反」，而这行字对 35 案一次都没有真实含义。

这不是"某几案漏了"，是**这条判据从未在任何一个案上执行过**。

### 为什么它能活这么久

因为它和它要查的东西**在同一个文件里、由同一次改动产生**：

- `prompt-copy.js:1276` 改措辞（S19 盲测后，为了让 AI 不当真去加渐变纹理）；
- `score.mjs:278` 的正则没跟着改；
- 两个文件之间没有任何闸门做交叉检查。

而 `check-ui-copy.mjs` 查的是**界面文案**（index.html/style.css/app.js），
`check-prompts.mjs` 查的是**提示词内容**，`score.mjs` 不在 quarter.mjs 的任何一步里。
**没有任何一条闸门知道 `score.mjs` 的正则和 `prompt-copy.js` 的措辞应该对应。**

### 这类缺陷的通解（建议加进 quarter.mjs）

> **凡是从被测物里抽字符串来匹配的判据，都必须有一条断言证明它能匹配上。**

具体到这里：`score.mjs --selftest` 现在有 30 条变异，但如果没人跑它，
那 30 条也不作数。所以真正的修法是把它接进 verify-research（已做，见 §十后续改动），
并且**在输出里显示匹配到了哪一版措辞**（已做）——
这样下次措辞再改，`⑤` 那行会变成「渐变 – 未判」而不是「无违反」。

- 保留 `hard` 只留一个语义，另两处文案改去读正确的字段。

只改文案会把 S21 从"零警告"修成"有警告"，但**警告内容仍然是错的**。

### 红队推翻不了的部分（这几条仍然成立）

1. 四案的事件处理器确实一条都没进提示词 —— 包括 S15 的年份切换、
   S18 的三个操作入口、S21 的互斥清单展开、S29 的编号跳转。
2. **没有任何闸门检查"提示词是否传递了原型的交互"**。
   `check-docs.mjs:451/454` 只校验 `hard` 名单与文档口径一致，
   不校验 `motion` 是否进提示词 —— 这让 35 案的 `motion` 静默蒸发。
3. **S15 无 JS 时出死按钮**：三个 `.yb` 仍渲染、看起来可点，

   这比"缺机制"更硬，因为它是用户能直接撞上的。
4. `hard` 语义分裂成立。

### 一句话改写

> **35/35 案的 `motion`（以及 `audit`）从未进入提示词，四案的交互细节因此丢失 ——
> 但丢的不是机制，是渐进增强层。四案的机制全部由静态 HTML+CSS 承担，

## 十八、为什么 `motion` 蒸发了却没人发现：没有任何闸门知道它该进提示词

`motion` 在**闸门里**出现过一次，但用法和"进提示词"无关：

```js
// prototypes/_build/check-scenes.mjs:134
function bodyText(r) {
  const parts = [
    r.cn, r.en, r.structure, r.tone, r.def, r.family, r.layout, r.visuals, r.motion,
    r.quirk, r.fontsSpec, r.risk, positiveScenes(r), …
  ];
```

它只是把 `motion` 当成**搜索文本**的一部分（用户打某个词能不能搜到这个案），
**不是**"它有没有进提示词"的断言。

实测：`prototypes/_build/check-*.mjs` 里提到 `motion` 的文件只有 `check-scenes.mjs` 一个，
且用法如上。**没有任何闸门检查 `motion` 是否被 `prompt-copy.js` 读取。**

### 同一条链上还有两个字段

| 字段 | data.js 有值 | 进提示词 | 有闸门吗 |
|---|---|---|---|
| `motion` | 35/35 | **0** | 无 |
| `audit` | 35/35 | **0** | 无 |
| `layout` | 35/35 | 3（含假命中） | 无 |
| `visuals` | 35/35 | 4（含假命中） | 无 |
| `risk` | 35/35 | 35 | 无（但它恰好全进了） |

`collect-schemes.mjs:191` 的 `FIELDS` 列了 13 个字段，提示词只用了一部分。
`risk` 全进、`audit` 全不进 —— **这是逐个手挑留下的漏，不是设计取舍。**

### 这类缺陷的通解

§十五 已经写过一条：凡是从被测物里抽字符串来匹配的判据，都必须有一条断言
证明它能匹配上。这里是它的兄弟版本：

> **凡是在数据层存在、且被产品文案承诺过会用的字段，
> 都必须有一条断言证明它真的到了交付物里。**

具体到这里，应该加一条闸门：

```
对每个 scheme 的每个非空字段 F：
  若 F 在 FIELDS 里、且 F 不是"仅供界面展示"的白名单成员
  则断言 buildStylePrompt(id) 里能找到 F 内容的可辨识切片
  否则 FAIL，报 "字段 F 在 data.js 有值但没进提示词"
```

白名单要显式写出来（比如 `cn`/`en`/`slug` 这类只给界面用的），
这样下一个加字段的人必须做一次有意识的决定，而不是默默漏掉。

**这条闸门写起来很便宜**（一个循环 + 切片匹配），
而且它会在 `motion` 蒸发的第一天就红，而不是等到 35 份产物都跑完才发现。
