1. **「没判」≠「通过」。** 判据读不到对象时，输出必须写「未判 + 原因」，

## 二、图片判据：74% 的案从未被检查

`prompt-copy.js` 里图片这一段有**三条**互斥分支（`:1136-1181`）：

| 分支 | 触发条件 | 句式 |
|---|---|---|
| strict | `have == 0` 或 `have >= minPics` | 「至少要 N 个**不同的**图片位置」 |
| alt | `0 < have < minPics` | 「这个版式有 N 个图片位，但你只有 M 条内容」 |
| zero | `minPics == 0` | 「本案是零图片设计」 |

`score.mjs:213` 只认第一条：

```js
const picM = prompt.match(/至少要\s*(\d+)\s*个\*{0,2}不同的\*{0,2}图片位置/);
```

而 `acp-run.mjs:96` 把测试输入写死成 `have: 5`。按这个输入分派，35 案的实际分布是：

```
strict「至少要 N 个」      9 案
alt「有N个位但你只有M条」  25 案   ← 评分器不认
zero「零图片设计」          1 案   ← 评分器不认
```

**未判覆盖 26/35 = 74%**。四个已测案里，S01、S19 走 alt，S34 走 zero，只有 S13 落在 strict。

后果直接可见：

| 案 | 提示词要求 | 实际 HTML | 评分器输出 |
|---|---|---|---|
| S01 | 6 个图片位、5 条内容 | 4 img / 4 唯一 src | **整行不存在** |
| S19 | 6 个图片位、5 条内容 | 5 img / 5 唯一 src | **整行不存在** |
| S34 | 零图片设计 | 0 img | **整行不存在**（做对了也没人知道） |
| S13 | 至少 4 个不同图片位 | 4 img / 4 唯一 src | `图片 提示词要 4 个位置；HTML 里 4 个 img` |

S01 和 S19 少放的那一两张图，是提示词**自己允许的**（"空出来的图片位改成留白或文字块"）。
所以这不是模型的问题，是判据没有对应的判分逻辑 —— 而且连"这里应该判"这件事都没有输出。

## 三、条目判据：量错了对象（第 4 类缺陷）

提示词原文（以 S19 为例，`_prompt.txt:21-22`）：

```
1. 这个版式设计时排了 20 个条目——这是版式的规模，不是你的内容量。
2. 你手上有 5 条内容，就排 5 条：不凑整、不留占位符。
```

**提示词明确要求 AI 排 5 条，不要排 20 条。** 而 `score.mjs:203` 拿 HTML 里的
`<article>` 数量去比 20，容差 ±2：

```js
const want = Number(itemM[1]);
st.items = { want, counts, closest, hit: Math.abs(best[1] - want) <= 2 };
```

实测 S19：AI 排了 5 条（完全遵照提示词），评分器报"最接近 article=5（启发式，仅供参考）"。

这个判据的两个问题：
1. **比错了对象** —— 应该比 `have`（5），不是 `minItems`（20）。
2. **量错了层** —— 提示词说的是"版式规模"，是 CSS 网格的设计尺度，不是 DOM 元素数。
   即使比 `have`，数 `<article>` 也只是在猜 AI 用哪个标签表示"一条内容"。

`70-blindtest-round1.md` §7 自己写了这一条：「结构条目数要能区分"设计规模"与"实际放置数"」，
但同一份报告的 §0 结论是「二十项检查全部通过」。

## 六、更贵的一条：`hard` 案的提示词把交互整个丢了

> ### ⚠️ 本节结论已被红队实测推翻，保留原文供对照
>
> 本节说「四个 hard 案原型依赖 JS，提示词没描述，所以做出来一定缺机制」。
> **错了两处**（见 §十六）：
>
> 1. **"机制依赖 JS"不成立。** 四案去掉 JS 后首屏差异是
>    0.00% / 16.43% / 0.12% / 0.70%，其中 S18 那 16.43% 是入场动画，
>    **关掉 JS 内容反而更全**（JS 开着时有 5 个 `[data-grow]` 在等滚动，
>    `opacity:0`）。四案的机制全部由静态 HTML+CSS 承担。
> 2. **范围错了。** 不是 4 案的问题，是 35 案：`motion` 字段
>    35/35 有值、35/35 没进提示词。
>
> 本节保留下半部分仍然成立的内容（事件处理器确实一条都没进提示词），
> 但"所以机制会消失"这个推论作废。

四个 `hard=true` 的案，原型全都有真实 JS 交互（逐个核过 `index.html` 的 `<script>`）：

| 案 | 原型里的 JS 行为 |
|---|---|
| S15 | scroll 翻状态、mouseenter 热区、click 切层、focus、`matchMedia` 降级、3× `setTimeout` |
| S18 | `IntersectionObserver` ×2、scroll、requestAnimationFrame、click |
| S21 | `IntersectionObserver`、click/mouseenter/mouseleave/change/keydown/blur、`matchMedia` |
| S29 | `IntersectionObserver`、scroll/resize/load/focusin/keydown、click |

而它们的提示词（离线生成，`buildStylePrompt` 与界面上"复制"按钮同源）
**一次都没提这些动作**。唯一与"动"相关的是通用防退化第 ⑧ 条：

```
⑧ 动效只用本案机制句里写到的那一个动作，其余位置保持静止。
```

而四个案的「机制句」全部只描述静态形态：

| 案 | 机制句（`_prompt.txt:10`） | 有没有写动作 |
|---|---|---|
| S15 | 「同一图叠三层，错位 0/3/7px，第三层 56% 不透明——版本差异靠错位与透明度读出」 | 无 |
| S18 | 「行尾 8×14px 块 530ms 方波——读序由走向给出」 | 方波（纯 CSS 可做，实测原型也是 `@keyframes`） |
| S21 | 「右端按 30/45/60° 斜切——先后由切口角度读出」 | 无 |
| S29 | 「归属由编号位与出血方向给出」 | 无 |

所以第 ⑧ 条对 S15/S21/S29 是**空指针**：它指向前文一个不含动作的句子。
AI 照做只能做出静态版 —— 而静态版看起来完全对，机制却不在。

这和 `app.js:949` 已有的自我描述吻合：

> ③ 机制依赖 JS（hard，4 案）—— 唯一一个"选了会坏、而且看不出来"的字段。

**「看不出来」不只是对店主说的，也是对闸门说的。** 没有任何一条闸门检查
「提示词是否传递了原型的交互机制」。

## 八、修完尺子立刻抓到一条真缺陷：S34 的提示词与自己的机制互斥

> ### ⚠️ 本节的诊断被审计 Agent 推翻，保留原文供对照
>
> 我当时说「`minItems` 一个字段承载了两种语义（内容规模 / 结构必需），需要拆字段」。
> **错了两处**（见 §十九）：
>
> 1. **`minItems` 只有一重语义**（设计规模）。「少排会不会散架」这件事
>    早在 2026-10-27 就交给另一个字段 `degrades` 了，而它工作正常。
> 2. **S34 的 `degrades=no` 是正确判定**：`style.css:99` 用的是
>    `.drift-block:last-child`，不是 `nth-child(7)` —— 作者本来就是按"最后一块"写的，
>    排 5 条只会变短。所以它不是"结构必需"。
>
> 真正的缺陷在**散文字段**（`quirk` / `mechanism` / `reuse`）把条目数写死了，
> 与 `degrades` 无关。全库 16/35 案有这个问题 —— 见 §十九。
>
> 下面这个 ✗ 仍然是对的（S34 产物确实排了 7 条、违反了"排 5 条"那句），
> 但"提示词里两条约束互斥"的原因是散文钉死，不是 `minItems` 双义。

改完判据重跑，S34 从「7/7 ✓」变成「应排 5 条，实得 7 条 ✗」。

我没有直接采信这个 ✗ —— 判据刚改过，可能就是判据又错了。逐层核了三处：

**① 提示词确实说了 5 条**（`_prompt.txt:20-22`）：

```
1. 这个版式设计时排了 7 个条目——这是版式的规模，不是你的内容量。
2. 你手上有 5 条内容，就排 5 条：不凑整、不留占位符。
3. 这个版式是自动流排版，删条目只会让页面变短、不会留空位，你按自己的数量排就好。
```

**② AI 排了 7 条，而且排的是七档**（`index.html` 的 `.entry:nth-child(1..7)`）：

```
.entry:nth-child(1) { margin-left: 0;    }
.entry:nth-child(2) { margin-left: 3%;   }
.entry:nth-child(3) { margin-left: 5.5%; }
.entry:nth-child(4) { margin-left: 2%;   }
.entry:nth-child(5) { margin-left: 7%;   }
.entry:nth-child(6) { margin-left: 4%;   }
.entry:nth-child(7) { margin-left: 1%;   }
```

**③ 原型本身就是七档，而且这七档就是这个案的全部机制**
（`prototypes/S34-.../style.css:102-108`）：

```
.d1 { margin-left: 0; }   .d2 { margin-left: 3%; }   .d3 { margin-left: 5.5%; }
.d4 { margin-left: 2%; }  .d5 { margin-left: 7%; }   .d6 { margin-left: 4%; }
.d7 { margin-left: 1%; }
```

而提示词自己抄的硬前提原文（`_prompt.txt:25`）就是：

> 「最难被复用到别的品牌之处：**七档缩进与文字重量的绑定** —— 没有一个
> "每块重量不同"的叙事，七档缩进就成了随机的错位。」

**所以：提示词在同一段里既要求"七档缩进"，又要求"只有 5 条就排 5 条"。**
5 条做不出七档。模型选了保住机制（排 7 条），提示词的另一句话被违反了。

这不是模型的错，也不是新判据的错 —— 是**提示词里的两条约束互斥**，
而旧判据（拿 `minItems` 当目标）恰好把这处矛盾掩盖成了「7/7 ✓」。

### 为什么会这样

`minItems` 在两个案上有两种互相冲突的语义：

| 案 | `minItems` | 真实含义 | 少一条会怎样 |
|---|---|---|---|
| S19 | 20 | 内容规模（可少排） | 没影响，第 3 条明说"按你的数量排" |
| S34 | 7 | **结构必需**（少一条机制就散） | 七档缩进少一档，机制消失 |

`minItems` 这一个字段承载了两种语义，提示词只能按其中一种写。
S19 的写法对，S34 的写法错。这个字段需要拆成两个
（比如 `minItems` 保留原义 + 新增 `structuralItems` 表示"少一条就坏"）。

**这条不需要跑盲测就能发现** —— 只要问一句「35 案的 minItems 里，
哪些是结构必需、哪些只是规模」，再检查提示词有没有区分。
现在的答案是一个都没区分。

## 九、`hard` 的四案：警告说了错的原因，对的原因只在一种情况下才说

`hard` 在这个仓库里有明确的、写了两处的定义：

| 位置 | 原文 |
|---|---|
| `app.js:876`（行卡 tooltip） | 「这个案的核心机制靠 **JavaScript** 跑。v0 一类工具会把 script 剥掉或改写，机制会消失，而且不易察觉」 |
| `app.js:949`（注释） | 「③ **机制依赖 JS**（hard，4 案）—— 唯一一个"选了会坏、而且看不出来"的字段」 |
| `prompt-copy.js:196-201`（v0 分支） | 「这一案的签名机制需要 **JavaScript**…**v0 会把 `<script>` 剥掉或改写**」 |

三处一致：**`hard` = 机制依赖 JS**。

但提示词上方那条始终可见的警告（`prompt-copy.js:1976-2011`）写的是另一回事：

```js
var riskyTopic = !!s.hard;
...
if (riskyTopic) why.push("机制绑在特定题材上，换普通内容会退化");
```

**"题材"不是 `hard` 的定义。** `hard` 说的是运行方式（要不要 JS），
"绑在特定题材上"描述的是 `dna.reuse` / `scenesNo` 那类可迁移性问题 —— 两个不同的字段。

### 后果对 S21 最明显

`hard` 与 `degrades` 是两个独立集合：

```
hard (4):          S15 S18 S21 S29
degrades=yes (13): S02 S04 S05 S08 S12 S14 S15 S18 S19 S20 S22 S23 S29
只 hard 不 degrades: S21
```

S21 是唯一一个「hard 但 degrades=no」的案。它 `riskyCount` 为假，
所以 `why` 数组里只有那一句题材话。于是：

- 店主选 **ChatGPT / Claude**（默认路径，`head()` 返回空数组，不加任何说明）→
  **提示词全文与整块界面上，没有任何一处告诉他"这个案要 JS"**。
- 只有选 **v0** 时才会看到正确的那句（`prompt-copy.js:196`）。

而 S21 的原型机制正是 `IntersectionObserver` 触发的释放路径。
提示词不要求它，AI 不会写；写出来的页面静态看完全正确，机制不在。

### 这不是措辞问题

同一条警告里，`riskyCount` 那半句是准确的（「单元位置是手工排定的，内容少于 N 条会留洞」，
读的就是 `capacity.degrades`）。`riskyTopic` 这半句读的是 `s.hard`，
却说了 `hard` 不负责的意思 —— 这是**字段与文案的错配**，属于本仓库记录的
第 4 类缺陷（量错了东西）在文案层的同构：警告量的对象不是它声称的对象。

### 与第八节的关系

第八节说的是「S34 的 `minItems` 有两种语义」，这一节说的是
「`hard` 的警告文案用了另一种语义」。两处都指向同一个根因：

> **这个仓库的字段没有单一含义，而下游的每一处文案各自猜了一个含义。**

`minItems` 猜了两次（规模 / 必需），`hard` 猜了两次（JS 依赖 / 题材绑定）。

## 十、最贵的一条：同一个案，两条线在机制层分开，两边五类判据都通过

这是整份审计里唯一一条**已发生的、可复现的"风格对、机制不在"**。

同一个 S13（盲压公函），两套 harness、同一份规格来源：

| 记号 | 新线 `_blindtest/S13/index.html` | 旧线 `_probe/_staged/S13-sandbox.html` |
|---|---|---|
| `135deg`（光源角） | **0** | 1 |
| `0.4mm`（压深） | **0** | 7 |
| `color-mix`（亮度差实现） | **0** | 3 |
| `inset`（凹槽阴影） | 4 | 5 |
| 文件体积 | 10,803 B | 31,256 B |
| CSS 规则数 | 130 | 314 |

判别值复算（`_discriminator-lib.mjs`，与 `_discriminator-check.mjs` 同一套函数）：

```
S13 判别值 n=8：
  #7B612C  #F4E3BE  #241F17  #D6CDB9  0.4mm  3%  5.5px  14.5px

新线命中: 5/8      旧线命中: 8/8
新线缺的三个: 0.4mm  3%  14.5px
```

**新线缺的三个全是机制量，不是配色。** 三个色值全中，说明新线做对了"公函的样子"；
三个机制量全缺，说明它没做"凸版压印"这件事。

而这三个量在提示词正文里（`_blindtest/S13/_prompt.txt`）：

> 「三是立体感必须能用「**亮度差 3% + 压深 0.4mm**」两个数解释，凡解释不了的凹凸全部删掉。」
> 「每份公函最后一行的最后一个字，**压深从 0.4mm 刻意降到 0.25mm**…」

### 为什么没有任何判据发现

`score.mjs` 的五类里，①②③ 查的是色值/字体/几何（圆角线宽字号），
④ 查条目与图位，⑤ 查禁用项。**没有一类查"机制"。**

判别值法（71/71）能看出这个差（5/8 vs 8/8），但它的判据是
「**只在这一份提示词里出现的 token** 有没有出现在产物里」——
比值 71/71 = 100% 是**在旧线 13 案上**算的，新线 4 案根本没进过这个统计。
换句话说：71/71 这个数字从来不覆盖新线，也不覆盖机制层。

### 这条修正了我先前的一个判断

我在 §一 写「④ 结构那一类是五类里最弱的一类」。**那是错的**：
最弱的是**整个五类里缺少机制这一类**。④ 只是碰巧在这四个案上有盲区，
而机制层是 35 案一个都没量过。

### 也修正了规划 Agent 的一处数字

规划 Agent 报的是「新线 1/8、旧线 6/6」。我用同一套 `_discriminator-lib.mjs`
复算是 **5/8 vs 8/8**。方向一致（新线缺机制量），量级不同。
差异可能来自它数的是"机制子项"而不是"判别值 token"——
两个口径不同，但两种口径都指向同一件事：**新线丢了机制，判据没发现**。
记在这里，免得下一个人以为 1/8 这个数是实测的。

## 十一、机制层能不能被量？能——35/35 案都有可测数值

判断"建机制量尺"这条路是否可行，可以先算一件事：
**机制句（`dna.mechanism`）里有多少个能直接在 CSS 里查的数值？**

实测（正则抓 `px / % / deg / mm / fr / #hex`）：

```
35 案机制句里的可测数值 token 总数: 137
有数值的案数: 35/35
```

分布（前 10）：

| 案 | token 数 | 构成 |
|---|---|---|
| S18 | 8 | 6 px + 2 % |
| S17 | 7 | 4 px + 1 mm + 2 fr |
| S22 | 7 | 7 px |
| S29 | 7 | 7 px |
| S30 | 7 | 5 px + 2 % |
| S08 | 6 | 6 px |
| S20 | 6 | 6 px |
| S26 | 6 | 3 px + 3 % |
| S31 | 6 | 6 px |
| S07 | 5 | 3 px + 2 % |

最少的案（S01/S04/S06/S16/S32）也有 1 个。**没有一案是纯形容词。**

这条结论的意义：**机制判据不需要人眼审美，它可以和 ① 配色一样硬**
（hex 精确匹配）。S13 那次 5/8 vs 8/8 的差，就是把它当判别值 token 算出来的，
不是主观打分。

### 但有三个必须处理的陷阱（在动手前就该定下来）

**① 数值可能只出现在"展示"位置。** 旧线 S13 产物里 `0.4mm` 出现 7 次，
但其中可能有一处是 `<dd>0.4mm</dd>` 这样的规格展示项 —— 那不算实现，
只算把数字抄进页面。仓库里已有先例：`check-provenance` 的
`displayOnly` / `mech-value-not-in-source` 判据就是为这个设的。
机制判据必须复用那套思路：**要求数值出现在会改变渲染的 CSS 声明里**。

**② `mm` / `deg` / `fr` 不能直接字符串比对。** 19/35 案的机制句含非 px 单位。
`0.4mm` 在浏览器里会被换算成 px（约 1.51px @96dpi），AI 可能写成 `1.5px`。
直接字符串比会把正确实现判成缺失 —— 这一条必须先定义"什么算等价"，
否则会产生大量假阳性，然后被判据作者"调松"，最后又变成恒真。

**③ 机制句里有的量是推导值，不是声明值。** S13 的 `14%` 在
`check-prompts` 里已被标为 `mech-value-comment-only`（「只在该案注释里找到，
不是声明 —— 不是错，但也没被守护」）。这类量不能当硬判据。

所以「机制保真度」应该和 ① 配色那样分档：
**能精确查的**（px 声明、hex）当 FAIL；**需要换算的**（mm/deg/fr）报数不判；
**推导值**只报不判。三档都要在输出里分开，不能合成一个分数。

### 为什么这条比看上去严重

`score.mjs:274-280` 的 ⑤ 禁项渐变分支，判据正则是：

```js
if (/允许渐变时只用相邻两级/.test(prompt) || /不用渐变/.test(prompt)) { … }
```

**它匹配的是旧措辞。** 今天的提示词 35/35 都不含这句了，
所以这条判据对现行提示词**永远为假**，一次都不会执行 ——
而报告里 ⑤ 显示"无违反"，读起来像"查过了没问题"。

判据守着一句已经不存在的措辞，而它的"通过"和"没查"长得一样。

1. **证据链**：现在这四份产物不能再用今天的 harness 复现（输入文本不同）。
   产物**本身是有效的**（它们确实是模型对某份提示词的回应），
   但"这份产物对应这份提示词"这个连接已经断了。报告里必须把这两件事分开写。
2. **判据**：⑤ 的渐变分支已死，`prompt-copy.js:1276` 改了措辞但判据没跟。

修法很便宜，但必须先决定：是让记录跟着代码走（重生成 4 份 `_prompt.txt` 并
标注"与产物对应的原始版本另存"），还是让判据跟着措辞走（改 ⑤ 的正则）。
**两件都要做**，顺序上应先改判据（它是活的），再处理记录（它是历史）。

## 十三、修这条判据时连犯两个错，两个都记下来

`score.mjs` 的 ⑤ 渐变判据（§十二）修的时候，我一次没修对。两个错都值得留着，
因为它们正是这个仓库反复描述的那两类。

### 错一（假阴性）：判据守着一句已经不存在的措辞

原判据：

```js
if (/允许渐变时只用相邻两级/.test(prompt) || /不用渐变/.test(prompt)) { … }
```

而 `prompt-copy.js` 已把措辞改成「只用同一色系里明度接近的两档」。
实测：现行 35 份提示词 **0 份**含旧措辞 → 分支一次都没执行，输出却写"无违反"。

这是第 5 类缺陷（闸门与被测物共享盲区）。修法：两版措辞都认，
且**认不出来时返回 `null` 而不是 `0`**，调用方必须把 `null` 显示成"未判"。

### 错二（假阳性）：补完立刻反着错了一次

第一版补丁把「CSS 里出现 `linear-gradient` 就报违规」当判据。跑出来：

```
S19 铜版标本柜    ⑤ 禁项   渐变受限×2
```

去看那两处：

```css
linear-gradient(var(--paper-deep),var(--paper-deep)) left top/100% .4px no-repeat
```

**两端是同一个变量。** 这是画 0.4px 细线的手法，不是颜色渐变 ——
CSS 里没有"1px 高的纯色矩形"这种原语，只能用同色两端 gradient 画。
而 S19 的提示词恰恰要求「只用同一色系里明度接近的两档」，
它用的 `#E4DECD` / `#D8CFB6` 正是同色系相邻两档，**完全合规**。

旧判据漏判（措辞变了），新判据误判（只看函数名）—— 两次都在量错的信号。
这正是本仓库记录过的那条：判据先信了一个间接信号，把直接信号扔了
（先例：S19 正文 16px 明明写在 `body{}` 里，判据却去取 ≥14px 声明的众数 22px）。

### 现在的判法

按**语义**判，不按函数名判：

```js
/* 同色两端的 gradient = 画线，不是渐变 */
function isDecorativeLine(gradBody) {
  const c = colorArgs(gradBody);   // 只取像颜色的片段：hex / var(--x) / rgb()
  return c.length >= 2 && c.every(x => x === c[0]);
}
```

只做**同色**判定，不做"明度接近"的色差判定 —— 后者要写色彩空间换算，
会引入它自己的 bug（本仓库已因此放弃追 `var()` 展开，见 `score.mjs:23-25`）。

**两头都保守**：
- 同色两端 → 剔除，并在输出里报「已剔除 N 处同色 gradient：那是画线，不是渐变」；
- 不同变量两端 → 不知道是否同色，按"可能是真渐变"报出来（宁可报，不可漏）。

修完实测四案：

```
S01 无违反〔渐变按旧措辞判〕
S13 无违反〔渐变按旧措辞判〕
S19 无违反〔已剔除 2 处同色 gradient：那是画线，不是渐变〕
S34 无违反〔渐变按旧措辞判〕
```

自测从 26 条加到 **30 条**，新增四条专门覆盖这次踩的坑
（同色算画线 / 同色计入 decorative / 真渐变仍报 / 不同变量按真渐变处理）。

### 一句话

**这条判据在修之前和修之后都报"无违反"，中间还有一次报"违规×2"。
三个结果里只有最后一个是查出来的，前两个分别是"没查"和"查错了"。**
如果只看输出那行字，三种状态完全无法区分 —— 这就是为什么三态标记
（✓ / ✗ / –）必须带原因，而不只是带符号。

## 十五、⑤ 那条死判据的精确覆盖率：0/35

对现行 35 份提示词逐个生成并统计渐变措辞（`buildStylePrompt`，`have:5`）：

```
旧措辞「允许渐变时只用相邻两级」   0 / 35
新措辞「只用同一色系里明度接近的两档」 35 / 35
禁渐变「不用渐变」                0 / 35
一版都没有                       0 / 35
```

**旧判据的正则对全部 35 案永远为假。** 它在报告里存在了几个月，
输出一直是「⑤ 禁项 无违反」，而这行字对 35 案一次都没有真实含义。

这不是"某几案漏了"，是**这条判据从未在任何一个案上执行过**。

### 为什么它能活这么久

因为它和它要查的东西**在同一个文件里、由同一次改动产生**：

- `prompt-copy.js:1276` 改措辞（S19 盲测后，为了让 AI 不当真去加渐变纹理）；
- `score.mjs:278` 的正则没跟着改；
- 两个文件之间没有任何闸门做交叉检查。

而 `check-ui-copy.mjs` 查的是**界面文案**（index.html/style.css/app.js），
`check-prompts.mjs` 查的是**提示词内容**，`score.mjs` 不在 quarter.mjs 的任何一步里。
**没有任何一条闸门知道 `score.mjs` 的正则和 `prompt-copy.js` 的措辞应该对应。**

### 这类缺陷的通解（建议加进 quarter.mjs）

> **凡是从被测物里抽字符串来匹配的判据，都必须有一条断言证明它能匹配上。**

具体到这里：`score.mjs --selftest` 现在有 30 条变异，但如果没人跑它，
那 30 条也不作数。所以真正的修法是把它接进 verify-research（已做，见 §十后续改动），
并且**在输出里显示匹配到了哪一版措辞**（已做）——
这样下次措辞再改，`⑤` 那行会变成「渐变 – 未判」而不是「无违反」。

## 十六、红队把我推翻了 80%：真缺陷是 `motion` 全库蒸发，不是四案缺交互

派了一个红队 Agent 专门攻击 §六。它给了数据，我逐条复核，**它是对的**。

### 反驳一：四案的机制不依赖 JS，去 JS 首屏几乎不变

### 反驳二：我漏了分母 —— 是 35/35，不是 4/4

## 十八、为什么 `motion` 蒸发了却没人发现：没有任何闸门知道它该进提示词

`motion` 在**闸门里**出现过一次，但用法和"进提示词"无关：

```js
// prototypes/_build/check-scenes.mjs:134
function bodyText(r) {

    r.cn, r.en, r.structure, r.tone, r.def, r.family, r.layout, r.visuals, r.motion,
    r.quirk, r.fontsSpec, r.risk, positiveScenes(r), …
  ];
```

它只是把 `motion` 当成**搜索文本**的一部分（用户打某个词能不能搜到这个案），
**不是**"它有没有进提示词"的断言。

实测：`prototypes/_build/check-*.mjs` 里提到 `motion` 的文件只有 `check-scenes.mjs` 一个，
且用法如上。**没有任何闸门检查 `motion` 是否被 `prompt-copy.js` 读取。**

### 同一条链上还有两个字段

| 字段 | data.js 有值 | 进提示词 | 有闸门吗 |
|---|---|---|---|
| `motion` | 35/35 | **0** | 无 |
| `audit` | 35/35 | **0** | 无 |
| `layout` | 35/35 | 3（含假命中） | 无 |
| `visuals` | 35/35 | 4（含假命中） | 无 |
| `risk` | 35/35 | 35 | 无（但它恰好全进了） |

`collect-schemes.mjs:191` 的 `FIELDS` 列了 13 个字段，提示词只用了一部分。
`risk` 全进、`audit` 全不进 —— **这是逐个手挑留下的漏，不是设计取舍。**

### 这类缺陷的通解

§十五 已经写过一条：凡是从被测物里抽字符串来匹配的判据，都必须有一条断言
证明它能匹配上。这里是它的兄弟版本：

> **凡是在数据层存在、且被产品文案承诺过会用的字段，
> 都必须有一条断言证明它真的到了交付物里。**

具体到这里，应该加一条闸门：

```
对每个 scheme 的每个非空字段 F：
  若 F 在 FIELDS 里、且 F 不是"仅供界面展示"的白名单成员
  则断言 buildStylePrompt(id) 里能找到 F 内容的可辨识切片
  否则 FAIL，报 "字段 F 在 data.js 有值但没进提示词"
```

白名单要显式写出来（比如 `cn`/`en`/`slug` 这类只给界面用的），
这样下一个加字段的人必须做一次有意识的决定，而不是默默漏掉。

**这条闸门写起来很便宜**（一个循环 + 切片匹配），
而且它会在 `motion` 蒸发的第一天就红，而不是等到 35 份产物都跑完才发现。

## 十九、`minItems` 审计推翻我：它不是双义字段，问题在**散文**

派了一个专家 Agent 做 35 案逐案分类。结论：**我在 §八 的诊断错了。**

### 错在哪

我说「`minItems` 一个字段承载两种语义」。事实是它**只有一重语义**
（同构重复单元的设计规模），而「少排会不会散架」这件事
**早在 2026-10-27 就交给另一个字段 `degrades` 了**，那一路工作正常：

```js
// prompt-copy.js:1123-1128 —— 已经是单一三分支，分岔正确
d.degrades
  ? "3. 但这个版式的位置是按 " + count + " 个数出来的…少一个就空一格：确实不足…整块重排"
  : "3. 这个版式是自动流排版，删条目只会让页面变短…你按自己的数量排就好。"
```

S34 的 `degrades` 是 `no`，**而且这个判定是对的**。证据（审计 Agent 给的，我复核过）：

```css
/* prototypes/S34-graphite-zero-photo-index/style.css */
:99   .drift-block:last-child { margin-bottom: 0; }        ← 用 last-child，不是 nth-child(7)
:223  .drift-block:nth-child(3n+1) { margin-bottom: 98px; }  ← 只在 @media (max-width:767px)
:235  .drift-block:nth-child(1) { margin-bottom: 104px; }    ← 只在 prefers-reduced-motion
```

**作者本来就是按"最后一块"写的。** 排 5 条就用 `.d1`–`.d5`，页面只会变短。
所以 S34 的 7 是内容规模，不是结构必需 —— 我判反了。

### 真缺陷在散文，与 `minItems` 完全正交

`quirk` / `mechanism` / `reuse` 三个**自由散文字段**各自把条目数重新写死了一遍，
而没有任何校验去核对散文与 `degrades` 是否一致。

审计 Agent 的 35 案分类（判据：`degrades` + 散文里有没有绝对序数）：

| 类 | 含义 | 案数 |
|---|---|---|
| A | `degrades=yes`，版面按序排定 | 13 |
| B | `degrades=no`，散文也干净 | 13 |
| **C** | `degrades=no`（能流），**但散文把 N 写死了** | **9** |

C 类 9 案：`S07 S11 S16 S21 S25 S28 S33 S34 S35`。
另有 7 个 A 类案（S05 S08 S12 S14 S15 S19 S23）**同时**被散文钉死 ——
**16/35 案有这个问题**，说明它与 `minItems` 正交。

### S19 才是真出事的那个，而且已经泄漏进产物

我把 S19 当"写对了"的正面样板。**看错了行** —— 结构约束段对了，签名怪癖段错了：

```
_prompt.txt 里同时存在三个互不相容的数：
  「这个版式设计时排了 20 个条目」
  「你手上有 5 条内容，就排 5 条」
  「位置随卡号从 001 到 240 每 20 张向右下偏移 1px…第 240 张…」
```

而盲测产物里真的写着：

```html
<!-- deliverables/78-northstar/_blindtest/S19/index.html:330 -->
<strong class="mono">NORTH-KEY / 240</strong>
```

**模型忠实执行了怪癖里的 240，把它写进了页头。** 用户只有 5 张卡。

### 修法：改散文 + 加闸门，不拆字段

**不要拆成两组正交字段。** 理由（审计 Agent 的，我认同）：

- `hard` 与 `degrades` **已经是**两组正交字段（4 案 vs 13 案，交集 3），
  不需要拆，需要**对齐文案**；
- `minItems` 与 `degrades` **不该拆** —— 它们是同一条轴的两个参数，已经正确分岔；
- 真正缺的是**一样东西，不是第三个字段**：一条校验「散文里的数必须与 `degrades` 一致」的闸门。

**散文改写原则**：靠「第 N 个」定位的一律改成不依赖 N 的相对说法。
S34 的改法（与 CSS 的 `:last-child` 天然一致）：

```
改前：第七块（下一期什么时候）的右边距，永远比其余六块窄 12px
改后：最后一块（收尾那一块）的右边距，永远比其余几块窄 12px
```

S19 的改法（同时消掉会把 AI 带偏的 240）：

```
改前：位置随卡号从 001 到 240 每 20 张向右下偏移 1px，因此第 240 张的压痕比第 001 张低了 12px
改后：位置随卡号每 20 张向右下偏移 1px，因此最后一张的压痕比第一张低了一截
```

## 二十、补上动效段之后：第一次有证据说明它真的到达了产物

**补对了没有？** 读提示词只能证明文本变了，不能证明产物变了。

## 二十一、S34 的「七档与重量绑定」：规律成立，但有一块坏点；AI 产物另有一个

§十九 末尾记了审计 Agent 的观察：「S34 原型自己只兑现了 36%」。
我复核后发现这个说法**不准确** —— 它是把整体相关性当成了"规律不成立"。
实际逐块算下来：

| 块 | 缩进 | 字数 |
|---|---|---|
| d1 | 0% | 130 |
| d2 | 3% | 110 |
| d3 | 5.5% | 108 |
| d4 | 2% | 128 |
| d5 | 7% | 104 |
| d6 | 4% | 115 |
| **d7** | **1%** | **74** |

```
整体 Spearman ρ = −0.43
去掉 d7 之后      = −0.94   ← 几乎完美
```

**所以规律本身是成立的（"字少的浮得远"），坏点只有 d7 一块。**
d7 缩进 1%（倒数第二小）却字数最少（74 字），它是整条规律的反向。

这比"兑现了 36%"有用得多：修一块就行，不是重做设计。

### AI 产物另有一个缺陷，而且比原型的更结构化

盲测产物 `_blindtest/S34-r2/index.html` 把七个缩进值**全写对了**
（`0/3/5.5/2/7/4/1%`，与原型逐字一致），但它多写了一句：

```css
width: calc(100% - var(--indent)); margin-left: var(--indent)
```

`margin-left: 7%` + `width: 93%` = 100% —— **每一块的右边缘都对齐了**。
缩进于是退化成"右边距"，"浮起"的视觉效果消失。

而原型 `style.css:102-108` 只设 `margin-left`，**不设 width**：

```css
.d5 { margin-left: 7%; }
```

块因此变窄、右边缘不齐，这才是"浮"。

这条值得单独记，因为它是**判据看不见的那类**：
缩进值全对（任何查数值的判据都判通过），但**语义反了**。
和本仓库 §9.19「量错了对象」是同一个家族 —— 量到了数字，没量到效果。

### 新闸门

`check-quality-distribution.mjs`：对每个声称「大小与重量相关」的案，
从原型取每个单元的缩进值与文本长度，算 Spearman ρ，
并逐块试"去掉某一块后能达到多少"来定位坏点。

**只报不判** —— 合格线取决于每个案自己的说法，而说法是中文散文。

写这个闸门时踩的两个坑都记在自测里：

1. `margin-left` 的正则要求 `%` 单位，把 `.d1 { margin-left: 0 }` 漏掉了。
   漏掉的恰好是缩进最小、字数最多的那一块 —— **ρ 从 −0.43 被拉到 −0.09**，
   直接翻转成"规律不成立"。一个单位后缀让结论反了。
2. 变异用例写成「把缩进数组 reverse」，那不是有效变异 ——
   reverse 一个本来就降序的数组只会让它变无序（实测 ρ 从 −1 变 −0.21），
   判据分不清"变了"和"该变的方向"。改成翻字数才是有意义的变异。

## 二十二、`audit` 字段：数据支持的结论是「不该整段进提示词」

`audit`（去 AI 味审查点）是最后一个已知缺口：35/35 有值、合计 11,365 字、

**但实测数据说不能直接补。** 复现：

### 数据

```

负面措辞     205 处（密度 18.0 处/千字 = 1.8%）
内部条款编号 123 处（C-x.y / 文件名 / P 编号）
正面标记      89 处
```

`audit` 里点名的 `C-x.y` 是 `deliverables/02-anti-ai-rules.md` 里那 27 条反 AI 规则的编号。
这个字段的本质就是「**我故意反了哪几条**」：

```
S34：第一，反 C-2.15「纯黑底 + 纯白字」：底色 #2C3034 而非 #000000，正文 #EBEEF0 而非 #FFFFFF。
     第二，反 C-1.6「白 / 灰交替分区」…
```

### 为什么不能直接补

这个仓库自己有一条硬发现，写在 `prompt-copy.js:1286`：

> arXiv 2601.08070 "Semantic Gravity Wells"（n=40,000，含 activation patching 因果干预）：
> **87.5% 的违规发生在「明确点名被禁词」时** —— 写下「不要用 #6366F1」
> 会**提高**模型输出 #6366F1 的概率。

而 `audit` 每 100 字就有 1.8 处点名被禁做法。整段塞进提示词，
等于把 205 处负面点名一次性交给 AI。

**这个仓库已经用同样的方法处理过一次这个问题**：`prompt-copy.js` 的防退化段
就是从「8 条禁令」改写成「8 条正面处方」的，改写原则写在
`:1298-1320` 的注释里（每条从「不要 X」变成「用 Y」，被禁项的名字一个都不留）。

### 自动转换也不可行

我试过只抽「跳脱之处：…」这类正面等价说法：

```
能抽出 ≥20 字的：9/35 案
抽不出的 26 案：S05 S07 S08 S09 S10 S11 S12 S13 S14 S15 S16 S17 S18 S19 S20
                S21 S23 S24 S26 S27 S29 S31 S32 S33 S34 S35
```

抽不出的案整段就是"我反了什么"，没有正面说法可抽。
**所以要做的是人工逐案改写，不是加个正则。**

### 结论与建议

`audit` **不该整段进提示词**，理由有三条独立的：

1. 负面点名密度 1.8%，与"点名即加权"直接冲突；
2. 123 处内部条款编号会一起泄漏，AI 没有图鉴目录；
3. 自动抽取正面说法只能覆盖 9/35 案。

**建议**：把它作为一条已知的、有明确处置方向的技术债记着，
修法是**逐案把 audit 改写成正面处方**（共 35 段，每段 216–444 字），
而不是加一行拼接。这与我先前对 `motion` 的做法不同——
`motion` 是纯描述性的（"滚动 200px 时缩放 68%"），可以直接拼；
`audit` 是负向评审记录，必须先转换。

`check-prompt-fields` 的 SKIP 名单里 `audit` 那条现在附带着这个结论，
不会被误读成"还没做，去做就行"。

2. **完整 token 匹配，不用子串。** `60px` 不能命中 `160px`

## 二十五、机制缺失要分层归因：是"提示词的洞"还是"机制句的问题"

§二十三 报了 9/14 命中、缺 5 处。但"缺"这个字掩盖了两件完全不同的事：

- 原型**自己也做不到** → 机制句写了一个两头都没落实的要求，那是机制句的问题；
- 原型**做得到、产物没做** → 提示词没把它传过去，或 AI 没复刻。那才是产品的洞。

不区分这两者，这个数只能说明"缺了几个"，说不出缺的是谁的锅。

### 修判据时先自己错了两次

**错一（字面匹配）**：第一版用 `decl.includes(tok)` 比对，于是
`opacity: .14` 不算实现 `14%`、`stroke-width: .5` 不算实现 `0.5px`。
实测 S07 因此被报缺 `14%`，而原型里写的是 `opacity: min(.14, calc(...))`；S19 的 `0.8px` 也是同一个原因被误报。

**仓库里早就有正确做法**：`check-prompts.mjs:634` 的 `mechSourceNumbers()`
把 px / mm / stroke-width / r / rx / ry / 百分比 / opacity 全归一成数值集合再比。
我另写一套字面匹配，等于把别人踩过的坑重踩一遍。现在直接照抄那个口径。

**错二（二值归因）**：修完归一化后，我把原型侧也判成"有/没有"两态，
于是 S13 的 `14%` 被归成"原型也没有"。查了 `style.css:13`：

```
一级 凹 条款标题盲压凹槽   压深 0.4mm  槽带亮度差 3.1%  边缘对比度 14%
```

它在**排版规格注释**里，实现里没有对应声明 —— 这正是
`check-prompts.mjs:1197` 已经在报的 `mech-value-comment-only`。
所以原型侧必须保留三态，不能压成两态。

### 修好之后的结论

```
S13  3%      原型：✓ 有声明   → 是产物/提示词的洞
S13  14%     原型：~ 只在注释里 → 本来就没有声明可复刻
S19  144px   原型：✓ 有声明   → 是产物/提示词的洞
S34  72px    原型：✓ 有声明   → 是产物/提示词的洞
```

**3 个是真洞，1 个是机制句写了推导值。** 这个分解是可以直接行动的：

- 那 3 个洞说明提示词没把机制量传够，或 AI 复刻时丢了 —— 下一轮盲测重点看这几个值；
- 那 1 个是机制句的老问题（S13 的 `14%` 是"用 3px 模糊反推出来的对比度"，
  原型靠截图实测回代定到 0.11，不是一条声明）。

### 判据现在的位置

`_mech-fidelity.mjs` 的用途从"报一个命中率"变成**给每个缺失值归因**。
自测 15 条（新增归一化 4 条：`opacity .14`、`opacity: min(.14,…)`、
`stroke-width .5`、百分比与长度不串）。

## 二十六、把「3 个真洞」逐条核到底：一个已修，一个真缺，一个判据盲点

§二十五 说 S13 的 `3%`、S19 的 `144px`、S34 的 `72px` 是三个真洞
（原型有声明、产物没有）。逐条核下来，这三个的情况**不一样**：

### S34 的 `72px` —— 已经不是洞了

第一轮产物缺，但**第二轮（S34-r2）实现得很完整**：

```
提示词要求：块间距 98/58/72px 三档
S34-r2 实际：margin-bottom: 98 / 58 / 72 / 98 / 58 / 72 / …
```

三轮循环，完全对齐。而两轮的差别是第二轮用了**当前提示词**
（含动效段 + 改过的第 2 条措辞）。

**所以这不是"提示词没传够"，是旧提示词没做到、新提示词做到了。**
`_mech-fidelity.mjs` 现在同时报 S34（1/2，缺 72px）和 S34-r2（2/2），
两个数都在，读者能自己看出这个进步 —— 这比只报一个数有用。

### S19 的 `144px` —— 真缺，而且我差点自己骗自己

产物里搜 `144` 是**有命中**的，但那唯一一处是：

```
.page { width: min(1440px, 100%); }
```

那是 `1440` 的子串。我先前手写 `grep` 时确实被它骗了一下，
所以专门验了归一化会不会误判：

```
"1440px" 归一化 → ['1440.00']
有 "144.00" 吗 → false
```

**判据没被这个子串骗到**（它按数值集合比，不按子串）。S19 确实没实现
`144px` 的开口高度 —— 它用对了 `grid-auto-rows: 24px` 的层级，
但开口尺寸这一档没做。

### S13 的 `3%` —— 真缺

原型有声明（`--shade` 系列变量），产物用的是 `--paper-deep` 一带的近似处理，
没有实现"槽带亮度差 3%"这个量。

### 这条对下一轮盲测的意义

三个洞里，一个是**已被新提示词修好的**（S34），两个是真缺（S13、S19）。
所以下一轮重点看的不是"机制句传没传"（它一直传着），
而是 **AI 复刻时丢了哪一档** —— 这是模型侧的问题，不是提示词侧。

## 二十七、⑤ 禁项只查了 7 条禁令里的 2 条

```

· 不要补满、不要删掉、编号不要重排

· 不要从深色直接过渡到浅色
· 禁止统一套做旧滤镜

```

而 `score.mjs` 的 ⑤ 只查两条：无阴影、渐变受限。

补了第三条**可机械验证**的：**字体链外**。判据是从提示词抽出允许的字体集合
（display 链 + body 链 + 等宽字体），产物里 `font-family` 出现的每个族名

**① 锚点写错**：我写「数字用等宽」，而原文是「编号/价格等数字用**等宽** Martian Mono」
—— 中间隔着「等」字。`Martian Mono` 因此没进允许集合，S01/S19/S21 全被判链外。

**② 正则跨行**：`[^（\n]+` 里的 `\n` 我漏了，正则吃掉整段，允许集合里混进了

```

```

这样一句完整的废话 —— 于是没有一个合法字体能匹配上。

**③ 空格截断**：等宽捕获写成 `等宽\s*([^\s、，,。]+)`，遇到空格就断，
只抓到 `Martian` 丢了 `Mono`。

三次都是一类错误：**判据在量错的信号**。而它们全都表现为「产物违规」，
三次都像是真缺陷。这正是这个仓库 §9.23 记的那条：
验证器本身是代码，错到「把对的判成错的」时，它会诱导你去改正确的东西。

现在 `UNDECIDED` 数组也收字体链与渐变，汇总如实报「⚠️ 未判 1 项：S13/字体链」。

|---|---|
| 不要回退成系统默认无衬线 | 能，但需要判断"某款字体是不是系统默认" —— 有主观性 |

## 三十、S18/S29 卡死的真实机制：模型在"先 glob 再写"路径上断掉

### 三次卡死是同一个位置

| 案 | 事件数 | 序列 |
|---|---|---|
| S18（两次） | 4 | chunk → usage → **glob** → glob completed |
| S29（两次） | 4 | chunk → usage → **glob** → glob completed |

全部停在 `glob` 完成后那一步，没有 `result`，10 分钟超时。

### 唯一成功的那次走了完全不同的路径

S15 的事件序列只有 3 个：

```
1. agent_message_chunk  text[27854]   ← 第一个事件就是完整 HTML
2. usage_update
3. result
```

**它没有 glob、没有工具调用、没有任何往返** —— 直接吐出了 27854 字的完整页面。

所以先前那个猜想（"cwd 里有文件导致 agent 进入探索模式"）解释不了这个现象：
两次开跑前 cwd 都是空目录，提示词结构也一样（三个都是 ~8000 字、
都含「图片位置写成」那一行）。

**真相是：模型有两条路径。**
- 路径 A：直接写完整 HTML —— S15 走的就是这条，一次成功。
- 路径 B：先 `glob` 探索目录，然后继续 —— S18/S29 走这条，而 `glob` 之后
  上游就断了（连续四次，两个案各两次）。

### 这对"重试"意味着什么

重试**不是**在赌上游随机好坏，是在赌模型这次走哪条路径。
S15 那次走 A 成功了；S18/S29 四次都走 B，四次都在同一处断。

所以：
1. **重试仍然有意义**（路径选择看起来与上游负载有关 —— S15 那次正是
   2.7 秒的最快窗口）。
2. **但"再试一次就过"的预期是错的** —— 四次里零次成功，不是运气差。
3. 如果一直走 B，改提示词让它别探索可能有用（`acp-run.mjs:99-104` 记过
   "空目录反而更快进入正题"），但那是在改被测对象去迁就工具，需要谨慎。

### 现在还缺什么

`hard` 四案：**S21 ✓、S15 ✓、S18 ✗、S29 ✗**。

两个跑出来的产物已经暴露了 5 条真缺陷（S15 的图片少一张 + 正文字号，

## 三十一、机制判据又一次「量了字面而不是量了等价」：S15 的 62%

机制保真度对 S15 报「缺 `62%`」。核实下来是我的判据错了，第三次犯同一类错。

### 事实

机制句：「图例挂 9–12 栏、**高度只到图幅 62%**」

产物：
```css
.legend { height: 403px; }
/* 图幅 */
.plate  { height: 650px; }
```

`403 / 650 = 62.0%` —— **换算完全正确**，只是写成了像素而不是百分比。

### 这是第三次同类错误

| 次 | 判据 | 字面缺的 | 实际实现 |
|---|---|---|---|
| §二十七① | 字体链允许集合 | `Martian Mono` | 锚点正则隔了「等」字 |
| §二十七② | 同上 | 整句进了允许集合 | 正则跨行 |
| §三十一 | 机制数值 | `62%` | 403px / 650px |

三次都是：**判据在量字面，而实现用了等价形式。**

### 修法

从产物抽出所有 px 高度，两两算比值；机制句里的百分比如果被某个比值
命中（±0.5%），算实现。只在百分比字面找不到时才走这条退路，
并在结果里标 `approx` 说明是换算命中，不假装是字面命中。

### 三条反向用例，防它变成恒真

```
eq('比值不符仍记 absent',     62% vs 200/650 → absent)
eq('百分比不被同数字的 px 满足', 62% vs width:62px → absent)
eq('换算中标记了来源',         approx.from === 403)
```

第二条尤其重要：`62%` 和 `width:62px` 的数字一样，但单位不同 —— 那是
`_discriminator-lib` 记过的坑（`60px` 不能命中 `60vw`），这里也要守。

### 结果

S15 从 3/4 变成 **4/4**。合计从 13/18 变成 14/18。

剩下 4 处缺失：S13 的 `3%`/`14%`、S19 的 `144px`、S34 的 `72px`
—— §二十六 已经逐条核过，那些是**真缺**（原型有声明、产物没有）。

## 三十四、「图片少一张」出现三次，根因是测试输入的 have=5

S01、S15、S24 三案的失败形态**一模一样**：

```
图片   版式 6 位 / 用户 5 条 → 合格线 5；实得 4 个 img（唯一 src 4）✗
```

三案的提示词措辞也逐字相同：

```
这个版式有 6 个图片位，但你只有 5 条内容：按你的内容放**不同的**真实图片，
空出来的图片位改成留白或文字块……
```

### 根因不是 AI 偷懒

`acp-run.mjs:96` 把测试输入写死成 `{biz, action, have: 5}`。
`minPics=6` 的案有 **18 个**（S01 S05 S09 S10 S12 S15 S16 S18 S19 S20
S21 S22 S24 S26 S27 S28 S29 S30），全部触发这个「6 位 / 5 条」分支。

而这句话里有两个互相拉扯的要求：

- 「按你的内容放**不同的**真实图片」→ 听起来是放 5 张（内容几条放几张）
- 「**空出来的图片位**改成留白或文字块」→ 听起来是有一个位可以空着 → 放 4 张

**模型选了后者。** 而评分器的合格线是 `min(have, slots) = 5`，判它少一张。

### 这到底是缺陷还是测试输入的局限

**主要是测试输入的局限。** 原型自己放 6–8 张：

| 案 | 原型 img 数 | AI 实得 |
|---|---|---|
| S01 | 6 | 4 |
| S15 | 8 | 4 |
| S24 | 6 | 4 |

原型没有被 `have=5` 这个约束，所以它按版式规模放满。AI 被塞了"你只有 5 条"，
于是它把"5 条内容"理解成"5 个图位最多"，再按"空出来的位"扣掉一个。

**换句话说：这个数字反映的是 `have=5` 这个假设与图片位数的冲突，
不是提示词写坏了。**

### 但它暴露了一个真实的产品问题

如果真实店主真的只有 5 条内容，而这个版式要 6 个图位，提示词该怎么说？

现在这句给 AI 的自由度过大（"空出来的位改成留白"），结果是它可能空两个。
**该说的是「尽量放满，最少放 N 张」**，而不是"空出来的位随你"。

这条记进待办，但**不在这一轮改** —— 因为改了之后 18 个案的提示词全变，
需要重跑才能验证，而归零的窗口随时会关。先把结论记下来。

### 顺带：S17 是目前唯一「结构标签用 section」还判对的案

S17 的 `<section>=4`、`<article>=2`、`<figure>=4`，判据选中 `section`（4 与 expect=5 差 1）
判 ✓。这说明 §三十三 那次「选最接近的标签」的改动是对的 ——
如果还是固定数 `article`，S17 会报 `article=2 ✗`，那是明显误判。

## 三十五、修正 §三十四：`have=5` 不必然导致图片少放

§三十四 我说「图片少一张的根因是测试输入的 `have=5`」。
**S22 推翻了这个结论。**

S22 与 S01/S15/S24 **完全同样的分支**（6 个图片位 / 用户 5 条内容），
但它放满了 5 张：

| 案 | 分支 | 实得 |
|---|---|---|
| S01 | 6 位 / 5 条 | 4 ✗ |
| S15 | 6 位 / 5 条 | 4 ✗ |
| S24 | 6 位 / 5 条 | 4 ✗ |
| **S22** | **6 位 / 5 条** | **5 ✓** |

四案同一分支，三个失手一个成功。所以「`have=5` 与图片位数冲突」
**不足以解释**这个现象 —— 它最多是一个风险因素。

### 那真正的差别在哪

S22 的 ④ 是 `<article>=6`（比 expect=5 多一个），说明它把这个版式的
重复单元做足了。而 S01/S15/S24 都恰好少一个。

现在能说的只有：**同一句提示词，模型产出不稳定**。
这个仓库记过同类结论（`_probe/31-content-instability.md` 判过"内容层不稳
不是缺陷"），图片位数量可能属于同一类 —— 需要更多样本才能定性。

**不改提示词。** §三十四 里我提的「改成尽量放满、最少 N 张」那个改法，
在没有足够证据说明这是系统性缺陷之前动手，就是在为一个不稳定现象
做过度设计 —— 而且会让 18 个案的提示词全变、需要重跑验证。

这条留作观察项，等样本够 5 个以上同分支的案再判。

### 这一节的教训

我在 §三十四 只看了三个失手的案就下了根因结论，而**手边就有第四个
同分支的案（S22）还没跑**。先跑完再归因，成本几乎一样。

这是这一整轮反复出现的同一个错误模式的又一例：
**手里的样本还不支持那个结论，但结论已经写下来了。**

## 三十六、图片位：「6 位 / 5 条」分支现在有 10 案数据，可以定性了

§三十四 我说这是提示词自相矛盾；§三十五 被 S22 推翻，改成"样本不足以定性"。
现在样本够了。

### 数据

### 结论

**这不是系统性缺陷，是模型不稳定性。** 10 案同一分支，60% 达标。

而且失手有两种性质，不能合并：

| 失手形态 | 案 | 性质 |

| 得 4 张（差一张） | S01 S15 S24 | 边界波动 —— 提示词允许"空出来的位改成留白"，模型在 4 和 5 之间摇摆 |
| 得 1 张（差四张） | **S09** | **真做了错**，不是波动 |

**S09 是唯一一个真正做错的。** 它整页只有 1 个 `<img>`，也没有用

### S09 的另外两处

```

④ 图片   6 位 / 5 条 → 合格线 5；实得 1 ✗
```

正文字号 14px 而要求 16px —— 这是全库跑过的 17 份产物里**偏得最多的一处**

### 对 18 个 minPics=6 的案意味着什么

按 60% 达标率外推，剩下未跑的 8 个 `minPics=6` 案（S10 S12 S16 S20 S26 S27 S28 S30）
里大约 3 个会失手。**这不是提示词要改的信号 —— 是"复刻保真度不是 100%"这件事的量化。**

提示词能做到的事：给出精确的图片位数量、允许空位留白。
它做不到的事：保证模型每次都严格数够。

这两件事必须分开。把后者当提示词缺陷去改，会陷入"为一个 60/40 的随机现象
做过度设计"——§三十五 已经在这个坑边上停过一次。

## 三十七、条目判据修完之后：20 份产物只剩 2 处失手

### 修了什么

S12 暴露两处判据错（详见提交 `eb83480`）：

1. **`rgba()` 不被识别为颜色槽**。`linear-gradient(45deg, transparent 0 26px, rgba(181,214,38,.035) 26px 28px)` 在 26px 硬切，但只解析出 1 个 stop。这是「判据量字面」第 N 次，这次把颜色写法抽成 `COLOR_TOKEN` 常量三处共用。

   7 = 5 内容 + 1 刻意空位 + 1 版式元素。判据把版式结构当成了内容条目。
   修法：剔除 class 里明确含 `empty/void/blank/placeholder/booking/cta` 的单元，
   但全都被标成空时不剔除。

### 修完之后的全部数据

20 份产物逐案看条目：

- S16：真做少了（只做 3 条内容，图片也只放 3 张）——和 S09 一样是"做少了"
- S34：做多了（7 条 vs 5 条）——已裁决为提示词与硬前提冲突

我原本猜「`degrades=no`（可流）的案更容易被 AI 用来少排」。**数据否掉了：**

## 三十九、渲染层的第二个盲区：入场动画让「可见性」变成时机问题

### 现象

渲染测量（`_render-audit6.mjs`）报：

```
S29    <section>: 源码  5 / DOM  5 / 可见  1  (opacity0 4)  ← 不一致
S32    <article>: 源码  5 / DOM  5 / 可见  2  (零盒 3)      ← 不一致
```

初看像"5 条内容只显示了 1–2 条"，是严重缺陷。

### 核实：不是缺陷，是测量时机

查 S29 的源码：

```css
.chapter { opacity: 0; transition: opacity 240ms linear; }
.chapter.revealed { opacity: 1; }
```

```js
document.documentElement.classList.add("js-ready");
// IntersectionObserver 回调里
item.classList.add("revealed");
```

**这是滚动入场动画** —— 每个 section 进入视口时才淡入。
而测量脚本在页面加载 0.9 秒后拍快照，那时只有第 1 个 section 进过视口，
其余 4 个还是 `opacity: 0`。

**而提示词恰恰要求了这个动效**（`motion` 字段：「滚动，章节索引条吸顶并随
滚动高亮当前章节（切换 100ms，阶跃无过渡）」）。所以 S29 是**忠实实现了要求**，
不是做错了。

### 这意味着什么

**「可见性」这个量在带动效的页面上不是常量，是时间的函数。**

我的测量在 t=0.9s 取一次快照，等于假设"页面是静态的"。凡是按提示词要求
做了入场动画的案，都会被这个假设误判成"内容缺席"。

这和 §9.19「量错了对象」是同一类：**量了 t=0.9s 那一刻的样子，
却当成"这个页面长什么样"**。

### 正确的量法（这次没做，记下来）

三种可选，各有代价：

1. **滚动到底再量** —— 模拟真人读完整个页面。代价：每个案多花几秒，
   而且滚动会触发 sticky/fixed 元素的状态变化，可能引入新偏差。
2. **量 `prefers-reduced-motion: reduce` 下的样子** —— 仓库的动效设计
   本来就要求降级到静态终态（`motion` 字段 35/35 都有「降级：」一节）。
   代价：量的是降级版，不是默认版。
3. **两次都量**（默认 t=0.9s + 滚动到底），把差异报出来 —— 差异本身就是
   "这个页面有多少内容依赖动效才出现"这个指标。

**推荐第 3 种**，因为它不假设哪个是"对的样子"，而是把两种状态都报出来。
但这一轮没有实现 —— 这一轮只做到"发现这个量是时机相关的"。

### 一个副产物

S32 的「零盒 3」和 S29 的 `opacity0 4` 是两种不同的隐藏机制：
- `opacity: 0` —— 元素有尺寸，只是透明
- 零盒 —— `getBoundingClientRect()` 返回 0×0，通常是被 `display:none` 或
  父容器压缩

判据要把这两种分开：前者多半是动画，后者多半是布局出错。

## 四十、渲染审计推翻了两件事，并查出一条我自己判据看不见的 A 级缺陷

派出的渲染审计 Agent（真 Chrome + `CSS.getPlatformFontsForNode` + 像素级裁决）
回来了。它做了 13 遍迭代，逐步排除了自己的误判。三条结论：

### ① 我上一节说的「S29 可见性」它查得更细，但也确认不是缺陷

它实测 S29 的 5 个 section：0.3s 时 1/5、1.3s 时 2/5、**3.3s 时 5/5**。
是 IntersectionObserver 的 lazy reveal，滚动到底就全出现。和我的判断一致。

但它额外查了 S18，结论更狠：

> `getComputedStyle(e).opacity` 对 job3–5 返回 `"0"`，但整页截图裁出的
> 区域里文字墨色 `17,17,17` 出现 3071 次 —— **内容被画出来了**。
> 成因是 `.job{animation:drop 40ms steps(1,end) both}` + 递增 delay，
> Chrome 把 `currentTime` 停在 `279.99999999999994`，
> `steps(1,end)` 在这个精度上取起始帧（opacity:0），但合成器用结束帧。

**这是一个 Chromium 的浮点边界 bug。** 所以 `getComputedStyle().opacity`
在 `steps()` 动画上会撒谎，`checkVisibility()` 也一样。
**这直接否掉了"加一条可见性判据"的方案** —— 那等于用一个会撒谎的量去判另一个量。

### ② 字体：10/18 案的渲染字体完全没落在链上（A 级）

这是我所有判据都看不见的。判据只查「`font-family` 里的字符串在不在链上」，
那只证明**字符串在**，证明不了**字体能加载**。

我自己复核了源码：

```
S18 产物：@font-face{font-family:GlowSansSC;src:local("Glow Sans SC")}
S18 原型：<link rel="stylesheet" href="../_fonts/css/glow-sans-sc-s18__400-500.css">
```

原型自托管 woff2；产物只有 `src:local()`。6 案（S13 S15 S19 S21 S22 S24）
连 `@font-face` / `@import` / `<link>` 都没有，只写了个名字。

**但关键判断：提示词从不要求自托管字体**（全文 0 处提到 `@font-face` / woff /
字体文件）。它只说「按这个顺序取第一个可用的」。所以这不是产物做错了，
是**提示词没告诉 AI 字体从哪来**。

已给 `score.mjs` 加 `fontSource` 四态（remote / embedded / local-only / none）。
实测 19 份产物：

```
9 案  无任何来源，只写了名字
3 案  仅 local()，依赖本机已装
7 案  远程
```

**12/19（63%）的字体加载不出来。**

### ③ `score.mjs` 读错了自己的源字符串

这一条与渲染无关，是判据自己的 bug：

```js
const bodyRule = html.match(/(?:^|\n)\s*body\s*\{([^}]*)\}/);
```

S01 的 CSS 是：
```css
html,
body { font-size: 16px; }
```
`body` 前面不是行首（前面是 `html,\n`），于是**这条规则被跳过**，
落到 `:root`，再落到「≥14px 众数」兜底，取到 **15px**。
而真实的 `body{font-size:16px}` 就在 `index.html:31-32`。

**修的时候我又错了两次：**

- 第一版 `(?:[^{}]*,\s*)?body` —— 把前一个块（`html { … }` 的尾巴）也吃进来
- 第二版 `[^,{}]{0,40}\s*,\s*` —— 还是跨到了 `html {` 那个块

根因是"从任意位置找 body"，而真正要的是「body 是某个选择器列表的一项」。
第三版改成**先切规则块、再逐个看选择器**，要求 `(?:^|,)\s*body\s*(?:,|$)`。

修完 S01 从 15px → **16px，与真渲染一致**。

### 修完之后正文只剩 4 案不达标

```

S09  14px（要 16）  ← 偏得最多
S15  15px（要 16）
S18  15px（要 16）
其余 17 案全对
```

这 4 案是**真缺陷**（不是判据问题）——它们确实把正文写小了。

### 一个方法论观察

字号判据是**内联在 `score()` 里的**，没法被 `--selftest` 打到。
所以「组合选择器漏匹配」这个 bug 静默存在了很久，没有任何断言发现它。

**能抽成纯函数的判据才有资格被自测。** 圆角、线宽、条目、图片、渐变、字体链
都已经抽出来了；字号还没有。这是下一步该补的。

## 四十二、改写"丢了 27% 的数值"——查下来丢的全是**被禁做法的尺寸**

### 现象

对 `audit` 改写前后做数值比对：

```

```

初看像信息损失。查丢失清单：

```
24px   S11 S12 S13 S15 S16 S17 S18 S19 S20 S21 S22 S23 S24 S25 S26 S27 S28 S29 S30 S31  （20 处）
32px   S04 S08 S09  （3 处）
2px    S29          （1 处）
```

**集中在 3 种值上，而 `24px` 一个人占了 20 处。**

### 查原文

```
S11 改前：「第二，反 C-2.11「24px 圆角 + 柔和投影的卡片浮起」：全部容器直角…」
S04 改前：「②它故意反 C-2.11——没有任何 16 至 32px 圆角，也没有一处柔和投影…」
```

**这些 `24px` / `32px` 全部出现在被禁做法的描述里** ——
`C-2.11` 就是反 AI 规则里那条「24px 圆角 + 柔和投影的卡片浮起」。

改写把它们删掉，是正确的：留着 `24px` 这个数在提示词里，
等于告诉 AI「有个叫 24px 圆角的东西」，而那正是要避免的。
这与 `prompt-copy.js` 防退化段记的 arXiv 结论一致（点名即加权）。

### 所以

**73% 的保留率不是损失，是把"不能用的值"剔掉了。**

真正该保留的设计值（`#DCDDD2`、`steps(4)`、`5:4:4:3`、`1px 实线框`）
全部还在。这条验证了改写没有伤到信息，反而减少了干扰。

### 一个可复用的检查

以后凡是"改写后某个量变少了"，第一件事是问：**丢掉的是"要做的"还是"不要做的"？**
负向清单里的数值天生就该消失 —— 把它们算作"信息损失"是量错了对象（§9.19 又一例）。

## 四十五、S19 的那条豁免，掩盖的是数据模型缺一个槽

这条注释写了两件事，第二件比第一件严重得多。**第一件是判据报了违规，

### 先说清楚：S19 的 `display` 没抽错

Spectral 加京华老宋体宽排」。**这段散文一次都没进提示词**
（`prompt-copy.js` 里 `fontsSpec` 引用数 = 0）。

### 普查：不是 S19 一例，是 5 例

写了一个提取判据（`_latin-role-probe.mjs`），两条来源按可靠性排序：

1. **作者显式命名的变量** `--f-latin` —— 直接声明，最可靠

结果：

| 案 | 拉丁角色 | 来源 | 作者原话 |
|---|---|---|---|
| S01 | Archivo | `--f-latin` 变量 | 「Archivo 拉丁标题（variable wdth 62.5–125）」 |
| S03 | Space Grotesk | `.h2` 规则 | （标题链是 IBM Plex Mono，`.h2` 级别换了） |
| S04 | Unbounded | `.board__latin` | 「Unbounded 拉丁标题 / Redaction 20 拉丁正文」 |

**第一次：靠选择器命名，两头不讨好。** v1 只看「选择器里带 latin/en/la」，
结果 S01 误报（`.latin` 那条其实是正文链，Archivo 写在 `--f-latin` 变量里

等宽是**已有的第三个角色**，不是第四角色。

修完之后 5/5 真阳、0 误报。但「5 个全中 0 个误报」这句话本身可以是
对着期望表写死的，所以加了三条变异：

```

· 变异 A（清空已占角色集）：误报 19 案（应 >0）✓ 守卫在起作用
· 变异 B（给 S21 注入 .zzz-latin → 中文族 Noto Sans SC）：认出（无）✓ CJK 过滤在起作用

```

## 四十六、「图片少一张」不是提示词缺陷 —— 7 份同构提示词否掉了这个结论

> 2026-11-22。这条的价值在于它否掉了一个很有诱惑力的行动。


|---|---|---|---|
| S01 | 4 | ✗ 少 1 张 | 12,304 |
| S09 | 1 | ✗ 少 4 张 | 15,496 |
| S15 | 4 | ✗ 少 1 张 | 28,920 |
| S24 | 4 | ✗ 少 1 张 | 13,880 |

**同一个输入，分成 3:5 两组。** 这就是全部结论。

也产生了 1–4 张 —— 那么原因就不在提示词里。

顺带排掉了一个更细的解释：**不是「写得短的偷懒」**。
失手组的字节区间 12,304–28,920，达标组 13,311–22,061，**两组完全重叠**。
S15 失手却有 28,920 字节（比任何达标的案都长），S20 达标只有 13,311 字节。
所以不是「篇幅不够导致细节丢失」这种可修的因果。

做成 `_pic-control-group.mjs` 接进了 `verify-research.mjs`（第 21 项）。
它守的不是「图片数对不对」，是**这个对照组本身还在不在**：

- 同构组少于 6 案 → 红（有人改了图片段措辞，对照没了）
- 某一组空了 → 红（无法再区分「提示词缺陷」与「模型失手」）

> 这一条是这一轮唯一一个**主动否掉行动**的判据。其余判据都在告诉你该修什么，
> 这一条告诉你**不该修什么**。在「5 个真缺陷」那种清单上，后者更稀缺 ——
> 因为清单上的每一条看起来都像该动手的地方。

### 那这 4 案怎么办

它们仍然是缺陷（产物确实少图了），但归属变了：

- **不是**施工图缺字段（字段在，7 份都写着 6 个位 / 5 条内容）

所以 `05-RESUME-HERE.md` §四 里这一行应当从「未修的产品缺陷」

它需要一次完整校准（§四 里还有几行同样需要重新归类），
单独改一行会让整张表的可信度反而更低。

## 四十七、`--all` 一直漏掉那两份最要紧的产物

> 2026-11-22。第①类缺陷（闸门读不到对象却报出干净数）的第五次复现。

给评分器加「提示词代次」标记之后，跑了一次全案汇总：

```
17 motion
 4 最早
```

**19 份。** 但磁盘上有 23 份产物。差的是 `S21-r2` 和 `S34-r2` —— 两个重跑目录。

原因是一行正则：

```js
.filter((d) => d.isDirectory() && /^S\d{2}$/.test(d.name))
```

`S21-r2` 不匹配 `^S\d{2}$`，被静默跳过。

### 为什么这一次特别糟

这两个目录不是随便两份产物：

| 目录 | 它是唯一能回答什么问题的样本 |
|---|---|
| `S34-r2` | `motion` 段的**唯一对照**（S34 两轮，第一轮四项动效全无、第二轮全有） |
| `S21-r2` | `audit` 段的**唯一样本**（全库唯一一份带 audit 段的产物） |

也就是说，**`--all` 一直在把「证明改动有效」的那两份证据排除在汇总之外**。
全案汇总里少掉它们，「`audit` 段有没有效」就永远没有分母；
而汇总照样打印一个看起来完整的分数。

### 这一条和前面几条是同一个病

这一轮已经抓到五次同一件事了，形状完全一致 —— **闸门读不到对象，然后报出一个干净数**：

1. 正对照跑的是产物不是原型（§阶段 2）
2. 只读第一个 `<style>`，渐变从来没被读过却报「渐变受限×4」
3. CSS 注释被当成字体声明
4. `undecided` 盖住了 `fontSource`
5. **`--all` 跳过所有重跑目录**

五次的共同点：**没有任何一处会报错。** 没有异常、没有警告、退出码是 0。
它们只能靠「心里有一个应有的数」去对 —— 这一次那个数是「目录里到底有几个文件夹」。

修法本身一行正则就够了。但要留住的东西不是那行正则，是**下次加筛选条件时先数一遍**：

```js
// 修法
/^S\d{2}(-r\d+)?$/
```

### 顺带：代次标记现在能读出四代

```
最早 4 案（S01/S13/S19/S34）      无动效段
motion 18 案                      有动效段，无 audit 段
audit 1 案（S21-r2）              有 audit 段
今 0 案                           加第四个字体槽之后
```

最后一行是 0，因为字体槽是刚加的，还没有任何产物用那版提示词跑过。
**这个 0 必须一直显示着** —— 它是最诚实的进度条：产品改了一处，
但要证明它有效，还差一整轮盲测。

## 四十八、把五次同形缺陷反过来用：枚举点巡检

> 2026-11-22。修完第五次之后，决定不再等第六次。

这一轮抓到五次同一形状的缺陷，五次都**不会报错**：没有异常、没有警告、退出码 0。
列在一起看，它们是同一句话的五种说法：

| # | 读不到什么 | 写了什么让它读不到 | 报出的干净数 |
|---|---|---|---|
| ① | 原型 | `score()` 的 `opts` 收了不用，dir 写死 | 「35 个原型 0 违规」 |
| ② | 第二个 `<style>` | 只取第一个匹配 | 「渐变受限×4」（其实一次没读过） |
| ③ | 真声明 | 注释没剥，注释里的 `monospace` 被当声明 | 一条纯注释制造的违规 |
| ④ | `fontSource` | `undecided` 一旦命中就不报来源 | 「字体链 – 未判」盖住「无字体来源」 |
| ⑤ | 重跑目录 | `/^S\d{2}$/` 不匹配 `S21-r2` | 汇总 19 份，实际 23 份 |

五次里**四次是筛选条件写窄了**（②③④⑤），一次是参数收了不用（①）。
共同点不是「判据逻辑错」，是**判据与对象之间的那一段路**。

### 所以写了 `_enumerate-audit.mjs`

它不修任何判据，只做一件事：把 259 个脚本里所有**枚举点**（`readdirSync` + filter、
以及用于「数出有几份」的正则）全部摆出来，然后在旁边列出磁盘上**真实存在**的数量：

```
磁盘上真实存在：
  盲测产物目录           25
  原型目录              35
  _probe 脚本          217

所有枚举点的正则（23 处）：
  assign-assets.mjs      /^S\d{2}-/
  _mech-fidelity.mjs     /^S\d/
  _report-numbers-audit.mjs  /^(S\d{2})-(?:sandbox|judge)\.html$/
  ...
```

旁边写着三个**只有人能答**的问题：

1. 这个正则允许的子名，和磁盘上真实存在的子名，一样吗？
2. 如果不一样，漏掉的那些里有没有最要紧的样本？
3. 漏掉时脚本会不会报错？（提示：这五次都不会）

### 逐条核的结果：23 处，没有第六个

核对下来两处最可疑的，都写对了：

- **`_mech-fidelity.mjs`** 用 `/^S\d/`（能匹配 `S21-r2`），而且显式处理了后缀：
  ```js
  /* S34-r2 这种带后缀的案号，数据要回退到前两位 */
  const base = id.match(/^S\d{2}/)[0];
  ```
- **`_report-numbers-audit.mjs`** 只认 `S\d{2}-(sandbox|judge).html`，
  而 `_staged/` 里确实就是这种命名，没有重跑目录。

**没有第六个。** 但这不等于以后不会有。

### 为什么这一项只报不判

`fail: false`。因为「应有多少」只有人知道 —— 脚本能数出磁盘上有 25 个产物目录，
但它不知道「这一次应该扫几个」。硬写一个期望值等于把答案抄进判据里，
下次条件写窄了，判据会跟着一起窄。

所以它的价值不在自动发现，在于**把人工核对的成本从「翻 259 个脚本」
降到「看一眼 23 行」**。这一轮我自己就是这样核的。

> 一条可以复用的问法：**加任何筛选条件之后，先数一遍。**
> 数出来的数和你以为的数不一样时，不要先解释为什么，先确认哪个对。

## 四十九、字体槽的端到端证据：S19 两轮，Spectral 从 0 次到 2 次

> 2026-11-22。这是这一轮唯一一份**只说一件事**的对比。

上游开了一次绿窗（中位 4.2s），先跑出 S09-r2，接着跑出 S19-r2。
S19 是第四个字体槽的靶案，两轮对比干净得少见：

| | S19（旧提示词） | S19-r2（新提示词） |
|---|---|---|
| 提示词代次 | `最早`（无动效段） | **`今`（含第四字体角色）** |
| 产物里的 `Spectral` | **0 次** | **2 次** |
| 判据②字体 | 3/3（Noto Serif SC, Georgia, IBM Plex Mono） | **4/4（+ Spectral）** |
| 图片 | 5/5 ✓ | 5/5 ✓ |
| 条目 | 5 ✓ | 5 ✓ |
| 配色 / 圆角 / 线宽 / 字号 | 全对 | 全对 |
| 产物字节 | 12,548 | 15,443 |

新产物里的实际声明：

```css
font-family:Spectral,"Noto Serif SC",Georgia,serif
font-family:Spectral,"Noto Serif SC",Georgia,serif
```

### 为什么这一份比 S21 那份更能说明问题

§四十三 的 S21 两轮，我明确写了「不是受控实验，不能归因」—— 同时变了三件事。
这一份不同：S19 两轮之间，**提示词只多了那一行第四角色说明**。

而且结果方向是**可以预先说出来的**：如果字体槽真到了产物，`Spectral` 的次数
必然从 0 变成非 0 —— 因为它此前根本不在允许集合里，任何产物写出它都会被判
「字体链外」。现在它出现 2 次，判据认了。

### 边界仍然要说清楚

- 它证明**这一次、这个案**上字体槽到达了产物
- 它**不**证明「5/35 案都会这么做」，也不证明「模型每次都会照做」
- 同轮跑的 S09-r2 不带这个字段（S09 不在那 5 案里），既不能当正例也不能当反例

现在的代次分布：

```
最早   4 案
motion 18 案
audit  2 案（S21-r2 / S09-r2）
今     1 案（S19-r2）  ← 第一个能验字体槽的样本
```

### 一条一直没解决的事，现在更清楚了

S19-r2 的判据⑤报「字体无可用来源×1」—— 它只写了字体名字，
没有任何 `@font-face` / `@import` / `<link>`。而原型是自托管的：

```
原型：<link rel="stylesheet" href="../_fonts/css/spectral__400-600.css">
产物：font-family:Spectral,... （然后就没有然后了）
```

这不是产物做错了。**提示词全文 0 处提到 `@font-face` / woff / 字体文件**，
只说「按这个顺序取第一个可用的」。AI 照做了，它做了被要求的事。

同一轮跑的 S09-r2 则自己用了 Google Fonts：

```
@import url('https://fonts.googleapis.com/css2?family=JetBrains+Mono:wght@500;
```

**两轮两种做法，提示词里都没有依据。** 这是产品侧一个明确的、已知的、还没补的缺口：
提示词没告诉 AI 字体从哪来。补法有两条，各有代价，这一轮没有选：

1. **给出自托管路径**（`prototypes/_fonts/css/...`）——
   但那要求用户的部署环境里有这些文件，而用户的站不一定放在同一个域名下
2. **允许 CDN**（`@import url(fonts.googleapis.com/...)`）——
   能做，但中文站点的 Google Fonts 可用性不稳定

第 2 条**已经在发生了**，只是提示词从没说过。

> 这种「行为已存在但没有依据」的状态最危险 ——
> 处理它的时候，很容易把已有行为当成回归误伤掉，或者反过来给一个
> 本来偶然的做法补一条它不配得到的许可。选择之前先要量清楚：
> 21 份产物里各有多少用了自托管、CDN、`local()`、什么都没有。

### 量清楚了：25 份产物，四种来源，内嵌为 0

按同一套判据（`judgeFontChain` 的 `fontSource`）扫全部 25 份产物：

| 来源 | 案数 | 含义 |
|---|---|---|
| **远程**（`@import` / `<link>` 到 CDN） | **10** | 能加载，但依赖外网 |
| **仅 `local()`** | **3** | 依赖**本机恰好装了**这款字体 |
| **无任何来源**（只写族名） | **12** | 能不能显示全看用户机器 |
| **内嵌**（`@font-face` + `url()` 自带文件） | **0** | —— |

四条结论，都和我原来的猜测不一样：

1. **内嵌是 0，不是「少数」。** 25 份里一份都没有。所以「让提示词给出自托管路径」
   不是修一件事，是**从零建立一种做法** —— 而用户的部署环境里根本没有
   `prototypes/_fonts/`。这条路在「用户拿提示词去别处生成」的产品形态下走不通。

2. **远程已经是主流（10/25）。** 不是我写的「已经在发生了」那种边角情况 ——
   是四成。提示词从没允许过，模型自己选的，而且是**最省事且大概率能work**的那条。

3. **12/25 什么都没写，这是最大的一档。** 这一档最危险：本地开发机上看是对的
   （系统里装了那些字体），部署到别的机器上就换字。**本地看不出问题**，
   所以它不会自己暴露。

4. **3 份只写 `local()`。** 这也是本仓库的老熟人 —— §四十五 里 S18 的
   `@font-face{src:local("Glow Sans SC")}` 就是这种，看着像声明了字体，
   实际是「赌用户装了」。

### 所以那两条候选路，第 2 条已经在赢

原来我写的是「两条路各有代价，这一轮没有选」。量完之后这个说法要改：
**第 1 条（自托管）在 25 份里实现了 0 次，第 2 条（CDN）实现了 10 次。**
不是没有偏好，是提示词没给依据而模型自己挑了。

正确做法因此不是「二选一」，是把已经占了四成的做法**写进提示词并说清代价**：

- 允许 CDN，并说明「中文站点若无法访问 Google Fonts，改用系统已有字体」
- 明确禁止只写族名（那 12 份的状态），因为它本地看不出问题
- 自托管不做强制，但可以写一句「如果你的部署环境能放字体文件，优先自托管」

这一轮不改提示词 —— 改产品要有依据，而这个依据（25 份分布）是刚拿到的。
下一个人接手时，这一节就是依据本身。

### 但复现的同时，抓出一处我自己写的自相矛盾

把 S19 的**拼好的提示词**整段读一遍（不是读数据、是读成品），发现：

```
2. 字体：标题按这个顺序取第一个可用的：Noto Serif SC → Georgia。
   …有一小块拉丁字单独用 Spectral 排。… 不要把标题、正文或数字改成它。
   不要用 上面两条链之外的字体。
```

**同一段里两句话打架**：一句让你用 Spectral，下一句说别用两条链之外的字体 ——
而 Spectral 恰恰在链外。

为什么没早发现：第 1 步我核的是 `dna-clean.json` 的字段，第 2 步核的是
「那句话在不在提示词里」，**两次都没读拼装后的整段**。
这是「验字段」和「验成品」的区别，而后者才是 AI 真正看到的东西。

修法是把「链」的范围改准，句式不变（抽取器靠 `/不要用 ([^。]+)。/` 识别这条约束）：

```
有第四角色 → 不要用 上面这几条链之外的字体。
无第四角色 → 不要用 上面两条链之外的字体。     ← 保持不变，别动没病的地方
```

连带后半句「也不要跳过上面这**两**条链回退成系统默认无衬线」也在同一个开关下改成
「这几条链」，否则矛盾只是往前挪了一句。

修完实测：

```
S01/S03/S04/S16/S19  有第四角色 → 「这几条链」✓
S09/S21              无第四角色 → 「两条链」  ✓
```

### 这条检查已经常驻

`_latin-in-prompt.mjs` 里加了一段「自相矛盾检查」，逐案读**拼好的提示词**、
比对「有没有第四角色」与「禁令用的是几条」，不一致就退出码非零。

> 这里有一条值得单独记的方法论：
> **核字段和核成品是两个动作，缺一个都会漏。**
> 这一轮字段核过了、到达也核过了，唯独「把成品当人来读一遍」没做 ——
> 而矛盾就长在那里。以后改提示词，三件事都要做：
> ①数据里有没有 ②提示词里有没有 ③从头读一遍这句话放在上下文里通不通。

### S04-r2：最严的那个检验，也过了 —— 而且它证明的是分工不是顺手

它应该把 Unbounded 用在标题上、或者两边都铺；实际是「楷体管主体、显示体管那一小块」——

### 但 S04-r2 同时暴露了三处真问题，都不能算在字体槽头上

否则对照组的分母会被悄悄改大。

**② 条目排了 8 条（要求 5 条，容差 ±1）。** 这次是**超了**，不是少了 ——
`<article>=8` 剔除 1 个空位后仍 8 条。判据报 ✗ 是对的。
注意这是**与图片相反方向**的失手：图片放少了，条目放多了。同一份产物里两个方向都有。

这个零数据现在是最要紧的一条：五个靶案全过，读起来像「字体槽没风险了」，

### 副作用：提示词层面查清了，产物层面在等数据

上面说的「零数据」分两层，这一轮把第一层补上了。

**第一层：提示词层面有没有泄漏。** 已查，结论是没有：

```
副作用检查（不该有第四角色的案）：
  ✓ 30 个不该有的案都没有出现那句话
```

判据：一个不在那 5 案里的案，提示词里不能出现「第四处字体分工」。
30 案逐个生成提示词比对 —— 都不含。所以那句新话**只写在它该在的地方**。

**第二层：产物层面有没有被带偏。** 这一层查不了，只能真跑。

「没泄漏」和「没副作用」是两件事，差别在于：即使提示词一字不多，
AI 在别的案上也可能**因为读到了这句句式**而改变行为（比如变得爱换字体）。
这种情况提示词检查是看不见的 —— 它是行为层的，不是文本层的。

所以 S21-r3 正在跑（S21 是普通案，`motion` 代有旧轮可比）。
它要回答的问题很具体：

> 同一案、同一代提示词（只差字体槽那一行），产物的字体数量和用法会变吗？

如果 S21-r3 的字体仍是 `5/5` 且没有多出链外族，说明那句新话没往外溢。
如果多出某个族，就要看它是不是被那句话勾出来的。

**在这个结果出来之前，「字体槽没有副作用」这句话不成立。**
已经成立的是更弱的一句：「字体槽没有在提示词里泄漏到别的案」。

### S21-r3 出来了：同一份提示词跑两次，字体完全一致

这是这一轮唯一一组**同输入重复**的数据，而它正好回答了副作用的问题。

S21 不在那 5 案里，所以新提示词对它**一个字都没变**：

```
S21-r2  _prompt.txt  md5 = 137348de…
S21-r3  _prompt.txt  md5 = 137348de…   ← 完全相同
```

同一份提示词跑两次：

| | S21-r2 | S21-r3 | 是否一致 |
|---|---|---|---|
| ② 字体 | 5/5（Antonio, WenJin Mincho, Georgia, Songti SC） | **5/5，同样四个** | ✓ 完全一致 |
| 线宽 | 0 处，无越界 | 1 处，无越界 | ✓ 都合规 |
| 图片 | 5 张 | 5 张 | ✓ |
| 条目 | 5 条 | 5 条 | ✓ |
| 字号 | 86/16 | 86/16 | ✓ |
| 字节 | 25,825 | 24,024 | 差 7% |

**字体那一栏是关键：两次都是同样四个族，没有多出任何链外字体。**

### 这条为什么能当「无副作用」的证据

推理链很短：

1. S21 的提示词在两轮之间**逐字相同**（md5 相同）
2. 两次产物用的是**完全相同的字体集合**，没有多、没有少、没有换
3. 所以在这份提示词上，字体行为是**确定的，不是随机的**

如果那句「第四处字体分工」有往外溢的倾向（让 AI 变得爱换字体），
它要么会出现在 S21 的提示词里（已验证不会，30 案全查过），
要么会让两次结果不一致（已验证不会）。

**这是目前能拿到的最强证据，但它仍然只覆盖一个案。**
要说得更硬，需要 2–3 个普通案各跑两次 —— 这一轮只跑成 S21 这一个。

### 顺带：S21 三轮的线宽，说明「概率性失手」确实是概率性的

```
S21    线宽越界 6px   （首轮，motion 代）
S21-r2 线宽 0 处      （audit 代）
S21-r3 线宽 1 处      （audit 代，与 r2 同提示词）
```

r2 和 r3 提示词完全相同，线宽一处 0 处一处 1 处 —— **同样不随机**，
但**用了几处线宽**这件事是会变的。这和图片数的结论一致：
「做不做这件事」稳定，「做了几处」有波动。

这个区分很重要，因为它决定了重跑能不能解决问题：

- **稳定的差异**（字体集合）→ 改提示词能修
- **波动的量**（图片几张、线宽几处）→ 重跑取优更实在


### 把它做成判据：`_repeatability.mjs`

S21-r2 / S21-r3 这一组数据太有用，不该只躺在报告里。做成判据（验证线第 24 项）：

```
══ S21  提示词 md5=137348de  产出 2 次：S21-r2 / S21-r3
   imgs     5 / 5                    一致
   arts     5 / 5                    一致
   lis      0 / 0                    一致
   fontN    3 / 3                    一致
   bytes    27015 / 25203            不一致
   字体集合 一致：Antonio|IBM Plex Mono|WenJin Mincho

稳定（改提示词可能左右）：imgs arts lis fontN 字体集合
波动（只能靠重跑取优）：bytes
```

它守着一条断言：**字体集合必须在同提示词下稳定。** 理由很直接 ——
如果「用哪些字体」都随机，那所有字体类判据的结论都不可重复：
一次通过不能说明提示词写对了，一次失败也不能说明写错了。

### 这个脚本自己错了两次，都留着

**第一次：不展开 CSS 变量。** 第一版「取 `font-family` 后面第一个族名」，
遇到 `font-family: var(--title)` 抽到的是 `var(--title)`，于是 S21-r3 的 `fontN=0`，
与 r2 的 3 个一比就报「不一致」。**假阳性，而且会把结论引向「字体随机」。**

**第二次：用错了判据。** 改用 `score.mjs` 的 `judgeFontChain` 之后，S21-r2 返回
`used: []`、`undecided: true` —— 因为**它不展开 `var()`**。

而同一份产物，评分器的判据②（`out.fonts`）**自己写了 `expandVars`**，报「字体 5/5」。

> **所以这个产品里有两份读字体的逻辑，一份展开变量、一份不展开，
> 对同一份产物给出相反的结论。**

它们并不是有一份错了，是回答的问题不同：

| | 问什么 | 展不展开 var |
|---|---|---|
| `judgeFontChain` | 写出来的族名**在不在链上**（管禁令⑤） | 不展开 → 全 var 时记 `undecided` |
| `out.fonts` | 提示词要的族名**出现了没有**（管覆盖②） | 展开 |

但要数「用了哪些字体」，必须用会展开的那一份。这是本仓库第一次为「读字体」
写出第三份实现 —— 明知有风险（记过四次「四份实现同一个 bug」），
但没有更好的办法：`score.mjs` 是 CLI 脚本、不导出判据，而这里要的是它的中间量。

**这条记在这里，是为了让第六份实现出现时有人能看见它。**
正确的长期修法是让 `score.mjs` 导出 `judgeFontChain` 并把 `expandVars` 提到共同位置，
而不是让每个探针各自照抄一遍。

### 样本量的自我约束

脚本现在会主动打印：

```
✓ 字体集合在同提示词下稳定（1 组 / 2 份产物）
  ⚠️ 只有 1 组，这个「稳定」没有第二组佐证 —— 多跑一组同提示词的才算数
```

第一版跑完只打印了「✓ 稳定」，而那时其中一份还因为不展开 var 读不到族名 ——
等于拿一个样本证明了一件事。这两个提示都必须留着。

## 五十、正对照第一次抓到真缺陷：S34 的等宽字体从来没进过提示词

> 2026-11-22。这是这一轮最有价值的一串因果，也是「正对照」这个概念唯一一次真正兑现。

### 起因是修一个「能力不对称」

上一节说到 `judgeFontChain` 不展开 CSS 变量，而判据②展开。这个不对称没有理由，
所以给 `judgeFontChain` 也加上展开。

加完立刻：

```
检查 35 个原型，1 个被判违规，0 条已豁免
  ✗ S34  字体链外×5
✗ 正对照失败：判据把合格样品判成违规了，先怀疑判据
```

### 按规矩「先怀疑判据」，查下来判据是对的

S34 的原型 CSS 里只有三条字体声明，全是变量：

```css
font-family: var(--font-body)
font-family: var(--font-head)
font-family: var(--font-num)
```

变量值是：

```css
--font-body: "Noto Serif SC", "Literata", Georgia, serif
--font-head: "Jost", "Noto Sans SC", sans-serif
--font-num:  "Sometype Mono", "Noto Sans SC", monospace
```

而提示词给的字体行是：

```
2. 字体：标题按这个顺序取第一个可用的：Jost → Noto Sans SC。
   正文同理，按序取：Noto Serif SC → Literata → Georgia。
```

**没有等宽那一段。** 「编号/价格等数字用等宽 X」这一句整个没生成。

### 往上追一层，根因在生成器的一个正则

`clean-dna.mjs` 的 `monoFamily()`：

```js
return /(mono|--num|figure|term|code)/i.test(d.name) && d.value;
```

`--num` 这个写法**匹配不到 `--font-num`** —— 因为 `--font-num` 里 `num` 前面是一个横线，
不是两个。S34 的等宽变量恰好叫 `--font-num`，于是 `dna.fonts.mono = ""`。

改按词匹配（`num` 而不是 `--num`），再补两条排除（值是纯数字长度的、以及
`--num-count` 这种计数变量不是字体），结果：

```
mono 有值的案：34/35
空 mono: S25
```

S25 查过了 —— 它全文 0 处 `mono|courier|consolas`，**确实没有等宽体**，空是对的。

### 这个缺陷为什么藏了这么久

这是整条链最值得记的一段：

| 层 | 之前的状态 |
|---|---|
| 原型 | 用 `var(--font-num)` 画数字，正确 |
| `dna.fonts.mono` | **空字符串**（正则漏了 `--font-num`） |
| 提示词 | 不生成等宽那一句 |
| 产物 | 确实没有声明等宽字体 |
| 判据⑤ | **不展开变量** → 读不到 `var(--font-num)` → 什么都没看见 |

**四层里三层是空的，而且互相吻合。** 提示词说「不用等宽」，产物就真不用，
判据又读不到，于是没有任何一处不一致 —— 这是一个**自洽的空洞**。

一旦把最后一层补上（判据开始展开变量），空洞立刻暴露：
产物用了 `Sometype Mono`，而提示词从没允许过 —— 「字体链外×5」。

### 这一串给出的两条可复用结论

**① 「两边都空」不等于「两边一致」。**
判据看不见 A，提示词又没写 A，看起来是「A 没问题」。
实际上可能是「A 从来没有被交付过，而判据也没能力发现」。
能区分这两种情况的唯一办法，是把判据的**读取能力**单独验一遍 ——
这一轮验的方式就是「判据②能展开变量，判据⑤不能，为什么？」

**② 正对照的价值不在于它通过，在于它会红。**
这一轮之前，正对照报过很多次「35 原型 0 违规」，但那次它**从来没真跑过原型**
（`opts` 收了不用）。修好之后第一次真跑、又第一次因为展变量而抓到真缺陷 ——
它是这一轮唯一一个**主动发现问题**的机制，其余判据都是我想到什么查什么。

现在的状态：正对照 **35 原型 / 0 违规 / 0 豁免**，自测 **105 条**，
研究线 **24 项**，产品链 **28 步**。

## 五十一、三次同提示词：图片数波动、字体稳定 —— 「概率性失手」有了直接证据

> 2026-11-22。§四十六 那个结论一直只有「同构但不同案」的间接证据，现在有了直接证据。

又跑了一次 S21。现在有**三份提示词完全相同**（md5 `137348de`）的产物：

| 量 | S21-r2 | S21-r3 | S21-r4 | 性质 |
|---|---|---|---|---|
| **图片数** | 5 | 5 | **4** | **波动** |
| 条目 | 5 | 5 | 5 | 稳定 |
| **字体集合** | Antonio/IBM Plex Mono/WenJin Mincho | 同 | 同 | **稳定** |
| 字节 | 27,015 | 25,203 | 24,670 | 波动 |

### 这一组为什么比前面所有证据都硬

§四十六 用的是**同构但不同案**的 7 份提示词（slots=6, have=5 逐字相同，但案号不同）。
那能说明「同一份约束在不同案上结果不同」，但留了一个反驳空间：
**也许 S01/S09/S15/S24 这四个案本来就比 S20/S21/S22 难。**

现在这个反驳没有了：**同一个案、同一份提示词、同一个模型，跑三次，
两次 5 张、一次 4 张。** 案难不难这个变量被彻底固定住了。

「图片少一张」是模型侧的概率性失手 —— 这句话现在不再需要推理，
它就是一个可以直接观察到的现象。

### 同时确认了「字体是稳定项」

三次的字体集合**逐字相同**：`Antonio|IBM Plex Mono|WenJin Mincho`。

这解释了两件事必须分开处理：

| 性质 | 例子 | 该怎么修 |
|---|---|---|
| **稳定** | 字体集合、条目数 | 改提示词 —— 重跑不会变 |
| **波动** | 图片数、字节数 | 重跑取优 —— 改提示词是白费力气 |

之前把「图片少一张」当成提示词缺陷去查，方向从一开始就错了。
而这个区分不靠推理，靠**同一份提示词跑两次**就能看出来 ——
代价是两次盲测，而它省掉的是改错提示词的一整轮。

### 一条给下一轮的现成方法

每当发现一个「做得不对」的量，先问一句：**它在同提示词下稳定吗？**

- 稳定 → 提示词的锅，去改提示词，改完重跑能验证
- 波动 → 模型的锅，别动提示词；要么多跑几次取最好的，要么接受这个方差

问这个问题只需要同一份提示词跑两次。而**没有任何一份重跑记录是提示词相同的**
（除了 S21 这三次），所以这一轮之前根本无从判断 —— 这是 `_repeatability.mjs`
存在的全部理由。

## 五十三、S34-r3：等宽缺口的端到端闭环，四层空洞全部打通

> 2026-11-22。§五十 那条因果链终于有了产出侧的验证。

### 三轮对比

| | 提示词里有等宽句 | 提示词代次 | 产物里 `Sometype Mono` | 判据②字体 |
|---|---|---|---|---|
| S34 | ✗ | `最早` | **0 次** | 4/4 |
| S34-r2 | ✗ | `motion` | **0 次** | 4/4 |
| **S34-r3** | **✓** | `audit` | **1 次** | **5/5** |

**提示词补上等宽那一句之后，产物就用上了。** 而且用法是对的：

```css
font-family: var(--mono)     /* :root 里 --mono: "Sometype Mono", ... */
```

### 这个案特别能说明「展开变量」那一步的必要

产物写的是 `font-family: var(--mono)` —— 一个变量引用，字面值里根本没有
`Sometype Mono` 这四个字。所以：

- **判据⑤不展开变量**时：读到的是 `var(--mono)`，判定「读不到」，记 `undecided`
- **判据⑤展开变量之后**：读到 `Sometype Mono`，判定「在链上」

同一份产物，同一句 CSS，两种读法两种结论。**S34-r3 引用变量、
S34 和 S34-r2 也没写 Sometype** —— 如果判据不展开，第三轮看起来会和前两轮一样干净，
而实际它多做了一件正确的事。

### 完整因果链回顾

这是这一轮唯一一条从「判据能力」一路修到「产物行为」的完整链路：

```
① 发现判据⑤和判据②的能力不对称（一个展开 var 一个不展开）
        ↓ 给判据⑤补上展开
② 正对照立刻红：S34 字体链外×5
        ↓ 按规矩先怀疑判据，查下来判据是对的
③ 追到 clean-dna 的 monoFamily 正则：`--num` 匹配不到 `--font-num`
        ↓ 改成按词匹配 + 两条排除
④ dna.fonts.mono 覆盖率 34/35（S25 是真没有）
        ↓ 提示词里「编号/价格等数字用等宽 X」那一句恢复生成
⑤ S34-r3 产物里 Sometype Mono 出现 1 次，判据②从 4/4 变 5/5
```

五步，每一步都有可验证的输出。而**起点是一个看起来无关紧要的「能力不对称」** ——
如果当时觉得「两份判据问的问题不同，不展开是设计」就收手，
这条链根本不会露头。

> 可以复用的判断：**当两份判据对同一份产物给出不同结论时，
> 先别急着解释成「它们问的问题不同」。** 先问一句「其中一份是不是能力更弱」。
> 这一轮的答案是：是的，判据⑤少了一个展开变量的能力，而这个缺失
> 掩盖了一个跨四层的产品缺陷。

## 五十四、变量展开这个改动，对 33 份产物到底改变了什么

> 2026-11-23。重启之后的第一件事：把改动前后的评分器都跑一遍，看差异。

改判据的时候只看了一处（S34 原型），没有核对它对其余产物的影响。
这种「改完之后没全量对比」正是这一轮反复吃亏的地方，所以补上。

### 做法

用 git 取出改动前的评分器（`7eba54a` 版），依次替换、跑 `--all`、比对。

### 结果：5 份从「判不了」变成「判了」，0 份新增违规

改动前，5 份产物的判据⑤显示「字体链 – 未判：产物全用 var()，不追展开」：

```
S13  S15  S21-r2  S34-r2  S34-r3
```

改动后，同一 5 份全部判出来了：

| 案 | 改动前 | 改动后 |
|---|---|---|
| S13 | 未判 | 字体 7 个在链上 |
| S15 | 未判 | 字体 6 个在链上 |
| S21-r2 | 未判 | 字体 8 个在链上 |
| S34-r2 | 未判 | 字体 5 个在链上 |
| S34-r3 | 未判 | 字体 9 个在链上 |

**没有一份从「在链上」变成「链外」。** 所以这个改动是纯增益：
判据覆盖面变宽，已判的结论一条没变。

### 为什么产物那边没有像 S34 原型那样暴露缺陷

S34 原型被抓到「字体链外×5」，是因为原型用了 `--font-num: "Sometype Mono"`
而这四个字不在提示词的允许集合里。产物那边没有同类问题的原因很具体：

- 那 5 份产物的字体变量值，**全部**是提示词允许的那几个族
- 也就是说这些产物本来就没乱用字体，只是**之前判据看不见**

这和原型那次不一样：原型那边是真的用了提示词没允许的字体。

### 这条对比最有价值的一点

如果一个改动只让你**多看见**问题、没让你**多有问题**，那它是安全的。
反过来，如果改完之后违规数上升，就必须逐个确认「是新发现的真问题，
还是判据变严造成的误报」——这一轮到目前为止每次都是前者，但那是运气。

所以以后改判据，标准动作应当是多一步：

> **改前跑一遍存基线，改后跑一遍做 diff。**
> 只跑改后那一次，你只知道「现在有多少违规」，
> 不知道「这个数是变来的还是本来就在」。

这次的做法是：`git show <改前 commit>:<文件> > 临时文件`，替换，跑，换回。
两次 `--all`，不到一分钟，但能回答一个否则永远说不清的问题。

### 工具本身也验了两遍，第二遍才发现它该测什么

`_scorer-diff.mjs` 写完之后，先用 `7eba54a`（变量展开那次的前一个提交）当基线：
33 案里 5 案变化、违规数不变。结果正确，但**这个基线太温和** ——
它只考了「结论从判不了变成判了」这一种差异。

换成 `e1c3478` 再跑：

```
共 33 案，其中 16 案的结论有变化

══ S01-r2
   改前  （无）
```

**「改前（无）」正是覆盖面缺陷的形状** —— 那时 `--all` 用 `/^S\d{2}$/`
扫不到重跑目录，所以 S01-r2 / S03-r2 / S04-r2 / S16-r2 / S19-r2 / S21-r2
这些案在旧版里根本不存在。工具把它们显示成「（无）」而不是「一致」，
这个区分很要紧：**「这一案没变化」和「这一案上次没被看见」是两件事。**

顺手确认了一件差点被我记错的事：`e1c3478` 那版的 `--all` 正则确实是

```js
.filter((d) => d.isDirectory() && /^S\d{2}$/.test(d.name))
```

（在 1525 行），而 `ac56c59` 那次修成了 `/^S\d{2}(-r\d+)?$/`。
证据在 commit 历史里，不是靠记忆。

### 三个设计点，都是踩过的坑换来的

1. **前置要求工作区干净** —— 否则「换回工作区版」这一步可能冲掉未提交改动
2. **恢复后校验 md5** —— 这一步静默失败的话，仓库里会留着旧版评分器，
   而之后任何人跑 `--all` 都得到过时结论，且**没有任何提示**。
   这和这一轮抓的五次缺陷是同一个形状。
3. **违规数变多时明确说「这既不等于改坏了也不等于改好了」** ——
   并给出分类办法：用正对照判，原型被判违规就是误报。

### 标准动作

> **改判据 → 改前跑一遍存基线 → 改后跑一遍 diff。**

只跑改后那一次，你只知道「现在有多少违规」，不知道「这个数是不是变来的」。
这一轮每一次改判据都只跑了改后一次，所以每次红都得重新论证一遍
「这是真问题还是误报」。有了 diff，这个问题变成一次对比。

## 五十五、给提示词补字体来源，连锁撞出三道闸门

> 2026-11-23。改产品的同时，闸门替我发现了两件我不知道的事。

§四十九 那份普查摆出了依据（28 份产物里 12 份只写族名、内嵌 0 份），
但当时写的是「这一轮没改提示词」。这一轮改了。

### 加了什么

`prompt-copy.js` 的输出要求段加两条：

```
字体必须写清来源，三选一：① 在 <head> 里用 @import 或 <link> 引入公共字体服务；
  ② 用 @font-face 指向随页面一起交付的字体文件；
  ③ 如果这两条都不可行，就在 font-family 里写出完整的回退链
  （例如 "Noto Serif SC", Georgia, Songti SC, serif），让缺字时能顺着链拿到字形。

中文站点若访问不到公共字体服务，直接退回系统已有字体即可，不要为了加载字体牺牲首屏。
```

两条设计都从普查数据来：

- **允许 CDN 而不是强制自托管** —— 内嵌是 0 份，用户环境里没有 `_fonts/`；
  而 CDN 已占 43%，是模型自己挑的
- **第③条写「写出完整回退链」而不是「不要只写族名」** ——
  按 arXiv 2601.08070，负面点名会加权那个做法；而且前者是可执行动作

### 改动立刻撞出三道闸门，三道都对

**① 文档一致性：提示词长度断言过期。**

```
✗ nums/prompt-len  区间下限 写 2923，实测 3147；上限 写 3509，实测 3750；
                   中位 写 3240，实测 3476
```

中文版和英文版都要改。这是闸门按设计工作 —— 它守的就是「文档里写的数 = 实测数」。

**② 提示词闸门的自测：`shape-output-short` 不响了。**

```
✗ shape-output-short —— 没响！断言无效
```

那条变异删掉「移动端单列」一行，原来让输出要求从 4 行变 3 行、触发「少于 3 行」。
**我加了两行之后模板变 6 行，删一行还剩 5 行，阈值 3 形同虚设。**

这是自测最有价值的一刻：它证明的不是「闸门能抓缺陷」，而是
**「我的改动让一条旧断言失效了」**。

### 修这条阈值时踩了第⑤类缺陷，第二次

第一次改法：把阈值从「硬编码 3」改成「当前这批提示词的行数众数」。
**仍然不响。** 因为自测会变异 `prompts.js`，众数跟着一起变小 ——
**阈值的来源和被判的对象是同一个**，两边同步，永远追不上。

这和这一轮抓过的五次缺陷是同一个形状，只是这次发生在「修闸门」的过程里。

第二次改法：阈值从**磁盘上的 `prompt-copy.js` + 真实 `data.js` 单独构建一次**得到，
不经过 `COPY_OVERRIDE` / `PROMPTS_OVERRIDE` 这两个自测变异通道。

改完仍然不响 —— 这一次是纯 bug：我写的 DOM stub 漏了 `getElementById`，
`prompt-copy.js` 里 `mountSceneChips` 调它时抛异常，`catch` 把阈值降级成 3。
补上 stub 之后：

```
全部变异都响了 —— 断言有效。
```

### 三条可复用的

1. **改产品会让闸门红，这是闸门在干活，不是障碍。** 三道红全是真信号：
   文档数字过期、旧断言因内容变多而失效、阈值算错。
2. **修「阈值的来源」时必须确认它和被判对象不同源。** 同源就是第⑤类缺陷，
   而且它长得特别像修好了 —— 因为代码确实变了，只是不会响。
3. **`catch` 里返回默认值会让测试静默失效。** 我那个 `catch { return 3 }`
   把「构建抛错」降级成「阈值是 3」，于是自测报的是「没响」而不是「构建坏了」。
   这类兜底要么不写，要么在兜底时**打一行日志**。

现在：产品链 **28 步**、研究线 **25 项**、评分器自测 **105 条**、正对照 **0 违规 0 豁免**，全过。
提示词长度 **3147–3750（中位 3476）**，35 案全部带字体来源句。

### 加完之后补一条常驻判据，因为「加了不等于好了」

`_font-source-rule.mjs`（验证线第 26 项）守三件事：

```
字体来源约束：35 案
  缺句 0 ／ 负面措辞 0 ／ 选项不全 0
  ✓ 35/35 都带，措辞正面，三条路齐全

  ⚠️ 还没验证生效：现有产物都不是用带这句的提示词跑的。
     验法：跑一个案，看它的 <head> 里有没有 @import / <link> / @font-face。
```

三条各自的理由：

| 查什么 | 漏了会怎样 |
|---|---|
| 35/35 都带 | 漏一案的后果是**那一案**的产物没有字体来源依据，而其余 34 案看起来都正常 |
| 措辞正面 | 「不要只写族名」会把那个做法加权（arXiv 2601.08070），反而提高发生率 |
| 三条路齐全 | 少一条 = 少一个合法选项，AI 被迫在剩下的里选，可能选到不适用的 |

**最后那句「还没验证生效」是刻意打印的。** 它挡的是这个仓库反复犯的错：
把「字段进了提示词」当成「事情办成了」。§四十五 那个字体槽从进提示词到
确认到达产物，中间查了三层（数据 / 散文 / 判据），才敢说生效。

所以这条判据通过**不代表字体来源问题解决了**，只代表「约束写对了」。
真要确认解决，得跑一个案看 `<head>` 里有没有 `@import` / `<link>` / `@font-face`。

## 五十七、渲染守卫量错了对象：内容没变 ≠ 没写报告

> 2026-11-23。改了个提示词，卡住整条产品链，追下去是第④类缺陷。

### 现象

给提示词补完字体来源之后，`quarter` 的陈旧度闸门红了：

```
⚠️ 1 项陈旧（改了源、没重渲就提交）：
   选型台(_selection)  prompt-copy.js  落后 6 个 commit
```

按提示重渲，渲染器自己报错：

```
report.json 与渲染前逐字节相同（inspect exit=1）—— 声称成功但没写报告，判为失败。
```

于是成了一个死循环：**stale 说该重渲，重渲说没写报告**。

### 根因：两条不同的路径被一个判据覆盖

`prompt-copy.js` 的改动是**提示词语句**。而选型台页面渲染的是**方案卡片列表** ——
提示词是用户点开详情、按「复制」才生成的。所以：

- 源文件（`prompt-copy.js`）变了 ✓
- 页面（`index.html`）一个字没变 ✓
- 报告（`report.json`）内容不变 **是正确结果**，不是失败

而那个守卫的判据是：

```js
if (before !== null && readFileSync(rep, 'utf8') === before) {
  console.error('声称成功但没写报告，判为失败。');
  process.exit(6);
}
```

**它量的是「内容有没有变」，而它想说的是「报告有没有被写」。** 这是第④类缺陷
（量错了对象），只不过这次发生在闸门自己身上 —— 而且这个守卫的注释里
还写着一段几乎相同的教训：

> `exit 码 ≠ 渲染成败，报告有没有被刷新才是`

那句话修的是「用退出码判成败」，改成用「报告有没有刷新」——
**而「刷新」被实现成了「内容有没有变」**。两步之间丢掉的正是「写但内容相同」这种情况。

### 修法：看 mtime，不看内容

```js
const repMtimeBefore = existsSync(rep) ? statSync(rep).mtimeMs : 0;   // spawn 之前取
...
if (contentUnchanged && statSync(rep).mtimeMs <= repMtimeBefore) {
  // 这才是真的没写
}
if (contentUnchanged) {
  console.log('内容与上次相同（页面未改动，属正常；mtime 已刷新）—— 继续。');
}
```

两个细节：

- **mtime 必须在 spawn 之前取。** spawn 之后取到的已经是本次渲染的时间，
  比较恒成立，等于没检查
- **内容未变时打印一行说明**，不是静默通过 —— 否则下次有人看到「渲染成功
  但报告没变」又会怀疑一遍

### 这一条和前面几条是同一族

这一轮抓了六次「闸门读不到对象 / 读错对象」。这次的特殊之处在于：
**它发生在一个已经写着正确原则的守卫里。** 注释说「报告有没有被刷新才是」，
代码写的是「内容有没有变」—— 原则对，实现偏了一步。

> 可复用的检查：**当一条判据的注释里有一句「X 才是真正的判据」，
> 就去核对代码里判的到底是不是 X。** 原则和实现之间的那一步，
> 是最容易被落下的一步，而且有注释作证时更不容易被怀疑。

- 某个案连续失败 → 是那个案有问题（提示词太长？某种句式让模型卡住？）

而失败时人的第一反应就是想清理干净。

## 六十、字体来源是波动项：同一份提示词，一次写 CDN 两次什么都不写

> 2026-11-23。给 repeatability 加上「字体来源」这一栏之后，立刻撞出一个反转。

### 数据

S21 三次跑的是**同一份提示词**（md5 `137348de`，逐字相同）：

```
   imgs     5 / 5 / 4                不一致
   arts     5 / 5 / 5                一致
   lis      0 / 0 / 0                一致
   fontN    3 / 3 / 3                一致
   fontSrc  remote / none / none     不一致   ← 这一行
   bytes    27015 / 25203 / 24670    不一致
   字体集合 一致：Antonio|IBM Plex Mono|WenJin Mincho
```

**一次写了 Google Fonts CDN，两次什么都没写。**

而这三份产物的提示词里**都没有**「字体必须写清来源」那句话（它们是 `audit` 代）。

### 这反转了什么

上一节（§五十九）刚拿到 S22-r2 的证据：加了约束之后，产物完整写了 Google Fonts 链接。
那只证明「约束能起作用」。

但这一组数据说明的是**另一半**：**不加约束的时候，「写不写来源」是随机的。**

```
S21-r2  remote  ← 自己想到要写
S21-r3  none    ← 没想到
S21-r4  none    ← 没想到
```

三次同样输入，1 次有 2 次无。所以：

- 43% 的产物有来源、57% 没有（§四十九 的普查），**不是两种不同的模型行为**
- 是**同一种行为的两次不同结果**
- 「12 份只写族名」不是「12 个模型决定偷懒」，是「12 次没想起来」

### 这对「补约束」意味着什么

好的一面：约束有效。S22-r2 证明了加上之后会写。

不好的一面：**如果它是波动项，那加约束只能提高概率，不能保证。**

一个粗略的估计：如果无约束时有约 1/3 的概率写来源，加了约束之后若变成
「每次都写」，那需要多份样本才能区分「概率从 33% 提到 100%」和
「概率从 33% 提到 50%」。而现在 `今+` 只有 **1 份**。

**所以 S22-r2 那一份证据，可能只是「本来就会写」的那 1/3 撞上了。**

这不是危言耸听 —— S21-r2 就是无约束时自己写了的那个例子。

### 该怎么补这个证据

最直接的办法：**用「今+」提示词再跑几次同一个案**。

```
已跑：S22-r2（今+，remote）
待跑：S22-r3（今+）—— 若也是 remote，说明是「稳定地写」
                    若变成 none，说明约束也只是提高概率
```

如果 `今+` 下连续两三份都是 remote，那可以说「约束把它从波动变成了稳定」。
如果仍有 none，那结论是「约束提高了概率但没消除波动」，而这对产品意味着：
**用户拿到的提示词可能生成有字体来源的站，也可能不生成，取决于运气。**

### 一条方法论

**别在拿到「一个正例」时就宣布改动有效。**
§五十九 那一节写的时候，我确实加了「样本是 1」的限定 ——
但这个限定的真实分量，是在看到 S21 那一行 `remote / none / none` 之后才明白的。

一个正例 + 一个已知的波动基线 = **可能只是碰巧**。
要区分「碰巧」和「有效」，最低限度是同一个输入跑两次。

## 六十一、两组独立证据：加了约束之后，字体来源仍然会漏

> 2026-11-23。这是这一轮最重要的一条，它推翻了「补了约束 = 解决了问题」。

### S22 两次跑同一份提示词，结果相反

```
══ S22  提示词 md5=115d3a38  产出 2 次：S22-r2 / S22-r3
   imgs     5 / 2                    不一致
   arts     9 / 3                    不一致
   lis      5 / 0                    不一致
   fontN    3 / 3                    一致
   fontSrc  remote / none            不一致    ← 这一行
   bytes    25869 / 11844            不一致
   字体集合 一致：IBM Plex Mono|Petrona|Zhuque Fangsong
```

**两份提示词 md5 逐字相同（`115d3a38`），都带着「字体必须写清来源」那两句。**

- S22-r2：写了 3 个 Google Fonts `<link>` + preconnect + display=swap
- S22-r3：**0 处来源**

而产物里的字体集合两次完全一致（`IBM Plex Mono|Petrona|Zhuque Fangsong`）——
**说明它知道该用什么字体，只是这次没写从哪加载。**

### 两组独立证据指向同一结论

| 组 | 提示词 | 有无来源约束 | fontSrc 结果 |
|---|---|---|---|
| S21 | `137348de` | **无** | `remote / none / none` |
| S22 | `115d3a38` | **有** | `remote / none` |

**两组都是「有时写、有时不写」。** 有约束的那组并没有变成「每次都写」。

### 这意味着什么

我上一节（§五十九）拿到 S22-r2 时的解读是「约束生效了」。现在必须修正：

**约束改变了措辞，但没有消除波动。** 准确的说法是：

- 无约束时：3 次里 1 次写了（S21）
- 有约束时：2 次里 1 次写了（S22）

两组的比例接近，**样本都太小，无法判断约束是否提高了概率**。
唯一能确定的是：**它没有把波动变成稳定。**

### 对产品的实际含义

**用户拿到的提示词，可能生成有字体来源的站，也可能不生成。**

这是一个真实的交付质量问题，而它的性质是：
**不是提示词写错了，是不可靠。** 而不靠改提示词能修好 ——
一个概率性行为，加一句更强的措辞只会略微抬高概率，不会消除。

可能的处置方向（这一轮没做，需要先想清楚）：

1. **接受它**，并在提示词里给出更强的兜底：
   「如果无法确定字体来源，就用系统已有字体的完整回退链」——
   至少让「不写来源」那种情况也有可用的兜底
2. **把它做进输出要求的结构位置**（比如固定编号），让模型更难跳过
3. **不修**，承认这是模型侧波动，把它归到和图片数同一类

**但做任何一条之前，得先知道基线。** 现在的基线是「2 组、5 份产物」，
其中 fontSrc 波动 2 次。要判断「约束有没有提高概率」，至少需要
每组 5+ 份同提示词样本。

### 一条方法论，这次是反向的

§五十 那条总结说「正对照的价值不在于它通过，在于它会红」。
这一条是它的镜像：

> **一个正例的价值不在于它出现了，在于它能不能重复。**

S22-r2 出现时，我有真实的理由高兴：它确实完整写了 Google Fonts，还加了
preconnect。但那个正例和 S21-r2（无约束时自己写的）**长得一模一样** ——
两者都是「有时候会发生」的那种事。

区分二者的方法只有一个：**同一份提示词再跑一次**。代价是几分钟，
而它推翻的结论如果不推翻，会一路传到用户手里。

## 六十二、`glob` 不是病因：它在成功和失败的跑里都出现

> 2026-11-23。收样本过程中连续失败，差点把伴随现象当成原因。

### 观察到的

S22-r5 连续两次失败，两次的失败形态都是：

```
session 建立 → glob → glob → glob → 进程消失
```

加上今天早先的 S10（三次失败，也都是 glob 后断），一个诱人的结论是：
**「glob 调用是死因」**。

### 对照推翻了它

把今天所有 S22 的跑排在一起，看 glob 出现次数与成败：

| 跑 | glob 次数 | 有产物 |
|---|---|---|
| S22-r2 | **0** | ✅ |
| S22-r3 | 1 | ❌ |
| S22-r4 | **1** | **✅** |
| S22-r5（两次） | 1 / 3 | ❌ / ❌ |

**r4 有 glob 且成功，r3 有 glob 且失败。** 所以 glob 不出现在成功的跑里这个说法是错的
（只有 r2 是 0 次），而「有 glob 就会死」也立刻被 r4 推翻。

**glob 只是失败时常见的伴随现象** —— 大概是因为模型在「不知道要做什么」时
会去探索目录，而探索到一半就断了。

### 这条为什么要单独记

因为「glob 后断」这个模式**看起来非常像根因**：

- 它出现的频率很高（5 次失败里 5 次有）
- 它有明确的因果外貌（调用 → 断）
- 修它看起来有明确的目标（比如在提示词里说「不要探索目录」）

而这些都是错觉。判据只有一条：**它在成功案例里也出现吗？**
出现了，就不是原因。

> 这和 §四十六 那次「图片少一张像是提示词缺陷」是同一类错误：
> 一个高频伴随现象，配上一个看起来说得通的机制，很容易被当成根因。
> 而推翻它只需要一个反例 —— r4。

### 顺带：新的取证机制第一次派上用场

这两次失败以前会**什么都不留下**（`rm -rf` 之后连痕迹都没了）。
这次因为 §五十八 加的 `persistEvents()`，目录里留下了 `_acp-events.jsonl`：

```
S22-r5 第一次：12 条 session/update
S22-r5 第二次：4 条，最后一条是 tool_call_update（工具调用中被打断）
```

**4 条 vs 12 条的区别，直接对应「断在更早的位置」** —— 这是以前拿不到的信息。

两份证据都存到了 `/tmp/s22r5-evidence.jsonl` 和 `/tmp/s22r5-evidence2.jsonl`。
（注意：`/tmp` 会被系统清理，重要证据应当在仓库内 —— 但这两份只是当次调试用，
结论已经写进本节，不必长期保存。）
