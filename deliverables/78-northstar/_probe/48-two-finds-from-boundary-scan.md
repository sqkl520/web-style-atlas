# 扫边界扫出两件事：4 案在说自相矛盾的话，以及中英中位数从来没比对过

> 2026-11-15　主线程
> 上一轮修了 `have` 与图片位的冲突（`47-have-pics-conflict.md`）。
> 那一轮只修了**我被撞到的那一处**，所以这一轮我系统扫了一遍：
> 用户内容很少时，提示词里还有哪些绝对要求会撞上。

---

## 一、扫法

把 35 案 × `have=1` 全部生成，抽出每案的结构约束段，把每条句子的数字归一化成 `N`，
按「同形句子」聚合。结果：**37 种不同句子**。

对含绝对量词（至少要 / 就排 / 必须 / 一律 / 只能 / 全站 / 每一个）的逐条人工判断。

### 1.1 结论：真正的冲突只有两类

| 类别 | 判定 |
|---|---|
| 第 2 条「就排 N 条」与第 4 条「至少要 M 个图片位」 | **已在上一轮修掉**（`have < minPics` 时降级） |
| 第 6 条「如果你的内容里没有这个东西，请先告诉我」 | **不是冲突**，是设计好的退出通道 |
| 第 4 条在 `minPics=1` 时的措辞 | **是真缺陷**，见 §二 |

第 6 条那 22 处「硬前提」句子看着像绝对要求，但每一句后面都跟着
「如果你的内容里没有这个东西，请先告诉我，我们换一个更合适的版式」——
它给的是退路而不是压力，不需要改。

## 二、真缺陷：`minPics=1` 的 4 案在说自相矛盾的话

S31 / S32 / S33 / S35 的提示词第 4 条：

```
4. 版式里至少要 1 个**不同的**图片位置（不是1 个 img 标签就够——同一张图重复用不算）。
   每个位都要占出真实可见的面积与合适比例，路径用 images/ 占位（见末尾输出要求）。
```

**只有 1 个图片位时，1 个 img 标签就是够的。** 「同一张图重复用不算」在只有一个位时
也无从谈起 —— 没有第二张图可以「重复」。

括号里那句警告是**为多图位写的**，套到 1 上就成了病句。

### 2.1 为什么一直没被发现

没有人逐字读过这 4 案的提示词。闸门读过它们 —— 但闸门查的是
「提示词列出的每个数字在 CSS 里存在不存在」，不查句子通不通。

这正是本仓库归纳的问题的一个变体：**闸门能证明「说得对」，不能证明「说得通」。**

### 2.2 修法

```js
(s.minPics >= 2
  ? "不是" + s.minPics + " 个 img 标签就够——同一张图重复用不算"
  : "这一处必须是真图，不能用纯色块或占位图顶替")
```

关键是**不能整句删掉**。原来那句里藏着两条实质约束：

1. 「必须是真图」（不许用色块顶替）
2. 「不同的图」（多图位时不许重复用）

`minPics=1` 时第 2 条不成立，但第 1 条仍然成立 —— 所以替换而不是删除。

### 2.3 两个变异，各守一种错法

| 变异 | 守什么 |
|---|---|
| `minpics-one-nonsense` | 退回原来那句自相矛盾的话 |
| `minpics-one-lost-constraint` | 走另一个错法：整句删掉，矛盾没了但实质约束也没了 |

第二个变异是有意设计的：**只做第一个变异，就分不清判据是真的在查「必须是真图」，
还是只在查「没有那句病话」。** 修一个错引入另一个错，是这类修复最常见的失败方式。

## 三、顺带发现：`check-docs` 从来没比对过中英中位数

修完之后提示词中位数从 1979 变成 1975，`check-docs` 报了一条警告。
顺着查下去发现：

```
README.md      中位 1979 字
README-EN.md   median 1,968
实测            1975
```

**两个文档差 11，而闸门报 0 FAIL / 0 WARN / 13 PASS。**

### 3.1 为什么会漏

`check-docs` 里有两条相关断言：

| 断言 | 管什么 | 为什么没抓到 |
|---|---|---|
| `nums/prompt-len` | 每个数字与实测的差 | 容差 3%，1979 和 1968 相对 1975 **各自都在容差内** |
| `i18n/facts` | 中英两份是否一致 | 只比了提示词区间的**两端**，没比中位数 |

**「各自都对」不等于「两份一致」。** 前者是 nums 的职责，后者是 i18n 的职责，
而 i18n 这一段漏了中位数这一个字段。

### 3.2 修法

在 `i18n/facts` 里加一条，**用严格相等**（不用容差）：
两份文档描述的是同一个实测值，没有任何理由容忍它们相差一个字。

实测两个方向都对：

```
一致时：README.md: 0 FAIL / 0 WARN / 13 PASS
不一致：✗ i18n/facts  README 与 README-EN 的同一事实不一致：提示词中位数：中 1975 vs 英 1968
```

### 3.3 写判据时又踩了一次同样的坑

第一版正则写成 `(?:median)\s*([\d,]{3,6})\s*characters`，以为英文会写
「median 1,975 characters」。实际是 `median 1,975)` —— 后面紧跟右括号。

结果只匹配到中文那份，报「只有一份写了」。

改成用千分位分隔符区分（`\d{1,2},\d{3}`），因为同一份文档里还有
「median 314」（反 AI 味评审点字数）和「median 10.9 h」（搬迁工时），
都不能误抓。

**这是这个仓库第 N 次因为「判据比原文更我以为的样子」而报假警。**
`check-docs` 自己在 2d 那一段的注释里就记过同一个坑。
