## 0. 为什么必须做在文本上：两个已经发生过的事故

### 事故 A（仓库已记录）：值在数据里，没进文本

`prototypes/_selection/prompt-copy.js:643-677` 的长注释记着：`h1Size` 在 `dna-clean.json` 里抽到 **30/30**，但渲染进提示词的案 **0/30**。原因不是数据缺口，是那句写在 `mech` 的 `else` 分支里，而 `mechanism` 在 build-prompts 阶段被 30/30 补齐，`if (d.mechanism)` 恒真 → else 永不执行。

这类缺陷的特征：**数据非空、文本缺失**。作用在 dna 上的断言（`check-prompts.mjs` 现有的 `stale-vs-dna-clean`、`mech-empty`）对它**零反应**——它们读的就是那个非空的字段。

### 事故 B（本轮实测复现）：值在文本里，被静默降级

把 S13 的 `bodySize` 清空，第 6 条从

> 6. 字号：正文约 15px；最大标题要压到正文的 3.7 倍（约 56px）。比这更小就撑不出这个版式——这是本案最容易被做塌的一处。

**静默降级**成

> 6. 字号：最大标题取 56px 这一档，比这更小就撑不出这个版式的气势。

而 `node prototypes/_build/check-prompts.mjs` 报 **FAIL 0 / WARN 1**，与正常态完全相同。

原因在 `prompt-copy.js:665-677`：整个第 6 条是一个 IIFE，`body > 0` 为假时走 `return "6. 字号：最大标题取 ..."`，**仍然返回一行**。因此「第 6 条存在」这件事恒真，而「第 6 条给了倍率」这件事没人看。

### 事故 C（本轮发现，已修）：值在文本里，但列表被挖了个洞

`buildStylePrompt('S34')` 的结构约束段，修复前是 `1、2、3、5、6`——**没有第 4 条**。

根因：`prompt-copy.js:826` 的 `s.minPics ? "4. …" : ""`。S34 的 `minPics` 是 `0`（全库唯一），falsy → 空串 → `prompt-copy.js:991` 的 `.filter(x => x !== "")` 把整行滤掉。**但 `"4. "` 这个编号是写死在字符串里的字面量**，整条消失时编号跟着消失，而后面 `"5. "`、`"6. "` 的编号仍然固定。

这不是排版瑕疵：提示词内部有交叉引用（`⑤ …（见第 5 条）`），**编号是可被引用的地址**。一个中间断号的列表会让模型无法判断「第 4 条是被截断了，还是本来就不适用」，而 `prompt-copy.js:838-843` 的注释讨论过跳号，讨论的却只是**末尾**缺条（reuse 为空 → `1,2,3,4,5`，连续但短一条），没覆盖这种中间挖洞。

**已修**（`prompt-copy.js:826-838`，工作区未提交改动）：`minPics === 0` 时第 4 条改成正向声明「本案是零图片设计：整页不出现任何图片位，全用文字与色块承载，不要自己补图片」。修后编号 `1,2,3,4,5,6`，并顺带补上了一条此前缺失的信息（AI 原本不知道「没图片位」是设计还是漏了，可能自己补几个来凑）。

### 三类缺陷的共同形状

| | 数据字段 | 输出文本 | 现有闸门 |
|---|---|---|---|
| 事故 A | 有值 | 缺句 | 绿 |
| 事故 B | 有值 | 句子退化 | 绿 |
| 事故 C | `minPics=0` 正确 | 编号挖洞 | 绿 |

现有 `check-prompts.mjs` 的唯一模板类断言是 `REQUIRED_MARKERS`（`check-prompts.mjs:847-861`），只查 4 个标记：`我经营＿+。`、`视觉硬约束`、`结构约束`、`输出要求：只给一个完整单文件 HTML`。**4 条 / 约 39 行骨架**，覆盖率约 10%。事故 B 的降级句里「6. 字号：」仍在，所以连 `无字号信息` 那条 WARN（`check-prompts.mjs:745`）都不会响；事故 C 的断号更无从查起，因为 `.filter` 之后编号本身就不连续地存在了。

## 2. 断言清单

设计分两层，**守的是不同的东西**：

- **T 层（24 条，形状断言）**：只看文本，不看数据。守「模板骨架没有被改坏 / 没有退化成更弱的句子」。**恒真风险最低**——它们读的就是最终交付物。
- **W 层（14 条，接线断言）**：把文本里的值拉回去和 `dna` 对账。守「值有没有接进文本、接的是不是那根线」。这一层直接对治事故 A。

### 2.1 T 层：形状断言（24 条，全部 35/35）

### 3.1 方法：如何在内存里造变异（不改真实文件）

`check-prompts.mjs` 的 `--selftest` 只支持 `PROMPTS_OVERRIDE`（`check-prompts.mjs:46`），也就是说**它只能变异 `prototypes/_selection/prompts.js`，无法变异 `prompt-copy.js`**。而本轮 39 条断言里有相当一部分的键位在 `prompt-copy.js` 的模板字面量里。

本轮探针用的办法：把三份源码读进内存，`new Function` 加载后**替换字符串再重新加载**，全程零写盘。要接进 `--selftest`，需要新增一个 `COPY_OVERRIDE`（见 §4.2）。

### 3.3 「假响」是怎么避免的

三类假响，本轮都实测识别出来了：

**假响 1：变异同时改了形状和接线，目标断言只是被「形状变化」带响的。**

例：删掉字号条的倍率子句 → T-11（形状）与 W-02（接线）同时响。这不构成对 W-02 的**独立**验证：无法排除「W-02 其实只看了形状」。

避免办法：**为每条 W 断言单独造一个「形状不变、只有值错」的变异**。上表里的 `bodySize 写死 16px`、`倍率写死 4`、`h1 按 0.7 缩放`、`hex 换 #ABCDEF`、`线宽换 99px` 就是这个用途——它们改的是**接的哪根线**，行仍然匹配整条正则，所以 T-11/T-06/T-10 都不响（实测：这三个变异各自只响 W-02 / W-03 / W-04）。

同理，T 断言的独立性靠「接线不变、只有形状坏」的变异：`圆角行双句号`（值没变，多了个句号）、`字体纪律行缩进 3→0`（内容没变，缩进变了）、`结尾多一个换行`。

**假响 2：断言自身缺 `/g` 而恒真。** 见 §4.3。

**假响 3：变异根本没生效，但探针打印了「✓」。**

本轮探针在早期版本上有过这个 bug：用正则替换 JSON 源码时把引号配对截错，导致 `new Function` 抛错，而错误被 `catch` 吞掉，输出回落成基线，于是「变异没变、断言没响」被误判成「✗ 没响」。修法是给每个变异加**生效断言**：`if (mutated === original) throw`，并且在跑断言前先比对 35 份输出与基线的**差异案数**，`changed.length === 0` 直接判 `!!`。上表所有行都通过了这一步。

### 3.4 复现历史事故 A 的验证

把第 6 条字号行整块搬回 `mech` 的 `else` 分支（复刻 `prompt-copy.js:643-649` 描述的那个事故），实测：

- 提示词里还有第 6 条的案：**0 / 35**
- 会响的断言：**T-11（105 处）+ T-16（编号跳号）+ W-02（接线断）**

也就是说，事故 A 那个「数据 30/30、文本 0/30」的形态，被这组断言抓到了 105 处。作为对照，现有闸门在这种状态下仍然是绿：它的 `REQUIRED_MARKERS` 不含字号条，`no-typescale` 那条 WARN 也查不出来——因为 `text` 里还有「最大标题」四个字，`/字号|字阶|最大标题|主标题取|font-size/` 会命中。

## 4. 接入 `--selftest` 的方案

### 4.0 先记一次判据放宽的教训（事故 C 的判据版）

本报告初稿的 T-16 判据是：

```
结构段：从 1 到 max(编号) 逐个补，但 n===4 且 minPics===0 时跳过该号
```

它把 S34 的 `1,2,3,5,6` 当成期望形态，也就是**把缺陷写成了判据**。后果会是：闸门上线第一天就带着一个「已知错误被固化成正确」的洞——以后任何人删掉第 4 条，T-16 都不会响。

这是本仓库记录在案的老病换了位置：**闸门与被测对象共用同一个盲点**。它比「没有断言」更糟，因为绿勾会让人以为这条被守住了。

正确的处理顺序是**先修被测对象、再收紧判据**，而不是反过来：

| 步骤 | 做法 | 结果 |
|---|---|---|
| 1 | 修 `prompt-copy.js:826`，`minPics === 0` 时第 4 条改成正向声明 | S34 编号变 `1,2,3,4,5,6` |
| 2 | 判据收紧成严格的 `[1..N]`，删掉例外 | 35/35 通过，无需例外 |
| 3 | 新增 W-15，守住「零图案不得要求图片位」 | 35/35 通过 |

修后实测（当前工作区代码）：

```
35/35  T-16 三段编号各自 1..N 连续（硬 6 / 结构 reuse?6:5 / 验收 3）
35/35  W-09 结构第 4 条始终存在；minPics=0 时为零图声明
35/35  W-12 结构段条数 == (reuse?6:5)
35/35  W-15 零图案不得出现「N 个图片位置」要求
S34 结构段编号: [1,2,3,4,5,6]
```

**变异验证**（三条都实测）：

| 变异 | 响的断言 |
|---|---|
| 删掉结构第 4 条整块 | W-09，34 案（除 S34 外全部，因为 S34 走另一支） |
| 零图声明删掉、退回空串（复发事故 C） | T-16 / W-09 / W-12，各 1 案 = S34 |
| 零图声明改成「至少要 1 个图片位置」（自相矛盾） | W-09 / W-15，各 1 案 = S34 |

**这条教训对后面所有断言都适用**：写判据时如果发现「某案通不过」，第一个动作是**查该案的输出是不是错了**，而不是改判据去迁就它。本轮的唯一例外是 W-13（S34 的 reuse 里带嵌套引号导致 `「[^」]*」` 截断）——那个是**判据的捕获方式**写错了，改成不贪婪后通过，案情本身的文本没有错。两者的区别是：前者改的是「什么算对」，后者改的是「怎么读」。

### 4.1 现有机制（`check-prompts.mjs` 实测结构）

```
check-prompts.mjs:39      SELFTEST = argv.includes('--selftest')
check-prompts.mjs:45-46   promptsSrc = readFileSync(PROMPTS_OVERRIDE || 真实 prompts.js)
check-prompts.mjs:47-126  MUTATIONS = { name: { from: 正则, to: 替换, expect: rule, level? } }
check-prompts.mjs:127-129 sandbox 加载 promptsSrc → STYLE_PROMPTS
check-prompts.mjs:135-153 loadBuildPrompt()：读 data.js + prompt-copy.js，stub DOM，返回 buildStylePrompt
check-prompts.mjs:155     const buildStylePrompt = loadBuildPrompt()
check-prompts.mjs:445-831 主循环（顶层代码，for (const d of DIRS) {…}）
check-prompts.mjs:906-944 输出（JSON / 静默 / 人读）
check-prompts.mjs:960-991 SELFTEST 块：对每个 MUTATIONS，把变异后的 promptsSrc 写到 mkdtemp 的临时文件，
                          用 PROMPTS_OVERRIDE 指过去，spawn 子进程带 --json，检查 findings 里有没有 rule === expect
```

**关键点**：selftest 用**子进程**而不是主进程重跑，因为主循环是顶层代码（`check-prompts.mjs:952` 的注释明说「要重跑就得把它包成函数，那是 300 行的大改」）。子进程零改动复用同一份逻辑，这是必须保留的设计。

### 4.2 新断言怎样接进去

**(a) 新断言写在哪里**

放在主循环里，与现有断言同层（`check-prompts.mjs:830` 的 `stats.pass++` 之前）。`text` 变量已在 `check-prompts.mjs:451-452` 算好，`STYLE_PROMPTS` 在 129 行可得，`id` 在 446 行。W 层需要 `dna` 与 `minItems/minPics/plain`：

```
const sp = STYLE_PROMPTS.schemes.find(x => x.id === id);   // 已有类似写法在 :757
const dna = sp.dna;
```

`window.SCHEMES`（tone / plain 的中文名来源）在主进程里**没有加载**——`loadBuildPrompt()` 只在子沙箱 `w` 里挂了 `w.SCHEMES`，那个对象在 `check-prompts.mjs:151` 之后就丢了。W-10 需要它，所以 `loadBuildPrompt()` 要改成返回 `{ buildStylePrompt, window: w }`，或者在主模块里单独加载一次 `data.js`。

**(b) `--selftest` 需要新增 `COPY_OVERRIDE`**

现有 `MUTATIONS` 只变异 `prompts.js`。变异 `prompt-copy.js` 需要对称的一个开关：

```
// check-prompts.mjs:45 附近
let copySrc = readFileSync(
  process.env.COPY_OVERRIDE || join(ROOT, 'prototypes/_selection/prompt-copy.js'), 'utf8');
```

然后 `loadBuildPrompt()` 用这个变量而不是内部重新 `readFileSync`（现在 `check-prompts.mjs:137` 是硬读）。

**(c) `MUTATIONS` 增加一个 `file` 字段**

现有条目靠 `from`/`to` 正则，对 `prompts.js` 够用。`prompt-copy.js` 里的变异大量涉及多行模板字面量，正则可读性差，建议加 `file: 'copy' | 'prompts'`，selftest 循环里按 `file` 选源：

```
'MUT-字号条降级': {
  file: 'copy',
  from: 'Math.round(body) + "px；最大标题要压到正文的 " +',
  to:   '"16px；最大标题要压到正文的 " +',
  expect: 'text-h1-size-triple',   // 新 rule 名
},
```

**(d) selftest 循环改动很小**（`check-prompts.mjs:967-988`）：

```
for (const [name, m] of Object.entries(MUTATIONS)) {
  const src = m.file === 'copy' ? copySrc : promptsSrc;
  const mutated = src.replace(m.from, m.to);
  if (mutated === src) { …既有的「变异没生效」分支… }
  const f = join(tmp, `${name}.js`);
  wf(f, mutated);
  const env = { ...process.env };
  if (m.file === 'copy') env.COPY_OVERRIDE = f; else env.PROMPTS_OVERRIDE = f;
  out = execFileSync(…, { env, … });
  …
}
```

**注意一个坑**：现有 `prompts.js` 的 `to` 支持 `'$1'` 反向引用（`check-prompts.mjs:52`），`String.replace` 照做即可；但 `prompt-copy.js` 的替换串里常含 `$`（正则里的行尾锚点、模板里的 `$`），必须对 `to` 里的 `$` 转义，否则 `$&` 之类会被当成反向引用。本轮探针里 `fx()` 用的就是纯字符串 `replace`，踩过一次（`to` 里出现 `$1` 字面量时被吞）。

**(e) 新增 `EXPECT` 的粒度**

现有 selftest 的判定是「findings 里**存在**某条 rule === expect」（`check-prompts.mjs:984`）。这对本轮够用，但有个盲点：它不检查「有没有别的 rule 也响了」。如果要区分「干净变异」与「兼响变异」，可以把判定升级成：

```
const fired = new Set(j.findings.filter(x => x.level === 'FAIL').map(x => x.rule));
hit = fired.has(m.expect);
extra = [...fired].filter(r => r !== m.expect && !(m.allow||[]).includes(r));
```

`allow` 字段用来登记已知的兼响（如 §3.2 表里标「兼响」的那些）。不升级也能用——只是「假响 1」那种情况不会被自动发现。

### 5.4 一条总的判断

这 39 条断言守的是「**骨架**」，不是「**内容对不对**」。
