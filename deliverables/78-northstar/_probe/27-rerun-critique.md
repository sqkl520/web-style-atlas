## §0 结论先行

**不该跑（以现在的形态）。**

一句话理由：**「删掉数值会怎样」的两个可能答案都不改变任何产品决策**，而依据已被
`check-prompts.mjs` 的 D3 闸门吃掉；同时这次实验有 **4 个混淆**（其中 3 个是管道 bug，
1 个是模型路由），实测证据显示它还缺一个干净的对照组。

补充一句我原以为会成立、但核实后**不成立**的反驳：S98 的 thinking 里已有一份自己造了
`48/12/24/6` 刻度的草稿（§1.2），它**不能**替代重跑 —— 它是被截断的思考体，不是交付物。
所以我的结论不是「答案已经有了」，而是「这个答案不值这个价」。

**唯一会让我改判的条件**：产品决定要新增一条「不带数值的精简提示词」出货路径。
实测：`buildPrompt()` 里**没有任何一条代码路径**会产出无数值提示词（§1.5），
所以这个条件目前不存在。

## §1 六个问题逐条回答

### 1. 这个问题的答案会改变产品吗？—— **不会。两个方向都不改。**

**先确认产品确实永远给数值。** 我用产品自己的函数跑了生成：

```
$ node …（prompts.js + data.js + prompt-copy.js 三者喂进 buildStylePrompt）
S31 lines 40 bytes 5025 px-count 13
S97 lines 1 bytes 0 px-count 0      ← data.js 里没有 S97，与本次结论无关
S35 lines 40 bytes 4946 px-count 8
S01 lines 40 bytes 5059 px-count 5

$ diff <产品输出> deliverables/78-northstar/blind/S31/task.txt
（无输出，exit 0）                    ← 盲测任务书就是产品输出，逐字节相同
```

35 案的「机制句是否含可测值」实测 **35/35 有**（`mech without unit: []`）。
所以「无数值」在产品里是不存在的状态。

**然后看两个答案各自会触发什么改动：**

| 若答案 = | 产品要改什么 | 实测状态 |
|---|---|---|
| 做不出来（文字不承重） | 保证提示词永远带数值 | **已经做了**：`check-prompts.mjs:394-421` 的 D3 断言「机制句至少一个带单位的值或 a:b 比例」 |
| 做得出来（文字承重） | 可以放松 D3；可以考虑出「精简提示词」 | 放松 D3 省不下任何东西（现状 35/35 通过，D3 零成本）；「精简提示词」不在任何计划里（`grep 简短版\|精简` 在 `prototypes/_selection/*` 命中 0） |

**结论：两个答案都是决策惰性的。** 唯一可能改变的东西是一个假设场景 ——
「将来新增一个机制句本身就不可测的案（比如某种纯排版气质），D3 会误拦」。
但那个场景用一句政策（「新案的机制句必须含可测值」）就能处理，不需要 4 小时盲测。

### 2. 有没有更便宜的方式回答同一个问题？—— **没有能替代的既有产物；但有一条零成本的旁证。**

**能间接推断吗？不能，因为对照组缺了两格。**

现有四个实验正好是 2×2 的四格，每格 **n=1**：

| | 有机制 | 无机制 |
|---|---|---|
| **有数值** | S31（399 行，六值精确） | —— 空 |
| **无数值** | S98（零产物，作废） | S97（466 行，自选 10 色） |

S97 vs S31 只能告诉你「两端都成立」，推不出中间那一格。
`deliverables/74-q7/prompt-*.txt` 那 9 份提示词，实测每份 **6–15 个 px**，
产物 8 份全闭合 —— 又是「有数值」那一侧，没有中间格。

**但有一条零成本的旁证，且它比我预期的强：**

S98 的 stream 里那段 165,299 字符的 thinking 含一份 HTML 草稿。我复算了：

```
region chars 120144（第一个 <!DOCTYPE 到最后一个 </html>）
hexes #F2F0EC #5F5B55 #DEDAD3 #55514B #8A857C     ← 提示词给的 5 色 5/5 全中
--maj:48px;  --min:12px;  --majlen:24px;  --minlen:6px;
<pattern id="majTicks" width="48" height="24">    ← 主次两级 + 两条基线都在
ellipsis in region: 98     longest uninterrupted chunk 7919
</head> 出现 3 次、</style> 3 次、</body> 2 次        ← 三段互相覆盖的草稿，不是一份页面
```

**它说的方向是「结构传到了，精确值没传到」**：S31 真值 `60/12`（1:5）、`34/12`；
草稿自选 `48/12`（1:4）、`24/6`（1:4）。

**但它不能当结论用**，三条硬理由（`10-RERUN-PLAN.md:§三` 也这么写）：
① 它是 thinking 不是交付物；② 98 处 `...` 省略，最长连续块只有 7,919 字符；
③ 它出现在一次**没跑完**的运行里。更硬的一条是 `<body>` 里的分节全被省略成
`<section class="sect services">...</section>`，也就是说**它连一份可渲染的页面都不是**。

所以更便宜的方式只有「读它当假设」，不能「读它当答案」。

**不能只跑更小的案子吗？** 可以，但那是另一个实验。S98 的自变量是「S31 的数值被删」，
换案就换了自变量；而按 §3 的成本表，省下来的不是主要项（S35 实测 1693s / $1.33，
S98 实测 4.27h / $0.62 —— 便宜的案子做完也不回答 S98 的问题）。

（`trusted`）+ 1 次可溯源的 S31 对照（因为现有 S31 产物是 `UNVERIFIED-PROVENANCE`：
`stream` 41,422 行、**0 次 Write / 0 次 Edit**，我复核过）。也就是 **3–4 次单跑**：


**串行是硬约束**，不是保守：`_blindbox-batch.ps1:4-9` 写明 Deny ACE 按**账户**生效，

**还有一条把时间窗口压死的实测**（`_probe/25-gateway-diagnosis.md:§3.2`）：
524 率按本地小时是 **16h–22h 的 37%–71%，00h–07h 的 0%**。所以「跑得成」的时间带
只有 00:00–07:00 这 7 小时。一次 S98 有效 API 时间实测 **123 分钟**，加上重试预算

**这个成本换来的信息**：把「S98 那段草稿显示的倾向」升级成一条有 2 个样本的实测。
而它要支撑的决策（保证给数值 + D3 闸门）**已经落地了**。

**判断：换来的信息不值这个价。**

### 4. 有没有更该做的事 —— **有，而且不止一件，全部零成本或几分钟。**

**第一件（威胁最大）：内容层完全不稳，这才是店主真正会碰到的问题。**

`_probe/20-reproducibility.md:§0.2` 实测（13 份产物、5 个有重复样本的案）：

```
S04  野电流·菜市场二楼    → 贴满印社·第04面墙      8-gram 0.042
S13  棉纸公函            → 蝉翼石室·拓本档案馆     8-gram 0.004
S29  液压缸大修规程册     → 漏点对章节            8-gram 0.000
```

**同一个提示词能把「菜市场展览」变成「印社」。** 对产品语义：
店主点复制 → 贴给 AI → 得到「结构相同、文案完全无关」的页面。
这不是「复刻保真度」问题，是**「按我的店做我的站」这句承诺**问题 —— 而那句承诺
是 `web-style-product-direction.md` 里写死的产品定义。

对照：数值层 13 份产物**零翻转**（字号比最大差 0.9%，配色/线宽从不错）。
也就是说**钱已经花了的地方是稳的，没花钱的地方是最不稳的**。
S98 测的是「稳定的那一层坏掉会怎样」，而现实里坏掉的是另一层。

**第二件（我这次新查出来的）：有一个正在漏的闸门洞，比 S98 的答案有用得多。**

真实的风险形态不是「把 40 行里的数值全删」（产品不会走到那），而是
**某个字段的抽取静默失败**。我按这个形态做了变异，并且**同步改 `dna-clean.json`**
（模拟「抽取器坏了，生成器照坏数据生成」这条真实路径）：

```
变异：S31 的 lineWidths → 生成器的空数组兜底文案「无边框线条（全站不画描边…）」
      S31 的 h1SizeAt1440 → ""（首屏主标题抽取失败）
```

**为什么漏**：`linewidth-not-in-css` 的判据是「提示词里出现的数字必须在 CSS 里查到」，
而这行**一个数字都没有**，`claimed=[]`、`notInCss=[]`，天然通过；
`no-typescale` 只是 WARN。`stale-vs-dna-clean` 也比对不出来 —— 因为
`dna-clean.json` 和 `prompts.js` **一起坏**，两边一致。

（对照：如果只改 `prompts.js` 不改 `dna-clean.json`，`stale-vs-dna-clean` 会报 FAIL。
但真实故障恰恰是「抽取器坏了、生成器照着生成」，两边一起坏。）

`_probe/28-s98-relevance-check.md:§三` 已经点名「补一条闸门：检查 dna 的每个关键字段非空
（现在没有这条）」—— **这条是对的，而且它几分钟就能写完，覆盖的正是产品真会遇到的形态。**
它比 S98 重跑更接近「防止店主拿到一份用不动的提示词」这个目标。

### 5. S98 的设计本身有没有问题 —— **有，四个混淆 + 一个自造的矛盾句。**

**去代码里查：`buildPrompt()` 会不会产出「没有数值」的提示词？**

不会。`buildPrompt` 的每个分支都是数值出口：

| 分支 | 位置 | 输出的数值 |
|---|---|---|
| 常规 | `prompt-copy.js:620` `"1. 配色只用这几个值：" + d.palette` | 5–9 个 hex |
| 常规 | `prompt-copy.js:642` `"5. 线宽只用这几级：" + d.lineWidths` | 2–7 档 px |
| 常规 | `prompt-copy.js:665-677` 字号行 | 正文 px + 倍率 + h1 px |
| **机制句为空时的兜底** | `prompt-copy.js:428-441` | `"线宽只分 " + d.lineWidths`、`"首屏主标题取 " + d.h1Size` |
| `h1SizeAt1440` 为 0 | `prompt-copy.js:668` `if (!h1) return ""` | **这一行整条消失（唯一一个静默丢值的出口）** |

我实测了「机制句被抽空」这个故障：兜底分支照样输出
`这个风格的签名动作：只给读数不表态，刻度当骨架。具体到实现：全站直角、零圆角；首屏主标题取 clamp(38px, 8.6vw, 104px) 这一档。`
—— **兜底也是带数值的**。

**所以 S98 这种提示词只能靠手改 `prompts.js` 或手写 `task.txt` 造出来。**
`_make-S98-task.mjs` 做的正是前者：它拿 `blind/S31/task.txt` 逐行替换 6 行（`diff` 实测
**40 行里改 6 行**），并自检「全文无 px、无 N 倍」。

**四个混淆（都已实测，不是推测）：**

| # | 混淆 | 证据 |
|---|---|---|
| 1 | **模型没收到指令**（`-p` 只吃掉 `Read` 一个词） | `lastPrompt:"Read"`；首 thinking「The user just said "Read"」 |
| 2 | **流式中断 + 被注入续写** | `S98`、S04、S13 都有 `cut off mid-stream. Resume directly…`；S98 的 `estimated_tokens` 47212→1→43199→1→40108，至少两次思考体被丢弃 |
| 3 | **结束前的 524 风暴** | 58,031–58,038 行 8 连 524；`terminal_reason:"api_error"`；重试预算 9.9 min vs 拥堵 10.2 min，**差 18 秒** |
| 4 | **实际服务的模型不是 opus** | 14 份 stream 的 `assistant.message.model` 全是 `deepseek-ai/deepseek-v4.1-flash`，只有 `init.model` / `modelUsage` 写 `claude-opus-5[1M]` |

**「半个具体」这个说法本身没被验证。** 08 号报告把 S98 概括成「具体到需要精确值、却没给值」。
但实测它删掉的是**全部尺寸量纲**（13 处 px + 1 处「N 倍」→ 0），而**完整保留了** 5 个 hex、
两条字体链、圆角/阴影/线宽档数语义。也就是说它是「量纲通道被清空」，
不是「具体度对半砍」。这两件事在产品里对应完全不同的修复方向，S98 分不开。

**还有一处自造的矛盾句**（这是我认为最硬的证据，说明它不是产品状态）：

```
S98 task.txt:31  二是记忆点必须落在主刻度的间隔、次刻度的间隔、主刻度的线宽这三个可测值上
```

这句在 S31 里是「落在 60px 主刻度 / 12px 次刻度 / 3px 主刻度宽这三个可测值上」。
改写成 S98 时数值被删、**「这三个可测值」这几个字留着**。于是提示词字面上说
「必须落在这三个可测值上」，而全文**一个可测值都没有**。
任何模型读到这里都只能停下来 —— 这不是「数值缺失导致无法收敛」，
这是**指令自指导致的逻辑死锁**，而它是手改的产物。

**还有一个更靠前的对照问题：零产物不是「无数值」的专属现象。**

| 案 | 任务书 px 数 | 写文件次数 | 结局 |
|---|---|---|---|
| S98 | **0** | 0 | api_error/524，零产物 |
| S21 | **7** | 0 | api_error（Connection lost），零产物 |
| S04 | **6** | 0 | api_error，零产物（磁盘有一份来源不明） |
| S31 | 13 | 0（stream 里） | api_error，产物来源待证 |

**S21 带着 7 个可测值、机制句完整，一样零产物。** 这说明「零产物」这个结局变量
在「有数值」那一格里也会出现。n=1 的 2×2、结局变量在两侧都出现，
这个实验连方向性都判不出来。

## §2 我认为该做什么（替代方案）

按「对店主的实际威胁 × 成本」排序，**全部不需要沙箱**：

| 优先 | 做什么 | 成本 | 为什么它比 S98 更值 |
|---|---|---|---|
| **1** | 补一条闸门：`dna` 的关键字段为空/兜底文案时 **FAIL**（`h1SizeAt1440`、`lineWidths` 取到空数组兜底、`palette`、`bodySize`、`mechanism`） | 30 分钟，0 元 | 我实测这条洞现在**能放过**「线宽 + 字号同时丢失」的提示词（FAIL 0 / WARN 2 / EXIT=0）。这正是产品**真会**遇到的失败形态，S98 那种不会 |
| **2** | 修 `-p` 参数拼接，并只验一件事：新跑一次 30 秒空任务，首个 thinking **不再**说「The user just said "Read"」 | 20 分钟 + $0.01 | 不修它，任何重跑（包括 S98）测的都是「模型自己猜任务」；`lastPrompt` 是唯一可靠判据 |
| **3** | 对「内容层不稳」定一个产品口径：8-gram 0.000 是缺陷还是预期？（店主拿到的是「同一个提示词 → 不同文案」） | 1 小时讨论，0 元 | 这决定产品承诺的措辞。S98 的答案不影响它 |
| **4** | 把 06:224 / 08:96 / 08:123 三处已被推翻的 S98 结论改掉 | 15 分钟 | 不改的话，下一个人会照着它们加更严的闸门（`09-VERIFY-PLAN:§5.1` 已预警） |
| **5** | 把 D3 的已知绕过（保留 1 个值就通过，我复现：5 个值只剩 `60px` → FAIL 0）登记为已知边界，而不是当成「D3 已守住」 | 5 分钟 | 这是 D3 唯一真正值得知道的事，且不需要跑模型 |

**关于第 1 条我要说清它不是什么**：它不是「再加一条更严的闸门」（`09-VERIFY-PLAN:§5.1`
警告的那个错误方向）。它守的是一个**独立于 S98 的**事实：`prompt-copy.js:668`

## §3 如果坚持要跑：最小方案

### 3.1 前置（不做这一条，重跑等于第二次白跑）

1. 修 `C:\tmp\runner-template.ps1:18` 与 `deliverables/78-northstar/_probe/_runner-template2.ps1:19`：
   `$argList = "-p `"$msg`" --model opus --permission-mode acceptEdits --output-format stream-json --verbose"`
2. 验收：跑一次 30 秒空任务，读第一个 `assistant.thinking`，**不得**出现
   `The user said "Read"`。**没验过就不要往下走。**

### 3.2 跑几次

**2 次，不是 3–4 次。**

- **S98 × 1**（`blind/S98/task.txt` 冻结，md5 `76e26f192e4f60a81c00c4ba8716934f`）
- **S31 × 1**（同一夜窗口，为了给对比一个可溯源基线）

理由：第三次的边际信息最低。`10-RERUN-PLAN:§5.3` 那张表里「两次都 trusted 且 L1 都成立 → 不跑第三次」
是唯一会被触发的分支（另一个分支「两次都不 trusted → 停」也不会跑）。

**并且先写死停跑规则**（不要临场判断）：第 1 次 `run.json.trusted !== true` → 当晚不跑第 2 次，
先查管道。

### 3.3 选案与参数

**不换案。** 换案就换了自变量（S98 的定义是「S31 删掉量纲」）。
跑 S35 更便宜（实测 1693s / $1.33）但它有 8 个 px，答不了这个问题。

```powershell
powershell -File _blindbox-run.ps1 -TaskDir C:\tmp\bb\S98 -OutFile C:\tmp\bb\S98\out.html `
  -TimeoutSec 5400 -MaxRetries 4 -RetryDelaySec @(120,300,600,900)
```

- `TimeoutSec 5400`：S98 有效 API 时间实测 123 分钟，90 分钟墙偏紧但能在真挂死时止损；
  若要更稳用 7200（代价：一晚只能跑 1 次）。
- `MaxRetries 4` / 退避 `@(120,300,600,900)`：依据 `25-gateway-diagnosis:§3.3`
  实测拥堵最短 10.2 分钟，原来的 30 秒首退避会在拥堵没结束时就把重试烧掉。
- **不加 `-RetryOnTimeout`**：超时说明 claude.exe 可能还在工作（S99 就是超时后仍在写），
  重跑会丢掉真产物。

### 3.4 什么时候跑

**只在本地 00:00–07:00。** 依据 `25-gateway-diagnosis:§3.2` 实测：
00h–07h 的 524 率 **0%**，16h–22h 是 **37%–71%**。S98 原次 16:34 起跑，正中窗口。
（这一条不改实验条件 —— 时段不是自变量。）

### 3.5 怎么判断可信（三层，任一不过就不进统计）

```
L0 运行层：run.json.trusted === true（= terminalReason === "success"）
           ∧ api_retry 里 error_status==524 的条数 == 0
           ∧ 禁用 "subtype":"success" 判成功（S97/S98 都是 subtype=success + is_error=true）
L1 产物层：out.html 存在 ∧ </html>/</body>/</style> 各 ==1 ∧ CSS 花括号净差 ==0
           ∧ 产物 mtime 与 stream 最后一次写 差 ≤ 120s（S35 实测 +0.4s、S97 +16s）
L2 判定层：结构在不在（主次两级刻度 / 两条贯穿基线 / SVG pattern）与
           数值对不对（六值）**分两列报，容差 0**（现用 0.6px 容差会把 48 认成 60 附近，
           见 10-RERUN-PLAN:§T6）
```

### 3.6 事先写下的可证伪预测

按 §1.2 的草稿，**预测 S98 会自选 1:4 比例的刻度**（`48/12`、`24/6`），
而 S31 真值是 **1:5**（`60/12`、`34/12`）。

- 若真出现一组自成体系但非真值的比例 → 结论「文字传结构、数值给精度」（D3 的立场成立）
- 若出现真值 60/12/34/12 → 结论「文字足够」（D3 立场要复核）
- 若又零产物 → **不可判**，写「仍未回答」，不得写「倾向」

```
判定 + 写报告                1 小时，0 元
────────────────────────────────────────
合计                        约 5 ~ 10 小时，$3 ~ $10，跨 1–2 个夜间窗口
```
