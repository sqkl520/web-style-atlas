# S34 的提示词在中间断号：用户拿到的是 1、2、3、5、6

> 2026-11-15　主线程
> 这条来自验证 40 号报告时的意外发现。40 号报告把「S34 结构段编号是 1,2,3,5,6」
> 当作**合法形态**写进了判据（它的 T-16 要求「n===4 且 minPics===0 时跳过该号」）。
> 我认为那个判断错了。**这是缺陷，不是合法形态。**

---

## 一、事实

`buildStylePrompt('S34')` 输出的「结构约束」段原文：

```
1. 这个版式设计时排了 7 个条目——这是版式的规模，不是你的内容量。
2. 用你自己的真实数量排：有几个排几个，不凑整、不留占位符。
3. 这个版式是自动流排版，删条目只会让页面变短、不会留空位，你按自己的数量排就好。
5. 首屏只用本案方式摆出的静态内容，一屏内所有内容同时可见。
6. 这个版式的硬前提（作者原话，请据此判断你的内容配不配得上它）：「…」
```

**没有第 4 条。** 编号从 3 直接跳到 5。

全库扫描（35 案）：

```
$ node -e "…逐案取结构段编号，检查是否有非连续…"
结构段有跳号的案: 1 S34 跳号 3→5
```

**只有这一案，但确实存在。**

---

## 二、为什么这是缺陷

### 2.1 用户看到的是给 AI 的施工图

产品交付物是用户复制走的这段提示词。里面的编号不是给人看的装饰，是**给模型的结构索引**。
而这段提示词内部还有交叉引用：

```
⑤ 图形一律用本案线宽级别的线条画（见第 5 条）
```

也就是说，**编号是可被引用的地址**。一个中间断号的列表，会让读者（模型）无法判断：

- 第 4 条是被截断了？
- 还是本来就不适用？
- 如果是「不适用」，为什么不说一句「本案无图片位」？

模型对不完整的编号列表有多种合理反应，其中任何一种都不是作者想要的。

### 2.2 根因是 `.filter` 吃掉了空串，而编号是写死在字符串里的

`prototypes/_selection/prompt-copy.js:826-831`：

```js
s.minPics
  ? "4. 版式里至少要 " + s.minPics + " 个**不同的**图片位置（…）"
  : "",
```

`S34` 的 `minPics` 是 `0`（全库唯一，实测：`minitems-parsed.json` 里 `minPics===0` 的案 1 个 = S34）。
`0` 是 falsy，于是这一项变成空串。然后 `prompt-copy.js:991`：

```js
]).filter(function (x) { return x !== ""; });
```

空串被滤掉。**但编号 `"4. "` 是写在那条字符串里的字面量**，一旦整条消失，编号也跟着消失，
而后面 `"5. "`、`"6. "` 的编号仍然固定，于是留下一个洞。

### 2.3 代码注释讨论过跳号，但讨论的不是这一种

`prompt-copy.js:838-843`：

```
 * 这一段里 9/30 案（dna.reuse 为空）**本来就没有**最后一条，
 * 所以"编号到 5 为止"和"编号跳到 6"都是合法的数据状态，不是漏了一条。
 * 2026-10-27 实测分布：5 条×9 案 + 6 条×21 案 = 30，与 dna.reuse 的 21/30 有值一一对应。
```

这段说的是**末尾**的两种情况：有第 6 条（reuse 非空）或没有（reuse 为空）。
两种都不产生**中间的洞**：

- reuse 非空 → 1,2,3,4,5,6（连续）
- reuse 为空 → 1,2,3,4,5（连续，只是短一条）

而 S34 是 1,2,3,**5**,6 —— 这是注释没有覆盖的第三种情况。作者当时没想到 `minPics=0` 会挖洞。

## 三、影响面与严重度

**影响 1/35 案。** 按比例很小，但：

1. 它发生在**产品交付物**上（用户复制走的文本），不是内部数据。
2. 它发生在**唯一一个零图片设计的案**（S34 是刻意的零图设计，不是缺陷案）——
   也就是说这个案的用户体验本来就特殊，再叠加一个断号。
3. 它属于本仓库明确归类的缺陷形态：**界面在说谎**——列表看起来有 6 条，实际只有 5 条，
   而它不说第 4 条为什么不适用。

**修法有两种，代价都很低：**

**A. 让第 4 条在 `minPics=0` 时仍然出现，但内容改成正面声明**

```js
s.minPics
  ? "4. 版式里至少要 " + s.minPics + " 个…"
  : "4. 本案是零图片设计：整页不出现任何图片位，全用文字与色块承载。",
```

这符合本仓库的既定原则（把否定句改写成正向处方），也让 AI 知道「没图片」是设计而非遗漏。

**B. 编号在生成后重排**，即先组装数组，再按实际条数加编号。改动更大（要把写死的
`"1. "` `"2. "` 前缀全部拆出来），但能一劳永逸。

**我倾向 A**：一处改动，不改结构，而且它顺便补上了一条现在缺失的信息（「本案不用图片」）。

## 四、这条发现对 40 号报告的影响

40 号报告写了 38 条断言，全部在当前 35 案上 35/35 通过。我独立复核了它最关键的六条，**全部成立**：

```
T-11 三件套: 35/35
降级句是否被 T-11 误判为通过: false
T-01 空输入形态: 35/35     已填形态: 0/35
minPics=0 的案: 1 S34
REQUIRED_MARKERS 条数: 4
S34 结构段编号: [1,2,3,5,6,1,2,3]
```

但它的 **T-16 把 S34 的断号写成了期望形态**：

> 结构段：从 1 到 max(编号) 逐个补，但 n===4 且 minPics===0 时跳过该号

**如果照这条实现，闸门就会把缺陷固化成正确。** 这是本仓库第五类缺陷的教科书形态：
闸门与被测对象共用同一个盲点——两者都认为「S34 跳号是对的」。

正确写法应该是反过来：**断言要求编号连续**，然后先修 `prompt-copy.js` 让 S34 不再跳号。
否则新闸门上线第一天就带着一个「已知错误被写进判据」的洞。

```bash
# 1. S34 的结构段真的有洞
node -e "…buildStylePrompt('S34') 取结构段…"
# 输出：1. … 2. … 3. … 5. … 6. …

# 2. 全库只有 S34 一案跳号
# 输出：结构段有跳号的案: 1 S34 跳号 3→5

# 3. minPics=0 只有 S34
node -e "const m=require('./prototypes/_prompts/minitems-parsed.json');…"
# 输出：minPics 为 0 的案: 1 S34

# 4. 根因位置
sed -n '826,831p' prototypes/_selection/prompt-copy.js   # s.minPics ? "4. …" : ""
sed -n '991p'    prototypes/_selection/prompt-copy.js   # .filter(x => x !== "")
sed -n '838,843p' prototypes/_selection/prompt-copy.js  # 只讨论了末尾缺条，没讨论中间挖洞
```
