# 哨兵测试：dna 的 12 个字段里有 2 个不影响产品输出

> 2026-11-15　主线程
> 本文的方法来自 38 号红队报告（它在没读过我报告的情况下独立提出「哨兵扰动」），
> 我把它扩展到全部字段、两种调用形态，并独立复算了每一个数字。

---

## 一、方法：为什么哨兵比「非空」强

**原来的判据**：`dna.字段 === ""` → FAIL。

它有一个根本弱点：**它测的是数据，不是产品。** 字段有值但没接进提示词，它照样 PASS。

**哨兵法**：把一个字段改成**绝对不可能自然出现的值**（如 `h1Size = "999px"`、
`palette = "#FF00FF（哨兵）"`），重新生成提示词，**比对文本是否变化**。

- 变了 → 这个字段确实流到了用户手里
- 没变 → 这个字段对产品零影响

这直接对治本仓库归纳的两类缺陷：① 闸门读不到数据也不报错、④ 量错了对象（元层级）。

### 1.1 两种调用形态都要测

`prompt-copy.js` 的 `buildStylePrompt` 有 4 种入口形态（40 号报告 §2.3 实测）：

| 形态 | 首行 |
|---|---|
| `buildStylePrompt(id)` | `下面这份是这个风格的施工图。开头两行要你自己填…` |
| `buildStylePrompt(id, {biz, action})` ← **用户真用时的形态** | `我经营一家咖啡店。` |
| `buildStylePrompt(id, {tool:'v0'})` | `【这条提示词是给 v0 用的…】` |

现有的 `check-prompts.mjs` **只测第一种**。所以哨兵测试必须两种都跑，否则「参与了渲染」
这个结论可能只对闸门调的形态成立。

### 2.1 死字段一：`h1Size` —— 0/35 渲染

**历史上修过一次，但只修了数据。**

`prompt-copy.js:643-649` 的注释记着：

> `h1Size` 在 dna-clean.json 里抽到 30/30，但**渲染进提示词的案 = 0/30**。
> 原因：原来这句写在 mech 的 `else` 分支里……这是**接线 bug，不是数据缺口**。

当时的修法是「改用 `h1SizeAt1440`」（`prompt-copy.js:666`），于是 `h1SizeAt1440` 接上了。
**但 `h1Size` 本身从来没有被接上，也没有被删掉。** 哨兵实测它至今 0/35。

它现在的作用只剩下一个：作为 `h1SizeAt1440` 的中间量。而它被放进了 `prompts.js` 的 `dna`
（产品数据），并且被 `check-prompts.mjs:880` 的 `KEY_FIELDS = ['h1Size', ...]` 列为关键字段。

**后果**：下一个读代码的人会以为它在起作用。如果有人为了「修提示词」去调 `h1Size`，
他会发现改了没有任何效果——而闸门是绿的。这正是 `42-why-fields-dropped.md` 说的
「有值但没人读」那一类的变体：**有值、有名分、但无效**。

### 2.2 死字段二：`radius` 对 31/35 案完全无效

`radiusBare=true` 的案有 31 个（35 案里）。这些案里改 `radius` 文本，提示词**逐字不变**：

```
radiusBare=true 的案: 31/35
  其中改 radius 文本后提示词不变的: 31/31  → radius 对它们完全死
```

原因在 `prompt-copy.js:630-633`：

```js
"3. 圆角：" + (d.radiusBare || d.radius === "全直角 0"
  ? "全站一律 0，卡片、按钮、图片、标签全部方角"
  : d.radius) + "。",
```

`radiusBare` 为真时直接用固定句，`d.radius` 整句丢弃。

**这个设计本身是对的**（31 案确实是全直角，写固定句更清楚）。问题在于：
`radius` 字段对 31 案而言是「有值、被生成、被 ANALYZE、但对产品零影响」。
而 `check-prompts.mjs` 里既有 `KEY_FIELDS` 陈旧度检查、又有 `stale-vs-dna-clean`，
都在认真守着这个对 88.6% 的案没有作用的字段。

**一句话概括**：闸门花在 `radius` 上的注意力，88.6% 花在了一个不影响输出的东西上。

## 三、这两个死字段该怎么处理

不是「加一条断言」，是**把名分和事实对齐**。两条路，选一条：

**A. 删掉产品数据里的死字段**
- `h1Size`：从 `build-prompts.mjs:376` 的 `dna` 里删掉（`h1SizeAt1440` 已够用），
  同时从 `check-prompts.mjs:880` 的 `KEY_FIELDS` 删掉。
- `radius`：不能删（4 案真的在用）。改成**注明它只对 `radiusBare=false` 的案有效**，
  并在闸门里把对 `radius` 的检查限定在这 4 案。

**B. 补一个「它不是死字段」的证明**
用哨兵法做成常态化断言：定期把字段改成哨兵值，比对输出。这条断言的价值在于
**它测产品**，而现有所有断言测的都是数据。

**我倾向 A + B 的组合**：`h1Size` 走 A（它是纯中间量，没有留在产品数据里的理由）；
两个字段都纳入 B（哨兵测试应该成为常规闸门的一部分，因为它能拦住「接线断了」这一类，
而这类恰恰是本仓库发生过两次的事故——S98 的元指令、h1Size 的 else 分支）。

## 四、这条发现改变了什么

### 4.1 它彻底否掉了「非空断言」

`h1Size` 当前 **35/35 非空**。一条「dna 关键字段非空」的断言，对它是**满分通过**——
而这个字段对产品零影响。这就是「断言恒真」的教科书：断言和被测对象一起绿，
而真正的问题（接线断了）两者都看不见。

### 4.2 它给 40 号报告的 38 条断言提供了独立理由

40 号报告主张把断言做在**输出文本**上。哨兵测试从另一个方向证明了同一件事：

> 数据层的完整性检查（非空、陈旧、类型）**无法发现**接线断裂。
> 只有比对「改动前/后的输出文本」才能发现。

两者是同一个结论的两种到达方式。

### 4.3 它暴露了 `KEY_FIELDS` 的一个隐含假设

`check-prompts.mjs:880`：

```js
const KEY_FIELDS = ['h1Size', 'lineWidths', 'radius', 'shadow'];
```

选这四个字段的理由大概是「它们是提示词的核心视觉约束」。但实测：

| 字段 | 是不是真核心 |
|---|---|
| `lineWidths` | ✓ 35/35 参与渲染 |
| `shadow` | ✓ 35/35 |
| `radius` | ⚠ 只对 4/35 有效 |
| `h1Size` | ❌ 0/35 |

**四个里有一个完全无效、一个 88.6% 无效。** 这个名单当初是凭「觉得重要」选的，
不是凭实测选的。

## 五、复算方法

```js
// 哨兵测试的核心：改一个不可能的值，比对文本是否变化
const base = new Map(ids.map(id => [id, buildStylePrompt(id)]));
for (const s of schemes) s.dna.h1Size = '999px';
const changed = ids.filter(id => buildStylePrompt(id) !== base.get(id));
// changed.length === 0  → 死字段
```

完整脚本在运行后已删除（`_tmp-sentinel*.mjs`）。要重跑，按上面 6 行复刻即可 ——
关键是**同时比对 `buildStylePrompt(id)` 与 `buildStylePrompt(id, {biz, action})` 两种形态**，
因为闸门只调前者，而用户拿到的多半是后者。
