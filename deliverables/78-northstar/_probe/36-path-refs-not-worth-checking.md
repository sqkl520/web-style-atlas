# 报告里的路径引用：查过了，不适合做自动核验

> 2026-11-14　主线程
> 结论先行：**不做。** 误报率太高，做出来会被关掉。

## 一、起因

`_report-numbers-audit.mjs` 已经能核「数字」与「commit hash」。
顺着这个思路想到第三类可核引用：**报告里的文件路径**。
直觉上「报告说 `_probe/foo.mjs` 存在，但它不存在」应该是个缺陷。

## 二、实测：398 个路径引用，95 个"找不到"

```
引用文件: 398   找不到: 95
```

第一版看起来是个大问题。逐个查过之后，**没有一个是真缺陷**，它们是：

### 2.1 沙箱内文件（不在仓库里，本来就不该在）

```
_run.ps1          ← 16-negative-control.md 等 6 份
run.json          ← 07-NEGATIVE-B.md 等 4 份
.claude.json      ← 04-ROUND-REPORT.md 等 3 份
settings.json     ← 5 份
batch-result.json ← 3 份
```

这些都在 `C:\tmp\bb\<案号>\` 下，是沙箱运行产物。
报告引用它们完全正确 —— 只是它们不在 git 里（`C:\tmp` 会被系统清理，
所以关键副本才要放进 `_probe/_staged/`）。

### 2.2 一次性脚本（用完就删，引用是历史记录）

```
_tmp78/structure-only.mjs    ← 02-report-coverage.md
rt/t1.mjs / t2.mjs / t3.mjs  ← 18-gate-redteam.md
vd/scan.mjs / anc.mjs        ← 18-gate-redteam.md
/tmp/dq.mjs                  ← 21-datachain-audit.md
```

这些是红队/审计当时临时写的探针，用完没入库。
报告写「用 `rt/t1.mjs` 验的」是在交代手法，不是承诺文件还在。

### 2.3 计划文档里的未来文件（WBS / PLAN 类）

```
out/index.html          ← 00-WBS.md
01-baseline.json        ← 00-WBS.md
_probe/northstar.mjs    ← 00-WBS.md
```

`00-WBS.md` 是工作计划，里面写的是**要产出**的文件。
把它们判成"缺失"等于把计划书当成完成报告。

## 三、能做的部分也做了，收益太小

把范围收窄到「非计划类报告 + 只查 .mjs/.ps1/.json」：

```
结论类报告引用脚本: 211   找不到: 33
```

33 个里 0 个是真缺陷 —— 全是上面三类。

## 四、为什么不做

1. **误报会是常态而非例外。** 沙箱产物、临时探针、计划文件，三类都合法地
   "不存在于仓库"，而它们占了全部引用的多数。
2. **一个天天误报的检查会被关掉。** 这一条我在 `_fact-index.mjs` 的注释里
   已经栽过一次（那次的「不符检测」报了 20+ 条全假）。

## 五、如果将来一定要做

判据必须是**语义**的，不是路径的：

- 只查「引用的脚本在**执行命令块**里」（` ```bash ` 围栏内的 `node xxx.mjs`）
  —— 那种引用是"照这个命令能跑"，缺了才是真问题
- 跳过所有 `C:\tmp`、`/tmp`、`_tmp` 开头的路径
- 跳过 WBS / PLAN / ROUND-SUMMARY / INTERIM 类报告

**但即使这样，收益也只是「抓到一个打错的脚本名」。**
相比之下，`_report-numbers-audit.mjs` 的 35 项数字核验已经覆盖了
更有价值的那一层。

## 六、记这一份的目的

免得下一个人看到「报告引用了 398 个文件」又去写一遍这个检查，
然后发现 95 个"缺失"里没有一个是错的。

**查过了，结论是不值得做** —— 这本身是结论。
