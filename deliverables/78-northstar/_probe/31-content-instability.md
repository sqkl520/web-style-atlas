## §0 结论先行

**不是问题。内容不稳是设计如此。**

但本轮挖出一件比分母题更值得报的事，以及**我自己的一个度量错误**（§2.4，必须写在最前面因为它影响你信谁）。

### 0.1 内容不稳是真的，成因是提示词里那两个空槽，不是随机性

我生成了 S04 / S13 / S29 的**真实提示词**（店主什么都不填时拿到的那份），逐字读完：

```
第 1 行：下面这份是这个风格的施工图。开头两行要你自己填（我不知道你做什么生意）：
第 2 行：我经营＿＿＿＿。
第 3 行：页面需要让访客＿＿＿＿。
```

`prompt-copy.js:126`（都没填的分支）把这两行留成**全角下划线空槽**。
这是 2026-10-27 明确修过的行为 —— 改之前是「我经营一家小店，有一些内容和图片要放上去」，
30/30 份提示词首行完全相同，系统替用户编了一门他没做过的生意（`prompt-copy.js:50-68`）。

**「菜市场展览」和「印社」不是同一个指令的两次随机执行，是同一个空白槽的两次独立填充。**
这是**设计如此**，不是缺陷。

而且 **35 案里没有任何一份要求标题或站名必须包含某个词**：

```
$ 「标题必须包含 / 标题必须写 / 必须叫 / 站名必须 / 店名必须」→ 35 案命中 0
```

### 0.2 结构是稳的 —— 我第一版说「不稳」，错了，错在哪写在 §2.4

我用了三个指标（页高、内容区左缘、主栏宽度），得出「S13 版式骨架差 186px、S29 差 37.8%」。
**这三个指标是错的**，判据是**对照组**（S08 两份产物店名一字不差、8-gram 0.912）：

```
S08-a  主栏 980→1280 (300px)
S08-b  主栏  380→ 830 (450px)      ← 内容完全相同，指标却差 50%
```

**一个在「内容一字不差」的样本上都差 50% 的指标，不能用来证明「内容变了所以结构坏了」。**
错因：我的「内容区左缘」取的是「最靠左的正文段落」——而 `<div class="wrap">` 这类包裹层的
padding 会随内部内容宽度变化，量的不是版式，是包裹方式（§2.4 有完整复盘）。

**换成对照组能站住的指标后，三案里两案的版式是稳的**（§2.2）：

| 指标 | 对照 S08 | 对照 S15 | S04 | S13 | S29 |
|---|---|---|---|---|---|
| 文字密度（字/1000px 页高） | 452→459 (**+1.5%**) | 413→415 (**+0.7%**) | 391→362（-7.4%） | 351→345（**-1.8%**） | 350→493（**+40.9%**） |
| 水平分区数 | 25→26（**+1**） | 26→25（**-1**） | 15→13（-2） | 14→13（**-1**） | 36→19（**-17**） |

**判读：**
- **S04 / S13 落在对照组的自然波动内**（密度 -7.4% / -1.8%，对照是 +0.7~+1.5%）。
- **S29 是唯一的真差异**（密度 +40.9%、分区 -47%）。但见 §0.3 —— 提示词**明确允许**它这么做。

### 0.3 S29 那个真差异，提示词允许了

S29 的提示词第 3 条（`prompt-copy.js:786`，`degrades=yes` 分支）原文：

> 3. 但这个版式的位置是按 23 个数出来的（写死坐标或编号，不是自动流），少一个就空一格：
>    确实不足 23 个时，**把空出来的位置整块重排**、每格都落到真实内容上。

`23` 是 35 案里最大的 `minItems`。S29-b 做的正是「整块重排」——它把 23 个编号位从

**两版都真的落了 23 个编号位**（实测）：

S29-b  唯一 № 编号 01…23 共 23 个 + 正文声明「23 格 · 现货 18 · 订货 2 · 停产 1 · 空置 2」

  72px 左缘带 ✓✓   3px 穿孔 ✓✓   18px 间距 ✓✓   1.2px 环线 ✓✓
  48px 栏外章节号 ✓✓   96px 右出血 ✓✓   下沉 18px ✓✓   两列 rail|content ✓✓

## §1 提示词对文案的约束强度（逐条）

`buildPrompt()`（`prototypes/_selection/prompt-copy.js:275`）。判据是「读这段文字的人能否据此写出一句确定的文案」。

### 1.1 「必须这样写」：**0 条内容指令**

唯一一条强指令是**调性**，不是内容：

| 出处 | 原文 | 力度 |
|---|---|---|
| `:597` | 「照这个调性写文案和标题，每一句都像这个案子的人自己说的。」 | 规定**怎么说**，不规定**说什么**。S04=tone「混乱活力/街头」、S13=「学术档案/严肃出版」、S29=「机能冷峻/工业」（7 个 tone 值，30/30 齐全） |

### 1.2 「你自己决定」：2 条

| 出处 | 原文 | 说明 |
|---|---|---|
| `:779` / `:782` | 「用你自己的真实数量排：有几个排几个，不凑整、不留占位符。」 | **明确把内容量交给模型**。这句是 2026-10-27 第五次修的结果，改之前是「我实际有 46 个条目」—— 系统替用户宣称有 46 个产品 |
| `:595` | 「请把整页做成这个风格：`{plain}`。」 | `plain` 是**版式描述**，不是行业 |

### 1.3 「你自己填」：2 行，在提示词最前面

| 出处 | 原文 |
|---|---|
| `:122` | `我经营` + `{biz}`，空则 `我经营＿＿＿＿。` |
| `:123` | `页面需要让访客` + `{act}`，空则 `页面需要让访客＿＿＿＿。` |

`:126` `if (!biz && !act) return [FRAME_EMPTY, l1, l2];`
`FRAME_EMPTY` = 「下面这份是这个风格的施工图。开头两行要你自己填（我不知道你做什么生意）：」

**提示词里唯一指名「做什么生意」的两行，默认是空的。**

### 1.4 藏在 `risk` 里的内容约束：只覆盖 6/35 案

`dna.risk` 35/35 有值，进提示词时截到 220 字（`:945-953`）。逐案扫内容级指令：

```
S02 必须挂真实|真实编号      S03 必须挂真实
S04 必须挂真实|真实的|作者   ← 本案      S07 真实的
S09 必须挂真实|真实的                 S29 真实列名   ← 本案
```

S04 原文：「③ 每个纸块必须挂真实的展期、作者与作品编号，混沌里要有可核查的事实。」

**这是「内容必须带事实」的约束，不是「内容必须是某行业」的约束。** 两版都遵守了（§3.2）。

### 1.5 小结：提示词在内容层 = **留白**

```
「必须这样写」的内容指令： 0 条
「必须包含某个词」：       0 条（35 案）
「你自己决定」：           2 条（数量、版式风格）
「你自己填」：             2 行（在提示词最前面，默认空）
「内容必须带真实事实」：   6/35 案，只约束真实度不约束行业
```

**两次产出不同生意，是这份提示词的必然结果，不是模型的失误。**

## §4 与传参 bug 的关系：要不要打折

**不打折。任务书那条推论的前提是错的。**

### 4.1 被吃掉的是元指令，不是产品提示词

`29-prompt-truncation-bug.md` 的记载是真的（`Start-Process -ArgumentList` 传数组不加引号，

task.txt（产品提示词）= buildStylePrompt(id)，38–39 行

模型只从 `-p` 收到 `Read`（一个**工具名**），接下来 `Glob *` → `Read task.txt`，拿到逐字节相同的全文。

### 4.2 为什么这对本结论没有影响

**内容不稳的成因是「提示词里那两个空槽」，不是「没收到提示词」。**

反证：如果模型真没读到 task.txt，它连「#2F7D4F #96550F #14100C #F0E2C8」
「4.2 倍 / 72px」「0.4mm / 3% / 14% / 315°」都不会知道 —— 而实测这些值**两版全中**，且可逐 byte 核。
**一个没读到提示词的模型不可能命中这些数。** 这本身就是「提示词到了」的因果证明。

### 4.3 要打折的是另外三类（必须一起说）

| 结论 | 打折？ | 理由 |
|---|---|---|
| **A 类：产物 vs 提示词**（配色/线宽/字号比/机制值/risk/防退化） | **不打折** | 提示词逐字节送达 |
| **D 类：内容层不稳**（本报告结论） | **不打折** | 成因在提示词文本里，与送达通道无关 |
| **B 类：耗时 / 卡不卡 / 零产物** | **打折** | 元指令绕道 `_run.ps1`，时序不同 |
| **S04 / S31 产物溯源** | **标 `UNVERIFIED-PROVENANCE`** | `20-reproducibility.md` §4.4：S04 stream 有 81079 事件但 **0 次 Write / 0 次 Edit**，result 是 `API Error: Connection lost mid-response`，而磁盘上有 32829 字节完整产物 |

**S04 这条对本报告的影响**：S04 的**产物内容**（配色/字号比/结构）可信，

### 4.4 一句话

> 传参 bug 伤的是「模型怎么收到任务」，不是「模型收到了什么」。
> 内容不稳的成因在提示词文本里 —— **读得到、抄得下、改得动。这个结论不需要打折。**

## §6 主线程对「加 C10 闸门量 minItems」的判断：**不该加**

报告 §5.2 建议加一条闸门，量产物有没有排够 `minItems` 个条目。
理由是「`minItems` 在 `measure.mjs` 里命中 0 次，这条约束从没被量过」。

**我核实了，这个建议会造出一条判错的闸门。**

### 6.1 提示词原文

`blind/S31/task.txt` 第 16–18 行：

```
1. 这个版式设计时排了 6 个条目——这是版式的规模，不是你的内容量。
2. 用你自己的真实数量排：有几个排几个，不凑整、不留占位符。
3. 这个版式是自动流排版，删条目只会让页面变短、不会留空位，你按自己的数量排就好。
```

**「6 个条目」不是要求产物排 6 个。** 它是在说「这个版式是按 6 个设计的」，
而紧接着第 2 条明确要求「**用你自己的真实数量排：有几个排几个**」。

所以：

- 产物排 3 个 → **完全合规**（用户只有 3 个产品）
- 产物排 12 个 → 也合规
- 拿「产物是否 == 6」去判 → **会在绝大多数合规产物上报 FAIL**

### 6.2 这与 `minPics` 的区别

`minPics` 用的是「**至少** N 个」（`版式里至少要 N 个不同的图片位置`）——
所以「多于 N」合规、「少于 N」不合规，判据成立。

`minItems` 用的是「**设计规模是** N 个」+「**按你自己的数量排**」——
两句话合起来的意思是「N 只是版式参数，产物数量由用户决定」。
**这两个字段的语义完全不同，不能套用同一个判据。**

### 6.3 那该不该量点什么

如果一定要加，能加的是这条**更弱的**断言：

> 产物的条目数与 `minItems` 处于**同一量级**（比如不超过 3 倍），
> 而不是「等于」或「至少」。

理由是：如果一个版式是按 6 个设计的，产物排了 60 个，那版式多半撑不住了。
但这属于「撑不撑得住」的问题，`degrades: yes` 的 13 案已经在提示词里
写了处理方法（「确实不足 N 个时，把空出来的位置整块重排」）。

**我的判断：先不加。** 理由：
1. 语义边界不清（「同量级」是个模糊判据，容易变成恒真或恒假）
2. `degrades` 已经在提示词层处理了这个问题
3. 加一条判不准的闸门，比没有闸门更糟 —— 这是本仓库反复的教训

### 6.4 但有一条**真**的缺口值得记

`measure.mjs` 不量条目数，所以「产物有没有塌成一个空壳页面」这件事
目前只有 `words`（总字数）这一个间接指标。

如果以后要补，应该补的是「**产物的内容密度**」而不是「条目数是否等于 N」。
这条先记下来，不实施。

## §7 主线程复核「线宽判据方向错误」：成立，而且改了之后结果完全不同

规划 Agent 指出线宽判据方向错了。我复核并重写了。

### 7.1 提示词原文是「包含性」，不是「全覆盖」

35/35 份都写：

> 5. 线宽只用这几级：0.5px、0.8px、1px、1.2px、2px、3px，**全站线条都从这几级里取**。

约束的是「**不许用档位表之外的值**」，不是「档位表每一档都必须出现」。
一个只用 1px 和 2px 的页面完全合规 —— 它没有需要 0.5px 的地方。

我原来的判据写反了：它要求「每档都出现」，于是任何省略档位的产物都被判缺线宽。

### 7.2 那个 0.6px 容差也太宽

```js
Math.abs(v - n) < 0.6 || Math.abs(v - Math.ceil(n)) < 0.01
```

实测：`miss([0.5,0.8,1,1.2,2,3], {1,2,3})` 返回 `[]` ——
本该返回 `[0.5, 0.8, 1.2]`，但 0.5 与 1 差 0.5 < 0.6 被误判为命中。

Chrome 的取整只发生在**计算值**上（0.5px 报成 1px），而这里比的是**源码声明的档位**，
所以只该保留「向上取整相等」这一种宽容。

### 7.3 重写之后：7/10，而三个违规都是真的

```
$ node _batch-compare.mjs S31 S04 S08 S13 S22 S32 S15 S18 S29 S35
  线宽全中:   7/10
  S31 用了档位表外的线宽: 3 （档位 1）
  S08 用了档位表外的线宽: 1 （档位 1.25/2/3/4）
  S13 用了档位表外的线宽: 5 （档位 1/1.5/2/3/5.5/9/14.5）
```

我逐条核了原始数据，**三条都是真违规，不是假失败：**

| 案 | 档位表 | 产物用了 | 判定 |
|---|---|---|---|
| S31 | `1px` | `3px` | 真违规 |
| S08 | `1.25px、2px、3px、4px` | `1px` | 真违规（1 ≠ 1.25） |
| S13 | `1px、1.5px、2px、3px、5.5px、9px、14.5px` | `5px` | 真违规（5 ≠ 5.5） |

**这推翻了我之前报的「线宽 8/10」** —— 那个数字是错判据的产物。
按正确判据是 **7/10**，而且之前报的「S13 缺 9px/14.5px、S18 缺 4px」全部是假失败
（那些档位没用上是合规的）。

### 7.4 S31 那一例是提示词自相矛盾

S31 的机制句写「主刻度每 60px、长 34px、**3px 宽**」，
而它的档位表只有「线宽只用这几级：**1px**」。

**提示词自己要求了两件冲突的事。** 模型用了 3px 去实现机制句 ——
那是它在两句话里选了机制句这一句。

规划 Agent 实测：35 份里 **2 份有同类内部矛盾（S27、S31）**。

而当前的 D3 闸门只查「机制句有没有可测值」，**不查「机制句的值与档位表相不相容」**。
这是一个真实的闸门缺口。

### 7.5 这条错的性质

我上一轮把线宽判据从「要求全覆盖」改成「检查包含性」，
但**没有回去核实提示词原文到底约束哪一侧**。

判据的方向比判据的精度更重要：方向错了，越精确越糟。
