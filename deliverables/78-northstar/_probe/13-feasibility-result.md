# 生成侧端到端可行性实测（主线程亲测）

> 2026-11-12　这是生成侧能不能做的决定性验证。不做这一步就开跑 35 案，是赌博。

## 结论先行

**能。** 一个隔离环境里的 agent，只拿到一段从 `prompts.js` 的 `dna` 拼成的提示词，
在 **704 秒**内产出了一个 414 行、10.7KB 的完整 HTML，而且**机制句的每一个可测值都精确命中**。

这不是「看起来像」，是逐条核过的数字命中。下面给证据。

## 二、硬约束逐条核对（这是我亲手 grep 的）

### 2.1 配色：5 个色值精确命中，一个不多一个不少

提示词给的 5 个色：
```
#F2F0EC（ink）、#5F5B55（paper）、#DEDAD3（ink-soft）、#55514B（paper-deep）、#8A857C（rule）
```

产物里出现的全部 hex：
```
#55514B #5F5B55 #8A857C #DEDAD3 #F2F0EC
```

**完全一致。** 这很重要，因为历史上这里是真实失败点：
`prompt-copy.js:600-616` 记录了 Q7 盲测「S17 缺 #D6C9AC」的历史，
以及「加一句『需要状态色时调明暗』反而更糟」的教训。这次没有复发。

### 2.2 零圆角零投影：做到了

```
grep -c 'border-radius' out.html  → 1
grep -c 'box-shadow' out.html     → 1
```

初看像违反，实际是这一行：

```css
*,*::before,*::after{box-sizing:border-box;border-radius:0;box-shadow:none;}
```

**这是遵守，不是违反** —— 模型用 reset 把圆角和阴影显式归零了。

### 2.3 最大标题：精确 104px

```
out.html:51   font-size:104px;
```

提示词要求「正文约 16px；最大标题要压到正文的 6.5 倍（约 104px）」。
产物 `body{font-size:16px}` + `h1{font-size:104px}`，比值 6.5，**精确命中**。

这条是提示词里标注「本案最容易被做塌的一处」的那条，模型照做到了。

### 2.4 机制句：四个可测值全部命中

提示词原文：
> 主刻度每 60px、长 34px、3px 宽，次刻度每 12px、长 12px、2px 宽，上下各一排共用两条贯穿基线

产物：
```css
.tick.major{width:3px;height:34px;}     ← 主刻度 3px 宽、34px 长  ✓
.tick.minor{width:2px;height:12px;}     ← 次刻度 2px 宽、12px 长  ✓
```
```js
var MINOR = 12, MAJOR = 60;             ← 次刻度间距 12px、主刻度间距 60px  ✓
var cls = (x % MAJOR === 0) ? 'major' : 'minor';   ← 分级逻辑正确
```
```css
.tick.top{top:1px;}  .tick.bottom{bottom:1px;}     ← 上下各一排  ✓
```

**六个可测值（60/34/3/12/12/2）全部命中，且间距与长短的对应关系没搞混。**
「上下两排」和「贯穿基线」也实现了（`.rulebar` 有 border-top/bottom）。

### 2.5 结构约束：6 个服务格

提示词要求「这个版式的设计规模是 6 个服务格，排 6 个」。
产物 6 个服务格（`grep -c '<li' → 6`），每格有具体服务说明。

## 三、这意味着什么

### 3.1 提示词确实承载了风格

之前所有「提示词有用/没用」的争论都缺一个干净实验。这次是干净的：
**没有任何浏览器工具、没有读原型、只有提示词**。

结果是：配色 5/5 精确、字号比 6.5 精确、机制句 6/6 可测值精确。
如果一个模型只能靠「猜」一个钟表修理铺长什么样，不可能猜出 `MAJOR=60, MINOR=12` 这组数。

### 3.2 成本是可算的

704s/案。35 案串行 = 6.8 小时。并行 5 路 ≈ 1.4 小时。

token 成本本轮没测（`claude -p` 不返回用量）。上一轮的实测是
**13 个盲测 agent 共 8.6M token、平均 0.6M/案**（`01-ROUND-SUMMARY.md` §… 已复算，不是规划说的 24.1M/案）。
按 0.6M/案 × 35 = 21M token 量级。

### 3.3 但这**不等于**「盲测成立」

三件事必须分开看：

1. **模型能不能照提示词做** —— 这次证明了能（至少 S31）。
2. **模型知不知道答案** —— 隔离挡住了读仓库，但**没证明它没有先验知识**。
   S31 是 Q2 我自己建的「安静中灰尺规」案，一个通用模型对「钟表修理铺 + 尺规刻度」
   可能有先验。要排除这条，必须做**记忆泄漏测试**（红队 Agent 正在做第 c 项）。
3. **不同模型/不同次会不会一致** —— 本机路由不可控，同一提示词两次跑可能不同。
   这条本轮没测，是下一轮必须测的。

**所以正确表述是：提示词可复刻性在 S31 上成立，但「盲」这个前提还没证。**

## 四、实际 routed model

`--model opus` 是名义参数。本机 `ANTHROPIC_BASE_URL=http://127.0.0.1:15721`，
所有模型名映射到 `deepseek-ai/deepseek-v4.1-flash`（见 `01-ROUND-SUMMARY.md` §零）。
隔离环境的 transcript 存在临时 HOME 里，脚本跑完就删了 HOME —— 这是我这边的疏漏：
**应该保留 transcript 以确认实际 served model**。下一轮批量跑时必须收集这个字段，
否则又是「名义模型」的老问题。

## 五、把这份盲测产物拿去对账，得到了一个闭环

用 `measure.mjs` 把隔离生成的 S31 与原型逐量对账（脚本 `_probe/_compare-S31.mjs`）：

| 量 | 原型 | 生成 | 判定 |
|---|---|---|---|
| 标题/正文比 | 6.50 | 6.50 | ✓ **精确一致** |
| 线宽集合 | [1.00] | [1.00] | ✓ 一致 |
| 栏数（tracks） | 4 | 3 | ✗ |
| 主容器 | `div#blocks.blocks` | `div.grid` | ✗ |
| 色值数 | 7 | 6 | 少 1 |

### 5.1 栏数差 1，但**这不是模型的错**

查 CSS 真相：

```
原型 S31  .blocks { grid-template-columns: repeat(auto-fit, minmax(280px, 1fr)) }
          → 在 1440 宽下浏览器算出来是 4 列

生成物    .grid { grid-template-columns: 1.55fr 1fr 1.2fr }
          → 写死 3 列
```

**关键：提示词里根本没有「几列」这条指令。** 提示词只说
「这个版式的设计规模是 6 个服务格，排 6 个」，没有说排成几列。
原型的「4 列」是 `auto-fit` 在 1440 视口下的**运行时展开值**，
不是作者写下的设计意图。

所以：

- 拿 `columns=4` 当验货基准，会把一个**完全遵守了提示词**的产物判成失败。
- 这正是 `01-ROUND-SUMMARY.md` §六 说的那条，现在有了**活证据**：
  不是"理论上可能假失败"，是"已经在我的第一次盲测上发生了"。

### 5.2 这直接决定 `layoutKind` 该怎么用

`auto-fit` 案（11/35）的 `columns` **不能作为验货判据**。
对它们该判的是：
- 每列最小宽度（`minmax(280px,1fr)` 的 280）有没有守住
- 有没有引入提示词没给的列数约束

而 `fixed` 案（如 S01 的 `5fr 24px 4fr 24px 4fr 24px 3fr`）的 `columns`
是**写死的设计意图**，可以判。

### 5.3 色值少 1 个

原型 7 个 hex、生成 6 个。查了提示词：给的是 5 个色值，
原型 `style.css` 有 7 个（多的两个是派生色）。
生成物用了 6 个 —— 比提示词给的多 1 个，比原型少 1 个。

这条**不算缺陷**：按 `compare.mjs:112-117` 定的判据（「提示词给的色是否都出现」），
6 ⊇ 5，配色这关成立。这也是那条注释里解释过的道理：拿原型全量色要求产物，
等于要求模型复刻它从未被告知的颜色。

## 六、对批量方案的直接约束


1. **超时不能设 900s**。这次 704s 是勉强够，抖一次就超时。建议 1500s。
2. **必须保留 transcript**（改 `HOME` 指向持久目录），从里面读实际 served model。
3. **必须并行**。串行 6.8 小时不可接受。
4. **每案产物要立刻做硬约束核对**，像本文 §二 这样逐条 grep —— 而不是等全部跑完再统一看。
   因为如果某个约束系统性失败（比如所有案都漏最后一色），早发现能早停。

## 七、复现性测试：**这一条失败得很重要**

同一份提示词（S31）、同一份配置（`--model opus`、`effort=max`、`acceptEdits`）、
同一个隔离方式，跑第二次（脚本 `_probe/_repro-run.sh`，超时设 1500s）。

| 项 | 第一轮 | 第二轮 |
|---|---|---|
| 耗时 | 704s | **> 1680s（28 分钟）仍未产出** |
| 结果 | 414 行 / 10722B | **被人工终止，无产物** |

### 7.1 这不是「偶然慢」，是生成任务的固有方差

差异的关键在于：这是**开放式生成任务**，模型要决定页面有多少内容。
第一轮它决定做一个 414 行的页面；第二轮它可能在做更长/更复杂的，
或者在某处打转（比如反复读 task.txt 反复改）。

**直接后果：不能设一个固定超时然后指望它够用。**

### 7.2 对批量方案的硬约束（修订）

我先前的建议「超时设 1500s（第一轮 704s × 2）」**被这个实验推翻了**。
真实做法应该是：

1. **按「是否产出 out.html」判成功，不按耗时判。** 一个跑了 40 分钟但产出了合格页面的
   agent，比一个 12 分钟放弃的更有价值。
2. **超时设成一个宽松上限（建议 3600s），并且超时不等于失败** ——
   超时后检查 `out.html` 是否存在，存在就收下。
3. **必须记录耗时分布**（`run.json` 里的 `ms`），第一批跑完就能知道真实分位数，
   第二批按 P90 设超时。
4. **不要相信「同一提示词两次结果相近」**。这一轮我就见到了 2.4 倍以上的耗时差，
   而产物质量是否同样波动，**尚未测**（第二轮没产出）。

### 7.3 这条对北极星指标意味着什么

「提示词能不能让模型做出这个风格」如果依赖一次成功的采样，
那答案就变成了「有时能」。所以验货口径必须是**多次采样的成功率**，不是单次得分。

这与本仓库 Q2 做确定性测试时学到的教训一致：单个样本的通过率高不代表系统稳定。

### 7.4 已确认的直接结论

- ✅ 提示词**确实**能驱动复刻（第一轮六个可测值全部命中，见 §二）
- ❌ 但**不稳定**（第二轮 28 分钟无产出）
- ⇒ 正确表述：**「提示词可复刻，但成功率未知，需 N 次采样才能估」**

这个表述比「盲测通过」诚实得多，也比「盲测不可行」有用得多。
