# clean-dna 的失败路径：三种「抽不到」被写成了「这个案子没有」

> 2026-11-15　主线程（原本派给调查 Agent，它两次启动都 0 字节没跑起来，我自己做）
> 目标：找出 `clean-dna.mjs` 里所有会产出**非空但对 AI 无信息、或者干脆误导**的值的代码路径。

---

## 一、总览

`clean-dna.mjs` 有五处「抽不到就给一个兜底说法」的返回。它们在当前 35 案上**全部零命中**
（实测：扫 `未声明`/`—`/`N/A`/`未知`/`0`/`NaN` 等占位形态，命中 0 处），
所以这不是「正在发生的故障」，是**潜伏的判据缺陷**。

| # | 位置 | 抽不到时会说什么 | 问题类型 |
|---|---|---|---|
| 1 | `clean-dna.mjs:952` | 「无边框线条（全站不画描边，只用色块与留白分隔）」 | **把失败说成设计** |
| 2 | `clean-dna.mjs:1579` | 「无阴影」 | **把失败说成设计** |
| 3 | `clean-dna.mjs:463` | 「全直角 0」 | **把失败说成设计** |
| 4 | `clean-dna.mjs:1581` | `map[sh.kind] \|\| sh.kind` —— 吐出英文枚举 | **兜底会把内部标识符漏给用户** |
| 5 | `clean-dna.mjs:1093` | `""` + why「不写进提示词以免编造」 | ✅ 这个是对的，见 §三 |

## 二、前三种：失败与设计不可区分

### 2.1 线宽：`clean-dna.mjs:949-953`

```js
if (!list.length) {
  if (provenance) provenance.push({ n: 0, decl: "(无任何线宽声明)", selector: "—", media: null });
  return { text: "无边框线条（全站不画描边，只用色块与留白分隔）", why: why };
}
```

`list` 为空有两种原因：

1. **这个案子真的没有画描边**（设计上就是靠色块与留白分隔）
2. **抽取失败了**（正则没覆盖某种写法——历史上就发生过：S27 的 `border: var(--mis) solid …`
   读不到、S25 的 SVG `stroke-width` 读不到，两次都让 `list` 变成空）

两种情况下 `text` **逐字相同**。所以：

- 如果是原因 2，提示词会告诉 AI「全站不画描边」，而原型的签名机制恰恰是描边
- 而 `provenance` 记的 `"(无任何线宽声明)"` 是给 `lineWidthsWhy` 用的，
  **但 `lineWidthsWhy` 没有任何消费者**（见 `42-why-fields-dropped.md`）——写了也没人读

**这正是 2026-10-26 那次真实事故的形态**：S27 抽出空数组，提示词里出现「5. 线宽只用这几级：未声明」。
当时的修法是「把 `未声明` 换成一句看起来像设计的话」——**修的是措辞，不是判据**。
换完之后，失败看起来更像成功了。

### 2.2 阴影：`clean-dna.mjs:1579`

```js
"none": "无阴影",
...
return map[sh.kind] || sh.kind;
```

`shadowDetail` 的 `kind` 在数不到任何 `box-shadow` 声明时是 `"none"`，于是文本是「无阴影」。
和线宽一样：**真的没阴影** 与 **抽取失败** 产出同一句话。

### 2.3 圆角：`clean-dna.mjs:463`

```js
if (!values.length) return { text: "全直角 0", bare: true, evidence: "该案 CSS 里 0 处 border-radius，所有元素一律直角" };
```

同样是「没抽到」→「全直角」。而 `bare: true` 还会让下游 `prompt-copy.js:631` 用固定句，
**把 `radius` 文本整个丢弃**——于是连「这个值可疑」的最后一点线索也没了。

## 三、第五种是对的，值得当作模板

`clean-dna.mjs:1093`：

```js
return { text: "", why: "该案没有显式的正文字号规则（浏览器默认 16px，不写进提示词以免编造）" };
```

它**返回空值并给出理由**，而不是编一个「正文 16px」。这是正确的方向。

前四种应该向它学：**抽不到就说抽不到，不要把「抽不到」写成「没有」。**

---

## 四、第四种：兜底会把内部标识符漏给用户

```js
return map[sh.kind] || sh.kind;
```

`map` 覆盖了 6 个 kind，当前 `shadowDetail` 只会产出这 6 个之一，所以现在不会漏。
但只要有人往 `shadowDetail` 加第 7 种 kind 而忘了同步 `map`，
用户看到的提示词就会出现一行英文内部标识符，比如：

```
4. 阴影：outer-and-inner-glow。
```

**这属于本仓库归纳的第①类：闸门读不到数据 → 不报错 → 打印漂亮结果。**
正确做法是 `map[sh.kind] ?? (() => { throw new Error('未映射的 shadow kind: ' + sh.kind) })()`，
让它在构建期就炸，而不是把内部标识符交付给用户。

## 五、我为什么不建议现在改

前三种「失败说成设计」是**真实**的判据缺陷，但修它需要先回答一个产品问题：

> 当某个案子的线宽抽取失败时，提示词应该（a）省略这一条、还是（b）说「本案线宽未能确定」？

- (a) 更干净，但 AI 会自由发挥
- (b) 诚实，但对店主是一句没有信息量的话，而且它出现在本该是施工图的地方

这个选择影响产品形态，不该由我在无人确认时定。

**而它现在的实际风险很低**：当前 35 案零命中，且历史上那两次抽取失败都已经修好
（S27 的 var 展开、S25 的 SVG stroke-width 都进了正则）。

**优先级判断**：这件事排在「让 `lineWidthsWhy` 第一次被读到」之后——
因为只要没人读 `why`，改 `text` 的措辞只是在两种都不可验证的说法之间换一种。
