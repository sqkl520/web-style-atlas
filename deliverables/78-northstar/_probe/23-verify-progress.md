## 二、修复一：banner 三处过时断言（`c998753`）

### 2.1 问题

`prompts.js` 头部的注释 banner 写着三句话，全是错的：

```
① 「dna.palette 由最多 5 色放宽到最多 7 色」      → 实为 9（clean-dna.mjs 的 MAX=9）
② 「21/30 案能检出主色」                          → 案数是 35 不是 30
③ 「9 案的 palette[0] 是纸色/底色的，不是强调色」  → **说反了**
```

### 2.2 第三条为什么高危

banner 正是写给「下一个改配色逻辑的人」看的，而它教人
**「不要把第一格当强调色用」**。旧 30 案恰恰相反 —— 照它写代码会把强调色当底色用。

### 2.3 我第一次的「更正」也错了

我先改成「palette[0] 一律是强调色」，然后写了个复算脚本验证，结果：

```
✗ ③ palette[0] 一律是强调色
    声称 0 案与底色相同  |  实测 4 案与底色相同（S32:#AE8ECD S33:#4A6763 S34:#2C3034 S35:#DCE0E4）
```

**4 案确实等于底色**，全是我 Q2 建的新案。

### 2.4 真相分两段

```
旧 30 案：  0 案相同，palette[0] 都是强调色（S01 #C1121F、S08 #C46A1F…）
新  5 案：  4 案相同（S32 S33 S34 S35），因为它们的 :root 把纸色声明在最前、
           又没有可检出的「主色」标记
```

banner 现在按这两段分别写，底色一律以 `data.js` 链的 `bg` 字段为准。

### 2.5 配了复算脚本

`_probe/_banner-check.mjs`（banner 里引用了它，必须有实物），4 条断言全过：


## 三、修复二：8 案在行业芯片里完全不可达（`1f801f9`）

### 3.1 问题

```
$ node -e "…统计 sceneIndex 覆盖…"
被索引的案数: 27 / 35
未索引的案: S10 S15 S21 S31 S32 S33 S34 S35
```

用户在选型台点行业芯片、或用搜索找这 8 案，**永远找不到**。

### 3.2 根因与 `plain` 为空完全相同

`SCENE_INDEX` 是 `build-prompts.mjs` 里的**手写映射表**，建 S31–S35 时没同步加进去。

而 `check-scenes.mjs` 发现了，但报的是 **INFO**：
「这些案的正向段里，一个词表成员都没有（用户点不到）」。
INFO 不阻塞，所以一直没被处理。

**这是本轮第三次遇到「手写表 + 新增案子时漏同步」**：
第一次是 `plain` 空（已修 + 加 D1 闸门），第二次是这个问题。

### 3.3 修法

每条映射都从各案 `data.js` 的 `scenesYes` 原文摘，不是编的：

| 案 | 原文里的行业 | 映射到词表 |
|---|---|---|
| S31 | 修表修鞋、开锁配钥匙 | 修鞋理发 |
| S32 | 花艺工作室、香氛、买手店、摄影、定制家具 | 花店 / 摄影 |
| S33 | 装修 / 施工 / 定制家具、咨询 / 设计 / 法务 | 律师 / 会计 |
| S34 | 写作课、编辑服务、翻译、出版、政策说明 | 出版 / 教育 |
| S35 | 设备、工具、服务系统、更新日志 | 工业设备 / 开发者工具 / 运维 / 数据看板 |

**只加 `near` 不加 `direct`** —— `direct` 表示「这一案就是这个行业的代表作」，
那需要更强的主张，不该由这次修补代劳。

顺带补了两处同类的：S15 的「档案馆」→ 档案，S21 的「CI/CD 流水线」→ 运维。

### 3.4 结果

```

仍未索引: S10
```

S10 的「B 端采购 / 工程规格 / 研究机构」确实不在 44 词表里 ——
那是**词表本身的缺口**，不是遗漏。要修得加词，属于产品决策，不在本轮范围。

### 3.5 一个必须说清的区别

修复后 `check-scenes` 仍报 INFO：
「S02 S10 S21 S33 S35 的正向段里，一个词表成员都没有」。

这**不是修复没生效**。那条查的是「正文原文里有没有词表词」，
我修的是「索引里有没有这个案」。两个口径都真实：

- 索引层（我修的）：用户点「花店」芯片，现在能看到 S32 ✅
- 正文层（INFO 报的）：S32 正文里写的是「花艺工作室」，不是「花店」二字

**用户实际能不能找到？能。** 但正文与词表用词不一致，仍然是可改进点。

## 六、复现性 Agent 的结果：它抓到三处我报错的数字

### 6.1 线宽是 8/10，不是 9/10（确认是我错）

我上一版报告写：

> 线宽 9/10（S13 缺 9px、14.5px 两档；S18 缺 4px）

**这句话自相矛盾** —— 列了两个缺的案却说 9/10。重跑对账：

```
=== 汇总 ===
  配色全中:   10/10
  线宽全中:   8/10      ← 实际
  字号比达标: 10/10
  图片数达标: 10/10

=== 缺口明细 ===
  S13 缺线宽: 9 14.5
  S18 缺线宽: 4
```

**2 案缺口 = 8/10。** 我写 9/10 是错的。

### 6.2 产物字节数已变，因为重跑覆盖了产物

| 案 | 我报告里写的 | 现盘实测 |
|---|---|---|
| S13 | 25730 | **31256** |
| S29 | 59861 | **41371** |
| S15 | 44814 | **47030** |

**这不是我编的数字。** Agent 在 `_staged/` 里存了历史版本
（`S13-v25730.html` 恰好 25730 B、`S15-v44814.html` 恰好 44814 B），证明当时确实是这些值。

**根因：产物没有版本化。** 每次重跑都会覆盖 `C:\tmp\bb\<案号>\out.html`，
而报告引用的是某一时刻的快照。`batch-result.json` 也被最后一次跑动覆盖
（现在只剩 S97 一条记录）。

这是本轮一个真实的方法论缺陷：**报告里的数字无法从当前磁盘复现，因为产物是易变的。**

### 6.3 `_batch-compare.mjs` 的配色判据是单向的（真缺陷）

Agent 指出：`_batch-compare.mjs:91` 只检查「提示词给的色是否都出现」，
**从不检查产物是否多用了未声明的色**。

它构造的例子：`S15-oldverify` 多加了 6 个未声明的 hex，仍然得 4/4「全中」。

这是**假绿**。但 Agent 同时核过：其余 13 个产物都是干净的，所以本轮的结论不受影响。

修法：加一条反向判据，或至少在输出里列出「产物用了但提示词没给的色」。

### 6.4 一个我必须纠正的前提：S31 那两份产物不是同一提示词的两次采样

Agent 查了 md5：

- `_sandbox-S31-out.html`（399 行 / 22064 B）的 md5 与 `C:\tmp\bb\S31\index.html` 相同 —— 这是真跑
- `_feasibility-S31-out.html`（414 行 / 10722 B）来自**另一份更短的提示词**
  （2338 B vs 5025 B；长版加「至少 1 个图片位置」，短版禁用 CDN 与图片）

**所以那不是「同一提示词的重复采样」，是两次不同实验。**
我之前隐约把它当成复现性证据，是错的。

### 6.5 它挖到了真正的重复数据（这是最有价值的部分）

git 历史里有 5 个案子存在 2 份以上产物，共 13 个：

- **数值层稳定**：24 个 pass/fail 格子里 23 个一致；13 个产物里字号比最大偏差 **0.9%**；
  配色与线宽从不出错
- **内容层完全不稳定**：S04 两次的标题是「野电流·菜市场二楼」与「贴满印社·第04面墙」
  （8-gram 重合度 0.042）；S13 是「棉纸公函」vs「蝉翼石室」（0.004）；
  S29 是「液压缸大修规程册 HY-114」vs「漏点对章节」（0.000）

**这条极重要**：它说明「10/10」只在**数值层**成立，在**内容层**完全不成立。
而产品的实际用途正是「给店主一个能用的站」——内容层不稳定意味着
同一个提示词给两个店主，会得到两份完全不同的文案。

### 6.6 产物没有截断（已核实）

Agent 核过 12 个产物：全部闭合 `</html>`/`</body>`/`</style>`，
CSS 花括号无不平衡，`<div>` 配对，无占位符残留。

那五个「超时边缘救回来」的案子（S08/S13/S22/S15/S29）全部以 `end_turn` 结束、
`is_error: false` —— **它们是正常完成的，只是收集器判早了**。

### 6.7 它建议重跑哪几案

- **S13**：唯一「线宽两次都在同样两个位置缺失」的案，测这个缺口是不是结构性的
- **S29**：内容重合度 0.000，需要第三个样本

**不建议降 effort**（那改变了条件，复现性问题就失效了）。

### 6.8 它发现的另外两个技术问题

**① `stream.jsonl` 被 NUL 字节污染**：S31 的 2.5 MB 里有 23% 是 NUL。
**② S31 的记录里零次 Write 调用**，却有完整产物 —— 所以 S04/S31 的 pass 项应标
`UNVERIFIED-PROVENANCE`。

第 ② 条我需要自己核实，因为它直接影响「产物是这个 agent 写的」这个前提。

### 6.9 我核实了「零次 Write」这一条：为真，但根因是记录被污染

```
$ node -e "…统计 S31 的 tool_use…"
总行: 41421
工具调用: 8       ← 没有一次 Write
```

确实是 8 次调用、零次 Write。但继续查发现根因：

```
$ node -e "…检查 NUL 与 session 数…"
S31   11022668 B  NUL  22.7%  session 2
```

**S31 的 stream 里有 2 个不同的 session，还有 22.7% 的 NUL 字节。**

说明文件被**重复追加**了 —— 我重跑 S31 时没有清空 `stream.jsonl`，
两次运行的记录混在一起，中间还有 NUL 填充。
真正创作的那次运行的工具调用记录，被埋在 NUL 里或与另一份混在一起了。

### 6.11 修法（已实施）

`_blindbox-batch.ps1` 每案开始时会 `Remove-Item $taskDir -Recurse`，
所以**批量跑**不会污染。污染发生在**单案重跑**时用了 `_blindbox-run.ps1` 直接调、
没有走批量的清目录逻辑。

已修：`_blindbox-run.ps1` 在启动前也清空 `stream.jsonl` / `stderr.txt` / `runner.log`。

### 6.12 对十案结论的影响评估

| 案 | 受影响吗 |
|---|---|
| S31 | stream 被污染，但产物完整（399 行闭合）。**产物本身可信，只是过程记录不全** |
| S18 | 产物是后一次的（29697 B），stream 混两次。**产物可信，过程记录不全** |
| S29 | 同上（41371 B） |

所以 S31/S18/S29 的 pass 项应标注为 **过程记录不完整**，
而不是 Agent 建议的 `UNVERIFIED-PROVENANCE`（产物来源是清楚的，
