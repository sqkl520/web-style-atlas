## 0. 结论先行

规划选的 **S09 / S28 / S03 / S07 / S14 / S19 / S26 / S24** 这 8 案，**不能代表 35 案**。不是"略有偏差"，是四个互相独立的系统性偏移同时发生，且四者的方向一致——**全部偏向"主流、安全、已验过"的一侧，把难的和新的全部漏掉**。

| 漏掉的东西 | 全库 | 8 案 | 随机抽 8 案恰好也全漏的概率 |
|---|---|---|---|
| `chroma ≤ 25`（很安静） | 6 案 | **0 案** | 18.24% |
| `hard`（认知门槛高且内容难） | 4 案 | **0 案** | 33.52% |
| `minPics ≤ 1`（少图） | 4 案 | **0 案** | 33.52% |
| Q2 新建（S31–S35） | 5 案 | **0 案** | 24.87% |
| `gate.fail > 0` | 6 案 | **0 案** | 18.24% |
| **以上五类的并集** | **11 案** | **0 案** | **3.12%**（精确超几何，非蒙卡） |

（脚本：`p18-prob.mjs`、`p19-joint.mjs`）

单看每一类都不算罕见（18%–34%），**五类同时全避开是 3.12%**——按 1/32 的概率抽出来的东西，不能叫"分层抽样"，只能叫"恰好躲开了难的那一堆"。

更严重的一条在第 4 节：**8 案里 6 案（75%）在 Q3-Q7 已经做过单案盲测了**，随机抽 8 案命中 ≥6 个已测案的概率是 **0.12%**。这不是"避开新的"，这是"避开了没验过的"——方向正好相反。

## 1. 先说三处与任务书不一致的事实

复算第一件事是把口径对齐。有三处必须先纠正，否则后面所有数字都会错。

### 1.1 `structure` 标签是 **23 个**，不是 22

```
去重后 23 个 = 出现2次 ×12 + 出现1次 ×11 + 出现3次 ×0
频次合计 35 ✓
```

（脚本：`p12-rep.mjs`、`p20-tables.mjs`）

22 这个数是 **Q2 之前的真值**——Q2 加了 5 个新案，只新增了 1 个标签 `SIGNAL-BOARD`（S31 用），所以 22 → 23：

```
Q2 前（30 案）structure 去重 = 22
全库（35 案）structure 去重 = 23
Q2 新增的标签 = SIGNAL-BOARD
```

（脚本：`p21-floors.mjs` 附带的验算）

`check-distribution.mjs:363` 的注释里那句"标签池只有 22 个"同样没跟上，是同一处腐坏。**这不影响结论**（8 案覆盖 8/23 ≈ 8/22，同样是低位），但说明"22"这个锚已经过期。

### 1.2 `loud` 不是独立维度，它是 `chroma` 的纯函数

```js
// prototypes/_build/collect-schemes.mjs:663
loud: chroma <= 25 ? '很安静' : chroma <= 60 ? '有态度不吵' : '就要扎眼',
```

我逐案验过：**35/35 全部满足 `loud === f(chroma)`**，零例外。（脚本：`p17-compare.mjs` 末段）

这条的意义：**"8 案里 `很安静` 是 0 案"和"8 案里 `chroma ≤ 25` 是 0 案"是同一件事，不能当成两条独立证据去叠加**。下面我把它们合并成一条（`risk:quiet`），不当两次用。

同样地，`ground`（亮/中间/暗）与 `band`（8 条带）都是从同一个 `bg` 色算出来的：

```js
// collect-schemes.mjs:654-665
ground: L >= 0.5 ? '亮底' : L >= 0.12 ? '中间调' : '暗底',   // CIELAB 亮度
band:   由 bh.l / bh.h / bh.s 三分支决定                      // HSL
```

两者高度相关但不完全同义（一个用相对亮度、一个用 HSL 明度），8 案里也确实出现了 `冷暗带` 同时算 `暗底` 的一致情形。我保留 `band`、降权 `ground`。

### 1.3 `built` 字段无法判定"新案"，必须用 git

`data.js` 里 `built` 字段 **35/35 全是 `true`**，对区分新旧零信息。（脚本：`p03-built.mjs`）

真正可机器执行的新旧判据是 git 的 add-commit：

```

S31–S35 首次加入 = 2026-11-10（Q2 新建，commit c02d813）
```

（脚本：`p09-provenance.mjs`）

所以"Q2 新建"= `{S31, S32, S33, S34, S35}`，共 5 案，**边界是干净的，没有歧义**。

## 3. "分层抽样"这个说法站不住

规划说的分层特征是 **P 色板 / R 比例字面 / C 栏数字面 / 骨架轨数**。我查了全仓：

```
grep -rn "骨架轨\|比例字面\|栏数字面\|轨数" prototypes/   → 0 命中
grep -rn "masterAxis\|column\|grid" 35 个 report.json    → 0 命中
```

（脚本：`p21-floors.mjs`、`p12-rep.mjs`）

`.inspect/report.json` 里**根本不存在** `column` / `grid` / `axis` / `lineWidth` 这些度量（我 35 个文件全扫过，全部为 0 次命中）。也就是说：

**这 4 个"二值特征"没有任何一个是可从现有数据机器算出来的。** 一个既不在 `data.js`、也不在 `report.json`、也不在任何脚本里的判据，无法验证、无法复算、也无法证伪——它在"分层"这个意义上是不成立的。特征存在与否无法检验，那"8 层"就只是一个叙事。

我用**实际可算的 62 个原子**做了一次蒙特卡洛，看规划的 8 案在 20000 次随机抽取里处在什么分位（脚本：`p07-baseline.mjs`）：

| 指标 | 规划 8 案 | 随机均值 | 规划处在随机分布的分位 |
|---|---|---|---|
| tone 种类 | 5 | 5.24 | 16.4% 以下（**比随机还差**） |
| structure 种类 | 8 | 7.43 | 48.5%（约等于随机） |
| band 种类 | 4 | 4.14 | 26.0% 以下（比随机差） |
| ground 种类 | 2 | 2.37 | **1.9% 以下（显著差于随机）** |
| loud 种类 | 2 | 2.77 | **0.4% 以下（显著差于随机）** |
| 含 quiet | 0 | 1.37 | 0.0% |
| 含 hard | 0 | 0.91 | 0.0% |
| 含 Q2 新案 | 0 | 1.15 | 0.0% |

**关键读法**：在"覆盖广度"这类指标上，规划的 8 案**比随机抽 8 案还差**（tone 16 分位、ground 1.9 分位、loud 0.4 分位）。它唯一做对的是 `structure`（48.5 分位，约等于随机）——这和 2.3 的发现一致：骨架确实没重复。

所以"分层抽样"的实际效果是：**在骨架一维上做到随机水平，在其余各维上低于随机水平，在风险维上系统性归零。**

## 4. 第 4 问：8 案里有多少是新建的 —— 0 案，而且有更糟的

任务书假设"8 案里有 2 案是 Q2 新建的"。**复算结果：这个前提不成立。**

### 4.1 更糟的一条：8 案里 6 案已经做过单案盲测

我扫了 `deliverables/74-q7/`（Q7 复刻验货）的产物文件：

```
out-S03.html  out-S03-v2.html  out-S06.html  out-S07.html  out-S07-v2.html
out-S14.html  out-S17*.html    out-S19.html  out-S23.html  out-S24.html
out-S26.html
=> Q7 实跑过 9 案 = S03 S06 S07 S14 S17 S19 S23 S24 S26
```

（脚本：`p22-reuse.mjs`）

规划选的 8 案与这 9 案的交集：

```
8 案 ∩ Q7 已盲测 = S03 S07 S14 S19 S26 S24   共 6 案 / 8 案 = 75%
真正"没被盲测过"的只有 2 案：S09、S28
```

**超几何检验：全库 9/35 已盲测，随机抽 8 案期望命中 2.06 案；实测命中 6 案，`P(X≥6) = 0.120%`。**

这是全份复算里最强的一条证据。**8 案里有 75% 是已经用同一套提示词、同一套测量、跑过一次单案盲测的案子。** 其中 S03 和 S07 更是"因为那轮盲测的结论而被改过提示词"的——`74-q7/REPORT.md:163` 记录 S03 补了三轨比例 `264:524:540` 后从 6/7 升到 7/7，`:164` 记录 S07 持续 7/7。

用这批案去"验货"，验出来的是**已经修好的东西会不会再坏**（回归测试），不是**没验过的东西会不会坏**（验货）。这两件事的价值完全不同：

- 回归测试：已知会坏的，修好后确认没退化——**8 案做这个够用，甚至偏多**；
- 验货：未知会不会坏的，靠抽一批没碰过的去探——**8 案在这件事上只完成了 2/8**。

规划的任务书写的是"盲测验货"，那就必须是后者。**6/8 的复用率让这次盲测的结论强度打了 1/4 折。**

补充：任务书说"S09 是老的，但 S31–S35 是新的"——S09 确实是老的（2026-10-20），这部分对；但 8 案里**一个 S31–S35 都没有**，所以"有 2 案是 Q2 新建"这个前提是错的。这也解释了 1.1 里 22→23 的标签数变化：因为新案一个都没抽到，抽样集看到的标签池还停留在 Q2 之前。

## 5. 我的抽样规则

### 5.1 判据（可机器执行）

我把"该覆盖什么"限定为**三类只能来自数据、且都有下游后果的特征**，共 **62 个原子**：

**漏 1：`有态度不吵` 这一档在 3 案里没有代表。** 全库 10/35（28.6%）是 `有态度不吵`，3 案（S08=就要扎眼、S15/S31=很安静）一个都没有。这与 `loud` 是向导第 3 问的三选一直接相关：**用户选"有态度不吵"时，这 3 案给不出任何参照。**

**漏 4：`load=三五屏` 零覆盖。** S08 与 S31 都是 `一屏说清`、S15 是 `很多栏目`；全库 12 案（34.3%）是 `三五屏`，一案未入。**"三五屏"是中等内容量的店主最常见的处境，3 案方案里完全缺失。**

## 7. 我这个规则漏掉了什么

必须自己先说清楚，否则就是重演"绿闸门 coexists with lying UI"的老病。

**漏 1：`structure`（23 个标签）这一维根本没解决。** 我的规则对 `structure` 只做"优先单例"，8 案覆盖 8/23、3 案覆盖 3/23。**抽样本身就解决不了骨架覆盖**——这是立案（35 → 更多案）或者降低"每标签至少 N 案"要求的问题，不是抽样问题。我的规则最多做到"同样 8 个名额，优先给不可替代的"。

**漏 2：规划说的 P/R/C/轨数四个特征，我一个都没用——因为它们**不存在**。** 我说"我的规则更好"，严格讲只在**可复算的 62 个原子上**更好。如果 P/R/C 真能算出来（比如拿 `_specs` 的结构字母 F/R 二分：16 F + 19 R），那规划的 8 层可能确实覆盖了某些我没看到的维度。

我验证过这个可能性：`_specs/Sxx.md` 里确实有 `**结构类型**：F` / `R` 的二分，但——

- 它只把 23 个标签压成 2 类（F=16 / R=19），信息量远低于直接用 23 个标签；
- 它和 `structure` 字段高度冗余（同一行的 `（NEWS-FRONT）`）；
- 它不是"二值 × 4 = 16 层"里的一个，撑不起 8 层。

所以我的判断是：**P/R/C/轨数这套说法没有可算的实体，无法验证。** 但如果规划者手里有我没找到的数据源，我的结论就要按那个数据源重算——这是我这套复算的**最大盲区**。

**漏 3：`gate.warn` 的 16 条规则我按计数处理，没有逐条展开。** `font-count` 32/35、`no-footage` 35/35 是全库恒定触发（等于无信息）；但 `contrast`(3)、`body-size`(5)、`measure`(5)、`micro-label`(5)、`outlined-box`(4)、`grey-body`(4) 这些是有区分度的，我把它们压缩成了一个 `gateWarn` 计数，**丢掉了"哪个案触发了哪条 warn"的信息**。

**漏 4：`scenesYes` / `scenesNo`（适用/不适用行业）完全没进规则。** 这是选型台的核心索引（`prompts.js` 的 `sceneIndex` 按 **44 个行业**反查，实测 `Object.keys(sceneIndex).length = 44`），8 案在"行业覆盖"上是否偏斜我没算。这是个真实的缺口——如果一个案"适合咖啡店"，另一个"不适合"，两者对用户的价值完全不同，而我的 62 个原子里没有这一维。

**漏 5：`minItems` 我只做了分档观察，没进目标函数。** 全库 3–46，跨度 15 倍（S07=46 对 S31=3）。`minItems` 直接决定提示词里"至少 N 条"那个数字（`prompt-copy.js:457`）。我把它留在了分布表里（第 2.5 节的表是 `minPics`，`minItems` 只在 `p19-joint.mjs` 里出过），但没让它参与选案。

**漏 6：权重 `1/freq` 是个任意选择。** 我用逆频次是因为"稀有特征更值钱"听起来合理，但**没有任何数据支撑这个函数形式**。换成 `1/log(freq)` 或 `1/freq²` 会选出不同的案。我能保证的只是：**给定这个权重函数，结果是全局最优且可复算**（穷举，非启发式）。权重函数本身是主观的——这是我这套规则最脆的一环。

**漏 7：所有"风险"标记都来自仓库自己的定义**（`chroma≤25`、`hardIds`、`minPics≤1`），我没有独立判断"哪些案真的容易出缺陷"。如果仓库的定义本身偏了（比如 `chroma≤25` 这个阈值是拍的），我的风险类就跟着偏。
