### 1.2 栏数：拆成两条，一条判分类一条判数

**旧注释的理由今天还成立吗？** 两条都成立，所以没有直接拿 `gridTracks` 对撞：

- 「哪个 grid 是主版式」无法可靠判断 —— **仍然成立**。实测证据比旧注释更强了：
  - `out-S03` 度量器选中 `dl.spec>div`：36 个子项、**平均每个 11 字**。那是一张 dl 规格表，
    不是版心。它报的 "2 轨" 没有任何证据价值。
  - 原型 S26 选中 `div.two.two--f`，提示词说的三栏容器根本没被选中。
  - 原型 S19 选中 `div.rowwrap>ul` 报 12 轨，而提示词说的是「宽取 2/3/4 栏三档」。
- 「机制句语义范围不同」—— **仍然成立**：S06/S14/S23 的机制句描述的是排布方式
  （沿斜轨漂、绕质心平漂、开口递减），压根没有栏数。

**所以改成两条：**

**①分栏结构（新增，判分类不判数）**：只问「有没有多栏版心」。
数值会漂（中缝让 2 栏数成 3 轨），分类不会。旧版根本没有这条，
而「原型刻意不分栏、产物却分了栏」这类偏差只有它能判 —— 旧版 `ok:true` 把它整个盖住了。

⚠️ 这条**必须带 artifact 守卫**，否则会制造假 FAIL。实测踩到的正是这个：

```
S14 原型：两栏首屏写的是 header.masthead（style.css:79 display:grid;
          grid-template-columns: 1.02fr 0.98fr）
          measure 的 landmark 规则把 header 整个排除 ⇒ 判 no-column-layout
S14 产物：等价的两栏首屏写在 <section> 里，不被排除 ⇒ 判 2 轨
⇒ 同一把尺子、一个排除一个不排除，报出「原型 0 轨 / 产物 2 轨」
⇒ 那是 DOM 标签差异，不是版式偏差。
```

守卫做法：判成 `no-column-layout` 时，回候选表里找「多栏 + 每子项 ≥40 字 + 非画廊」
的元素；找得到就说明版式存在、只是没被选中 ⇒ 跳过。

**守卫的第一版写错了，值得记下来**：它把 `landmark:footer` 也算作证据，
结果本库 30 案页脚普遍是多栏（S14 `div.foot-grid` 3 栏、S16 同、S34 `footer` 4 栏），
`no-column-layout` 的案全部退化成跳过，**这条判据在本库等于被关掉**。
收窄成「页脚不算证据」后（依据是 measure.mjs 自己写的「版心不会长在 footer 里」，
那是**有意的规则**而不是 artifact），S34 重新变得可判，S14/S16 仍跳过。
实测：

```
S14 gridFrom=no-column-layout → 守卫说「不可信」（header.masthead 2 栏 89 字）→ 跳过
S16 gridFrom=no-column-layout → 守卫说「不可信」（div.masthead-grid 2 栏 95 字）→ 跳过
S34 gridFrom=no-column-layout → 守卫说「可信」（无多栏候选）→ 可判
```

**②主体栏数（自校准后真判）**：三个条件全满足才判。
1. 提示词给了栏数（只读**机制句**，见 §4.1 的噪声）；
2. 度量器在**原型**上量出的数等于提示词那个数（尺子准）；
3. 产物那一侧选中的容器**平均每子项 ≥40 字**（像版心，不像清单）。

任一不满足就 skip 并打印原因。阈值 40 与 measure.mjs 的 `MIN_TEXT=40` 同源。

### 1.3 主轴比例：自校准 + 可信度门槛

旧注释说它「最不可靠」，两个原因：选到页头、机制句语义范围不同。

- 「选到页头」——**已由 measure.mjs 的重写修掉**（按文字量取第一）。实测 S23 现在选中
  `div.degrade-grid` 而不是 `HEADER.masthead`。
- 「语义范围不同」——**用门槛消除**：只在机制句真的给了比例时才判
  （「两页宽度比 5:7」「三栏按 5:3:4 分宽」「3fr、16px、9fr 分栏」），
  没给比例直接跳过。

再加两道关：原型侧要能复现提示词的比例（尺子准），产物侧要可信（同上 40 字门槛）。

实测这个设计真的挡下了三案：

```
S24  提示词比例候选 [5,3]，原型实测 [0.125×8]           → 跳过（那个 5:3 是分支线宽比，不是版心）
S26  提示词比例候选 [5,3,4]，原型实测 [0.5,0.5]          → 跳过（三栏容器没被选中）
S03  产物侧选中 dl.spec>div（11 字/子项），不可信         → 跳过
```

### 1.5 线宽集合(border)：判法不动，只改比对分辨率

这条本来就能失败（少了就红）。但它有个会制造假 FAIL 的问题，实测踩到：

```
out-S07 的 CSS 里写了 12 处 0.5px 边框 → measure 报 borderWidths=[1.00, 2.00]
out-S17 写了 0.5 / 0.8 / 2.4           → measure 报 [1.00, 2.00, 5.00, 6.00]
```

Chrome 在 `getComputedStyle` 里把亚像素边框取整了（measure.mjs ④ 的注释记的是同一件事）。
拿浮点数做集合包含 ⇒ 产物**正确地**用了 0.5px 反而被判「缺 1px」。
改成两边都四舍五入到整像素再比。代价（已知、接受）：0.4 与 0.8 在这一层分不开。

> ⚠️ **2026-11-14 更正：是「截断」，不是「四舍五入」。**
>
> 上面那条结论当时只有 0.5 / 0.8 / 2.4 三个观测值，而四舍五入与截断
> **只在 x.5 处分歧**，这三个值恰好都不在分歧点上，所以没被发现。
>
> 实测（`_roundtest.html` 一次声明四个值，用 `measure.mjs` 量）：
>
> ```
> 声明  5.5px / 5.4px / 1.25px / 0.5px
> 量到  borderWidths: ["1.00", "5.00"]
> ```
>
> 即 **5.5 → 5.00（向下截断）**、5.4 → 5.00、1.25 → 1.00、
> 0.5 → 1.00（小于 1px 时进到最小可见宽度，这是唯一向上走的情况）。
>
> 用四舍五入会把 S13 那个**完全正确**的 `--w55: 5.5px` 判成「自创 5px 违规」
> —— 实测确实报了，`_batch-compare.mjs` 因此改回截断：
> `quantize(v) = v>0 && v<1 ? 1 : Math.floor(v)`。
>
> **这条更正说明一个更一般的规则**：写「取整方向」这种结论时，
> 必须专门测一个 `.5` 的值，否则两种规则在样本上长得一样。

### 1.6 stroke 线宽：**决定不改**，另立一条

旧判据 `:101-110` 的理由是：**它测的是实现手段（用不用 SVG），不是视觉结果。**
产物完全可以用 CSS 画出同样的细线。

**这条理由今天仍然成立，而且有实测证据**：

```
out-S17：CSS 里声明了 0.5 / 0.8 / 2.4 / 5 / 6px，svgStrokeWidths = []
         也就是细线体系做对了，只是没用 SVG。
         拿「有没有 SVG」判对错，会把这个正确实现判红。
```

所以**没有硬改它**。做法是：删掉那条恒真判据，另立一条 **⑥线宽档位合规** ——
判「产物用到的每一级线宽，是否都在提示词给的档位里」。这才是原判据真正想守的
视觉约束，且它确实会失败：

```
提示词 S17 第 5 条：线宽只用这几级：0.5 / 0.8 / 1 / 2 / 2.4 / 5 / 6px
产物用到 3px ⇒ FAIL
产物用到 1/2/5/6px ⇒ PASS（即使它一个 SVG 都没用）
```

原型那组 stroke 数字仍然打印在 note 里，诊断价值不丢。

## 四、我发现的、你没提到的问题

### 4.1 提示词解析会抽出噪声数字（已修，但值得记）

第一版把「N 栏 / N 轨」在**全文**里抓，抓到三处假数：

```
S26：「与 10 号（五栏非对称基线网格）」  → 抽出 5，会让 5 栏的错误产物蒙混过关
S24：「8 栏加中轴，每层各伸 2 栏」       → 抽出 2，「每层伸几栏」不是「版式几栏」
S19：「宽取 2/3/4 栏三档」              → 抽出 4，那是三档宽度不是轨道数
```

修法：只读机制句那一行（含「签名动作」），且紧邻前 4 字出现「伸/跨/缩/扩/号」就跳过。
实测修后 S26 → `[3]`（修前 `[3,5]`）、S24 → `[8]`（修前 `[2,8]`）、
S19 → `[4]`（**修前修后相同**，因为「宽取 2/3/4 栏三档」的 4 紧邻字是「取」，
不在排除词里；这一条靠自校准挡下：原型量出 12 轨 ≠ 4）。
**如果不修，S26 与 S24 的主体栏数判据会明显变松** —— 这比原来更糟，因为它是假判据。

修后的行为在 S26 上能直接看到（`node compare.mjs S26`）：

```
修前：提示词给 [3, 5] 轨 … → 5 也在允许集里，一个 5 栏的错产物会被判 PASS
修后：提示词给 [3] 轨    … → 只剩 3，且原型量出 2 轨 ⇒ 自校准判定「尺子不准」→ 跳过
```

### 4.2 `measure.mjs` 有个会持续咬人的上限：`gridCandidates` 只留前 24 个

`measure.mjs:474` `cands.slice(0, 24)`。我的守卫要靠候选表判断「有没有多栏」，
但候选表被截断了 —— 前 24 名之外的多栏容器守卫看不见。
本库实测没撞上（`no-column-layout` 的案候选都很短），**但生成物变复杂时会撞上**。
这是 `measure.mjs` 的问题，按纪律我**没有改**，只在这里记下。

如果要修，最小改法是让 measure 额外返回一个摘要字段，
例如 `multiColCount`（整表里 cols≥2 且每子项≥40 字的元素个数），
而不是让消费方去数一个被截断的数组。

### 4.3 `measure.mjs` 的 `PICK` 在产物侧比在原型侧更容易错

九案实测，原型侧 PICK 平均每子项字数：193 / 500 / 394 / 312 / 198 / 136 / 230 / 282（八案），
产物侧：**11** / 66 / 800 / 114 / 304 / 63 / 1323 / 125 / 86。

`out-S03` 的 11 是数量级不同的异常（选中了 dl 规格表）。原型侧八案全部 ≥136，
产物侧有两案低于 66。**产物是 AI 写的，DOM 结构更随意，度量器更容易选错元素。**
所以「可信度门槛」在产物侧比对原型侧更重要 —— 我把它做成两侧都查，不是只查原型。

### 4.4 图片位判据有个口径缺口（没修，只在 note 里写清）

提示词要求的是「至少 N 个**不同的**图片位置（同一张图重复用不算）」，
而 measure 只给 `imgCount`（标签数）和 `imgVisible`（可见数），**不给唯一 src 数**。

`out-S07` 就是 16 个标签只有 8 个唯一 src 的情形（8 ≥ 7，结论不变）。
但一个把同一张图复制 8 遍的产物会**通过**这条判据 —— 那是假通过。

要按「唯一」判，得让 measure 多返回一个 `imgUnique` 字段；那属于改度量器，
按纪律没动。**这是本判据目前最大的已知假阳性。**

### 4.5 S03 的产物疑似有真偏差，但度量器看不见（重要）

`out-S03` 的提示词机制句要求「264:524:540 三轨分宽」。实际产物是：

```css
--axis:264px; --rail:24px;
.axis{position:fixed;left:0;width:var(--axis)}
.rail{position:fixed;left:var(--axis);width:var(--rail)}
.page{padding-left:calc(var(--axis) + var(--rail))}
```

即 **264px 固定轴 + 24px 轨 + 剩余区**，用 `position:fixed` 实现，
根本不存在 524 / 540 两个宽度，也不进 grid 候选表。**这大概率是真偏差**（指令没照做）。

但新版判据给不出 FAIL —— 因为它无法区分「真没做」和「用嵌套 flex 做了但度量器看不见」。
所以我给的是 **skip + 一句会让人去核的话**：

```
— 主轴比例 … 不拿这个数判人；全表有 23 个多栏候选（如 dl.spec>div 2 栏），结构可能只是没选中，需人工核
```

这是刻意的选择：**宁可说「需人工核」，不拿「看不见」当「没有」**。
一条会制造假 FAIL 的判据比只报不判更糟 —— 这正是这次任务的核心告诫。

### 4.6 `--selftest` 的素材来源是固定的

自检依赖 `out-S03` / `out-S14` / `out-S17` 三个文件存在且内容不变。
如果有人重新生成这三案，`columns-untrusted-pick` 与 `col-landmark-artifact`
两条变异的语义可能变（它们靠真实数据的特定形态触发）。
文件缺失时自检会打印 `? 缺素材` 并 `exit 2`，不会静默通过 —— 这一点已经处理。

## 六、更正记录：产品提示词 vs 简化提示词（**改判据前必读**）

> 2026-11-12 补。协调者中途给过一条**错误建议**，随后自己撤回了。
> 这条记在这里，是为了防止下一个人拿着那组错数字去改判据。

### 6.1 错的是什么

协调者曾提出「图片数 0/35，这条判据不该存在，应降级为 INFO」。
**这个结论是错的，来源是一次扫错对象**：他扫的是
`deliverables/78-northstar/blind/*/task.txt` —— 那是**生成侧盲测用的简化任务书**，
不是产品实际输出的 `deliverables/74-q7/prompt-*.txt`。

我独立复算了这个差别（不采信转述）：

```
产品提示词 74-q7/prompt-*.txt（9 案）：
  S03 图片指令=1 条目规模=true 栏字=3 线宽档位=true 字号倍=4.3
  S07 图片指令=1 条目规模=true 栏字=6 线宽档位=true 字号倍=4.9
  S17 图片指令=1 条目规模=true 栏字=3 线宽档位=true 字号倍=5.1
  …（9/9 每一案都有图片指令、条目规模、线宽档位、字号倍）

blind/task.txt（35 案）：
  有图片指令 0/35   有条目规模 0/35   有'栏'字 18/35
  有线宽档位 35/35  有字号倍 35/35
```

**两套文本的差别是结构性的**，不只是少几句：简化任务书保留了「线宽档位」和
「字号倍」这两条**数值约束**，却把「至少要 N 个不同的图片位置」「设计时排了 N 个条目」
这两条**规模约束**整条删掉了。所以从 `blind/task.txt` 统计「提示词里有没有图片指令」，
得到的必然是 0 —— 而那个 0 说的是简化版，不是产品。

### 6.2 为什么这直接决定判据对错

`prompt-S03.txt:19` 原文：

> 4. 版式里至少要 8 个**不同的**图片位置（不是8 个 img 标签就够——同一张图重复用不算）。

这是**明确的数字指令**，所以按本仓库的判读纪律（§6.3：有指令没做到 = 模型偏差；
没指令 = 提示词缺陷），它必须判，不能降级成 INFO。
**`got.imgVisible >= minPics` 这条改动是对的，不回退。**

### 6.3 顺带补做的交叉核对（本轮新增，之前没人验过）

判据的基准取 `minitems-parsed.json` 的 `minPics`，所以我核对了它和提示词里那个数字是否同源：

```
S03 提示词写 8 | minitems 表 8 ✓     S07 提示词写 7 | 表 7 ✓
S17 提示词写 5 | 表 5 ✓              S14 提示词写 10 | 表 10 ✓
S19 提示词写 6 | 表 6 ✓              S23 提示词写 10 | 表 10 ✓
S24 提示词写 6 | 表 6 ✓              S26 提示词写 6 | 表 6 ✓
S06 提示词写 7 | 表 7 ✓
9/9 全部一致 —— 判据基准与提示词同源，不是我自己编的数。
```

### 6.4 「栏数 12/35」这个数字也不可信，但结论方向碰巧对

协调者给的「栏数 12/35」同样是从 `blind/task.txt` 算的，不可信。
我用**产品提示词**在内存里重新生成了全部 35 案并实算（复用 `make-prompts.mjs` 的加载方式，
不写盘）：

```
35 案产品提示词实算：
  含图片位指令      35/35
  含栏数指令        16/35   S01:[4] S03:[3] S04:[5] S07:[2,3] S10:[5] S15:[8,12]
                            S16:[9] S17:[3] S19:[4] S21:[6,10] S22:[6] S24:[8]
                            S25:[7] S26:[3] S27:[3,5,9] S28:[2,7,16]
  含主轴比例候选     6/35
  含线宽档位        35/35
```

**真实覆盖率是 16/35（46%），不是 12/35。** 但协调者提出的**方法**是对的：
「栏数只能按提示词有无指令分情况判」—— 这正是我实现的做法
（`specColumnCounts` 返回空 ⇒ 跳过；非空且原型能复现 ⇒ 判）。
差别只在**数据来源必须是产品提示词**。

### 6.5 由这次核对抓出的一个真缺陷（已修 + 加了回归）

按 35 案全量实算时发现：**S31 / S34 的产品提示词写的是单值档位**。

```
S31: 5. 线宽只用这几级：1px，全站线条都从这几级里取。
S34: 同
```

我的 `specWidthScale` 第一版要求 `vals.length >= 2`，于是把这两案静默降级成
「无法判定」。**这是错的** —— 单值档位是一条**更严格**的判据（产物出现 2px 就该红），
读到了却不判，和「读不到就放行」是同一类毛病。

改成 `>= 1` 后实测：

```
旧版(>=2) 单值档位 → null   ⇒ 判据跳过（旧缺陷）
新版(>=1) 单值档位 → [1]    ⇒ 判据生效
两版在多值档位（S17）上结果相同 → [0.5,0.8,1,2]
```

并补了两条变异把坑钉死（`--selftest` 从 24 条增到 **26 条**）：

```
✓ width-single-tier [反向]      —— 触发了 PASS（期望 PASS）  单值「只有 1px」，产物也只有 1px
✓ width-single-tier-violated    —— 触发了 FAIL（期望 FAIL）  单值「只有 1px」，产物用了 2px
```

### 6.6 这一节的适用范围

- 「图片数 0/35」「栏数 12/35」这两个数字，**在讨论产品提示词时都是错的**，不要引用。
- 讨论**盲测简化任务书**的覆盖率时，那两个数字才有意义 —— 那是另一个问题
  （而且它本身说明简化任务书丢了规模约束，值得单独查）。
- 本轮所有判据的数据来源已统一为 `deliverables/74-q7/prompt-*.txt`
  + `prototypes/_prompts/minitems-parsed.json`，两者 9/9 同源（§6.3）。

## 七、环境问题记录：跑批量对账时的内存

> 2026-11-12 实测，与判据无关，但会伪装成「代码坏了」。

跑 `--selftest` 与六案批量时各遇到一次失败，都不是代码问题：

1. **一次 `CDP timeout: Page.navigate`**（S14）。单独重跑即通过 → 浏览器/端口偶发抖动
   （measure.mjs 的 `BAD_PORTS` 注释记的是同类问题）。
   但它暴露了真问题：**单案抛错会炸掉整批，前五案的结果全部丢失**。
   已改为逐案 try/catch，失败记成一条 `测量失败`（state=fail，计入分母 ——
   验货没做成不等于通过），其余案照常出结果。这是本轮唯一一处
   会让「整批静默无输出」的脆弱点，已修。
2. **一次 `FATAL ERROR: Zone Allocation failed - process out of memory`**。
   查下来是环境：本机 34.3GB 内存只剩 **0.9GB 可用**，
   其中 `qemu-system-x86_64-headless.exe` 占 14.9GB；另有 16 个我自己的调试端口
   Chrome 残留（742MB）。清掉残留、等内存回到 1.5GB 后，同一份代码
   `--selftest` 26/26 通过、六案全过。

**下一次有人跑批量对账前，先看一眼可用内存**：

```bash
node -e "const os=require('os');console.log('可用 GB:',(os.freemem()/1e9).toFixed(2))"
```

低于 ~1.5GB 时，Chrome 会以 OOM 或导航超时的形式随机失败，看起来像判据坏了。
必要时给 node 加 `--max-old-space-size=3072`。
