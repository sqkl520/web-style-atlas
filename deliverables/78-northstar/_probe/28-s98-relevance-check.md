# S98 测的是产品不会出现的状态（主线程自查）

> 2026-11-13　主线程
> 在批判 Agent 回来之前，我先自查了一个问题：**S98 那种「有机制、无数值」的提示词，
> 产品真的会产出吗？**

---

## 一、结论：不会

S98 是把 S31 的提示词**手工删掉全部数值**造出来的。而产品的提示词由
`prompt-copy.js` 的 `buildStylePrompt()` 生成，它的数据来自 `prompts.js` 的 `dna`。

**实测：35 案里没有一案的 `dna` 处于「有机制、无数值」的状态。**

```
$ node -e "…统计每案机制句里的可测数字与数据字段…"
机制句零数字的案: 0 （无）
数据字段零个的案: 0 （无）
机制句数字最少: 1
```

```
$ node -e "…检查各字段是否为空…"
lineWidths / h1Size / bodySize / palette / radius / shadow
—— 所有字段全部非空
（0 案缺任何字段）
```

---

## 二、这意味着什么

### 2.1 S98 是一个产品不会进入的状态

产品的数据链是：

```
_specs/*.md → extract-dna.mjs → clean-dna.mjs → dna-clean.json
            → build-prompts.mjs → prompts.js (dna)
            → prompt-copy.js:buildStylePrompt() → 用户拿到的提示词
```

这条链上每一环都要求数值存在：
- `extract-dna.mjs` 从 `style.css` 抽色值/字体/圆角/阴影/线宽
- `clean-dna.mjs` 把它们规范化成可执行的一句话（缺失时会给「未声明」而不是留空）
- 而**实测 35 案一个「未声明」都没有**

所以 S98 那种状态要么得手工编辑 `prompts.js`，要么得在生成器里挖个洞才做得出来。

### 2.2 那 S98 的回答值多少

它回答的是「如果我给模型一份产品不会产出的提示词，会发生什么」。

**这不是产品问题。** 产品问题是「用户实际拿到的那 35 份提示词，做得出来吗」——
那已经由十案盲测回答了（配色 10/10、字号比 10/10、图片 10/10）。

### 2.3 但有一个例外要说清

有一种情况产品**会**产出接近「缺值」的提示词：**某案的某个字段抽取失败**。

历史上有过：
- `plain` 为空（S31–S35，已修 + 加 D1 闸门）
- `minPics` falsy-0（S34，已修 + 加 D2 闸门）
- `palette` 曾被 `pickPalette` 截断到 7 色（已修，MAX 改 9）

**这些才是真实的风险形态**：不是「人为删掉全部数值」，而是「某一个字段静默变空」。
而这一类问题，闸门能拦（D1/D2/D3 就是干这个的），比跑一个 4 小时的盲测便宜得多。

## 三、对重跑方案的影响

如果批判 Agent 也认同这个判断，那 S98 的重跑**优先级应该降低**。

**更该做的可能是**：
1. 补一条闸门：检查 `dna` 的每个关键字段非空（现在没有这条）
2. 修 `probe.mjs` 的画廊判据（C9 已暴露 5 案）
3. 处理「内容层完全不稳」（同一提示词两次产出文案完全不同，见 `20-reproducibility.md`）

第 3 条我认为对产品的威胁最大：店主拿到提示词给 AI，AI 每次给的文案都不一样，
而他期望的是「按我的店做」。这不影响「结构复刻」，但影响「可用性」。

## 五、网关诊断 Agent 的发现：S98 的失败是**时段**选错了

这个发现改变了整件事的性质。

### 5.1 524 与运行时长、输出长度无关

```
案    api_retry   duration_api   文件大小
S15       0        253 分钟      24.8 MB     ← 跑最久、文件最大，零重试
S18       0         ?           12.0 MB
S98      10        123 分钟      11.0 MB
S97      10         27 分钟       1.3 MB     ← 只跑 27 分钟，10 次重试
```

S15 跑了 **253 分钟**、文件 **24.8 MB**，一次重试都没有。
而 S97 只跑 27 分钟就有 10 次。**「任务太长」这个解释被直接否定。**

### 5.2 真正的自变量是时段（我独立复核了）

```
案     起始小时    api_retry   其中524
S04      00          2          0
S08      00          2          0
S13      00          4          0
S22      00          3          0
S32      01          0          0
S15      03          0          0
S18      03          0          0
S21      03          0          0
S29      03          4          0
S99      03          2          1
S35      05          0          0
────────────────────────────────
S98      16         10          8     ← 下午
S97      18         10         10     ← 下午
S31      19         18         12     ← 下午
```

**下午 16 点后开跑的三案吞掉了 30/31 的 524。凌晨 0–5 点的十一案总共只有 1 次。**

### 5.3 Agent 的机制解释（我引用，未独立复现）

524 是网关的 **60 秒静默超时**，不是运行时长限制：

- 181 条 `app=claude` 的 524，服务端耗时全部落在 **60 294–61 616 ms**（中位 60 404）
- 同一秒对照组：`claude-desktop` 通道 2.3 秒返回 200，`app=claude` 通道 60.4 秒被切断
- 差别只在**有没有心跳**：它发了个 80 万 token 的请求，靠 8 条 `: PING` 在 **91.6 秒**成功返回

它还算出：S98 的 8 次重试总预算是 9.9 分钟，而它撞上的拥堵是 10.2 分钟 ——
**差 18 秒**。12:48:51Z 上游就返回 200 了，而 S98 在 12:48:49Z 放弃。

> 我没独立复现这些数字（需要抓包与网关日志）。但「524 集中在下午、凌晨为零」
> 这一条我用自己的数据复核了，与它的结论一致。

## 六、这如何改变我的判断

### 6.1 S98 的「零产物」现在有三层解释，只有一层是任务的

| 层 | 原因 | 证据强度 |
|---|---|---|
| ① 网关在下午拥堵 | 524 集中在 16–19 点 | **强**（我独立复核） |
| ② 重试预算比一次拥堵还短 18 秒 | 9.9 分钟 vs 10.2 分钟 | 中（Agent 算的，我未复现） |
| ③ 任务本身（缺数值） | 无 | **无直接证据** |

**所以「S98 零产物 ⇒ 缺数值导致卡死」这个推理，主要支撑在第 ① 层，
而第 ① 层与任务设计毫无关系。**

### 6.2 但 §一 的发现仍然成立

即使解决了网关问题，**S98 测的仍是产品不会产出的状态**：
35 案的 `dna` 六个关键字段全部非空、机制句无一零数字。

所以现在有两条独立的理由指向同一个结论：

1. S98 的失败是时段问题（可修复，但与任务无关）
2. S98 测的状态产品里不存在（即使跑通，答案也不改变任何决策）

### 6.3 我的建议

**不重跑 S98。** 理由不是「跑不出来」，而是「跑出来了也不改变什么」。

**但要采纳 Agent 的两条基础设施修正**（它们对以后任何盲测都成立）：

1. **错峰运行**：盲测排在本地 00:00–07:00。这一条能把 524 率从 37–71% 压到 0%
2. **重试预算要覆盖一次完整拥堵**：首次重试等 120 秒而不是 30 秒，
   且总预算不能少于 25 分钟（Agent 算出熬过 25 分钟需要 16 次尝试）

这两条与 S98 是否重跑无关，是沙箱方法论的一部分。
