**14% 不是「致命」，是「偏乐观」**。所以我把它从「致命」降到这里，真正致命的部分是我下面写的方差。

**真正的问题：6.7 倍的单案方差，WBS 只给了一个点估计。** 16 次会话的 token 分布：

```
mean 24.10M  sd 10.20M  min 7.13M (S26)  max 47.81M (S17-b)  spread 6.7×
```

```
8 案合计：p5 = 148M / p50 = 192M / p95 = 241M
他写：193M   ← 恰好是 p50，没错，但把 148–241 这个区间藏掉了
```

**为什么这比我原来那条「1.8 倍」更要紧**：WBS-6 的验收和排期是以 193M / 1.2 小时为基线写的。**真实区间的上界是 241M（+25%），下界 148M（−23%）**。一个季度只跑一次的东西，落到 p95 是常事——而「5 路并行 1.2 小时」在 p95 下是 1.5 小时，且**并行度受限于本机路由层**（见 S4：16/16 都没跑在声明的模型上，本机代理是否支持 5 路并发，WBS 没有验证）。

**他没写、但决定成本的那一条**：token 与「agent 自己截图自查的深度」强相关：

| agent | tokens | Bash 调用 | Read |
|---|---|---|---|
| a42b54 | 7.1M | 29 | 12 |
| afb88f | 19.2M | 15 | 2 |
| a27d69 | 31.0M | 98 | 28 |
| ad676d | 47.8M | 103 | 35 |

**低 Bash（≤40 次）3 个均值 16.8M；高 Bash（>40）13 个均值 25.8M**。也就是说「24.1M/案」不是一个属性，而是**「这个 agent 拍了几十张截图、量了几十次自己调的」的副产品**。

WBS-3 的 L2 隔离（`:153`）想做的正是「**不给它 Bash，只给 Write**」。若真这么做，成本会掉到 ~17M/案（−30%），但**产出质量会一起掉**——上一轮 9 个 7/7 的案子里，`a27d69`（98 次 Bash）和 `ad21c6`（94 次 Bash）是靠反复截图自纠做出来的。**`00-WBS.md` 把 Bash 只当成隔离漏洞（V1/V2），没意识到它同时是成本的主变量和质量的唯一来源**。这是本文档在「隔离」与「成本」两节之间掉的一块。
