## 一、`（作者原话）`：61 次，但**不改**

提示词里出现 61 次「（作者原话）」，分布在第 6 条硬前提与 risk 段标题。

**它是什么**：仓库内部溯源标注——告诉维护者「这句话不是从 CSS 抽出来的，是作者写的判断」。

**对 AI 有用吗**：没有。AI 不关心谁说的。

**但我判断不值得改**，三个理由：

1. **它不造成困惑**。前两个缺陷（「请先告诉我」「与 10 号的分界」）会让 AI
   产生错误行为或读到无意义内容；这个只是多了 6 个字。
2. **它保留了一个真实信息**：「这是作者判断，不是实测值」。万一 AI 或店主
   追究「这个数哪来的」，这个标注是诚实的。
3. **改它会牵动审计脚本**：`deliverables/66-audit/count-constraints.mjs`
   等三个脚本用这个前缀定位 risk 段。

**这不是「没找到问题」，是「找到了但判定不是问题」。**

## 二、物理单位 `mm`：两案，**都是合法的**

提示词里有 8 处物理单位（`0.4mm`、`2mm`、`22cm`、`200g` 等）。AI 输出 CSS
时只认 px —— 所以单位会不会造成问题？

逐个查：

| 案 | 值 | CSS 里的实现 | 判定 |
|---|---|---|---|
| **S17** | `2mm` | `--stamp-shift: 2mm;`（第 20 行） | ✅ **合法**。CSS 原生支持 mm，浏览器按 96dpi 换算 |
| **S13** | `0.4mm` | 只出现在**注释**里；实际是 `--press-depth: 0.8px` | ⚠️ 设计语言，不是实现值 |

S13 的情况值得说清：提示词第 6 行同时有「凹槽压深 0.4mm」和「下沉 0.8px」。
前半句是作者的**视觉描述语言**（「凹槽要浅」），后半句才是可执行值。
AI 读到 0.4mm 只能理解成定性描述，具体数值得看后面的 px。

**这不算缺陷**：两份信息各司其职。但它确实混了「设计语言」与「实现值」两种精度 ——
记为观察，不改。

## 四、用户输入边界：**全部合理**

测了 `have` 参数的各种极端值：

| 输入 | 第 2 条的输出 | 判定 |
|---|---|---|
| `undefined` / `0` / `''` / `'abc'` / `-5` | 「用你自己的真实数量排…」 | ✅ 退回原文 |
| `1` / `3` / `999` | 「你手上有 N 条内容，就排 N 条」 | ✅ 正常 |
| `2.5` | 「你手上有 2 条内容」 | ✅ 取整 |
| `'3abc'` | 「你手上有 3 条内容」 | ✅ 解析前导数字 |
| `'007'` | 「你手上有 7 条内容」 | ✅ |

`999` 在 `parseHave` 的上限内（≤999），所以通过。没人有 999 条内容，
但那属于用户乱填，不是系统缺陷。

另外测了 biz 字段的边界：

```
'Blue Bottle Coffee Roastery' → 我经营Blue Bottle Coffee Roastery。
'茶'                          → 我经营茶。
'「一杯」咖啡馆'               → 我经营「一杯」咖啡馆。
'咖啡店\n第二行'               → 我经营咖啡店 第二行。   （换行被压成空格）
```

四种都正常。
