# 64 · 选型台决策路径 · 第一类：给店主做判断的数字是旧的

日期：2026-11-05
范围：`prototypes/_selection/`（选型台 + 向导）
命题：**店主凭什么从 35 个风格里选出 1 个并带走提示词。**

---

## 0. 这一类的形态

不是"数字显示错了"。是：

> **页面用一份错误的统计，替店主做出了一个判断。**

`index.html:188` 那句话的句式是：「30 个里有 18 个落在暖浅色带……**如果你觉得可选项看起来都差不多，这就是原因。**」

它在向店主解释一件事——"你觉得都差不多，不是你的问题，是供给结构的问题"。这是一个**结论**，而它的证据（色带分布）已经过期。

同类问题在本仓库有过一次记录，`app.js:1776-1782` 的注释：

> 起因（2026-11-04）：`index.html` 的 summary 写「11 组 47 颗芯片」而实际渲染 45 颗，
> 「多数案 10 段」而实际 12 段——两个数字都在公网对外服务了至少 8 天，
> 而 `check-docs.mjs` 的 13 条断言**只读 README.md**，`index.html` 零条。

当时的处置是引入 `fillDerived()`，并在函数头立了一条铁律：

> 页面上任何「复述某个可计算量」的数字，都必须由这里注入，不许手写。

**这条铁律立了 13 个月，而 `index.html:188` / `:197` 两条 rail-hint 从来没有被纳入。** 它们不只在注释宣布修复时被漏掉，还在那之后又漂移了一轮。

## 1. 实测：色带分布

`data.js` 的 35 条 SCHEMES，`axes.band` 实际分布：

| 色带 | 文案声称（`index.html:188`） | 实测 | 差 |
|---|---|---|---|
| 暖浅色带 | 18 | 18 | ✓ |
| 冷暗带 | 5 | 5 | ✓ |
| 暖暗带 | 3 | 3 | ✓ |
| 中间明度带 | **1** | **3** | **少 2** |
| 中性浅带 | 2 | 2 | ✓ |
| 冷浅色带 | **1** | **2** | **少 1** |
| 中性中带 | *未提* | **1** | **漏** |
| 纯中性暗带 | *未提* | **1** | **漏** |
| **合计** | **30** | **35** | **差 5** |

合计 30 是最直接的证据：这句话写于方案还是 30 个的时候，之后加了 5 个方案（S31–S35），这句话一个字没动。

复现：

```js
globalThis.window = {}; eval(fs.readFileSync('prototypes/_selection/data.js','utf8'));
const t = {}; window.SCHEMES.forEach(x => { const v = x.axes.band; t[v] = (t[v]||0)+1; });
// { 暖浅色带:18, 冷暗带:5, 暖暗带:3, 中间明度带:3, 中性浅带:2, 冷浅色带:2, 中性中带:1, 纯中性暗带:1 }
```

## 2. 实测：认知门槛分布（向导页）

`wizard.html:65`：

> 参照：30 案里有 11 个的认知门槛是"低"，12 个"中"，7 个"高"。

`data.js` 的 `threshold` 实际分布：

| 门槛 | 声称 | 实测 |
|---|---|---|
| 低 | 11 | **14** |
| 中 | 12 | **14** |
| 高 | 7 | 7 |
| 合计 | 30 | **35** |

同一形态：合计 30，实际 35；两个数错，第三个对。

**这一行比第 188 行更严重**——它是 `wizard.html` **第 4 题「访客第一次进来，你希望他怎么样？」的提示行**，直接挂在题干下面：

```html
<div class="wz-q" data-q="guide" hidden>
  <p class="wz-n">问题 4 / 5</p>
  <h2>访客第一次进来，你希望他怎么样？</h2>
  <p class="wz-hint">参照：30 案里有 11 个的认知门槛是"低"，12 个"中"，7 个"高"。</p>
```

它不是一句旁注，而是**店主回答这一题时的唯一参照系**。他读到"多数方案门槛是低的"（11+12=23 vs 高 7），和实测"低中合计 28、高 7"虽然结论方向一致，但两个中间值都错了 25%——而这题的两个选项恰好是"三秒内知道先看哪"（对应低门槛）和"愿意花点时间读进去"（对应高门槛）。**他在判断"我这样要求算不算过分"时，引用的是一个错的分布。**

附带一个更隐蔽的问题：这题只有 **2 个选项**，另外四题都是 3 个。店主能选的门槛只有"低"和"高"两档，而数据里 `threshold` 是三档（低 14 / 中 14 / 高 7）——**"中"这一档在向导里没有对应答案**，那 14 个方案在门槛这一维上永远只能靠"相对更近"被勉强归到某一侧。

## 4. 正确的分类

不是所有数字错误都同等严重。按"会不会改变店主的决定"分三级：

**A · 改变决定**（用错误证据替他判断）
- `index.html:188` 色带分布 —— 它明确在替店主解释"为什么你觉得都差不多"
- `wizard.html:65` 门槛分布 —— 它是回答第 5 题时的参照系

**B · 改变预期**（他以为的规模与实际不符）
- `wizard.html:21` `<h1>`、`wizard.html:7` description、`index.html:6` title、`index.html:7` description

**C · 只影响内部一致性**（注释里的数字，用户看不见）
- `index.html:41/101/269/273/321`

C 类不该算产品缺陷，但它会**持续误导下一个维护者**——他读注释以为有 30 个案。

## 5. 为什么这一条能被漏掉

三道闸门都没覆盖它：

1. `fillDerived()` 是**运行时注入**机制，它只对写了 `data-derived` 的元素生效。`:188` 和 `:197` 根本没写这个属性——**机制存在，但没有强制"必须走机制"的检查**。
2. `check-docs.mjs` 的 13 条断言只读 `README.md`，`app.js` 自己的注释就写明了这一点（`app.js:1781-1782`：`index.html` 零条）。
3. `verify-prototype` / `inspect.mjs` 测的是**布局与视觉**（正文尺寸、横向溢出、emoji），不测"这句话说的事实对不对"。

**这是第 ⑥ 类缺陷的一个具体实例**：判据（闸门）在一个正确的层次上运行，但它读的对象（DOM 结构、视觉指标）与这一类问题的载体（陈述性文字的真值）不在同一层。

## 6. 待定：修法

三个选项，等 agent 报告汇齐后裁决：

**① 全部改成 `data-derived` 注入。** 干净，但需要给"色带分布"这种**多值句子**设计新的派生 key（现在是单值 slot）。而且句子结构会随数据变（哪个带最多、有几个带为零），模板化会很难读。

**② 数字不写进句子，句子改成动态生成整段。** 由一个函数根据实测分布拼出整句话。灵活，但把文案的控制权从 HTML 移到 JS，与仓库"文案在 HTML、数字在 JS"的现状相反。

**③ 删掉具体数字，只留定性的那句判断。** 例如「这一层 35 个里有 18 个挤在同一个色带——如果你觉得可选项看起来都差不多，这就是原因」。**这句判断本身在 18/35 的实测下是成立的**（最大带占比 51%），只有枚举细节是错的。删掉枚举，保留结论。

我倾向 ③ 加一条闸门：**扫描 `rail-hint` / `.mast-*` 等面向用户的文本节点，凡是出现"数字 + 量词"的，必须在白名单里说明该数字为何不需派生。** 这样下一处手写数字会被拦下，而不是等它再漂移 13 个月。

## 7. 闸门为什么没拦住（变异实测）

`check-ui-copy.mjs` 的职责就是这一类问题。脚本头自己写着：

> 判据的设计原则：**界面里复述可计算量的数字必须派生，不许手打。**

但它的 `HARDCODED_GUARDS`（第 100–124 行）只有 **2 条硬编码锚点**：

```js
const HARDCODED_GUARDS = [
  { rule: 'chip-count-hardcoded',
    re: /rail-fold-sum[^>]*>([\s\S]*?)<\/summary>/,
    what: '筛选条 summary（组数 / 芯片数）',
    digits: /\d+\s*组|\d+\s*颗/ },
  { rule: 'field-count-hardcoded',
    re: /class="[^"]*\brail-note\b[^"]*"[^>]*>([\s\S]*?)<\/div>/,
    what: '「怎么用」说明里的字段段数',
    digits: /(多数案|个别)\s*\d+\s*段/ },
];
```

它守的是「**W2 修过的那两处**没有退回手写」，不是「**这一类数字**不再出现」。
`rail-hint` 的锚点不在其中，所以从来没被看过一眼。

**变异实测**：往 `index.html:197` 的 rail-hint 里塞进一个荒谬的假数字——

```html
<p class="rail-hint">按调色板里最高彩度算。实测 999 个方案里 888 个是暗底。<b>19 个都属于"就要扎眼"</b>…</p>
```

结果：

```
选型台界面文案：index.html / style.css / app.js
合计 FAIL 0 / WARN 0
```

**闸门报了干净的 0。** 它连"999 个方案"（实际 35 个）都看不见。

这是第 ⑤ 类缺陷的教科书形态：**闸门与被测对象共享同一个盲区**。闸门的锚点是「已知的两处」，而缺陷长在锚点之外——所以闸门越是被认真维护（两条锚点守得很紧、还有 `--selftest` 变异测试），越会给人"这一类已经守住了"的错觉。

`--selftest` 也救不了：它变异的是**已在那两条锚点里**的内容，天然不可能发现"锚点集合本身太小"。

## 8. 闸门该怎么改

不是再加两条锚点（那样只是把「已知的两处」扩成「已知的四处的」，下一次仍然会漏）。要换判据层次：

**从「这些位置不许有数字」改成「凡面向用户的文本节点里有数字，必须要么在派生槽里，要么在白名单里被解释」。**

具体做法：静态解析 `index.html`，把所有**不在 `<!-- -->` 注释里、不在 `<script>/<style>` 里**的文本节点取出，匹配 `\d+(个|案|组|颗|段|条|张|屏|次|%)`，逐个判断：

1. 该节点是否被 `<span data-derived>` 包裹 → 通过（派生）
2. 否则查白名单：`{ 文件, 行, 理由 }`。白名单条目要求写清「这个数字为什么不需要派生」（例如"键盘快捷键 1/2/3，永不随数据变"）。
3. 两者都不满足 → FAIL。

这样 `:188`（"18 个"、"5"、"3"、"2"、"1"）和 `:197`（"19 个"）会立刻红，而 `:224` 的「1 2 3 切视口」这类真正固定的数字只要写进白名单就安静。

**代价**：白名单会逐渐变长，每加一条都要人解释。这反而是好事——它把"我为什么认为这个数字不会漂移"从脑子里搬到了文件里。

**为什么优先做这个而不只是修数字**：修数字是一次性的，`rail-hint` 已经漂移过至少一轮（30→35）且无人发现。改判据层次才能止住下一轮。
