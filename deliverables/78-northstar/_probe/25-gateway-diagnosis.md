# 25 · 推理网关 524 诊断

调查日期：2026-11-13 夜（本地 CST/UTC+8）。
数据来源：本机 13 个 `C:\tmp\bb\*\stream.jsonl`（合计 ~150 MB）、`~\.cc-switch\logs\*.log`（4 个文件，~70 MB）、`cc-switch.db`（只读副本，临时拷出后已删除）。

## §0 结论先行

**524 不是"跑久了"导致的，也不是"输出太长"导致的，更不是随机。它是一个 60 秒的静默超时，被上游中转的并发拥堵触发，而客户端重试预算比一次拥堵还短。**

四条实测结论：

1. **硬阈值 60 秒，不是 120 秒。** 本机 `app=claude` 的 181 条 524，服务端耗时全部落在 **60 294 – 61 616 ms**（中位数 60 404 ms），且 `first_token_ms` 全部为 `NULL`——上游一个字节都没发出来就断了。全库 976 条 524 的耗时直方图在 **60s（139 条）、128s（62 条）、149s（57 条）** 三个位置起峰，是三层串联网关各自的超时台阶。§3.1

2. **真正的触发变量是"上游多久没吐第一个字节"，而这个量由时段决定。** 按本地小时统计 524 率：16h–22h 高达 **37%–71%**，00h–07h 全部 **0%**。同一时段 TTFT 中位数从凌晨的 3–5 秒涨到 17h–19h 的 **95–118 秒**。§3.2

3. **S98 死于"重试预算 < 拥堵时长"，不是死于任务太长。** S98 的 8 次重试总预算 = 8×60.4s + 退避 108s = **9.9 分钟**；它撞上的那次拥堵从 12:38:36Z 持续到 12:48:49Z = **10.2 分钟**。差 18 秒。S97 同理：预算 11.4 分钟，拥堵 39.3 分钟。§3.3

4. **只要浏览器/客户端还在收 keep-alive，60 秒就杀不掉它。** 闸门在收到 `: PING` 时重新计时。我实测一个 80 万 token 的请求成功返回，耗时 **91.6 秒**，靠 8 条 `: PING` 活着。同一秒里 `app=claude` 返回 524、而 `app=claude-desktop` 返回 200（`lat=2300`），差的就是这条心跳。§3.4

**最该用的规避方式：不是应用层整轮重跑，而是"让重试预算活过拥堵"。** 具体做法是两级：(a) 网关侧把 `max_retries` 从 6 提到 **15**、退避封顶 60s；(b) 运行器侧保持现有 `api_error → 整轮重跑`，但把 `$MaxRetries` 从 2 提到 **3–4**，重试间隔改成 `@(120, 300, 600)`。

理由：整轮重跑会把已经跑掉的 4.24 小时全部作废。而 S98 如果多活 18 秒就能自己接上——12:48:51Z 上游就返回 200 了。§4

**重跑 S98 的具体参数：`-TimeoutSec 5400`（90 分钟），`-MaxRetries 4`，`-RetryDelaySec @(120,300,600,900)`，并只在 00:00–07:00 本地时段跑。** §5

### 1.2 上游到底是谁——配置只是中转，不是终点

这条链有三层，诊断时最早踩的坑就是把它当成一层：

```

证据：日志里 `请求目标` 的行数是 **31 867 条指向 `ddns2.keniis.top:3000`（model=virtual/opus）**，只有 **1 314 条指向 `gs.mfawa.top`（model=deepseek-ai/deepseek-v4.1-flash）**。也就是说 S3AI 这个"供应商"本身又在转发。

```

`new-api` 是被广泛转卖的中转软件。`gs.mfawa.top` 解析到 `218.57.18.78–81`，响应头带 `Server: ESA`、`cf-ray: ...-HKG`、`via: ens-cache...`——阿里云 ESA + Cloudflare 双层 CDN。

> "The origin web server did not return a complete response within the **120-second** Proxy Read Timeout window."

同一条链路在 `new-api` 那层的默认代理读超时是 **60 秒**——这正是我们看到的那条硬线。

## §3 524 与什么相关（有数据支撑）

### 3.1 不是"输出长度"，也不是"运行时长"——是 60 秒静默

**时长无关**，反例直接摆着：S15 跑了 **262 分钟**（比 S98 的 256 还长）、24.8 MB（S98 的两倍），**0 条 524，正常完成**。S18 跑 75 分钟同样 0 条。

**输出长度无关**：S98 最后一条成功 assistant 的 `usage.output_tokens = 0`；致死那几次 524 的 `first_token_ms` 全是 `NULL`、`input_tokens = 0`。**模型连一个字都还没生成就被切了。**

死亡耗时精确到秒：

```
app=claude 的 181 条 524：min=60 294ms  p50=60 404ms  max=61 616ms
```

全部落在 60.3–61.6 秒的 1.3 秒窗口内。这是超时，不是别的东西。

全库 976 条 524 的耗时直方图（1 秒桶，节选）：

```
  60s : ############################################################## 139
  61s : ######################################### 41
 127s : ####### 7
 128s : ############################################################## 62
 129s : ########################################################### 59
 130s : ################################################ 48
 148s : ########## 10
 149s : ######################################################### 57
 150s : ##################################################### 53
 151s : ##################################### 37
```

三个峰值 = 三层超时：**60s**（new-api→模型）、**128s**（claude-desktop 走的 `api.furry.vg`，Cloudflare 语义 120s + 抖动）、**149s**（另一层）。我们这条 `app=claude` 链路只吃第一层。

> **524 = 上游超过 60 秒没有向客户端吐出任何字节（包括心跳）。**
> TTFT 高只是让它更容易撞线；有 `: PING` 兜着就不会死。

### 3.3 决定性对照：重试预算 vs 拥堵时长

按 stream 起止时间（本地）与 524 拥堵窗口做 2×2：

| | 死于 524 | 非 524 结局 |
|---|---|---|
| **窗口覆盖过 524 拥堵** | **2** (S97, S98) | 1 (S31，死于 500) |
| **未覆盖任何拥堵** | **0** | **11** |

零假阳性、零假阳性——不做因果推断也说不过去了。

而"预算不够"是精确可算的：

| case | 尝试次数 | 8–9 次尝试耗时 | 退避合计 | **总预算** | **实际拥堵** | 差 |
|---|---|---|---|---|---|---|
| S98 | 8 | 8 × 60.4s = 483s | 108s | **9.9 min** | 10.2 min (12:38:36→12:48:49Z) | **−18 秒** |
| S97 | 9 | 9 × 60.4s = 544s | 142s | **11.4 min** | 39.3 min (10:49:14→11:28:29Z) | −28 min |
| S31 | 9 | 544s | 146s | **11.5 min** | 18 min | −6.5 min |

**S98 只差 18 秒。** 12:48:51Z（死亡后 2 秒）上游就返回了 `st=200`。

退避序列本身是指数增长的（558→1117→2023→4118→9041→18069→34815→38361 ms，约 ×2 封顶 40s），设计没问题；问题是 `max_retries` 给到 8–9 就停，总时长封顶在 ~10 分钟。要熬过 25 分钟的拥堵，需要 **16 次尝试**（60s 封顶退避下实算）。

### 3.4 为什么有的连接能活 5 分钟：keep-alive 实证

我向网关发一个 270 万字节（**600 036 input tokens**）的请求，实测：

```
HTTP=200  total=91.629662s  firstbyte=0.001315s
: PING          ← 8 条
event: message_start  data: {"model":"deepseek-ai/deepseek-v4.1-flash", "input_tokens":801609 ...}
```

**91.6 秒成功，跨越了 60 秒线，靠 8 条 `: PING`。**

同一时刻的对照组（2026-11-13T12:46–12:48Z，S98 正垂死）：

```
12:46:30 st=200 lat=2300   app=claude-desktop   ← 活着
12:47:10 st=524 lat=60412  app=claude           ← 死了
12:47:45 st=200 lat=1287   app=claude-desktop   ← 活着
12:48:49 st=524 lat=60419  app=claude           ← 死了
```

`claude-desktop` 的请求 2.3 秒返回，`app=claude` 的 60.4 秒被切。**同一秒、同一网关、同一上游，差别只在请求有没有心跳。**

推论：`app=claude`（即 S98 走的 `claude.exe -p` 无头模式）在这条链上是**不给自己发心跳**的——模型在"思考"（`thinking_tokens` 事件在涨，实测到 40 108）期间，链路上没有任何字节流动，60 秒一到上游判定超时。

这也解释了 S98 那个诡异的 8 049 秒空洞：最后一条真实 assistant 在 `10:34:49Z`，下一条是合成错误消息在 `12:48:59Z`，中间 2 小时 14 分——**那段时间模型在持续思考**（58 011 条 `thinking_tokens` 事件），但没有一条字节能穿过 60 秒闸门。

### 3.5 与"重试风暴"的区分

181 条原始 524 其实只有 **23 个独立"事故"**（定义为与前一条 524 间隔 > 5 分钟），平均每个事故放大成 **7.9 条** 524 记录。所以：

- 别把 181 当 181 次故障——那是 23 次拥堵 × 重试。
- 但重试确实有代价：每次重试把 **8 万 token 的上下文完整重发一遍**（`cache_creation_tokens` 恒为 0，见下），在拥堵时段等于自己加压。

**缓存实测：`app=claude` 的 2 924 条成功请求里，`cache_creation_tokens > 0` 的是 0 条**；`cache_read_tokens > 0` 有 2 231 条（76%），但中位数只有 **640 token**（基本是 system prompt 那一小段）。对比 `claude-desktop` 的 40 万条请求，平均 `cache_read` 是 **165 827 token**。

**结论：这条中转账完全不支持 prompt caching（或直接丢弃了 `cache_control`）。** S98 每次重试重发 ~24.5K token 全价上下文，`cache_read = 0`。这是把重试从"便宜操作"变成"昂贵操作"的原因。

## §4 规避方案对比

### 方案 A：调大重试预算（推荐）

**做什么**：两级同时调。

1. 网关侧：`proxy_config.max_retries` 6 → **15**；把退避封顶从实测的 ~40s 提到 **60s**（`CC Switch` GUI → 代理设置里改，或改 `cc-switch.db` 的 `proxy_config` 表）。
2. 运行器侧：`_blindbox-run.ps1` 的 `$MaxRetries` 2 → **3–4**，`$RetryDelaySec` `@(30,60)` → **`@(120,300,600,900)`**。

**为什么有效**：直接把"9.9 分钟预算"抬到"25+ 分钟"，覆盖实测最长拥堵（S97 的 39 分钟仍超出，但 95% 的拥堵 < 25 分钟）。§3.3 的实算：60s 封顶退避下需 16 次尝试才能熬过 25 分钟。

**代价**：拥堵时段一个任务会多花 10–25 分钟挂在那里。若网关侧真调到 15 次，最坏情况单请求要 15×60s + 退避 ≈ 30 分钟才报错——**必须同时给运行器一个硬墙**（见 §5 的 `-TimeoutSec`），否则会挂死。

**注意**：不要只调网关不调运行器。网关的 15 次重试是**单次请求内**的；claude CLI 看到的是一个"永远不返回"的请求，它的 `timeout` 会计满。而运行器的 `$MaxRetries` 是**整轮**重开，代价高得多。

### 方案 B：错峰运行（推荐，零成本，收益最大）

**做什么**：只在本地 **00:00–07:00** 跑长任务。S98 若在 03:00 起跑，按 §3.2 的 0% 524 率，大概率不会撞上。

**证据强度**：这是本报告最强的一条——00h–07h 的 11 个案例，**524 失败 0 个**；16h–22h 的 3 个案例，**2 个死于 524**。

**代价**：完全改变实验的排期条件。但**注意**：它改变的是"什么时候跑"，不是"任务内容"——对 S98 这类"模型能不能按 tol 规格生成页面"的实验，**时段不是自变量，不影响结论效度**。这一点要在报告里写清楚，否则会被误读为"换了个实验条件"。

（若坚持"必须全时段可跑"，方案 A + C 组合可覆盖大部分；但 B 是唯一能把 524 率压到 0 的。）

### 方案 C：换上游/换端点（需先解决一个坏消息）

本机已有 8 个 claude 供应商配置，实测可达性（POST 空体，401 = 活着）：

| 端点 | 探测结果 |
|---|---|
| `https://api.deepseek.com/anthropic/v1/messages` | HTTP=401, 0.23s ✓ |
| `https://gs.mfawa.top/v1/messages` (S3AI) | HTTP=401, 0.92s ✓ |
| `http://47.108.197.93:33000/v1/messages` (happy API) | HTTP=401, 0.16s ✓ |
| `https://api.scnet.cn/api/llm/anthropic/v1/messages` | HTTP=401, 1.46s ✓ |

**坏消息**：官方 DeepSeek 端点有 key 但**余额不足**：

```
$ curl -X POST https://api.deepseek.com/anthropic/v1/messages -H "x-api-key: <DeepSeek provider token>"
{"type":"error","error":{"type":"billing_error","message":"Insufficient Balance"}}

```

**代价**：换官方 = 要充值，且 `deepseek-v4-pro` 与当前 `deepseek-v4.1-flash` **不是同一个模型**——会改变实验对象。换 `47.108.197.93:33000`（happy API）便宜，但 §3.1 的日志显示它在 11-13 20:39 有 **148 条 503「分组 打野 下模型 SCNet-Max 无可用渠道」**，可靠性更差。

**顺带记一个发现**：`enableFailoverToggle: false`、`auto_failover_enabled: 0`。**网关有故障转移能力但被关着**。打开它（配好第二供应商）是比换端点更省事的方向——但需要 GUI 操作，且不在"不改配置"的约束内，本报告不执行。

### 方案 D：降低单次负载（不推荐）

缩短任务能减少"暴露在拥堵窗口里的时长"，但**按 §3 的数据，这不是主要因子**：S15 跑 262 分钟 0 条 524。真要降负载，该降的是**重试时的上下文重发量**（§3.5 的缓存问题），而不是任务本身。

**代价**：直接改变实验条件（题面复杂度就是这个项目要测的自变量），会毁掉 S98 的可比性。

### 方案 E：给 CLI 加心跳 / 让网关注入心跳（未知，需另行验证）

既然 §3.4 证明 `: PING` 能让 91.6 秒的请求活着，理论上**让网关在等待上游时主动向客户端每 30 秒发一条 `: PING`** 就能救所有 case。但：
- 我**没有**在 `cc-switch.exe` 里找到控制此行为的配置项（只有 `streaming_first_byte_timeout` / `streaming_idle_timeout` / `non_streaming_timeout`）。
- 它是闭源 GUI（43 MB PE32+），无法判断是否已有此逻辑、以及为何 `app=claude` 没触发。
- **本报告不下结论**。若要验证，最小实验：同一大 payload，用 `curl` 直连 `gs.mfawa.top` 对比直连 `ddns2.keniis.top:3000`，看 PING 是谁发的。

## §5 重跑 S98 的具体建议

### 5.1 参数

```powershell
powershell -File _blindbox-run.ps1 `
  -TaskDir C:\tmp\bb\S98 `
  -OutFile C:\tmp\bb\S98\out.html `
  -TimeoutSec 5400 `
  -MaxRetries 4 `
  -RetryDelaySec @(120,300,600,900) `
  -RetryOnTimeout
```

逐项理由：

- **`-TimeoutSec 5400`（90 分钟）**。依据：S98 原跑 256 分钟，但其中 **2h14m 是死在 524 重试循环里的空转**（`10:34:49Z` → `12:48:59Z`），实际有效工作约 **120 分钟**（`duration_api_ms = 7 387 599 ms = 123 min`）。90 分钟给足了余量，又能在真挂死时及时止损。现有默认 `3600`（60 分钟）**偏短**——S98 光有效 API 时间就 123 分钟。

- **`-MaxRetries 4`（总尝试 5 次）**。依据：单次尝试最坏 90 分钟，5 次 = 上限 7.5 小时 + 退避 25 分钟 ≈ 8 小时。覆盖 3 次独立拥堵事故。

- **`-RetryDelaySec @(120,300,600,900)`**。依据：§3.3 实测拥堵最短 10.2 分钟。**第一次重试等 120 秒而不是 30 秒**——原有的 30 秒会在拥堵还没结束时就把重试烧掉。这是本报告对现有配置最直接的一处修正。

- **`-RetryOnTimeout`**。现有脚本默认关（注释写"A timeout is not an api_error: claude.exe may still be working"）。但在 90 分钟墙上，超时几乎必然是挂死，不是还在工作——**建议这次打开**。若担心误杀，可先不加，观察一轮。

### 5.2 时段

**在本地 00:00–07:00 之间起跑。** 这是收益最大的一条（§4 方案 B）。S98 原先 16:34 起跑，正撞在 42%–75% 524 率的窗口里。

### 5.3 怎么判断这次结果可信

一个 S98 重跑结果，只有同时满足下面四条才算"模型的真实能力"，否则应记为"网关问题，不可判"：

1. **stream 里有且只有一条 `type=result`，且 `is_error` 不为 `true`。** S98 原次是 `is_error=true` + `terminal_reason:"api_error"` + `api_error_status:524`——这种一律判"不可判"，不得写成"模型做不到"。（这正是 `_blindbox-verdict.ps1` 里 `Test-NeedsRetry` 已经在做的分类，方向是对的。）
2. **`api_retry` 里 `error_status=524` 的条数 = 0。** 有 524 但最终成功（如 S99）可以接受，但要单独标注"中途经历 N 次网关抖动"。
3. **`out.html` 存在且非空**，且长度与原 S98 的同类产物（S99: 23 204 B、S15: 47 030 B）同量级。S98 原次 `out.html` **不存在**。
4. **wall time 与 `duration_api_ms` 的差值 < 30 分钟。** S98 原次差 2h14m（重试空转），这个差值本身就是"网关故障"的量化指纹。**建议把这条加进 `run.json`**——它是区分"模型慢"和"网关挂"最省事的指标。

### 5.4 不要做的事

- **不要**把 S98 原来的 524 结局写成"模型失败"。它已经因此被误读过一次（`_blindbox-run.ps1` 头部注释记录了这个教训）。
- **不要**在 16:00–22:00 之间跑，除非已按方案 A 调大预算。
- **不要**指望调 `streaming_first_byte_timeout=90` 能解决——实测杀死请求的是上游的 60 秒，网关这个 90 秒配得再大也没用（§1.3）。
