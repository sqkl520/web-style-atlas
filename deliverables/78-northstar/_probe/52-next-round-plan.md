### 1.1 第 3 条要修正：那三个「兜底值」大部分是**真的**

我原以为这三处是「抽不到就编一句」，是潜伏缺陷。实测当前触发数：

```
「全直角 0」: 30/35 案
「无边框线条…」: 0/35 案
「无阴影」: 22/35 案
```

**30/35 案的圆角真的全是直角，22/35 案的阴影真的没有。** 这些不是「抽取失败」，
是真实的设计结论。

### 1.1.1 逐案查完：三处兜底当前**没有一处是错的**

先查 `radiusWhy` 在 30 案里的分布：

```
×21  "border-radius 只出现过 0"
×9   "该案 CSS 里 0 处 border-radius，所有元素一律直角"
```

看起来后 9 案的依据是「我没找到」，可疑。于是逐案核实那 9 案
（S04 S07 S08 S21 S31 S32 S33 S34 S35）的实际源码：

```
$ for id in S04 S07 S08 S21 S31 S32 S33 S34 S35; do
    grep -c "border-radius" prototypes/$id-*/style.css
    grep -c "border-radius" prototypes/$id-*/index.html
  done
→ 全部 0 处（CSS 和 HTML 都是 0）
```

**9 案确实一处 border-radius 都没有。「全直角 0」是正确结论。**

再查 `shadow === "无阴影"` 的 22 案里，有没有「有 box-shadow 却被判无阴影」的：

```
$ grep -c "box-shadow" prototypes/*/style.css | 只有 S08 有 1 处
$ grep -n "box-shadow" prototypes/S08-*/style.css
2:  物理机制：等距叠层亚克力板，透光相乘。全站零背景模糊、零渐变、零 box-shadow。
```

**那是一句注释，说「全站零 box-shadow」—— 它恰恰证明了无阴影是对的。**
S16 在 HTML 里有 1 处，也是正文文案（「页面里没有一处 box-shadow」）。

线宽那一处「无边框线条」**当前 0 案触发**。

### 1.1.2 所以第 3 条要降级

| 兜底 | 当前触发 | 输出是否正确 |
|---|---|---|
| 圆角「全直角 0」 | 30 案 | ✅ 逐案核实，全部正确 |
| 阴影「无阴影」 | 22 案 | ✅ 抽查正确（命中的两处是注释/文案） |
| 线宽「无边框线条」 | 0 案 | — 潜伏，无实例 |

**结论：这是潜伏缺陷，不是活跃缺陷。** 它值得记一笔，但不该排成最高优先级。

我原先写这一节时把它当成了「真缺陷」并排成任务 A，那是错的 ——
**在规划阶段就把一个潜伏问题当成了活跃问题**。这个错误本身值得记下来。

### 1.2 第 6 条：不能用规则名个数回答

`check-prompts.mjs` 有 53 条断言、25 个变异。但 40 号报告的 38 条用的是另一套编号
（它的 T-11 对应这边的 `typescale-degraded` 一族）。所以「38 条做了几条」必须建映射表
才能回答，数个数会得出错误答案。

## 二、任务拆分

按「对产品的价值 ÷ 风险」排序。冲突标注：`[同文件]` 表示会和别的任务改同一个文件。

### 任务 A（原定最高，**已降级**）：给「失败空」与「合法空」造判据

**为什么降级**：§1.1.2 逐案查完 —— 三处兜底可以触及的 52 个案例里，
**没有一案的输出是错的**。所以「造判据」现在是在防一个**尚未发生**的问题。

**它仍然值得做，但理由变了**：不是「现在有错」，而是「现在分不清，
所以下次抽取器出问题时，闸门不会响」。这是预防性工作。

**做什么**（如果做）：
1. 让 `clean-dna.mjs` 的三个 verdict 函数在返回文本之外，多返回一个**结构化状态**：
   `found`（找到声明）/ `absent`（确认为无）/ `unreadable`（读不到）。
2. `absent` 与 `failing` 的判据要用**证据**：比如 `absent` 要求「CSS+HTML 里
   该属性出现 0 次」，`unreadable` 是「出现了但我解析不了」。
3. 加断言：`unreadable` 在 35 案里必须为 0；一旦出现就 FAIL。

**验收**：35 案全部落在 `found` 或 `absent`，`unreadable` = 0。
**风险**：中（改 `clean-dna.mjs` 输出结构）。
**角色**：执行 + 红队（红队要问「你怎么知道你判的 absent 是真的 absent」）。

### 任务 B：内容层可复现性（产品价值最直接）

**为什么要做**：这是唯一一项**用户直接感知**的。其余全是内部质量。

**做什么**：
1. 先查清跑一次已填形态盲测的真实成本（`20-reproducibility.md` §2 有数据，
   但那是空槽形态；已填形态要额外传 biz/action）。
2. 如果成本可接受（比如 1 案 20 分钟），挑 2 案各跑 2 次，比对内容层。
3. 如果成本不可接受，**明确写出来**，并给出「最低成本的验证方式」。

**产出**：实测数据或成本论证。
**验收**：要么有数据，要么有说服力的「为什么现在不能做」。
**风险**：**高**。要跑沙箱、花钱、花时间。**必须先得到用户确认才能跑。**
**角色**：检索（查成本）+ 执行（跑）。

### 任务 C：`xref` 主题从枚举改成结构判定

**为什么要做**：现在是 6 个主题的白名单，补一个漏一个是无底洞。

**做什么**：
1. 设计一个不依赖枚举的判据：从硬约束段的每条里提取「主题词」，
   看引用上下文是否提到某个主题词、而被引条目完全不含它。
2. 难点：中文没有空格，主题词提取不可靠。要先试「按条目的前 6 个字做锚」这种近似。
3. 如果做不到可靠，就**明确说做不到**，并保留白名单 + 在注释里写明「新增主题要同步这里」。

**产出**：要么是更好的判据，要么是「为什么枚举是当前最优」的论证。
**验收**：新判据在当前 35 案零误报，且能拦住 `51` 号报告里那两个绕过。
**风险**：低（只改闸门）。
**角色**：执行 + 红队（红队负责打穿新判据）。

### 任务 D：`o.unit` 修病句

**为什么要做**：定时炸弹，零调用方时无害，一旦有人用就出病句。

**做什么**：
1. 查 `unit` 的所有调用方（预计 0）。
2. 三个方案选一：让 unit 含量词 / 加 classifier 参数 / 直接删。
3. 改完确认 35 案提示词零变化。

**产出**：小改动 + 零变化验证。
**验收**：`node prototypes/_prompts/build-prompts.mjs` 后 `git diff` 为空。
**风险**：极低。
**角色**：执行。

### 任务 E：`h1Size` 与 `radius` 的死字段处理

**为什么要做**：闸门 88.6% 的注意力花在 `radius` 上，而它对 31 案无效。

**做什么**：
1. `h1Size`：决定删还是留。删要同步改 `KEY_FIELDS`。
2. `radius`：**不删**（4 案真的在用），改成在 `KEY_FIELDS` 里注明它只对 4 案有效。
3. 可选：给 `KEY_FIELDS` 加一条自检 —— 声明的字段必须真的影响输出（哨兵法常态化）。

**产出**：决策 + 改动。
**验收**：季度体检全过。
**风险**：中（改生成链）。
**角色**：执行 + 验证。

### 任务 F：建 40 号报告的编号映射表

**为什么要做**：回答「38 条做了几条」，现在没人答得出。

**做什么**：读 40 号报告，逐条对照 `check-prompts.mjs` 的规则名，建映射表。
**产出**：一张表 + 「实际做了 N 条」的结论 + 「剩下哪些值得做」。
**风险**：无（只读）。
**角色**：检索。

## 三、不该做的

1. **不要为「clean-dna 三处兜底」直接改措辞。**
   30/35 案的「全直角 0」是真的。改措辞会让真实的结论也变成「未能确定」，
   那是在用一个错误换另一个错误。**先做任务 A。**

2. **不要加更多 `KEY_FIELDS` 类断言。**
   `43` 号报告已经证明「字段非空」这条路上次是错的。除非任务 A 给出了区分方法。

3. **不要在没有用户确认时跑盲测。**
   任务 B 需要花钱花时间，必须先问。

4. **不要继续试图用后台 agent。**
   11 次派发只成功 1 次，而那 1 次跑了 23 分钟没产出。

## 四、建议顺序（按 §1 核实后重排）

```
任务 C（xref 结构化）   ← 唯一有真实缺陷可修的高价值项
任务 D（unit 病句）     ← 小而确定
任务 F（映射表，只读，随时可并行）
任务 E（死字段）
任务 A（造判据）        ← 降级为预防性工作
任务 B（盲测）          ← ⚠️ 需要用户先确认
```

**排第一的是任务 C**，理由：`51` 号报告已经证明 xref 判据有**两个可执行的绕过**
（⑪ 圈号、圆角引用），那是活跃缺陷。而任务 A 的前提（三处兜底有错）已被推翻。

**这一轮规划最大的收获不是计划本身**，是发现我差点把一个潜伏问题当成活跃问题、
并把它排成了最高优先级。如果直接按原计划做，会花大量精力去修三处**当前正确**的代码。
