K1+K2 合起来是**最要命的一条**。`compare.mjs` 最多输出 7 行（第 7 行「stroke」仅在原型有 SVG 线宽时才生成，所以**分母本身在 6 与 7 之间漂**——实测 S07 是 7、S26 是 6）。这 7 行里：

- **2 行恒真**（栏数 `:56-57`、主轴比例 `:77`）；
- **3 行比对的是提示词里字面给出的数**（字号倍 35/35 有、线宽列表 35/35 有、色板 35/35 有）——但「字面给出」不等于「送达到」，S24/S31 的色板被 `MAX` 截断（K6），那 3 行的分母在那些案子上是**假的**；
- **2 行有真余量**：线宽 border 集合（能少不能多）、图片位（只要 `>0` 就过，实测 9 案全部 ≥5）。

也就是说，最理想的情况下「7/7」=「4 个真判据全过 + 3 个照抄」；若该案原型没有 SVG 线宽，分母降到 6（实测 S26），**同样叫完成却少判一条**；若该案色板被截断（S24/S06），配色那行的 `want` 本身是残缺的，「通过」没有意义。

所以本文的工作包不是「把 3 案扩到 35 案」，而是**先把尺子修到能失败**，再谈覆盖。

## 一、规模：35 案全测还是抽样

### 1.1 判定：不抽样。35 案全测，但**分两级**

理由不是「35 太小」，而是成本结构变了。实测（§六）：

- 一次生成 = **24.1M token / 43 分钟中位**（16 个盲测 agent 的实测均值）
- 一次对账 = **3.5 秒/页 + 无头 Chrome 启动 0.5 秒**（实测 `measure.mjs` 单页 3.5s；`Browser.launch` 536ms）

对账侧便宜到没有理由抽样：35 案全量对账约 **2.5 分钟**（假定浏览器复用，见 D2）。
贵的只有生成侧，而生成侧**必须**抽样——因为一次生成 24M token，35 案 = 842M token。

**所以真正的规模问题是「生成侧抽几案」，不是「对账侧抽几案」。**

### 1.2 生成侧的抽样规则（可计算）

样本必须让**每一条会被判的量都至少能在若干个案子上失败**。上一轮的 3 案是「有硬错史的三案」，那是按缺陷史抽的——而缺陷史不是代表性。

规则用四个二值特征分层（全部可从 `prompts.js` 与 `dna-clean.json` 机器算出）：

| 维度 | 判定 | 为什么它决定了「能不能测出来」 |
|---|---|---|
| **P**（色板大小） | 提示词 hex 数 ≥ 8 → P8，否则 P7 | 色板越大，`MAX=9` 的截断风险越高（`clean-dna.mjs:1003`）。实测仍有 **9 个色被截**（S06/S24/S31） |
| **R**（比例是否字面给出） | 机制句含 `数字:数字` → R1 | 只有当比例在提示词里**字面存在**，「主轴比例」才有意义可比；否则是拿模型没接到的约束判它 |
| **C**（栏数是否字面给出） | 机制句含 `数字栏`/`数字列` → C1 | 同上。实测 35 案只有 **12 案**机制句带栏数（S01/S04/S07/S15/S16/S19/S21/S22/S24/S25/S27/S28） |
| **D**（度量器是否可判） | 骨架 2–4 轨 → D1 | 超出 2–4 轨的案子，`measure.mjs` 的启发式直接失效（S27 得 0 轨） |

实测分层结果（`node` 现算，见 §五 WBS-2 的产出）：

```
P7/R0/C0  14 案  S02 S08 S09 S11 S12 S13 S18 S29 S30 S31 S32 S33 S34 S35
P7/R0/C1   9 案  S01 S04 S15 S16 S21 S22 S25 S27 S28
P7/R1/C0   4 案  S03 S05 S10 S20
P7/R1/C1   1 案  S07
P8/R0/C0   4 案  S06 S14 S17 S23
P8/R0/C1   1 案  S19
P8/R1/C0   1 案  S26
P8/R1/C1   1 案  S24
```

**抽样规则（可机器执行）**：取全部 8 个非空层各 1 案，层内按「可测性得分」取最高。得分定义（每个 +1，可从 §1.2 四特征与基线表算）：
`骨架2–4轨` + `线宽级≥2` + `SVG stroke≥1` + `R` + `C` + `色板≥8` + `图片位≥8`。

层内排序规则（必须写死，否则不可复现）：**得分降序 → 图片位数降序 → 案号升序**。第三档是为了打破并列（S28/S15/S22 都是 5 分，靠图片位 15>8>8 分出 S28；若仍并列则取案号最小者）。

按此规则算出的 8 案（每层一案，可复现）：

| 层 | 选中 | 得分 | 层内次优（说明并列有多近） | 选它的理由 |
|---|---|---|---|---|
| P7/R0/C0 | **S09** | 4 | S11(4) S30(3) | 骨架 3 轨；SVG **三级**线宽（2.00/3.50/3.60）——Chrome 取整后仍可区分；11 个图片位 |
| P7/R0/C1 | **S28** | 5 | S15(5) S22(5) | 15 个图片位（全库最多）；机制句 3 条栏数声明（16/7/2）——栏数是**唯一能证伪「照抄」的量** |
| P7/R1/C0 | **S03** | 4 | S20(4) S10(4) | 比例字面在（`264:524:540`）；是上一轮的对照组，**保留它才能把两轮结果接上** |
| P7/R1/C1 | **S07** | 5 | （唯一） | 上一轮满分对照组；机制句 2 栏 + 3 栏 + 比例三样都有 |
| P8/R0/C0 | **S14** | 5 | S23(5) S06(4) | 色板 9；骨架 4 轨；机制句描述的是**内容排布**（`compare.mjs:65-68` 自己指出），正好测「语义不成立时度量器会不会误判」 |
| P8/R0/C1 | **S19** | 6 | （唯一） | 得分最高；色板 9；机制句 4 栏声明 |
| P8/R1/C0 | **S26** | 4 | （唯一） | 色板 9；机制句只有比例没有栏数 |
| P8/R1/C1 | **S24** | 5 | （唯一） | 色板 9 且**截掉 4 个色**（实测）；8 级 SVG 线宽；机制句 8 栏 + 2 栏 + 比例 |

**为什么这个规则能代表全库**：它不取「有代表性的」，取**覆盖全部非空单元格**的。8 层覆盖了 `prompts.js` 能算出的全部分支；每一层内部按固定的三档排序取第一，因为得分高的案子**更可能暴露缺陷**——上一轮的教训恰恰是「只测了容易过的案子会得到一片假绿」。

**注意 S17 落选**：它属于 P8/R0/C0，得分 4，输给 S14 的 5。这是规则的结果，不是我认为 S17 不重要。若要保留上一轮全部三案做纵向对比，应把 S17 作为**第 9 案**附加，并明确记「这是对照组，不是分层样本」——两者不能混在一个通过率里。

**已知的不可消除偏差**（必须写明，不许假装没有）：
- 8/35 案里没有一案的**骨架**是 5 轨以上。5 轨以上的容器（S07 的 `.plate-grid` 7 轨、S23 的 `.wall` 37 轨，见 `S23.../style.css:151`）**永远测不到**，因为度量器按设计排除 5 轨以上（`measure.mjs:75` 的 `tracks > 4` 直接 `return`）。这些容器恰恰是本仓库的「签名结构」——S23 的 37 轨是它整案的辨识点。
- 这 8 案全是 `minPics ≥ 5`。`minPics ≤ 2` 的 5 案（S31–S35）测不到——而它们恰好是 `FAIL=3` 的五案（`77-quarters/2026-11-10.md` 的闸门行）。

## 二、盲测怎么保证是盲的

### 2.1 上一轮的真实做法（不是自欺，但也不是隔离）

我没有只看 REPORT 的措辞，而是直接读了 16 个生成 agent 的完整 transcript（`~/.claude/projects/D--Web-style/f932d1d4-.../subagents/agent-*.jsonl`）。事实：

1. **每个 agent 的 system prompt 里有一条硬禁令**，原文：
   > `You must NOT read any files in D:/Web/style/prototypes/ — not S17*, not any other scheme... Reading the source would invalidate it.`
2. **禁令被遵守了**：16 个真正写出 `out-*.html` 的 agent，对 `prototypes/S\d\d-*`（案件目录）的 Read/Bash/Grep 访问次数**全部为 0**。
3. 另外有 20 多个 agent 读了 `prototypes/`——但它们是**修闸门的 agent**，无一产出 `out-*.html`。两类 agent 可干净分开。

**所以上一轮的「盲」是真的，但它是「靠指令约束 + 事后可核查」，不是技术隔离。** 区别很重要：它成立是因为 transcript 可审计，不是因为它物理上做不到。

### 2.2 但隔离有真实漏洞（三条，都已实测）

| 漏洞 | 实测证据 | 后果 |
|---|---|---|
| **V1** 工作区里存在完整仓库副本 | `.claude/worktrees/agent-*/` 四份，每份 **191 MB**，含 `prototypes/S07-slate-ink-contents` 等全部 35 案 | agent 只要 `ls .claude/worktrees/` 就能读到原型。上一轮无人这么做，但**没有任何东西阻止它** |
| **V2** 输出目录就在 `deliverables/74-q7/`，同目录有 `prompt-S*.txt` 与**上一轮所有 `out-*.html`** | 第二轮 agent 的 `out-S17-v2.html` 与第一轮 `out-S17.html` 同目录 | 一个 agent 若 `ls`，会看见别人的成品。实测第二轮 agent 对 `out-S17.html`（上一轮）访问 **0 次**，但它们读了**自己**的 `out-S17-v2.html`（35 次）——那是自查，正常 |
| **V3** 模型会在中途被换掉，且不影响「盲」但影响「固定模型」 | `agent-ad676d`：第 938 条消息从 `SCNet-Max` 切到 `deepseek-ai/deepseek-v4.1-flash`，而它的成品在第 101 条就写完了。另 `ad8498` 切了两次 | 计划 `:254` 要求「固定同一个模型」，实际上 **1/16 的生成 agent 中途换了模型**，且 transcript 里能看到 |

### 2.3 真正的隔离手段（WBS-3 的内容，这里只给判据）

三级，按强度递增，**每一级都有可机器判定的验证**：

**L1 目录级隔离（最低可接受）**
- 建 `deliverables/78-northstar/_blind/<case>/`，里面**只放** `brief.txt`（提示词）与一个空的 `out/`。
- 不给 agent 仓库路径，只给它这个目录的绝对路径。
- **验证**：跑完后 `find _blind/<case> -type f` 的清单必须**恰好**是 `brief.txt` 与 `out/index.html`。任何多出来的文件 = 隔离失败。

**L2 权限级隔离（推荐）**
- 用 `--add-dir` 语义或子进程 cwd 把 agent 限制在 `_blind/<case>/`，并**不给它 Bash**（只给 Write）。
- **验证**：transcript 里 `tool_use` 的 `name` 集合必须 ⊆ `{Read, Write}`，且每个 `Read` 的 `file_path` 必须以 `_blind/<case>/` 开头。这一条**可以从 jsonl 机械检查**，本文 §2.1 就是这么查的。

**L3 物理隔离（最强，成本最高）**
- 把 `brief.txt` 复制到仓库**外**的临时目录（如 `%TEMP%/blind-S07/`），在**另一个 OS 用户**或另一台机器上跑。
- **验证**：仓库侧 `git status` 在整个盲测期间零变化（除 `_blind/` 下新增的 out）。

**推荐组合：L2 + L3 的验证部分。** 理由：L1 挡不住「agent 记得仓库路径」（它会猜 `D:/Web/style/prototypes`）；L3 最贵但只需一次。L2 的 `tool_use` 白名单检查是**唯一能事后证明没偷看**的手段——而它零成本。

### 2.4 必须记进验收的一条

**盲测的隔离声明必须附 transcript 路径，否则无法复核。** 上一轮 REPORT 只写了方法（`74-q7/REPORT.md:4`），没写 transcript 在哪。我是靠翻 `~/.claude/projects/` 才核出来的——这不是可复现的做法。

## 三、6 个可度量之外还要量什么

### 3.1 先回答「6 个够不够」：不够，而且现状比「不够」更糟

我把 35 案逐案实测了 `measure.mjs` 的 6 个量（见 §五 WBS-1 产出）。现状：

| # | 计划里的量（`MASTER-PLAN:21`） | `measure.mjs` 实际行为 | 35 案里能失败吗 |
|---|---|---|---|
| 1 | 栏数 | 只报不判，`ok: true` 写死（`compare.mjs:56-57`） | **不能** |
| 2 | 主轴宽 | 计划说「主轴**宽**」，度量器量的是「主轴**比例**」；且只报不判（`:77`） | **不能** |
| 3 | 最大标题字号 | 量的是**比值**（h1/body），±20% 容差；提示词 35/35 字面给了倍数 | 能，但测的是照抄 |
| 4 | 正文比 | 同上（与 3 是同一个数） | 同上 |
| 5 | 线宽集合 | border 必须全含；SVG 只报不判（`:108`） | 能。但实测 9 案里 border 只测出 `[1.00]`，**真正的线宽体系在 SVG 里** |
| 6 | 图片位数 | `imgVisible > 0` 即通过（`:126`）——**完全没有比对提示词写的 `minPics`** | **不能**：提示词写「至少要 8 个」（`prompt-S03.txt:19`），判据只要 `>0`。实测 9 案 imgVisible 全部 ≥5，S19 甚至原型 11 个、产物 6 个，判据仍给通过 |

**「主轴宽」这一整条从未被测过。** 计划写的是「主轴宽」（`MASTER-PLAN:21`），`probe.mjs:283` 确实算了 `axisWidth`，但 `measure.mjs` 算的是 `mainRatio`（比例），两者不是一回事。而 S03 那次失败（`74-q7/REPORT.md:52-62`）讨论的正是**比例**——所以「主轴宽」这个量在整条链上**既没被算也没被判**。

### 3.2 建议新增的 6 个量（每个都必须能从 CSS/DOM 机械算出）

| 新量 | 定义（机械可算） | 怎么算 | 为什么它能失败，且测的是「复刻」不是「照抄」 |

## 三之二、顺带实测到的两个工具缺陷（影响成本估算，先记在这里）

这两条不属于「北极星」本身，但它们让上面的成本数字差 **7 倍**，所以必须先记账。

### D1　`measure.mjs` 不复用浏览器：每页各起一次 Chrome

`measure()` 内部 `Browser.launch()` / `browser.close()`（`measure.mjs:43, 219`）。实测一次 `measure()` 3.5 秒里，Chrome 冷启动占 0.54 秒、`goto` 的 `settleMs:1500` 硬编码休眠占 1.5 秒。**跨页复用浏览器可以把启动摊薄到 0**，实测连续三页 7.6 秒（2.5 秒/页）。这是 `compare.mjs` 每次对账都慢的原因（三案 42 秒）。

### D2　进程在浏览器关闭后仍挂 22.7 秒才退出

**实测**：`node measure.mjs <一页>` 的 `real` 时间是 **26.1 秒**，而脚本自己在页面里打印的耗时段只有 **3.4 秒**。差额 22.7 秒全在进程退出阶段。

**定位**：`Browser.close()`（`cdp.mjs:119-125`）做了 `Browser.close` → `ws.close()` → `proc.kill()` → `rmSync(dir)` → `sleep(300)`，但**没有销毁 `proc.stderr`**。实测加一行 `b.proc.stderr.destroy()` 后，同一命令 **1.3 秒**退出（26.1s → 1.3s，**20 倍**）。

**为什么这条要紧**：`quarter.mjs` 的渲染步骤要跑 35 案 × 3 档 = 105 次 Chrome。若每次多挂 22.7 秒，就是**多 40 分钟纯等待**。而 `deliverables/77-quarters/00-Q4-REPORT.md` 记的「渲染实测十几分钟」很可能已经包含这笔账。

**修法**：`cdp.mjs:119` 的 `close()` 里加 `try { this.proc.stderr.destroy(); } catch {}`。这是一行改动，但 `cdp.mjs` 是 vendor 文件（`render-scheme.mjs:18-22` 说明它来自 `tools/taste-skill`），改动需要记进 vendor 差异，否则下次 vendor 覆盖会丢。

**未验证**：我没有跑完整的 `quarter.mjs --render` 来实测「省下 40 分钟」这个推算。上面的 26.1s→1.3s 是单页实测。

## 四、判读纪律：把「该怪谁」写成可执行规则

### 4.1 现状（`compare.mjs:158` 只有一条正则）

```js
const promptDefect = allFail.filter((f) => /未提|未给|未给色值/.test(f.note));
```

这条规则的问题是：它靠 `note` 字符串里有没有「未提/未给」。而 `note` 是**每条判据自己拼的**，三条 note 都是三元表达式，例如 `74-q7/compare.mjs:83`：

```js
/字号|字阶|font-size|标题/i.test(prompt) ? '提示词有字号约束' : '提示词未提字号'
```

也就是说，**这个「该怪谁」的判据实际的输入不是「提示词有没有这条约束」，而是「prompt 里有没有出现『字号』这两个汉字」**。实测 35/35 份提示词都含「字号」，所以字号那一行的 note **恒为**「提示词有字号约束」——该行一旦失败，永远落进「模型偏差」。

同理线宽（`:100`，35/35 含「线宽」）。所以真正可能出「提示词缺陷」的只有配色那一行（`:123`），以及图片那一行永远输出「有图片且可见」（不匹配正则，恒落模型偏差）。

**实测印证**：本次跑 `compare.mjs`，S17 缺 `#D6C9AC` 被判为**【模型偏差】**——而 `REPORT.md:63-81` 的结论是**提示词缺陷**（7 色上限截断）。工具的输出和报告的结论**互相矛盾**。

### 4.2 可机器执行的判读规则（三分类）

对每个失败项，按**提示词里有没有一条可机械定位的指令**分三类：

```
输入：case_id, metric, want, got, prompt_text, provenance_json
输出：A(提示词缺陷) | B(模型未执行) | C(度量不可信)
```

| 判定 | 条件（全部可机器算） | 处置 |
|---|---|---|
| **A1 指令缺失** | `metric` 对应的正则在 `prompt_text` 里匹配数为 **0** | 回流数据层（补提示词），**该案本次不计分** |
| **A2 值被截断** | metric=配色 且 `prompt_hex_count < :root_hex_count`（`clean-dna.mjs` 的上限生效） | 回流 `clean-dna.mjs` 的 `MAX` |
| **A3 值不可定位** | metric 的 want 值在 `dna-provenance.json` 里 `status == 'missing'` 或 `display-only` | 回流机制句（`check-provenance` 已能抓） |
| **B1 有指令未执行** | 正则在 prompt 里匹配数 ≥1，且该值**不是**被截断的（不是 A2/A3） | 重跑一次同案；两次都失败才记 B |
| **C1 度量不可信** | 第 1 步的「元素选取」在原型与生成物上选中了**不同语义的元素**（如一个选到 `HEADER`、一个选到 `.row`） | 该量本次弃权，记 WARN，不计入分母 |

**C 类的具体判据**（这是最容易漏的，也是 K3 的根源）：
选定元素的 `selector` 里若含 `header`/`footer`/`nav`，或该元素 `innerText.length` 小于全库中位数的一半 → 判 C 类。

### 4.3 「6 个量对了 5 个」怎么判

**不判通过，也不判失败，判「样本量不足」。** 规则：

1. 先把该案的 6 个量按 §4.2 分成 `可判` / `弃权(C)`。
2. 分母 = 可判量数，不是 6。
3. 若可判量数 **< 3**：该案**结论为 `INCONCLUSIVE`**，不参与通过率统计。
4. 若可判量数 ≥ 3：`pass_rate = 通过数 / 可判数`，且**必须同时报出分母**。

**实测验证这条规则的必要性**：`compare.mjs` 给 S26 报的是 **6/6**，因为 S26 的 `wantSV.length === 0`，那一行整条不生成（`compare.mjs:101`）。也就是说**同一个工具对不同案子报的分母不同**（S07=7，S26=6），而报告里写「7/7」时没人知道分母怎么来的。

### 4.4 哪里会误判（必须写进交付）

| 误判 | 条件 | 表现 |
|---|---|---|
| **把 C 类当 B 类** | 度量器选中页脚而不是版心 | S23 实测：`want [0.417,0.583]` vs `got [0.933,0.067]`，工具报「只报不判✓」，若有人手工判会判成模型把版心做错——实际是量了页头 |
| **把 A2 当 B** | 色被 `MAX=9` 截断，模型忠实执行了 9 色 | S17 第一轮：模型用了列表里全部 7 色，被判「缺 1 色」= 模型偏差 |
| **把 A3 当 A1** | 提示词里有这个数，但它在实现里不存在（S07 的 `0.5px`） | 会去补一条**本来就错**的约束。`check-provenance` 的 `missing` 才是正确标签 |
| **分母漂移** | 某量的 `want` 为空时该行不生成 | 见 §4.3 |

- **依赖**：WBS-3
- **风险**：模型中途被换（实测 1/16 发生）。验收 3 会把这种事抓出来并**作废该案**，不静默接受。

## 六、与 MASTER-PLAN 的分歧

### 分歧 1「3 案复刻验货能证伪提示词有用」——只能证伪，不能证实

计划 `:20-22` 说这是「唯一能证伪『提示词真的有用』的动作」。

**证伪可以，证实不行。** 一条否定命题（「提示词有用」）需要 35 案都过；一条肯定命题（「提示词没用」）一案失败就够。所以 3 案（或 8 案）**只能发现缺陷，不能证明产品好**。

更具体地：上一轮说「三案全部 7/7」（`74-q7/REPORT.md:159`），按 §三的分析，那个 7/7 里有 2 行恒真（`compare.mjs:56-57, 77`）、3 行测照抄。**它连证伪的能力都很弱。**

建议改口径：这个动作的名字应该是**「提示词缺陷猎捕」**，产出是「找到 N 个缺陷」，不是「通过率 X%」。

### 分歧 2「6 个可判定量」中，「主轴宽」从未被实现

计划 `:21` 列的是「主轴**宽**」。`measure.mjs` 算的是 `mainRatio`（比例）。`probe.mjs:283` 算了 `axisWidth`，但：
- 只有 5/35 份 `report.json` 含这个字段（实测：S31–S35）；
- `compare.mjs` 完全没读它。

所以「6 个量」实际是「5 个量的名字 + 1 个从未落地的量」。§3.2 的 N2 是补这个洞。

### 分歧 3「同一段 CDP 量测脚本对账」——实际是两段，且结论相反

`74-q7/REPORT.md:5` 说「用与原型**同一段** CDP 量测脚本对账」。

实测：仓库里有**两套**度量器，对同一案给出相反答案：

| 案 | `measure.mjs` | `probe.mjs` | 真值（CSS 声明） |
|---|---|---|---|
| S01 | 2 轨 `[0.5,0.5]`（`DIV.plate-grid`） | **4 栏**（`div.columns`） | `style.css:195` `5fr 24px 4fr 24px 4fr 24px 3fr` → **4 栏 + 3 条 24px 栏沟** |
| S07 | 3 轨 `[0.416,0.583]` | 2 栏（`div.pages`） | 版心 `5fr 1px 7fr` 是**两页宽度比**；真实栏数是 `column-count:2/3` |
| S27 | **0 轨** | 9 栏 | 需第三来源（未验证） |

`sanity check`：S01 的 `probe.mjs` 结果 4 栏与 `style.css:195` 的 `5fr/4fr/4fr/3fr` 完全吻合，`measure.mjs` 的结果与 CSS 完全不符。**所以 `measure.mjs` 在 S01 上是错的，这是可证的。**

后果：`compare.mjs:56-57` 把栏数降级成「只报不判」，注释给的理由是「哪个 grid 是主版式是主观判断」（`:48-53`）。**这个理由对一个已经被证明做错的启发式是合理的，但它掩盖了另一件事：正确做法（`probe.mjs:183` 按文字量选）已经存在于仓库里。** 降级不是唯一选项。

### 分歧 4「固定用同一个模型」在今天的执行条件

计划 `:254`：「复刻验货依赖一个模型 API key……建议固定用同一个模型」。

**这条判断在两点上不准：**

1. **「依赖一个 API key」是错的。** 上一轮的盲测**不是**用 API key 跑的，是用**子 agent**（Claude Code 的 subagent）跑的。transcript 里每个 agent 都有 `agentType: general-purpose` 和 `model: opus` 的元数据（`agent-*.meta.json`），没有任何 `api_key` 参与的痕迹。所以「没有 API key 就做不了」是**对上一轮做法的误描述**——上一轮做成了，靠的不是 key。
2. **「固定用同一个模型」实际没做到。** 实测 16 个生成 agent 里 **1 个中途被换模型**（`ad676d`：第 938 条消息从 `SCNet-Max` 切到 `deepseek-ai/deepseek-v4.1-flash`）。这不是配置错误，是本机路由层的自动切换（100 个 agent 里 33 个发生过中途切换）。**所以「固定模型」这条验收今天无法用「配置一个 model 参数」保证，只能用「审计 transcript 的 model 去重集合」保证**——这正是 WBS-6 验收 3。

### 分歧 5「每季度抽 3 案」的样本量不足以支撑纵向对比

`:254` 建议「每季同一 3 案，做纵向对比而非横向评分」。

纵向对比的前提是**同一把尺子**。而 §三 已证明这把尺子在两轮之间**换过**：上一轮判 7 行（`git show ed7889d:deliverables/74-q7/compare.mjs` 可见当时「主轴比例」是真判的，`:55-61` 有 0.08 容差），今天只判 4 行、另 3 行恒真。**所以上一轮报告里的 `6/7`、`7/7` 与今天 `compare.mjs` 打印的任何分数都不可比。** 跨轮引用分数时必须连同工具版本一起记，否则会像 §3.3 那样把「同一变量对照」误读成别的。

建议改口径：纵向对比只在**同一版本的工具**内成立。工具改版后，基线必须重跑（WBS-1 存在的理由）。
