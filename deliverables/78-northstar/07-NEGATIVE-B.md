# 负对照 B（S98）：实验被上游网关打断，结论作废

> 2026-11-13　主线程
> ⚠️ **这份报告的初版结论（「删掉数值后模型做不出东西」）已被推翻。**
> 验证 Agent 查出：S98 的 stream 结尾是 8 次连续 524 重试后 `terminal_reason: api_error`。
> 那一轮**不是模型的失败，是网关的失败**。

---

## 一、结论（修正后）

**S98 这个实验不能用来回答「删掉数值会怎样」，因为它没有跑完。**

```
stream 共 58,040 行 / 11,572,986 字节
第 58031–58038 行    api_retry attempt 1..8，error_status: 524
第 58040 行          type=result  is_error=true  api_error_status=524
                     terminal_reason: "api_error"
                     result: "API Error: 524 ... check your inference gateway (127.0.0.1:15721)"
首末时间戳           16:34:31 → 20:48:59（4.24 小时）
duration_ms          15,381,773（4.27 小时）
api_retry 总数       10 次
```

**所以「零产物」至少有两个可能原因：**

1. 没有数值导致模型无法收敛（我原来主张的）
2. **上游网关在最后两小时反复 524，模型根本没拿到机会再动手**

而且 524 风暴之前的 thinking 已经到 **47,212** ——
不能排除「它本来快要收敛，被网关打断了」。

**这两个原因我无法区分。所以这个实验的结论作废。**

### 1.1 我原来写的三条「排除的替代解释」全错

| 我当时写的 | 实际 |
|---|---|
| 「不是 API 故障：那 205 处 524 全部来自 UUID 和 token 计数，真实错误数 = 0」 | **错。** `api_retry` 事件 10 条、`is_error: true` 2 处、`terminal_reason: "api_error"` |
| 「跑到超时（约 2 小时）」 | **错。** 实测 4.24 小时，结束原因是 `api_error` 不是 timeout |
| 「不是死循环：thinking 单调递增」 | 这一条本身没错，但它证明不了「模型会收敛」 |

### 1.2 为什么我会漏掉：我只看了前 2.9 万行

```
grep -c 'API Error\|upstream_error\|524' 全量 stream   → 427
                                          前 29,000 行  → 204–211
所有 524 事件都集中在第 58031 行之后。
```

我查的时候实验**还在跑**，我只读了当时已有的那部分。
于是「在那一刻没有错误」被我当成了「整场没有错误」。

**这是同一个错误的第七次**，而我在报告里把它写成了「第六次，我抓到了」——
实际上当时的「抓到」用的是同一个坏判据，只是换了个位置。

## 二、这个实验还有价值的部分

尽管结论作废，S98 的过程仍然产出了一些确定的事实：

- 任务书本身是完好的：40 行 / 5090 字节，格式与 S31 同构，全部 `px` 与「倍」都清干净了
- 模型确实读了 `task.txt`（工具调用记录在第 5 次）
- 在被打断之前，它思考了 47,212 token 而没有开始写

**这些说明「可能有卡住的倾向」，但不构成结论。** 要验证必须重跑，且要能扛住网关抖动。

---

## 三、重跑需要什么条件

1. **重试机制**：单次 524 不该让整轮作废，应该有退避重试
2. **结束原因必须记录**：`terminal_reason` 要进 `run.json`，区分 `success` / `api_error` / `timeout`
3. **判据要读全量**：任何「有没有发生 X」的断言，必须对**完整的** stream 跑，不能读前缀

第 3 条是这一轮反复栽的坑，已经写进 §四。

## 四、这一轮我在这件事上错了几次

| 次 | 判据 | 真实情况 |
|---|---|---|
| 1 | `grep 'API Error 524'` 在文本里 | 错误在 JSON 字段里，文本搜不到 |
| 2 | 改用 `grep -c '524'` | 命中的是 UUID 与 `estimated_tokens:524` |
| 3 | 逐条核查那 205 处 | 是对的，但**只查了前 2.9 万行**，而所有 524 在 5.8 万行之后 |

**三次都是「查了一个不完整或不对的截面」。**

规则：**任何「有没有发生 X」的断言，必须先确认自己读的是完整数据。**
`wc -l` 看一下总行数，再决定读哪一段。

## 五、原始实验设计（保留，因为任务书是好的，可用于重跑）

### 5.1 怎么造的 S98

从 S31 的产品提示词出发，只改数值相关的内容：

| 项 | S31（有数值） | S98（无数值） |
|---|---|---|
| 机制句 | 主刻度每 60px、长 34px、3px 宽，次刻度每 12px、长 12px、2px 宽 | 主刻度的间隔宽、刻线长而粗，次刻度的间隔窄、刻线短而细，主次两级按固定倍数递进 |
| 线宽 | 1px | 只用一级，全站同粗细 |
| 字号 | 正文 16px；最大标题 6.5 倍（约 104px） | 正文是常规阅读字号；最大标题压到正文的好几倍 |
| 条目数 | 6 个条目 | 一组条目 |
| 图片数 | 至少 1 个图片位置 | 要有不同的图片位置 |
| 风险段 | 含 60px / 12px / 3px / 1px | 改成「主刻度的间隔、次刻度的间隔、主刻度的线宽」 |

**刻意保留配色 hex 与字体名**：它们是设计身份，不是尺寸参数。
