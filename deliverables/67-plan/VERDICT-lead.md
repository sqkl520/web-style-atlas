# 第 7 轮裁决：移动端两个缺陷

> 5 份报告到位（规划 62KB / 红队 40KB / 移动端预算 50KB / 排版基线 66KB / 详情执行 27KB / 列表执行 29KB）。
> 本文件是我对冲突的裁决，以及「下一轮该做什么」的判断。

## 一、三方结论一致的三件事

### 1. 「首屏 1 张完整卡」这个目标不该追

| 来源 | 论证 |
|---|---|
| **移动端预算审计** | 「首卡 430.2–577.8px，首屏剩给卡的空间最多 **469px** ⇒ 必须把卡压到 ≤469px 才可能出 1 张完整卡」 |
| **红队** | 「那 1 张卡只在默认排序成立。`#sort` 里有『闸门 FAIL 多在前』，FAIL 多→WARN 多→row-foot 行数多→卡更高。S13 卡 473px > 可用 456px，**余量 −18px**，完整卡回 0」 |
| **我实测** | 默认排序 S01 卡 410px / 可用 432 / **1 张**；换「闸门 FAIL 多在前」→ 首卡 S13 **454px** / 可用 432 / **0 张** |

**裁决**：接受审计的建议，**改用「首卡可辨认」判据**——编号 + 标题 + 一句话定义 + 闸门结论都在首屏内，即为达标。执行 A 实现的现状（首卡 top 412.4、卡高 410、露出 100%）已满足。

### 2. 「压排版」这条路不该走

| 来源 | 论证 |
|---|---|
| **排版基线审计** | 「上一轮『−48.7%』里折叠占 **−43.4%**，排版收紧只占 **−5.3%（223px）**。而『不折字段 30/30 达标』用的**是 15px 不是 16px**——同参数换回 16px 重跑：**13/30 超线**；即使左右内距压到 0 仍 1/30 超」 |
| **规划 Agent** | 「`G4C`（折同样 4 个字段、**排版一个值不动**）已经 0/30；`G2`（**只折 2 个**、排版不动）也已经 0/30。所以『必须折 4 个』和『必须压排版』都不成立」 |
| **执行 Agent** | 「我没走审计推荐的 R2（要压行高 1.62→1.5、内距 12→8）。实测只折字段就能 30/30 达标，**不需要动可读性变量**」 |

**裁决**：维持执行 Agent 的做法——**只折字段，排版不动**。实测结果支持：390 档 `3538–4668 → 2301–2690`（我独立复核），16px / 1.62 / 355px 全部未动。

### 3. 「全展开无成本」是错的，需要如实申报

| 来源 | 论证 |
|---|---|
| **红队** | 「『折叠全展开只 +31px』少算 40 倍。全开 8 条 details 实测 **+1282/+1405/+1409px**。31px 只数了新增 4 条 summary，没算原有 4 条折叠块」 |
| **我实测** | S01：折叠态 2405 → 全展开 **4820**，增量 **2415px** |

**裁决**：红队的批评成立，但需要澄清口径差异——「+31px」指的是**新增 4 条折叠条本身的高度**（默认收起时的成本），2415px 是**全展开后的总增量**。两者都对，但**必须同时申报**，否则「分层无成本」是误导。

**这是我要求执行 Agent 补的**：报告里要写清「默认收起 +31px / 全展开 +2415px」。

## 三、我实测发现的两处「文件违反自己声明的规则」

### 1. `figcaption` 11px 违反 13px 下限

- `style.css:8` 明写：「2 小字下限收到 13px（**原先 11/12px 有 115 处**）」
- `style.css:815`：`.shot figcaption { font-size: 11px; }`
- 我实测 390 档 `li.row figcaption` computedStyle = **11px**

**已派执行 Agent 修**（问题 1）。

### 2. `--s-h1` 是死变量

- `style.css:9` 明写：「3 大标题 3.8vw → **5.2vw**（首屏要有一个明确的主导元素）」
- `style.css:42` 定义了 `--s-h1: clamp(34px, 5.2vw, 74px)`
- `style.css:129` 的 `.mast h1` 用的是 `clamp(30px, 4vw, 56px)`
- **`--s-h1` 零引用**

**这是 `focal-point` FAIL（3.9vw < 4.5）的根因**，也是「作者以为在用 A，实际在用 B」的典型。与上一轮 `--s-15` 同类。

**已派执行 Agent 修**（问题 2）。

## 四、比这些更根本的问题（规划与红队都指出）

- `verify-prototype.mjs` 的 `--all` 只匹配 `/^S\d{2}-/` 的目录
- **`prototypes/_selection/` 完全不在闸门范围内**
- 规划 Agent 用仓库自己的 `probe.mjs` + `rules.mjs` 实跑选型台：1440 档 **4 条 FAIL**（`emoji` / `body-size` / `small-text` / `focal-point`）

**红队补了一刀**：「`verify-prototype.mjs` 145 行零豁免机制。`README.md:348` 把 4 处 mono 的豁免写在文档和 `_CONTRACT.md §9.15` 里，没写进检查器。**26/30 结构上永远到不了 30/30**。」

## 五、我的裁决：本轮做什么

### 已落地、我确认保留

| 改动 | 实测结果 | 裁决 |

| 列表页折 3 块 chrome | 390 首卡 954 → **412.4**；1440 Δ0 | **保留**（但换排序的脆弱性要记进文档） |

### 本轮还要做（已派 Agent）

1. **修 `figcaption` 11px**（违反文件自己声明的 13px 下限）
2. **接上 `--s-h1`**（死变量，`focal-point` FAIL 根因）
3. **去掉 `.cap` 的 `⚠`**（`emoji` FAIL）

### 下一轮该做（本轮不做，避免冲突）

1. **选型台进闸门**——这是最根本的：一个自称「26 个闸门 FAIL=0」的仓库，自己的主界面从不被扫

3. **8 个行业词的模板层答案**（红队推荐）

## 六、不该做的

| 项 | 理由 |
|---|---|
| 追「首屏 1 张完整卡」 | 三角一致：物理上要求卡 ≤469px，代价是删截图或家族字段；且换排序就失效 |
