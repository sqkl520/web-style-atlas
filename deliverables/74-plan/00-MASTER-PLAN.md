## 一、这份产品是什么（一句话）

**店主打开站点 → 挑一个风格 → 复制一段 AI 提示词 → 粘进自己的 AI → 得到自己的站。**

选型台是产品，**提示词是交付物**。提示词错了 = 产品给了客户一个坏站。
其余一切（闸门、截图、审计报告）都只是为这句话服务的工具。

由此得出唯一的北极星指标：

> **一份被复制走的提示词，能让一个店主做出他愿意发布的站。**

它无法直接埋点（纯静态、无遥测）。**代理指标**：每季度抽 3 案做一次复刻验货，
用 DOM 量 6 个可判定量（栏数／主轴宽／最大标题字号／正文比／线宽集合／图片位数），
与原型对账。这是本计划里唯一能证伪「提示词真的有用」的动作。

#### W0 为什么排在最前

批评 Agent 独立 curl 了线上站点，确认 `47 颗芯片`（出现 2 次）与 `多数案 10 段` 仍在对外服务。
这是全计划里性价比最高的一步——**十分钟，消除一个正在被所有访客看到的错误**。
它也是 W2 的探针：改完这两处若 `check-ui-copy.mjs` 仍绿，说明那个闸门没写对。

#### W1 的两处细节

- 向导 bug：`wizard.js:275-281` 接受 NaN/越界参数后，**不管答案都返回 S01/S02/S03**，且页面显示 `undefined`（约 10 行）。
- 删图缺陷：`inspect.mjs:57-58` 在 `Browser.launch()`（`:59`）**之前**删截图；失败后
  `verify-prototype:134` 只查 JSON 字段不 stat 文件、`check-stale:93` 的 `if (jpgs.length)` 在截图清零时整段跳过，
  于是两个闸门同时报「达标」与「全部新鲜」。

#### W3 的关键澄清（经批评复核）：31 张并非同一类

**只有 12 张是确认的第三方位图**（S07 的 7 张报纸缩微扫描 + S17 的 5 张）。
**S04 与 S08 盘上有生成脚本**（`build/make-plates.py`、`make-torn.py`），
但 `CREDITS.md` 首段又说是「网络可用时从 Wikimedia 抓取」——定性命中前无法二选一。

所以正确做法是**先分类再动手**：

1. S07/S17 的 12 张必须换或撤（真第三方）；
2. S04/S08 先核实是生成还是抓取：生成则补一行出处声明即可，**无需重渲染**（这一步能把 6–9 天压到 3–5 天）；
3. 无论哪一类，CREDITS/LICENSE/README 三处数字统一为实测值（现在是 LICENSE 56 / README 46 / 盘上 51）。

#### W4 的范围要如实（经批评复核，原估法低估了）

真正的工程量是**在 179 个 `@media` / 373 个 `grid-template-columns` / 618 个 `line-height` / 437 个 `gap`
声明上建一条 CSS 语义抽取**（四个数都实测过），约 **4.5–7.5 人日的语义工作**，不是改模板。

所以 Q1 的诚实交付是：**3 句修正 + 重算分档 + `check-mechanism`（带 4 条变异测试）+ `corrections.json` + 零成本版 Q7a**。
**完整的 7 行 SPEC 与 Q7b 是 1.5–2 个季度的事，不在 Q1。**

三条硬错的准确修法（已逐条核实到 CSS 行）：

| 案 | 现在写的 | 实际 | 修成 |
|---|---|---|---|
| S03 | 「右侧 9 栏」「游标随**焦距比**移动」 | `.plates{repeat(2,…)}` 两栏一组；`cursor` 是 1:1 跟随鼠标，`grep 焦距` 全案 0 命中 | 「两块图版各 2 栏」；「游标 1:1 跟随指针」 |
| S07 | 「正面 5 栏对背面 7 栏」 | `5fr 1px 7fr` 是**两页宽度比**；真实栏数 `column-count:2` / `column-count:3`（`style.css:81-82`） | 「正页 2 栏、背页 3 栏，两页宽度比 5:7」 |
| S17 | 「金额列 **96px**」 | `96px` 出现 **0 次**；真值 `td.num{width:88px}` 且只在一个断点（`style.css:320`） | 「金额列 88px（窄档）」 |

> 注：S03 的「28px 一档」**经复算是对的**（`round(秒×28/30)` 八档全中），属措辞问题不是假数——
> 不要把它一起改掉。

顺带要修的一个闸门缺陷：现存的朴素 token 匹配器既**误报**（S09/S13）又**漏掉最坏的一例**——
S07 的栏数错误之所以通过，是因为 `grid-template[^;]*5` 匹配到了 `5fr`。
新闸门必须做结构化断言（`columnCounts`/`gridTracks`），不能只比字面 token。

#### W6 的三个硬约束（直接做会踩）

1. **不要以「你是做什么的？」作为首屏唯一入口。** 44 个行业词只有 16 个有直连方案，28 个只有近似，
   另有 29 个连芯片都没有——首屏问行业，**64% 的答案会落到「我们没有这个」**。
   行业筛选保持在选型台内；首屏用一句钩子 + 一张真截图 + 一个主行动。
2. **不能删掉 meta refresh 而不建根级 hash 路由。** 仓库唯一的可分享形式是 `/prototypes/_selection/#Sxx`；
   根 `#Sxx` 现在就是坏的。删跳转前要么建根路由，要么明确放弃根深链（并改 `index.html:12` 的 canonical 与 `README.md:255`）。
3. **根路径下所有相对前缀都要改。** `data.js:59-63`、`_selection/index.html:8-10`、`prompt-copy.js:1438-1457`、
   `app.js:1284` 都用 `../`，在根路径会 404（已实测）。这不是「复制一个文件」的活。

### Q2：让「挑」这件事成立

主题：从「30 张卡」变成「我的处境有答案」。

- **N31–N35 首批新增**，按缺口选题：中间明度 ≥2 案、亮底紫 ≥1 案、「很安静」+3 案、少货少图（`minPics≤2`）≥2 案。每案走完整链路（契约 → 渲染 → 闸门 → 提示词）。
- **分布闸门 `check-distribution.mjs`**：把目标分布写成可计算断言，只管新增、不管删除。
- **详情面板分层**：12 段压成「判决层（≤180 字）+ 施工层」，判决层要能回答「这是不是我的店」。
- **向导与芯片合并答案**：行业词、`prompt-copy.js` 里的「你经营什么」、向导五个问题今天各存一份答案，要收成一份。
- **Q2 验收**：新增 5 案全部过闸；「很安静」从 2 → 5；中间明度从 0 → 2；少货少图有正解。

### Q3：让「带走」这件事成立

主题：复制的不是一段话，是一份能对账的施工说明。

- **SPEC 七行结构化段**替代单句机制句（比例／密度／字阶／节奏／图像／交互／构造），每行可回溯到 CSS。
  ⚠️ **这是全计划最大的一块未估准工作，且它装不进 Q1。** 需在 179 个 `@media` / 373 个 `grid-template-columns` /
  618 个 `line-height` / 437 个 `gap` 声明上建语义抽取，评估 **~1.5–2 个季度**。
  Q3 的做法是 **3 案试点**：若 CSS 抽取可靠则铺开，不可靠则退回到「机制句 + 出处」的轻量版。
- **出处进剪贴板**：`dna.provenance`（哪一行 CSS 支撑这句话），让「实测抽取」这句话可被用户自己核对。
- **交接体验**：不抢焦点、`role=status` 双通道确认、`.md` 下载兜底、按工具（ChatGPT/Claude/v0/Cursor）只改首部上下文。
  ⚠️ **这是审批 Agent 唯一全额背书的一项**，因为它「从仓库自己的失败史出发，用架构消除缺陷类，而不是用闸门追着抓」——
  正是 `README.md:101` 记的那条 M01 分叉教训的直接应用。
- **Q3 验收**：任取一份提示词，用户能点开看到每个数字的 CSS 出处。

### Q4：让它能被持续维护

主题：季度节奏跑通一轮，且有数据可依。

- **第一次完整增删演练**：按 R3 只增不删，但演练「若某案表现差，归档流程是什么」。
- **季度体检脚本**：`npm run quarter`（或 `node _build/quarter.mjs`）一键跑完渲染 → 生成 → 8 闸门 → 探针 → 分布报告。
- **可选：轻量使用信号**。若你愿意，加一个只在链出时记录「哪个案被复制」的静态计数（如 Cloudflare Analytics 免费版），这是唯一能知道「哪个案是废的」的方式。**但这条与「数据不出本机」的自我描述冲突，需你单独批准。**
- **Q4 验收**：季度全流程可在一台干净的机器上从零复现。

## 五、方案增删的具体标准（R3 的可执行版）

R3 说「只加不删」，但没有说「加什么算合格」。这一节把它变成可以打勾的清单。

### 5.1 新增一个方案，必须同时满足

**机器可查（缺一不可）**

1. 过 `_CONTRACT.md` §6 全部硬约束；
2. 三档视口渲染产 `report.json`，`FAIL=0`，或每条 FAIL 命中 §9.15 允许表；
3. `prompts.js` 的 `dna.palette` 与 `style.css` 的 `:root` 一致（`check-twolines` R7/R8 绿）；
4. 机制句里每个带单位数字，能在该案 `style.css` 或 `index.html` 里找到（W4 的 `check-mechanism.mjs`）；
5. `assets/CREDITS.md` 逐张有作者 + 许可，**且许可允许再分发**（这是 R1 之后的硬门槛）；
6. `capacity.minItems` / `minPics` 有值，并如实标注 `degrades`。

**人判（作者自述，写进交付说明）**

7. 一句话说明「它解决哪个现存方案解决不了的处境」——**若答不出来，它不是新方案，是旧方案的一个配色**；
8. 指出它与 30 案里最接近的那一案的结构差异（22 个结构标签里已有 8 对撞车，不允许再加第 9 对）。

### 5.2 为什么现在不归档任何方案

复算过：删 OFFERING 点名的 5 案之后，光 21→16、暗 8→8（比例反而更挤）、中间明度仍 0、很安静仍 2、紫色仍 0。
**五根轴里四根没改善**，唯一变化是「用户少了一个选项」。

归档的真正触发条件应该是**数据**，不是分布表：某案连续两个季度被复制次数排末位 5，且它的结构标签与另一案重合。
在拿到任何使用数据之前（Q4 之前不会有），归档没有依据。

### 5.3 「30」这个数字的迁移清单

一旦增删生效，以下每一处都会失效，必须同时改：

| 位置 | 现在的内容 |
|---|---|
| `README.md` / `README-EN.md` | 标题、副标题、徽章 `Schemes: 30`、正文多处「30 个」 |
| `prototypes/_selection/index.html` | 标题、meta description、报头 |
| `check-docs.mjs` | `nums/schemes` 断言 |
| `_build/_entries.mjs` | 30 个方案目录的枚举 |
| `.inspect/` 截图总数 | 272 张（30 × 三档 + 折页） |
| 向导文案 | 「30 个方案里」 |
| `prompts.js` | `schemes` 数组长度 |

**原则**：把「30」换成一个从 `window.SCHEMES.length` 现算的占位符，而不是换成一个新字面量。
否则下一次增删又要把这张表重走一遍。

## 六、本计划明确不做的五件事

| 不做 | 为什么 |
|---|---|
| **删掉 S10/S21/S26/S11/S23** | 已复算：删完中间明度仍 0、暗底比例 26.7%→32.0%（更拥挤）、很安静仍 2 案。四根轴没改善，唯一变化是「少了个选项」 |
| **把两条数据链合并成单一来源** | 上一轮 Agent 三次自我推翻后确认：`data.js` 是设计意图（4 主色）、`prompts.js` 是施工细节（4–7 色含派生色），两者都对。合并会抹掉这个区分 |
| **给 30/30 案都标 needsJS** | 实测三档（原报 A=3/B=9/C=18，**经复核后该分布不成立**）。S17 那 129 行 JS 是 CSV 导出与错误态，不是风格。全标会把纯 CSS 案也推向脆弱代码。**注意**：按「`index.html` 是否含 `<script>`」来算会得 30/30，因为 13 案各有一个 `classList.add('js')` 探针——这个判据测的是「页面带脚本」而非「机制依赖脚本」 |

  **分档本身要重算，且必须机器算，不能手列**。批评 Agent 发现原方案的规则执行不一致：
  它把 S26/S28/S30 提为 B（理由是「原型另有滚动视差」），却把 **S02 留在 C** ——
  而 S02 的源码注释原话是「签名机制：滚动 100px 对应右侧纹样相位 3px」，
  `addEventListener('scroll')` 在 `index.html:369`，机制句里也有「相位」。**同一条规则，两个结论。**
  反向也有：S14（`animation: drift 24s` + keyframes）与 S16（纯 `calc()`）是纯 CSS，不该归 B。

  复核给出的两套口径：**按机制句字面 A3/B4/C23**；**按「要复刻那个会动的原型」A3/B14/C13**。
  两个都自洽，差在「产品承诺的是机制句还是那张截图」。**W4 里必须先定口径，再用
  `classify(detectJsApi())` 从源码算出来，不许维护一张手写对照表**（手写表就是下一个 §9.15 豁免表）。

  **反向也要做**：对那 18 个「CSS 就够」的案，提示词里要**明确写「不要用 JS 实现这个签名机制」**。
  因为 S02 已有先例：它的脚本在 `index.html:266` 用 `translateY(0)` 覆盖了 `style.css:149` 的 `-28px`，
  **带 JS 的版本反而比不带 JS 的更不忠实**。鼓励 AI 加脚本会主动制造这种退化。

## 七、风险与已知的未知

1. **R3「只加不删」会让库持续变大**，Q2 之后需要首屏之外的分层浏览（已有「看全部 N 个」第二层的设计）。若某季新增超过 5 案，需重新评估。
2. **SPEC 七行是最大的一块未估准的工作**。`dna` 现有键不足以支撑，Q3 试点若证明 CSS 抽取不可靠，退回到「机制句 + 出处」的轻量版。
3. **复刻验货依赖一个模型 API key**，且不同模型产出差异大。建议固定用同一个模型、每季同一 3 案，做纵向对比而非横向评分。
4. **`inspect.mjs` 的 Chrome 超时是环境敏感的**（本机冷启动实测 14.1s，超时 20s，余量 1.41×）。vendor 之后这个数要写进 CI 的机器规格说明。
5. **2026-11-04 实测的线上状态**：`index.html` 仍显示「11 组 47 颗芯片」与「多数案 10 段」。这两处在 W2 前对外是错的。
6. **W1–W6 不是全独立的**（原方案说「各自可 push」是错的）。已识别的硬依赖：修芯片样式会改变芯片计数（45→73），所以 W2 内的顺序是「先计数后样式」；卡片的 `scenesNo` 依赖生成器先吐 `scenesNoBrief`（今天零命中）；W6 依赖 W2 的路径重基。
7. **`scenesNo` 上卡片还有一个坑**：它与行业芯片有 3 处直接矛盾（展览→S23、诊所→S29、内容媒体→S07），另有 27/30 案的首句**不含否定词**——极性完全靠「不适合：」这个前缀承担。截断显示会直接把语义翻反。
8. **字体「≤220 KB」这个数没有独立测过**，只有 871 个文件 / 30.3 MB 的总量。W2 的性能预算里这一项要实测后再定。
