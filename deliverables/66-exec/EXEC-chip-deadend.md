## 0 一句话结论

**"先搜词再点同名芯片"在改前对 44 个行业词里的 18 个是死路（0 行），且空状态正在教用户这么做。**
根因是 `match()` 把 `sceneIds` 与 `q` 取交集，而芯片只写 `sceneIds`、不碰 `q`。
改法选了**丁：点芯片时把搜索词「挂起」**（移出输入框、存进 `state.qParked`、搜索框旁留一条
可点复原的条子），既让芯片按自己的白名单筛，又不丢用户打的字。
改后：**先搜后点 44/44 有结果；先点后搜 44/44 不死路；reset 仍 30/30。**

### 1.1 四种操作顺序 × 44 个 `sceneIndex` 词

|---|---|---|
| **A 只搜该词** | **17 / 44** | 行业词不在方案正文里（`hay` 是整串匹配）——这是供给缺口，本来就该 0 行 |
| **B 只点该词芯片** | **0 / 44** | 芯片这条路一直是通的（每个词都 ≥1 行） |
| **C 先搜后点** | **18 / 44** | ← 空状态让用户做的正是这件事 |
| **D 先点后搜**（点芯片后搜「白色」） | **34 / 44** | 另一条顺序的死路 |

**C 的 18 个词**：咖啡店 茶饮 餐厅 书店 潮牌 修鞋理发 小吃店 花店 民宿 婚礼 **摄影** 健身 宠物 诊所 律师 会计 招聘 非营利

### 1.2 与审计 Agent 报的 17/17 对照

审计（`deliverables/66-audit/template-layer.md` §2.4）报「按空状态字面指示点芯片，17/17 仍 0 行」，
名单是：咖啡店 茶饮 餐厅 书店 潮牌 修鞋理发 小吃店 花店 民宿 婚礼 健身 宠物 诊所 律师 会计 招聘 非营利。

我实测的 C 集合是它的**超集**，多的正是 **摄影**：

```
A0（只搜 0 行）17 词 = 审计的 17 词，逐一相同
C0（先搜后点 0 行）18 词 = A0 + 摄影
C0 − A0 = 摄影        ← 审计漏掉的这一个
A0 − C0 = （空）
```

**为什么审计漏了**：它的判据是"按指示点芯片后仍为 0"，而它挑的 17 个词本身就是搜索 0 行的词。
**摄影**搜索有 8 行、不在它挑的样本里，所以"点了芯片反而归零"这一类没有进入它的取景框。
**结论：审计的 17/17 是真的，但它是下界。实际受影响 18 个词，其中 1 个是"有结果被清零"。**

### 1.3 死路的机制（一行代码）

```js
// app.js match()，改前
if (state.sceneIds && state.sceneIds.size && !state.sceneIds.has(r.id)) return false;  // 先缩到 4 个 id
...
if (hay.indexOf(state.q) < 0) return false;   // 再要求正文含「咖啡店」
```

`sceneIds` 与 `q` 是 AND。点芯片只写前者（`prompt-copy.js` 的 click handler），`q` 留在原处。
`sceneIndex["咖啡店"].near = ["S19","S22","S09"]`，这三个的 `hay` 里没有「咖啡店」→ 交集恒为空。

`app.js` 里那段注释已经说清了**为什么芯片不能往搜索框里拼方案号**（"S06 S19" 这种串在 hay 里不存在），
但**没有处理"芯片与已存在的搜索词如何共存"**——这就是缺口。

## 2 三个候选的取舍

| | 做法 | 优点 | 为什么没选 |
|---|---|---|---|
| **甲** | 点芯片时清空搜索框 | 最直接，3 行 | 用户刚打的字**被静默吃掉**且不可撤销；而他很可能就是想"在咖啡店这 4 个里再挑"，这一半意图被抹掉。审计也点了这个风险（"要么留一句已按行业筛选，要么…"） |
| **乙** | `sceneIds` 与 `q` 改 OR | 语义上"点芯片=再加一批" | 破坏其余九组筛选器的 AND 一致性。搜「咖啡店」再点「暗底」，用户期待交集不是并集。`rail-lead` 上写着"组间是「并且」"，改 OR 等于改这张台子的基本语法 |
| **丙** | `q` 命中行业词时就不参与 hay 匹配 | 不用碰输入框 | 需要"猜"搜索词是不是行业词，歧义真实存在：**摄影**既是行业词、又真的出现在 8 行的正文里（`hay` 命中 8 行）。按丙改，「摄影」会从 8 行变成 2 行，而且没有任何提示——用一个静默改动换掉另一个 |
| **丁 ✅** | **点芯片时把搜索词「挂起」** | 芯片立刻按白名单筛；字一个不丢；一键可放回；AND 语义一点没动；`摄影` 这类词也不特殊处理 | 唯一代价：搜索框旁多一条 33px 高的条子（1440 档实测 `.bar` 60→107px），窄屏做成了固定底栏 |

### 2.1 丁 的具体语义（三条，都可断言）

1. **点芯片**：若 `#q` 非空 → 把词存进 `state.qParked`、清空输入框、**一次渲染**同时换掉 `sceneIds`。
   条子写「已暂存搜索词「X」——芯片正在按行业筛」，带「放回搜索」「丢弃」两个按钮。
2. **放回搜索**：把词写回输入框、按词筛、**同时取消芯片**（同一根轴上不能两个主人，否则又回到交集）。
3. **再点一次芯片（取消）**：只清 `sceneIds`，**不碰**已挂起的词 —— 取消不该再丢一次。

### 2.2 为什么不顺手把「先点后搜」也改掉

「先点芯片 → 再在框里打字」在改前是 34/44 死路。我**没有**让"打字自动取消芯片"，试过之后否掉了：

- 那会让用户没点过的芯片**自己灭掉**，是新的一种静默改动（和甲同类错误）；
- 「组间是并且」是这张台子的语法，`q` 只是其中一组筛选：先点芯片再打词，本来就该是
  **在这几个里继续缩小**。缩得太狠是允许的，只要**能一键退回去**。

所以这里改的不是语义，是**出口**：0 行时空状态给出带行数的两个按钮
（「只看芯片（4 行）」「只看搜索词（3 行）」），点一下就到。实测 34 个 0 行组合，
**一键退回后仍为 0 的组合：0 个**。

### 3.1 核心做法：文案不再写死，数字与按钮同源

`syncEmptyNext(idx)` 每次 0 行时**先算**每条退路各能得到几行，再按当前状态只说那几条，
并且每条后面挂一个当场可点的按钮。**计算走同一个 `match()`**，不另写判据 ——
文案不可能再和行为分叉，因为按钮就是行为本身。

四种状态、四条不同的真话：

```
a) 芯片 + 搜索词同时生效  → 「两边都要满足才留下，所以是 0 行」+ 两个"只留一边"按钮
b) 只有芯片（被后面几组筛空）→ 芯片本身几行、只留芯片几行 + 松开按钮
c) 只有搜索词             → 行业词：按芯片筛 N 行 + 按钮；非行业词：直说这 30 案没有
d) 都没有                 → 只有"条件加多了"这一种解释 + 清空按钮
```

**这个探针抓出了我自己写的三个谎**（`_empty-probe.mjs`，均已修）：

1. 「只留芯片，松开后面几组（30 行）」点下去只有 4 行 —— 算 `nChipAlone` 前没把 `sceneIds` 恢复，
   算出的是"什么都没留"；
2. 「只看搜索词（30 行）」点下去 3 行 —— 算的时候只去了芯片，没把被挂起的词算回来；
3. 「丢弃」后列表停在 0 行 —— `restoreQuery()` 分支走错，把词填回输入框却没重渲染。

三条都不是文案错，是**数字与行为用了两套代码**。修法统一为"按钮的 click handler 与算数字的
状态转换是同一组操作"。

### 4.1 那 17 个"只搜仍然 0 行"的词，为什么本来就该 0 行

`state.q` 是**整串子串匹配**，而 `sceneIndex` 是**人工裁定**的"行业→案子"映射，两者本来就不要求逐字对齐。

`data.js` 的 30 行里没有任何一行逐字写着这些词。

它们**不该**靠搜索框命中，该靠芯片。所以界面现在不再说"这三十个案没有它"，
而是说「按文字搜不到，但索引里 S06 就是它的直连方案」+ 一个「按「咖啡店」芯片筛（4 行）」按钮。
**17 个词全部有可点出口，实测每个按钮点下去的行数 = 按钮上写的行数**（见 §5）。

## 7 我可能弄坏的地方

按"最可能真的坏了"排序，每条都写清为什么、以及怎么验。

1. **`#empty` 的 DOM 被我改了（运行时，不是文件）**
   `index.html` 那段静态尾句（"想继续在这三十个案里挑…"）是**在渲染时被 app.js 摘掉**的，
   连同它里面嵌的 `#e-direct2`（"只挑实心的那 16 个"里的 16）。
   *为什么这么做*：`index.html` 不在我的写作用域里，而那句文案与修好后的行为矛盾。
   *风险*：任何按 `index.html` 源码断言空状态文案的脚本（读文件而不是读 DOM）会看到旧句子；
   任何按 `#e-direct2` 存在性断言的地方会找不到它。
   *怎么验*：`_empty-probe.mjs` 是读 DOM 的；它验了 7 条按钮全部兑现承诺。
   **建议 lead 后续把这段静态文案直接从 `index.html` 里删掉**，让 DOM 与文件一致。

2. **`#e-direct2` 这个 id 从此不再出现在渲染结果里**
   它只在 `index.html` 里被 `syncEmptyFacts()` 填过数（`set('e-direct2', direct)`）。
   现在节点被摘掉，那行 `set` 是空操作（`set` 本身有 `if (el)` 保护，不会报错）。
   没有任何断言依赖它（`check-docs.mjs` 不碰它）。

3. **新增了 4 个全局接口**
   `benchSetSceneIdsParkingQuery` / `benchClearSceneIdsKeepQuery` / `benchParkQuery` / `benchParked`。
   旧的 `benchSetSceneIds` / `benchClearSceneIds` **保留且行为不变**（仍带 `render()`），
   所以别的脚本（如果有）调旧接口不会坏。
   *风险*：`benchParkQuery()` 单独调用时**不 render**（设计如此，给组合用）；
   单独用它的人会看到状态变了但界面没变。已在注释里写明。

4. **`#q` 的 `input` 事件不再自动取消芯片**
   我试过并**撤销**了这个行为（理由见 §2.2）。现在"点芯片后打字"是 AND（在这几个里继续缩小）。
   *风险*：若 lead 认为这条也该改，需要另一个决定 —— 它会引入"芯片自己灭掉"的静默改动，
   我判断那比现状更糟。**这一条请 lead 确认。**

5. **窄屏多了一个 `position:fixed` 的底栏**
   只在"有暂存词"时出现，一放回/丢弃就 `display:none`。
   *风险*：它 `z-index:60`，可能压住别的东西；实测只在 390 档出现，且页面底部 48px 内
   原本没有可点控件（`#empty-tpl`、模板卡都在文档流里，会被它遮住最下面一条）。
   *怎么验*：`_parked-pos.mjs` 量了位置；建议在 390 档手动看一眼"暂存条出现时页面最底部有没有被挡住的东西"。

6. **`syncEmptyNext()` 会临时改 `state` 再还原**
   为了算"只留芯片能出几行"，它把九个 Set 备份→清空→算→还原。
   *风险*：如果将来有人在这个函数里 `return` 提前退出，`state` 会留在被清空的状态。
   目前四条分支都走到函数末尾才还原，但这是个脆弱的写法。
   *怎么验*：`_filters-probe.mjs` 的 f01–f12 每次都从 `reset` 开始、且断言了完整 id 集合，
   `state` 被弄坏会立刻红。

7. **`match()` 本身一行没改**
   这是有意的：死路出在"谁来写 `sceneIds` / `q`"，不在判据。所以 AND 语义、
   `scenesYes` 而非 `scenes` 的选择、`hay` 的字段清单全部原样。
   *风险*：如果将来有人给 `sceneIds` 塞进非 `S\d{2}` 的 id（比如模板 `M02`），
   仍会被白名单静默吞掉（实测 `{M02}` → 0/30）——那个坑没修，本轮不涉及。

8. **改前那次 `#e-why` 的假话，我只修了 `#e-why`，没修 `#empty-tpl` 里同源的句子**
   `prompt-copy.js` 空状态分支的 `head`（"「咖啡店」按文字搜不到…但索引里 S06 就是它的直连方案 ——
   点左侧「咖啡店」芯片能筛出来"）现在**成立**了（芯片真的能筛出来），所以没动它。
   但如果后续有人改芯片行为，这句会再次变成假话，而它不在 `app.js` 里。
   *怎么验*：`_chip-probe.mjs` 的 C 列就是它的判据（44 词先搜后点全都 ≥1 行）。

9. **没跑的一档：`wizard.html`**
   本轮只测 `_selection/index.html`。向导（`wizard.js`）若也依赖 `benchSetSceneIds`，
   行为不变（旧接口保留），但我没实测它。`git grep` 显示 `wizard.js` 不引用任何 `bench*SceneIds`。
