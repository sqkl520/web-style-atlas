## 1. `minItems` 到底是什么（追溯，含 S07 的真实单元数）

### 1.1 三处独立写下的定义，说的是同一件事

| 出处 | 原话 |
|---|---|
| `prototypes/_prompts/build-prompts.mjs:90` | `minItems = 同构重复单元的**设计规模**（不是"至少要这么多"）` |
| `deliverables/60-minitems-degrade-audit.md:7-10`（判定口径 1） | `minItems — HTML 里"同构重复单元"的规模：同一父级下 tag 相同、class 相同（或 class 族前缀相同）的兄弟组，取最大的一组` |
| 同上 `:84-88`（对照「我只有 3 个产品」） | `标出的数字是它"设计时"的条目规模，不是"至少要这么多"` |
| 同上 `:75-77` | `degrades=yes` 的共同点：**单元位置不是由内容算出来，是作者数出来的** |

数据链：`60-minitems-degrade-audit.md`（人工实测表）→ `prototypes/_prompts/minitems-parsed.json` →
`build-prompts.mjs` 的 `CAPACITY` → `prompts.js` 的 `s.minItems` 与 `s.capacity` → `prompt-copy.js` 的 `count`。

所以 `minItems` 是**版式的一个属性**（作者当时排了几个槽位），不是**用户的一个属性**（用户手上有几条内容）。
`prompt-copy.js` 把它写成「我实际有 46 个条目」，等于把版式属性贴到了用户身上。

脚本 `deliverables/66-exec/_count-units.mjs`（只读 `prototypes/`，按案给一条显式定位规则，逐案数同父级同 tag 同 class 的兄弟组）：

- **S07 = 46 是真数出来的**，不是我抄审计文档：`index.html:40-59` 的 `ol#toc-list` 里 18 个 `<li>`，
  `index.html:63-92` 的 `ol.toc start="19"` 里 28 个 `<li>`，18+28 = **46**。
  两个 `<ol>` 是跨页的两栏（正页 / 纸背），编号 `start=19` 接续，所以它们**是同一个重复单元的 46 个实例**，

  漏掉了 `class="ln ln--out"` 那几行（挂牌/回执行带一个光标块），数出 47 行 / 3 段 = 15.67，
  看起来像"数据错了"。把正则改成 `<span class="ln(?:"|\s)` 后是 **60 行 / 3 段 = 每段 20**，
  与 `minItems=20` 吻合，`aria-label` 也写着「行 1 至 20」「21 至 40」「41 至 60」。
  **审计文档说 20 的时候，先怀疑自己的正则，不要先怀疑数据** —— 我差点在交付物里写下
  一条"审计文档错了"的结论，而错的其实是我自己的计数脚本。

### 1.3 `degrades=yes` 与 `degrades=no` 的语义**确实不同**（这是本轮最关键的判断）

| | `degrades=no`（17 案） | `degrades=yes`（13 案） |
|---|---|---|
| 单元位置怎么来 | 由浏览器按内容算（`column-count` / grid 自动流 / flex 堆叠） | **由作者数出来**（绝对定位、写死 `grid-row/column`、手绘 SVG 坐标、写死行标题） |
| N 的角色 | **参考规模**：少几条只是变短，N 丢失不影响成立 | **结构参数**：N 就是槽位数，少一个就空一格 |
| 「不足 N 个怎么办」 | 无所谓的，按真实数量排即可 | **必须整块重排**，不能留空槽也不能编造 |
| 实例 | S07（46 条目录，`column-count`） | S15（14 个手绘 `<rect>`）、S29（23 个 `g.pt` 坐标） |

这个区别正是**候选 A / B 必须分岔**的理由，也是候选 C（彻底不提 N）不可接受的代价 ——
`degrades=yes` 那 13 案里，"不足 N 个就整块重排"这条唯一可执行的指令**离开 N 就说不出来**。

补一条实测：`s.minItems` 与 `s.capacity.minItems` 在 30 案里**完全相等**（`prompts.js` 两者都由
`build-prompts.mjs:291/295` 从同一个 `CAPACITY` 写入），所以不存在"两个 N 打架"的问题。

## 2. 三个候选的取舍

### 候选 A：条件句
```
1. 这个版式是按 N 个条目设计的：如果我有 N 个左右的内容，就排 N 个……如果我只有 M 个（M < N），{分岔}
```
**否掉。** 三个问题：
1. 「如果我有 N 个左右」仍然是**用第一人称替用户假设**，只是把断言换成了条件 ——
   病根没除：AI 读到的第一个数量仍然挂在「我」身上。
2. `M` 从哪来？提示词里没有任何地方知道用户真实有几个（界面只收 `biz` / `action` 两个字段）。
   写 `{M}` 就得引入第二个假值，比原缺陷更糟。
3. 一句话里塞两个分支 + 一个未知量，可读性差；这一段的其余部分都是"一条一句"的。

### 候选 B：分成两条（**采用，并扩成三条**）
```
1. 这个版式设计时排了 N 个条目——这是版式的规模，不是你的内容量。
2. 用你自己的真实数量排：有几个排几个，不凑整、不留空位、不留占位符、编号连续不跳号。
3. {按 degrades 分岔：yes 讲"位置是按 N 个数出来的，少一个就空一格，不足就整块重排"／
     no 讲"自动流排版，删条目只是变短，按你自己的数量排就好"}
```
**采用理由：**
1. **第 1 条把 N 的主语换掉了**，从「我实际有」换成「这个版式设计时排了」。
   这是本轮唯一真正修掉缺陷的动作 —— 不是加限定词，是换归属。
2. **第 2 条无条件**。上一轮记录的缺陷正是「不要拉高」+「先凑够」两句并存（13/30 案同时命中，
   恰好是 `degrades=yes` 全部），AI 只能二选一，选哪边都错。所以这一条里刻意不出现
   「如果」「不足」这类词 —— 它是这个段里唯一的**不变量**。
3. **第 3 条承接分岔**，保住 `degrades` 那 13 案的关键信息（上一轮刚修好，不能改回去）。
4. 三条各管一件事（归属 / 不变量 / 后果），符合这一段其余部分的写法。

**为什么从两条扩成三条而不是两条：** 若压成两条，第 2 条就得同时承担"不变量"和"分岔"，
那正是上一轮出事的形状。三条的代价是 +20~26 字（见 §4），完全在 ±80 预算内。

### 候选 C：彻底不提 N
```
1. 用你的真实条目数排，不凑整、不留空位、编号连续。
```
**否掉。** 代价是任务书点明的那一条：丢掉「这个版式是为 N 个设计的」。
对 `degrades=yes` 的 13 案，N 是**结构参数**而不是参考值 —— S15 的 14 个 `<rect>` 坐标、
S29 的 23 个 `g.pt` 手绘路径，不告诉 AI 槽位数，它就没法判断"我的 5 条内容该整块重排"。
另外它也更短（少 ~60 字），但短不是目的。

### 附带修掉的一处旧错（不在任务书里）

`prompt-copy.js` 输出要求那段有条注释写着「这里必须与上面结构约束**第 4 条**对齐」，
而当时图片位是**第 3 条**、第 4 条是「首屏不要轮播图」—— 引用一直差一位，只是没人读到那儿。
本轮数量段 2→3 条，图片位正好后移成第 4 条，错位被顺手抹平。
我把注释改成**按内容指代**而不是按编号指代，下次再挪位也不会重新说错。

### 为什么选择「写清楚为什么它留着」而不是「删掉」

1. **没有可删的东西**（见上）。要"删"只能删一个已经不在的语句，或者把 `o.mood` **重新接回去** ——

3. **留着的实际代价是明确的、可写的**：`window.buildStylePrompt(id, { mood: '…' })` 会**静默忽略** mood。
   把它写成一条明账（死键位置 + 死掉的提交 + 为什么不该复活 + 将来要复活该怎么做），
   比删掉一行然后让下一个人重新踩一遍要好。
4. 顺带把 `opts` 的**全部 7 个键**逐个交代了一遍（`biz` / `what` / `action` / `tone` / `count` / `unit` / `mood`），
   这是本轮唯一新增的接口文档，`mood` 只是其中一行。若将来有人要接 `mood`，
   正确做法也写在里面了：让它覆盖 `tone` **并且**在界面上给出输入框（像 `biz` / `action` 那样），
   一处消费者 + 一处入口。

## 4. 长度账：为什么是 +20~+26，以及中位数有两个口径

改动前后逐案长度（完整表见 §5 的 `acc2` 原始输出）：

| | 改动前 | 改动后 | Δ |
|---|---|---|---|
| 最短 | 1632（S09） | **1652**（S09） | +20 |
| 最长 | 1920（S23） | **1946**（S23） | +26 |
| 中位（`check-docs` 口径 = 上中位） | 1822 | **1842** | +20 |
| 中位（均值口径 = 第 15/16 个平均） | 1814 | **1834.5** | +20.5 |

Δ 是**两档常数**，不是逐案不同：

- **`degrades=no` 的 17 案：+20 或 +21**（差 1 是 `count` 位数不同：单位数 vs 两位数）
- **`degrades=yes` 的 13 案：+26**（yes 分支那句比 no 分支长 5~6 字）

推导（设 N 为 minItems，`L(x)` 为字数）：

```
旧结构约束（数量部分，2 条）  = 1. 我实际有 N 个条目，就排 N 个：  +  不凑整…  +  第 2 条(分岔)
新结构约束（数量部分，3 条）  = 1. 这个版式设计时排了 N 个…  +  2. 用你自己的真实数量排…  +  3. 第 3 条(分岔)
```

**关于中位数两个口径（这一条必须写下来）**：`check-docs.mjs:398` 取 `sorted[floor(n/2)]`，
30 个元素时是**上中位**（第 16 个）；我第一版取 `(sorted[14]+sorted[15])/2`（均值中位）。
两者在基线就差 8（1822 vs 1814）—— 我一度以为是自己引入的差异，查到 `check-docs.mjs:398` 才确认是口径不同。
README 的「中位 1822」按 `check-docs` 口径写。所以脚本现在**两个都打印**，
交付物里也两个都给，否则读者会拿一个去对另一个然后以为改坏了。

   可能有人断言过 `5. 这个版式的硬前提`；那些不是产品路径，我只保证产品路径没坏。

3. **`o.count` / `o.unit` 的**语义**被我明确定义成"换一个版式规模"了。**
   行为没变（还是覆盖 `count`），但如果有人原本指望用 `o.count` 告诉 AI "用户有 5 条"，
   那是拿错了旋钮 —— 现在注释里写清楚了。仓库内零调用方（全库 grep：只在定义处命中），
   但 `window.buildStylePrompt` 是对外公开接口。**如果外部真有调用方按旧语义传 `o.count`，
   它现在会得到"这个版式设计时排了 5 个"而不是"我有 5 个"。**

4. **我差点自己造出一条假缺陷：`S18` 我数错过一次。**
   第一版计数正则漏了 `class="ln ln--out"`，数出 47 行 / 3 段 = 15.67，与 `minItems=20` 不符，
   我一度准备在交付物里写"审计文档这条错了"。改成 `<span class="ln(?:"|\s)` 后是 60 行 / 3 段 = 20，
   **审计文档是对的，我的脚本是错的**。§1.2 里保留了这段教训。
   这件事本身不代表风险已经清零：我的计数脚本是**按案手写定位规则**的（12 条正则），
   不是通用解析器，所以"12/12 吻合"只证明这 12 条规则覆盖的案没被数错，
   **不证明另外 18 案也对**（另外 18 案我直接采信审计文档）。
   若要全量复核，应该跑 `deliverables/99-scratch/minitems/verify.mjs`（审计文档 §复现 里列的那个），本轮没跑。

5. **`degrades` 分岔句里 yes 分支现在带一个"但"字开头的句子（"但这个版式的位置是…"）。**
   这是为了让第 3 条读起来是第 2 条的**补充**而不是**否定**。代价：如果 AI 只读前两条、
   跳过第 3 条，它会以为这个版式完全不挑数量。我保留了这个结构是因为
   第 3 条同时给出了"不足就整块重排"的动作，比第 2 条更具体，AI 不太可能跳。
   但这是一个**赌**，没有实测数据支撑（本轮没有做端到端"让 AI 照提示词生成一遍"的测试）。

6. **长度我只验了"总字数"这一维，没验框选/换行在面板里的观感。**
   提示词块在详情面板里是固定换行的文本，多 20~26 字可能让某一行多折一次。
   本轮没有重跑 `65-exec` 那套面板高度测量（`measure-panel-cost.mjs` 是另一个 Agent 的脚本），
   也没有出截图。**如果 reviewer 认为面板高度敏感，需要重跑一次那个脚本。**

7. **CDP 只验了"文本一致"，没验"复制按钮真的把新文本写进剪贴板"。**
   `cdp-verify.mjs` 调的是 `window.buildStylePrompt(id)`（与按钮同一条路径、同一个函数），
   不是点按钮读剪贴板。上一轮的 `shot-opener.mjs` 覆盖过按钮那一层（50 断言），
   但它测的是**首行**逻辑；本轮的改动在提示词中段，按钮那条链一个字节都没改
   （`copyPrompt` / `execCopySync` / `showManual` 全未触及），所以我认为不需要重跑。
   如果 reviewer 要"按钮端到端"的完整证据，需要跑一次 `65-exec/shot-opener.mjs`。
