## 0 这份文件要纠正的三件事

1. **判据被写错了。** 早期版本里约 12 个规则 ID 是我**凭空造出来的**（`cream-palette`、`default-font`、`overused-font`、`icon-tile-stack`、`performative-label`、`serif-premium`、`wide-tracking`、`bounce-easing`、`skipped-heading` 等），同时漏掉了 20 条真规则。**造出来的规则名会让整个审计无法被复核**——它们既不能被 `validate-rule-ids.mjs` 校验，也不能被任何一个真实工具触发。
2. **配色根本不是按源码判的。** 早期（以及 v4 的前几份个案）是靠"读规格字段 3 的色表，凭感觉判它属于哪一族"。而源码 `rules.mjs` L86–89 只从**四个来源**取样，L90–92 又是**互斥链**。按色表判，**12 行 `palette-*` 命中里有 5 行不成立，假阳性率 42%**。
3. **"贴边"被当成了"命中"。** `hexToHsl` 返回的 s 与 l **不取整**（只有 h 取整），所以 0.8510 与 0.88 之间不存在任何可利用的余量。有三条命中是明知临界仍记为 `earned` 的，其中 S13 那一条的理由栏自己写着"本例 85.1% 贴边"。

## 1 方法与口径：七条源码级更正

以下七条全部来自源码逐行阅读或已核实的裁定记录，**不是推测**。它们是 v4 与早期版本的全部实质差别。

### 1.1 `colourFamily()` 的准确判据

```js
const inRange = (h,a,b) => (a<=b ? h>=a && h<=b : h>=a || h<=b);
export function colourFamily(hsl) {
  if (!hsl) return null;
  const { h, s, l } = hsl;
  if (inRange(h,22,62) && s>=0.16 && l>=0.88 && l<0.995) return 'cream';
  if (inRange(h,6,30) && s>=0.38 && s<=0.85 && l>=0.42 && l<=0.72) return 'terracotta';
  if (inRange(h,244,295) && s>=0.42 && l>=0.3 && l<=0.8) return 'ai-purple';
  return null;
}
```

`hexToHsl` 的关键事实：**h 被 `Math.round`，s 与 l 不取整。**
**推论：凡以"贴边／约等于／四舍五入后可达"为由判为命中的，一律作废。**

### 1.2 palette 只从四个来源取样

`bodyBg`、`sectionBgs`、`button.bg`、占比 ≥0.01 的文字色。
**字段 3 的色表里列出、但没被真的用作背景／按钮／文字的颜色，结构上不可能触发。** 「照着色表逐颗判族」这个方法本身是错的。

### 1.3 cream / terracotta / claude 三者互斥

源码 L90–92 是 `if / else if / else if` 链：

```js
if (cream && terracotta) fam.push('palette-claude');
else if (terracotta)      fam.push('palette-terracotta');
else if (cream)           fam.push('palette-cream');
if (purple)               fam.push('palette-purple');   // 独立
```

**一份裁定里同时出现 `palette-claude` 与另两条中任一条 = 结构不可能，整块作废。**（S06 即此例，三行全废。）
`palette-purple` 独立，可与任一条并存。

### 1.4 `mono` —— 规则文本与实现不一致，**以实现为准**

| | 内容 |
| --- | --- |
| 规则文本 | `rules.mjs:54` — `if (m.type.monoProseShare > 0)`；原文「Monospace is for literal code inside `<pre>/<code>` only.」→ 按字面读，域是"散文正文里的等宽" |
| **实现** | **`probe.mjs:216–219`**：`if (isMono(t.ff)) { ... if (!t.inCode) { monoProse += t.chars; ... } }` → **只有 `inCode` 一个条件，没有散文过滤** |
| **后果** | `<pre>/<code>` 之外的**所有**等宽字符（编号／日期／读数／金额／页码／坐标／时刻）全部计入 `monoProse`。**页面只要有一处非代码等宽，规则就触发。** |

**修正后的口径：以实现为准，凡在 `<pre>/<code>` 之外使用等宽一律记为触发**；规则文本的域更窄这件事写进"非规则观察"留痕，**但不能因此把命中抹掉**。（本文件先前版本据此压掉了约 9 案，是错的。）

**本批规模：`mono` 是 30/30 触发。** 核对 30 份 `scheme-specs/S*.md` 的字段 4，**每一案都声明了一款承担"辅助数字"的等宽面**：编号／期号／道岔号／标本号（30 案）、金额／税率／价格列（≥5 案）、读数／刻度／坐标／遥测（≥10 案）、页码／字数／印数（≥4 案）、时间戳／日期／年份（≥6 案）。

> **逐案表格的一个已知偏差：** `v4/S*.md` 的命中表里只有 **13 案**列了 `mono`。原因是这批文件里的多数在**本次口径修正之前**判定，当时（错误地）按"散文域"把它压掉了。**逐案表的 13 案是修正前的子集，权威数字是 30/30**；合并时凡引用 `mono` 计数，一律用 30/30，不要用 13。

**关键点：这个 30/30 是"被规定的"，不是"三十个方案共有一个毛病"。** `01-research-brief.md` 与 12 字段格式**强制要求字体三分工（标题／正文／辅助数字）**并规定辅助数字必须等宽对齐——**brief 要求的东西，正是这条规则禁止的。** 30 条命中全部是那条强制条款的产物，**按三重裁定口径全部为 `earned`**。

**另一处独立缺陷：** `probe.mjs:39` 的 `isMono()` 只比对 `iiiiiiii` 与 `WWWWWWWW` 的实测宽度——**宋体（Songti／SimSun）等拉丁字形定宽的中文回退栈会被整页判成等宽**（S08 实测）。

### 1.5 六条渲染专属规则，散文层面结构上不可能判定

`covered-text`、`clipped-text`、`pinned-over-picture`、`long-pin`、`still-page`、`empty-screens` —— 需要真实渲染 + 多滚动位置数据。**已发生 3 例可证伪误报**（S01、S07 报 `covered-text`；S10 报 `still-page`）。

### 1.6 `font-count` 对中文站有结构性下限

中文站天然需要 ≥3 款（拉丁显示／拉丁或中文正文／中文），工具目标是 2 款。**该规则在任何中文主站上都不可能达到"无触发"。**
判据：**3 款 = 中文站下限 → earned；第 4 款看它有没有非"字体气质"的机制（承载脚本／承载量测／承载退化），无且可合并 → habit。**
**这与"24/26 命中"一起说明：那个 24 是工具与 CJK 的不匹配，不是 24 个方案共有一个毛病。**

### 1.7 `font-fallback` 永不可判 `earned`

已核实裁定第 16 条。10 案实测：earned 0 / habit 9 / indefensible 1。

## 5 工具盲区与已定位缺陷

### 5.1 八个已定位的工具缺陷（都有具体证据）

| # | 缺陷 | 证据 |
| --- | --- | --- |
| 1 | `isMono()` 把中文衬线回退栈判成等宽 | `probe.mjs:39` 只比对 `iiiiiiii` 与 `WWWWWWWW` 的实测宽度。S08 的 `mono` FAIL 来自**宋体（Songti／SimSun）拉丁字形定宽**；同页第二条 `mono` FAIL 来自 lint 把 Google Fonts URL 里的 `family=IBM+Plex+Mono` 当成 `font-family` 声明做了静态扫描 |
| 2 | `inspect.mjs` 传目录会假 FAIL | 用法是 `<url \| file.html>`。**同一个页面，传目录得 3 FAIL / 7 WARN（`broken-image`「相对资源全部 404」），传 `index.html` 得 5 FAIL / 4 WARN，而允许模式是 0 FAIL / 2 WARN**——同一页三种结果，只因调用形式不同 |
| 3 | impeccable 文件模式是假绿 | `gradient`／`shadow`／`eyebrow`／`mono` **只在 URL 模式触发**。`--json` 走 stdout，文本模式的发现走 stderr；退出码 0 干净 / 1 有发现 / 2 用法错误 |
| 4 | `document.fonts.check()` 对不存在的字族返回真 | 字族是否真的能加载，不能用这个 API 验证 |
| 5 | `lint.mjs` 的 "lock" 子串会吞掉目录名 | 字符串匹配未做词边界 |
| **6** | **规则文本的域 ≠ 实现的域（`mono`）** | 规则说「Monospace is for literal code inside `<pre>/<code>` only」，实现 `probe.mjs:218` **只有 `inCode` 一个过滤条件、没有散文过滤** → 所有非代码等宽都计入。**后果：本批 30/30 触发**（见 §1.4、§5.5）。这是唯一一条"文本读起来没问题、实现却不给豁免"的规则 |
| **7** | **规则名描述的是手法，实现匹配的是属性（`gradient`）** | `probe.mjs:321` 把 `repeating-linear-gradient` 一律计入 `gradient`。S29 的黄黑 45° 警示条纹是**硬边、零插值**的——规则真正针对的"色彩插值色阶"并不存在，照样触发。**与本表第 6 条同型。** 推论：任何用 `repeating-linear-gradient` 画硬边条纹的方案都会触发 `gradient`，且都该判 `earned` |
| **8** | **同一个 1px 边，写法不同就落到三条不同规则、两种严厉度** | `probe.mjs:337/338` 是 `else-if`：**同一个 1px 边——写成四边 `border` → `outlined-box`（≥3 个即 **FAIL**）；只写单轴 → `hairline`；用 `box-shadow: 0 0 0 1px` 顶替 → `shadow`（317–319）**。视觉完全相同，裁定分属三条规则。**这是"实现按属性匹配、不按视觉"的第三个实例**（前两个是第 6、7 条） |

### 5.2 工具盲区：**没有那个 CSS 属性，就没有那条发现**

三条已确认的规避，都是用**另一种实现方式**绕过按 CSS 属性检索的规则：

| 规则 | 它查什么 | 本案怎么绕过 | 案 |
| --- | --- | --- | --- |
| `gradient` | CSS 色彩插值 | 预先烘焙成位图渐晕，规格自述「避免出现平滑色带」 | S03 |
| `shadow` | `box-shadow` | 声明 3px 单向硬投影，但用**非 `box-shadow`** 实现 | S08 |
| `dashed` | `border` 的 dashed | 用平铺位图 + SVG `stroke-dasharray`，"不是 `border`" | S09 |

**`glass` 与 impeccable 的 R7 双双落空，是最有说服力的一例：** S08 的冻结美学家族就是 **Glassmorphism**，而两条规则都没触发（`S08-impeccable.json` 是 7 字节，即 `[]`）。裁定结果正确——但原因是它把 `backdrop-filter` 全禁、把"玻璃"重做成 6–10px 几何侧壁的琥珀厚板。**一个真正彻底的改造，在判据眼里就是"这里没有玻璃"。**

### 5.3 其他盲区

- **全屏 SVG 矢量画布**（S20）既不算图片，也不算主导元素。
- **位图渐晕与 CSS 渐变的区别，工具看不见**（S03）。
- **非 `box-shadow` 的硬投影完全不可见**（S08；S11 用 SVG `<pattern>` 画铁窗格投影，S22 用几何暗带做折痕，同型）。
- **所有 SVG／位图断线对 `dashed` 不可见**（S09）。
- **`overflow` 与 `focal-point` 需要真实渲染**：S11 的"向右出血 24px"、S26 的"倾斜块边界"都因规格没给外距而无法机械判定。

### 5.4 两个工具对同一处用法可以给出相反裁定

**已记录两组，两组都不能相加：**

| 组 | taste-skill | impeccable | 案 |
| --- | --- | --- | --- |
| 等宽用于量测 | `mono` 报（修法：「monospace 只给 `<pre>/<code>`」） | **R11 明文豁免 code／data／measurement** | S04、S03 |
| 章节编号 | `numbering` **FAIL** 级（修法：写进文字里或用真 `<ol>`） | **R4 明文豁免"顺序本身携带读者需要的信息"** | S11 |

这给出第三波判定的五条边界：

1. **坐标落在窗口内 ≠ 属于第三波**（S22、S26 在窗内）。
2. **坐标落在窗口外 ≠ 不属于第三波**（S04 h31.11°、S21 l0.3000 都在窗外）。
3. **要看暖色在结构里干什么活**——S26 的红是承重色版，不是温柔点缀。
4. **要看它是"装饰件"还是"结构件"**——S04／S21 的锈是装饰性强调，S08 的琥珀是**材料色**（滤光片本体）。
5. **两半可以独立出现**（S08 只有铁锈腿，S19／S20 只有暖米腿）。

**可判定的定义：第三波的特征是"暖米底 + 陶土／铁锈作为装饰性强调"这一整套默认选择，不是任何一颗 HEX 的坐标。**

**同一条链上还有两处反向教训：**

1. **S09 拒绝了 07 号的建议，而且拒绝是对的。** 07 号建议把主色移到 **H≈283°**，而 283° 落在 `palette-purple` 的 244–295——**采纳它就会凭空造出一条"AI 味主色"命中**。S09 的拒绝理由：「色相属矩阵冻结的配色情绪分量」。**07 号检查了"这个新色和什么冲突"，没检查"这个新色落在哪条禁令上"。**
2. **S27 把旧读数留在了校验行上**（§7.5 表第 2 行）——同一份规格里，正文的 11.94:1 是对的，校验行的 13.36:1 是旧值。

**结论：审计建议本身需要被审计。** 一份"替换色清单"至少要通过三道检查才能落地——**①它是按哪个背景算的；②它落不落在哪条禁令上；③它的读数有没有随上游修订一起更新。**

### 7.7 第六条边界：照处方配色的案子，两条判据都看不见它

tells.md §3 给第三波开的**处方原文**是「**Warmth from a low-chroma stone, a deep ink…**」。S22 的底色正是一颗 **s＝11.69% 的低彩度石色**（`#DDDAD4`），正文墨是 **l＝16.08% 的 deep ink**（`#2E2A24`）——**它是照处方配的色。**

| 判据 | 结果 |
| --- | --- |
| `colourFamily()` | **两轴同时不达**：cream 的 s 差 0.0431、l 差 0.0310 → 不落任何 palette 族 |
| tells.md 三波登记表 | 三条腿逐核全不成立 → 不进任何一波 |
| **观感** | **仍落在同一片暖纸＋侘寂色温区**（三色饱和度只有 11.69%／10.98%／12.20%） |

**因此真正的族群名不是"暖米底＋陶土"，而是"暖纸＋侘寂"——它在三波表里没有任何条目。**

> **第六条边界：第三波的实际范围比它的登记表大。** tells.md 用**坐标清单**去登记它，而**处方文字描述的是色温**。照处方写出来的案子，恰好穿过两条判据之间的缝——`colourFamily()` 查不到，三波表也查不到。

**这条同时解释了 S22 为什么只能判"未判定波次"**：它在色温上属于这个族群，在坐标上不属于任何一条腿。**正确处置是"未判定"并单独登记，不是硬塞进某一波、也不是硬排除。** 注意 S26／S27／S29 也都贴着这条缝（§7.1：三条明度精确同值 0.809804 却互不相同）。
