## 0. 先说最要紧的：我原来报的那条"唯一确凿发现"是假的

初版 §2 说：

> S08 是真偏差。规格说「<768px 转垂直堆叠」，实际是「<640px 才转」。
> 641–767px 区间仍是等距横向布局。

**这是错的，而且错得很干净。** 详见 `deliverables/73-exec/LEAD-RETRACTION-s08.md`。

三处错：

1. **我编了一个规格里不存在的档。** 规格只有三档（`<768` / `1024–1439` / `≥1440`），
   我读成了四档，把 `768–1023` 当成了一档。它其实是规格的空档。
2. **我只看了 `@media` 的条件，没看它改了什么。** `style.css:277-291` 的
   `@media (max-width: 1023px)` 里写着 `perspective: none` / `transform: none` /
   `position: static` —— **那正是"等距轴转垂直堆叠"**。
3. **方向搞反了。** 规格要求 `<768` 堆叠，实际 `<1024` 就堆叠 —— 是**超集**，不是遗漏。

锐评 Agent 用 Chrome 无头实测了 9 档宽度（`_p3out/s08-stack-probe.mjs`）：
500/608/668/**728**/852/992/1008 全部堆叠（板高 54px），1388/1408 是等距（300px），
分界正好 1023/1024。**728px 在 641–767 区间内，实测是堆叠。**

如果我按原结论去改 `640→767`，不会改变任何视觉结果（真正让它堆叠的是 1023 块），
却会扰动一个已取证、已有 2 条 FAIL 的案。

## 2. 面积和（31 条 / 29 案）：算术 30/30 正确，但**表述不能高估**

### 探针改了三轮才敢下结论

| 版本 | 报出偏离 | 根因 | 修法 |
|---|---|---|---|
| v1 | 9 案 | 同一 hex 重复计数（S02 的 `#B8860B` 出现 18% 与 38% 两次） | 同一 hex 只取第一次声明 |
| v2 | 1 案（S26） | 否定语境的 hex 被算成声明色（`#6366F1` 是"反的是"） | 分句含否定词则丢弃 |
| v3 | **0 案** | HSL 分量被当成面积（S26「饱和压到 21.7%」） | 先剥掉「饱和/明度/色相 + 数字%」 |

最终：**面积和 = 100 的案 30/30**。

### 但这个「30/30」的含义被我初版夸大了

锐评 Agent 的指正（我核实后接受）：

> 它核的**是规格自己的加法**。29/30 规格字面就写着「面积和 100」。
> 真正碰 CSS 的只有 10 案（这 10 案 hex 完全交叠，是真的），
> **另 20 案的原型面积从没被检验**。

所以正确的表述是三段式：

| 层 | 结论 | 证伪能力 |
|---|---|---|
| 规格自身的加法 | 30/30 精确 = 100 | 强（能抓"规格写错面积"） |
| 规格 vs CSS 注释里的面积声明 | 10 案可比，10/10 一致；另 20 案 CSS 无面积注释 | 弱（只覆盖 1/3） |
| 原型**渲染出来的真实像素面积** | **未检验** | 无 |

锐评另外手工核了 S02(58+18+20+4)、S13(56+27+9+8)、S26(44+30+14+12)，都精确 = 100，
且**没有真面积声明被丢弃**（丢弃项全是重复 hex / 否定语境 / HSL 分量，都该丢）。
探针本身有真本事：4 类变异全抓到（+2→102、−3→97、删色→96、加色→107）。

## 3. 断点（67 条 / 30 案）：29/30 全覆盖（修完切片后）

**初版报的「21/23」和重写稿一度写的「28/30」都不对。** 两处探针 bug：

| bug | 后果 | 修法 |
|---|---|---|
| 分母硬编码 `- 7`（从栏数探针抄来） | 报 21/23，真实分母 30 | 用循环实际计数 |
| 固定切 `字段5起点 + 1800` 越界 | 把字段 8 的 `border-radius ≥ 100px` 当成断点，报「S13 缺 100」 | 切到下一个字段标记为止 |

修完后：**29/30 全覆盖，1 案有缺（仅 S08），且经核实不是缺陷。**

| 指标 | 初版 | 重写稿 | **最终** |
|---|---|---|---|
| 分母 | 23（硬编码 `- 7`） | 30 | **30** |
| 全覆盖 | 21 | 28 | **29** |
| 有缺 | 2 | 2（S08、S13） | **1（仅 S08）** |

### S08 的「缺 768」不是缺陷

见本文 §0。规格的三档是 `<768` / `1024–1439` / `≥1440`，
CSS 是 `<640` / `<1024` / `1024–1439` / `≥1440`。
`768` 这个数字确实不在 CSS 里，但**「<768 堆叠」这个行为被 1024 块超集覆盖了**。

### S13 的「缺 100」是我的探针越界

**初版归因也是错的。** 我写「100 是 100ms 时长」，但正则要求 `px`，`100ms` 物理上不可能匹配。

真实来源：探针固定切 `字段5起点 + 1800 字符`，而字段 8 的
`border-radius ≥ 100px` 落在切片尾部（距字段 5 起点 1756 字符）被捞了进来。

**结论对（不是真偏差），归因错**——而"归因错"比"结论错"更危险，它会让人去修错地方。

## 4. 基线（29 条 / 29 案）：全部成立

判据：规格说「基线 Npx」，CSS 里该值应作为变量定义或反复出现的间距单位。

结果：**全部有变量定义或 ≥3 处出现**。S03 只有 1 处字面量但判为通过，

## 5. 栏数（118 条 / 24 案）：**不可核，撤回初版结论**

初版写「11 条机器确认成立」，**锐评证明这个数字站不住**：

`explain()` 的判据是「spec 能被某个 CSS 轨道整除就算能解释」。
我用实测轨道集 `[1,2,3,4,6,8,12,16]` 对随机整数 2..41 跑 1000 次：

```
被判「能解释」的比例: 68.8%
```

**随便编一个栏数，近七成会被判"能解释"。** 这个判据没有区分力。

锐评抽 3 个 FULL 人工核：
- S04：真
- **S16：假阳性**（漏抽「4/6/7/9 栏」前三个，只剩 9、12，再用 `%3` 洗白，CSS 里根本没有 12 栏）
- S10：推理无效（抓的是「第 3 栏」序数，结果碰巧对）

**结论：栏数这一类我给不出机器判定。** 118 条里 0 条可信，需要人工看。

原因是布局意图不是正则能解析的：S03 用 `grid-template-columns: var(--axis-w) minmax(0, 1fr)`
实现 3/9 比例，S10 用 `6fr 7fr 9fr 8fr 5fr` —— 都不含 `repeat(12,...)`。

| 类别 | 断言数 | 机器判定 | 结果 |
|---|---|---|---|
| 面积和 | 31 | 可核 | 规格自身加法 30/30 正确；与 CSS 注释交叉 10/10；渲染像素未检验 |

### 净结论

**30 案 × 260 条机械断言，没有一条真实的规格-CSS 不一致。**

这本身是有价值的信息：这套原型的规格忠实度相当高。
但它的价值**不在"找到 1 个 bug"**（那个 bug 不存在），而在：

1. **可核性分类**（260 / 154）—— 下次有人问"这些页面符合规格吗"，
   第一件事应该是问"哪部分问得出客观答案"
2. **假阳性比假阴性更贵** —— 本次三次修探针（面积和 9→1→0、断点 21→28、
   栏数 11→0）全是假阳性。若第一版就下结论，会报出三个错误判断，
   其中一个（S08）还差点让人去改一个正确的实现
3. **诚实承认不可核** —— 栏数 118 条我给不出判定，就直说
