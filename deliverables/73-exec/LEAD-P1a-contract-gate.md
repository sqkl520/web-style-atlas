## 1. 为什么做这个

`prototypes/_CONTRACT.md` §7.2 写完成判据：

> `render-scheme.mjs` 跑通，**`FAIL = 0`，或 FAIL 集合 ⊆ §9.15 允许表 ∪ 逐案批准记录**，
> 且每条在交付说明里有一条引到文件行号的豁免理由。

但这句判据从前**只靠人读**。这个仓库已经为它翻过一次车——契约 §9.15 的
`palette-terracotta` 那一行自己记着：

> **⚠️ 这一行是 Lead 于 2026-10-24 补登记**：此前 README 与「已知缺口」长期写
> "S08 琥珀是已知豁免，理由见 §9.15"，**而 §9.15 从来没有这一行**——豁免被反复
> 声称却从未落进允许表（51/55 号双语审计抓出："引用跳空"，按本仓库 §7.4 自己的
> 定义即 bug）。

补了那一行之后引用为真，但**没有任何机制保证它下次不会再跳空**。本闸门就是那个机制。

## 2. 做了什么

新建 `prototypes/_build/check-contract.mjs`，查六件事：

| 断言 | 查什么 | 破坏时 |
|---|---|---|
| **C0** | `report.json` 缺失/损坏 → 无法判定 | exit 1（「无法判定」≠「成立」）|
| **C1** | 30 案 `report.json` 的每个 FAIL 规则名是否都在 §9.15 允许表里 | exit 1 |
| **C2** | §9.15 登记的规则名是否真的存在于规则引擎 `RULE_IDS` 里；引擎源码读不到也算失败 | exit 1 |
| **C3** | §9.15 登记但当前无案触发的规则 | INFO（审计线索）|
| **C4** | **文档声称的 FAIL 是否等于实测 FAIL**（反向断言） | exit 1 |
| **C5** | §9.15 登记的规则是否**可能**产生 FAIL（引擎里有没有 FAIL 分支）| WARN |
| **C6** | §9.15 里"像规则行但没解析出规则名"的行数 | WARN（防判据静默缩小）|

**刻意不查 WARN**——契约只对 FAIL 有约束。

## 2.1 锐评验收打了三轮，每一轮都揭出一个真缺陷

第一版只有 C1/C2/C3，被判「不通过」。以下是逐轮修复记录——**这一节比结论更重要**，
因为它记录了"一个闸门怎样从看起来对、到真的对"。

### 第一轮：方向错了（规划 Agent + 红队独立指出）

> C1 守的是「**多出来**的 FAIL」。但今天真正的问题是**文档写着有、实际没有**。

正例两处，C1 全都无反应（因为 FAIL 集合是空集，空集是任何集合的子集）：
- `_CONTRACT.md:110` 称「S13 的 17 处 `shadow` + `button-fx` 属真未修」，实测 0 条
- `README-EN.md:425` 称同一件事（中文版 README 已纠错，英文版没跟上）

→ 加了 **C4**。细节见 `deliverables/73-exec/LEAD-doc-decay-s13-shadow.md`。

### 第二轮：闸门自身有两个 bug（规划 Agent 用变异测试打穿）

| 缺陷 | 位置 | 后果 |
|---|---|---|
| **切片锚错 84 行** | `md.indexOf('9.15')` | `'9.15'` 首次出现在**第 110 行**（§6 表里引用它那行），真标题在第 **194 行**。§6 整张表落进"允许表" |
| **「无法判定」被当成「成立」** | `C0` 只报 WARN | report.json 缺失/损坏时 `continue`，exit 只看 FAILS ⇒ 假绿 |

第一条今天没炸纯属运气：§6 的规则名写成 `| **正文不得 <15px** |`（加粗、无反引号），
解析器只认反引号。但只要有人往 §6 加一行 `` | `shadow` | … | ``，它就会被当成允许规则
（实测确实变成 exit 0 的假绿）。

### 第三轮：C1 是恒真式 / 契约里没有 §7.4 / C4 会反向伤人（P1a 锐评 Agent）

**① C1 在今日数据上近乎恒真式。** 这是最重的一条：

`font-fallback`（`rules.mjs:103`）与 `measure`（`rules.mjs:119`）在规则引擎里
**只有 `add('WARN', …)` 分支，根本没有 FAIL 分支** —— 它们永远不可能出现在 C1 的输入里。
剩下 3 条里 `mono` 在 30 案实测触发 0 次。
所以今天真正参与 C1 判定的只有 S08 的 2 条规则，而这 2 条本来就是为 S08 登记的。

→ 加了 **C5**：直接读引擎源码，看每条允许规则有没有 `add('FAIL', '<rule>'` 这个字面。
报告「2/5 条登记规则没有 FAIL 分支，C1 的有效判定面只有 3/5」。

**② 契约里根本没有 §7.4。** 实测：397 行里 `7.4` 只出现在 L127 与 L201 两行、共 4 处，**全是引用、无定义标题**。
而我在闸门第 17 行写「按本仓库 §7.4 自己的定义，那是 bug（引用跳空）」——
**一个治引用跳空的工具，立论本身引用了不存在的章节。** 已改为直接描述现象，不引章节号；
契约第 201 行那处同样的引用也一并改了。

**③ C4 会假阳性到让人删正确文档。** 锐评在收尾时**现场撞到**：
并行写入者往 `README.md:177` 加了一行**介绍 C4 这个工具**的文字
（「C4 当天抓到两处…S13 有 17 处 shadow 未清，实测 0 条」），闸门立刻 exit 1。
它把「描述工具能力」读成了「仍在声称欠款」。

→ 加**元语境判据**：窗口里出现「为什么需要 / 检查器 / 断言 / 闸门 / 抓到 / 实测 0 条」
就视为元描述放过。这比继续往词表堆词更稳——元语境是可判定的结构特征。

**④ 两处 fail-open。** 实测：移走 `rules.mjs` → exit 0（绿）；删掉一行规则名的反引号 →
允许表**静默 5→4**，C2 仍报 4/4 全绿。

→ `rules.mjs` 读不到改为 **FAIL**（C2 的 fail-open）；新增 **C6** 统计"像规则行但没解析出"
的行数。

### 第四轮：C4 的判据被打穿两次，第二次它抓到了一条我自己漏掉的真腐化

**① 元语境判据过宽（终验打穿）。** 上一版 isMeta 是词表 OR，只要 ±410 字符窗口里
出现任意一个元词就放过。终验构造 9 条真欠款声称、每条只嵌一个元词，**9/9 全漏报**。
→ 改成「元语境主语 + 工具动作落在同一句」的结构判据。10/10 通过。

**② 结构判据仍可绕过（复核打穿）。** 复核构造 4 条**同时是元描述又是真欠款**的句子：

```
这个工具至今没有发现：`S13` 的 17 处 `shadow` 属真未修。
检查器没有报出 `S13` 的 17 处 `shadow` 属真未修，所以它还欠着。
`S13` 的 17 处 `shadow` 属真未修——该规则从未被任何断言检测到已清。
`S13` 的 17 处 `shadow` 属真未修；这个工具只会据此放行，不会修它。
```

4/4 全漏报。→ 加「元描述句若自身含欠款核心词则不算元描述」+「否定式工具动作也算欠款」。
后来还发现 `isRetracted` 也在 ±410 窗口里生效，把「从未检测到**已清**」误当成撤回词。
→ 撤回判定改为逐句。

**③ 修完之后，C4 立刻抓到一条我自己漏掉的真实腐化。**

`README-EN.md:427` 的「Limitations」段还写着：

> ❌ **Four older prototypes still have gate failures —— 8 in total**:
> `S07` `mono` (1); `S08` `palette-terracotta` + `font-count` (2);
> `S13` `mono` + `shadow` (17 occurrences) + `button-fx` + `empty-screens` (4); `S21` `mono` (1).

实测四案的 FAIL 数：

| 案 | README-EN 声称 | 实测 |
|---|---|---|
| S07 | 1（mono） | **0** |
| S08 | 2 | 2 |
| S13 | 4（mono/shadow/button-fx/empty-screens） | **0** |
| S21 | 1（mono） | **0** |
| **合计** | **8** | **2** |

中文 README 早已改成「`S08` 一案仍有闸门 FAIL，合计 2 条」，**英文版落后了整个版本**。
这正是 C4 该抓的东西——而它是 C4 在被修好之后自己抓到的。

已改英文版，并在其中注明「An earlier revision said 8 in total … That was stale」。

## 3. 为什么它不是恒真式（变异测试 8/8 + C4 另测 4/4）

本仓库踩过两次「恒真式闸门」：第 71 轮的 R2/R3/R4（`palette[0]===bg` 等）
是构造恒真式，30/30 全绿却测不出任何东西。所以新闸门必须先证明它会红。

### 三套变异测试 + 一个专项，合计 26/26

| 套件 | 数量 | 覆盖 |
|---|---|---|
| `deliverables/73-verify/ab-contract2.mjs` | 8 | C1/C2/C0 的正反两面 |
| `deliverables/73-verify/ab-c4.mjs` | 4 | C4 能抓新腐化、不误伤撤回记录 |
| `deliverables/73-verify/ab-c4-meta.mjs` | 10 | **isMeta 收窄**：9 条真声称全抓 + 1 条元描述放过 |
| `deliverables/73-verify/ab-failopen.mjs` | 4 | 两处 fail-open 的修复 |

其中 **M1b / M5 / M6 是修完才通过的**——它们证明那两个缺陷是真的，不是理论担忧。

`ab-failopen.mjs` 的四个：

| 变异 | 期望 | 旧版行为 | 现在 |
|---|---|---|---|
| F1 移走 `rules.mjs` | exit 1 | **exit 0（fail-open）** | ✓ exit 1 |
| F2 删掉 `mono` 的反引号 | C6 报警 | **允许表静默 5→4，C2 仍 4/4 绿** | ✓ C6 报警 |
| F3 C5 报出没有 FAIL 分支的规则 | 报 WARN | 无此断言 | ✓ |
| F4（反向）恢复后 | exit 0 | — | ✓ |

`ab-c4-meta.mjs` 的 10 个（**复现终验的攻击**）：

终验构造了 9 条真在声称欠款的句子，每条只嵌一个元词，上一版 isMeta **9/9 全放过**。
修正后这 9 条**全部被抓到**，且 1 条真元描述（「C4 上线当天抓到两处…」）正确放过。

### 踩过的七个坑（都写进了注释）

1. **变异测试没有隔离**：`ab-contract2.mjs` 第一版在每个变异**末尾**才 `restore()`，
   M1a 写入的 `invented-rule` 残留到 M1b，且跑完一次后仓库留下一条 `shadow` FAIL。
   **修法：每个变异开始前和结束后都 `restore()`。**
2. **C4 把记录纠错的文字当成了新声称**（第 1 次）：改完文档后 C4 反而变红。
   **修法：加撤回判据**（"是错的/已清账/was wrong/cleared"）。
3. **C4 把介绍工具的文字当成了新声称**（第 2 次）：README 检查器表里的
   「为什么需要 C4：它抓到两处…」被判成仍在声称。
   **修法：加元语境判据。**
4. **元语境判据过宽到失效**（第 3 次，终验打穿）：只要窗口里出现任意一个元词就放过，
   9 条真声称 9/9 漏报。**修法：改成「主语+动作落在同一句」的结构判据。**
5. **C6 把表头当成了数据行**：`| 规则 | …` 和分隔线 `| --- |` 都被计入"未解析"。
   **修法：排除表头与分隔线。**
6. **注释里的正则片段提前闭合了块注释**：写 `/…|check-*/` 作说明时，
   其中的 `*/` 让整个注释块在这里结束，导致语法错误。**修法：正则用文字描述，不贴原文。**
7. **`JSON.stringify(j, null, 2)` 会改掉 report.json 的缩进与键序**。
   内容正确、格式被改。跑完必须 `git checkout --` 还原。

## 4. 三条 C3 线索（不是失败，是待审计）

`mono` / `font-fallback` / `measure` 登记在 §9.15，但当前 30 案没有一条触发。

三种可能：
- 这三条规则真的已经修好了（那 §9.15 该收窄）
- 它们在 768/390 视口触发，但 `report.json` 的 `findings[]` 只保留 1440 的判定
- 规则引擎行为变了，某条不再产出

**没有查明是哪一种**——这是本闸门刻意留给下一轮的线索，不是遗漏。

## 6. 没做的事

- **没有把 C1 接进「全链」脚本**（如果仓库有一个统一的 `verify-all`）。
  现在它和 `check-docs` / `check-stale` / `check-twolines` 平级，需要单独调用。
- **没有查 §9.15 之外的条款**。契约里还有 §9.14（`measure` 的 0.5em 假设）、
  §9.16（纹理挂 body 会伪造通过）等，同样「声称了没人查」。本闸门只锁了 §9.15 一个门。
