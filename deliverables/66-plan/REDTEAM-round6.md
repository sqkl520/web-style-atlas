## 2. 逐条证据

### 2.1 前提 1：`minItems` 被讲成「我实际有 N 个」

**Lead 的证据成立**（HEAD 版逐字）：

```
$ node _p1_prompts.mjs
S07 minItems=46 | 1. 我实际有 46 个条目，就排 46 个：
S29 minItems=23 | 1. 我实际有 23 个条目，就排 23 个：
```

30 案全部命中，N 的分布（`p1b-out.txt`）：

```
min=6 med=9.5 max=46 合计=370
  6–10: 17 案   11–15: 7 案   16–20: 3 案   21–30: 2 案   31–99: 1 案
  N ≥ 20 的只有 5 案：S07=46 S17=27 S18=20 S19=20 S29=23
```

**但「错得多严重」这个问题，Lead 问错了方向。** 三个反证：

**(a) N 不是"至少要这么多"，也不是"该版式需要的最少条目"——它是真页上排了几个。**

```
$ node _p16_final.mjs
== (3) S07 真页的条目数 ==
  <ol> 各自的 li 数 = [18,28]  合计 46
  提示词里说的 N（capacity.minItems）= 46
```

46 = S07 的 `index.html` 里**两组目录 li 加起来**。它是**这个版式排出来的量**。所以「版式设计规模」与「真页条目数」是**同一个数**——Lead 在前提里假设"设计规模和实际条目数可能是两件事"，实测在这个仓库里它们恒等（30/30，`p1-prompts.json` 的 `minItems` 与 `p18-now.json` 的 N 逐案相同）。

**(b) 「数量不够时按实际数量收敛」这句已经不在 HEAD 里了，而且它当初也没兜住。**

HEAD 版 S07 的结构约束段（`p1b-out.txt`）：

```
1. 我实际有 46 个条目，就排 46 个：
   不凑整、不留空位、不留占位符、编号连续不跳号。
2. 这个版式是自动流排版，条目增减只会让页面变短、不会留空位。按你真实的数量排即可，不要为了凑数编造内容。
```

第 1 条命令「排 46 个」，第 2 条说「按你真实的数量排即可」——**这两句互斥**。实测 **17/30 案同时命中**（恰好是 `degrades=no` 的全部案子）：

```
$ node _p1c_conflict.mjs
S01 「就排N个」=Y  第2条=「按你真实的数量排即可」  ← 互斥
... 互斥（第1条命令 N、第2条说按真实数量）: 17 / 30
```

**这才是真正的缺陷，而且它比 Lead 说的那个更硬**：上一轮 `cea8436` 的 commit body 明写修掉了「不要拉高」+「先凑够」这对矛盾（13/30），但**修完之后又长出一对新的**（17/30）。

**(c) AI 拿到「我有 46 个条目」会真的排 46 个吗？——仓库里有现成的端到端实证，答案是"会"。**

`deliverables/62-verify/` 里有三份"只给提示词、让 AI 照做"的产物（`prompts/S07.txt` + `impl/S07.html`）。我逐份数了它到底排了几条（`p8-out.txt`）：

```
=== S07 ===
  提示词说「我实际有 46 个条目，就排 46 个」
  AI 实际产出：article=46  h3=46  figure=7
  h1 = 「存目四十六件：一九五〇至一九九八年的纸与墨」
  两位编号唯一值个数 = 46；范围 1–46
  ⇒ 条目数 == 提示词里的 N ?  YES（照 N 排了）
=== S23 ===  N=9  → li=9   YES
=== S30 ===  N=10 → article=10 YES
```

**3/3 都照 N 排了**，而且 S07 连 h1 都写成了「存目**四十六**件」、编号 001–046 连续。

> **所以前提 1 的准确说法是**：措辞确实把"版式规模"说成了"我的内容量"，**但后果不是 AI 排错数量——AI 排的数量恰好就是该版式该有的数量**（46 是这个版式的正确规模）。真正的伤害是：用户在提示词里被替他说了一句他没说过的话（"我有 46 个条目"）。这是**诚实性问题，不是功能性问题**，严重度低于 Lead 的判断。
>
> 而且这句话的作用在 30 案里**方向一致**：17 个自动流案子 AI 会排 N（正确规模），13 个手工定位案子第 2 条会拉回来。**没有一案的输出是"错的条目数"。**

**工作树状态**：另一个 Agent 已改成「这个版式设计时排了 N 个条目——这是版式的规模，不是你的内容量」，并把三条拆成"归属/不变量/后果"。实测 `p18`：

```
含「我实际有」的案数 = 0        含「版式设计时排了」的案数 = 30
长度 min=1652 max=1946
```

**这个改法是对的，我没意见。** 但它同时**改坏了一件事**：README L80 写「1632–1920 字（中位 1822）」，实测现在是 **1652–1946**。这是**本轮修 bug 引入的新文档腐化**，正是第 7 条要说的那个循环。

### 2.3 前提 3：`o.mood` 是死参数，要修

**不成立。实测它连"假话"都产生不了：**

```
$ node _p19_mood.mjs
== 传 {mood:"MOOD_PROBE_XYZ"} 与不传，输出是否逐字节相同 ==
  相同：30 / 30；不同：0
  输出里出现探针字符串的案数：0
```

**对比上一轮修 `biz/what/action` 的理由**：那三个字段会在提示词里生成「我经营一家小店」这种**假事实**，用户粘给 AI 就会得到一门他没做过的生意。`mood` 一个字节都不改。

**「两者冲突时谁赢」——实测答案是"后加的赢"，而这就是新增功能会造成的伤害**（`p16`）：

```
SCHEMES[S12].tone = 「荒诞幽默 / 玩心」
不传 tone：这个案子的调性是「荒诞幽默 / 玩心」。
传 tone：「安静、有手艺感」→ 这个案子的调性是「安静、有手艺感」。
⇒ 传了就以入参覆盖，SCHEMES.tone 被丢弃：YES（后加的参数赢）
```

注意 `tone` 这个参数**已经**是"死键但有覆盖路径"（仓库里零调用方）。如果给 `mood` 也接一条读取，就会出现**两个能覆盖气质的外部入口**，而 `SCHEMES.tone` 是 30/30 齐全的实测值。**这不叫修 bug，叫给一个已经有真源的维度再加一个假源。**

**「把已知死代码写进注释是不是比删掉更好」——我的判决：是，但注释不算完成，要配一个断言。**

现在工作树里那段注释写得很好（逐键交代活/死、死掉的那次提交 `d4f19ec`、为什么不复活）。但它**无法防止未来有人加回读取行**。缺的是一条断言：`buildStylePrompt(id, {mood:'X'})` 必须恒等于 `buildStylePrompt(id)`。这条断言 5 行就能写，`p19` 就是它。

**(a) 3800 这个阈值在仓库里没有任何推导过程。**

**(b) 用仓库自己的尺子：3800 对"原型页"来说是个荒谬的阈值。**

30 个原型页在 390×844 的页高（取各自 `.inspect/report.json` 的 `metrics.page.height`，不是我猜的）：

**(c) "为次要动线砍内容不值"——Lead 这个方向对，但结论反了：不需要砍内容就能达标。**

我把三个最重的字段（`布局与网格`/`可落地要点`/`动效与交互`）原封不动塞进 `<details>`（DOM 文本一个字不动），实测：

### 2.5 前提 5：行卡 `clamp:2` 视觉截断有 N 案括号不配平

**部分成立。而且 Lead 的 2 和前任的 9 都是对的——它们是两个判据。**

**(a) 第一个被推翻的子前提：「有没有省略号？」——有。**

我用 `Range.getClientRects()` 逐字量出可见文本，再用 CDP `captureBeyondViewport` 以 3× 截了那几行的像素（`clamp3x-S10.png` / `S18.png` / `S12.png`）。**S10 的末尾是 `（悬挂标点与基线偏移的做…）` 那个"…"是真实渲染出来的**，不是我的错觉。`getComputedStyle().textOverflow === "clip"` 但 `-webkit-line-clamp: 2` 会自己画省略号——这是 `line-clamp` 的规范行为，`text-overflow` 管不到它。

所以「没有省略号才是问题」这个判据**指向"没有问题"**：省略号在，用户看到的是"这里被截断了"，而它确实被截断了。

**(b) 子前提「13px 灰色辅助信息」——实测确认，Lead 说对了。**


**把 `prompt-copy.js:901` 的 `display:none` 去掉，并让展开按钮同时切换它。**

理由，按重要性排：

1. **它是唯一一条"README 明文承诺、页面完全不兑现"的**。README L78 写「29 个如实标为没有…**不藏起来**」，而那 29 个词**一次都没被画出来过**（`p22`：点开展开后 `note` 仍是 `display:none`）。
2. **它影响的是最该被影响的人**。29 个词里有电商/金融/政务/医疗/地产——搜索量最大、最需要被告知"这套图集给不了你"的那批。现在他们搜到 0 行，只看到"这一类，这套图集和模板层都给不了你"，但**看不到"哪些同类也没有"这个更重要的信息**。
3. **它的代价是 2 行**（展开后多 2 行文字），修法是一行 CSS + 一处联动，无回归风险。
4. **它不在这 7 条前提里的任何一条**。这正是"红队该找的东西"——Lead 的 7 条全部指向已被人反复看过的地方，而这个洞在 README 的金句背面。

**次优选择**：§2.4 的折叠方案（24/30 → 0/30，零信息损失）。它比"改阈值"诚实，比"删内容"便宜，而且**本仓库已有 4 个 `details` 的成熟先例**。

**明确不建议做的三件事**：
- ❌ 修 `o.mood`（新增功能，制造第二个气质真源）
- ❌ 把模板塞进 `sceneIndex`（撞白名单，且抹掉"独立一层"的定位）
