## 1 缺口在哪：三道闸门，逐层定位到源码

### 1.1 第一道：`read_image` 的模型能力判定

直接读图，得到的是模型级拒绝，逐字如下：

```
Error: cannot read "D:\Web\style\deliverables\tool-runs\S04-inspect-shots\full-1440.png" as an image:
model "deepseek-ai/deepseek-v4.1-flash" does not declare image input;
switch to an image-capable model to read images
```

这句话里的判据在 `dsh-tool-fs/lib/index.js:896`：

```js
if (active.inputModalities === void 0 || !active.inputModalities.includes("image"))
  throw new Error(`cannot read "${requestedPath}" as an image: model "${model}" does not declare image input; ...`);
```

**判据是「活动模型的 `inputModalities` 里有没有 `"image"`」——不是"模型能不能看图"。** 这是一个配置声明，不是能力探测。

### 1.2 第二道：`inputModalities` 从哪来

`dsh-llm-pi-ai/lib/index.js:821 / 836`：

```js
inputModalities: [...model.input]            // listModels
inputModalities: [...resolvedModel.input]    // resolveModel
```

而 `resolvedModel.input` 在 `:1340` 解析：

```js
input: declaredInput(entry.input) ?? base?.input ?? [...request.defaultInput]
```

**三级兜底：内联声明 → 目录基座 → 供应商 `defaultInput`。三条全空就没有图像能力。**

### 1.3 第三道：desktop profile 的 `s3ai` 模型三条全空

`C:\Users\Administrator\.dsh\profiles\desktop\cordis.patch.yml` 里 `s3ai` 供应商的模型是这样声明的：

```yaml
  - id: deepseek-ai/deepseek-v4.1-flash
    name: deepseek-ai/deepseek-v4.1-flash
  - id: nvidia/nemotron-3.5-super-vl-120b-a12b
    name: nvidia/nemotron-3.5-super-vl-120b-a12b
```

**只有 `id` 和 `name`，没有 `input`。** 该供应商也没有 `defaultInput`。

**⇒ 结论：desktop profile 下，`s3ai` 的任何模型都读不了图，换哪个 id 都一样。** 这条不是"模型不支持"，是"配置没声明"——而且它把真正能看图的模型（`nemotron-3.5-super-vl`、`llama-3.2-90b-vision`、`minicpm-v-4.7`）一并挡在门外。

### 1.4 环境里本来就有为这件事准备的插件，但没挂给这条 profile

发现 `@linxin666/dsh-tool-describe-image` v0.2.5（Apache-2.0），自述：

> *"Model-facing describe_image tool for the dsh web GUI: **gives a text-only model image understanding** by asking a vision-language model at an OpenAI-compatible endpoint to describe one image."*

**它就是为"纯文本模型看图"设计的。** 但它挂在 `web` profile（`profiles\web\node_modules\@linxin666\dsh-tool-describe-image`），而本会话跑在 `desktop` profile——`desktop` 的 patch 里没有它。且 `describe-image` 在 `storages` 下**没有任何已存配置**（只在 `pnpm-lock.yaml` 和 `synapse\workspaces.json` 里出现过名字），所以它既没挂上、也没配好端点。

### 1.5 两条可行路径，和那条一行修复

| 路径 | 做法 | 代价 |
| --- | --- | --- |
| **A（本次采用）** | 直调 `https://ai.furry.vg/v1/chat/completions`，把图 base64 塞进 `image_url` | 不动配置、不重启宿主；密钥从 `.credentials.yaml` 按行读取（只用于 `Authorization`，不落盘不打印） |
| **B（对人更省事）** | 给 desktop profile 的模型声明补 `input`，或给 `s3ai` 设 `defaultInput` | 需要改配置并重启宿主 |

**路径 B 的确切改法**（依据 `dsh-llm-pi-ai/lib/index.js:1607` 的 `input: z.array(z.union(MODALITIES))`）：

```yaml
# C:\Users\Administrator\.dsh\profiles\desktop\cordis.patch.yml 内 s3ai 的 models 下
  - id: nvidia/nemotron-3.5-super-vl-120b-a12b
    name: nvidia/nemotron-3.5-super-vl-120b-a12b
    input: [text, image]        # ← 只加这一行，read_image 就会放行
```

改完之后 `read_image` 应当直接可用；另一条路是把 `describe-image` 也装到 desktop profile。

## 2 一级证据：像素测量（不是看图，是算数）

### 2.1 我自己的第一版口径是错的，先纠正

第一版把"相邻行底色差"判据写成 **RGB 三通道差之和 > 24**。结果 S21 报出「12 段底色」、S04 报出「10 段」。

复核后发现那是**我自己的假阳性**：S21 那些"不同底色"是 `#E4DCC9` / `#E3DAC9` / `#D9D0BF` 这种**每通道差 1–12 的 JPEG 噪声与压痕阴影**，不是分区底色。S04 的"10 段"里 6 段是同一个 `#F0E2C8`。

**改成感知阈值（相邻行底色最大通道差 < 20 视为同一种底色）后重跑**，并且另出一个更稳的指标：

> **主要色带 = 纵向高度占比 ≥ 8% 的底色段。**

同时以「**最大单色占比 + Top-2 是否同色系**」作为底色判定的主判据。**口径写在这里，任何人都可以按这两句复算。**

- **能**给出面积占比、底色段数、墨覆盖、空屏、左右贴边墨。

## 3 二级证据：视觉模型读图

### 3.1 选模型花了五次尝试

密钥绑在 `ai.furry.vg` 的 **NIM 分组**上，这决定了候选池：

| 模型 | 结果 |

| `gemini-3-flash`、`gemini-2.5-flash`、`claude-sonnet-4-6`、`claude-haiku-4-5`、`minicpm-v-4.7-35b-a3b-free` | **HTTP 503** `model_not_found`：`分组 NIM 下模型 X 无可用渠道` |

| `nvidia/nemotron-3-nano-omni-30b-a3b-reasoning` | **503** `ResourceExhausted: Worker local total request limit reached (16/16)` |
| `nvidia/nemotron-parse-2.0` | 是**文档解析**模型，输出为乱码 token 流，弃用 |
| **`nvidia/nemotron-3.5-super-vl-120b-a12b`** | **可用**，本文二级证据全部来自它 |

**第一轮它失败 8/14**，返回"空回答"。诊断一次失败请求，原始响应逐字如下：

```
usage: {"prompt_tokens":1347,"completion_tokens":1800,
        "completion_tokens_details":{"reasoning_tokens":1800}}
finish_reason: "length"
message 的键: content, role, reasoning_content
  content: 长度 4   null
  reasoning_content: 长度 6172   The user wants me to identify the main color...
```

**这是一个推理型 VL 模型，`max_tokens:1800` 全被推理 token 吃掉，正文一个字都没轮到。** 修法两处：`max_tokens` 提到 **8000**，并对 `content === "null"` 做 `reasoning_content` 兜底。改完 **11/11 全部成功**。

> **这条值得单独记：任何"模型返回空"的现象，先看 `reasoning_tokens` 是否等于 `completion_tokens`。** 我最初把它当成"这个模型读不了某些图"，那是错的。

### 4.5 【已定性 · 工具缺陷已两次复现】`desktop-page-0N` 滚动截图上的 `#888888` 灰块

一级测量报出：`#888888` 占 **49.9%**，且是全图最大单色。定位其形状：

- **不是散布，是一整块**：列剖面显示 **x 800–1599 的灰度占比 > 50%**；灰度像素总数 **400,010**，而右半幅面积是 800×500 ＝ 400,000 —— **几乎精确等于右半幅的整个面积**。左半幅 x<800 几乎无灰。

| 可能来源 | 核对结果 |
| --- | --- |

| 某一次抓取的偶发故障 | `S08-shots\desktop-page-03.jpg` 与 `S08-shots-allowed\desktop-page-03.jpg` **同为 40,522 B**（逐字节相同）——**两种运行下都在**，不是偶发 |
| 二级看错了 | **独立确认**：`右侧为大片灰色空白区`、`可见缺陷：右侧大片空白区域无内容`、`主色 中灰（约 50%）`、`底色段 深棕黑（左侧）、中灰（右侧）` —— 与一级逐项吻合 |

把同类测量跑遍全部 31 张后，中性灰审计给出决定性结果：

| 图 | Top-8 里的中性色（`R=G=B±6` 且占比 ≥2%） | 占比 |
| --- | --- | --- |

| S03 tablet-fold | `#010101` ／ `#000000` | 8.26% ／ 2.87% |

| **S17 desktop-page-01** | **`#888888`** | **24.27%** |

1. **同一个 HEX**：`#888888`，一个字节都不差；

**⇒ 后果（两条，第二条是给后续所有渲染审计留的口径）：**

- **`S08-shots*/desktop-page-03.jpg` 与 `S17...\.inspect\desktop-page-01.jpg` 都不能用作"页面渲染正常"的证据，需重抓**；两者其余各屏测量正常（S08 fold／page-01／page-02 最大单色 78.0%／45.1%／48.7%；S17 fold 58.6%／68.7%／48.4%），**可用**。

## 6 这次审计仍然不能声称什么

**必须逐条留下，否则上面所有数字都会被读成比它们实际更强的东西。**

1. **这不是"人看过图"。** 一级是像素统计，二级是**另一个模型的转述**。本次关闭的是「**有没有机器按像素看过成品**」，**不是**「有没有设计师判断过它好看」。taste-skill 方法第 8 步的字面要求（"You look at what you made"）仍然只被**代理**满足。
2. **二级是转述，且已被证明会错。** §3.4 记录了它把左对齐读成居中（2 次）、把「徵信」读成「微信」。**它的任何版式结论未经三级核对一律无效**——本文已按此执行，但无法保证别处没有漏网的。
3. **只有 8／30 有原型，且只有首屏与少数几屏。** 另外 22 个方案**没有任何渲染**，本文对它们一个字都没有说。
4. **没有测交互。** 悬停、键盘焦点、`data-loading` 状态、滚动驱动的动画**全部未测**。`inspect.mjs` 独占的 6 条规则（`covered-text`／`clipped-text`／`pinned-over-picture`／`long-pin`／`still-page`／`empty-screens`）需要"渲染 ＋ 多个滚动位置 ＋ 交互"，本次只覆盖了"多个滚动位置"（S04／S08 各有 3–4 屏），**其余两项仍缺**。
5. **折屏图是 JPEG，不是 PNG。** `*-fold.jpg` 的压缩会把精确 HEX 偏移 ±2 左右。**本文所有精确 HEX 都取自整页 PNG**（S04 的 `full-1440/768/390`）；来自 `*-fold.jpg` 的占比是可靠的，色值有上述误差。
6. **没有做真实内容长度测试**（长标题、超长段落、空数据）。
7. **"墨覆盖"这个指标尚无基线。** 8–17% 是常态、36–50% 是异常，这个判断来自本批次内部对比，**没有外部参照**，不应作为独立结论使用。

## 7 结论

**一句话：缺口从"从未打开"变成了"打开了、并且第一次拿到了能证伪规格的数字"。**

四件确定的事：

1. **S04 的面积预算表在成品上不成立。** 两枚声明的油墨（主色 `#96550F` 34% ＋ 辅助色 `#2F7D4F` 26% ＝ 预算的 60%）实测合计只有 **0.30%／0.31%／0.66%**，单色相差 **68–240 倍**；声明占 14% 的背景色实测占 **76–87%**。这是唯一一条把此前的文本内部矛盾升级为实测证伪的发现（§4.1）。**并且它顺带暴露了一个取数风险：主色在终局修正时已由 `#E8871E` 改为 `#96550F`，拿旧值对照会得出完全不同的结论。**
2. **S03 的青色 24% 与实测 0.479% 的落差，这次拿到第三个独立来源**（§4.2）。
3. **S25 声明的第二色 `#2E6B5E` 在成品里不存在**，实测是 `#2A6052`，且裁定 18 要求的 `#181C0D` 确实以 3.3% 存在（§4.3）。
4. **S07"命中禁令骨架"的指控被源码核对推翻**——同时这也说明**二级的版式判断不能直接用**（§4.4）。

两件挂着的事：

5. **`desktop-page-0N` 滚动截图上的 `#888888` 灰块已在两个独立原型上复现**（S08 49.86%、S17 24.27%），定性为 `inspect.mjs` 的工具缺陷；受影响的两屏不可用作证据（§4.5）。
6. **S17 有渲染图，而且它是唯一一个声明配色在像素上完全站得住的案子**（`bodyBg #e1d6bd` 实测 58.6%／68.7%／48.4%；`sectionBg #c9bfa6` 实测 9.5%／6.0%）。**本文第一版说它"从未渲染"是错的，已改正**（§5）。

一条方法学产出，我认为比上面任何单条发现都重要：

7. **VLM 的色域估计可信（与像素测量吻合在 5 个百分点内），版式判断不可信（4 次里 3 次与源码不符），专名转录会幻觉（把「徵信」读成「微信」）。** 这个分界线是可复现的，任何人拿着本文的三级核对流程可以重跑（§3.4）。

**下一步值得做四件**：① 把 desktop profile 的模型声明补上 `input: [text, image]`（一行，见 §1.5），让后续渲染审计不必再走旁路；② 重抓受 `#888888` 影响的 `desktop-page-0N`（或先给 `inspect.mjs` 的滚动抓取加一道"未绘制区域"检测）；③ 建立**"声明面积预算 vs 实测"的机械校验**，把 §4.1 那条从人肉发现变成每次渲染都自动跑；④ 到 768px 亲眼确认 S17 的印章遮字（`covered-text`，§5.2）。
