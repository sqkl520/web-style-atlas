# Q2 开工实测：四处与计划不符的事实

> 2026-11-10　基线 `1718b52`　执行：主线程 + 3 个独立复核 Agent
> 本文只记**实测推翻计划/假设**的部分。计划本身在 `deliverables/74-plan/00-MASTER-PLAN.md`。

Q2 的主题是「让『挑』这件事成立」，计划列了四件事：新增 N31–N35、分布闸门、
详情面板分层、向导与芯片合并答案。开工后逐项实测，**四项里有三项的前提是错的**。
下面每条都给出复算命令与实测值。

## 一、缺口数字：计划写「中间明度 0」，实测是「1」——而那个 1 是尺子造出来的

`00-MASTER-PLAN.md:123` 的 Q2 验收写：「『很安静』从 2 → 5；中间明度从 0 → 2；
少货少图有正解」。逐项复算（`prototypes/_selection/data.js` 的 `axes`）：

| 缺口 | 计划写的 | 实测 | 差在哪 |
|---|---|---|---|
| 中间明度带 | 0 案 | **1 案（S09）** | 计划漏了 S09 |
| 亮底紫 | 未量化 | **0 案** | 色相桶 270–299 / 300–329 / 330–359 **三个连续空桶** |
| 很安静（chroma ≤25） | 2 案 | 2 案（S15/S22） | 一致 |
| 少货少图（minPics ≤2） | 「有正解」 | **0 案**，全库最小 minPics = **4** | 计划高估了库的覆盖 |
| 暖浅色带 | 18 案 | 18 案 | 一致 |

### 1.1 更要紧的：那个「1 案」是 HSL 明度这把尺子的产物

`collect-schemes.mjs:604-613` 用 **HSL 的 l** 判带，阈值 `l >= 78` 算浅。而 S09 的底色是
`#F5C842`（亮黄），HSL l = 61。换成任何感知口径都不是"中间明度"：

| 尺子 | S09 的值 | 判定 |
|---|---|---|
| HSL 明度（现行） | 61 | 中间明度带 |
| **CIELAB L\*** | **82.0** | **浅** |
| WCAG 相对亮度 | 0.610 | **亮底**（`ground` 字段自己也说"亮底"） |

`data.js` 自己的 `axes.ground` 用 WCAG 算，说 S09 是「亮底」；`axes.band` 用 HSL 算，
说它是「中间明度带」。**同一份数据里两个字段互相矛盾，而对外文案照抄了后者。**

30 案里 ground 与 band 互相矛盾的只有这 1 个（复算脚本
`_det/_axes-selfcontradiction.mjs`；第一版脚本把带名后缀写成 `浅带` 而实际是
`暖浅色带`，导致误报 20/30 —— 修好后是 1/30）。

**结论**：按感知口径，中间明度**今天就是 0 案**。「加 2 案」是对的，但理由不是
「从 1 到 2」，而是「从 0 到 2，且其中一案不能再是亮黄」。

**这不是要闸门替产品做决定**：改成 CIELAB 会让对外文案从「暖浅 18 / 中间明度 1」
变成「暖浅 19 / 中间明度 0」。那句文案是产品承诺，该由人定。
分布闸门因此**两把尺子都打印**，判据沿用现行口径（与站点显示一致），把差别摆在报告里。

## 二、分布闸门已建（`check-distribution.mjs`），但「只管新增不管删除」这句话需要拆开实现

计划说「把目标分布写成可计算断言，只管新增、不管删除」。实测下来这句话要拆成**两类红**，
否则闸门会立刻变成「永久红」：

| 类 | 含义 | 今天的值 | 默认 |
|---|---|---|---|
| **回归类** | 以前对、现在错了 | 暖浅占比 18/30 = 60.0%（正好压在 60% 上限）、结构撞车 8 对、7 种调性各 ≥3 | **FAIL** |
| **缺口类** | 一直是缺的，要新增才能补 | 中间明度 1/2、亮底紫 0/1、很安静 2/5、少货少图 0/2 | **WARN**（`--strict` 时 FAIL） |

为什么不能全设 FAIL：`.github/workflows/gates.yml:5` 自己记着这条教训——
「把那种闸门设成阻塞项，等于训练所有人无视红灯」。Q2 的 5 个新案落地后
切 `--strict`，那时缺口类必须全绿。**这个开关本身就是 Q2 的验收判据。**

### 2.1 这条闸门如何防止本仓库的「假绿」

病史（全是实测记录，不是假设）：

1. `check-prompts` 第一版把 `d.mechanism` 用在**目录名字符串**上 → `undefined` → 整块
   断言静默跳过 → 照样打印「FAIL 0」（`check-prompts.mjs:416-419` 记着这段）；
2. `check-docs` 的 `nums/gate` 把句子「转交」给一个看不见它们的正则 →
   `README.md` 写 26 / 8，实测 29 / 2（见本文第四节）；
3. `check-contract` 的 C1 只核 3/5 条允许规则，另 2 条在规则引擎里根本没有 FAIL 分支。

共同形状：**闸门读不到数据 → 不报错 → 打出一个好看的 0**。

所以 `check-distribution.mjs` 的第一条断言不是分布，而是 `dist-parsed`：
每一案必须有完整 `axes`，缺一个就 FAIL 并点名；算出的案数必须等于 `SCHEMES.length`；
带名解析不出来一律 FAIL（不猜）。并且 `--selftest` 用**内存变异**证明 11 条断言
既不是恒真也不是恒假。自测当场抓出三个我自己的 bug：

| 自测用例 | 抓到的真问题 |
|---|---|
| B9「所有案同一个调性」 | **断言有真空洞**：`perValueFloor` 只判「已出现的取值够不够 3 案」，调性塌缩成 1 种时那一种有 30 案 ⇒ 通过。已加 `expectValues` 覆盖面判据 |
| A2「人造完美数据」 | 我把调性名写成「学术严肃」，真值是「学术档案」——清单拼错会永远报"少一种" |
| B7「结构多撞一对」 | **夹具设计错**：把 S02 改成 NEWS-FRONT 的同时拆散了 SPLIT 那对，撞车对数净变化 0。改成新增一案才是真 +1 |

## 三、详情面板「≤180 字判决层」这个数不成立

计划 `:121` 写「12 段压成『判决层（≤180 字）+ 施工层』」。实测 30 案各段字数
（`_det/_judgment-layer.mjs`）：

能回答「这是不是我的店」的只有三段：`def`（长什么样）、`scenes`（哪个行当能用）、
`scenesNo`（哪个行当**不能**用）。这三段合计：

| 组合 | 最短 | 中位 | 最长 | 装得进 180 字的案数 |
|---|---|---|---|---|
| def + scenes + scenesNo | 167 | **279** | 334 | **1 / 30** |
| def + scenes | 145 | 219 | 265 | 3 / 30 |
| def + scenes + scenesNo + risk | 324 | 469 | 613 | 0 / 30 |

**「≤180 字」只有 1/30 的案能装下。** 180 字能装的是
「一句话视觉定义(95) + 当前有效配色(31) + 不适合的场景(49) = 175 字」——
这个组合恰好**丢掉了「适用场景」**，也就是丢掉了正向答案。

替代数（从实测推）：**≤340 字**（30 案 def+scenes+scenesNo 的最大值），中位 279。
或者换一个更诚实的构造：判决层 = `def` 一段（中位 95 字）＋ 一行
「适合 X / 不适合 Y」的**摘要**（不是原文），摘要由人写、长度另定。

另有一条与计划不符：**施工层今天已经是折叠态了**。`app.js:1393-1403` 的 4 个字段
（布局与网格、可落地要点、关键视觉元素、动效与交互）已经带 `foldHint` 默认收起。
所以「分层」不是从零加一层，而是**把判决层提到折叠之上**——12 段里现在平铺的是
前 4 段 + 后 5 段，中间的 4 段折着。

## 四、向导与芯片「各存一份答案」——实测是**五份**，且互相矛盾到会让用户拿不到结果

计划 `:122` 说「行业词、`prompt-copy.js` 里的『你经营什么』、向导五个问题今天各存一份答案」。
实测是**五份**，而且不只是重复，是**互相矛盾**（`_det/_answer-duplication2.mjs`）：

| # | 答案在哪 | 规模 |
|---|---|---|
| 1 | `build-prompts.mjs:172` 的 `SCENE_INDEX`（手写常量） | 44 个词 |
| 2 | `STYLE_PROMPTS.unsupported`（「这套图集撑不起来」） | 29 个词 |
| 3 | 每案 `_specs` 字段 10 的「适合…」 | 30 份 |
| 4 | 每案 `scenesNo`（从字段 10 切出的负向） | 30 份 |
| 5 | `build-prompts.mjs:135-170` 的 `HUMAN.scenes` | 30 份 |

**30 案共自称 69 个行业词，其中 48 个不在 `SCENE_INDEX` 的 44 个词里**——
也就是说方案自己说「我适合文化机构 / 拍卖行 / 科研机构 / 气象看板 / 财务对账…」，
而用户**点不到、也搜不到这些词**。

### 4.1 更严重：芯片与搜索是两条互不相通的路径

| 方向 | 词数 | 具体 |
|---|---|---|
| 芯片能点出结果，手动搜同一个词 **0 行** | **3** | 潮牌（→S12）、修鞋理发（→S09）、小吃店（→S09） |
| 芯片说「没有直连方案」，但搜索**能命中** | **15** | 博客、播客、戏剧、影展、文化节、快闪、工业设备、说明书、开发者工具、运维、数据看板、档案、科普、教育、摄影 |

第二个方向最伤：站点告诉用户「没有为这行做的方案」，而用户同一个词打进去能搜出一堆案。

`潮牌` 那一例的机制很典型：`SCENE_INDEX` 说它直连 S12，而 S12 的 `scenes` 字段写的是
「潮流品牌快闪页」——**换了个说法，全文搜「潮牌」命中 0 行**。S09 同理
（芯片词「修鞋理发 / 小吃店」，正文写「修理、清洁、烘焙、理发」）。

还有个更隐蔽的：`农业` 在 `unsupported` 里（"撑不起来"），但搜「农业」能命中 S19。

**所以 Q2 第四项的工作量不是「合并三份答案」，是「让三个入口回答同一个问题」。**
具体顺序：先建一份**唯一的行业词表**（词 → direct/near 的映射从 `SCENES` 派生，
不再手写第二份），再让芯片、搜索、向导都读它，最后加一条断言：
「每个词的 direct 命中，在该案的 `scenes` 原文里必须能找到同义表述」。
最后这条是最难的，因为它需要一个同义词表——**这是 Q2 唯一没法纯机械做的部分**。

## 五、附带确认：季度复刻验货的六个可度量，`report.json` 只装得下三个

`00-MASTER-PLAN.md:20-22` 把复刻验货定为「唯一能证伪『提示词真的有用』的动作」，
用 DOM 量 6 个：栏数／主轴宽／最大标题字号／正文比／线宽集合／图片位数。

独立复核 Agent 实测（`_det/03-determinism-verify.md`）：S17 的 `report.json` 里
`column` / `Column` / `grid` / `axis` / `lineWidth` / `border` / `gutter` **全部 0 次命中**。
我用 grep 复算确认同一结果。

也就是说「6 个可度量」此前只能兑现 3 个（标题字号、正文比、图片位数）。
另外 3 个过去只能拿 `dna-clean.json` 的**规格值**自我印证——那是「设计说了什么
vs 设计说了什么」，不是「设计说了什么 vs 渲染出什么」。

**本轮已补**：`vendor/probe.mjs` 新增 `metrics.structure`
（`columns` / `axisWidth` / `lineWidths`）。补的过程本身踩了四个坑，全部写进代码注释：

| 坑 | 症状 | 修法 |
|---|---|---|
| `grid-template-columns` 在 `display:block` 上仍返回声明值 | S01 的 390px **单栏**页被判「3 栏」 | 先检查 `display` 是否含 `grid` |
| 栏沟轨道被算成栏 | S01 的 `5fr 24px 4fr 24px 4fr 24px 3fr`（真值 4 栏）→ 数成 **7** | 剔掉 <32px 的窄轨道 |
| 取全页最大栏数 | S07 的 `header.bar` 4 栏（导航条，53 字）压过正文的 2/3 栏 | 按**容器文字量**排序取第一 |
| 单栏返回 0 | 「没测到」与「单栏」混为一谈 | 有正文容器但无多栏 ⇒ columns = 1 |

三案 × 三档交叉验证全部对上 CSS 真值：

| | 1440 | 768 | 390 |
|---|---|---|---|
| S01（`grid` 4 栏 + 铅条） | 4 ✓ | 2 ✓ | 1 ✓ |
| S07（`column-count` 2/3） | 2 ✓ | 1 ✓ | 1 ✓ |
| S17（`auto-fit` 网格） | 3 ✓ | 2 ✓ | 1 ✓ |

### 5.1 同时确认：截图不是字节可复现的，但测量值是

同一份源码连渲染 7 次（`_det/03-determinism-verify.md`，含 7 组归因实验）：

- 8 张 jpg 里 **7 张字节全等**，只有 `tablet-page-01.jpg` 在一个 8×8 DCT 块上抖
  （4:3 两个离散变体，41 像素，每通道 ±1）；
- 归因：不是时间戳（文件里没有 EXIF），是 `.perf` 齿孔 SVG 点阵在缩放时的**亚像素光栅化**；
- **`report.json` 的 810 个测量值在 7 次渲染里零漂移**，唯一变化的是 `at`。

**所以季度验货的基准必须用 `report.json`，不能用截图比对。**
理由不是「截图不好」，是两者的容差需求差三个数量级：要吞掉 41 像素的抖动，
容差得放到「允许任意 1 个 DCT 块内 ±2 通道差」——这个容差同时也能放过
「一条 0.5px 线变成 0.4px」这类真缺陷。

（附带纠错：我最初的两次测量得出「差异只在时间戳」，方向是错的。抖动是**间歇性**的，
两次撞上同一边的概率约 57%——用两次去下一个二值结论，测法本身不稳。）
