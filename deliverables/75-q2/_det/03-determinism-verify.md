## 结论

**断言部分成立。**

- **数字全部复现**：`tablet-page-01.jpg` 总长 184858 字节、两个变体之间只差 **1 个字节**、首差偏移 **51023**；`report.json` 810 个叶子键中只有 `at` 不同。这些都与原断言逐字吻合。
- **但归因写错了，而且结论方向反了一半**：那 1 个字节**不在 EXIF/时间戳里**，它在 **JPEG 熵编码的扫描数据区**里，是一块 8×8 DCT 块被重新量化。解码后是 **41 个像素、每个通道差 ±1**。也就是说像素确实在抖，不是「只有元数据带时间」——原断言给的两种可能里，它落在更严重的那一种。
- **而且这不是「每次都抖」**，是**间歇性**的：第一次复核（3 连跑）里 run1/run2 相同、run3 不同；第二次复核（7 连跑）里出现了 4:3 的两个变体分布。原断言的测法只跑两次，恰好撞上「前两次相同」，如果照它的方法继续跑就会得出「可复现」的错误结论。**两次不够。**
- **最重要的一条**：`report.json` 的 810 个测量值在 7 次渲染里**逐键完全稳定**，零漂移。季度复刻验货的基准是稳的——抖的只有截图。

## 二、那个字节的位置与含义

### 2.1 它不在元数据里

我写了个 JPEG 段解析器（`determinism/../jpeg-parse.mjs`）逐段走完文件头：

```
SOI    start=      0 len=     2
APP0   start=      2 len=    18     ← JFIF 头，无时间戳
APP2   start=     20 len=   474     ← ICC 色彩配置
DQT    start=    494 len=    69     ← 量化表
DQT    start=    563 len=    69
SOF0   start=    632 len=    19     ← 1536x1366, baseline, yuvj420p
DHT    start=    651 ... 842        ← 4 张 Huffman 表
SOS    start=    843 len=    14     ← 扫描头
        ↑ 从这里到文件尾（133835 字节）全是熵编码数据
```

**偏移 51023 距 SOS 头 50180 字节、距文件尾 133835 字节，落在纯扫描数据区**。文件里没有 EXIF 段，也没有任何时间戳字段。原断言推测的「差异只在 EXIF 的某个时间戳字段」**不成立**。

### 2.2 它改了 41 个像素

附近字节对比：

```
offset 51023:  A=0x86(134)   B=0x66(102)   XOR=0xe0
```

前后各 512 字节内**零差异**，所以只有这一个字节被重新编码。

用 ffmpeg 把两个变体解码成 rgb24 后逐像素比：

```
尺寸 1536 x 1366（tablet contact sheet，3 列 x 2 行，每格 512x683）
不同像素数 = 41
bbox: x 64..71, y 352..359
通道差值: 绝大多数 ±1，最大 ±2
```

**41 个像素全部落在 x∈[64,72)、y∈[352,360) 这一个 8×8 块内**，正好是一个 DCT 块。差值是每个通道 ±1 —— 这是 DCT 系数在量化边界上的抖动被反变换后的典型形态：编码器内部浮点结果差了最低位，四舍五入到不同的量化档，于是这一个块重编码，其余 184857 字节一模一样。

### 2.3 抖的是哪个视觉元素

该块在 sheet 的第 0 格（`tablet-page-01` 的第 1 帧 = fold 帧）里。按行统计差异分布：

```
y 352..359  每行 16 个差异（整块）
y 360..367  每行 4~8 个
y 416..423  每行 8 个
```

16 像素的横向周期 + 两段 8 行高 —— 对上 `prototypes/S17-revenue-stamp-stub/style.css:151`：

```css
/* 齿孔撕线：1.2px 孔径、6px 孔距的圆孔，不是虚线边框 */
.perf {
  background-image: url("data:image/svg+xml,...width='16' height='6'...
     <circle cx='8' cy='3' r='1.2' .../>
     <circle cx='8' cy='3' r='1.9' fill='none' stroke='%23CFC0A2' stroke-width='0.5'/>");
  background-repeat: repeat-y;
}
```

即**齿孔撕线的 SVG 点阵平铺**：16×6 的贴片、0.5px 描边圆、`repeat-y`。这个元素本身就是一个亚像素精度的矢量图案，被缩放到 512px 宽的格子里时，光栅化落在半像素边界上——这就是抖动来源。

### 2.4 归因实验：抖动发生在「合成」这一步，不在页面渲染

为了分清是「页面在抖」还是「JPEG 编码器在抖」，我做了 7 组受控实验（脚本与输出都在 `determinism/control-exp*.mjs` / `*-out.txt`）：

| 实验 | 做法 | 结果 | 说明 |
|---|---|---|---|
| exp1 | 同一次启动内连拍 8 帧，PNG + JPEG 双写 | PNG unique=1, JPEG unique=1 | **进程内完全确定** |
| exp2 | 跨 6 次独立 Chrome 启动，截 fold 帧 | PNG unique=1, JPEG unique=1 | fold 帧跨启动也确定（与 7 次渲染中 `tablet-fold.jpg` 全等一致） |
| exp3 | 直接复刻 `sheet()` 拼图，输入字节固定 | **JPEG unique=2**（217401 / 217474 字节） | **合成层抖** |
| exp4 | 同 exp3，改截 PNG 无损 | **PNG unique=2**（361072 / 361173） | 抖的是**栅格化结果**，不是编码器 |
| exp6 | 同 exp3，拍完等 1.5s 再拍一张 | 每次启动内 early==late，跨启动仍 unique=2 | **不是「没画完就截图」的竞态** |
| exp5 | 输入从 JPEG 换成同一张的 PNG | JPEG 输入 unique=1，PNG 输入 unique=2 | 与输入编码无关，排除 JPEG 解码 |
| exp7 | 输入换成纯色 PNG | **unique=1** | 合成管线本身确定 |

七组实验合起来给出唯一解释：**合成管线是确定的；把带有 `.perf` 亚像素点阵的图缩放并平铺时，Chrome 的光栅化在两个离散结果间摆动。** 原断言里「像素真的在抖」这半句成立，但抖的是**缩放光栅化**，不是页面布局，更不是时间戳。

> 补充：exp3 差异 bbox `x 88..239, y 352..423`，落在第 0/1/2 格的同一水平带上——与真实渲染里 41 像素的 bbox 同一条带。两次独立实验指向同一个视觉元素，不是巧合。

## 四、对「季度复刻验货」的影响与建议

### 4.1 截图比对不能用来做验收基准

在这种抖动下，任何「截图逐像素比对」的方案都必须先定义一个容差，而容差一旦放宽到能容忍这 41 个像素，就不再能抓到真正的问题：

- 抖动幅度：**41 / 2098176 像素（0.002%），每通道 ±1**，只在 1 个 8×8 块里。
- 真实要抓的缺陷（栏数错、字号错档、图片少一张、线宽变粗）动辄是整块布局位移或几十像素的差异。

要把抖动挡住，容差得放到「允许任意 1 个 DCT 块内 ±2 的通道差」——这个容差恰好也能放过「一张图片整体偏色 2 个色阶」「一条 0.5px 线变成 0.4px」这类真缺陷。**容差和信噪比是同一个旋钮，拧到能容忍抖动的位置，真缺陷也一起漏掉了。**

### 4.2 建议：验收基准改用 DOM 测量，截图只做人工目检

理由不是「截图不好」，而是两者的**失败模式不对等**：

| | 截图比对 | DOM 测量（report.json） |
|---|---|---|
| 本仓库实测稳定性 | 8 个文件里 1 个抖，1 字节 / 41 像素 | **810 键 0 漂移** |
| 容差需求 | 必须放宽到能吞掉抖动 | **可以取零容差精确比对** |
| 定位能力 | 只告诉你「第几帧不一样」 | 直接给出「哪个视口哪个字段从 X 变成 Y」 |
| 失败语义 | 抖动与真缺陷混在一起 | 每个字段独立，误报可归因 |

具体做法：

1. **验收判据 = `report.json` 去掉 `at` 后与基准逐字节全等。** 这个判据在本仓库已经实测可用：7 次渲染、810 键、0 漂移。零容差，不需要定。
2. **数值容差只在跨机器/跨 Chrome 版本时放宽**，且应按字段定，不按整体定。本机实测全部字段是整数或一位小数，跨环境建议 `|Δ| ≤ 0.5px`（字号、线宽、间距）与 `|Δ| ≤ 1`（计数类：栏数、图片数、字号档数）。**计数类字段不该有容差**——栏数从 2 变 3 不是「误差」，是错。
3. **补齐 3 个缺失字段。** 在 `probe.mjs` 里加 `columns`（从 `grid-template-columns` / `column-count` 解析有效栏数）、`axisWidth`（主轴内容宽度）、`lineWidths`（去重后的所有 `border-*-width` + 伪元素线宽集合）。**在这三项进 `report.json` 之前，「6 个可度量对账」只能兑现 3 个**，剩下的靠 `dna-clean.json` 的规格值自我印证——那是「设计说了什么」和「设计说了什么」对比，不是「设计说了什么」和「渲染出什么」对比。
4. **截图降级为人工目检材料**，并在 README 里写明「截图不保证字节可复现，原因是 `.perf` 一类亚像素 SVG 点阵的缩放光栅化」，避免下一个人重新踩一遍并得出反向结论。
5. **如果一定要留一条自动化的截图闸门**，判据应当是「解码后像素差 > 阈值的像素数」，不是「字节全等」。本仓库实测抖动上限是 41 像素 / 单通道 ±2，取「差异像素数 > 200 或单通道 > 8」为红，能挡住真缺陷又不会被抖动触发。

## 五、原测法的问题（明确指出）

### 5.1 结论要「部分成立」而不是「成立」：两次不够

原断言用「连渲染两次 → 比 sha」得出「不是字节级可复现」。但抖动是**间歇性**的。我第一批三次就跑出了「run1==run2、run3 不同」——如果只跑两次且恰好是 run1/run2，结论会翻成「可复现」。

从 7 次样本看，两个变体是 4:3 分布。两次渲染撞上同一边的概率约 `(4/7)² + (3/7)² ≈ 57%`。**用 57% 可靠性的实验去下一个二值结论，测法本身不稳。**

建议：至少跑 5 次，或者更好——直接跑 `report.json` 比对（一次就够，因为它在 7 次里零漂移）。

### 5.2 「差异只在 EXIF 时间戳」是错的方向

原断言写「如果差异只在 EXIF 的某个时间戳字段，那结论是渲染是确定性的」。这个文件**没有 EXIF 段**，差异在扫描数据里，是真实像素抖动。这个方向的猜测如果没被验证就写进结论，会把「合成层有亚像素抖动」误报成「渲染完全确定，只是元数据带时间」，从而放过一个真实存在的可复现性缺陷。

### 5.3 只查了 `tablet-page-01.jpg`，没查其余 7 张

原断言只报了 `tablet-page-01.jpg` 不同、`report.json` 相同。我补测了全部 8 张：**其余 7 张在 7 次渲染里字节全等**。这个补充很重要，因为它把问题范围精确锁定到「contact sheet 合成」，而不是「渲染器整体不确定」——两者的处置方式完全不同。

### 5.4 那个「12906 字节」对不上

原断言说 `report.json` 是 12906 字节。我实测 **20591 字节**（7 次全部 20591），去掉 `at` 后 20556 字节，紧凑序列化 13350 字节。三个数都跟 12906 对不上。可能原断言测的是别的原型、别的版本，或者记错了。这个数字不影响主结论，但说明原日志里至少有一个数是没核对的。
